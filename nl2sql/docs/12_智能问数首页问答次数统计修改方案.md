# 智能问数首页问答次数统计修改方案

> 状态：2026-11-12 代码实施与自动化测试完成，Claude 文档审核 1 轮、Kimi 代码审核 2 轮、Codex 最终审核 1 轮均通过，已发现问题已修复。真实后端联调仍待服务加载新代码，验收边界见 §8/§9。未提交 Git。
> 实施时按本文任务逐项验证；不自行扩大范围，不自动提交代码，不停止或重启用户管理的服务。

**目的（Goal）：** 在智能问数首页显示已登记问答的总体规模，数值是计入 `total_all` 的有效历史会话登记的 `turn_count` 缓存之和；缓存边界见 §2.1。页面把该数值放在「查询会话」的「总问答次数」中，见 §1.1。

**实现方式（Architecture）：** 复用会话登记中已有的 `turn_count`，在 `GET /api/v2/sessions` 既有的一次完整 Store 枚举中同步累加，新增全局响应字段 `total_turns_all`。前端沿用现有会话列表请求与加载状态，不新增接口、不逐会话读取问答明细、不修改数据库结构。

**技术范围（Tech Stack）：** 现有 Python 3.12、FastAPI、Pydantic、LangGraph Store、Vue 3、TypeScript 和 Node/Vue 现有工具链；不新增依赖。

**依据（Spec）：** 用户确认的“所有对话轮次中的一问一答次数求和”，以及 [doc 10](10_智能问数导航与会话首页设计方案.md) 的会话列表统计、筛选、分页和未知状态规则。本文实施后补充其中的统计字段契约。

## 1. 需求与研究结论

### 1.1 页面需求

首页顶部按 [ui/12](ui/12.智能问数.html) 显示两张统计卡：

- 「查询会话」：左侧「会话次数」是 `total_all`，表示有效 Web 会话数量，不是一问一答数量。右侧「总问答次数」是 `total_turns_all`。说明为「已启动的会话与累计问答次数」。未加载成功时两个数字都显示 —。
- 「分析统计」：历史分析尚未接入。「分析次数」和「总问答次数」都显示 —，说明为「全部分析与累计问答次数」。历史分析列显示「共 — 份分析」。不得把查询侧的 `total_turns_all` 填到分析侧。

例如两个计入统计的有效会话，其 `turn_count` 登记缓存分别为 3 和 2，则总问答次数为 `3 + 2 = 5`，不是会话数 `2`。

### 1.2 已核实的代码与数据事实

2026-11-12 已完成代码分析和 GET 接口核验。这里的“只读核验”指客户端不主动提交业务变更；`GET /api/v2/sessions` 仍可能按既有规则调度异步元数据校正，不能把它当作保证无写库副作用的探针：

- `SessionInfo` 已包含每个会话的 `turn_count`，会话列表条目已经返回该字段。
- 正常收尾分支在问答日志写入且回读有效后，将对应会话的 `turn_count` 加一。知识一致性复核未通过的安全摘要分支只写安全摘要轮并使会话失效，不在该分支即时增加；登记写入失败等异常也不保证即时增加。
- `WebStore.reconcile_metadata()` 会按有效问答日志条数校正 `turn_count`，但校正按需异步触发；坏记录、超限等写入前失败不覆盖旧缓存，登记写入异常时实际持久化结果可能未确认，以实际存储为准，不承诺必然保留旧值。因此 `turn_count` 是“校正成功后更新、校正未完成或退避时可能持续陈旧”的缓存值，不是每次列表请求都现场重算的日志行数，也不保证无条件最终收敛。
- 当时运行环境中的核验快照为：会话数 16、登记中的 `turn_count` 合计 21、实际保存的有效问答日志合计 21，不一致会话数为 0。该快照只证明当时二者一致，不排除其他时间或异常路径存在暂时差异。

上述 16/21 只是研究时的数据快照；代码、测试和页面不得硬编码这两个值。

## 2. 统计口径与边界

### 2.1 本次采用的口径

`total_turns_all` 等于本次列表读取中，所有计入 `total_all` 的有效 guest Web 会话的 `turn_count` 之和：

```text
total_turns_all = Σ 有效 guest Web 会话.turn_count
```

具体规则：

1. `total_turns_all` 是本次枚举中各有效会话登记的 `turn_count` 缓存之和，不是现场逐条重算 `web_turns` 的实时精确值；本次沿用现有缓存语义，不重新解释业务状态。
2. 正常收尾分支中，已保存的成功、失败或澄清答复在回读确认后增加 `turn_count`。安全摘要、登记写入失败等异常路径可能已保存日志但尚未增加缓存，仅在校正成功后更新；校正失败或退避时可能持续陈旧，不能承诺所有已保存答复都立即或最终必然计入。
3. 空会话贡献 0；执行前被拒绝、尚未保存或仍在执行的提问不计入。正常成功问答保存后，下一次读取可见增量；安全摘要和异常路径以校正成功后的缓存为准，不承诺保存后立即加一。
4. 失效但仍可完整构造 `SessionInfo` 的历史会话继续计入，与 `total_all` 保持一致。
5. 非 guest、非 Web、归属不符或展示字段损坏而被列表跳过的登记不计入，即使其命名空间中仍保留有效问答日志也不例外，避免问答总数与会话总数采用不同集合。
6. 继续使用现有异步元数据校正机制；本需求不把列表读取改成等待全量校正，也不增加额外写操作。列表只会为当前页条目及跳过的损坏登记按需安排校正，不在当前页且未校正的会话可能暂时保留旧缓存；坏记录、超限等写入前失败保留旧值，登记写入异常时结果可能未确认，以实际存储为准。
7. **已知限制：** 本统计不覆盖被列表排除的损坏/非归属登记，也不保证异常路径日志及时反映到缓存。若未来要求严格等于全部已保存日志的实时条数，当前方案不满足，应另行设计实时统计；不在本次低成本改造中隐式承诺。

### 2.2 筛选、分页与加载状态

- `total_turns_all` 是全局统计，与 `total_all` 一样不受 `source_id`、`q`、`limit`、`offset` 影响。
- 搜索或筛选只改变列表条目和 `total_filtered`。请求完成后，「查询会话」里的会话次数和总问答次数保持全局值；请求期间这两个数字按未知态显示 `—`。分析统计保持 `—`。
- 必须在筛选、排序和分页之前累加；不得只对当前页的 `items` 求和。
- 第一页加载、筛选变化或重置期间，`total_turns_all` 与现有两项数量一样先置为 `null`，页面显示 `—`；请求失败不得显示伪造的 0。
- 加载更多失败时保留已确认的统计值；过期响应不得覆盖新请求状态。

### 2.3 非本期范围

- 不增加“仅成功问答次数”或按状态拆分统计。
- 不增加按数据库、标题筛选后的问答次数字段。
- 不接入历史分析统计。
- 不新增统计接口、数据库表、缓存服务、定时任务、环境变量或灰度开关。
- 不重构现有元组返回、分页、搜索、校正或会话状态体系。

## 3. 接口契约

继续复用现有端点：

```http
GET /api/v2/sessions?source_id={optional}&q={optional}&limit={n}&offset={n}
```

仅在会话列表的 `data` 中增加一个必需的非负整数：

```json
{
  "items": [],
  "limit": 6,
  "offset": 0,
  "has_more": false,
  "next_offset": null,
  "total_all": 2,
  "total_filtered": 0,
  "total_turns_all": 5
}
```

字段定义：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `total_all` | `int` / `number` | 全部有效 Web 会话数 |
| `total_filtered` | `int` / `number` | 来源和标题筛选后的会话数 |
| `total_turns_all` | `int` / `number` | 全部有效 Web 会话登记的 `turn_count` 缓存之和 |

该字段只加入会话列表响应，不加入 `SessionInfo`、轮次分页或其他接口。前后端 DTO 使用显式字段，需在同一改动中同步；不利用任意 `dict` 静默传递。

`total_turns_all` 的非负性由 Store 的 `display_field_problems()` 不变量保证：只有每条 `turn_count` 均为非负整数的有效登记才进入求和。DTO 仅声明 `int`，不重复增加 `Field(ge=0)`；这与现有 `total_all`、`total_filtered` 的约束层次一致。

## 7. 审核重点与完成标准

实施和审核重点：

- 分页只返回少量 `items` 时，统计是否仍覆盖所有有效会话。
- 来源和标题筛选是否只影响列表与 `total_filtered`，不影响全局问答总数。
- 展示字段损坏的登记是否同时排除在会话总数和问答总数之外。
- 空会话、首次加载、请求失败和过期响应是否保持正确的 0/`—`/旧值边界。
- 是否复用现有 `turn_count`，而没有引入逐会话读取 `web_turns` 的 N+1 查询。

全部满足以下条件才算完成：

1. 后端响应和前端类型均包含 `total_turns_all`，语义与本文一致。
2. 「查询会话」中的总问答次数等于全部有效会话的 `turn_count` 之和；分析统计不显示该值。
3. 新增后端测试和 `sessionList.test.cjs` 关键状态用例全部通过，既有 API v2 回归无新增失败，前端类型检查和构建通过；过期响应、加载更多和越界页二次请求不得以未验收替代。
4. 浏览器验收已执行并记录；只有不影响核心状态逻辑的动态或服务相关项目可在未执行时明确标注，不能把未执行的自动化测试记为完成。
5. doc 10、根文档 doc 2 与本文状态已按实际结果同步。

本方案不改动问答执行与持久化链路，主要工作是一次后端累加、一个响应字段和一处前端展示，保持低开发成本。

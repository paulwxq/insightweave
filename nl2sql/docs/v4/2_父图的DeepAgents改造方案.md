# 父图的 Deep Agents 改造方案

创建日期：2026-10-14  
文档定位：整理当前父图改造的已达成共识，明确新增模块、能力复用及新旧实现对比方式。  
前置文档：[v4 改造目标与总体方向](1_v4改造目标与总体方向.md)。

## 1. 本阶段目标

使用 Deep Agents SDK 新增一个数据库查询与分析 Agent，接管当前父图承担的查询规划、步骤调度、结果反馈和回答组织职责。

本阶段采用新增实现与原实现并行的方式：开发新代码、封装已有能力，保持当前模块和原有运行逻辑可用，便于随时选择旧父图或新 Agent 进行对照测试。

数据库 Agent 首先能够独立使用，后续再作为主分析 Agent 的 subagent，承接数据库范围内的查询与分析任务。主分析 Agent 结合网络信息编写完整报告的能力，属于后续阶段。

## 2. 当前代码结构与调用边界

当前核心编排由一个 LangGraph 父图和一个 LangGraph SQL 生成子图组成。

| 模块 | 当前职责 | 代码位置 |
| --- | --- | --- |
| 父图 | 简单／复杂路由、查询拆分、依赖调度、SQL 执行及结果总结 | [graph.py](../../src/modules/nl2sql_father/graph.py) |
| SQL 生成子图 | 问题解析、Schema 检索、SQL 生成、三层校验及失败修复 | [create_subgraph.py](../../src/modules/sql_generation/subgraph/create_subgraph.py) |
| SQL 执行节点 | 从父图状态获取待执行 SQL，执行并回写结果 | [sql_execution.py](../../src/modules/nl2sql_father/nodes/sql_execution.py) |
| PostgreSQL 客户端 | 提供数据库查询等底层能力 | [pg_client.py](../../src/services/db/pg_client.py) |

父图通过 `sql_gen_wrapper` 或 `sql_gen_batch_wrapper` 调用 SQL 生成子图，并完成父图状态与子图输入输出的转换。SQL 实际执行发生在父图的执行节点中，SQL 生成子图负责返回验证通过的 SQL。

当前流程可以概括为：

- 简单路径：创建单个子查询 → 调用 SQL 子图 → 执行 SQL → 总结。
- 复杂路径：规划子查询及依赖 → 按依赖分批调用 SQL 子图 → 执行 SQL → 检查是否继续 → 总结。

## 3. 改造顺序：优先改造父图层

先以 Deep Agent 承担父图层的编排职责，复用现有 SQL 生成子图。

这一顺序直接对应当前目标：让 Agent 自主决定需要查什么、查询多少步，以及看到结果后是否继续查询。已有子图中的 Schema 检索、SQL 生成、验证和修复能力，可以继续为新 Agent 提供支持。

本阶段的“改造父图”指新增一套能够承担相同业务入口职责的 Deep Agent 实现。原父图继续保留，不直接在其代码中重写编排或切换默认路径。

| 当前父图职责 | 新实现中的承担方式 |
| --- | --- |
| Router 与 Simple Planner | Agent 统一接收问题，自主决定查询步骤 |
| 一次性 Planner | Agent 根据任务与工具结果持续规划 |
| 参数注入及依赖推进 | Agent 将前一步的必要结果提供给后续查询工具 |
| 完成度检查 | Agent 判断数据任务是否完成，代码执行运行预算等约束 |
| SQL 生成调用 | `generate_sql` 工具封装现有 SQL 子图 |
| SQL 执行 | `execute_sql` 工具封装现有底层执行能力 |
| Summarizer | Agent 根据真实查询结果组织回答与分析发现 |

该表描述新实现如何承担职责，原父图节点在对照测试阶段继续按原方式运行。

## 4. 新增模块命名与路径

新模块统一命名为 **`db_deepagent`**，路径为：

`src/modules/db_deepagent/`

名称明确其数据库职责及 Deep Agents SDK 技术实现，与现有固定编排模块区分。代码模块名不携带版本号；v4 规划文档统一存放在 `docs/v4/`。

以下为建议的内部目录组织，具体文件划分可在实现设计中细化：

```text
src/modules/db_deepagent/
├── __init__.py
├── agent.py                 # 使用 create_deep_agent 创建数据库 Agent
├── tools/
│   ├── __init__.py
│   ├── generate_sql.py      # 封装现有 SQL 生成子图
│   └── execute_sql.py       # 封装现有底层 SQL 执行能力
└── skills/                  # 查询规划与数据库分析 Skill
```

已有模块 `src/modules/nl2sql_father/` 和 `src/modules/sql_generation/` 继续保留。新模块通过明确的接口调用已有能力。

## 5. 使用一个 Deep Agent 统一规划

新数据库 Agent 使用 `create_deep_agent` 构建，通过系统指令、Skill 和工具执行数据库查询与分析任务。

新流程统一接收数据需求，不再设置简单／复杂问题的前置分类和两条业务路径：

`接收任务 → 决定本次查询 → generate_sql → execute_sql → 查看结果 → 继续查询或形成回答`

该过程允许根据真实结果调整查询方向：

- 一次查询足够时，完成一轮生成和执行后返回结果。
- 后续查询依赖前一步结果时，获得必要结果后再安排下一步。
- 结果暴露数据缺口、异常或原方案不足时，补充查询或修订方案。
- 工具返回失败时，根据失败原因决定调整查询、重新尝试或结束，并说明未完成部分。

拆分规则强调优先使用一条合理 SQL 完成数据库能够直接处理的工作。JOIN、CTE、子查询、同比和环比等结构本身不要求拆成多个工具调用；确有结果依赖或分析需要时再安排多步查询。

SQL 子图自身负责 SQL 级别的生成修复，数据库 Agent 负责更上层的查询需求和分析方向，减少两个层级重复处理相同问题。

## 6. 两个独立的核心业务工具

### 6.1 generate_sql：生成并验证 SQL

`generate_sql` 接收本次查询需求及必要上下文，调用现有 `run_sql_generation_subgraph`，并将输出转换为适合 Agent 使用的工具结果。

继续复用子图内部能力：

- 问题解析与改写。
- Schema、维度值、JOIN 路径及历史 SQL 案例检索。
- SQL 生成。
- 三层校验和限次修复。

工具成功时返回验证通过的 SQL 及必要元信息，失败时返回明确的失败类型和原因。工具本身不执行 SQL。

### 6.2 execute_sql：执行 SQL 并返回真实数据

`execute_sql` 接收 SQL，调用已有底层数据库执行能力，返回执行状态、列信息、结果数据、耗时及必要错误信息。

现有代码中的 SQL 执行能力主要由父图节点和底层 `PGClient` 提供，尚需封装成 Deep Agent 可以调用的独立工具。

新增的 `execute_sql` 封装可以调用已有 `PGClient.execute_query` 等能力，并在新模块中完成参数与结果适配。它不经过原父图，也不要求先修改原来的 SQL 执行节点。

### 6.3 两个工具分别注册

SQL 生成和 SQL 执行继续保持为两个独立业务工具，分别注册给数据库 Deep Agent。执行结果回到 Agent 后，由 Agent 判断下一步行动。

本阶段不将两者合并成一个生成后自动执行的查询工具。后续若需要增加数据目录、指标说明或计算分析能力，再另行设计；框架提供的 Skill 读取等工具不影响这两个核心业务工具的分工。

## 7. SQL 校验与生成执行交接

三层校验继续保留在 SQL 生成子图内部，与失败反馈和重新生成构成闭环。暂不单独开放校验工具，由子图完成 SQL 级别的修复。

`generate_sql` 可以直接返回 SQL，`execute_sql` 接收 SQL。当前没有强制引入 `validated_sql_id` 或为了工具交接专门保存 SQL 到数据库的要求。

执行工具不重复完整的三层校验，但需要通过代码确认实际执行的 SQL 与验证通过的 SQL 相对应，避免模型转交时修改 SQL 后仍将其视为已验证内容。

当前运行中记录验证通过的 SQL，并在执行前进行一致性确认，是已讨论的可选实现方式。具体交接接口留待工具设计文档细化。

## 8. Skill 与运行约束

Skill 用于指导查询规划和数据库分析，例如：

- 如何识别指标、维度、时间范围及比较口径。
- 什么时候可以一次查询完成，什么时候需要依赖结果继续查询。
- 如何检查缺失、空结果和异常，避免使用错误口径解释数据。
- 什么时候继续查询，什么时候已有证据足够形成回答。

系统指令提供基础职责和工具调用规则，Skill 补充具体方法与领域知识。实际执行限制、验证交接、超时和运行预算由代码保障。

## 9. 保留原逻辑与对照测试

开发以新增模块、工具封装和独立测试入口为主。原有父图、SQL 子图及原有运行入口继续可用，选择旧实现时仍走原调用链。

新 Deep Agent 使用独立入口，不在首轮改造中自动替换旧入口。具体 CLI、配置或测试程序的选择方式在后续实现设计中确定，要求能够明确选择两种实现并保存各自结果。

对同一组问题，比较以下方面：

| 对比项 | 检查重点 |
| --- | --- |
| 结果正确性 | SQL 和答案是否符合问题及业务口径 |
| 查询规划 | 是否合理使用一次或多次查询，是否正确使用前一步结果 |
| 分析能力 | 是否能根据查询发现补充检查，并说明证据不足 |
| 失败处理 | 生成失败、执行失败及空结果是否被正确处理 |
| 可追溯性 | 回答是否能够关联实际 SQL、查询结果和采用的口径 |
| 效率与成本 | 总耗时、模型调用次数、工具调用次数及 Token 消耗 |

对照任务至少覆盖一次查询、依赖查询、验证失败、执行失败和空结果。使用相同的数据条件与业务口径，记录模型及配置差异，避免将环境差异误判为编排方式的差异。

依赖调整如有需要，应验证新旧实现的兼容性，确保原入口仍能运行。新 Agent 达到预期效果后，再单独讨论正式入口的切换。

## 10. 本阶段实施顺序与完成标准

建议实施顺序：

1. 在 `src/modules/db_deepagent/` 中封装 `generate_sql`，复用现有 SQL 子图。
2. 封装独立的 `execute_sql`，复用底层数据库执行能力，并明确验证与执行交接。
3. 使用 `create_deep_agent` 创建数据库 Agent，注册两个工具并配置查询 Skill。
4. 新增独立运行与对照测试入口，使用代表性问题验证查询闭环。
5. 根据对照结果完善规划、工具反馈及分析能力。

本阶段完成后，应具备一个可以独立使用的数据库查询与分析 Deep Agent：能够统一处理一次查询和多步查询，根据执行结果继续行动，并返回真实数据、分析发现及查询依据。原有父图仍可按原方式运行，便于持续对照。

后续将该模块接入主分析 Agent 作为 subagent 时，沿用其数据库查询与分析职责，并细化任务输入与结构化输出协议。

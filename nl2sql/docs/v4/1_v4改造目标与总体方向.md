# v4 改造目标与总体方向

创建日期：2026-10-14  
文档定位：记录 v4 的目标、范围和已达成共识的架构方向，为后续详细设计提供依据。  
状态：目标与方向已确认；具体接口、状态结构、模型及依赖版本将在后续文档中细化。

## 1. v4 的最终目标

v4 的最终目标是构建一个具备深度分析能力的 Agent。它能够根据用户输入的一段需求，或者持续多轮对话中逐步明确的需求，开展研究、获取证据、分析数据，并为用户编写一份分析报告。

v4 分析报告的主要证据来源为：

- **数据库查询结果**：业务指标、趋势、分布、比较结果及必要的明细数据。
- **网络搜索及网页内容**：公开统计、行业背景、相关事件和其他可核验的外部信息。

v5 可以进一步考虑接入面向业务文档和知识库的 RAG。该能力不纳入 v4 的交付范围。

这里的“深度分析”体现为能够根据已有证据决定下一步行动：提出假设、分解问题、补充查询、寻找外部资料、核对口径、修订判断，并说明结论成立的条件。分析能力需要模型、工具、业务知识、Skill 和评估共同支撑，不能仅靠更换 Agent 创建函数获得。

## 2. 当前项目与改造起点

当前项目以 LangGraph 状态图组织 NL2SQL 流程，主要由父图和 SQL 生成子图组成。

| 当前模块 | 当前职责 |
| --- | --- |
| 父图 Router | 判断问题进入简单路径还是复杂路径 |
| Simple Planner | 为简单路径创建单个子查询 |
| Planner | 一次性生成复杂问题的子查询及依赖关系 |
| 参数注入与完成度检查 | 按依赖关系推进查询批次，管理完成状态和轮次 |
| SQL 生成子图 | 问题解析、Schema 检索、SQL 生成、三层校验及内部修复 |
| SQL 执行节点 | 执行验证通过的 SQL，记录查询结果和错误 |
| Summarizer | 根据执行结果或失败信息生成最终回复 |

当前 SQL 生成子图的主流程为：

`问题解析 → Schema 检索 → SQL 生成 → 三层校验 → 成功返回，或在限次内重新生成`

父图的复杂路径在规划后按依赖推进，尚未形成根据查询发现主动调整研究方向的分析闭环。v4 将从这一层开展改造，复用已有的数据访问和 SQL 专业能力。

## 3. 实施顺序：先构建数据库查询与分析 Agent

v4 的近期实施重点，是将当前项目改造为一个专门的**数据库查询与分析 Agent**。它能够独立接受用户需求并完成数据库范围内的查询和分析，将来再作为主分析 Agent 的 subagent 使用。

先完成数据库 Agent，是实现 v4 最终报告能力的第一阶段。数据库 Agent 完成后，继续构建主分析 Agent、网络证据获取和报告输出能力，才能达到 v4 的最终目标。

| 层级 | 核心职责 | 交付定位 |
| --- | --- | --- |
| 数据库查询与分析 Agent | 理解数据需求、获取数据、开展数据库范围内的分析、返回证据 | 近期优先实现，可独立使用 |
| 主分析 Agent | 制定研究计划，结合数据库发现与网络信息，形成综合判断和报告 | v4 最终目标 |

数据库 Agent 应从一开始就提供清晰的任务输入与结果输出，支持直接调用和被主 Agent 委派两种方式。内部查询细节不应成为主 Agent 必须理解的接口要求。

## 4. 数据库查询与分析 Agent 的职责

数据库 Agent 应具备以下能力：

1. 理解用户的数据需求，识别时间范围、指标、维度、过滤条件和比较基准。
2. 理解可访问的数据目录、表结构、指标口径、单位及数据粒度。
3. 自主判断一次查询是否足够，必要时安排多次查询及其依赖关系。
4. 调用现有 SQL 生成子图和 SQL 执行工具，获取真实数据。
5. 根据执行结果、数据缺口或错误，决定补充查询、调整方案或结束任务。
6. 完成数据库范围内的趋势、比较、分布、异常检查及必要计算。
7. 返回数据、分析发现、查询依据、使用口径及限制，供用户或主 Agent 继续使用。

例如，接到“分析今年销售额下降的服务区”后，它可以先查询总体变化，再检查区域、月份、品类等维度，并根据已有数据进一步核对客流和客单价变化。发现异常后，应检查数据缺失、时间覆盖和聚合口径，再给出分析发现。

数据库 Agent 的 Skill 应包含业务查询方法、指标口径和数据分析步骤。主分析 Agent 的 Skill 则侧重研究规划、外部证据核对和报告写作。两个层级分别配置适合自身任务的 Skill。

## 5. 使用 Deep Agents 的改造方向

### 5.1 技术选择

优先以 `create_deep_agent` 构建数据库查询与分析 Agent，通过工具和 Skill 支持自主规划、查询及结果反馈。

Deep Agents 基于 LangChain 的 Agent 能力，并使用 LangGraph 运行时。现有子图仍然具有复用价值，可以与新的 Agent 编排方式共同使用。[官方概览](https://docs.langchain.com/oss/python/deepagents/overview)

实施时评估当时可用的稳定版本及兼容性，确定 Deep Agents、LangChain、LangGraph 和模型集成的版本组合，并通过项目锁文件固定。具体版本选择属于后续技术方案，本篇不预先指定。

### 5.2 统一处理问题，不再预先分为简单路径和复杂路径

数据库 Agent 统一接收数据需求，决定需要执行多少步。取消当前父图中预先进行简单／复杂分类并进入两套路径的设计。

- 一步可以完成的问题，直接完成一次生成与执行。
- 后续查询依赖前一步结果时，读取结果后继续安排查询。
- 新结果显示原有方案不足时，调整计划或补充查询。

拆分规则应强调：优先使用一条合理的 SQL 完成数据库能够直接处理的工作。JOIN、CTE、子查询、同比或环比等结构本身不构成必须拆分的理由。是否拆分取决于数据依赖、结果反馈和分析需要。

### 5.3 保留 SQL 生成子图

现有 SQL 生成子图已经积累了问题解析、表列检索、维度值匹配、JOIN 路径规划、历史 SQL 案例、三层校验和修复能力，应优先作为数据库 Agent 的内部工具复用。

Agent 决定“这一步需要获取什么数据”；SQL 子图将该需求转换为经过验证的 SQL。查询结果返回后，Agent 再决定下一步行动。

当前父图的 Router、一次性 Planner、参数注入和完成度检查等职责，逐步由新的 Agent 循环和相应运行约束承接。具体替换顺序及可复用代码在后续设计中确定。

### 5.4 两个核心业务工具

数据库 Agent 的两个核心业务工具暂定为：

| 工具 | 输入与职责 | 输出 |
| --- | --- | --- |
| `generate_sql` | 接收本次查询需求及必要上下文，调用 SQL 生成子图 | 验证通过的 SQL，或结构化失败信息 |
| `execute_sql` | 接收 SQL，执行符合验证与执行约束的查询 | 列信息、真实数据、执行状态及必要元信息 |

工具名称和参数属于初步约定。后续可以增加数据目录、指标说明、结果读取和计算分析等能力；读取 Skill 等框架工具也会存在。

SQL 可以直接由生成工具返回，再传给执行工具。当前没有为了这一交接而强制引入 `validated_sql_id` 或专门数据库存储的要求。

### 5.5 校验继续保留在 SQL 子图内部

现阶段保留 SQL 子图的三层校验和失败修复循环，暂不将校验单独暴露为主 Agent 的第三个业务工具。它能让一次工具调用完成“生成—验证—修复”，使数据库 Agent 专注查询和分析步骤。

执行工具不应机械地重复完整的三层校验，但必须由代码保证实际执行的 SQL 符合验证与执行约束。需要防止模型转交时修改 SQL 后仍被当作已验证内容执行。

具体交接机制在后续工具设计文档中确定，例如将验证通过的 SQL 保存在当前运行的共享上下文中，执行前确认其一致性。该上下文需要显式实现；是否需要持久化取决于跨请求、跨进程和恢复执行需求。

如果将来需要接收用户提供的 SQL，或者让 Agent 自主主导 SQL 修复，再评估独立的校验工具。

### 5.6 Skill 与代码约束的分工

Skill 适合表达拆分原则、业务知识、分析步骤和工具使用方法，Deep Agents 支持按需加载这些说明。[官方 Skills 文档](https://docs.langchain.com/oss/python/deepagents/skills)

必须每次遵守的基础规则应放在系统指令和工具实现中，不能只依赖 Agent 是否选择读取某个 Skill。执行权限、校验结果关联、查询超时、工具调用预算和结果大小等约束由代码保障。

## 6. 将数据库 Agent 作为 subagent

数据库 Agent 独立运行成熟后，接入主分析 Agent，承担专门的数据任务。

主分析 Agent 负责研究问题、判断证据缺口、决定要获取哪些内部数据及外部资料，并据此完成综合分析。数据库 Agent 负责把一次委派的数据任务完成，包括必要的多次查询和数据库范围内的分析。

例如，主 Agent 委派“获取今年及去年同期各服务区按月销售额、客流量和客单价，并检查数据缺失”。数据库 Agent 完成任务后，主 Agent 根据发现决定是否研究某个区域的交通变化，或再次委派更具体的数据任务。

这种分工将 Schema、候选表、SQL 生成重试和执行细节保留在数据库 Agent 内，减少主 Agent 上下文中的中间信息。Deep Agents 支持专门的 subagent 及结构化输出，适合这一交接模式。[官方 Subagents 文档](https://docs.langchain.com/oss/python/deepagents/subagents)

委派时必须明确任务范围、口径和相关上下文。结果应以结构化形式返回，至少包含以下内容：

| 返回内容 | 用途 |
| --- | --- |
| 数据与列信息 | 让主 Agent 继续计算、比较和绘图 |
| 数据文件或其他可读取的完整结果引用 | 承载较大结果，避免全部塞入模型上下文 |
| 时间范围、过滤条件、单位、粒度和指标口径 | 支持正确解释与复核 |
| 实际执行的 SQL 和查询记录 | 追溯结论使用的数据依据 |
| 分析发现 | 传递数据库范围内已经确认的结果 |
| 缺失、截断、警告和未完成事项 | 防止主 Agent 将不完整数据当作完整证据 |

原始查询数据应由执行工具和结果存储保留，结构化返回中的数据引用应指向真实结果。不能只依赖 subagent 用自然语言重新描述数据。

## 7. 主分析 Agent 与分析报告能力

主分析 Agent 在数据库 Agent 的基础上增加网络搜索、网页正文读取、计算绘图和报告输出等能力。最终工作过程可以是：

`理解需求 → 制定研究计划 → 获取数据库及网络证据 → 分析与核对 → 发现缺口并补充研究 → 编写报告`

这是一种可迭代的工作方式，具体行动顺序由任务和证据决定。

多轮对话应支持逐步补充研究范围、修订指标口径、追加问题和更新报告。需要维护当前任务的研究目标、已确认口径、证据引用和待解决问题，避免只保留零散的历史消息。

最终报告应能够追溯数据库查询依据和网络来源。对于网络资料，应保留链接、发布时间或适用时期及必要的获取信息。报告应区分数据事实、推断和待验证假设；外部事件与数据变化同时发生，不能直接认定存在因果关系。

具体报告格式、图表能力、证据保存方式和多轮状态设计将在后续文档中确定。

## 8. v4 与 v5 的范围边界

| 范围 | v4 方向 |
| --- | --- |
| 可独立使用的数据库查询与分析 Agent | 优先实现 |
| 根据查询结果动态规划及补充查询 | 核心能力 |
| 主分析 Agent、网络证据和分析报告 | 最终交付目标 |
| 单轮需求与持续多轮对话 | 支持 |
| 现有 Schema、维度值、JOIN 路径和历史 SQL 检索 | 继续复用并按需优化 |
| 新增面向业务文档、企业知识库的 RAG | 留到 v5 评估 |

“v4 不新增业务知识 RAG”不影响当前 SQL 链路中的 Milvus／pgvector Schema 检索、历史 SQL 检索及 Neo4j JOIN 规划，这些是现有数据库访问能力的组成部分。

## 9. 阶段性完成标准

数据库 Agent 阶段应验证：

- 同一入口能够处理一次查询和需要依赖结果的多次查询。
- 能根据真实结果补充查询或调整方案，并在失败时返回明确状态。
- 能解释使用的数据口径，返回可追溯的数据和 SQL 依据。
- 可以独立使用，也具备被主 Agent 委派任务的输入输出边界。

v4 最终阶段应验证：

- 能根据单轮或多轮需求，完成数据库证据与网络证据结合的分析报告。
- 报告中的关键数据、计算和外部事实可以核验，限制与不确定性有明确说明。
- 在代表性业务任务上评估结果正确性、研究完整性、延迟、调用次数和成本。

评估需要覆盖一步查询、依赖查询、异常调查、数据缺失及包含外部资料的报告任务，不能仅以 SQL 成功执行或报告篇幅作为完成标准。

## 10. 后续规划文档

后续规划统一存放在 `docs/v4/`，优先细化以下事项：

1. 数据库 Agent 的运行循环、工具边界和 Skill 组织。
2. SQL 子图复用方式、生成与执行交接及错误反馈。
3. 数据目录、指标口径、结果存储和分析计算能力。
4. 会话状态、多轮对话及 subagent 任务交接协议。
5. 模型与依赖版本评估、迁移步骤及代表性任务验证。
6. 主分析 Agent、网络证据获取与报告生成方案。

本篇确认目标和方向，后续设计应围绕这些目标展开，并通过实际任务验证关键技术选择。

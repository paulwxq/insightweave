# 默认工具调用修补中间件装配精简方案

> 状态：**已实施，代码审核与收尾复核通过（2026-11-11）**，实施记录见文末。以下为实施前设计（含两轮设计审核修订），保留原文。

**目的（Goal）：** 删除项目无定制的 `PatchToolCallsMiddleware` 显式覆盖，由 SDK 默认实例继续修补历史中缺少工具结果的调用。

**实现方式（Architecture）：** 仅精简 `build_db_agent()` 的中间件参数；通过生产装配的离线图验证删除前后行为等价。

**技术基线（Tech Stack）：** DeepAgents 0.7.34、LangChain 1.4.9、LangGraph 1.2.20；不升级依赖。

**依据（Spec）：** [doc 4 §3.1](4_DeepAgents实现简化与旧链保留价值分析.md)。本方案针对装配冗余，不增加工具修补能力。

## 1. 已核实的依据与范围

- 当前 `agent.py` 显式传入 `PatchToolCallsMiddleware()`，没有定制参数或子类。
- 安装版 `deepagents/graph.py` 的主 Agent 默认栈已创建该中间件；`_apply_custom_middleware()` 按名称原位替换。因此当前只有一个生效实例，删除显式覆盖后应继续只有一个 SDK 默认实例。
- 显式实例占据的是**默认栈槽位**，并非用户 `middleware` 列表中的位置。同名替换保留原槽位；在当前 SDK 和 Harness 配置下，删除前后有效栈的中间件类型/名称及顺序一致，`extra_mw` 的相对位置不变，不因删除而重排用户列表。
- 已接入的 `summary_mw` 同样替换默认栈中 `create_summarization_middleware(model, backend)` 创建的同名实例；doc 5/5.1 的装配和摘要测试已使用该机制。它是既有生产依赖，本次不改变摘要器路径；其验证可作为佐证，不能替代本方案的修补行为测试。
- 默认实例需保持未被 `HarnessProfile.excluded_middleware` 排除。`PatchToolCallsMiddleware` 不在 SDK 强制保留清单中；当前项目注册的 profile 仅禁用通用子 Agent，排除集合为空。未来更改 profile 时须保留该中间件。此约束**也适用于当前显式实例**：SDK 在自定义合并前后均执行排除过滤，显式传入不能抵消最终排除规则，不将它称为删除后唯一新增的依赖点。
- 修补发生在 `before_agent`，即每次图调用开始时：对缺少结果且具有调用 ID 的历史工具调用补一条 `ToolMessage(status="error")`；已有结果的调用不重复补齐。该机制不重试原工具、不重新执行 SQL。
- 项目未上线，直接删除冗余代码；不新增兼容开关、回退路径或历史数据迁移。
- 文件中间件、独立 Flash 摘要器、预算/审计/最终答案门控保留；权限、工具集、配置值、Runner、持久化结构、UI/API 和旧 LangGraph 链路保持原样。

SDK 核对位置为 `nl2sql/.venv/lib/python3.12/site-packages/` 下的：

- `deepagents/graph.py`：默认主栈与同名替换规则。
- `deepagents/middleware/patch_tool_calls.py`：`before_agent()` 的修补行为。

不修改 SDK 源码，不新增 SDK 私有接口适配。

### 步骤 1：补充并运行行为基线测试

**新增：** `src/tests/db_deepagent/unit/test_default_tool_call_patch.py`。

为每个用例准备独立会话/线程和运行上下文：

1. 创建 `DbAgentContext`，设置本用例的 session/thread/request/run ID，以及有效的时钟、指纹、数据源和未过期 deadline；不要直接使用 `db_agent_context` 中已经过期的 `deadline_monotonic=0`。
2. 用 `limits_from_config()` 与 `services.budget.open_run()` 注册预算，再调用生产图；传入 `metadata.dbda_call_kind="agent"`。
3. 假模型响应最终答案提醒后再返回普通文本，使图正常结束；不伪造 SQL 证据、不要求业务状态 `completed`。
4. 用例结束关闭对应预算；不调用真实模型、真实数据库或 PostgreSQL Store。

历史消息使用独立消息 ID 和工具调用 ID；在历史 AI 工具调用之后追加一条新的 `HumanMessage` 作为本轮请求，避免把旧工具调用当作待执行的新任务。

SDK 修补更新采用 `RemoveMessage(id=REMOVE_ALL_MESSAGES)` 加重建后的完整消息列表，由图的消息通道应用。历史保留断言比较消息 ID、内容、工具调用 ID、name 和 status，不比较 Python 对象身份；在模型实际收到的消息及最终图状态上核对，不将删除哨兵本身当作模型消息。

| 用例 | 输入历史 | 必须断言 |
| --- | --- | --- |
| `test_completed_tool_history_is_preserved` | Human → AI 调用 `inspect_tables(id=call-done)` → 已有 ToolMessage → 新 Human；对 success/error 两种 status 参数化 | 第一次模型输入中，原结果内容/status/调用 ID 保留且仅一条，无新增修补结果 |
| `test_missing_tool_result_is_patched_once` | Human → AI 调用 `inspect_tables(id=call-missing)`，无 ToolMessage → 新 Human | 第一次模型输入前已出现且只出现一条对应 `call-missing` 的错误 ToolMessage，name 正确、content 非空；原历史 AI/Human 消息保留 |
| `test_partial_tool_history_only_patches_missing_result` | 一条 AI 含两个调用，只有其中一个已有结果 → 新 Human | 两个 ID 各有一个结果；已有结果内容/status 原样，缺失项补为 error；不重复已有结果 |
| `test_invalid_tool_call_history_gets_error_result` | AI 的 `invalid_tool_calls` 含带 ID 的畸形 JSON 参数 → 新 Human | 第一次模型输入中该 ID 获得 error 结果，name 正确；不把它当成功，也不执行该调用 |

畸形调用按当前 langchain-core 的形态构造，`args` 为字符串而非字典，例如：

```python
from langchain_core.messages import AIMessage

invalid_history = AIMessage(
    id="msg-invalid",
    content="",
    invalid_tool_calls=[{
        "name": "inspect_tables",
        "args": '{"table_ids": [',
        "id": "call-invalid",
        "error": "invalid JSON (test)",
    }],
)
```

本机 `AIMessage` 会补齐 `type="invalid_tool_call"`；`error` 可省略并规范化为 `None`，示例显式填写以说明测试意图。先确认消息构造成功，再运行生产图，避免将假件校验错误算作修补行为失败。

在缺失结果用例中，再用**同一内存检查点和 thread_id**、新的 request/run ID 调用一次：

- [x] 第二次模型输入中 `call-missing` 仍只有原来那一条错误结果，没有再次补齐；首次修补结果可从最终图状态读取。
- [x] 两轮均不重新执行历史工具：工具预算计数为 0，假业务库查询计数不增长。

可在测试内对 `PatchToolCallsMiddleware.before_agent` 加薄包装，计数后调用原方法，确认每次新图调用只执行一次修补钩子。不要替换成返回假结果的实现，不通过继承改名影响同名替换规则，不断言完整英文错误文案。

## 4. 验收与审核重点

1. **SDK 默认职责保留：** 没有显式覆盖后，生产图仍在模型调用前补齐缺失结果；每次 invoke 修补钩子只执行一次。

3. **错误语义正确：** 缺失或畸形调用补为 error，不伪装成成功，不重新执行历史工具。
4. **检查点行为保留：** 同一内存检查点再次 invoke 不重复插入修补消息；不把它扩展表述为全套中断恢复已验收。

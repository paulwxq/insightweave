## 0. 结论摘要

**T01–T09 里只有 Q38F 全部通过。T10 分两层看：七个模型的直调与端点流式开关都通过，但 T10 里“残缺工具参数不能触发执行”是项目共用路径上的公共子项，第 2 轮离线对照判不通过，对七个模型同样成立。** 按角色看，七个模型都至少能承担一个角色。

| 模型 | 一句话结论 |
| --- | --- |
| Q38F `qwen3.8-flash` | T01–T09 通过，T10 的直调与端点流式开关通过。关闭思考有效，主 Agent（合成后端）、摘要、日期解析三个角色在关闭模式下都通过，是现有路径的回归基线。 |
| Q4M `qwen4-max` | 关闭思考有效（文档写法 `reasoning_effort: none`），主 Agent 与摘要通过；**日期解析不通过**：关闭模式下配合 `json_object` 输出 JSON 数组、伪工具调用或 thinking 块（工厂 1/6、直调 2/6）。工厂无法表达 `reasoning_effort`。 |

**T10 的项目级缺口对七个模型都成立**：工具参数在流式传输中残缺时，SDK 会把它解析成“参数为空对象的合法调用”。对必填参数的工具，必填校验能拦住；对参数可全省略的工具，函数体会按默认参数真正执行（§7.2）。这发生在客户端一侧（SDK 与工具节点），离线对照即可判定。角色结论不受影响，因为本轮所有角色都用非流式请求（§4.10）。

### 三层结论

“端点可用”“ChatOpenAI 可用”“NL2SQL 角色可用”按 Doc 24 §5 分列。角色列只统计真实角色用例，不以 T01 或单条 JSON 请求替代。

| 模型 | 端点可用 | ChatOpenAI 可用 | NL2SQL 角色可用 |
| --- | --- | --- | --- |
| Q38F | 是 | 是 | 严格关闭：主 Agent、摘要、日期解析 **均通过** |
| Q4M | 是 | 是 | 严格关闭：主 Agent、摘要通过；日期解析 **不通过** |
| G54 | 是 | 是 | 思考开启：主 Agent、摘要、日期解析通过；严格关闭不通过 |
| G53 | 是 | 是 | 思考开启：主 Agent、摘要、日期解析通过；严格关闭不通过 |
| G53F | 是 | 是 | 思考开启：主 Agent、摘要、日期解析通过；严格关闭不通过 |
| K31-C | 是 | 是 | 思考开启（须去掉 `temperature: 0`）：主 Agent、摘要通过；日期解析 **不通过**；严格关闭无法判定 |

“主 Agent 通过”的范围是合成数据加隔离运行状态（见 §1.5），**没有在真实业务库、向量库和平台库上执行完整问数**，这一项按阻塞记录（§10 B-01）。角色结论基于非流式请求，T10 的项目级断流保护缺口不改变上表（§4.10）。

### 跨模型的主要发现

1. **输出上限字段**：`ChatOpenAI(max_tokens=…)` 在出线时变成 `max_completion_tokens`。百炼与 Kimi 采纳该字段；DeepSeek 官方 API 和智谱 Coding Plan 三个模型**忽略**它（上限 64 时实际输出 660–1863 token，`finish_reason` 仍是 `stop`）。改用 `extra_body={"max_tokens": N}` 后四个端点都生效。现有工厂的 `max_tokens` 覆盖对 DeepSeek 与 GLM 无效。
2. **推理字段的保存与回传**：当前 `ChatOpenAI` 既不保存也不回传 `reasoning_content`。在不回传的条件下，本次合成场景的思考开启工具往返仍然完成，七个端点都没有返回文档所述的 400；“端点不强制回传”只限于本次场景，更复杂的工具链没有验证。Kimi 不回传时中间工具步的推理为空。
3. **Kimi 的两处限制**：思考模式只接受 `temperature: 1`，关闭后的无思考模式只接受 `0.6`，与项目三类角色配置里的 `temperature: 0` 冲突；流式请求默认不返回用量，需显式 `stream_usage=True`。
4. **工厂待适配**：`reasoning_effort` 不在白名单；`thinking` 只允许 `deepseek` provider，GLM 与 Kimi 无法经工厂控制思考。
5. **项目级断流保护不通过**（离线发现，§7.2）：流式中途断流的残缺工具参数会被解析成“参数为空对象的合法调用”。必填参数的工具靠校验拦住；参数可全省略的工具，函数体会按默认参数真正执行。另一个离线发现是 `extract_llm_content()` 在响应正文是内容块数组时抛 `AttributeError`。

### 1.6 工厂的装配边界

工厂用例**没有修改**磁盘上的 `config.yaml` 或 `.env`。做法是在探针进程内，向已加载的配置单例登记临时 provider（`doc24_<模型>`，含 `base_url` 与密钥引用）和临时 profile（`doc24_main_*`、`doc24_summary_*`、`doc24_time_*`），之后完全走项目的 `get_llm`。因此结论只说明“现有工厂代码能否构造并发出对应请求”，不代表线上配置已经或应当这样改。

### 1.7 判定口径

- 状态用词：通过、不通过、无法判定、阻塞、不适用。
- **关闭思考**按 Doc 24 §2 的表判定。关闭组的“开关是否有效”与“正文是否可用”分开记录：关闭组答错多步计算题不算关闭失败，单独列为文本可用性观察。
- **参考子项**（采样参数的实际效果、调用点未使用的强制工具选择等）记录结果但不计入用例总评；Doc 24 所列“接受且生效 / 接受但忽略 / 拒绝 / 未验证”按参数逐项登记。
- **429 一律记阻塞**。由 429 导致的后续未执行同样记阻塞，不记不通过。
- T08 的证据选用规则见 §4.8。
- T10 分“直调 / 项目”两层分别记状态。项目级一栏取公共路径的离线对照结果，对七个模型相同。
- 每个用例的证据在 `results/cases_<模型>*.json` 里给出对应 HTTP 记录的 `seq`，可在 `raw/http_<模型>*.jsonl` 里按 `seq` 复核。

### 6.3 推断

以下是根据上述事实做的推断，不是实测结论。

1. **`k3.1-pro` 的 `thinking.type=disabled` 确实返回 400**，与文档一致。
2. **`k3.1-pro` 的 `reasoning_effort: none` 返回 200，没有可见推理，`model` 回显原 ID**。这与文档“关闭请求返回 400”不一致。
3. **没有实际换模的确证**。`prompt_tokens` 的差异不能用来区分模型：三个模型 ID 在思考模式下都是 91–92 / 108–109；`k3.1-pro` 与 `k3` 在无推理模式下都是 24 / 41，`kimi-for-coding` 关闭后的简单题同样是 24。差值恒为 67–68 个 token，更像思考模式附加的一段固定内容，而不是分词器不同。响应的 `model` 字段只是回显请求的 ID。
4. **也没有达到严格关闭的放行条件**。文档明确 K3.1 Pro 不能关闭思考，实测表现（200、无推理、计数与 `k3` 关闭后及 K2.8 Preview 的无思考模式完全相同）与文档描述的“交由无思考模型处理”的路径相符，但无法从响应判断应答的到底是哪一个模型。按 Doc 24 属于“响应模型身份不清楚”，记**无法判定**。
5. `k3` 的表现与文档一致：`none` 与 `thinking.type=disabled` 都返回 200 且无推理。
6. `reasoning_effort` 取 `off` / `disabled` 时两个模型都返回 200 且思考开启。文档说未知取值返回 400，实测这两个取值被当成“开启”处理，**不能用来关闭思考**。

能定论的条件：厂商确认 `k3.1-pro` 在 `reasoning_effort: none` 下的服务方式，或者找到能区分 K3.1 Pro 与 K2.8 Preview 的能力指纹。

## 7. 离线模拟

用项目锁定的依赖和注入的合成 HTTP 响应执行，不访问网络（主机名 `doc24-offline.invalid`，151 次往返）。证据：`cases_OFFLINE_r1.json`、`raw/http_OFFLINE_r1.jsonl`。离线结果说明解析与隔离规则，不是某个模型的通过或不通过。

### 7.1 T09 解析规则

| 响应形态 | SDK 解析结果 | 项目取文与清理函数 |
| --- | --- | --- |
| 推理在独立字段 | 正文干净，推理不进消息 | `extract_llm_content` 原样返回；`TimeResolver` 取文可解析 JSON |
| 内容块 `reasoning` + `text`，或 `thinking` + `text` | `content` 是块列表 | **`extract_llm_content` 抛 `AttributeError: 'list' object has no attribute 'strip'`**；`TimeResolver` 取文只取 `text` 块，可解析 JSON |
| `<think>R</think>A` | `content` 原样带标签 | `extract_llm_content` 去掉成对标签，返回 `A`；直接做 JSON 解析失败 |
| `A1<think>R</think>A2` | 同上 | 返回 `A1A2`，标签前后文本都保留 |
| `A<think>R</think>` | 同上 | 返回 `A` |
| 未闭合标签且 `finish_reason: length` | 只有开标签 | `extract_llm_content` **不剥离**，返回原串；需要结合结束原因判为不完整输出 |
| 流式，标签跨分片切断 | 拼接后与非流式一致 | 标签可识别 |
| 流式，中途截断 | 没有结束块，正文为空 | 不完整输出 |

`extract_llm_content` 位于 `src/services/llm_factory.py`，它假定 `response.content` 是字符串。七个目标端点在本轮都没有返回内容块形态，所以这个缺陷目前不会触发；换成会返回内容块的模型或适配器时会。

### 7.2 T10 断流与残缺工具参数

第 1 轮用必填参数的工具（`spy_count_orders(month: str)`）。第 2 轮按协调者要求补了参数全部可省略、可计数、无副作用的工具（`spy_touch(count: int = 1, label: str = "x")`）。两者都走 `create_deep_agent` 的真实工具节点和注入的合成 SSE。

| 流式情形 | 必填参数的工具：函数体执行 | 可全省略参数的工具：函数体执行 | SDK 侧的表现 |
| --- | --- | --- | --- |
| 参数完整分片 | 是（`{"month": "2026-09"}`） | 是（`{"count": 3, "label": "a"}`） | 合法工具调用，参数完整 |
| 参数本身就是 `{}` | 未测 | 是（按默认值） | 合法工具调用，参数 `{}` |
| 参数后截断，没有结束块和 `[DONE]` | **否**，被必填校验拦住 | **是，按默认值执行** | 工具调用合法、参数 `{}`，`invalid_tool_calls` 为空，`ToolMessage` 状态 success |
| 只有参数首片就截断，没有结束块和 `[DONE]` | 未测 | **是，按默认值执行** | 同上 |
| 有结束块和 `[DONE]`，但参数残缺 | 未测 | **是，按默认值执行** | 同上 |
| 完全没有参数分片 | 未测 | 是（按默认值） | 与参数为 `{}` 的合法调用无法区分 |
| 连接中断 | 否 | 否 | `OpenAIConnectionError` |
| 参数完整但不是 JSON | 否 | 否 | 进入 `invalid_tool_calls`，不产生 `ToolMessage` |

**项目级断流保护：不通过。** “残缺工具参数不能触发执行”只对必填参数的工具成立，而且靠的是参数校验，不是对流完整性的检查。对参数可全省略的工具，三种残缺情形下函数体都按默认参数真正执行了。

边界：

- 这发生在客户端一侧，是 `ChatOpenAI`（1.7.4）加 deepagents（0.7.34）工具节点的公共行为，离线对照即可判定；没有对七个端点逐一做断流。
- 没有修改业务代码，也没有验证任何修复方案。
- 当前角色都是非流式请求（§4.10），不受影响。NL2SQL 的真实工具里不少带有可选参数，给 Agent 打开流式之前需要先补这层保护。

证据：`results/round2_probes_r1.json`（第 2 轮）、`raw/http_R2_r1.jsonl`；第 1 轮的消息明细在 `results/offline_t10_messages_r1.json`。

### 7.3 T08 三种推理存放形式的去向

用唯一合成标记分别放进三种位置，跑真实的 Agent、摘要中间件、模型观测器和线程交接函数。表中“含”表示在该位置检索到了标记。

| 推理存放位置 | checkpoint（内存与序列化） | 同端点的后续请求 | 摘要请求 | 历史转存文件 | 模型观测器 DEBUG 日志 | 线程交接消息 |
| --- | --- | --- | --- | --- | --- | --- |
| `AIMessage.additional_kwargs["reasoning_content"]` | 含 | 不含 | 不含 | 不含 | 不含 | 不含 |
| `AIMessage.content` 中的 `reasoning` 块 | 含 | 不含 | **含** | **含** | **含** | 不含 |
| `AIMessage.content` 字符串中的 `<think>…</think>` | 含 | **含**（原样回到下一轮请求） | **含** | **含** | **含** | 不含 |
| 摘要文本（合成摘要器把标记写进摘要） | 不含 | 不含 | 含 | 不含 | 含 | **含** |

- 前三种形式与 Doc 24 §4.1 的表一致，并补充了表里没有的三项：`reasoning` 块在回传时被丢弃，`<think>` 文本会原样发回端点，两种形式都会进入模型观测器的 DEBUG 日志。
- 线程交接消息由摘要文本和携带证据拼成。摘要里没有标记时它是干净的；摘要一旦带入推理，交接消息也会带上（第四行）。
- 这三种形式在七个目标端点的真实响应里都没有出现，因为当前 `ChatOpenAI` 不保留独立推理字段，而七个端点也不返回内容块或内嵌标签。将来若接入会返回这两种形态的模型或适配器，摘要输入、历史文件、DEBUG 日志都需要先做隔离。

## 12. 探针修订记录

本轮执行中修正过以下探针缺陷。修正前的记录若已影响结论，相关用例都重跑过；没有重跑的在此说明原因。

| 编号 | 缺陷 | 影响 | 处理 |
| --- | --- | --- | --- |
| P-01 | 记录器最初包装的是 `httpx`，而 OpenAI SDK 3.x 实际走 `httpx2` | 最早几次冒烟没有记录；没有产生错误结论 | 改为包装 SDK 实际使用的库 |
| P-02 | 传输层字节是 gzip 压缩的，DeepSeek 的 SSE 是增量压缩 | 首轮 DSF 的三个流式组合被误判 | 改为增量解压后复跑直调层 |
| P-03 | T10 用了 `tool_choice: required`，思考模式的 DeepSeek 会拒绝 | 首轮 DSF 开启组全部 400 | 改用 `auto` 后复跑；`required` 的行为另以补充探针留证 |
| P-04 | T02 把“关闭组答错计算题”当成关闭失败 | 首轮 Q38F 被误判不通过 | 拆成开关有效性与文本可用性，复跑 |
| P-05 | T02 用 `prompt_tokens` 差异推断换模 | 首轮 K31-C 被判“换模，不通过” | 经 `k3` 对照发现 token 数不能区分模型，改判无法判定，K31-C 直调层复跑 |
| P-06 | T04 的参考子项（采样效果、强制工具选择）计入了总评 | 首轮多个模型 T04 被判无法判定或不通过 | 标为参考项，复跑直调层 |
| P-07 | 完整问数的合成库用了内存 SQLite，不支持 PostgreSQL 的 `GROUPING SETS` | Q38F 开启组一次运行失败 | 改用临时 PostgreSQL 容器和项目真实的 `BusinessDbService`，角色层整体重跑 |
| P-08 | 完整问数的 Agent 没有传 checkpointer | 早期运行在 P0 失败 | 传入内存 checkpoint |
| P-09 | 超时行为测试在传输层内模拟延迟，触发不了读超时 | 首轮该子项误判 | 改用回环慢速服务 |
| P-10 | T06 的第四条预置事实落在保留窗口内，没有进摘要器 | 首轮所有模型都显示保留 3/4 | 移到被摘要区间，角色层整体重跑 |
| P-11 | T08 的两轮 invoke 复用了同一份运行配置（相同的 `run_id` 元数据和同一个模型观测器回调），第二轮没有发出模型请求 | 第二用户轮出现空判 | 每轮改用独立的运行配置后恢复，T08 整体重跑。两个因素是一起改的，没有单独隔离是哪一个导致 |
| P-12 | T08 模型切换的线程标识绑定到了别的变体，新模型拿到空历史 | `_roles` 的模型切换一项是空判 | 默认参数绑定；单独补测 `r2`，G53 另以 S3 补齐 |
| P-13 | checkpoint 序列化扫描调用了不存在的 `dumps`，异常被吞掉后按“未检出”计 | 首轮隔离一项是空判 | 改用 `dumps_typed` 并加阳性对照；无标记可查的扫描点不再参与判定 |
| P-14 | K31-C 的角色 profile 带了 `temperature: 0`，完整问数全部 400 | 首轮 K31-C T05 不通过 | 去掉覆盖后重跑；原配置被拒的证据保留在 T04 |
| P-15 | 离线 T08 的脚本顺序写死，摘要器拿到了错误的响应；工具有一处名字写错 | 首轮离线摘要未触发 | 改为按请求体决定响应，重跑离线 |
| P-16 | 第 1 轮只对必填参数的工具做了断流对照，把“必填校验拦住”当成了“残缺参数不触发执行” | T10 的项目级断流保护被高估；Q38F“全部十项通过”的表述不成立 | 第 2 轮补可全省略参数的工具对照，判不通过；矩阵的 T10 拆成直调 / 项目两层 |
| P-17 | 第 1 轮的 T10 只有直调矩阵，没有经工厂和项目装配的出线证据 | Doc 24 “在直调和项目装配分别跑”未落实 | 第 2 轮补离线矩阵与 Qwen 真实交叉验证 |

受 P-10、P-11 影响的首轮角色层记录保留在 `results/superseded_r1/`，**不应作为结论依据**，只用于核对修订前后的差异。受其余各项影响的早期记录已被复跑覆盖。

探针本身有三处已知局限：

- HTTP 记录器包装的是传输层，能看到发到网络上的字节，但看不到传输层之下的连接细节。
- 流式响应的分片到达时间受本机网络影响，只用于判断“是否真的在流式到达”，不作为性能数据。
- 工厂用例通过进程内登记 profile 完成（§1.6），没有覆盖从磁盘配置加载新 provider 的路径。

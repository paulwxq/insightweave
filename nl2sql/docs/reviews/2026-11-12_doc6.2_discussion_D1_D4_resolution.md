# doc 6.2：D1—D4 讨论处理

本轮仅修改 [6.2 方案文档](../6.2_db_deepagent最终答案兜底问题与补齐建议.md)、详细设计 §13.3 的待实施契约及离线验证脚本，不修改生产业务代码，不新增 Orca 委托轮次。

| 讨论点 | 核实与选择 |
| --- | --- |
| D1：跨版本 status 同名异义 | 成立。v1 原 answer.status 是模型状态，v2 delivery_answer.status 是 Runner 状态。选择在 v1 读取副本中将 status 改名为 submitted_status，v2 保留交付 status；不改写归档、不推定历史 Runner 状态。跨版本展示/统计统一读取归档顶层 status，缺失/非法按未知处理，不能回退模型状态。同步契约表、读取片段、详细设计和验收项。 |
| D2：行数映射重复计算 | 存在，但非 correctness 问题。改为 _finalize() 在证据组装前只计算一次，传给 _assemble_evidence(..., known_row_counts=...) 与模板。映射参数必传，不设内部重算分支；现有生产调用点仅在 _finalize()。未知值兼容投影为外部整数零，模板仍只认可靠映射，不反推零行。 |
| D3：兜底正文偏技术 | 建议合理，属于产品取舍。采用简版正文：不展示账本术语和内部证据 ID，未知行数省略；可靠行数以“已记录 N 行结果”说明，仍保留历史沿用、源头截断、最终答案未完成等边界。证据、警告和证据面板的既有信息保留，不新增另一套答案或 DTO。 |
| D4：公开客户端属性的版本依赖 | 属合理提示，不判为当前私有接口违规。核对固定 langchain-openai 1.7.4 的公开 root_client/root_async_client 字段及标准构造代码，补充升级或改变认证/客户端注入后的复验要求。None 代表无法确认，错误信息据此调整；不静默略过或宣称客户端确已开启重试。未来若延迟构造，先补适配与测试。 |

不采用 D1 的“仅注释提醒、保留返回字段同名”的最低限度方案：访问器尚未实施，现在显式区分模型状态，能减少消费方误用。保留原归档 answer 字段的兼容策略不变；本次改名只作用于新访问器的读取副本。

## 验证证据

[离线验证脚本](2026-11-12_doc6.2_payload_safety_probe.py) 读取当前文档片段，在内存 AST 副本中应用方案：

- 30 个 Runner 场景继续通过：20 个非法 payload、8 个归属异常、2 个正常基线；原值保留、归档分流、状态及无新增 P3 异常的断言保留。
- 每次收尾只计算一次行数映射；证据组装和模板复用同一对象且不修改，正常提交仍只做一次 Runner 侧 Pydantic 解析。
- v1 顶层 failed、模型 completed 时，读取视图只有 submitted_status=completed，原档不变；v2 status 仍为 Runner 状态。跨版本统计按顶层状态得到一致语义，缺键不补造。
- 6 种零行/未知行数场景验证简版文案：可靠零行保留，其余未知不输出零；内部编号和账本术语不出现在正文；历史沿用、截断、未完成说明保留。另检查无证据和最多展示五项的分支。
- 用固定版本 ChatOpenAI 实际构造同步/异步客户端，确认 max_retries=0；将任一公开客户端字段设为 None 时，“无法确认”分支拒绝启用。只构造并关闭客户端，不发送 HTTP；构造期间临时隔离验证进程的代理变量，随后恢复，不安装缺失的 SOCKS 可选依赖。
- 15 段 Python 片段语法检查通过；既有配置迁移和浅投影边界检查继续通过。

# db_deepagent 已登记任务终态与答案覆盖门控方案

整理日期：2026-11-12；本轮复核修订：2026-11-13。

## 1. 结论、范围与分析基线

针对 [6.1 清单](6.1_db_deepagent能力补齐问题清单与实施建议.md) 的问题 **02：已登记任务的终态与答案覆盖门控**，建议增加业务任务账本 `db_sub_tasks` 和登记工具 `record_sub_tasks`，由共享规则统一核验：

1. 本轮至少有一项有效业务任务，简单问题也不例外。
2. 正常提交时，已登记任务均已进入明确终态。
3. 成功任务有属于该任务当前版本的可信证据，且在最终 findings 中逐项覆盖。
4. 失败、待澄清和作废任务有可追溯原因，并向用户明确披露。
5. 提交工具与 Runner 使用同一套校验和状态映射，异常收尾保留已有结果。

**任务表、执行证据与最终答案必须形成闭环。** 只增加任务列表、只相信模型填写 `completed`，或只在最终提交时让模型补报任务，都不能提供上述保证。

本文给出方案，不实施生产代码变更。02 的可靠落地依赖 03 的任务授权与证据归属，以及 04 的版本、依赖失效和历史沿用规则；本文规定它们必须提供的最小契约，不扩展实现 SQL 修正次数、自动批次调度或防重复执行等后续条目。

本轮分析基线为已提交的 `50067ce`（doc 6.2 实施收尾完成），读取该提交上的业务代码；开始本轮修订时工作区干净。本轮仅修改本文，6.3 的新账本和门控仍未实施。实际安装版本为 `deepagents==0.7.34`、`langchain==1.4.9`、`langgraph==1.2.20`；核心文件 SHA-256 及可重放探针见 §12。6.2 的最终答案兜底、归一提交视图、单层模型重试与归档 v2 已生效，不能再把它们当作本篇仍需从零实现的能力，实施记录见 [6.2 收尾](reviews/doc62_implementation_closeout.md)。

背景参考 [总体对比 §7.2](6_db_deepagent与LangGraph作业编排对比分析.md#72-高优先级缺少针对已识别子任务的代码级终态门控)、[当前复核 §4.3](reviews/2026-11-12_db_deepagent替代能力复核.md#43-原文任务方案还需澄清的实现边界)；与问题 01 的收尾衔接参考 [6.2 最终答案兜底方案](6.2_db_deepagent最终答案兜底问题与补齐建议.md)。这些文档中的建议不等于当前实现。

## 2. 当前代码实际保证了什么

### 2.1 当前链路没有业务任务账本

| 位置 | 当前行为 | 对问题 02 的影响 |
| --- | --- | --- |
| [query-planning Skill](../src/modules/db_deepagent/skills/query-planning/SKILL.md) | 要求分别跟踪独立子问题；允许单条 SQL 处理简单问题 | 是模型指导，没有登记动作与代码门控。 |
| [state.py](../src/modules/db_deepagent/state.py) 的 `DbDeepAgentState` | 保存校验、执行、分析、时间、维度、错误、运行状态和最终答案 | 没有任务集合、任务版本及状态。 |
| [agent.py](../src/modules/db_deepagent/agent.py) 的 `build_db_agent()`、`stage_expected_tool_names()` | 可选装配 `TodoListMiddleware/write_todos`，默认关闭 | 通用待办没有证据归属和业务终态约束，提交与 Runner 均不读取它。 |
| [schemas.py](../src/modules/db_deepagent/schemas.py) 的 `FindingItem` | 只有 `text/evidence_ids` | 无法知道 finding 回答了哪项任务。 |
| [sql_pipeline.py](../src/modules/db_deepagent/services/sql_pipeline.py) 的 `LedgerView` | 只提供 `validations` 和 `evidence_of_run()` | 当前视图不能提供任务、任务版本或分析输入归属查询。 |

因此，`write_todos` 不能作为本方案的事实来源；提示词中的“已完成”也不能代替结构化账本。

### 2.2 提交工具只检查已提供的引用

[tools/final_answer.py](../src/modules/db_deepagent/tools/final_answer.py) 的 `make_submit_final_answer_tool()` 在工具函数执行前，先由继承 `DbAgentFinalAnswer` 的参数模型校验结构及正文；6.2 新增的 answer validator 拒绝纯空白正文。参数校验通过后，工具函数依次检查：

1. 单独调用，不与其他工具处于同一条 AIMessage。
2. 本轮尚未提交。
3. findings 中的 ID 属于本轮 `purpose="query"` 的执行记录，或本轮分析记录，包含已登记的沿用证据。
4. `completed` 时 findings 非空。

它没有“全部应该回答的任务”这个可核对的集合。两条执行记录只引用一条仍能提交 `completed`；这本身不证明漏答，因为另一条记录可能只是探索，但说明**执行记录数量不能替代任务覆盖检查**。

`no_data` 当前不要求零行查询证据。现有 `test_no_data_without_findings_ok` 只验证允许 findings 为空，不能证明返回 `no_data` 具有足够业务依据。

### 2.3 Runner 的复核比任务门控更弱

[runner.py](../src/modules/db_deepagent/runner.py) 的 `_evaluate()` 会去除无效 evidence ID，并去除没有剩余证据的 finding；随后仅在 `completed` 且整个 evidence 列表为空时改判失败。

这意味着：如果账本中还有其他成功证据，即使过滤后 findings 全空，Runner 仍可能返回 `completed`。这属于防御性复核路径的不一致，不表示正常提交工具允许 `E-ghost` 通过。

`_assemble_evidence()` 只负责将本轮 query 执行和分析投影为交付证据；它不判断任务完整性。`_archive_run()` 的“存在真实执行”条件负责决定是否保存 QA，也不能当作整体完成证明。

### 2.4 SQL 和分析尚无任务归属

当前 `ValidationRecord/ExecutionRecord/AnalysisRecord` 均没有任务 ID 和 revision。`auth_key()` 包含线程、请求、运行、数据源、校验指纹和 SQL，但不含任务版本，甚至未把 `purpose` 纳入键。

`analyze_result` 按 `result_ref` 读取输入，可以本地计算或经 `validate_and_execute(purpose="pushdown")` 查库；`reuse_evidence` 可以登记历史 E-/A-，但没有目标任务信息。因此不能在增加任务列表后，按 SQL 文本或模型自报把既有执行“补挂”为任务成果。

## 3. 与旧链的关系及保证边界

旧 [check_completion.py](../src/modules/nl2sql_father/nodes/check_completion.py) 针对 Complex Path 的已规划子查询检查 `pending/in_progress`；达到轮次上限或无法推进时标记失败，再进入总结。旧 [simple_planner.py](../src/modules/nl2sql_father/nodes/simple_planner.py) 也为简单问题建立一条子查询，但 Fast Path 不经过 `check_completion`。

本方案承接“已规划任务必须有交代”的保证，并进一步检查证据和答案覆盖；不恢复旧父子图的固定执行拓扑，也不要求模型先把每次检索、校验都建成任务。

任务表示**本轮需要交付的业务问题或必要结果**，不是工具调用步骤。检索结构、修正 SQL、读取分页通常属于同一任务内的工作。复杂比较可以登记“取得 A”“取得 B”“比较 A/B”三项任务；必要中间结果也要有简短 finding，例如选出的比较对象，避免产生“登记了但无需任何交代”的隐形任务。

门控的保证范围仍然有限：

- 可证明已登记集合在结构上有终态、证据和覆盖关系。
- 不能证明模型最初没有漏识别用户意图，也不能仅凭 task_ref 证明结论的业务语义正确。
- 不能从 SQL 成功推断业务口径正确，不能从结果文件行数推断 COUNT、SUM 等单元格含义。
- 不提供新的跨进程执行幂等、数据库快照一致性或强杀进程后的必达交付保证。

规划完整性和业务正确性仍须通过题集与人工抽查单独评估。

## 4. 任务账本与身份设计

### 4.1 私有通道与记录

新增 `SubTaskRecord` 与私有状态通道 `db_sub_tasks`。记录只保存可 JSON 序列化字段，沿用当前工具返回 `Command(update=...)` 写账本的方式。

| 字段 | 约束与用途 |
| --- | --- |
| `session_id/thread_id/request_id/run_id` | 从服务端 context 填入，不接受模型覆盖。 |
| `sub_task_id` | 本运行内稳定的逻辑 ID；禁止删除后重用或重编号。 |
| `revision` | 从 1 开始；语义、依赖变更时由服务端递增。 |
| `content` | 业务目标，必须为字符串且 Python `str.strip()` 后非空；不能只写“执行 SQL”。 |
| `dependencies` | 本轮依赖的 `{sub_task_id, revision}` 列表；版本固定，不在读取时自动换成新版。pending/in_progress/completed 的引用参加执行依赖校验；失败、澄清和作废后的引用仅供审计，见 §5.2。 |
| `status` | `pending/in_progress/completed/failed/needs_clarification/voided`。 |
| `evidence_ids` | 本任务当前版本选定的成果证据；completed 必须非空。 |
| `creation_operation` | 服务端保存完整规范化 add 操作，包含 content、dependencies 及全部可写参数；用于 §5.3 的精确幂等比较，不仅比较正文。revise 产生的版本另记其创建操作，不伪装成 add。 |
| `reason_code/reason` | failed、needs_clarification、voided 必填；reason 必须为字符串且 Python `str.strip()` 后非空；区分实际工具错误、Agent 放弃和系统停止。 |
| `failure_refs` | 默认空列表；声称工具失败时必填非空 TaskFailureRef 列表，定位服务端错误并核对同一任务版本，见 §5.1。自由文本 reason 不能代替错误引用。 |
| `clarification_question` | needs_clarification 必填，必须为字符串且 Python `str.strip()` 后非空，作为向用户展示的具体问题。 |
| `blocked_by` | 仅 `failed + reason_code=dependency_blocked` 使用，列出导致阻塞的直接依赖版本；服务端核验并生成原因，不要求伪造 clarification_question。 |
| `termination_context` | failed/needs_clarification/voided 时由服务端生成的终止依据：decision_plan_version 及当时依赖版本的状态/原因快照；dependency_blocked 保留已核验的阻塞根因；replacement_snapshot 保留替代目标在作废决策时的身份、revision、状态。历史依据不随后续 revise/void 改写，不能接受模型自报状态。 |
| `replacement` | 计划替换时指向同一 run 的替代任务版本；登记时核验为候选计划中存在、当前且未作废的其他逻辑任务，后续按历史审计引用复核，不要求仍为当前/未作废。普通取消可无替代，不强制伪造引用。 |
| `decision_source` | 服务端记录 `agent/tool/system`，不把模型的主动放弃伪装成数据库错误。 |
| `created_at/updated_at/tool_call_id` | 服务端写入的时间和登记调用信息。 |

账本键采用规范化编码的 `(run_id, sub_task_id, revision)`，不能直接使用 tuple 作为 JSON 对象键。完整任务版本身份为 `(session_id, thread_id, run_id, sub_task_id, revision)`；单个 `sub_task_id` 只在当前 run 中有意义。

再增加私有 `db_task_plans`，按 run 保存单调递增 `plan_version`，用于整批任务修改的乐观前置检查和审计。它不是任务 revision：前者标识一次整批修改，后者标识某项任务的业务版本。

### 4.2 最新版本选择与作废

LedgerView 对一个逻辑任务必须**先取最大 revision，再判断该版本的状态**。不得先过滤 `voided` 再取最大值，否则最新版本作废后旧版可能重新成为当前任务。

- `revise` 保留旧记录，新建 revision+1，固定为 `pending/evidence_ids=[]/reason=None`，failure_refs 清空，终止依据和 replacement 不复制。旧版被新版取代，不复制 completed 状态或成果。
- `void` 把最新版本置为 voided，保留原因。其旧版本全部仍是历史。
- voided 逻辑 ID 不再接受 status/revise；恢复需求时新增 ID，并记录与旧任务的关系。
- 所有版本都不能被静默删除；缺失版本、重复冲突或不可解码的记录应报账本错误。

void 用于计划替换、重复任务合并或有依据的范围调整，不能作为普通失败的替代。替换任务需写明 replacement 引用，整批登记时核验其存在、为当前且未作废版本，并由服务端生成 replacement_snapshot；执行失败使用 failed。后续替代目标 revise/void 不反向否定原作废决策，Runner 只核验固定历史身份与决策时依据，展示“当时由 B@1 替代”，不声称 B@1 现在仍有效。若 B 后来也作废，仍须披露其作废事实；不能用这条历史关系绕过“全部作废禁止成功”的规则。作废原因由系统展示，但这仍不能自动证明范围调整符合用户意图。

### 4.3 LedgerView 的最小扩展

新增以下只读能力，返回副本或不可变视图：

- `current_tasks(run_id, include_voided=True)`：先选最新版本，保留作废记录用于审计。
- `require_current_task(run_id, sub_task_id, revision)`：拒绝未知、旧版或已作废目标。
- `require_writable_task(...)`：在上述身份校验后，只允许 pending/in_progress 目标产生新授权、执行、分析或沿用成果；不影响对 completed 任务的只读引用。
- `executions_of_run()/analyses_of_run()`、本轮 `evidence_by_id()`、历史 `evidence_by_ref(full_evidence_ref)`、`records_by_result_ref()`、`error_by_ref(full_error_ref)`。
- `task_plan_version(run_id)`、`task_snapshot(full_task_ref)`、`validate_lineage(...)`。

任务工具、SQL 管线、分析、沿用、提交和 Runner 都应复用视图与共享规则。现有 `reuse_evidence` 对相关账本的直接读取需要同步收口；不能只给新工具提供视图而留下旧入口绕行。问题 07 的表检查视图可后续增加，不作为 02 的发布前提。

`error_by_ref()` 要求合法错误账本中每个完整 error_ref 恰有一条记录。未知引用报未找到；缺失身份、同完整引用重复（即使事实相同）或事实冲突，均报 LedgerConsistencyError，不能用字典覆盖或取第一条来掩盖损坏。正常写入重放由 §5.1 的 reducer 先去重，因此不会制造读取歧义；旧 checkpoint、封存快照或直接注入绕过 reducer 时仍须做上述检查。提交与 Runner 将读取一致性错误收敛为门控拒绝，沿用 §7.5 的状态优先级及兜底，不把非法错误记录当成合法失败依据，也不推迟到 P3 才发现。

## 5. 登记工具、状态转移及并发约束

### 5.1 一个工具维护计划与终态

新增 `record_sub_tasks(expected_plan_version, operations)`，其中 `operations` 为非空操作列表：

| 操作 | 允许的变化 | 必须校验 |
| --- | --- | --- |
| `add` | 新建任务，服务端指定 revision=1、pending | ID 唯一、content 必须为字符串且 `str.strip()` 后非空、依赖合法。仅完整规范化操作一致且满足 §5.3 的版本前置条件才可幂等返回；同 content 但不同 dependencies 等参数仍冲突，不能覆盖。 |
| `revise` | 针对当前 revision 创建下一版 | 旧版不能 voided；清空成果；重新校验依赖图。 |
| `status` | pending→in_progress；pending/in_progress→completed/failed/needs_clarification | completed 必须通过任务成果校验；failed 必填 reason，needs_clarification 必填 reason 和 clarification_question，按状态必填的文本均须为字符串且 `str.strip()` 后非空。允许跳过显式 in_progress，减少简单题调用。 |
| `void` | 将当前版本作废 | reason 必须为字符串且 `str.strip()` 后非空，原因及替换关系合法；不得让依赖它的有效任务悄悄继续成功。 |

终态不通过普通 status 原地恢复。重做失败任务、纠正成果或更换依赖时使用 revise，形成新的 pending 版本。重放完全相同的 status 按 §5.3 可以幂等返回，不能因此修改原事实。若已 completed 的下游因上游变化而不再继续，不能直接 completed→failed：应作废该任务，或先 revise 清空成果、重绑依赖，再在后续批次登记新版本的终止状态；每批对同一逻辑 ID 至多一个修改操作。

`completed` 不由 execute_sql 自动设置：一个业务任务可能需要多条查询和分析。模型通过 status 选择成果，服务端核验后才接受。任务工具不能接收模型提供的行数、结果值或“证据可信”布尔值作为判据。

对 `failed`，`reason_code=tool_failed` 时必须通过 failure_refs 引用服务端可查的该任务版本失败记录；主动放弃使用明确的 `agent_abandoned` 原因。`TaskFailureRef` 保存完整 `error_ref={session_id, thread_id, run_id, error_id}`，以及 `tool_call_id/error_type/source_task_ref`；后几项必须与被引用记录精确相符，不能信任模型自报。ToolErrorRecord 增加服务端 error_id、完整运行作用域和可空 source_task_ref，原 tool/error_type/message/retryable 字段保留；同一工具调用可有多个错误，因此不能仅以 tool_call_id 寻址。

error_id 由服务端错误事件工厂在构造错误记录时生成，例如 `ERR-` 加 uuid4 的完整十六进制值，不使用短截断哈希或模型填写值。在 `(session_id, thread_id, run_id)` 内必须唯一；完整 error_ref 才是索引键，不要求不同 run 的裸 error_id 永不相同。同一错误的 Command/update 重放携带原 error_id 和原记录，不能重新分配 ID；真实工具重试产生的新错误事件使用新 ID，即使 message 相同也不合并。UUID 只是生成方式，重复键校验仍必须执行。

`db_tool_errors` 由现行 operator.add 改为专用 `append_dedup_tool_errors()`：按完整 error_ref 合并，对左右输入及单个输入内部都校验，不因一侧为空而跳过。相同引用且事实完全相同可保留首条，异事实抛 LedgerConsistencyError，拒绝该次合并，不修改原输入。事实比较必须包含 request_id、tool_call_id、tool、error_type、message、retryable、source_task_ref 及其他结构化错误依据；类型合法后规范比较，不对 message 做模糊匹配。不能照搬执行证据 reducer 排除 tool_call_id 的规则，因为它是 failure_refs 核验的错误事实之一。服务端纯登记时间等审计元数据若存在可不参加事实比较，但不得覆盖首条；未知/缺失必填身份或非法字段同样拒绝，不伪造默认引用。

SQL 校验/执行、分析（含下推）和 E/A 沿用的可恢复错误都写错误账本，并在错误包中返回 failure_ref；包括正常返回的拒绝结果，不能只记录抛出的异常。建议共享 `tools/_task_errors.py::make_task_error_record()/task_error_command()`，通过 Command 一并返回错误消息和账本更新，避免直接修改 runtime.state。下推与外层分析可分别留轨迹，引用必须选确实对应本任务的记录，不把一次错误伪装成多次执行失败。不可恢复异常仍遵守 Runner 的异常优先级，不为留错误记录掩盖持久化故障。

source_task_ref 只在服务端核验目标身份后填入；参数层未通过、未知/旧版/不合法目标，以及 probe 的错误，不能声称属于当前有效业务任务，可保留 source_task_ref=None 及独立诊断信息。无任务 probe 错误不能填入该任务的 failure_refs；因此无法推进业务任务时，可用 agent_abandoned 说明“未取得前置探测信息，本轮停止”，不谎称该任务的 SQL 执行失败。agent_abandoned、dependency_blocked 等非工具失败原因不伪造 failure_refs，分别读取主动终止说明或阻塞依据。共享提交与 Runner 复核引用的作用域、任务版本和错误事实，封存快照保留被引用错误；每任务修正次数与自动耗尽转移仍归问题 06。

### 5.2 整批校验后一次提交

工具以当前账本副本构造候选计划，统一应用本批操作，再对合并后的视图校验。须区分两类引用：

1. **执行依赖**：最新 pending/in_progress/completed 任务的 dependencies。所有目标都必须存在、为当前且未作废版本；允许登记时依赖尚未完成，但使用成果前必须全部 completed。对这组当前版本引用检查自依赖、重复、未知目标和环。处于失败或澄清终态的当前上游可以成为待处理计划的依赖，但不会因此获准执行。
2. **终止审计引用**：failed/needs_clarification/voided 任务保留的 dependencies、blocked_by、failure_refs、replacement 及 termination_context。核对完整身份、历史版本/错误存在性、字段完整性与决策时依据；replacement 使用封存的 replacement_snapshot，不要求目标后来仍是当前/未作废版本。也不把这些引用重新加入执行图，它们不能提供执行授权、成功覆盖或成果沿用资格。

同批前向引用仅允许指向候选计划中确实新增的任务版本；同一逻辑 ID 的重复修改、缺失/不可解码历史引用或非法版本变化仍拒绝整批。审计引用不是允许创建未知任务、自依赖或环的入口：add/revise 固定创建 pending，并先通过执行图校验；终止操作不得修改 dependencies。任一错误则整批不写。

下游开始 SQL 校验、执行或分析之前，其声明依赖必须全部为当前且 completed 的版本，首版没有放行非 completed 依赖的执行例外。登记计划时可以引用尚未完成的当前版本，登记下游 failed/needs_clarification 等非执行终态也不要求上游 completed；这两类操作不消费上游成果。最终门控对 completed 任务复核依赖完成条件，对失败或待澄清任务核验依赖身份和终止原因，不因其上游同样失败或待澄清而拒绝解释性提交。零行上游是否允许继续属于业务策略，不自动把下游推成 no_data。

上游需要澄清或已经失败、下游尚未开始时，首版仍不允许 pending 随整体 needs_clarification 提交。可在一次 `record_sub_tasks` 中批量将受影响下游登记为 `failed + reason_code=dependency_blocked`：登记当时，`blocked_by` 指向候选计划中确已 failed/needs_clarification 的直接依赖；服务端沿依赖链核对阻塞根因并生成说明及 termination_context，不得仅因上游仍 pending 就谎报已阻塞。以后上游修订或作废时保留该决策时快照，最终门控校验封存依据，不再以当前上游状态重新编造原因。该终态表示本轮未能执行，不表示下游 SQL 曾执行失败；没有独立澄清问题时不填 clarification_question，也不把下游标成 needs_clarification。只有下游自身确有独立歧义，才登记其具体澄清问题。

这种处理保留“普通提交前任务全终态”的统一规则，又可在一次批量操作中交代整条阻塞链。上游仍有 needs_clarification 时，整体按 §7.4 返回 needs_clarification，正文说明根问题和受阻任务；澄清任务数按具有独立问题的 needs_clarification 任务计数，dependency_blocked 单独统计，不膨胀澄清计数。同一根问题的展示按根任务版本去重。用户下一轮澄清后建立新 run 的计划，不把本轮 failed 任务原地复活。

上游 revise/void 时，所有仍处于执行图且依赖将失效的下游，必须在同批 revise 重绑依赖、依法转为非执行终态，或作废；既有失败/澄清终态只保留历史审计依据，不强制为了追随上游升级而复活。未处理的有效执行依赖导致整批拒绝，并返回受影响任务清单。

例如 A@1 completed、B@1 pending 且依赖 A@1：同批 revise A→A@2 并把 B@1 以 agent_abandoned 明确终止，可以保留 B 的历史 A@1 引用；B 已不具备执行/覆盖资格，因此不会因旧依赖再次阻止这批修改。若 B 还要继续执行，则必须 revise B→B@2 并显式改依赖为 A@2，等待 A@2 completed 后再执行。若 B@1 已 completed，则按 §5.1 作废或 revise，不能原地改 failed。最终门控仍防御性检查当前执行图、审计引用及成果血缘。

### 5.3 首版采用串行任务修改

同批工具通常看到同一份状态快照，不能靠各工具局部检查保证合并后无环，也不能用 `merge_by_key` 实现 CAS。

首版规则如下：

1. 一条 AIMessage 只能有一次 `record_sub_tasks`，且不能同时调用任何其他工具；不符合即拒绝本批任务修改。
2. `submit_final_answer` 继续单独调用；登记、校验、执行、终态登记、最终提交跨工具批次依次完成。
3. 执行和分析只追加成果，不并行修改任务状态。不同已登记任务的独立调用可以并行，但 02 不增加自动调度。
4. 任务通道使用专用 reducer，拒绝同批冲突写入和非法版本变化；先检查 `expected_plan_version`，不符一律返回 task_plan_conflict，即使 operations 完全相同也不例外，禁止最后写者静默覆盖。冲突返回当前版本和只读任务摘要，模型据此重新确认计划，不自动重执行 SQL。
5. 保留 Runner 现有会话锁。任何绕过正常 Runner 的写入口也必须遵守同一规则；不宣称单靠进程内锁就支持多写者或跨进程 CAS。

仅在 `wrap_tool_call` 外面加锁而仍读取旧快照，不足以实现该契约。实施需用真实图验证串行约束与 reducer 合并，而不仅测试工具函数。

**幂等采用版本匹配前提，不设置绕过版本检查的重放缓存。** 通过身份/参数检查及 expected_plan_version 后，才在整批候选视图中识别无变化操作：add 与服务器保存的完整 creation_operation 精确比较，status 与当前版本已保存的完整状态事实比较（包括成果、原因、failure_refs 等），不能只比 content/status。规范化补齐默认值，依赖等集合型列表先拒绝重复再按身份排序，content/reason 不做隐式空白折叠；操作批次保持原序。比较排除服务器时间、登记 tool_call_id 等不可由模型指定的审计字段，包含全部合法可写参数及操作类型。

add 仅在该逻辑任务仍为 revision=1、未作废且创建操作一致时可视为 no-op；若状态已经推进，回执必须明确“未新增，当前状态为 …”，不能让模型误认为又变回 pending。已 revise/void 的 ID 返回冲突，不以旧创建事实掩盖当前状态。整批全为合法 no-op 时不递增 plan_version；有真实修改时整批提交一次、版本加一。任何不匹配整批零写入；重放和冲突尝试仍消耗模型/工具预算。比如 p=3 上 add 成功得到 p=4，再带 p=3 重放相同操作仍冲突；重新确认 p=4 后完全相同 add 才可 no-op。同 content 改依赖则冲突。识别依据是作用域、当前 revision 和完整规范化操作，无额外模型可填幂等键，也不以新的 tool_call_id 认定新业务操作。

## 6. 证据归属与版本的配套契约（03、04）

### 6.1 先登记，再产生或沿用成果

`validate_sql/execute_sql/analyze_result` 增加必填 `sub_task_id/sub_task_revision`；E-/A- 沿用也必须提供目标任务。服务端用 context 补全身份，并在有副作用之前校验任务当前版本、可写状态与依赖。未知目标、旧版或任一终态目标直接拒绝；不得先执行再登记归属。首版只有 pending/in_progress 可产生新的授权、执行、分析或沿用记录，失败/澄清/作废任务不能继续查库，completed 后补证也须先 revise；终态目标的拒绝使用 `task_not_writable`，并提示先修订而非原参数重试。

该写入准入与读取分开：completed 上游可作为其他任务的已选成果被消费；`read_result` 仍可按会话权限读取已有结果，包括用于诊断的失败任务结果，但读取不改变任务终态，也不授予 finding 引用资格。真正的副作用前检查同时放在管线/分析/沿用服务内，不能只依赖模型可见工具参数校验。

简单问题最短流程为：登记一项 → 校验 SQL → 执行 → 登记 completed 及成果 ID → 单独提交。允许前置结构检索、时间解析和维度探针帮助规划，但它们不能直接成为业务完成证据。

`ValidationRecord/ExecutionRecord` 增加任务 ID、revision；query/pushdown 必填，probe 固定为 None。`AnalysisRecord` 同样保存完整目标版本，且 `ResultMeta` 在保存时记录产生结果的任务身份，避免跨轮仅凭消息或 SQL 猜归属。

授权键升级为既有作用域加 `purpose + sub_task_id + revision`，使用无歧义的规范编码。校验、执行、`trusted_record` 内部路径均检查用途、任务版本和原有 SQL/占位符摘要：

- A 校验的 SQL 不能用于 B 执行，旧 revision 授权不能用于新版。
- 同 SQL 的不同任务、版本和 purpose 各自保有独立授权。
- `validate_and_execute` 透传任务版本；pushdown 继承分析任务；probe 使用独立 None 作用域，不因 02 要求建立一个伪业务任务。
- 02 不增加 SQL 缓存；同 SQL 再次执行仍可能查库，防重复执行归问题 08。

### 6.2 成果必须能用于最终覆盖

任务 completed 的主成果只接受本轮、该任务当前版本下的 query E- 或分析 A-，包含受控沿用登记后的新 ID。

probe、T-/D- 和裸 pushdown E- 不作为主成果。下推执行轨迹通过对应 A- 成为可引用的分析成果。这比“任务允许裸 pushdown 成功、finding 又禁止引用它”更一致，避免制造无法覆盖的 completed 任务。

零行查询仍是成功执行，不要求 `saved_row_count>0`。完整性、截断和语义正确性分别处理；截断结果可以说明已保存部分，但不能凭截断输入声称总体结论已获支持。

### 6.3 分析输入与依赖快照

将内部 `AnalysisRecord.input_result_refs` 从 `list[str]` 升级为结构化列表，每项保存 `result_ref`、`evidence_ref` 和 `source_task_ref`。`evidence_ref` 使用完整 `(session_id, thread_id, run_id, evidence_id)` 身份，`source_task_ref` 使用 §4.1 的完整任务版本身份，均由服务端从实际来源记录补齐。这个字段作为唯一输入血缘列表，不再维护一个容易脱节的平行任务映射。消费结果占位符的 `ExecutionRecord` 同样保存此列表，无结果输入时为 `[]`。

在分析开始前统一校验所有操作的输入：

- 输入须有可核验的业务执行/分析记录，probe 输入拒绝，不只限制 compare。
- 同任务输入必须属于本任务当前 revision；不能把上次 revision 的执行重新解释为本次成果。
- 跨任务输入必须对应已声明依赖及其固定 revision；比较输出归比较任务。
- 通过结果占位符消费上游结果的 query 也要保存相同的版本血缘快照，不能只在分析记录中检查依赖。
- 依赖或任一输入血缘已失效时拒绝使用；血缘遍历需要去重和环检测，不能仅检查直接输入一层。

同一 result_ref 可能经沿用登记属于多个目标任务，不能通过 `records_by_result_ref()` 随便取第一条。建议同步将 `analyze_result.inputs` 从字符串列表升级为 `[{result_ref, evidence_id}]`，由模型选择工具实际返回的记录，服务端核对两者匹配，再填入完整来源任务身份；原 compare 参数内的 ref 仍指向这些已核验输入。其他路径若没有唯一来源选择，也应拒绝歧义，不能猜测归属。这个可见参数变化要一并更新工具契约、Skill 和测试。

保留同任务的“先 query 后 analysis”路径，不要求自依赖。其他任务只能在上游完成并选定成果之后消费其结果。`read_result` 继续只接收 result_ref，由已有记录与 ResultStore 校验会话归属，不新增一套手填任务参数。

### 6.4 跨轮沿用不能混淆任务身份

当前每次运行都会生成新的 run_id。本轮先登记本轮任务；沿用历史结果时，新登记证据归目标任务，历史来源保留其原 run/task/revision。历史任务 ID 不要求与本轮 ID 相等，也不能只用本轮 LedgerView 去寻找历史任务。

**模型可见来源寻址选择完整身份，不保留 E/A 裸 ID 的兼容猜测。** reuse_evidence 的业务成果模式接收 `source_evidence_refs: list[{thread_id, run_id, evidence_id}]`，并必填目标 `sub_task_id/sub_task_revision`。来源 session_id 固定取 ctx.session_id，因此在当前会话内形成完整 EvidenceRef；thread/run/evidence 字段由模型选择可见来源，不接受指定其他会话。目标的 session/thread/run 仍由当前 context 填入。全部来源必须属于服务端可见的本线程历史/轮换携带清单，不能因知道完整身份就任意检索归档扩大可访问范围。

保留原工具名称及 T/D 沿用能力：`evidence_ids` 仅接收 T-/D-，与上述 E/A 来源列表互斥；T/D 模式不填业务目标，E/A 模式必须填目标，拒绝混用及裸 E-/A- 参数。工具 schema 与函数签名须同时实现这些条件，不只更新文案。T/D 裸 ID 也必须在可见候选中唯一解析，歧义返回 evidence_source_ambiguous，不按遍历次序取值。

执行、分析和 E/A 沿用的成功返回均提供 source_evidence_ref，历史提示和交接清单也暴露相同的可选来源引用，保证模型能取得合法参数。服务端按完整来源键建立候选索引：不同 run 的同名 evidence_id 各自保留，同完整键且同事实可去重、异事实报 evidence_source_conflict，禁止字典覆盖。补全 scope 必须来自已知的运行归属/封存快照，不能仅拿结果文件的原生成 run 代替中间沿用记录的 run。解析失败整批拒绝，不写新的沿用成果。

规则区分如下：

| 场景 | 处理 |
| --- | --- |
| 同一 run 中任务已 revise，尝试沿用其旧 revision | 拒绝；需按新目标重新执行或分析。 |
| 沿用其他历史 run 的最终有效成果 | 在会话、数据源、结果可读、来源版本及血缘均可核验后，显式登记到当前任务；说明原生成时间，不宣称刷新。 |
| 沿用 A- | 原输入血缘快照不改写成目标任务；递归校验来源及输入。 |
| 只有旧结果文件，没有任务归属或来源任务快照 | 不能计入新门控的成功成果。 |

本轮 `dependencies` 只描述本轮任务 DAG；历史来源保存在证据来源引用中，使用完整身份核对，不把不同 run 的同名 ID 拼成自环。`reused_from` 可继续保留链首来源用于审计，但还需保存**直接沿用来源记录与任务版本引用**，不能因当前实现压平链首而丢失中间版本和输入信息。

直接来源保存为 `direct_reuse_from={evidence_ref, source_task_ref}`；保留 `reused_from` 的链首展示语义，不能用链首代替直接来源。每一跳都须能找到原始 E-/A- 记录及其结构化输入。当前 `ResultMeta.derived_from: list[str]` 只能说明文件来源，当前外部 EvidenceItem 投影也不保留完整私有血缘；二者均不足以单独恢复来源任务和分析输入。

运行结束后按 §8.2 封存完整运行快照；后续轮次不能重开原 run 修改它。归档提供按完整身份读取任务和原始证据的能力，线程轮换携带的 E-/A- 也要保留该引用。删除旧 checkpoint 后仍须能独立验证来源。来源缺失、过期清理、协议不支持或不可核验时返回明确错误，不能默认“历史来源可信”。沿用 ID 的生成与 reducer 去重事实字段均需包含目标任务版本及完整直接来源身份，不能只按 run+链首证据生成 ID；同一来源到多个目标、同裸 ID 的不同历史来源均不互相覆盖。

### 6.5 沿用与清理的互斥边界

只保护归档后的来源闭包仍有缺口：当前 `maintenance.py::_cleanup_result_dirs_global()` 在会话锁外按目录年龄删除结果，`_cleanup_snapshots()` 同样在锁外删除 PG result_snapshots；不能把会话其他清理已经取锁误当成它们也受保护。沿用完成校验到新证据写入、运行封存及 QA/run_errors 持久化之间，尚无新归档根可见；必须覆盖这个活动窗口。

首版采用**来源与目标同会话、运行和清理共用会话互斥**，不另建先检查后登记的临时 pin 机制：

1. PostgreSQL 模式复用 Runner 已持有的 SessionAdvisoryLock，覆盖来源发现、有效期/完整性及递归血缘检查、沿用 Command 应用、整个运行和 P3 收尾（含快照、QA/run_errors、交接清单）。工具消费同一持锁凭据，不用新连接重复取自己的锁。内部直接调用沿用/分析/占位符服务也要求有效运行持锁凭据；否则返回明确准入错误，不能依赖“通常由 Runner 调用”。
2. 将全局 R2/R3 改为按资源所属 session 分组处理，与该会话的线程/归档/运行快照清理使用同一把锁。仅候选枚举允许在锁外；取得锁后重新读取归属、年龄和保留闭包，直至实际删除结束才释放。取锁失败或锁后端异常跳过并报告，不能再在循环外做一次无锁全局兜底删除。PG result_snapshots 按其 session_id 过滤，且排除受保护 refs；新的运行来源快照是另一种资源，遵守同一互斥和闭包规则。
3. 来源和输入均须与 ctx.session_id 相同，不引入跨会话多锁顺序。运行先持锁时清理跳过该会话；清理先持锁时运行按既有 session_busy 停止，清理结束后的新运行重新检查来源，已删除则明确拒绝。活动运行即使尚无 QA 根或来源刚跨过清理时限，也不被并发实删；保护不刷新 created_at，不豁免各入口已有的沿用有效期校验。
4. ResultStore.delete()/purge_expired() 等直接物理删除入口同步收口：清理服务在持锁并校验闭包后调用受控删除，禁止保留一个绕过互斥的独立全局 purge。孤儿/坏元数据目录无法可靠确定 session 时只报告，不按 mtime 强删；锁内复核仍失败也跳过。会话发现补上运行来源快照及 PG result_snapshots 的 session，不能只依赖 sessions 元数据存在。
5. memory 模式当前跳过 PG 锁，须增加 Runner 与清理共用的进程内会话 guard，提供同样的非阻塞排他语义；同一会话内工具并行共享持有凭据，不各自抢锁。建议以 `persistence/session_guard.py` 统一 PG/内存适配和 SessionGuardLease，context 传递私有运行凭据，服务端校验作用域及存续状态，绝不写入模型参数或持久化记录。memory 模式不支持多进程共享结果根并发写/清理，配置层拒绝该组合；不能声称进程内锁提供跨进程保护。

锁在正常收尾后释放，之后 §8.2 的持久化根与递归闭包接管保留；若进程崩溃或归档失败而未留下持久化根，不承诺后续保留或自动续跑，恢复时须重新核验，缺失即拒绝。方案只约束受控应用入口，不保证外部人工删文件后的可读性；不为填补竞态而延长结果业务有效期。

## 7. 共享完成判定与答案覆盖

### 7.1 一个纯规则模块，两个调用位置

建议新增 `services/task_completion.py`，将结构校验、任务成果有效性、依赖血缘、覆盖集合和整体业务状态计算集中在此。I/O 由调用方预先装配为一致的只读快照；规则函数不查库、不调用模型、不写账本。

共享返回结构至少包含：`accepted`、`expected_status`、`errors`、`pending_task_refs`、`uncovered_task_refs`、`stale_evidence_ids`、`coverage_map` 和用于交付的任务结果摘要。

`submit_final_answer` 调用它，通过才保存原提交与服务端规范化后的答案记录；Runner 从最终 checkpoint 再执行同一规则。最终记录保存 `plan_version`、规则版本和覆盖映射用于审计，但 Runner 不仅相信缓存的 `accepted=true`。

结构归一与业务门控分层：复用 6.2 的 `normalize_final_answer_record()`，收尾时只生成一次 `normalized_submission`，随后一次计算语义判定 `decision`。原始提交始终单独保留用于审计；评估、交付和归档条件 b 共用以下资格视图，不各自重算或重新接受原始 payload：

```python
# 方案示意：normalized_submission 已通过结构及运行归属校验；
# decision 来自同一只读账本快照上的共享业务规则。
eligible_submission = (
    normalized_submission
    if normalized_submission is not None and decision.accepted
    else None
)
```

`accepted` 表示提交合法，不表示业务成功。完整交代失败任务、业务状态为 failed 的合法提交仍可 accepted=true，并继续交付模型答案。来源快照读取由调用方完成，纯规则只消费装配结果；缺失来源作为拒绝依据传入，不在纯规则内隐式读文件。

### 7.2 扩展提交结构

`FindingItem` 增加提交内唯一 `finding_id`，以及非空 `task_refs: list[{sub_task_id, revision}]`。现有 `text/evidence_ids` 保留，去除纯空白文本；`DbAgentFinalAnswer` 增加 `unresolved_task_refs`，仅列本轮失败和待澄清任务，使用 `Field(default_factory=list)` 默认空列表，工具参数与之保持一致。没有 failed/needs_clarification 任务时，恰覆盖的集合即为空集；存在这些任务时，省略该字段虽可通过结构校验，仍会因默认空集漏覆盖而被业务门控拒绝。显式 None 不等同于省略，不接受为列表。

`finding_id` 由模型在提交时填写，首版格式为 `^F-[1-9][0-9]{0,5}$`（例如 F-1、F-2），同一提交内不允许重复。它只是覆盖映射的局部标签，不是服务端签发的证据 ID，不采用 evidence_id 的哈希样式，也不能证明内容真实。提交被拒后可复用同一标签；接受后原样保存，Runner 复核格式和唯一性，不另行重编号。缺失、空值、格式错误或重复均按参数校验拒绝，且不写最终记录。

三个“问题”字段按以下分工固定：`unresolved_task_refs` 承担失败/澄清任务的结构化覆盖；任务级 `clarification_question` 提供实际阻塞问题；原提交的 `open_questions` 保留为模型自由填写的非阻塞补充问题，不承担任务覆盖职责，不与 unresolved 做结构化一致性校验，也不参与 expected_status 计算。因此 unresolved 为空而 open_questions 非空可以合法提交；真正阻塞本轮任务的问题必须登记到任务账本，不能仅填进 open_questions。自由文本仍有语义误写风险，由题集与抽查评估，不能声称此处已经自动校验。

交付问题列表使用以下固定算法，不依赖字典遍历顺序、工具完成先后或展示端语言环境：

1. 先取本 run 最新且未作废、status=needs_clarification 的任务，按 `(sub_task_id, revision)` 升序排列：sub_task_id 使用原字符串的 Unicode 码点序，revision 按整数比较；例如 T10 排在 T2 前，不采用自然数排序。依次提取 clarification_question，权威问题全部在前。此排序使用已有身份字段，不新增登记序号或以可能同秒的时间戳决定次序。
2. 随后追加原提交 open_questions，保持其原始列表顺序，补充问题全部在后。
3. 对候选文本使用 Python `str.strip()` 去除首尾空白，丢弃结果为空的条目；从前向后按清理后的完整字符串精确去重，保留首次出现。保留内部空白，不做大小写折叠或其他 Unicode 归一化，也不按文本再排序。因此重复补充不会挤掉已有权威问题，不同任务的相同问题只显示一次。
4. 将该列表一次性写入 `delivery_answer.open_questions` 和 `DbAgentResult.open_questions`；原提交中的列表保持原样归档。任务覆盖与澄清计数始终读账本，不读合并后的展示列表；显示去重不合并任务身份。

第 3 步丢弃空条目是展示清理规则，不能代替任务字段校验。按状态必填的 reason/clarification_question 在登记时即拒绝纯空白；共享提交门控与 Runner 还需复核，避免损坏或绕过登记的账本进入交付。空白权威问题或必填原因须作为非法任务记录拒绝，不能过滤后仍接受提交，也不能渲染成空的“未完成事项”。dependency_blocked 的服务端生成原因适用同一非空白要求，但该状态仍不要求伪造 clarification_question。

覆盖规则：

1. task_ref 必须指向本轮最新、未作废、status=completed 的任务版本。
2. 对 finding 中的**每个** task_ref，该 finding 至少引用一条属于该任务版本、且已经选入其成果列表的可信主证据。
3. 同一 finding 覆盖多个任务时，每项分别满足规则；不能给 A 的一条证据加上 A/B/C 三个标签就认为全部覆盖。
4. 每个 completed 任务至少被一条合法 finding 覆盖。未被选为主成果的探索记录无需全部引用；允许将它们作为附加旁证，但覆盖计算只认属于该 task_ref、且已选入其成果列表的主证据。附加证据必须属于本轮某个最新且未作废、status=completed 的任务版本，同时通过可引用类型和完整血缘检查；来自其他任务时不把该任务自动计入覆盖。仅有探索证据的 finding 不能取得覆盖资格，任一附加证据非法也拒绝整次提交，不能靠删除该 ID 后继续成功。
5. `unresolved_task_refs` 必须恰好覆盖所有 failed/needs_clarification 最新任务，不接受重复、旧版或未知任务。原因与澄清问题从账本读取，不让最终提交重写历史原因。
6. voided 不计入成功覆盖，但由服务器追加作废说明；其他状态不能伪装为成功 finding。全局口径、限制继续放既有字段。

`covered_finding_ids` 不反写任务账本，由提交内容反算，避免维护两套覆盖状态。

上述旁证资格是相对现行“任意本轮 query E-/A- 可引用”的有意收紧：failed、needs_clarification、voided 或已被新版取代的任务版本名下，即使存在真实且可读取的结果，也不能作为 finding 的主证据或附加旁证。例如 partial 场景中，T2 查询成功但后续分析失败、任务最终 failed，则其查询结果不能挂到 T1 finding 下作为旁证。真实执行事实仍保留在 evidence、结果文件和诊断记录中，并可按异常交付规则说明；保留结果与取得 finding 引用资格分别判断，不能靠临时改挂任务或旧版沿用绕过该限制。

仅有上述标签仍不能保证 answer 自由文本真的包含分项结果。建议共享交付规范化函数在最终正文附上确定性的“分项结果/未完成事项”段落，逐项展示合法 finding 的文本、任务失败原因和澄清问题；已有完全相同条目可去重。提交记录区分原始内容与实际交付内容，实时、归档、历史和 CLI 读取同一交付正文，与 6.2 的 `answer/delivery_answer` 分工衔接。这里保证已登记分项确实可见，仍不替代结论的语义校验。

### 7.3 正常提交的校验顺序

1. 原有单独调用、重复提交和参数结构检查。
2. 读取本 run 最新任务视图；禁止空集合以及全部作废后的真空通过。
3. 检查计划版本、任务身份、执行依赖 DAG、终止审计依据和成果血缘，并按任务状态复核必填 reason/clarification_question 的字符串类型及 strip 后非空约束；failure_refs 核对原始错误归属及事实，replacement 核对历史身份和决策时快照，终态历史引用按 §5.2 核验，不误用“必须仍是当前依赖”的执行条件。
4. 检查每个 completed 任务的主证据；拒绝旧版、其他任务、probe 或来源不可核验的证据。
5. 检查 pending/in_progress；存在则拒绝普通最终提交，要求继续处理或显式解释终止。
6. 检查所有成功 finding、任务覆盖、未完成集合及 no_data 资格。
7. 计算唯一业务状态，与模型提交的 status 比较，不一致则拒绝并返回 expected_status。
8. 规范化交付正文，写入最终记录。提交工具不顺手把任务改成 completed。

首版保留第 7 步的严格拒绝：status 是模型对本轮业务结果的明确声明，正文分项补全和展示去重属于交付格式规范化；两者不采用同一改写规则。即使其他内容全部合法，服务端也不静默把 completed 改成 no_data，以免掩盖模型对结果的理解偏差。错误包返回原 status、expected_status 和触发判据，模型只需修正提交，不重新执行 SQL；例如全任务主成果均为未截断零行而模型报 completed，应以 `final_status_mismatch` 拒绝，并要求改报 no_data。原始/交付分存用于保留真实来源，不意味着所有语义字段都可自动修正。

这是增加一次模型/提交尝试的有意取舍，登记和提交被拒的尝试均消耗原有预算，不退款、不新增无限重试。预算不足时按 §8.1 收敛并保留结果，不为取得“合法成功”强制追加模型调用。Runner 因运行异常、预算或持久化故障调整最终交付状态属于 §8.1 的服务端故障判定，与在正常提交中静默纠正模型业务声明是不同路径。

建议错误码包括：`task_not_registered`、`task_revision_mismatch`、`task_not_writable`、`task_plan_conflict`、`task_operation_conflict`、`invalid_task_dependency`、`invalid_task_failure_ref`、`invalid_task_replacement`、`task_not_terminal`、`task_evidence_mismatch`、`stale_task_inputs`、`task_answer_uncovered`、`invalid_task_outcomes`、`final_status_mismatch`、`no_data_not_proven`。沿用另提供 `evidence_source_ambiguous/evidence_source_conflict`，缺少运行持锁凭据使用 `session_guard_required`。错误包应包含具体任务版本及修复动作；是否 retryable 按原因确定，不能全部提示“原参数再试”。

### 7.4 业务状态映射

先通过结构、证据和覆盖门控，再按下表从上至下计算。表中的任务集合均为最新且未作废版本。

| 条件 | 正常提交行为 / expected_status |
| --- | --- |
| 没有有效任务 | 拒绝提交；自然结束时 failed。 |
| 有失效血缘、非法执行依赖/终止审计依据、缺证据或缺覆盖 | 拒绝提交；不能用 partial 掩盖结构不合法。合法的终态历史依赖不因此拒绝。 |
| 有 pending/in_progress | 拒绝提交，包括上游已 needs_clarification 的依赖阻塞场景；先按 §5.2 批量登记 dependency_blocked 等明确终态。 |
| 至少一项 needs_clarification | needs_clarification；同时保留其他已完成分项及失败原因。 |
| 全部 failed | failed；findings 可以为空，unresolved 集合必须完整。 |
| completed 与 failed 混合 | partial；所有 completed 分项仍须有证据和覆盖。 |
| 全部 completed，且所有分项均通过严格空结果判定 | no_data。 |
| 全部 completed，存在有数据结果或不能证明全空 | completed。 |

空结果判定首版采用保守且可执行的规则：至少一项任务，且每项选定的全部主成果均有可信原始记录，可靠保存行数为 0，且 `source_truncated is False`。缺少截断字段不能按未截断处理。不能由模型填 `no_data=true` 决定。`COUNT(*)=0` 返回一行、`SUM=NULL` 返回一行，都不满足该行数规则；作为 completed 的事实结论回答即可。若以后要识别这些聚合语义，另加结构化判据和专项测试。

可靠行数读取原始 `saved_row_count`，要求 `type(value) is int and value >= 0`：缺失、None、布尔值（包括 False）、负数、字符串、浮点数均为未知，不能从默认 `row_count=0` 的交付投影反推。相同完整证据身份的原始记录发生行数冲突时也为未知，不取第一条或默认零值。建议新增共享纯函数 `services/result_facts.py::known_saved_row_count(record)`，供 6.2 的 `_known_saved_row_counts()` 与任务门控复用；身份聚合和冲突处理仍集中在映射构建处，门控消费同一映射。合法分析成果也须按自身原始记录核验，不能拿输入文件行数代替输出行数。

“未截断”也必须按完整证据身份聚合全部原始记录，不能先取首条/末条：该组非空且每条都满足 `source_truncated is False` 才能证明未截断。任一条为 True、缺失、None、整数（包括 0）或其他非布尔值，都不能证明未截断；False/True 混合以及 False/缺失混合也一样。重复的显式 False 可保持证明，记录顺序不得影响结论。建议同模块增加纯函数 `is_proven_untruncated(records)`，共享规则先对原始证据按完整身份分组，再与可靠行数映射共同判断 no_data，不从默认公开投影倒推。无法识别归属的损坏记录按账本结构错误拒绝，不能先丢弃再声称“所有记录均未截断”。

首版对此类截断缺失/冲突采用“不能证明全空”的保守降级，并给出明确诊断；不静默选择某条记录，也不单凭该未知项将合法业务任务改为失败。若其余任务、证据和覆盖均合法，整体按上表 completed；若同时存在其他账本一致性错误，仍按对应规则拒绝。正常执行/分析 reducer 已比较截断字段，不代替 Runner 对绕过 reducer 的旧 checkpoint 或直接注入记录的防御性聚合。

零行任务仍是 completed 状态，并以引用该空结果证据的 finding 覆盖；`no_data` 是整个运行的业务交付状态，不新增任务状态。多个任务一项有数据、一项为空且全部成功，整体 completed，并分别说明。只查了一个空结果、另一个任务尚未处理，不得整体 no_data。

### 7.5 Runner 不能“过滤后继续成功”

改造 `_finalize()`：显式取得 run_id、预装配来源与任务快照，按 §7.1 生成一次归一提交及语义判定；`_evaluate()`（当前没有 run_id 参数）接收 run_id、该判定和 `eligible_submission`，不能只检查投影 evidence 是否非空。

- 发现原提交不合法时，`eligible_submission=None`，记录明确门控失败，正常退出判 failed；不能仅改 status 后继续交付其非空正文。
- 不先丢弃一部分 ID 再把剩余答案当作通过；若展示层需要过滤，过滤后的内容也不得恢复成功资格。
- `_mark_primary()`、RunFailureRecord 的类型约束和 Web 安全错误映射同步支持 `task_completion_rejected`；具体原因保留在共享规则 errors 中，既有业务 failed 任务也要有可定位原因。
- 无效提交的正文、findings、模型自报口径/限制和补充 open_questions 均不进入交付，只保留原始审计值；受信任务原因和问题另行从已验证账本生成。Agent 已调用时，复用 6.2 的 `_build_fallback_answer()` 及确定性任务摘要，`answer_source=system_fallback`。合法提交为 model，前置拒绝为 none；不引入第四种来源，不新增模型调用。
- `_archive_run()` 条件 b 使用同一个 eligible_submission，门控拒绝时必为假，不能因结构合法或原 payload 自报 completed 就通过；真实执行条件 a 保持原规则，仍可保存失败 QA。归档原始提交不因资格视图为空而丢失。

这是对现有 6.2 收尾的必要合流：其 `_finalize()` 只在没有非空有效正文时触发兜底；若任务门控只把状态改 failed、却继续传递原归一 payload，将仍输出无效正文，并可能误获沿用归档资格。新方案必须把上述同一资格结论贯穿评估、正文构建和归档；后续运行异常/预算/持久化优先级继续按 §8.1，不由 accepted 覆盖。

兜底触发由现行 `invoke_started and not answer.strip()` 明确扩展为“Agent 已调用，且没有可合法交付的正文”：缺失、空白、结构/运行归属无效，或 `decision.accepted=False` 均在内。替换谓词如下；其中 answer 已仅从 eligible_submission 生成，无资格时为空，绝不读取原始提交正文：

```python
# 方案示意：状态已按 §8.1 判定，eligible_submission 沿用 §7.1 的同一结论。
should_fallback = invoke_started and (
    eligible_submission is None or not answer.strip()
)
if should_fallback:
    answer = self._build_fallback_answer(status, evidence, known_counts)
    answer_source = "system_fallback"
    # 再按已核验任务账本补充确定性任务摘要及问题列表。
```

资格合法且业务 status=failed 不满足“无可合法交付正文”，保留 model 来源；invoke_started=False 的 P0 拒绝也不进入兜底。该谓词只决定交付正文来源，不改写先前确定的预算、运行或持久化故障状态。

`FinalAnswerGateMiddleware` 仍以“有效记录已被接受”作为正常结束信号；拒绝提交不写 `db_final_answers`，因此不会提前结束。漏提交提醒应带上待处理或未覆盖任务摘要；提醒次数和全局预算仍有限，不能形成无限修正循环。

## 8. 异常收尾、持久化与展示

### 8.1 普通完成门控与异常收敛分开

正常提交要求没有 pending/in_progress。模型异常、预算耗尽或 checkpoint 故障时，不再调用模型补任务状态，也不要求重新通过普通成功门控才能交付已有结果。

保留现有 Runner 优先级：持久化异常 → `persistence_error`；运行异常或工具集合异常 → `failed`；预算/时限停止 → `budget_exhausted`；之后才考虑有效提交的业务状态。P3 归档失败仍按现有规则调整结果，不能被任务状态覆盖。

服务器在可核验快照中保存运行中止原因、停止时 pending/in_progress 列表及各任务已有状态；可以记录独立的 `interrupted_tasks` 收尾摘要，不必把原始 pending 记录批量篡改成 completed。兜底文本列出已完成结果和未完成事项，不伪造 `submit_final_answer` 或 findings。

若没有可信账本，只说明无法核验，不推断任务成功。尚未开始 Agent 调用的 P0 拒绝不创建虚假任务，不为了满足“简单题至少一项”覆盖原有错误。进程被强杀而无法回到 Runner 的情形仍需另层恢复机制。

### 8.2 持久化与历史来源

checkpoint 保存私有任务与计划通道。新增独立的、不可变的**运行来源快照**，QA 和 run_errors 均引用它并保存任务摘要、覆盖结果和中止说明；不能仅在成功 QA 保存任务，否则失败轮次无法解释。只存任务 evidence_ids 不够：旧 checkpoint 清理后，还必须找到原始执行/分析记录及每一跳输入。

建议 `QaArchive` 增加 `write_run_snapshot()/read_run_snapshot()`，以及基于完整身份的 `read_task_snapshot()/read_evidence_snapshot()`。明确持久化契约如下：

| 项目 | 首版约定 |
| --- | --- |
| 寻址 | namespace 为 `("db_deepagent", "run_snapshots", session_id)`；key 为 `[thread_id, run_id]` 的规范 JSON 编码。读写都校验记录内作用域，不能依靠 request_id 猜来源。 |
| 版本 | 独立 `RUN_SNAPSHOT_SCHEMA_VERSION=1`，另存账本协议版本和完成规则版本；不与 6.2 的 QA 归档版本 2 混用。未知版本拒绝作为成果来源。 |
| 身份及任务 | 服务端 scope（含 session/thread/request/run）、plan_version、所有任务的全部 revision、creation_operation/dependencies/failure_refs/termination_context/replacement，含替代目标决策时快照；不得只保存最新 completed 任务。 |
| 原始证据 | 本轮原始 executions、analyses、任务关联 tool_errors；包括结构化 input_result_refs、完整 task_ref、direct_reuse_from、链首 reused_from 和结果 ref。保留审计原值，读取时再验证，不能用公开 EvidenceItem 列表替代。 |
| 收尾 | 覆盖结果、门控结论和 interrupted_tasks，记录 `run_status_at_seal`。快照存在仅证明封存事实，不证明整体成功、答案已送达或之后 P3 一定成功。 |
| 写入边界 | 按 §6.5 保持同一会话 guard，Runner 装配最终快照后、写 QA/run_errors 前封存；相同内容可幂等写，不同内容冲突须报错，不能静默覆盖。这不是跨进程 CAS 保证。已有持久化故障路径无法承诺必写成功；缺失或不完整快照不得沿用。 |
| 归档关联 | QA/run_errors 保存 snapshot_ref，读取方按完整身份获取只读副本；整体 failed 轮次内某个已 completed 任务能否沿用，仍按该任务的当前有效版本、选定成果及完整血缘判定，不能只看记录在 QA 还是 run_errors。 |

封存后不得补写历史 run；轮换携带来源引用及必要原始事实。取得 §6.5 同一会话锁后，清理才以仍在保留期的 QA/run_errors、轮换携带引用为根，重新计算递归保护直接沿用来源、分析/占位符输入涉及的快照和结果文件的保留闭包；不能把锁外扫描结果当作删除依据。归档保留期清理完成后，按最终根集合计算闭包并删除不受保护的资源，至删除完成才释放锁；读取保护根或闭包失败时跳过该会话后续资源实删并报告，不用空集降级删除。缺源或循环等错误必须显式报告，不能把不完整闭包视为可信。来源保留保护不延长原有成果的可沿用有效期；过期成果即使文件仍在也不能沿用。具体 TTL 随现有配置统一实施，并测试先删 checkpoint 仍可核验、孤儿快照可清理以及来源过期时拒绝。活动运行尚未封存的窗口由互斥保护，不要求它先写 QA 才有保护资格。

结构化 `input_result_refs` 必须同步修改 `refs_of_record()`，从条目提取字符串 ref，再供归档清理保护。只改分析写入会导致当前 `set` 收集遇到 dict 或遗漏输入文件保护。

采用总体文档已有的未上线直接切换前提：旧的无任务记录、旧版结构化输入缺失记录不进入新成功门控，不根据自然语言或 SQL 自动重建任务。实施时显式标记账本协议版本并重建演练数据；本文不执行历史删除。历史展示与把旧证据作为当前成果是两条不同路径，后者必须满足新规则。

字段过渡须区分默认与必填：旧提交仅缺 unresolved_task_refs 时按 §7.2 归一为空列表，不因此判结构非法；若旧 finding 缺少新必填 finding_id/task_refs 等字段，归一返回 None；即使结构可归一，没有新协议要求的有效任务账本也会被语义门控拒绝。以上非法旧记录若进入本轮 Runner 收尾，均不作为 eligible_submission，按 §7.5 交付：没有更高优先级停止原因时 failed，Agent 已调用时使用系统兜底，原值留档。历史只读展示仍走原归档版本 reader，不用新提交 schema 重评估旧轮次，也不据此承诺恢复执行旧 checkpoint。

### 8.3 API、CLI 的配套改造

内部 FindingItem 的新增引用可以由现有 `WebFinding(text,evidence_ids)` 显式投影隐藏；无需首版把任务账本作为 Web 必填协议。CLI JSON 的内部结果字段会随 schema 增加，应更新契约测试；普通文本展示采用规范化交付正文。

`unresolved_task_refs` 留在内部提交、覆盖校验及归档中，首版不新增 Web/CLI 必填输出字段。`DbAgentResult.open_questions` 采用 §7.2 的权威问题与非阻塞补充合并列表，实时 `WebQueryResult` 继续显式复制这一展示字段，CLI JSON 采用相同列表；阻塞原因及任务引用已由规范化正文交代。CLI 当前将 open_questions 标为“待澄清”，实施时与 Web 一起改为“澄清与补充问题”，避免把 completed 下的非阻塞建议展示成尚有阻塞；该列表非空不改变 status。

启用本方案任务门控时，**交付 payload 的 `open_questions` 即 §7.2 算法产生的合并列表，不是原提交列表的拷贝**。6.2 §7.3 当前示意代码的直接复制仅适用于其未接入任务账本的阶段；两方案合流时必须替换该赋值，并将同一个列表传入 delivery_payload、DbAgentResult 和归档。原始列表只作为原始 answer payload 的内容保留，不能被交付列表覆盖。QA 归档 reader 消费保存的 delivery_answer，不重新合并或排序；旧归档继续按既有版本读取，不追补新规则。

**Web 历史另有真实改造，不能假设它读取 QA 的 delivery_answer。** 当前 `WebTurn`、`WebStore.write_turn()` 没有 open_questions，Web 历史由 WebStore 自己保存。首版新增 `WebTurn.open_questions: list[str] | None = None`，`write_turn(..., open_questions=None)` 同步保存；`runs.py::_make_finalize_hook()` 将最终安全投影后的同一列表写入，明确无问题的新记录为 `[]`，旧记录缺失为 None（未知），不从正文或当下账本重建。安全复核拒绝分支写安全投影的列表（当前为 `[]`），不能把被抑制的原问题单独写入历史。

前端 `api/types.ts::WebTurn` 同步兼容可选/null 列表，`useChat.ts::snapshotTurn()` 和历史展示消费保存值，实时快照与刷新后的历史一致。旧记录 None 不显示问题列表，也不能作为“明确没有问题”的统计事实。新增字段须覆盖严格 DTO、WebStore 旧记录读取与写入回读测试；这里是有默认值的增量历史契约，不切换历史存储来源。

内部 `AnalysisRecord.input_result_refs` 改为结构后，Runner 显式提取其中 ref，使外部 `EvidenceItem.input_result_refs/WebEvidenceItem.input_result_refs` 继续为 `list[str]`；SQL 执行的私有输入血缘保存在原始记录/快照中，公开 sql_query 投影继续遵守现有 input_result_refs 为空的校验，不能直接把私有列表复制进去。

需要特别处理 [dto.py](../src/api/v2/dto.py) 的 `WebEvidenceOrigin(**dict(item.reused_from))`：它使用严格模型，内部来源增加任务字段后直接解包会被拒绝。应改为显式白名单投影，或经过有版本的公共协议升级，不能声称内部增加字段完全不影响 API。

预算验收应区分理论最短脚本与真实检索路径：在只调用“登记→校验→执行→终态→提交”的受控单任务脚本中，基线为 5 次模型步骤、5 次工具调用、1 次受预算统计的业务执行（EXPLAIN 不计入现有 db_execute）；登记拒绝后纠正增加 1 次模型和工具尝试，合法内容仅 status 不符后重提也各增加 1 次，两种拒绝都发生时共 7/7/1。应验证真实中间件顺序，成功后 FinalAnswerGate 结束运行，不额外预占第 6/7/8 次模型步骤。这个数字不是实际模型检索、探针、摘要或传输尝试的总开销承诺。

# db_deepagent 最终答案兜底问题与补齐建议

整理日期：2026-11-12。

## 1. 问题与讨论范围

本文只讨论 [6.1 能力补齐清单](6.1_db_deepagent能力补齐问题清单与实施建议.md) 中的 **01：最终答案缺少确定性兜底**，说明问题、旧链已有实现及方案，并在 §7 给出代码修改清单、新增函数和核心代码片段，不展开其他能力改造。

**实施状态（2026-11-12）**：§7 方案已全部实施并通过审核闭环——codex 三轮实施审核（末轮仅余一项测试缺陷，经用户裁定补正）与 Kimi 两轮复审（第二轮 PASS）；完整记录见 [实施收尾记录](reviews/doc62_implementation_closeout.md)。§1–§6 为实施前的分析与决策基线，描述的是实施前行为，保留用于追溯，不代表当前代码状态；当前行为以代码与收尾记录为准。

具体场景是：**SQL 已成功执行并保存结果，但后续模型异常，或运行结束时没有有效最终答案，导致返回空答案。**

```text
SQL 校验通过
    ↓
SQL 执行成功，结果已保存
    ↓
模型继续读取、分析或组织答案
    ↓
模型调用失败，或未有效提交最终答案
    ↓
当前 Runner 可能返回 failed + 空 answer，但保留已有 evidence
```

当前并非完全丢失执行结果。Runner 已有读取执行账本、保留证据和按条件归档的处理；缺少的是运行未正常完成时，对已有结果提供一致、可展示的说明。

依据：

- [当前 Runner](../src/modules/db_deepagent/runner.py)：`_run_locked()`、`_finalize()`、`_evaluate()` 和 `_archive_run()`。
- [现有故障注入测试](../src/tests/db_deepagent/unit/test_runner_persistence.py)：`test_sql_success_then_model_failure_archives_qa` 明确断言失败状态、空答案和执行证据保留。

“确定性兜底”指通过代码和可信记录生成基本说明，不要求再成功调用一次模型，也不意味着异常后仍能完整回答用户问题。

本文所称“有效最终答案”，至少要求符合 `DbAgentFinalAnswer` 的结构、正文为非空白字符串，并通过本方案明确的运行归属校验及既有证据引用检查。当前只有 `min_length=1`，纯空白正文仍可能被接受；因此补齐方案必须同时修改提交校验、Runner 评估和归档资格，不能只在评估之后替换文本。

## 2. 旧 LangGraph 代码如何处理

### 2.1 固定进入总结节点

旧父图在正常执行路径中安排最终总结：

```text
简单问题：sql_exec → summarizer → END
复杂问题：sql_exec → check_completion → 继续执行或 summarizer → END
```

这由项目定义的节点和边控制，不需要模型自行决定调用最终答案提交工具。见 [旧父图](../src/modules/nl2sql_father/graph.py) 的执行后路由。

### 2.2 模型总结失败后重试并转为模板

[旧 Summarizer](../src/modules/nl2sql_father/nodes/summarizer.py) 的处理是：

1. 从执行结果中提取成功记录。
2. 默认调用模型生成总结，最多尝试 3 次，包含首次调用。
3. 普通可重试异常达到上限后，改用模板。
4. 根据错误文本识别到部分 400、401 错误时，直接改用模板。
5. 模板不调用模型，生成 `summary` 后返回。

默认次数见 [旧父图配置](../src/modules/nl2sql_father/config/nl2sql_father_graph.yaml) 的 `summarizer.llm_retry`；配置 `use_template=true` 时可直接使用模板。

### 2.3 旧模板提供的保证有限

`_build_template_summary()` 统计成功执行记录中的结果行数：

| 结果行数 | 模板内容 |
| --- | --- |
| 0 | 查询成功，但未找到相关数据。 |
| 1 | 查询成功，找到1条记录。 |
| 多行 | 查询成功，共找到 N 条记录。 |

例如，SQL 返回 `total_sales = 1280000` 时，旧兜底只会说“找到1条记录”，不会自动把金额值组织成业务答案。原始数据通过旧结果结构中的 `execution_results` 另行交付。

旧代码也有覆盖边界：

- `get_llm()` 构造模型发生在兜底的 `try` 外，构造失败可能直接向外传播。
- 模型正常返回空字符串时，没有非空检查，可能直接返回空 `summary`。
- 图在进入 Summarizer 前异常退出时，不保证总结节点执行。
- 多查询中有成功也有失败时，基础模板只统计成功结果，不能据此保证完整交付或准确说明全部失败。

因此，准确的迁移结论是：**旧链已有“总结模型调用失败后的有限重试与基础模板兜底”，新链尚未承接；不能表述为旧链在任何异常下都保证有完整答案。** 这层保障由项目代码实现，不是 LangGraph 自动提供。

## 3. DeepAgents 能否实现

**可以。现有 API 足以支持，无需恢复旧父子图。** 本文以项目当前安装的 `deepagents==0.7.34`、`langchain==1.4.9` 为基线。

建议分为两层：

| 层次 | 作用 | 建议位置 |
| --- | --- | --- |
| 有限重试 | 对适合重试的模型故障做有限恢复 | 通过 DeepAgents 的 `middleware=` 接入已安装 LangChain 的 `ModelRetryMiddleware`。 |
| 最终结果兜底 | 模型恢复失败或没有有效最终答案时，基于可信记录生成说明 | 现有 Runner 的结果评估与归档收尾流程。 |

`ModelRetryMiddleware` 支持设置重试次数、异常筛选和失败策略。其 `max_retries` 是首次调用之外的次数；若要对应旧链最多 3 次尝试，应按首次调用加最多 2 次重试理解。

但该中间件默认失败提示不会自动读取本项目的 SQL 执行账本，也不会生成符合本项目要求的最终答案记录。**只加重试中间件，不能完成 01。**

当前独立的 `summarizer_model` 用于压缩对话上下文；`FinalAnswerGateMiddleware` 用于已提交后结束和漏提交提醒，两者也不等于最终答案兜底。

## 4. 建议先实现的最小范围

### 4.1 在 Runner 统一收敛

建议在现有结果评估和归档流程中补充统一处理：

```text
Agent 正常结束或异常返回 Runner
    ↓
按现有规则评估状态、有效最终答案和本轮可信证据
    ├─ 有可使用的有效最终答案：保持正常处理
    └─ 缺少可使用的有效最终答案
          ├─ 有可信查询或分析结果：生成基础结果说明
          └─ 无可信结果或无法确认结果：生成明确失败说明
    ↓
统一形成对外交付内容
    ↓
按现有持久化条件归档，并供 Web、历史、CLI 和本地记录使用
```

选择 Runner 是因为它已有捕获 Agent 异常、读取 checkpoint 账本和归档的职责，能够同时覆盖“模型抛异常”和“运行结束但未提交答案”。仅依赖正常返回后的模型 hook，不能覆盖全部这类退出。

兜底仅使用可核验的本轮记录，不能把模型未接受的自然语言草稿当作正式答案，也不能直接把本会话其他轮次的结果当成本轮结果。已有证据沿用须符合当前登记规则。

本方案的兜底触发范围限定为已开始调用 Agent 的运行。会话忙碌、锁后端失败或 P0 校验拒绝等“请求未执行”路径保持原有结构化错误和答案行为，不将它们描述为模型最终答案生成失败。

### 4.2 基础模板只说明已确认事实

有可信结果时，可采用类似文案：

> 本轮查询已执行，但完整答案尚未生成。以下是已确认的执行情况。

具备可靠行数记录时，可以说明保存行数；例如：

> 本轮已记录查询结果，其中一项记录了 100 行。完整答案尚未生成。

首版采用面向业务用户的简版正文，不展示“账本”、evidence_id 或“保存行数未知”；无法确认行数时省略行数句，不把未知写成零。技术定位信息继续保留在既有 evidence/warnings 和证据面板中，不另建一套答案或新 DTO。下面的“结果 1”等序号只对应本次 evidence 的展示顺序，不是稳定证据标识。

必须保留以下边界：

- 有 `source_truncated` 时明确说明结果被截断；保存行数不能当作总体行数。
- 多条查询分别说明各自结果，不默认把多次查询的行数相加当作业务总量。
- 零行结果可说明该次查询没有返回记录，不能据此断言整个问题都没有数据。
- 尚不知道全部任务是否完成时，不声称完整回答了用户问题。
- 首版不读取结果文件，只陈述账本中可核验的执行事实，不承诺结果文件当前可读，也不编造具体值。
- 未完成模型分析时，不由模板补猜指标含义、单位、比较关系或业务结论。

没有可信结果或账本读取失败时，应说明本轮未完成及无法确认结果，不声称查询成功。

### 4.3 第一步保留现有状态和错误

建议将“提供可展示说明”和“是否调整状态为 partial”分开。第一步保留 persistence/runtime/预算等现有状态优先级，同时新增无效正文检查：空白提交不再被视为有效最终答案，应与缺少最终答案一样判为 failed，除非已有更高优先级故障。不能先保留 completed，再追加系统失败说明。

| 场景 | 建议状态处理 | 兜底内容 |
| --- | --- | --- |
| 模型失败或未提交有效答案，已有可信结果 | 保留当前评估出的 failed | 提供已有结果说明，保留错误和证据。 |
| 已开始调用 Agent，但没有可信结果 | 保留 failed | 明确说明本轮未完成，不生成结果结论。 |
| 预算耗尽 | 保留 budget_exhausted | 有可信结果时说明已有结果，同时保留停止原因。 |
| 持久化故障 | 保留 persistence_error | 说明故障及归档状态；只展示仍可核验的内容。 |
| 工具集合异常等其他运行故障 | 保留原评估状态 | 不因发现结果记录而改判成功。 |
| 尚未调用 Agent 的前置拒绝或失败 | 保留原评估状态和答案行为 | 不新增模型答案兜底或兜底 warning，保留原有结构化错误。 |
| 已开始调用 Agent，原提交为 completed 但正文只有空白 | 无更高优先级故障时为 failed | 将原提交视为无效；可生成兜底，不能返回 completed + system_fallback。 |

`failed` 与非空 `answer` 可以同时存在：前者说明整轮未正常完成，后者向用户解释已有结果和失败情况。

后续若需要将明确的最终生成故障改为 `partial`，应单独定义错误分类和判定条件，不把所有 runtime 异常统一转换为部分成功。本项第一步不依赖该状态调整。

### 4.4 同步返回、归档和展示内容

当前 `_archive_run()` 从答案记录提取 payload，不是直接读取返回对象的 `answer`。只在构造 `DbAgentResult` 前填入字符串，无法同时保存实际交付说明。本方案选择保留归档原 `answer` 的模型提交含义，另增 `delivery_answer` 保存交付内容；不把现有 `answer.status` 改成 Runner 状态。

当前各入口还存在以下差别：

- [Web 实时响应](../src/api/v2/dto.py) 和 [CLI](../src/modules/db_deepagent/cli.py) 消费 `DbAgentResult.answer`；为空时，实时响应仍投影为空字符串，CLI 显示“（无答案）”。
- [Web 历史收尾](../src/api/v2/runs.py) 也消费 `result.answer`，但为空时会填入“本轮未生成答案（状态：……）”；`needs_clarification` 且存在待澄清问题时另行拼接澄清文案。
- QA 归档消费的是 `answer_record` 中的 payload，不能仅凭前述入口已经有文字就认定归档答案也已补齐。

Web 历史已有的通用替代文案不是基于执行账本的结果兜底。Runner 兜底落地后，历史应优先使用统一生成的交付内容，原替代文案保留为残余兜底。

建议统一形成有效交付内容，再用于实时响应、历史、CLI 及归档的 `delivery_answer`。归档原 `answer` 保留模型提交，`answer_source` 描述交付来源。不得伪装模型提交；归档条件 b 也必须使用通过本轮归属、答案结构及非空白规则校验的共享视图，不能仅依赖 `answer_record` 存在。

持久化不可用时仍按现有规则报告未归档，不能承诺此时历史和实时返回均已保存。

## 5. 有限重试的范围与约束

本文只讨论支撑答案生成恢复的有限重试，不展开全项目模型重试治理：

- 重试模型请求，不重跑整轮 Agent，避免重新执行已经成功的 SQL。
- 仅对明确适合重试的错误重试，不照搬旧代码基于字符串识别异常的全部策略。
- 当前底层客户端默认还可能重试两次，叠加项目层首次加两次，可产生最多九次 HTTP 尝试。B 阶段选择单层重试：主模型构造时显式设置 `max_retries=0`，由项目中间件统一管理，见 §7.5—§7.7。
- 每次项目层尝试前检查剩余时限和停止原因。该机制是协作式停止，不是硬 deadline：检查与发送之间仍有时序窗口，已经开始的请求可能在运行期限后结束；不能声称本方案能强制取消请求或严格限制整轮墙钟耗时。
- 区分模型步骤计数和实际调用尝试；当前 `before_model` 预占一次并不自动覆盖中间件内部的每次重试。
- 重试耗尽后交由 Runner 统一处理，不能依赖最后一次错误 AIMessage 自动通过本项目提交规则。
- 主 Agent 的模型重试覆盖范围不能自动推定包含上下文摘要模型的内部调用。

OpenAI SDK 的 `max_retries=0` 用于关闭自动重试，默认重试次数为两次，见 [官方重试说明](https://github.com/openai/openai-python#retries)；项目具体行为仍以当前安装源码和 MockTransport 实验为准。

重试与模板兜底可以分别实施：即使暂未增加项目层重试，Runner 仍应能在已有结果时返回基本说明。

## 6. 与旧链等价的补齐和后续增强

| 范围 | 内容 |
| --- | --- |
| 承接旧链已有机制 | 模型调用有限重试；失败后根据成功执行结果生成基础模板；交付已有查询结果。 |
| 本次建议补齐的覆盖边界 | 未有效提交最终答案时也能生成说明；保留失败状态与原因；统一各入口交付内容，避免只在前端补提示。 |
| 可后续增加的内容增强 | 在有可靠结构与语义依据时，展示少量具体结果值、指标名称、单位及更清晰的未完成说明。 |

后续增强不是旧链原本已完整具备的能力，也不应成为基础兜底交付的前置条件。本项无需等待任务账本、执行调度或旧协议适配完成。

## 7. 函数级解决方案与核心代码片段

以下方案已于 2026-11-12 实施。代码片段是设计期示例，用于说明关键接口与语义；省略现有参数、日志及无关分支的地方已注明，**不是逐字应用的完整补丁**。最终实现与片段在关键语义上一致（共享步骤额度、`RunBudgetLedger.run_shared_state()` 随 `close_run()` 释放、成功尝试即清 `last_error`、归档 v2 与 M1/M2 文案）；细节以代码为准。

建议分两步交付：先完成 **A：Runner 确定性兜底**，再完成 **B：主模型有限重试**。A 不依赖 B，也不依赖任务账本等其他改造。

### 7.2 共享有效性校验与可信模板输入

#### 7.2.1 提交、评估及归档共用有效性判断

在 `schemas.py` 中增加以下函数，并把 validator 追加到现有 `DbAgentFinalAnswer`，其余字段保留：

```python
from typing import Any
from pydantic import ValidationError, field_validator


def extract_raw_final_answer_payload(answer_record: object) -> Any:
    if isinstance(answer_record, dict) and "answer" in answer_record:
        return answer_record["answer"]  # None、空串、空列表也原样返回。
    return {}  # 仅外层记录/answer 键缺失时使用缺失约定值。


def has_nonblank_answer(value: object) -> bool:
    return isinstance(value, str) and bool(value.strip())


# 放入已有 DbAgentFinalAnswer 类，不替换其他字段或校验：
@field_validator("answer")
@classmethod
def _require_nonblank_answer(cls, value: str) -> str:
    if not has_nonblank_answer(value):
        raise ValueError("answer 必须包含非空白正文")
    return value  # 不重写正常正文的首尾格式。


def normalize_valid_final_answer_payload(payload: object) -> dict[str, Any] | None:
    if not isinstance(payload, dict) or not has_nonblank_answer(payload.get("answer")):
        return None
    try:
        return DbAgentFinalAnswer.model_validate(payload).model_dump()
    except ValidationError:
        return None


def normalize_final_answer_record(
    answer_record: object, *, run_id: str, request_id: str,
) -> dict[str, Any] | None:
    if not isinstance(answer_record, dict):
        return None
    if answer_record.get("run_id") != run_id:
        return None
    if answer_record.get("request_id") != request_id:
        return None
    return normalize_valid_final_answer_payload(
        extract_raw_final_answer_payload(answer_record)
    )
```

`SubmitFinalAnswerArgs` 继承该模型，空白输入在写 `FinalAnswerRecord` 前就应通过现有参数错误通道拒绝。Runner 使用归一函数防御旧 checkpoint；不先调用布尔校验函数再 model_validate，避免对同一 payload 做两遍 Pydantic 校验。模型提交工具自身的参数校验仍保留。

本方案采用**字典键与记录内部字段均一致**的运行归属语义：先按当前 `db_final_answers[run_id]` 取记录，再要求外层 `run_id`、`request_id` 分别与 Runner 本轮上下文精确相等。比较基准来自 Runner 参数，不从该记录推导；缺失字段或任一不一致都视为无效提交，不根据字典键自动补齐或改写。现有提交工具已经用 `ctx.run_id`、`ctx.request_id` 写入这两个字段，因此正常工具记录不受影响；缺少标识的旧记录不会作为本轮有效提交。

这项检查只确认上述运行/请求标识自洽，不增加 tool_call_id、submitted_at 的完整性校验，也不代替工具与 Runner 现有的证据引用复核。历史归档浅投影不新增这项校验；它与当前运行的提交有效性是不同契约。

`_evaluate()` 的具体调整为：

1. 将原 `answer_record` 形参替换为 `normalized_submission: dict[str, Any] | None`，位置不变。它只能来自本次 `_finalize()` 调用归一函数的结果，不能直接接收模型输入或 checkpoint 中预存的所谓“已验证视图”。
2. 仅以 `normalized_submission is not None` 判断 `valid_submission`。无效时评估用 payload 置空，findings/口径/限制等不从无效提交对外交付；不在此处重新解析原始值。
3. 将 findings 复核的 `if answer_record is not None` 改为 `if valid_submission`；现有证据引用复核只处理归一后的 payload，不修改共享视图，复核后的 findings 另行返回。
4. 将原 `elif answer_record is None` 改为 `elif not valid_submission`，沿用 `no_final_answer` 错误类型，说明“未提交有效最终答案（缺失、归属不符、结构非法或正文空白）”，并判 failed；persistence/runtime/预算停止仍按原优先级先判。

关键前置片段：


这样空白 completed 提交在生成兜底之前就已是 failed，不会形成 completed + system_fallback。原始空白 payload 可以保留作归档审计，但不得满足条件 b。

Runner 只需导入原值提取函数与 `normalize_final_answer_record()`，无需自行调用 `DbAgentFinalAnswer.model_validate()`。归一结果为普通字典和列表，所有正文/状态读取及 findings 遍历只作用于此视图；原值只用于审计保存。`_finalize()` 在评估之前只生成一次视图，再交给评估、交付与归档复用；三处都不重新解析或修改该视图。

#### 7.2.2 从原始账本核对行数

当前 `_assemble_evidence()` 对缺失的 saved_row_count 投影为零，TypedDict 标注不等于运行时保证。为避免扩大 Web/API 的 row_count 类型，本阶段增加内部可选行数映射，**模板不使用 `EvidenceItem.row_count` 推断可靠行数**。

```python
@staticmethod
def _known_saved_row_counts(
    values: dict[str, Any] | None,
    run_id: str,
) -> dict[str, int | None]:
    counts: dict[str, int | None] = {}
    for channel in ("db_executions", "db_analyses"):
        for record in (values or {}).get(channel) or []:
            if not isinstance(record, dict) or record.get("run_id") != run_id:
                continue
            if channel == "db_executions" and record.get("purpose") != "query":
                continue
            eid = record.get("evidence_id")
            if not isinstance(eid, str):
                continue
            raw = record.get("saved_row_count")
            count = raw if type(raw) is int and raw >= 0 else None
            if eid in counts and counts[eid] != count:
                counts[eid] = None  # 重复记录冲突也不能推定为可靠行数。
            else:
                counts[eid] = count
    return counts
```

字段缺失、None、布尔值、负数和非法类型都表示未知；明确存在的整数 0 才表示确知零行。此处理不读取 ResultStore，也不宣称同时修复了其他入口原有的默认零语义；全局改为 nullable 属于另一项协议调整。

`_finalize()` 在证据组装之前只调用一次该函数，并将同一映射传给 `_assemble_evidence()` 和兜底模板。`_assemble_evidence()` 新增必传关键字参数，不在内部重算；当前生产调用点只有 `_finalize()`，实施时同时更新该调用及相关测试，不保留一个“未传则重算”的默认分支：

这样显式 None 或非法类型也能兼容为既有外部整数类型，不会在模板之前因 row_count 校验失败；真正的未知仍通过同一份内部映射传给模板，不能从该兼容投影反推。其他字段损坏不在本次行数兼容范围内，仍按既有错误路径报告。两处消费者均不修改映射；即使已有 evidence 无需重新组装，模板仍只使用本轮原始记录核对出的行数，不从 EvidenceItem 默认零推定行数。

#### 7.2.3 新增 `_build_fallback_answer()`

建议把它作为 Runner 内的静态辅助函数：输入状态、本轮证据和上述可选行数映射，返回非空字符串。

```python
@staticmethod
def _build_fallback_answer(
    status: str,
    evidence: list[EvidenceItem],
    known_row_counts: dict[str, int | None],
) -> str:
    header = {
        "failed": "本轮未正常完成，未能生成有效的最终答案。",
        "budget_exhausted": "本轮已达到运行次数或时间限制，完整答案尚未生成。",
        "persistence_error": "本轮出现保存异常，最终交付或保存未完成。",
    }.get(status, "本轮未能生成有效的最终答案。")
    lines = ["系统兜底说明：" + header]
    if not evidence:
        lines.append("未取得可确认的查询或分析结果。")
        return "\n".join(lines)

    for index, item in enumerate(evidence[:5], start=1):
        kind = "查询" if item.kind == "sql_query" else "分析"
        origin = "使用此前的" if item.reused_from is not None else "本轮已记录"
        lines.append(f"- 结果 {index}：{origin}{kind}结果。")
        count = known_row_counts.get(item.evidence_id)
        if count == 0:
            lines.append(
                "  该查询没有返回记录。"
                if item.kind == "sql_query" else "  该分析没有输出记录。"
            )
        elif count is not None:
            lines.append(f"  已记录 {count} 行结果。")
        if item.reused_from is not None:
            lines.append("  这项结果来自历史记录，不代表本轮重新查询的最新数据。")
        if item.source_truncated:
            lines.append("  结果仅包含部分数据，已记录行数不代表全部数据量。")
    if len(evidence) > 5:
        lines.append(f"另有 {len(evidence) - 5} 份结果记录，未在此逐项列出。")
    lines.append("以上仅为执行情况说明，完整答案尚未生成。")
    return "\n".join(lines)
```

该函数的保证范围：

- evidence 由 Runner 的既有本轮投影提供，函数不自行搜索历史状态或信任模型草稿。
- 基础版本只陈述可信账本中的事实，不打开结果文件，也不承诺文件当前一定可读；具体数据仍由现有结果接口检查。
- 不合计多查询行数，不把零行当作整个问题无数据，不替模型解释指标或单位。
- 返回最多五条逐项说明，未知行数省略，不展示内部证据编号；完整 evidence 列表及技术定位信息仍保留。
- 不生成业务 finding，也不写入 `db_final_answers`。

文案取舍确定为：可靠零行按结果类型分别写“该查询没有返回记录。”或“该分析没有输出记录。”，不把单项零行推广为整个问题无数据；未知行数仍省略。保留“系统兜底说明：”前缀，使实时响应与历史正文都能独立辨识兜底来源。

将来如展示具体值，应另加受控结果读取，并在读取失败时退回这份元数据说明，而不是让读取失败覆盖原运行结果。

### 7.3 修改 `_finalize()`：评估前归一，归档前生成交付内容

原始记录读取后、`_evaluate()` 调用前，使用本轮 run_id/request_id 生成唯一的归一提交视图；评估之后、调用 `_archive_run()` 之前生成交付内容。保持 `answer_record` 为原始记录（可能来自旧 checkpoint 且无效），不修改原记录。

在 `_finalize()` 现有参数列表末尾追加 `invoke_started: bool = False`。`_run_locked()` 已有同名局部变量：它在调用 `agent.invoke()` 前置为 True；P1/P2 后的主 `_finalize()` 调用增加 `invoke_started=invoke_started`。会话锁失败以及两个 P0 异常收尾调用不传该参数，保留默认 False。不能由 `status` 或证据数量推断是否执行，也不在 `_finalize()` 内自行把它改为 True。

核心片段如下，放入现有 `_finalize()` 的对应位置：

注意：

1. 不重跑 `agent.invoke()`，不把最终提交工具再调用一次；不改变失败状态为 completed 或 partial。
2. 正常非空答案不覆盖；P1 异常时是否允许读取原提交记录，仍由现有 `read_final_answer` 规则决定，不能为了复用文本绕过该规则。

6. P3 涉及多次存储写入，可能部分写入后才失败。本方案不新增事务保证，也不要求为追求文本一致而重新写库；`archived=False` 及现有错误语义照常报告。
7. 尚未调用 Agent 的路径不生成兜底；无可交付答案时 `answer_source="none"`，不能把空答案标为模型输出。`answer_source` 的三种取值为 model、system_fallback、none，均只作为服务端归档元数据。
8. 有效性在评估前计算，状态由 `_evaluate()` 判定，不能等生成兜底时才发现提交无效；保留当前七值状态集合。实施测试必须拒绝 completed + system_fallback；若发生，说明评估与交付规则仍不一致。
9. 评估、交付和归档复用同一个 normalized_submission，不重复结构解析或归属检查，也不由后续函数原地修改。普通有效 payload 在 Runner 本次收尾中恰好调用一次 `DbAgentFinalAnswer.model_validate()`；归属已不符的记录直接拒绝，不解析其正文。工具提交时的参数校验属于另一个边界，不计为本次收尾的重复校验。

### 7.4 修改 `_archive_run()`：分开资格判断与保存内容

在保留现有全部参数的基础上，增加三个必传关键字参数：

```python
# 加在现有 _archive_run() 参数列表末尾；其余参数保持原样。
# *, normalized_submission: dict[str, Any] | None,
```

函数内严格分开原值与资格视图。条件 a 仍按实际执行记录判断；条件 b 除原状态/证据规则外，复用 `_finalize()` 已校验归属并归一的结果，不再次 model_validate。原始 payload 不得参与 `.get()` 或 findings 遍历：

这里保留 `answer` 为原始模型提交 payload，只有外层记录或 answer 键缺失时采用 `{}`。已有的 None、空字符串、空列表以及其他 checkpoint 可序列化的非法值仍按原类型和值保存，不替换成 `{}`；它们不进入资格视图。非 JSON/不可序列化的底层损坏不承诺强制归档，仍走现有存储错误路径。不新增与原值重复的 `submitted_answer`。新 `delivery_answer` 保存实际交付内容，其 status 采用 Runner 评估状态。

这是明确的版本化归档契约，定义如下，并同步到 [详细设计 §13.3](v4/5_db_deepagent详细设计.md)：

| 字段 | v1 旧记录 | v2 新记录 |
| --- | --- | --- |
| archive_schema_version | 缺失，按 1 解释 | 固定为 2 |
| answer | 原模型提交 payload（QA 原有字段） | 保留 answer 键原值，包括已存在的非法值及空值；仅缺失时为 `{}`，绝不据此字段直接计算资格 |
| delivery_answer | 缺失 | 归一后的交付 payload；其 status 为 P3 写入时的 Runner 状态，answer 与实时交付正文一致 |
| answer_source | 缺失，不凭空补成 model | model / system_fallback / none，描述 delivery_answer 来源 |
| 顶层 status | Runner 状态 | 继续为 Runner 状态；P3 部分写入失败的限制仍遵循 §7.3 |
| read_delivery_answer() 返回视图的 status | 不返回该键，原模型状态改名为 submitted_status | delivery_answer.status，Runner 写入时的状态 |
| read_delivery_answer() 返回视图的 submitted_status | 原 answer.status 的原值；原键缺失则不补 | 不自动生成；原模型状态仍从归档 answer.status 读取 |

选择保留原 answer，是为降低对既有或仓库外消费者的影响，不再承诺“所有读者不改读取字段就自动看到兜底”。面向交付内容的新读取方应使用明确的兼容入口；仅需要原模型提交的读者继续使用 answer。

建议在 `persistence/archive.py` 集中定义版本号，Runner 写入与历史读取均从该模块引用。文档表中的 v1/v2 是契约版本说明，不是允许各处独立硬编码；以后增加新格式时须保留旧版本解码分支，并同步 writer/reader 测试。

```python
LEGACY_ARCHIVE_SCHEMA_VERSION = 1
ARCHIVE_SCHEMA_VERSION = 2
```

`QaArchive.read_delivery_answer()` 的职责是**按版本返回历史浅投影，并在 v1 视图中将模型状态显式改名**。原 v1 的 answer.status 是模型提交状态，v2 的 delivery_answer.status 是 Runner 状态，不能因名字相同而混用于展示或统计；因此 v1 返回前将 status 移至 submitted_status，不生成一个推定的 Runner 状态。跨版本状态展示和统计必须读取归档顶层 `record["status"]`（两版本均为 Runner 状态，缺失/非法时由消费方按未知处理），不能统一读取本访问器返回值的 status，更不能在其缺失时退回 submitted_status。

除了这项显式字段改名，该函数仅作版本路由与字典容器检查；它不是归档契约内容验证入口，不保证 status、answer、findings 或业务结论有效；调用方如要把结果作为当前交付契约使用，必须另行验证。函数只改读取副本，不回写或批量迁移旧记录：

```python
@staticmethod
def read_delivery_answer(record: dict[str, Any]) -> dict[str, Any]:
    version = record.get("archive_schema_version", LEGACY_ARCHIVE_SCHEMA_VERSION)
    if type(version) is not int:
        raise ValueError("归档契约版本必须为整数")
    if version == LEGACY_ARCHIVE_SCHEMA_VERSION:
        raw = record["answer"] if "answer" in record else {}
        view = dict(raw) if isinstance(raw, dict) else {}
        # v1 的 status 是模型提交状态，不能伪装为 Runner 状态。
        if "status" in view:
            view["submitted_status"] = view.pop("status")
        return view  # 不追补兜底、不重新判定历史状态、不改原记录。
    if version == ARCHIVE_SCHEMA_VERSION:
        raw = record.get("delivery_answer")
        if not isinstance(raw, dict):
            raise ValueError("归档 v2 缺少字典型 delivery_answer")
        return dict(raw)
    raise ValueError("不支持的归档契约版本")
```

旧记录没有 answer_source 时应展示“历史来源未标注”，不要凭存在正文推定已经通过当前有效性规则。v1 原 answer 为字符串/列表等非法值时，浅投影可以返回 `{}`，但原归档值不改写、不表示已修复。v1 视图的 submitted_status 明确表示原 status 值，不进行合法性推定；即使非法旧 payload 已有同名扩展字段，视图也以原 status 为准，原值仍保存在归档中。v2 即使返回 status/answer 缺失的字典，也仅表示路由与容器检查通过。兼容读取与当前运行重新沿用证据是不同路径，后者仍须通过当前校验。

当前仓库内检索不能证明仓库外消费者不存在。实施前需登记已知读取方、核对新增版本字段与读取目的；未知外部消费者不能宣称已兼容验证。此核查属于实施验收项，不阻塞本次方案文档修订。`write_qa`/`write_run_errors` 仍保存字典，但“能写入任意字典”不等于新契约已获验证。

**禁止把 `delivery_payload` 当作 `answer_record` 传回资格判断。** 例如，只有沿用结果且没有有效提交的失败轮次，仍进入 run_errors，不能因生成了兜底而进入 QA。向错误记录增加说明也不自动增加结果文件的保留资格。

持久化失败时仍由外层原有处理收敛，不为了保存兜底引入无限重试或第二次归档流程。

| 配置场景 | 预期行为 |
| --- | --- |
| 原生 DashScope + 未声明 model.retry | 默认关闭项目重试，保持旧 provider 启动行为，不注入 max_retries=0 |
| 原生 DashScope + 显式 enabled=true | 启动校验拒绝，错误提示如何关闭新功能 |
| OpenAI 兼容路径 + 未声明 model.retry | 项目重试默认关闭，不宣称三次 HTTP 上限 |
| 标准 YAML + OpenAI 兼容主 profile | 显式开启统一重试，SDK 内部为零，项目层管理次数 |

### 7.6 新增 `BudgetAwareModelRetryMiddleware` 并接入 `build_db_agent()`

建议在新的 `middleware/model_retry.py` 中封装公开 `ModelRetryMiddleware`。当前生产 Runner 使用同步 `invoke()`，首版明确覆盖同步主 Agent 模型调用，不承诺新的异步调用入口或摘要模型内部调用。

本节以 §7.5 已确保主模型 SDK 重试为零为前置条件。首版项目层不增加 sleep，最多首次加两次；请求超时仍保留。后续若增加退避，必须另行实现按剩余时限截断等待，不默认引入 SDK 长退避。

这里的“模型步骤”包含上下文超限后压缩恢复的主模型再请求。SDK 的 SummarizationMiddleware 位于重试外层，恢复会重新进入 wrap_model_call()；因此不能在每次进入时发放全新额度。按 run_id 与已预占的 model_call 步骤序号共享 `1 + max_retries` 总额度，只有新步骤才重置。运行结束必须释放共享状态及保留的原异常；不能仅设置缓存条数上限并等待后续运行触发整表清空。

核心片段如下。`wrap_model_call()` 放入已有 BudgetAwareModelRetryMiddleware；构造器和辅助方法在此省略：`_step_state()` 返回本运行、本步骤共用的 key/used/last_error 状态，`_stop_response()` 保留前述停止/时限检查并返回停止响应或 None。状态存储已实现为 `RunBudgetLedger` 运行条目（`run_shared_state()`），随 `close_run()` 释放；成功尝试即清 `last_error`，失败保留至本运行结束供额度耗尽 cause。下面的局部 SDK 包装器不拥有独立的整步额度。

```python
from langchain.agents.middleware import AgentMiddleware, ModelRetryMiddleware
from langchain.agents.middleware.types import ModelResponse
from langchain_core.messages import AIMessage
from openai import APIConnectionError, APIStatusError, RateLimitError


def is_transient_model_error(exc: Exception) -> bool:
    # 覆盖当前主模型 OpenAI 兼容路径；超时属于 APIConnectionError 子类。
    if isinstance(exc, (APIConnectionError, RateLimitError)):
        return True
    return isinstance(exc, APIStatusError) and (
        exc.status_code in (408, 409, 429) or exc.status_code >= 500
    )


class ModelStepAttemptsExhausted(RuntimeError):
    pass


def wrap_model_call(self, request, handler):
    ctx = request.runtime.context
    state = self._step_state(ctx.run_id)
    total = 1 + self._cfg.max_retries

    def attempt(inner_request):
        stopped = self._stop_response(ctx.run_id)
        if stopped is not None:
            return stopped  # 停止条件优先于额度拒绝。
        if state["used"] >= total:
            raise ModelStepAttemptsExhausted(
                f"本模型步骤的主模型尝试额度已用尽（上限 {total} 次，含上下文恢复）"
            ) from state["last_error"]
        state["used"] += 1
        try:
            response = handler(inner_request)
        except BaseException as exc:
            state["last_error"] = exc
            raise
        state["last_error"] = None  # 成功即释放原异常回溯，不等运行结束。
        return response

    # 每次进入只使用本步骤剩余额度；即使额度已用完，也先由 attempt
    # 检查停止，再抛额度异常，绝不再调用底层 handler。
    remaining = max(0, total - state["used"])
    retry = ModelRetryMiddleware(
        max_retries=max(0, remaining - 1),
        retry_on=is_transient_model_error,
        on_failure="error",
        initial_delay=0.0,
        max_delay=0.0,
        jitter=False,
    )
    return retry.wrap_model_call(request, attempt)
```

实施时补齐完整类型标注和必要审计；该片段展示接口与核心边界，不应直接替代现有审计或预算中间件。

关键规则：

- 用明确异常类型和状态码筛选，不重试普通 RuntimeError、参数错误、鉴权错误、模型拒绝或持久化异常。
- 当前主模型必须通过 §7.5 的 ChatOpenAI 兼容路径及客户端零重试验证；原生 Tongyi 等未适配路径不得开启本项目重试。关闭本项目重试后可维持原 provider 行为，但不适用本节统一次数承诺。
- 每次项目尝试前检查协作式时限及停止原因，客户端不再自行发起额外重试。检查到发送存在时序窗口，已开始的请求仍可能跨过期限；此方案不提供强制取消或硬 deadline 保证。
- 停止条件触发时返回普通模型响应，让已有 gate/Runner 按停止原因收敛；它不是正式答案，Runner 仍生成系统兜底。若在前序失败后因时限停止，失败尝试仍由 ModelCallObserver 的错误回调保留在审计中，停止原因由既有 RunFailureRecord 表达；不伪造一次成功模型调用。
- 真正重试耗尽或错误不在白名单时重新抛出，由现有 P1 捕获和 Runner 状态优先级处理，不抹去原异常。
- 摘要恢复重入若已经没有本步骤额度，抛 ModelStepAttemptsExhausted，并以 cause 保留该步骤最后原异常，交给既有 P1 runtime 路径；它不同于运行步骤预算停止，不新增一次 model_call 预占。原异常链只保留至本运行结束，清理须覆盖成功、失败及正常收尾前的异常退出。

`build_db_agent()` 中的自定义中间件相对顺序建议如下，其余 SDK 与现有中间件保持原装配：

```python
extra_mw = [
```

### 7.7 计数、记录和不修改的边界

采用保留当前预算语义的方案：

| 指标或机制 | 本方案口径 |
| --- | --- |
| `RunStats.model_calls` / `budget.model_call` | 主 Agent 模型步骤数；由现有 before_model 每步骤预占一次。 |
| `RunStats.total_model_calls` | 观察器看到的主模型及摘要模型尝试总数。开启统一重试后，主模型每次 handler 调用不再藏有 SDK 重试；摘要仍独立，不能把全部 total_model_calls 等同于全部 HTTP 数。 |
| 每步骤主模型尝试上限 | enabled=true 且实际客户端 max_retries=0 时，同一步骤连同上下文压缩恢复后的主模型再请求，共享 1+max_retries 总额度；标准配置最多三次主模型 HTTP 尝试。 |
| 全轮主模型理论上限 | 模型步骤预算上限乘以 `1 + model.retry.max_retries`，时限或其他停止条件可提前减少；不包含独立摘要调用。 |
| 关闭项目重试 | 恢复既有客户端配置，可能继续有 SDK 重试；不能外推上述三次上限与停止检查覆盖范围。 |
| 时限 | 协作式：每次项目尝试前检查，不取消在途请求，不承诺整个步骤/整轮在截止时刻之前返回。 |
| 数据库执行预算与次数 | 不因重试或兜底增加；继续由 SqlPipeline 控制。 |
| `db_final_answers` | 只由有效最终提交工具写入，兜底不写。 |
| 外部协议 | 继续使用既有 answer、warnings、evidence 等字段；本阶段不新增 Web/CLI 必填字段。 |

现有 RequestAudit 在 handler 抛异常时不会写入成功的 `model_request` 记录，不能把该记录数量当作所有尝试数。失败尝试与用量统计仍以现有 ModelCallObserver 为依据；必要的重试事件仅记录运行定位、尝试号和异常类别，不重复写提示词或凭据。

预算目标仍为限制模型步骤，不能称为限制全部模型或 HTTP 请求次数。若后续要求按尝试预占，应单独修改预算模型并取消重复预占，而不是在这里再调用一次 `reserve("model_call")`。

## 8. 针对本问题的验收建议

以下为后续实施时的验收项，不表示这些修改已经完成：

- [ ] 已有可信 SQL 结果，随后模型调用持续失败：返回非空基础说明，证据和原失败信息保留，不重复执行 SQL。
- [ ] 模型正常结束但未有效提交答案：存在可信结果时同样能够兜底。
- [ ] 已开始调用 Agent，但没有可信结果：明确说明失败，不声称查询成功。
- [ ] 会话忙碌、锁失败、P0 拒绝及其他尚未调用 Agent 的退出：维持原错误和答案行为，不生成最终答案兜底；无可交付答案时来源为 none。
- [ ] 正常有效答案：不被兜底模板覆盖。
- [ ] 空白 completed：提交工具拒绝；已有 checkpoint 中出现时，Runner 判为无效提交，不产生 completed + system_fallback。
- [ ] 空白提交 + 纯沿用证据：不满足归档条件 b，不能因 record 存在或兜底非空而进入 QA。
- [ ] 非法 payload/findings 经完整 Runner 收尾仍为 failed + 系统兜底，无额外 P3 runtime；纯沿用进 run_errors，原始 None/空串/空列表等值按约定保留。
- [ ] 字典键属于本轮但外层 run_id/request_id 缺失或不一致：不能作为有效提交，也不能满足归档条件 b；正常工具写入的标识一致记录仍有效。没有其他高优先级故障时返回 failed + 系统兜底，原 payload 按审计约定保留。
- [ ] 归一只在本次收尾入口执行一次；评估、交付与归档复用该结果，原值不参与正文/状态交付或条件 b，普通有效提交只进行一次 Runner 侧 Pydantic 解析。
- [ ] 零行、截断、多查询部分成功：文案符合已有事实，不误报总体行数或整体完成。
- [ ] 预算停止及持久化故障：保留原有状态语义，账本不可核验时不推测结果。
- [ ] 首版兜底不读取 ResultStore/结果文件，只陈述账本事实；用“结果文件已删除但账本仍存在”场景验证不会承诺文件可读或发起文件读取。
- [ ] 可靠零行与行数未知区分，未知时不把投影默认零当作实际行数。
- [ ] 本次收尾只计算一次行数映射，证据投影和模板复用；简版正文不出现内部证据编号、账本术语或未知行数句，仍保留沿用/截断/未完成说明，技术信息不从 evidence 中删除。
- [ ] 实时响应、可成功写入的归档和历史、CLI 使用一致的交付内容，并能识别服务端兜底来源。
- [ ] 归档契约 v2 的原 answer/新 delivery_answer、来源和版本符合约定，v1 仍可读；已知外部读取方完成核查，未知范围明确保留。
- [ ] 历史读取将 v1 模型 status 显式投影为 submitted_status，v2 status 仍为 Runner 状态；跨版本展示和统计统一读归档顶层 status，缺失/非法按未知处理，不回退模型状态。读取不改原档、不作为内容验证证明，写读共用版本常量。
- [ ] 开启统一重试时，主模型实际 SDK 内部重试为零；HTTP 次数、停止检查、预算及观测口径符合约定，不将协作式停止宣称为硬 deadline。
- [ ] 原生 provider 旧配置未声明重试时默认关闭；显式开启不支持的路径时，错误明确指引 `model.retry.enabled=false`。
- [ ] 升级 langchain_openai 或改变模型工厂的构造方式时，复验公开客户端字段、同步/异步重试配置与真实 SDK 的模拟 HTTP 次数；客户端尚未构造时不静默跳过校验。
- [ ] 区分服务端兜底与模型提交，不伪造正式提交或业务 findings。

保证范围是控制权仍能回到 Runner 且必要事实可核验的退出场景；进程被强制终止等无法执行收尾的情况，不属于这层代码模板能够单独保证的范围。

后续若实现“受控读取具体结果值”，再增加文件读取失败回退到元数据说明的专项验收；该路径不计入首版已实现能力。

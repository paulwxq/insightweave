# db_deepagent 时间常识问答被任务校验拒绝问题分析

> 状态：问题分析稿。**只描述问题与根因分析，不含处置结论。**
> 依据：2026-11-15 真实查询日志（`logs/nl2sql.log`）与当前代码
> （分支 `feature/multi-source-knowledge-isolation`，HEAD `6a98f4d` 工作区，
> 含 doc 16 时间解析 LLM 重写、doc 13 上下文日志、doc 6.2/6.3 终态与覆盖门控）。

## 1. 问题概述

用户向 WebUI 询问一个纯时间常识问题：**"请问大前天是哪一天"**（2026-11-15 18:31）。

该问题的答案（11月12日）不依赖数据库内容。系统内部的时间解析完全正确（LLM
解析器一次返回正确区间），但随后的**任务登记校验**与**任务门控**两层校验先后
拒绝了模型的合法路径，迫使模型：作废原任务 → 两次提交被拒 → 重新登记一个
"附带取数"的任务 → 执行一条与问题无关的 `COUNT` 查询 → 第三次提交通过。

最终以 **36 秒** 交付——**主 Agent 模型调用 11 次（seq=1..11），另有时间
解析模型（flash）调用 1 次**——且交付正文混入了无关信息（"当天订单数为
0"）与内部审计内容（finding 编号、任务版本、作废/完成状态）。

## 2. 对照案例：系统正常工作的形态

同日三个真实查询均一次通过，作为问题案例的对照组：

| 案例 | 时间 | 查询 | 过程 | 结果 |
| --- | --- | --- | --- | --- |
| A | 18:18 | 9月份到现在的订单总数 | 解析→查库→交卷 | 一次通过，[2026-09-01, 2026-11-15T18:18:19)，33 单 |
| B | 18:24 | 今年初第一个月的订单数量 | 同上 | 一次通过，[2026-01-01, 2026-02-01)，26 单 |
| C | 19:40 | 当前数据库的版本号是多少 | 登记 T1→`SELECT version()`→交卷 | 13 秒 5 次调用一次通过，PostgreSQL 18.1 |

案例 C 说明：元数据查询（无时间/维度谓词，SQL guard 无事不扰放行）在
**取得合法执行成果并完成任务后**可以正常提交——畅通的前提是走完
"登记→执行→成果→交卷"的取数路径。

问题案例与对照案例的关键差异：**回答是否需要数据库结果**——对照案例的
答案可以由查询成果支撑，问题案例的答案是库外事实，系统没有为它留出
成功提交的出口。

## 4. 用户可见的三层痛点

1. **常识题被迫查库**。答案本是日历事实，系统却强制产生一次数据库查询：
   相比对照案例 C（13 秒 5 次调用）多出约 23 秒、6 次模型调用，其中两次
   是被拒后的重试轮。且答案混入"当天订单数为 0"这一与问题无关的信息。
2. **交付正文暴露内部审计**。`结论 F-1（T2@1）`、`已作废：…`、`已完成：…`
   等内部编号与任务状态直接出现在用户答案尾部（来源见 §5.5）。
3. **任务状态叙述自相矛盾**。用户看到"已作废：确认大前天的具体日期（任务
   不必要）"与"已完成：确认大前天（2026-11-12）的日期并获取相关数据"并存——
   同一件事先被判"不必要"再被"完成"，原因是第二次登记必须附带取数才能
   通过校验。

## 5. 逐层根因分析

### 5.1 时间证据的结构性位置

证据体系分两级（doc 6.3）：

- **成果证据**：查询执行记录（E-）、分析记录（A-）。产生时携带
  `sub_task_id` + `sub_task_revision`，天然挂在某个任务名下，**能**支撑
  业务数值结论。
- **辅助证据**：时间证据（T-）、维度证据（D-）。`resolve_time_range` 的
  入参只有 `source_text`/`context`（doc 16 设计），**不带任务号**。定位是
  整次运行的公共背景事实（类似"今天的日期"），**不能**单独支撑业务数值
  结论。本案例中解析（18:31:28）确实先于首个任务登记（18:31:30），但这是
  本次执行的时序事实，不是结构限制——模型也可以先登记任务再解析。

T- 证据"挂不到任何任务头上"的结构性原因有二：**时间记录没有任务版本
归属**（工具入参无任务号，记录中不存在 sub_task_id/revision 字段）；
**§5.2 的成果校验只接受查询/分析记录**（E-/A-）。两者叠加，无论调用
顺序如何，T- 都不可能成为任何任务的登记成果。

### 5.2 第一层拒绝：任务登记校验（写入侧）

`record_sub_tasks` 的登记规则（`services/task_ledger.py`）：

- `:811` completed 必须携带 `evidence_ids`（不能空）；
- `:819` 非 completed 不得携带 `evidence_ids`；
- `:940` 起的成果归属核验（§6.2）：completed 提交的**每条** evidence_id
  必须是"**该任务、该版本**下产生的 query E- 或分析 A- 记录"，从
  执行/分析记录中按 `sub_task_id`+`sub_task_revision` 精确匹配。

推论：**"确认大前天的日期"这类任务仅凭时间证据无法登记 completed**——
它唯一能引用的成果就是时间证据 T-73e6613d，而 T- 永远不满足 `:940` 的
归属核验。模型在 18:31:33 被拒后的合法收尾只有失败或作废两条：登记
failed（reason_code 可取 `agent_abandoned`，`task_ledger.py:763-766`），
或作废（实际选择，18:31:38）。两条路径的结局不同：**登记失败可以失败
收尾**（唯一任务为 failed 时任务视图非空，失败答案可合法提交）；**全部
作废后任务视图为空，任何提交仍被拒**（§5.3 步骤 2，本案例 18:31:41/
18:31:47 两次拒绝即此形态）。共同点是：**两条路径都不能正常交付已经
取得的日期答案**——缺少正常成功回答的出口。

### 5.3 第二层拒绝：任务门控（读取侧）

`submit_final_answer` 内部调用共享规则 `evaluate_submission`
（`tools/final_answer.py:200`），检查顺序（该文件头注）：参数结构 → 单独
调用 → 未重复提交 → 共享任务门控。共享门控中与本案相关的两步
（`services/task_completion.py`）：

- **步骤 2 任务视图**（`:370-377`）：`not tasks or not non_void` →
  `task_not_registered`"本轮没有有效业务任务（未登记或全部作废），不能提交
  成功结论"。18:31:41/18:31:47 两次拒绝即此：T1 已作废、T2 未登记，任务
  视图为空。该检查在状态分支之前**无条件早退**——`needs_clarification`
  提交同样被拒：即"先向用户澄清问题再回答"的路径在零任务时也不存在
  （连带缺陷，独立于本案例成立）。
- **步骤 6 成果资格核验**（`:617-655`）：从 `snapshot.executions`（仅
  `purpose=="query"` 的 E-）与 `snapshot.analyses`（A-）**独立重建**
  `eligible_evidence` 池，再逐条核对每个 completed 任务选定的成果
  "存在于池中且归属本任务当前版本"。T- 证据结构性不在池中。

关键设计（`:614-616` 注释，R2-08）："资格视图与任务级成果核验独立于是否
存在最终提交……**不能把状态映射的存在当成'成果已核验'**"——门控**不信任**
登记结果，交卷时从原始执行/分析记录重新推导证据资格。

### 5.4 两层校验的耦合关系

登记侧（task_ledger）与读取侧（task_completion）是**同一政策的重复执法**：
政策均为"completed 必须有本任务产生的查询/分析证据"，且互不信任——读取侧
不信写入侧的登记结果，自行重建证据池。因此单独调整任一层的行为推演：

| 状态 | 行为 |
| --- | --- |
| 两层均在（现状） | 本案例实际行为：作废表演 + 强制 COUNT（§3 时间线） |
| 仅放开登记侧 | T1 可挂 T- 登记成功，但交卷时门控步骤 6 重核：T- 不在 eligible_evidence 池 → 仍 `task_evidence_mismatch` 拒绝，仅错误信息不同 |
| 仅放开读取侧 | 交卷可通过，但登记侧仍拒绝"T1 completed 挂 T-"，模型的作废/僵尸任务行为残留 |
| 两层一致放开 | 登记与交卷对"成果证据"的强制要求同时消失（本案的直接触发链不存在） |

（本表为耦合事实陈述，非处置建议。）

补充：除表内两层校验的调整组合外，还存在第三条行为路径——模型对无需
取数的问题**不登记任何任务**、直接提交 `findings=[]` 的解释型答案。当前
该路径同样被步骤 2 的任务视图检查拒绝（与"登记→被拒→作废→再被拒"同源，
见 §5.3 连带缺陷）。

### 5.5 展示层放大器：审计段落无条件追加

`runner.py:770`（`_finalize`）：合法交付后无条件执行

```python
section = build_delivery_answer_section(decision)
if section:
    answer = f"{answer}\n\n{section}"
```

`build_delivery_answer_section`（`task_completion.py:909`）逐项输出 finding
文本及 `T1@1` 式任务引用、已完成任务、失败、澄清与**作废说明**（R1-13/R2-07
设计：防模型 answer 只写"已处理"）。即使模型 answer 已完整，追加仍然发生——
痛点 2/3 的"已作废/已完成/F-1（T2@1）"文本即来源于此，而非模型自写。
（doc 17 §4 已针对该追加行为单独立稿，与本问题在展示层交叠。）

### 5.6 提示词层的同源约束

最直接的约束是 `config/prompts.yaml` "业务任务登记"节（`:37`）：

> "**回答任何问题前先用 record_sub_tasks 登记本轮业务任务（简单问题也
> 登记一项）**；任务 = 需要交付的业务问题或必要中间结果，不是工具步骤。"

括号中"简单问题也登记一项"正是本案例模型为"大前天"登记 T1 的直接指令
来源；查询规划 Skill（`skills/query-planning/SKILL.md`）同源。若只放开
程序出口而不调整此条，提示词仍会推动模型登记无法以 completed 收尾的
日期类任务。

其次是证据规则：system prompt 明文"所有数据结论必须来自本次实际执行的
查询或结果计算……**时间／维度证据不能单独支撑业务数值结论**"，与两层
校验同政策。
对"数值结论"与"时间事实"的区分并未在规则文本中给出出口：本案例答案
"大前天是 2026年11月12日"不含业务数值，但在任务/证据规则下没有区别于
数值结论的合法通道。middleware 的收卷提醒同源：`final_answer_gate.py:84`
提醒原文"请调用 submit_final_answer 单独提交最终答案，**并引用已有
evidence_id**"——对纯解释答案同样构成引用压力，会把模型推向补造证据。

### 5.7 问题触发边界

- **分界线**：**回答是否需要数据库结果**（而非"能否写成 SQL"——本案的
  COUNT 证明"大前天"也能勉强写成 SQL，但没有必要；业务术语解释、查询前
  澄清同样无需取数）。
- 会触发：日历常识（昨天/大前天/某月几号星期几）、与库内数据无关的业务
  常识、口径解释类问题。
- 不触发：已按现有规则取得成果并正常完成任务的数据查询（对照案例
  A/B/C，含元数据查询）。注意数据查询在取数前需要澄清时，同样受
  "零任务澄清无出口"影响（§5.3 连带缺陷）——"不触发"仅覆盖成果取得
  之后的路径。
- 历史注记：同日 13:40（旧规则解析器时代）同类问题以 `needs_clarification`
  收场，形态是"解析不出"（模型无法填 boundary_date），与本案"解析正确但
  交不了卷"不同——本问题独立于解析器版本，doc 16 重写后依然存在。

## 6. 涉事机制盘点（事实清单）

### 6.1 任务门控的三个调用方

| 位置 | 用途 |
| --- | --- |
| `tools/final_answer.py:200` | submit 工具内调用 `evaluate_submission`，拒绝时返回错误信封 |
| `runner.py:870-960` | 收尾时装配同一快照**再执行同一规则**（K19：Runner 从最终 checkpoint 复评），结果用于交付判定/兜底分级/status |
| `middleware/final_answer_gate.py:98-120` | 读任务视图生成 pending 提醒注入模型（`before_model` 的"答案已登记→收卷"是运行结束开关，非校验） |

### 6.2 任务登记校验的检查项分组

- 结构类：单独调用约束、`expected_plan_version` 乐观并发、操作结构解析、
  幂等识别（no_op）。
- 内容类：§5.2 所列成果证据三条绑定规则。
- 依赖图类（doc 6）：`dependencies`/`dependency_snapshots`/`blocked_by`
  系列结构与一致性校验（本案未触发）。

### 6.3 同场作证、与本案无关的机制

- **SQL guard**（`services/sql_guard.py`）：本案例中放行了
  `resolve_time_range`（仅记录映射）与带时间谓词的 COUNT SQL（区间与
  T- 证据对质通过）；对照案例 C 的 `SELECT version()` 无时间/维度谓词，
  无事不扰放行。未参与两次拒绝。
- **RunBudget**（`services/run_budget.py`）：model_call=40 次/run 预占记账
  （日志 `remaining=39` 递减），资源保险，未触发停止。
- **系统兜底**（`runner._build_fallback_answer`）：本案未触发（模型三次
  提交最终成功）。

### 6.4 证据编号体系的消费者现状

编号挂靠（E-/A-/T-/D- 及归属关系）的消费者：任务登记校验（§5.2）、任务
门控（§5.3）、`reuse_evidence` 工具（跨 run 沿用；**2026-11-13 17:41 已有
成功沿用记录**：`reuse_evidence(E/A): exec=1 analysis=0 target=T1@1`，见
`logs/nl2sql.log.2026-11-13`，随后提交成功）。

导出、后续追问引用——与编号挂靠体系相互独立。

## 问题 1：「当前」被误判为时间约束 → 恒假时间过滤

### 场景

问题文本含「当前」（如"查询当前…"）。System 提示词明确要求「未明确提及时间时 time 必须为 null」（`question_parsing.py:132`），但解析 LLM 仍把「当前」判定为显式时间约束，输出 `time = {start: 2026-10-13, end: 2026-10-13, grain: day, is_full_period: true}`，signals 自由发挥为 "today"。下游 `_format_time_hints` 无校验直通，拼出 `日期时间条件：>= 2026-10-13 AND < 2026-10-13`——半开区间 start==end，恒假空区间，SQL 结果 0 行。

### 根因链条

1. **语言歧义是本质**：中文「当前」兼具时间义（当前**月**、当前**季度**——几乎总是绑定后随时间单位）与状态义（当前**库存**、当前**状态**——指现状，事实表本身即现状快照，无需时间过滤）。裸「当前」无法靠"理解"消歧。
2. **解析提示词诱导**：is_full_period 规则的英文示例含 `"today/whole day"`（`question_parsing.py:143`），与「当前」语义相邻。
3. **日期注入赋能**：user prompt 首行 `Today's date is: …`（`:158`）让模型有能力把「当前」物化成具体日期。
4. **边界无人计算**：解析侧被明令「不计算日历边界、不补全缺失部分」（`:135, :145`），下游也无任何代码按 grain 展开边界 → 模型输出 start==end，无人修正。
5. **代码无校验**：`_format_time_hints`（`sql_generation.py:313-344`）无 `start < end` 校验，恒假条件直通进提示词；生成提示词规则 3 又要求模型照抄 `>= start AND < end`。

### 涉及代码

- `src/modules/sql_generation/subgraph/nodes/question_parsing.py:131-153, :158`（time 规则与日期注入）
- `src/modules/sql_generation/subgraph/nodes/sql_generation.py:313-344`（`_format_time_hints` 直通格式化）
- `src/tools/schema_retrieval/retriever.py:720`（time 非空 → 强制走事实表路由，误判会连带影响表路由）
- 附：`signals` 字段全代码库无消费方，纯日志噪音。

### 初步改造方向（备忘，未定稿）

- 解析提示词规则细化：裸「当前/目前/现在」≠ 时间约束；仅当后随时间单位（当前月/当前季度）才视为时间表达。
- question_parsing 出口加确定性守卫：time 非空时校验 rewritten_query 是否含时间单位证据（正则：`\d{4}年|\d{1,2}月|\d{1,2}[日号]|季度|Q[1-4]|[本上](月|周|年)|今[天年月]|昨[天日]|最近|过去|截至`），无证据则置空 time 并告警。单方向守卫：只压无证据的 time，不凭空造 time。
- 时间边界正规化：LLM 定锚（哪个周期）+ 代码算界（day→+1d、month→+1月…）；`start >= end` 视为解析异常，丢弃过滤 + 告警（BI 语境宁宽勿空，fail-open）。

## 问题 2：「系统」被识别为 role="value"（伪维度值 + 兜底透传）

### 场景

执行 2 中解析器把「系统」判为 `dimensions: [{text: "系统", role: "value"}]`。该词经维度值向量检索（当日配置 `dim_value_top_k=3, dim_value_similarity_threshold=0.75`）正确地未命中任何库内真值 → 「维度值匹配」段为（无）。但提示词仍出现 `维度过滤：value=系统` 一行——无绑定列的裸噪音。本次生成模型正确忽略（未产生 WHERE，结果 500 行），但存在远期风险（模型可能自作聪明构造 `LIKE '%系统%'`）。

**最关键的一环是源头：「系统」被识别为了 value。** 后续所有噪音皆由此派生。

### 关键认知：两条互不通气的通路

同一个词的信息流过两条路径，B 不服从 A 的裁决：

- **A 路（裁决者）**：`dim_value` 向量检索 → 0.75 阈值过滤 → 命中才进「维度值匹配」段（生成提示词规则 8 只授权此段转 WHERE）。库内无「系统」真值 → 正确拒绝。
- **B 路（复读机）**：`build_optimized_filters` 读的是 `parse_result["dimensions"]` 原始列表（不是检索结果），对 role="value" 且无命中的词**无条件照抄原文**（`value_matcher.py:167-169` 兜底分支）。检索拒绝得越干净，兜底越必然触发；调任何阈值都拦不住这一行。

注意：`column_backfill_similarity_threshold=0.65` 与本案无关——它只管 role="column" 文本的列记录回填，「系统」是 role="value"，走的是 dim_value 路（0.75）。

### 核心难点（为什么不能简单过滤）

「业务系统」「订单系统」在真实业务中**可以是库内真值**，停用词表必然误伤。判别权应在**证据**（向量匹配是否命中）而非**词表**：

| 输入 | 向量匹配 | 正确裁决 |
|---|---|---|
| 业务系统 / 订单系统 | 命中库内真值 | 保留，生成等值条件 |
| 裸「系统」 | 无命中 | 拒绝，不进提示词 |

A 路已按此逻辑正确工作；做错的只是 B 路把被拒绝的候选复述进提示词。

### 涉及代码

- `src/modules/sql_generation/subgraph/nodes/question_parsing.py:148`（column/value 二分类规则，无泛化名词过滤，evidence 字段未被强约束）
- `src/tools/schema_retrieval/value_matcher.py:129-174`（`build_optimized_filters` 未命中兜底分支 `:167-169`）
- `src/modules/sql_generation/subgraph/nodes/sql_generation.py:346-363`（`_format_dimension_filters` 接线）

### 初步改造方向（备忘，未定稿）

- 源头（最关键）：改造解析 agent 的维度抽取——role="value" 的 evidence 必须逐字引用问题中的实体子串；泛化头名词（单独的「系统」「平台」等）不作为 dimension 列出。判别依据仍是证据而非词表。
- 通路：删/收紧 `build_optimized_filters` 未命中兜底分支——无匹配（或低于 `optimize_min_score`）不再输出 filter 行，未命中候选转日志。信息不丢失：问题原文仍在提示词，生成模型仍可从「问题 + 表结构」自行构造过滤（规则 5 只限制列必须来自表结构）。
- 远期：真值但向量未召回的 case（错别字/同义词），用确定性探针兜底（候选维度列上有界 `SELECT DISTINCT … ILIKE '%X%'`），以库内实据为准，优于裸文本透传。

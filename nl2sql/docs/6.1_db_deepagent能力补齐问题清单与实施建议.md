# db_deepagent 能力补齐问题清单与实施建议

整理日期：2026-11-12。

## 1. 清单范围与优先级

本清单承接 [6_db_deepagent与LangGraph作业编排对比分析](6_db_deepagent与LangGraph作业编排对比分析.md)，根据 [当前代码复核结果](reviews/2026-11-12_db_deepagent替代能力复核.md) 整理后续需要补充的工作，仅记录问题、优先级、建议和依赖，不展开详细设计。

目标是完整承接旧 LangGraph 父子图中仍需保留的业务功能和可靠性保证。DeepAgents 当前仍使用 LangGraph 运行时与 checkpoint；本清单不以移除 LangGraph 底层依赖为目标。

共列出 **13 个工作条目**，须区分以下性质：

- **当前缺口**：现有业务实现尚未提供的能力或约束。
- **配套改造**：为新增任务账本等机制必须同步完成的工作，不应视为当前已存在的独立漏洞。
- **条件项**：是否实施取决于产品支持范围、旧调用方需求或性能测量结果。

| 优先级 | 含义 |
| --- | --- |
| P0 | 替代验收前必须解决，避免无答案或错误宣告完成；包含相关机制必需的配套改造。 |
| P1 | 补齐运行可靠性、失败退出和执行约束。 |
| P2 | 补齐调度与特定功能，按替代目标决定实施范围。 |
| P3 | 先测量，再决定实施的性能优化。 |

优先级不等于所有条目都必须无条件实施。条件项一旦纳入产品承诺，就应成为对应版本的必做范围。

## 2. P0：结果交付与完成判定

| 编号 | 工作项 | 性质 | 问题说明 | 补充建议 |
| --- | --- | --- | --- | --- |
| 01 | 最终答案的确定性兜底 | **已实现**（2026-11-12；doc 6.2 方案实施，离线回归通过，正常真实查询已验证；异常分支证据来自离线故障注入，见 reviews/doc62_implementation_closeout.md） | SQL 已成功执行，但后续模型异常或未提交答案时，仍可能返回空答案；已有执行证据和归档不等于已有可展示答案。 | 在 Runner 根据可信账本生成降级答案，保留结果、错误、截断标记及未完成说明。同步实时返回、归档、历史和 CLI，避免内容不一致。普通生成失败、预算停止、持久化故障等分别保留明确状态语义。 |
| 02 | 已登记任务的终态与答案覆盖门控 | 当前缺口 | 当前检查 finding 的证据是否合法，不检查全部已规划任务是否处理完毕、是否被最终答案覆盖。 | 新增任务登记工具与任务账本，记录依赖、状态及原因；由提交工具和 Runner 共用判定规则，核对任务终态、证据及答案覆盖。简单问题也有明确的任务记录。 |
| 03 | 任务范围内的 SQL 授权与证据归属 | 配套改造，依赖 02 | 当前 SQL 授权、执行和分析记录没有任务版本。只增加任务清单，无法证明证据属于某个任务，也无法隔离同 SQL 在不同任务中的授权。 | 将任务 ID、revision 和 purpose 贯穿校验授权、执行、分析及最终引用，扩展授权键；拒绝跨任务、跨版本使用授权。同步覆盖内部 probe、pushdown 和证据沿用路径。 |
| 04 | 任务修订、依赖失效与历史沿用规则 | 配套改造，依赖 02、03 | 新任务账本若没有完整版本规则，可能出现修订后继续使用旧证据、作废后旧版本重新生效、历史任务无法唯一定位或并发更新冲突。 | 明确任务完整身份、最新版本选择、作废、依赖失效及历史沿用规则；分析和沿用证据保留来源版本；规划变更整批校验，避免使用旧状态快照造成冲突。 |

共同边界：

- 02—04 应协同设计，不能只靠模型自报 `completed`。
- 完成门控只约束已登记任务，不能证明模型没有漏识别用户意图。
- 正常提交应检查未完成任务；异常中止时，应由服务器保留原因并交付已有结果，不能因仍有 pending 任务再次丢弃结果。
- `no_data` 也需要有效查询证据；成功查询返回零行不等于执行失败。

## 3. P1：运行可靠性与执行约束

| 编号 | 工作项 | 性质 | 问题说明 | 补充建议 |
| --- | --- | --- | --- | --- |
| 05 | 统一模型调用重试策略 | **已实现**（2026-11-12；doc 6.2 §7.5–§7.7 单层重试+步骤共享额度，离线回归通过，正常真实查询已验证；覆盖范围限 OpenAI 兼容主模型同步调用，见 reviews/doc62_implementation_closeout.md） | 底层传输重试和漏提交提醒不能代替项目层故障处理；新增重试还可能叠加调用次数、等待时间和成本。 | 对明确的暂时性错误实施有限重试，统一底层重试、剩余时限、预算和实际尝试次数；耗尽后进入 01 的收敛流程。区分主 Agent 调用与上下文摘要调用的覆盖范围。 |
| 06 | 每任务 SQL 修正上限与失败退出 | 当前缺口 | 当前有全局预算，但 SQL 校验失败后修正几次、何时补查结构、何时放弃，主要由 Agent 决定。 | 基于任务账本记录尝试次数和错误分类，区分补查、修正、澄清及不可恢复错误；达到上限后确定性退出，保留失败原因。不能只新增次数限制而没有耗尽后的状态转移。 |
| 07 | 表结构检查的可验证前置条件 | 当前缺口；硬门控范围待明确 | 模型可能跳过必要的表结构检查；SQL 校验通过不代表字段、关联和业务口径均有依据。 | 新增表检查账本，在 SQL 校验时核对实际物理表；处理 CTE、裸表名、目录不可用、结构来源、新鲜度和内部探针例外。可先观察警告，再对选定范围启用硬门控。 |
| 08 | 任务范围内的防重复执行 | 当前缺口；保证范围待明确 | 同一 SQL 再次成功调用会再次查库；证据 reducer 去重不能消除已发生的数据库执行，同批并发请求也可能重复执行。 | 在查库前识别同任务、同版本、同执行意图的重复请求，处理正在执行中的重复调用；明确重查最新值和沿用已有结果的区别，以及是否覆盖跨进程恢复。 |

共同边界：

- 05 的模型调用重试与 06 的 SQL 业务修正是两类机制，应分别计数和验证。
- 07 不能把 EXPLAIN 成功当作业务口径正确，也不能把 AST 解析失败当作没有表引用。
- 08 不默认建设跨轮全局 SQL 缓存，用户明确要求刷新时应允许重查。

## 4. P2：功能与调度能力

| 编号 | 工作项 | 性质 | 问题说明 | 补充建议 |
| --- | --- | --- | --- | --- |
| 09 | 确定性的批次执行调度 | 调度差异；依赖 02、03、08 | SDK 支持工具并行，但不会自动选择依赖满足的任务、组织执行批次、跳过已完成任务并限制数据库并发。 | 若要承接旧调度语义，增加可信批次执行能力，选择已授权、依赖满足、未执行的任务，受控并行并逐项保存结果和失败。不要求同步增加 SQL 生成并行。 |
| 10 | 常用时间表达扩展 | 条件项 | “前天”“最近三周／个月／一年”等仍受限，部分表达存在滚动区间和完整自然周期等多种口径。 | 明确产品支持范围和默认口径，再扩展确定性解析；补充月末、闰年、跨年、时区和边界验证；无法确定的表达继续澄清。 |
| 11 | 独立 SQL 生成模式 | 条件项 | 完整问答流程不能直接替代旧独立 SQL 子图；现有关闭结果工具的选项仍保留 SQL 执行工具。 | 若需保留该入口，增加服务端强制的生成模式和独立结果契约；明确是否允许 EXPLAIN、元数据查询及维度探针，不依赖提示词禁止执行。 |
| 12 | 旧调用协议与入口的去留 | 条件项 | 新结果协议不能自然还原旧父图全部状态；旧 v1 模块仍在代码中，但当前未挂载。 | 列清实际调用方和入口，分别选择保留、适配或退役；仅为确有需求的调用方提供适配，不默认恢复旧 v1 API。 |

共同边界：

- 09 的并发调用不能依赖同批其他工具尚未提交的状态更新；校验授权与执行的先后关系须明确。
- 10 不能简单把月当作 30 天、年当作 365 天。
- 11 不应通过放松普通问答的证据要求实现 SQL-only。
- 10—12 一旦纳入产品承诺，应进入对应版本的验收清单。

## 6. 所有改造共同需要的配套检查

以下是实施各项时的共同检查，不另计为独立业务缺陷：

- [ ] 工具或参数变化时，同步工具构造、工具集合常量、可见参数契约、装配验证、请求审计和相关测试。
- [ ] 状态或证据结构变化时，同步 reducer、LedgerView、持久化、归档、Runner、API 投影及历史读取；明确已有记录的兼容或重建策略。
- [ ] 修改结果状态时，明确 `completed / partial / failed / needs_clarification / no_data / budget_exhausted / persistence_error` 的判定与各入口展示。
- [ ] 保留已具备的只读执行、实际行数上限、源头截断标记、证据追溯、来源绑定及运行预算约束。
- [ ] 为每项补充可验证的验收条件，覆盖正常完成、部分完成、失败、预算停止及异常中断。
- [ ] 新旧链对照覆盖简单题、依赖任务、独立多问题、多轮、重复调用、历史沿用和零行结果，不只比较正常题集成功率。
- [ ] 统一统计任务覆盖、结果正确性、模型实际尝试、Token、数据库执行次数、重复执行率及延迟，区分离线单测与真实业务验证。

- [ ] 明确任务终态门控的保证范围是已登记任务，不是完整识别所有用户意图。
- [ ] 区分历史验收、当前离线验证与尚待完成的真实模型、数据库和性能对照。

## 8. 建议推进顺序与依赖

- **第一批**：01 可先独立交付，05 与其协调；02—04 作为一组设计。
- **第二批**：基于任务账本补齐 06、08，推进 07 的账本与门控范围。
- **第三批**：在任务身份、授权归属和防重复机制明确后实施 09；10—12 按产品范围安排。
- **测量后优化**：性能测量可提前进行，13 的具体改造以测量结果为依据。
- **全过程**：各批次完成配套检查和针对性验证；全部适用条目达到约定标准后，再进行整体替代验收。

2026-11-24 方案精简后，本文件保留原实验范围、C1—C6 判定及时间戳取证事实。当前首期来源 CI 的正常成功结果复用按 doc 15 §6.3，不能由 C3 的取证要求推导出“全部来源 suite 必须在同一 attempt 重新执行”；私有部署授权禁止跨 attempt 复用仍适用。以下实验准备和执行要求用于解释已完成实验，不要求因方案精简重新运行全部案例。

## 1. 交付目标

使用最小 GitHub Actions 实验验证：将部署并发组放在执行 job 层后，未通过 verify 或本次授权绑定的请求，不会替换同组中已经等待的合法任务。

核心证据必须同时覆盖：C 的执行 job 没有运行，以及原来等待的 B 没有被 C 取消。只有 C 显示 skipped、YAML 能解析或本地模拟通过，不算完成实测。

本任务只验证授权门槛与 GitHub 调度的配合，不验证真实业务发布、Docker、部署锁、来源 CI 查询程序、数据库或服务健康。通过后也不直接启用生产自动发布。

## 2. 执行范围

1. 在维护者指定且允许写入、触发测试的独立实验仓库，或已准备好的私有部署控制仓库内执行。所有测试工作流必须在同一仓库，才能验证共享并发组。先检查是否存在用户任务，避免冲突。
2. 未明确实验仓库或远端写入/实跑范围时，先在本地交付实验文件、执行命令和预计运行数，再向维护者确认缺失信息；已有明确授权时直接在该范围内完成。不要自行创建、公开或修改仓库可见性。
3. 不向当前源码仓库 main 合入实验文件。现有 local-release 仍可能监听 main，不能为了测试云端调度触发现有发布。
4. 所有实验 job 使用标准 GitHub 托管 Runner，例如 ubuntu-latest；不得使用 self-hosted 标签，不触发真实 deploy.yml/local-release，不调用 Docker、部署脚本、Runner 管理服务或本机运行目录。
5. 实验采用专用组 `insightweave-concurrency-probe-<batch_id>-<case_id>`，绝不能使用生产组 `insightweave-local-release`。同一案例 A/B/C 和跨 workflow 的模拟维护 job 必须使用完全相同的组；不同批次/案例隔离。不能将每次运行独有的 github.run_id 加入组名，否则失去互斥测试意义。
6. 只用测试参数和输出，不接入真实部署 Secret。GITHUB_TOKEN 使用实验所需的最小权限；不打印认证凭据。不提高 Actions 付费预算、不升级套餐；私有实验仓库的托管任务会消耗账号每月包含额度，应先估算 job 数和用量。
7. 由维护者自行转交任务即可，本文件不要求另建 Agent、发送消息或改变现有 Agent 会话。

## 3. 待验证的目标结构

| 位置 | 要求 |
| --- | --- |
| workflow 顶层 | 不设置部署组 concurrency，避免 verify 前进入组；实验首期不另加 workflow 层并发 |
| verify | 托管 Runner，处于部署组外，输出实际生成的本次授权绑定 |
| release / 模拟维护执行 job | needs verify；完整 job 级 if 通过后，使用同一固定组，cancel-in-progress 为布尔值 false |
| finalize | needs verify 和执行 job，沿用 doc 15 的严格结果检查，处于部署组外 |
| pending 策略 | 使用默认 single，不设 queue: max；本任务须测清默认 pending 替换行为，不顺便改排队政策 |

执行 job 的 if 至少同时核对：

- `needs.verify.result == 'success'`。
- `authorized_private_run_id == github.run_id`。
- `authorized_private_attempt == github.run_attempt`。
- `authorized_triggering_actor == github.triggering_actor`。

授权条件放在 job 层，不能仅放在执行 job 第一个 step。verify 应从本次上下文产生这些输出，不直接接受外部传入一组“授权成功”结果。实验可用明确标注的测试模式模拟拒绝或缺失输出，但不能声称已验证真实操作者名单或来源 CI 核验。

release 和维护使用同样的授权门槛与并发策略；每个执行 job 覆盖完整模拟操作，不拆成会在中间释放组的多段 job。实验输出开始、结束、失败标记即可，不执行部署。

## 4. 实验准备及观察方法

- 准备最小发布实验工作流和最小维护实验工作流；使用 workflow_dispatch、唯一的 batch/case/角色名称，以及可恢复关联的运行名称。记录固定文件路径、workflow ID 和实际提交 SHA。
- 同一批实验固定工作流提交。局部重跑沿用旧提交及事件，不通过中途改 YAML 冒充一次真实重跑。
- A 是模拟执行者，在执行 job 内保持一段有界时间，例如 90—180 秒；job 总超时需覆盖预期等待。B 是已通过门槛、等待同一组的任务；C 按具体案例产生。等待时长只用于制造窗口，不能单靠睡眠长度判定 B 已入组。
- 发出 C 前，必须取得 A 已开始执行、B 已通过 verify 且正在等待同组的证据。若 A 已结束、B 的 verify 尚未完成，或 B 只是因 Runner 容量不足排队，则本轮没有建立有效前置条件，不能给出 PASS。
- 控制脚本使用 gh api 查询已记录的明确 run ID；缺失时按 doc 15 当前 §5.4 人工核实，不要求旧版自动关联恢复，不用最近一条运行代替 A/B/C。查询 runs/jobs 时按 attempt 分开保存并完整分页。
- 尽量由脚本采集状态和时间，AI 在阶段变化或异常时分析，不让模型反复读取相同日志。每次等待有界并遵守限流，信息不足时报告，避免无限重发或重跑。

## 5. 必测案例

| 编号 | 输入及步骤 | 通过条件 |
| --- | --- | --- |
| C1：verify 拒绝 | A 执行、B 等待后，提交 C；C 的 verify 明确失败 | C 执行 job 不运行；A 不被取消；B 保留并在 A 结束后执行，不能只观察 C skipped |
| C2：job 级绑定拒绝 | 新案例建立 A/B；C 的 verify 返回 success，但故意缺少必需绑定输出或输出错误的 run ID | C 被 job 级 if 阻止；A/B 不受 C 替换影响。它与 C1 分开，避免只验证默认 needs 失败传播 |
| C3：真实局部重跑复用旧输出 | 先创建 F：attempt 1 的 verify 成功，执行 job 按实验模式失败。F 结束后建立 A/B，再对 F 使用 Re-run failed jobs 或指定执行 job 重跑，使旧 verify 未重跑 | 新 attempt 仍引用旧授权输出，因此执行 job 被阻止且 B 保留。保存两个 attempt 的 job 列表，证明 verify 确实未重新执行；若 verify 实际重跑则未测到目标分支 |
| C4：合法 C 的对照 | 新案例建立 A/B，C 通过全部门槛并进入同组 | 默认 single 下，B 被合法 C 替换，A 不被取消；A 结束后 C 执行。作为对照，证明 C1/C2/C3 的 B 保留不是因为 C 根本没有走到调度阶段 |
| C5：跨 workflow 互斥 | 同一仓库中，模拟 release 与维护来自不同 workflow，但共享本案例组 | 两个执行 job 的实际执行区间不重叠；verify 可独立运行。不用 workflow 总起止时间判断执行 job 是否重叠 |
| C6：finalize 不占组 | A 的执行 job 完成后，让 A 的 finalize 保持一段有界时间；B 已通过门槛并等待同组 | B 可在 A 的 finalize 结束前开始执行；证明锁定范围是执行 job，而非整个 workflow。finalize 不输出 deployed 来冒充真实发布 |

C3 的真实重跑至少验证一次；离线手工把 attempt 改成 2 只可作为辅助，不替代 GitHub 输出复用实测。若涉及 API 取消或重跑，先确认目标运行的 batch/case/角色，限制在本次实验，不对任何生产运行操作。

2026-11-23 的 C3 已完成该实测。复核发现：attempt 2 不仅列出旧 verify，还为其登记新 job ID 和 run_attempt=2，实际 job/步骤执行时间却仍属 attempt 1。后续取证必须结合指定 attempt 的 run_started_at 与实际执行时间；不能按“名字出现”“ID 不同”或“run_attempt=2”判定重新执行。原驱动的 C3 自动判据仍有此缺陷，本次 PASS 以报告中的原始 JSON 复核为准；不改写原 verdict/证据，也不为修正文档重新运行六项。

## 6. 检查及判定

先用 YAML 解析和可用的 actionlint 检查实验文件，记录工具版本。结构检查应识别 workflow 顶层误加并发组、verify/finalize 误入组、组名按 workflow/run 分裂、取消策略为 true、绑定条件缺失等问题；只做字符串搜索不能代替结构检查。

真实调度结果逐项使用以下判定：

- **PASS**：前置条件成立，关键 run/attempt/job 证据完整，实际行为满足预期。
- **FAIL**：有效前置条件下行为不符，例如 C 被拒绝后 B 仍被取消。保留证据和最小复现，不通过改变目标条件掩盖失败。
- **INCONCLUSIVE**：没有建立 A/B 等待窗口，证据丢失，平台容量/额度不足，或发生无法排除的外部取消。它不是通过，也不直接证明设计错误。
- **NOT RUN**：未实际触发该项 GitHub 实验。静态检查结果须单独记录。

时间证据至少包括每个 run/attempt 的 verify、执行 job、finalize 状态/结果，以及执行 job 的 started_at/completed_at 和日志中的模拟操作开始/结束标记。API/UI 对并发等待的状态名称如有差异，保存实际响应，结合等待原因和合法 C 对照判断，不仅凭一个 queued 字段断言入组。

一轮无效只在排除原因后补测必要案例，不做无依据的大量重复。若观察到跳过的 job 仍影响并发队列，不宣布方案已保证隔离，应报告 GitHub 调度事实并提出替代门禁方案供复审。

交付：

1. 最小实验 YAML、驱动/证据采集脚本及可复现命令；均与生产工作流区分，标注实验仓库、提交和测试组。
2. 脱敏的 run/attempt/jobs 响应与必要日志，包含每个 A/B/C/F 的明确 ID 和运行链接。无实际日志的结论不得标为实测。
3. 一份 Markdown 报告，建议保存到 `docs/reviews/doc15_job_concurrency_test_report.md`，逐项列出 C1—C6 的前置条件、步骤、证据、判定及失败/未测原因；区分静态结果、调度结果、真实身份核验和生产部署边界。
4. 报告实际测试仓库、工作流 SHA、gh/actionlint 版本、观察到的运行数/用量，以及测试结束后的残留运行和文件情况。必要时只取消仍在运行的本批实验任务，保留结果证据，不删除用户任务或账单数据。
5. 给出对 doc 15 §8.2/§11 的建议修改。当前只做实验和报告，不擅自改生产 YAML、升级套餐、挂接 Runner 或启用部署。

任务完成前阅读实际结果，不以“命令已接受”“工作流总体绿色”或“其他 AI 认为可以”代替证据。若没有完成 GitHub 实测，应如实交付准备成果和未完成原因，不填写通过结论。

## 8. 官方依据

- [GitHub 并发规则](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)：区分 workflow/job 层、默认 single 的 pending 替换及运行中任务的取消策略。
- [GitHub job 条件](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idif)：确认 job 层条件的写法；条件与并发队列配合的实际行为按本任务实测。
- [局部重跑及输出复用](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs)：选定 job 及其下游会重跑，未重跑 job 可保留旧输出，因此必须验证 attempt 绑定。

官方规则提供设计依据，本任务的目标是取得能够复现的调度证据，不能把文档说明本身记成已通过的实验。

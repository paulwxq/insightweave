# 102. 开发与提交备忘录

> 适用范围：InsightWeave 日常功能开发、修复、文档修改、PR 提交及合并后的自动部署。
> 当前流程依据：[doc 15](15_公开项目与私有部署仓库联动及CI_CD改造方案.md)、[上线验收记录](reviews/doc15_release_pipeline_acceptance.md)、[部署手册](../deploy/README.md)。

## 1. 先记住这些原则

- 正常入口固定为：**功能分支 → PR → PR CI → 维护者手动合并 → main CI → 自动部署**。
- **合并 PR 就是发布授权**，main CI 成功后无需再点击部署按钮。
- 不直接推送 main，不使用长期 dev 分支，不启用自动合并或 merge queue。
- PR CI 成功不代表已经部署；通知成功也不代表部署成功。
- 公开仓库只保存可公开的源码、测试和文档，不提交密码、PAT、API Key、完整运行 env 或私有部署日志。
- AI 可以辅助开发和审核，但不能替代测试、CI 和维护者检查。

## 2. 仓库分工

| 仓库 | 用途 | 日常是否需要手动操作 |
| --- | --- | --- |
| `paulwxq/insightweave` | 公开源码、功能分支、PR、公开 CI 和部署通知 | 是，开发、提交和合并都在这里 |
| `paulwxq/insightweave-deploy` | 私有部署控制、来源核验、本地 Runner 发布和结果记录 | 正常流程自动执行；查看部署结果或处理异常时进入 |

两个仓库不合并分支、不双写源码。实际部署版本始终由公开仓库 main 的完整 `source_sha` 确定。

## 3. 日常开发与提交步骤

### 3.1 同步 main 并创建功能分支

```bash
git switch main
git pull --ff-only origin main
git switch -c feat/short-description
```

分支命名：

- 新功能：`feat/xxx`
- 问题修复：`fix/xxx`
- 文档或维护：可使用 `docs/xxx`、`chore/xxx`

一个分支尽量只处理一个明确目标，避免混入无关修改。

### 3.2 修改代码并检查本地差异

```bash
git status --short
git diff
git diff --check
```

提交前确认：

- 修改范围符合本次目标，没有误改或无关格式化。
- 新代码配有项目已有测试体系中的适用测试。
- 配置示例不包含真实凭据，敏感文件没有被加入暂存区。
- 文档中的命令、路径和行为与当前代码一致。

按改动运行相关测试。需要执行共享离线检查时：

```bash
bash deploy/scripts/check.sh all
```

本地检查不能替代后续 PR CI、main CI 和私有发布前的完整检查。

### 3.3 提交并推送功能分支

```bash
git add <明确的本期文件>
git commit -m "feat: concise description"
git push -u origin feat/short-description
```

提交前再次查看：

```bash
git status --short
git diff --cached
```

推送功能分支不会触发生产部署。不要为方便而直接提交或推送 main。

### 3.4 创建目标为 main 的 PR

可在 GitHub 页面创建，或使用：

```bash
gh pr create --base main --head feat/short-description --fill
```

PR 描述至少说明：

- 修改目的和主要变化。
- 已执行的测试及结果。
- 是否影响部署、配置、数据库、接口或使用方式。
- 需要审核者特别注意的风险或未完成事项。

### 3.5 等待 PR CI 并修正问题

PR CI 包含五个必需套件：

- `nl2sql`
- `agent_core`
- `metaweave`
- `deploy_tests`
- `frontend`

汇总检查固定为 `ci-required`。任何必需套件失败、取消、跳过或缺失，都不能视为通过。

如果检查失败：

1. 查看失败日志并确认原因。
2. 在原功能分支修改。
3. 提交并再次推送同一分支。
4. 等待新的 PR CI，不另建重复 PR。

```bash
git add <修复文件>
git commit -m "fix: address CI failure"
git push
```

### 3.6 审核并手动合并

合并前检查实际差异和检查结果：

```bash
gh pr view <PR编号>
gh pr diff <PR编号>
gh pr checks <PR编号>
```

当前是单人维护流程，不要求其他人 Approve；维护者自查和 CI 是合并门槛。确认本次修改可以发布后，在 GitHub 选择 **Create a merge commit**，或执行：

```bash
gh pr merge <PR编号> --merge
```

**执行合并前必须确认愿意发布，因为合并即授权后续自动部署。**

## 4. 合并后的自动链路

```text
main 实际合并提交
  → 公开 main CI
  → notify-deploy 发送 source_sha / source_run_id / source_run_attempt
  → 私有 verify 核验维护者身份、固定来源、最新 attempt 和当前 main
  → 私有 release 在本地 Runner 复核并固定检出 source_sha
  → 完整测试、三镜像构建、部署预检、排空、替换和冒烟
  → 私有 finalize 核实并记录实际部署结果
```

注意：

- PR 使用合并预备引用检查，生产部署只使用 main 的真实合并提交。
- 私有端只接受当前 main HEAD 对应的最新成功来源 CI，不选择更早版本兜底。
- `notify-deploy` 绿色只表示私有工作流已受理，不表示服务已经更新。
- `finalize` 只有在 release 成功且明确输出 `outcome=deployed` 时才确认实际部署成功。
- 当前设计不保证每次合并都实际部署，也不保证异常后自动补发或最新 main 最终一定自动部署。

## 5. 合并后需要做什么

### 5.1 查看公开 CI 和通知

在公开仓库 Actions 中确认 main CI 和通知结果。也可使用：

```bash
gh run list --repo paulwxq/insightweave --workflow ci.yml --limit 5
```

通知摘要中的私有 run ID 是后续追踪的主要依据，不要用“最近一条私有 run”自动认领本次部署。

### 5.2 查看私有部署结果

按通知回执中的实际编号查看：

```bash
gh run view <PRIVATE_RUN_ID> --repo paulwxq/insightweave-deploy
```

需要浏览列表时：

```bash
gh run list --repo paulwxq/insightweave-deploy --workflow deploy.yml --limit 5
```

确认私有摘要中的源码 SHA、来源 run/attempt、私有 run/attempt、release_id 和实际结果。必要时再检查本机服务状态。

### 5.3 同步本地 main

```bash
git switch main
git pull --ff-only origin main
```

本地同步不影响远端自动部署。功能分支是否删除可另行决定，不影响已经完成的发布。

## 6. 常见情况处理

| 情况 | 正确处理 |
| --- | --- |
| PR CI 失败 | 在原功能分支修复并推送，等待新检查；不直接合并 |
| main CI 失败 | 不取得发布资格；新建修复分支和 PR，不直接推送 main |
| 通知发送失败或受理结果不明 | 先检查公开通知、私有 run 和本机现场；不自动重复 POST，不盲目重跑 |
| 请求已过期或 main 已前进 | 不部署旧请求；`DEPLOY_STALE_REQUEST` 对应的红色未部署结果可能属于预期，核实最新 main 后再决定 |
| 私有部署失败、取消或中断 | 同时核对工作流与真实现场，不凭颜色认定未部署，不假定已经自动回滚 |
| `finalize` 未运行或失败 | 核查 release 的实际 `deployed` 输出和本机服务，不自动补账 |
| 部署成功后想做健康检查 | 使用只读检查，不重跑通知或部署；完整重跑可能再次构建和部署同一源码 |
| 连续快速合并多个 PR | 较早请求可能过期、取消或未部署；不依赖系统自动补偿，按最新 main 和实际运行逐项核实 |
| 只修改文档 | 当前同样运行 main CI 并可能进入部署，合并前仍按发布操作对待 |

## 7. 重跑与恢复底线

- 不为了“再试一次”而连续重跑公开 CI、通知和私有部署。
- 先确认旧运行已经结束、现场状态明确、来源仍是当前 main 和最新有效 attempt。
- 私有部署需要重试时，按 doc 15 的恢复表使用 **Re-run all jobs**，不用局部重跑代替完整身份核验。
- 不批量重放旧通知，不把重跑部署当作只读健康检查。
- 维护暂停、配置修改、手动恢复和回滚按 [部署手册](../deploy/README.md) 及 doc 15 的维护章节执行，不在日常提交流程中临时发挥。

## 8. 最短记忆版

```text
拉最新 main
→ 建 feat/fix 分支
→ 修改、测试、检查 diff
→ commit、push
→ 创建 PR
→ 等 ci-required 通过
→ 检查差异并确认要发布
→ 手动 merge commit
→ main CI 自动运行
→ 私有仓自动核验和部署
→ 查看私有 run 与实际服务
→ 同步本地 main
```

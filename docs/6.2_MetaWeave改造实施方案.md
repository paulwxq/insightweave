# 6.2 MetaWeave 改造实施方案

编写日期：2026-10-21。状态：**开发前的实施方案；尚未据此修改代码或执行数据库重建、旧数据清理。**

## 1. 文档定位与实施边界

本文把已经审核的 [第 6 章：四层模型](6_工作区采集作业与发布作业四层模型.md) 和 [6.1：建表语句汇总](6.1_建表语句汇总.md) 转换为开发任务、接口约定、执行流程和验收清单。业务规则以第 6 章为准，表、约束及 manifest 格式以 6.1 为准；本篇不重复维护另一套建表语句。第 5 章系列是讨论过程记录，其中 Domain 描述的生命周期继续参考 [5.4](5.4_Domain采集步骤变更方案.md)，但作业模型和参数保存方式以第 6 章、6.1 为准。

**当前项目未上线。实施时先将本次改造范围内的旧表统一改名留存，全部完成后再创建新表；不迁移、不向下兼容。**旧表及其数据仅隔离留存，不供新业务使用，不复制到新表。不保留旧 UUID 数据源、旧作业、旧发布及旧会话的业务可用性，不建立旧接口、旧目录或旧表兼容层；也不操作源数据库中的业务数据。命名及对象冲突处理见 6.1 §10.0，实施顺序见本篇 §12。

本文中的文件清单是现有代码的主要改造入口，不表示只有这些文件受影响。接口路径、请求结构和同进程执行方式按本篇约定实施；这些是目标能力，当前代码尚未实现。

### 1.1 本期交付范围

- 数据源短 ID、工作区创建及工作区目录。
- 采集作业和发布作业的保存、不可变配置版本、默认运行和手工子集运行。
- 一次运行一条 run_info、多条 run_step，保存真实参数、逐步骤状态和 manifest。
- 工作区产物共享、生成时整目录备份、人工编辑时文件级备份、采集 marker、发布预检和发布页采集时间展示。
- 旧表替换、资产查询、短 ID 的下游写入与 NL2SQL 联动。
- 首次使用前的一次性旧数据清理及端到端验证。

本期不实现调度器、步骤并行执行、运行取消或中止、作业启停管理、独立人工确认版本、完整产物快照、历史重放或自动新鲜度判断。表中的 `scheduled` 取值仅预留给后续调度接入。运行发起后不提供取消接口或按钮；离开页面、关闭浏览器或停止轮询都不表示取消执行。

**本期完全不提供工作区、采集作业、发布作业及其配置版本、运行记录的删除入口。**WebUI、API 和 CLI 均不新增这些对象的删除操作，不实现软删除、级联删除或自动回收。工作区和作业可以创建、查看及按既定规则修改、执行，但不能通过产品删除；明确接受试错后废弃对象继续保留、`output/` 残留目录由人工清理的限制。人工清理目录不自动删除数据库中的工作区、作业或运行记录。

### 1.2 实施时必须保留的结论

| 事项 | 本期规则 |
| --- | --- |
| 文件隔离 | 只由 `workspace_id` 隔离，目录为 `output/<source_id>/<workspace_id>/`。 |
| 下游内容 | 同源只保留一套当前内容，五张内容表保留现有主键组成；同源各工作区向同一目标发布按步骤既有范围替换，不增加工作区内容副本。 |
| 作业与运行 | 作业保存默认配置；每次执行生成新运行 UUID。修改作业不改写历史版本和运行。 |
| 手工执行 | 只能选择引用版本中步骤的非空子集；临时参数不保存回作业。 |
| 采集排序 | 复用现有后端拓扑排序；只处理选中步骤，不自动补选上游。 |
| 发布准入 | 创建运行前，集中检查本工作区全部所选步骤的输入目录、唯一成功采集 marker、必要文件、内容及配置；任一步骤不合格即整单返回 `400`，不生成运行、不写业务记录。全部通过才创建运行；执行期复查不合格才记 `blocked`。 |
| 时间展示 | 展示各输入目录 marker 中的采集完成时间；不自动比较新鲜度，不告警、不阻断。 |
| 标志文件 | 只写采集 marker，不写 `.pub_run_id_*`。`blocked` 不写 marker。 |
| 备份方式 | 采集或发布生成文件时整目录备份；发布前人工编辑只复制将被覆盖文件的旧版本，其他文件和采集 marker 原地不动。 |
| 备份失败 | 生成场景告警、删除尚未移走的旧内容后继续生成；人工编辑保存则明确报错，不写回、不删除任何现有内容。 |
| 发布历史 | 使用 6.1 §12 的最后成功发布视图；不新增 current 表或 `is_current_publish`。 |
| 删除边界 | 本期不提供工作区、作业、版本和运行记录的删除入口，不级联删除；废弃目录接受人工清理，与一次性旧数据清理区分。 |
| 清单 | 使用已有可空 manifest 字段，不额外生成清单文件或产物版本表。 |

### 2.1 已有能力与真正需要调整的地方

1. `collection_run.py` 的 `normalize_collection_steps()` 已经完成非空、白名单、去重和拓扑排序。**不另建采集排序模块，不以本次改造为理由重写算法。**仅将 `dim_config` 标识改为 `dim`，更新相应依赖、调用和测试。
2. 当前 `CreateCollectionJobView.vue` 先排序，再逐步骤调用 API，每次请求只传一个步骤。新模型必须让一次点击选中的整组步骤归属同一个 `collection_run_id`；不能照搬为“一步创建一个新运行”。
3. 当前发布后端 `normalize_publish_steps()` 只校验和去重，前端 `SELECTABLE_STEPS` 负责构造固定顺序。新入口要把固定顺序落实到后端，不能只依赖页面。
4. 旧 `job_info` 的同一条步骤记录会被重跑更新；新 run_step 每次运行新建，不覆盖上次执行结果。旧 `job_id` 同时承担过隔离和执行归属，不能全局替换为新作业 ID。
5. 现有 Rel 发布同时包含内容检查、冲突检查和时间新鲜度检查。只移除跨步骤时间先后的新鲜度要求，不删除其他检查。
6. 当前 `publish_steps()` 在生成 `publish_id` 前集中预检：所选步骤未就绪时返回 HTTP `400`，旧 `_assert_job_admission()` 要求整个采集 job 的现有步骤全部成功，否则返回 HTTP `409`；两者均拒绝整次发布且不生成发布 ID。新模型仍废除依赖旧 `job_info` 的 `409` 作业级准入，但保留步骤就绪的集中预检及整单拒绝形式：创建运行前，按当前工作区输入目录的唯一成功采集 marker、必要文件、内容及配置检查全部所选步骤，任一步骤不合格即返回 `400`，指出具体步骤和原因，不生成运行、不写业务记录。全部通过才创建发布运行和步骤行；创建后执行期复查不合格的步骤才记 `blocked`，实际执行出错记 `failed`，最终按实际结果汇总。请求或全局环境错误仍按 §6.4 返回。

## 4. ID、数据库与作业版本

### 4.1 ID 与关联关系

| 身份 | 数据库类型 | 值示例 | 生成与关联 |
| --- | --- | --- | --- |
| 数据源 | `text` | `db_src_1` | 数据库独立序列生成；字段仍叫 `source_id`。 |
| 工作区 | `text` | `ws_1` | 独立序列生成，保存唯一的所属 `source_id`。 |
| 采集作业 | `text` | `coll_job_1` | 独立序列生成，引用 `workspace_info.workspace_id`。 |
| 发布作业 | `text` | `pub_job_1` | 独立序列生成，引用 `workspace_info.workspace_id`。 |
| 采集运行 | `uuid` | 每次生成的新 UUID | 用 `(collection_job_id, revision_no)` 引用采集版本。 |
| 发布运行 | `uuid` | 每次生成的新 UUID | 用 `(publish_job_id, revision_no)` 引用发布版本。 |

短 ID 序列全局递增，不按每个父对象重新从 1 编号，不承诺连续无缺号。不能使用 `MAX(id) + 1`。运行 UUID、用户 UUID 与短 ID 使用不同校验函数，不能把所有原 UUID 检查一起改成任意字符串检查。当前只实现数据库来源，不因预留 `file_src_` 而增加文件采集功能。

后端通过“运行 → 作业 → 工作区 → 数据源”获得上下文；同时传入父、子 ID 的请求必须校验归属一致。`workspace_info` 虽未对数据库来源表建立外键，服务仍须检查本期数据源存在及其可用性。不能把缺少数据库外键理解为允许任意来源字符串。

### 4.2 模型和初始化

先统一改名本次范围内的全部旧表，再创建十五张目标表和一个视图，名称、约束、注释、索引以 6.1 为准；`db_source_info` 使用 §13 的 `text` 短 ID 定义，五张内容表按 §14～§18 保留原主键组成。旧 `job_info`、`publish_info` 一并改名留存，不再以原名称创建业务表，不建立映射表或兼容视图。

DDL 和 ORM 要核对字段类型、可空性、默认值、复合主外键以及 `partial_success`。运行表只保留到版本表的复合外键，不重复添加到作业主表的单列外键。版本表不增加独立的 revision ID、`created_by_user_id` 或 `updated_at`；步骤表不增加 `step_order`。

数据库初始化应有明确入口，先完成旧表及冲突索引、序列等对象的统一改名，再按外键依赖顺序创建新对象，最后创建视图。旧外键保持关联旧表，新外键按新 DDL 建立；不将旧对象误当新对象复用。该操作显式执行一次，不放进普通服务启动或每次运行流程。

### 4.3 作业保存和版本生成

1. 首次保存，在同一事务中写作业主表和 `revision_no = 1` 的版本行；保存成功不执行采集或发布。
2. 执行配置修改时锁定作业主表，读取最大版本号后加一并插入版本，更新主表的 `updated_at`。旧版本不可原地更新。
3. 默认版本取该作业最大 `revision_no`。仅修改名称、用途说明等主表信息，不需要伪造一次执行配置变更；改变步骤或默认参数才新增配置版本。
4. `steps` 非空、无重复、在白名单内；参数只属于已选步骤，且为该步骤支持的参数。错误明确返回，不能悄悄忽略未知参数。
5. 四处 `step_config` 统一可空。无额外参数用 SQL `NULL`，空对象归一为 SQL `NULL`；版本保存按步骤组织的默认参数，运行步骤保存本次实际消费的参数。
6. 作业所属工作区创建后不可更换。本期明确不提供工作区、作业、版本或运行记录删除，不增加级联删除、软删除字段及对应管理功能；废弃作业和历史记录继续保留。

作业默认配置示例：

```json
{
  "steps": ["ddl", "json", "md", "domain", "rel"],
  "step_config": {
    "domain": {"description": "订单与销售分析数据库"}
  }
}
```

这个 `description` 是首次生成的默认输入，不是工作区当前数据库描述的数据库副本，也不是整份 YAML 的快照。

## 5. 工作区文件处理

### 5.1 工作区创建与路径

创建工作区先验证来源，保存工作区记录并创建 `output/<source_id>/<workspace_id>/`。若目录创建失败，接口明确返回失败并回滚本次新增记录；短 ID 序列因此出现空号可以接受。目录创建不必预先生成各步骤产物。

所有受管读写通过统一路径解析函数定位，不接受前端传来的任意绝对路径。将现有 resolver 的隔离参数由旧 `job_id` 改为 `workspace_id`，保留项目边界、目录归属和符号链接检查。

现有重跑及编辑冲突保护按工作区定位：同一工作区的两个不同作业可能更新同一目录，不能因为作业 ID 不同就绕过冲突检查。本期沿用现有锁和复核方式进行适配，不新增分布式锁系统。

步骤及目录更名要同时覆盖常量、依赖图、API 白名单、页面、配置注入和测试：采集 `dim_config` → `dim`，目录 `dim_config/` → `dim/`；`sql-rag/` → `sql/`。发布步骤 `dim_value`、`table_schema` 不因输入目录更名而改名。现有底层生成器函数名和 CLI 功能开关保持不变，包括 `--generate-domains`、`--generate-dim-config`、`--generate-sql-rag`；通过配置和调用参数适配新步骤标识、工作区路径及短 ID，不做无差别字符串替换。身份定位参数按已确定的新模型调整：`--source_id` 名称不变、值改为短 ID，原隔离参数 `--job_id` 改为 `--workspace_id`，不保留旧参数兼容入口。

### 5.2 生成与人工编辑的备份

**采集生成、发布辅助文件生成使用整目录备份。**抽取共用的目录更新前备份函数，由采集生成及发布生成 `cql/` 等辅助文件的流程调用，沿用第 6 章 §6 的规则；人工编辑不调用此函数。

1. 先读入本次更新必须保留的旧内容，再对本次将改写的目录执行备份。
2. 旧内容移入 `<步骤目录>/.backup/bak_yyyyMMdd_HHmmss_SSS/`，保留文件名和相对结构；包括点号文件及旧 marker，只排除 `.backup/` 自身。
3. 时间戳固定 `Asia/Shanghai`、毫秒三位；同名时生成不覆盖既有目录的唯一后缀。没有旧内容时不创建空备份。
4. 备份以一次目录更新为单位，只执行一次，不在每写一个输出文件或 marker 时重复备份。
5. **仅生成场景：**备份失败记录目录和失败原因的告警，删除尚未移走的残留旧内容，继续生成；不完整备份不作为完整版本使用。删除或新文件写入本身失败时，应如实记录文件操作失败，不能伪报成功。人工编辑备份失败不适用“删除残留、继续生成”，而是按下文终止本次保存并明确报错。

**发布前人工编辑使用独立的文件级备份。**当前只有以下三个入口，均属于第 6 章 §5 的“发布前编辑、准备工作区产物”，不是采集步骤执行的一部分：

| 编辑入口 | 当前服务 | 本次改写文件 |
| --- | --- | --- |
| Domain 配置编辑 | `metaweave/backend/profile_loading/domain_config_api.py` | `domain/db_domains.yaml`。 |
| Rel 配置编辑 | `metaweave/backend/profile_loading/rel_config_api.py` | `rel/` 下本次将被改写的关系配置文件。 |
| Dim 配置编辑 | `metaweave/backend/profile_loading/dim_value_config_api.py` | `dim/dim_tables.yaml`。 |

文件级备份及保存规则：

1. 沿用现有内容校验和编辑冲突检查。保存前，只把本次将被覆盖文件的旧版本**复制**进 `<步骤目录>/.backup/bak_yyyyMMdd_HHmmss_SSS/`，保留文件名；不移动原文件，不扫描或备份其他产物。全部待覆盖文件的旧版本复制成功后，才写回本次编辑内容。
2. 时间戳与第 6 章 §6 一致：固定 `Asia/Shanghai`、24 小时制、毫秒三位，重名不得覆盖已有备份。编辑备份只包含被覆盖文件的旧版本，不包含其他产物或采集 marker。
3. **编辑全程不得生成、修改、移动或删除采集 marker，也不把 marker 复制进编辑备份。**目录内其他文件原地不动，不需要读取后重建或恢复 marker。marker 继续表示原采集运行的产物来源；编辑不生成新采集运行、不伪造 run_id 或采集完成时间，也不写发布 marker。
4. 旧文件复制备份失败时，本次保存整体失败，明确返回保存错误；不进入原文件写回，不删除任何现有内容，原文件、其他产物及 marker 保持保存前原状。不得以“告警后仍保存成功”处理，用户可重试保存；本次未完成的备份不能作为完整备份使用。
5. 备份成功后，写回编辑内容本身失败时，同样明确返回保存错误，不伪报成功；本次已完成的文件级备份保留，供人工核对恢复，本期不做自动回滚。沿用现有临时文件和单文件原子替换方式，不改为直接截断原文件写入；多文件保存若已有部分文件替换成功，应说明已写入范围，不能承诺整组文件保持原状。写回失败也不触碰采集 marker。用户可在人工核对已写入范围后手动重试保存，仍须通过现有内容及冲突校验；重试产生的新备份只反映重试时点的文件状态，不能替代或覆盖前次失败保存前已完成的完整备份。

两类备份可共用时间戳和备份目录命名工具，但文件级复制与整目录移动、以及各自失败策略必须明确分开，不能以编辑后恢复 marker 的方式复用整目录备份。

### 5.3 采集 marker 与普通产物扫描

提供专门的 marker 读写函数，规则完全按第 6 章 §6：

```text
.coll_run_id_<collection_run_id>_<yyyyMMdd-HHmmssSSS>_success
.coll_run_id_<collection_run_id>_<yyyyMMdd-HHmmssSSS>_failed
```

每个采集步骤目录顶层最多一个。采集重跑的整目录备份通常会移走旧 marker；采集写入新 marker 前仍清除顶层旧采集 marker。成功产物通过检查后写 `success`，实际执行失败写 `failed`；未启动或 `blocked` 不写。未选目录不改动。人工编辑不进入此 marker 写入或清理流程，成功或失败都不触碰现有 marker。意外退出未写 marker 的情况按第 6 章处理，不新增崩溃恢复系统。

普通扫描递归进入目录时，同样忽略每一级名称以 `.` 开头的文件和目录；marker 由专门逻辑读取，不混入产物清单。发布找不到采集 marker 或读到失败 marker 时不可发布，不回退 `.backup/`，不从历史成功运行中补一个 marker。

## 6. API 与一次运行的生命周期

### 6.1 资源接口

接口统一使用 `/api` 前缀。下表中的 `{id}` 按所在资源分别指采集或发布作业 ID，不新增一个混用的通用 job ID。

| 操作 | 接口 | 核心行为 |
| --- | --- | --- |
| 工作区列表、创建 | `GET/POST /api/data-sources/{source_id}/workspaces` | 列出同源工作区；创建记录和目录。 |
| 跨源工作区列表 | `GET /api/workspaces?source_id=&limit=&offset=` | `source_id` 可选；服务端分页返回 `items/total/limit/offset`，供全局工作区管理页使用，不由前端逐源拉取后拼接。 |
| 工作区详情、基本信息修改 | `GET/PATCH /api/workspaces/{workspace_id}` | 返回来源与基本信息，不允许改绑来源。 |
| 采集作业列表、创建 | `GET/POST /api/workspaces/{workspace_id}/collection-jobs` | 保存定义，首次创建版本 1，不执行。 |
| 发布作业列表、创建 | `GET/POST /api/workspaces/{workspace_id}/publish-jobs` | 保存定义；没有产物也可以保存。 |
| 作业详情、基本信息修改 | `GET/PATCH /api/collection-jobs/{id}`、`/api/publish-jobs/{id}` | 返回作业信息和默认版本；PATCH 仅修改主表信息。 |
| 版本列表、新配置保存 | `GET/POST /api/collection-jobs/{id}/revisions`、发布对应路径 | POST 新增版本，不更新旧版本。 |
| 单版本详情 | `GET /api/collection-jobs/{id}/revisions/{revision_no}`、发布对应路径 | 运行详情可以查看当时默认配置。 |
| 发起运行 | `POST /api/collection-jobs/{id}/runs`、`/api/publish-jobs/{id}/runs` | 一次提交整组步骤；发布须先全部通过集中预检才生成运行，否则整单 `400` 且不留业务记录。 |
| 运行详情 | `GET /api/collection-runs/{collection_run_id}`、发布对应路径 | 返回整体、逐步骤状态、时间、参数和 manifest。 |
| 作业运行历史 | `GET /api/collection-jobs/{id}/runs`、发布对应路径 | 按该作业列出运行，不把运行当成已保存作业。 |
| 工作区采集运行列表 | `GET /api/workspaces/{workspace_id}/collection-runs` | 服务端查询该工作区所有采集作业的运行，供首页展示最近运行。 |
| 工作区发布运行列表 | `GET /api/workspaces/{workspace_id}/publish-runs` | 服务端查询该工作区所有发布作业的运行，供首页展示最近运行。 |
| 发布产物预检 | `GET /api/workspaces/{workspace_id}/publish-check` | 不提供 `steps` 参数，固定返回 §8.1 全部 8 个发布步骤的条件、原因及输入目录采集时间，由前端按当前作业版本和本次选择过滤展示；正式请求仅集中预检本次所选步骤。 |
| 文件编辑 | `GET/PUT /api/workspaces/{workspace_id}/domain-config`、`GET/PUT /api/workspaces/{workspace_id}/rel-config`、`GET/PUT /api/workspaces/{workspace_id}/dim-config` | 沿用现有方法：GET 读取，PUT 保存；将三个入口改为工作区定位，保留编辑能力和冲突检查，保存前按 §5.2 文件级备份。 |

跨源工作区列表的 `source_id` 可省略，传入时必须为合法短 ID；`limit` 默认 20、范围 1–100，`offset` 默认 0、不得为负；按 `created_at DESC`、`workspace_id DESC` 排序，列表项字段与 `WorkspaceItem` 一致。该接口只解决“跨源列表与分页”，工作区详情、作业数和运行统计仍从各自资源接口读取；本期不返回设计稿中尚未定义的作业数、运行状态分布等聚合统计。

原数据源登记、连接检查、启停接口保留其业务能力，参数改短 ID。旧的“在 source 下直接创建并执行旧 job”接口由新资源接口替代，不保留旧请求格式。作业列表和执行历史必须分开返回。

本期不提供工作区、采集/发布作业、版本或运行记录的 `DELETE` 接口，也不以其他 HTTP 方法、清空目录接口或 CLI 命令提供等价删除入口。不能通过删除父对象间接级联删除这些对象；现有数据源删除流程遇到已关联工作区时应拒绝操作，不得借旧 `delete_output` 参数删除新工作区目录或留下无来源的工作区。

工作区运行列表在后端通过运行与作业主表关联限定工作区，不由前端逐个作业拉取再聚合。与作业运行历史统一使用 `limit`、`offset` 分页：`limit` 默认 20、范围 1～100，`offset` 默认 0、不得为负；按运行 `created_at DESC`、运行 UUID `DESC` 排序。列表项包含对应运行 ID、作业 ID、作业名称、`revision_no`、`status`、`trigger_type`、`created_at`、`started_at`、`finished_at`，时间为空时原样返回；不跨工作区混入记录。作业运行历史与工作区运行列表的响应统一包含 `items/total/limit/offset`；`total` 是筛选条件下的全部运行数，不是当前页条数。

采集/发布作业列表（`GET /api/workspaces/{workspace_id}/collection-jobs`、`/publish-jobs`）返回该工作区的**全部作业**，不提供 `limit`/`offset` 参数，也没有 `items/total/limit/offset` 分页信封；本节的运行分页约定不适用于作业列表。数据源列表（`GET /api/data-sources`）同样一次性返回全部登记记录。前端对这两类全量列表可在客户端做筛选，但不做分页。

**工作区运行列表的索引支撑：**本期复用 6.1 已定义的约束索引和运行索引，不重复增加作业表的单列 `workspace_id` 索引：

- `collection_job_info_workspace_name_key`、`publish_job_info_workspace_name_key` 的 `UNIQUE (workspace_id, job_name)` 会各自建立唯一 B-tree 索引，首列均为 `workspace_id`，可支持按工作区筛选作业。这来自唯一约束，不是外键自动建索引。
- `collection_run_info_job_created_idx`、`publish_run_info_job_created_idx` 分别覆盖对应的 `(作业 ID, created_at DESC)`，可支持按筛出的作业关联读取运行。

这些索引不保证跨作业的 `created_at DESC, 运行 UUID DESC` 全局排序免于额外排序；具体执行计划由 PostgreSQL 选择。实施时先复用上述索引，后续若出现实际慢查询，再根据数据量及 `EXPLAIN (ANALYZE, BUFFERS)` 结果调整，不因外键列没有单独的 `CREATE INDEX` 就重复建索引。

### 6.2 发起请求与参数确定

运行请求明确携带界面已展示的 `revision_no`，避免用户看的是旧版本却执行了刚保存的新版本：

```json
{
  "revision_no": 2,
  "mode": "custom",
  "steps": ["rel"],
  "step_config": null
}
```

- `mode = default`：执行请求所引用版本的全部步骤和默认参数。`steps` 允许省略、传 `null` 或空数组 `[]`，均表示不覆盖步骤，仍执行该版本全部步骤；传入非空步骤数组时，须与该版本的完整步骤集合一致，视为对默认范围的确认，不作为步骤覆盖。缺少或增加步骤则返回 HTTP `400`，明确指出不匹配内容，不忽略、不创建运行。`step_config` 仍允许省略、传 `null` 或空对象 `{}`，均表示没有临时覆盖；非空配置返回 `400`，需要临时参数时使用 `custom` 模式。非数组步骤、非对象配置等错误类型按请求格式校验拒绝，不能当作无覆盖。
- `mode = custom`：步骤非空且为该版本的子集，**允许与版本全集相同，不要求真子集**，不能因用户选全步骤而要求改用 `default`。未覆盖的参数继承该版本默认值，覆盖仅作用于所选步骤允许的参数；选择全集且没有临时参数覆盖时，步骤范围和生效参数与默认模式一致，采集仍按本次请求进行既有依赖排序。选择全集时也允许临时修改参数，不把临时配置写回 revision。
- 顶层 `step_config = null` 表示没有临时覆盖。最终写入 run_step 的是解析后的实际参数，不是请求中的覆盖片段；无参数时仍写 SQL `NULL`。
- 版本和临时配置解析不能覆盖工作区 YAML 当前有效描述，具体见 §7.2。准备阶段读取文件后应记录真正消费的参数，不把被忽略的默认输入写成生效值。
- `mode` 只是请求含义，不因此增加数据库字段；手工两种模式的 `trigger_type` 均由服务写为 `manual`，不由客户端伪装成定时运行。

默认模式的非空 `steps` 沿用现有白名单校验和去重逻辑，再比较完整步骤集合，不要求请求数组与版本数组的顺序相同。真正执行的步骤及排序输入仍取自引用版本：采集按现有后端依赖排序，发布按固定顺序执行；请求数组只用于确认范围，不能改变默认执行顺序。显式 `revision_no` 固定配置版本，新版本保存后不自动切换本次执行版本。

| 默认模式字段 | 接受的形式 | 不接受的形式 |
| --- | --- | --- |
| `steps` | 省略、`null`、`[]`，或通过校验后与引用版本完整步骤集合一致的数组。 | 缺少或增加步骤、未知步骤或错误类型；不静默忽略不匹配内容。 |
| `step_config` | 省略、`null`、`{}`，均为无临时覆盖。 | 非空配置或错误类型；非空配置须改用 `custom`。 |

这里有意保留步骤与参数的不同约定：非空 `steps` 可以确认默认执行范围，非空 `step_config` 只作为临时参数覆盖，不提供“确认默认参数”的通道；即使对象内容与版本默认参数完全相同，默认模式仍返回 `400`，应改用 `custom`。本期不增加参数对象的深比较和相等放行逻辑。

上述空值约定仅表示默认模式不覆盖步骤和参数；`custom` 模式仍必须提供非空步骤子集，不能因 `steps` 为空而自动执行全部步骤。

### 6.3 创建、执行与进度返回

本期采用**同进程后台执行加状态查询**：使用 FastAPI 的 `BackgroundTasks`，在任务内复用线程执行同步步骤服务，不引入独立任务队列或调度系统。

1. 接口验证来源、作业归属、版本、步骤和参数，对整组采集步骤调用现有排序函数；发布步骤按 §8.1 的固定顺序排序。
2. **仅发布运行增加创建前集中预检：**检查当前工作区全部所选步骤需要的采集 marker、文件、内容和配置，任一步骤不合格即返回 `400`，指出步骤和原因，不生成运行、不写业务记录，也不启动后台任务。全部通过才进入下一步；此流程不依赖页面之前的 `/publish-check` 结果，不能用页面预检替代本次请求的集中预检。采集流程不增加这道发布准入，仍在创建运行后处理各步骤的前置条件。
3. 同一事务创建一条 `pending` run_info，以及所有本次选中的 `pending` run_step。只给选中步骤建行。
4. 返回 `202` 和新运行 UUID、引用版本、本次步骤；同进程任务持有这次解析后的执行计划。前端轮询运行详情，不再按步骤反复创建运行。
5. 后台任务仅执行本次 HTTP 请求刚创建的那一个运行：按本次运行 ID 校验其仍为 `pending` 后，设置整体 `running` 和 `started_at`，各步骤执行前、后分别写状态及时间。本期不存在扫描数据库并接管其他 `pending` 运行的机制，服务启动时也不扫描或恢复遗留的 `pending/running` 运行（见本节末段及验收 A25）。发布步骤在实际启动前仍需复查，创建后复查不合格按 §6.4 记 `blocked`。数据库会话在任务内创建，不能把请求已关闭的会话带进后台。
6. 整组执行完后按 §6.4 汇总终态和 `finished_at`。运行期间新保存的作业版本不影响本次版本、步骤和参数。

服务进程退出后，尚未完成的同进程后台任务不会自动恢复执行，可能留下 `pending/running` 记录。本期不实现启动扫描、定时扫描或其他自动续跑机制；新请求附带的后台任务也不补跑旧记录，用户重跑产生新的运行 UUID。浏览器等待或查询失败不等于执行失败，前端应以运行记录为准，不自动重新提交一次执行。后续接入持久任务系统时保留现有运行模型。

服务重启后，详情、历史和工作区运行列表均原样展示数据库中的 `pending/running`，不自动翻转为失败，不新增“可能已中断”的判定状态或提示。页面展示 `created_at`、`started_at` 和尚为空的 `finished_at`，由用户据此判断；不能把“查询到 running”解释为已确认后台任务仍存活。

### 6.4 状态与失败处理

| 对象 | 流转和判定 |
| --- | --- |
| run_step | 已创建运行内，`pending → running → success/failed`；采集步骤前置条件不满足，或发布步骤在创建后执行期复查不合格时，`pending → blocked`。发布创建前的准入失败不建立步骤行。 |
| run_info | `pending → running → success/partial_success/failed`。 |
| 全部成功 | 所选步骤均 `success`，整体 `success`。 |
| 部分成功 | 至少一个 `success`，且有 `failed/blocked`，整体 `partial_success`。 |
| 没有成功 | 运行结束且无成功步骤，整体 `failed`，包括全部被阻断的情况。 |

采集运行中，本次所选上游失败后，其依赖步骤记 `blocked` 并给出原因；没有这种依赖的其余步骤可以继续。不能因某个步骤失败就丢失后续步骤行，也不能把未选步骤纳入整体结果。

采集的上下游关系使用已有采集依赖图。发布按各 loader 的实际前置条件判断，不把采集依赖图直接套用成发布依赖图，也不因另一发布步骤失败而无条件阻断全部剩余步骤。

请求本身不合法时直接返回明确错误，不建立无效运行。来源、工作区、作业或版本不存在、归属不符、来源停用及平台库不可用，仍按对应错误返回，不能统一伪装为步骤 `blocked`，也不恢复旧的“采集 job 全部步骤成功”准入。

**发布准入失败与运行内失败分开处理：**创建前集中预检发现任一已选步骤的采集 marker、文件、内容或配置不合格，属于整次发布请求的 HTTP `400` 拒绝；响应指出具体步骤和原因，不生成 `publish_run_id`，不写 run_info、run_step 或 manifest 等业务记录，不把失败尝试落成 `blocked` 运行。预检只读，不执行备份、文件生成或下游发布。

集中预检全部通过并创建发布运行后，执行期复查若发现文件被删除、编辑后不合格或其他前置条件变化，尚未实际执行的步骤记 `blocked`，`started_at` 保持为空并记录原因及 `finished_at`；实际执行后出错记 `failed`。其他仍具备条件的步骤可以继续，最终按表中规则汇总，仍可能 `partial_success`。采集仍保持先建运行、前置条件不满足或上游失败时记 `blocked` 的语义。

运行内的 `message` 写具体原因，不能只有一个“失败”字样。平台故障导致无法登记状态时应返回或记录实际故障，不能宣称已经完成状态写入。

## 7. 采集流程实施

### 7.1 一次采集执行

1. 读取已固定版本及本次步骤、参数，解析工作区目录和源连接配置。
2. 复用 `normalize_collection_steps()`，按选中步骤之间的依赖排序。请求顺序已满足依赖时保持；独立可执行步骤按请求先后选择。
3. 执行每步前检查本次上游结果；未选上游则检查工作区现有产物，不自动补跑。把旧的“同 job 成功行”检查适配为当前工作区产物条件。
4. 在实际读取输入时填写 `input_manifest`；需要保留旧内容的步骤先读入，写入前执行一次备份，然后调用原生成器。
5. 产物通过现有检查后填写 `output_manifest`、写成功 marker 并登记成功结果；实际执行失败写失败 marker 和原因。失败时不把半成品记录为成功输出。
6. 汇总整次结果，保留每步的开始、结束时间。重跑是新运行，不重置旧运行。

规则示例：`["md", "ddl", "json"]` 应执行为 `["ddl", "json", "md"]`；只选 `rel` 时不自动执行 JSON、Domain，只读取当前工作区符合条件的现有上游文件。一个工作区的另一个采集作业可以提供这些文件，其他工作区不能提供。

### 7.2 Domain 描述的具体处理

- 创建作业时，若尚无有效 Domain 文件，可以用数据源描述初始化默认输入；用户明确保存的默认输入进入 `collection_job_revision.step_config.domain.description`。
- 首次生成且不存在 YAML 时，依次采用本次明确的临时输入、版本中保存的默认输入；两者均未提供时使用数据源描述。LLM 生成 `database.description`、`domains` 和表归属。不能把明确输入与“没有传入”混为一谈。
- 按上述优先级确定的输入若为 `null`、空字符串或纯空白（包括兜底的数据源描述也为空），允许无补充描述首次生成，不因描述为空拒绝。沿用现有生成器的无描述分支，以 `user_description=None` 调用 LLM，依据数据库名称和有效 MD 表结构摘要生成 `database.description`、`domains` 及表归属；MD 输入、LLM 配置和产物检查仍须通过。
- 已有有效 YAML 时，先读取其 `database.description`；重跑只更新 `domains` 和表归属，保留该描述。默认或临时首次生成输入不能悄悄覆盖 YAML。
- 页面明确区分“首次生成输入”和“编辑当前描述”。编辑已存在描述时调用文件保存接口，按 §5.2 完成文件级备份后更新 YAML，不调用 LLM，也不更新作业版本或数据源描述，不触碰采集 marker；备份失败则本次保存失败。
- Domain 重跑前读取需保留的描述，再执行整目录备份。其他人工编辑过的领域分类不承诺自动合并，主动重跑会重新生成；本期不开发通用合并机制。
- 已有 YAML 损坏时明确返回文件无效，不能当作从未生成过而静默覆盖；修复后重试。不增加自动检测新表、提醒或自动重跑。

6.1 的版本参数用于保存首次生成的默认提示；YAML 用于保存工作区当前描述。这两者含义不同，不恢复旧 `job_info.db_desc`，也不保存整份 YAML 到版本参数。

## 8. 发布流程实施

### 8.1 发布步骤、输入与执行顺序

后端采用当前前端已经使用的固定顺序：`db → ddl → json → domain → table_schema → dim_value → rel → sql`。只排序本次所选步骤，不自动追加未选步骤；保存或执行发布作业都不需要绑定唯一采集作业。

| 发布步骤 | 主要采集输入目录 | 继续保留的检查与处理 |
| --- | --- | --- |
| `db` | `db/` | 主文件、数据库画像结构及来源匹配等现有检查。 |
| `ddl` | `ddl/` | 必要 SQL 文件、对象识别及现有有效性检查。 |
| `json` | `json/` | JSON 可解析、画像字段和对象身份等现有检查。 |
| `domain` | `domain/` | `db_domains.yaml` 结构、领域及表配置检查。 |
| `table_schema` | `json/`、`md/` | 两类文件及对象匹配检查，按实际读取文件生成 manifest。 |
| `dim_value` | `dim/` | `dim_tables.yaml`、表配置、有效 `embedding_col` 及现有加载前检查。 |
| `rel` | `json/`、`domain/`、`rel/` | 关系配置、端点等内容检查；生成 `cql/` 后加载 Neo4j。 |
| `sql` | `sql/` | SQL 样例文件和现有内容、加载配置检查。 |

表中为主要输入，开发时逐个核对 loader 实际读取范围，有其他实际文件也应纳入清单。`cql/` 是发布辅助产物，不要求预先具备采集 marker。

### 8.2 准入和执行

1. 保存发布作业仅验证定义，不以当前文件是否齐全作为保存条件。
2. 发布页预检只检查当前工作区；按输入目录读取唯一采集 marker，展示状态、来源 UUID、采集时间和不可发布原因。多个目录分别展示，不能归并成一个虚构的统一采集时间。`GET /api/workspaces/{workspace_id}/publish-check` 不提供 `steps` 参数，也不按某个发布作业过滤，固定按 §8.1 顺序返回全部 8 个发布步骤。前端可选列表按当前发布作业引用版本的 `steps` 过滤，执行前确认区域再按本次所选步骤过滤，展示对应产物及校验结果。预检接口在请求和全局读取正常时返回 HTTP `200` 及逐步骤可用性，某一步骤不可发布不导致整份预检响应返回 `400`；未选步骤不就绪也不阻断本次发布，正式请求仅对本次所选步骤进行集中预检。
3. 正式发布请求在创建运行之前，按新口径集中预检全部所选步骤：各依赖目录必须具备唯一成功采集 marker，并通过必要文件、内容和配置检查。任一步骤不合格即整单返回 `400`，指出具体步骤及原因，不生成运行 UUID，不写运行、步骤或 manifest 等业务记录，也不执行备份或发布。全部合格才创建运行及全部所选步骤行；不读取备份，不要求整工作区历史全部成功，不恢复旧 `409` 作业级准入。
4. 运行创建后，各步骤实际启动前仍按现有锁及冲突保护复查。此时才暴露的前置条件问题（如文件在集中预检后被删除或编辑后不合格）记 `blocked`，表示该步骤未实际执行；实际执行后出错记 `failed`。其他仍具备条件的步骤可以继续，按实际结果汇总为 `success/partial_success/failed`；不能悄悄删除已选步骤后宣称全成功。
5. 实际读取后填 `input_manifest`，实际尝试写目标时填 `target_manifest`；结果由步骤状态和消息表达。一次发布可以读取多个采集运行的产物。
6. 发布只写外部目标时不备份文件；Rel 发布需要重新生成 CQL 等本地文件时，先对相应目录执行整目录备份。发布前人工编辑配置则按 §5.2 独立执行文件级备份，不因在发布页保存而套用整目录规则。任何发布步骤均不写发布 marker。

移除 `metaweave/backend/profile_loading/rel_loader.py` 中 `_assert_fresh_ordering()` 所表达的 Rel 必须晚于 JSON、Domain 的判定，以及其他执行路径中的同义要求。保留原登记信息、内容校验及发布中重跑或编辑冲突保护；旧 `expected_run_marker` 如果原本指 `job_info.updated_at`，需要适配为当前采集来源和现有文件冲突检查，不能继续读取旧表，也不能借适配重新引入新鲜度限制。

### 8.3 成功记录与下游写入

PostgreSQL 内容写入、对应行的 `publish_run_id` 和该发布步骤成功状态在同一数据库事务提交；失败回滚时，不更新原内容行的成功来源。不能用整次运行是否全成功代替逐步骤提交结果。

Milvus、Neo4j 保留实际目标写入及失败说明。接受中途失败可能产生新旧混合的局限；记录 `failed` 并提示重新发布，不新增撤销 current 的模型。

工作区最后成功发布直接查询 `public.vw_workspace_latest_successful_publish`。结果来源取该成功步骤的 `input_manifest`，不能换成工作区现在最新一次采集运行。后续失败不隐藏上次成功，整体 `partial_success` 中的成功步骤仍能进入视图。

该视图展示各工作区自己的成功历史。下游当前内容按 `source_id` 保存一套，同源另一工作区后续发布可能已覆盖旧内容；资产页以内容行的 `publish_run_id` 为实际来源，不将工作区历史误作仍然独立存在的下游副本。按源替换继续保留既有源行锁和提交前复核，不能因为两个发布作业属于不同工作区就视为不同下游写入范围。

### 8.4 manifest 落实

统一通过服务函数构造和校验，格式严格使用 6.1 §11：输入为实际相对路径和采集来源 UUID；输出为成功生成的文件路径数组；目标为实际尝试写入的 PostgreSQL 表、Milvus 集合或 Neo4j 数据库。

不记录点号文件，不记录计划但没有实际消费的输入，不以非空清单冒充成功。无对应内容可为 SQL `NULL`；不能写顶层 JSON `null` 或 `files: null`。辅助 CQL 的来源可以为 JSON `null`，必要采集输入不能以此绕过 marker。

在写入前解析并规范 UUID，非法结构明确报错。6.1 的视图不增加正则兜底或静默过滤非法 ID。

## 9. WebUI 改造

### 9.1 页面与调用关系

页面编号、路由、用户路径、视觉规范及未覆盖页面的实现约定见 [6.3 WebUI 设计稿索引与实现约定](6.3_WebUI设计稿索引与实现约定.md)。

1. 数据源下先展示工作区列表，允许新建、进入工作区；页面始终清楚显示当前来源和工作区。
2. 工作区内分别管理采集作业和发布作业。创建页选择名称、步骤和默认参数，点击“保存作业”；不再把保存和执行混为一次动作。
3. 作业详情展示默认版本，提供“按默认配置执行”和“手工选择步骤执行”。手工模式只展示该版本可选步骤；临时参数只有执行入口，没有保存回作业入口。
4. 编辑作业配置走新版本保存；旧版本和运行详情可查看当时配置。作业信息编辑与配置版本编辑分清楚。
5. 一次执行只提交一组步骤，创建成功后展示返回的运行 UUID，并通过详情查询更新进度。发布创建前集中预检不通过时展示 `400` 响应中的步骤及原因，不新增运行条目，也不伪造 `blocked` 运行结果；用户修复后重新提交。运行内的独立步骤失败、阻断及部分成功分别显示。
6. 发布页保留 Domain、Rel、Dim 三个编辑入口；每个发布步骤显示各依赖目录的采集时间。编辑保存成功后刷新预检，不产生发布作业新版本；文件备份或写回失败时明确展示保存错误，保留草稿，不显示保存成功或新的采集完成时间。备份失败可重试；备份成功但写回失败时，保留备份供人工核对恢复，并展示已知的部分写入情况，不自动回滚或重试保存。
7. 首页、作业列表、运行历史和资产来源链接更新为新身份，取消“旧采集 job 汇总全部成功才允许进入发布”的页面限制。
8. 工作区、采集作业、发布作业、版本和运行历史均不显示删除、批量删除或清空目录入口；废弃对象继续显示，不为隐藏废弃对象新增软删除或回收站功能。

主要涉及 `CollectionHomeView.vue`、`CollectionJobsView.vue`、`CreateCollectionJobView.vue`、`PublishHomeView.vue`、`PublishJobsView.vue`、`SelectPublishJobView.vue`、`PublishView.vue`、`SourceWorkBrowser.vue` 及 API 类型、路由。页面按工作区、作业、运行三个层次组织，操作入口、接口和业务流程按本文约定执行；具体布局和组件拆分保留实现自由。

### 9.2 前后端职责

前端继续使用排序和可用性提示改善交互；最终白名单、步骤子集、依赖排序、工作区归属、参数有效性及发布准入由后端执行。页面不能因为文件时间先后显示自动过期告警或禁用发布。

`partial_success` 要进入前端类型和状态显示。未选步骤不展示为“本次失败”，步骤 `blocked` 不混为已经执行失败。点击执行后临时选择可以退出页面状态，但已经创建的运行记录必须保留实际步骤和参数；发布准入被拒绝时不创建记录。

## 10. NL2SQL、资产及 CLI 联动

### 10.1 短 ID 不能只改 MetaWeave 路由

NL2SQL 当前多处把来源解析为 UUID，应一起核对：

- `nl2sql/src/api/v2/dto.py`、`router.py`、`webstore.py`：请求、查询参数和会话记录校验。
- `nl2sql/src/modules/db_deepagent/source_registry.py`、`runner.py`、`cli.py`：登记查找、请求与服务来源一致性、CLI 入口。
- `services/__init__.py`、`services/milvus_retrieval.py`、`services/join_graph.py`：服务构造及按源图、向量检索。

改短 ID 后仍必须验证来源存在、绑定一致及查询范围，不能退化为来源缺失时查询全图或全部向量。NL2SQL 会话 ID、运行 ID 等其他 UUID 不随之改成短 ID。

### 10.2 发布就绪与资产查询

`nl2sql/src/api/v2/backend.py` 当前直接查询 `public.publish_info` 的 `is_current_publish` 等字段；`readiness.py` 及相关缓存指纹也依赖这些记录。必须切换到新发布记录和成功查询口径，不能只改表名而继续索取已删除字段。

NL2SQL 继续只按 `source_id` 绑定来源，不新增工作区会话绑定。源级最后成功发布按 `source_id + step_name`，从同源各工作区的成功发布步骤中选最近一条：可将 6.1 §12 的工作区视图关联 `workspace_info` 得到来源，再按源和步骤，以 `published_at DESC NULLS LAST, publish_run_id DESC` 选择一条，不新增当前态表或第二个视图。不同步骤可以来自不同工作区，但同一步骤不能任意拼接多个工作区的历史结果；后续失败不替代之前成功，外部目标中途失败的局限仍按 §8.3 接受。

就绪查询继续保留实际下游内容及必要配置检查，不能只凭历史成功记录保证目标完整；发布就绪的来源关联、缓存指纹及失效依据同步改为上述源级结果，同源任一工作区成功更新相关步骤后都应反映在查询中。

`metaweave/backend/assets/` 的画像、对象、DDL 等查询应使用确认后的内容表结构，展示内容行实际 `publish_run_id`，不能反向用最新成功视图覆盖旧行来源。

### 10.3 下游和 CLI

- Neo4j 检查脚本头来源解析、`entity_id = source_id:id` 构造及按源替换条件；不能继续用固定 36 字符 UUID 正则解析新来源，不加入工作区命名空间。
- Milvus 检查 `source_id` 及派生主键的构造、过滤、删除条件和字段长度，集合结构需要变化时按新结构重建；沿用按源身份及替换规则，不为同源不同工作区保留重复副本。
- `metadata_cli.py`、`loader_cli.py`、共享执行层及登记脚本中的受管目录定位改用 `source_id + workspace_id`；`--job_id` 改为 `--workspace_id`，不保留旧参数入口。既有生成器函数名及 CLI 功能开关按 §5.1 保持原名。
- CLI 保留现有单步生成、调试加载能力，不因 Web 作业版本功能而擅自增加命令行跨步骤编排。调试命令不冒充正式发布成功记录；正式 Web 运行需具备本方案要求的记录和 marker。

## 12. 一次性重建和旧数据清理

本节是开发完成后的操作清单，**编写本文件不执行任何清空或重建动作**。

1. 核对目标环境和项目数据范围，停止会继续写入旧模型的服务或任务。
2. 先将本次 MetaWeave 范围内的八张旧表统一改名留存，名单见 6.1 §10.0；命名为 `<原表名>_old_<yyyyMMdd_HHmmss>`，同批次使用同一时间戳，例如 `db_source_info_old_20261021_153000`。改名前核对目标名称及标识符长度，不覆盖已有留存对象。同步改名会与新 DDL 冲突的旧主键/唯一约束支撑索引、普通索引、拥有序列和视图，保留旧数据及旧外键关联，不直接删除或清空旧表。
3. 上述统一改名全部完成后，再按依赖创建新序列、十五张目标表、约束、索引和视图；不能逐表交替改名和创建。新结构为空，不复制旧行、不转换旧 UUID、不将旧外键改指新表。全新空库无旧对象时直接创建。应用只读写新表，不读取改名后的留存表。
4. 清理本项目在 Neo4j 的旧子图、Milvus 的旧发布记录；需要调整集合结构时重建受管集合。仅靠新短 ID 的“按源替换”无法清除旧 UUID 数据。
5. 清理本项目 `output/` 旧 UUID 来源与旧 job 目录，不将其复制到新工作区。
6. 作废并清理 NL2SQL 旧会话、归档、checkpoint、Store、`result_snapshots` 及对应本地结果文件。当前持久化 schema 常用 `db_deepagent`，具体连接、schema 和结果根目录以实际配置为准，不能只清 `output/`。
7. NL2SQL 表的清理依据实际存储结构进行；不是每张表都有独立 UUID 来源列。若只是清空记录，保留框架初始化和版本元数据，不扩大为重做会话模型，也不纳入上述 MetaWeave 旧表统一改名范围。
8. 启动新版本，重新登记来源、创建工作区和作业、采集、编辑、发布，再以新会话执行查询。

核验不再存在被新服务引用的旧表、旧来源记录或旧目录。清理不触及源业务库，不清空其他项目或共享服务中不属于本项目的数据；不把清理脚本挂到启动或每次发布流程。

改名留存的 PostgreSQL 旧表不属于本次删除或清空对象，其旧数据不参与新业务；未来清理由人工另行安排。本期不新增留存表的自动清理能力。

以上是断代改造的一次性旧数据清理，不是日常删除能力。新模型运行后接受废弃工作区、作业记录和输出目录残留；不新增日常自动回收或清理入口，需要释放空间时由人工确认无运行读写后清理相应废弃目录。仅清理目录不联动删除数据库记录、作业版本、运行历史或已发布下游数据，也不补造采集 marker；仍引用缺失产物的发布请求按既定准入规则拒绝。

### 13.3 开发完成判据

对应存量表 DDL 和下游隔离决定已补齐；新模型、接口、页面、CLI 及 NL2SQL 联动一致；相关测试与浏览器验收通过；重建与清理已在测试环境验证。不能仅因九张新表已创建，或采集按钮能执行，就认定整个改造完成。

发布验收必须区分创建前和创建后：集中预检任一步骤不合格时，整单 `400` 且不产生业务记录；全部通过才创建运行，执行期复查不合格记 `blocked`、实际执行失败记 `failed`，保留可能的部分成功。旧 `409` 作业级准入不得恢复，采集运行语义不变。

备份验收必须区分生成与编辑：生成时整目录备份失败告警并继续生成；人工编辑先复制待覆盖文件的旧版，复制失败则保存失败且不改动现有内容。备份成功后的编辑写回失败同样报错，保留完整备份供人工核对恢复，不自动回滚。三个编辑入口在成功或失败时均不得生成、修改、移动或删除采集 marker。

不把工作区或作业删除能力列为交付前置，也不得为了处理废弃对象而临时补入删除入口、级联删除或自动清理功能；按本期边界保留对象及历史，接受目录人工清理。

实际使用环境的一次性旧表改名、新建目标结构和其余旧数据清理，应使用核对后的连接配置和项目数据范围，记录执行结果，并完成新模型的全链路核验；不直接删除改名留存的旧表。

# 4.1 Web 对话历史与 Store、Checkpoint、结果目录的查找关系

记录日期：2026-10-18。状态：**按当前代码与库表核对后的查找说明**。

本文说明 Vue 左侧导航下方的对话历史，如何对应到 `lg_persist` 库里的 Store、checkpoint，以及磁盘上的结果目录。关联文档：[2_NL2SQL_Vue接入设计.md](2_NL2SQL_Vue接入设计.md)、[3_SQL查询结果文件存储问题与改造思路.md](3_SQL查询结果文件存储问题与改造思路.md)、[4.2_WebUI从打开到提问的逻辑线路.md](4.2_WebUI从打开到提问的逻辑线路.md)（本文的动态调用链视角）。

## 1. 四样东西各存什么

页面地址 `/query/s_……` 里的 `session_id` 是同一段对话的编号。它不是 LangGraph checkpoint 的 `thread_id`，也不是结果目录名。

| 位置 | 存什么 | 和 session_id 怎么对上 |
| --- | --- | --- |
| 左侧对话列表 | 标题、数据源、最后活动时间 | Store 行的 `key` 列就是 `session_id` |
| 重新打开后的问答 | 每轮的问题和答案；新写入的轮次还有 SQL 与 `result_ref` | Store 行的 `prefix` 末尾是 `session_id` |
| checkpoint | Agent 续聊用的线程状态 | 表列 `thread_id` 的值是 `dbda:<session_id>:<序号>` |
| 结果目录 | 一次 SQL 的 `meta.json` 与 `rows.jsonl` | 目录名是 `result_ref`（`res_` 开头），`meta.json` 里写着 `session_id` |
| 会话运行目录 | 每轮运行的 JSON 与审计日志 | 文件夹名就是 `session_id` |

左侧列表不扫描结果目录，也不读 checkpoint。页面初始化调用 `GET /api/v2/sessions`，只读下面第 3 节的 Web 会话登记。

当前没有用户表。登记值里的 `owner` 固定为 `guest`，`origin` 固定为 `web`。所有打开页面的人看到同一份列表。

Web 创建的 `session_id` 形如 `s_` 加 UUID4 的 32 位十六进制，没有横线，例如 `s_9bd1b61e58b240b9921d0c4779200ca4`。脚本或测试会话可以是别的合法字符串，例如 `s-f01-live`。两种都能按同一规则查找。

## 2. 平台库与 schema：配置值，启动时按代码校验

当前 db_deepagent 路径连接的数据库是 `lg_persist`，Store 与 checkpoint 的表在 schema `db_deepagent` 下。库名和 schema 都写在配置里，代码在启动时校验，通过后把 `search_path` 设成该 schema。

配置文件：`nl2sql/src/modules/db_deepagent/config/db_deepagent.yaml`

```yaml
platform_db:
  host: ${LANGGRAPH_DB_HOST:localhost}
  port: ${LANGGRAPH_DB_PORT:5432}
  database: ${LANGGRAPH_DB_NAME}
  user: ${LANGGRAPH_DB_USER:postgres}
  password: ${LANGGRAPH_DB_PASSWORD:}
  expected_database: lg_persist
  schema: db_deepagent
```

| 配置项 | 来源 | 当前值 |
| --- | --- | --- |
| 实际连接的库名 `database` | 环境变量 `LANGGRAPH_DB_NAME`（`nl2sql/.env`） | `lg_persist` |
| 期望库名 `expected_database` | 上面这份 yaml 的字面量 | `lg_persist` |
| schema | 上面这份 yaml 的 `schema` | `db_deepagent` |

连接建立时，`nl2sql/src/modules/db_deepagent/persistence/platform_pool.py` 读取 `schema`，在连接参数里设置 `search_path`。因此 `store`、`checkpoints` 等表落在 `db_deepagent` 下，查询时写 `db_deepagent.store`。

代码里有一条写死的校验（`config.py` 的 `_check_platform_target`）：`database` 与 `expected_database` 必须都等于字符串 `lg_persist`，否则启动失败。schema 的具体名字不写死，从配置读取；代码只拒绝 `public` 和非法标识符。

`nl2sql/src/configs/config.yaml` 里旧的 `langgraph_persistence.database.schema` 仍是 `public`，库名同样来自 `LANGGRAPH_DB_NAME`。`public.store` 中 `prefix` 以 `chat_history.` 开头的行来自这条旧配置，不是 Vue 左侧列表。左侧列表用的是 `db_deepagent.store`。

Store 行 `prefix` 里出现的 `db_deepagent`（例如 `db_deepagent.web_sessions.guest`）是代码里的命名空间字符串，与 PostgreSQL schema 同名，但是两回事。改 yaml 的 `schema` 不会自动改这些 `prefix`。

## 3. Store 表：没有 session_id 列，也没有 thread_id 列

Vue 使用的表是 **`lg_persist.db_deepagent.store`**。`public.store` 里 `prefix` 以 `chat_history.` 开头的行是旧对话数据，不是左侧列表。

`db_deepagent.store` 的列是：

| 列 | 含义 |
| --- | --- |
| `prefix` | 命名空间。代码里的元组用点拼成这一列 |
| `key` | 该命名空间下的记录键 |
| `value` | JSON。标题、`thread_id`、`result_ref` 都在这里面，不是表的列 |
| `created_at` / `updated_at` | 行的写入时间 |
| `expires_at` / `ttl_minutes` | 过期控制，Web 会话登记通常为空 |

命名空间与 `prefix` 的对应：

| 代码中的命名空间 | `prefix` 列 | `key` 列 |
| --- | --- | --- |
| `("db_deepagent", "web_sessions", "guest")` | `db_deepagent.web_sessions.guest` | `session_id` |
| `("db_deepagent", "web_turns", session_id)` | `db_deepagent.web_turns.<session_id>` | `request_id` |
| `("db_deepagent", "sessions")` | `db_deepagent.sessions` | `session_id` |
| `("db_deepagent", "qa", session_id)` | `db_deepagent.qa.<session_id>` | `request_id` |

### 3.1 左侧列表：Web 会话登记

```sql
SELECT key, value->>'title', value->>'source_id', value->>'last_active_at'
FROM db_deepagent.store
WHERE prefix = 'db_deepagent.web_sessions.guest'
ORDER BY value->>'last_active_at' DESC;
```

- `key`：页面上的 `session_id`。
- `value->>'title'`：左侧显示的对话名。新建时是「新对话」；第一次提问成功后，取问题去掉首尾空白后的前 40 个字符，之后不自动改名。
- 这条登记里没有结果目录，也没有 `result_ref`。

### 3.2 重新打开会话时的问答：web_turns

```sql
SELECT key,
       value->>'question',
       value->>'answer',
       value->'display'->'evidence' AS evidence
FROM db_deepagent.store
WHERE prefix = 'db_deepagent.web_turns.s_9bd1b61e58b240b9921d0c4779200ca4';
```

把最后一段换成实际的 `session_id`。`key` 是这一轮的 `request_id`。

2026-10-18 之后新保存的轮次，`value.display.evidence[].result_ref` 指向结果目录。更早的轮次只有 `question` 和 `answer`，JSON 里没有 `result_ref`，要从第 3.3 节或 checkpoint 里找。

### 3.3 问答归档：value 里的 thread_id 与 result_ref

成功执行并归档的一轮，存在 `prefix = db_deepagent.qa.<session_id>`。下面只节选查找用的字段。`write_qa` 写入的顶层键还有 `question`、`answer`、`stats`；`evidence` 每一项除 `result_ref` 与 `sql` 外，还有 `evidence_id`、`kind`、`tool_call_id`、`source`、`row_count` 等字段。会话号写在 `thread_id` 字符串中间，不是单独的 JSON 键。例子中的值与该次结果目录里的 `meta.json` 一致。

```json
{
  "thread_id": "dbda:s-f01-live:1",
  "run_id": "run_2404521ed53e485d8d5025a705e10318",
  "status": "completed",
  "evidence": [
    {
      "result_ref": "res_e3b4a010f5a149119fb03bbbb061e545",
      "sql": "SELECT COUNT(o.order_id) AS order_count FROM public.orders o WHERE ..."
    }
  ]
}
```

用这条 `value` 直接取关联字段：

```sql
SELECT prefix,
       key,
       value->>'thread_id' AS thread_id,
       value->'evidence'->0->>'result_ref' AS result_ref
FROM db_deepagent.store
WHERE value->>'thread_id' = 'dbda:s-f01-live:1';
```

| 要从这条 value 得到的东西 | JSON 路径 | 这条例子的值 |
| --- | --- | --- |
| 会话号 | `thread_id` 中 `dbda:` 与最后一个 `:` 之间 | `s-f01-live` |
| checkpoint 线程号 | `value->>'thread_id'` 整串 | `dbda:s-f01-live:1` |
| 结果目录名 | `value->'evidence'->0->>'result_ref'` | `res_e3b4a010f5a149119fb03bbbb061e545` |
| 本行对应的一轮请求 | 表的 `key` 列 | `request_id` |

`prefix` 若是 `db_deepagent.qa.s-f01-live`，最后一个点后面的那段与 `thread_id` 中间的会话号相同。

当前续聊线程另有一行：`prefix = 'db_deepagent.sessions'` 且 `key = 会话号`，`value->>'current_thread_id'` 等于 checkpoint 要查的线程号。

## 4. Checkpoint 怎么对上

checkpoint 在另一张表。`db_deepagent.checkpoints` **有**列 `thread_id`。它的值等于 Store 归档 JSON 里的 `value->>'thread_id'`。

线程号格式：

```text
dbda:<session_id>:<序号>
```

序号从 1 开始。同一段对话续聊时通常仍是 `:1`；线程轮换后变为 `:2`、`:3`，`session_id` 不变。

```sql
SELECT thread_id, checkpoint_id
FROM db_deepagent.checkpoints
WHERE thread_id = 'dbda:s-f01-live:1';
```

已知页面上的 `session_id`、还不知道序号时：

```sql
SELECT DISTINCT thread_id
FROM db_deepagent.checkpoints
WHERE thread_id LIKE 'dbda:s\_9bd1b61e58b240b9921d0c4779200ca4:%' ESCAPE '\';
```

`_` 在 `LIKE` 里是单字符通配符。Web 会话号固定是 `s_` 加 32 位十六进制，中间这个下划线必须写成 `\_`，并加上 `ESCAPE '\'`。不转义时，它会匹配同长度、仅第 2 个字符不同的线程号。`s-f01-live` 没有下划线，`LIKE 'dbda:s-f01-live:%'` 可以直接写。已知完整线程号时，用上面的等值条件，不需要 `LIKE`。

checkpoint 状态里的执行账本同样带 `result_ref`（查询在 `db_executions`，分析输出在 `db_analyses` 的 `output_result_ref`）。该状态在 `checkpoint` / `checkpoint_blobs` 中序列化保存，不是 `checkpoints` 表上的独立列。要看编号，优先用第 3.3 节 Store 的 `value`，不必先拆 blob。

## 5. 两个磁盘目录

都在 workspace 根下面，根路径见第 6 节。

### 5.1 结果目录：一次 SQL 的表格

```text
<workspace.root>/results/<result_ref>/
├── meta.json
└── rows.jsonl
```

`result_ref` 来自 Store 的 `value->'evidence'->0->>'result_ref'`，或来自 `web_turns` 的 `value.display.evidence[].result_ref`。`meta.json` 内写有同一个 `session_id`、`thread_id`、`request_id` 和 `result_ref`。目录名等于 `result_ref`，不等于 `session_id`。

当前机器上的例子：

```text
/opt/projects/insightweave/nl2sql/var/db_deepagent/results/res_e3b4a010f5a149119fb03bbbb061e545/
```

不知道 `result_ref`、只有会话号时，可以用会话号反查说明文件：

```bash
grep -l '"session_id": "s-f01-live"' \
  /opt/projects/insightweave/nl2sql/var/db_deepagent/results/*/meta.json
```

### 5.2 会话目录：每轮运行记录

```text
<workspace.root>/sessions/<session_id>/
├── runs/<request_id>.json
└── audit.jsonl
```

`request_id` 等于 Store 里 `db_deepagent.qa.<session_id>` 或 `db_deepagent.web_turns.<session_id>` 那一行的 `key`。`runs/<request_id>.json` 是该轮运行的落盘副本，其中同样有 `evidence[].result_ref`。页面列表不读这个目录。

## 6. results 路径在配置里的定义

配置文件：`nl2sql/src/modules/db_deepagent/config/db_deepagent.yaml`

```yaml
workspace:
  root: ${DB_DEEPAGENT_WORKSPACE:var/db_deepagent}
```

含义：环境变量 `DB_DEEPAGENT_WORKSPACE` 有值就用它，否则用 `var/db_deepagent`。这个值是相对**进程启动目录**的路径，不是相对该 yaml 文件的路径。

装配结果存储时传入这份根路径，再固定追加 `results`：

- `nl2sql/src/modules/db_deepagent/services/__init__.py`：`ResultStore(Path(cfg.workspace.root))`
- `nl2sql/src/modules/db_deepagent/services/result_store.py`：`self._root = Path(workspace) / "results"`

因此一条结果的完整目录是：

```text
<workspace.root>/results/<result_ref>/
```

2026-10-18 核对时，`DB_DEEPAGENT_WORKSPACE` 未设置，服务从 `nl2sql` 目录启动，实际根目录为：

```text
/opt/projects/insightweave/nl2sql/var/db_deepagent/results/
```

## 7. 从左侧一条对话查到结果文件

设页面会话号为 `s_9bd1b61e58b240b9921d0c4779200ca4`。

1. 确认标题行：`prefix = 'db_deepagent.web_sessions.guest'` 且 `key` 等于该会话号。
2. 查问答：`prefix = 'db_deepagent.web_turns.' || 会话号`。新轮次读 `value.display.evidence`。
3. 旧轮次没有 `display` 时，查 `prefix = 'db_deepagent.qa.' || 会话号`，读 `value->>'thread_id'` 与 `value->'evidence'->0->>'result_ref'`。
4. 用第 3 步的整串 `thread_id` 查 `db_deepagent.checkpoints.thread_id`。
5. 用 `result_ref` 打开 `<workspace.root>/results/<result_ref>/`。
6. 用会话号打开 `<workspace.root>/sessions/<session_id>/runs/`，文件名是第 2 或第 3 步那一行的 `key` 加 `.json`。

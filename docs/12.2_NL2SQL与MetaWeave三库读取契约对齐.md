# 12.2 NL2SQL 与 MetaWeave 三库读取契约对齐

## 1. 范围与结论

本文件以 MetaWeave 当前的 `db/rebuild_platform_schema.sql`、ORM 模型和知识发布写入代码为基准，主要对照 NL2SQL API v2 与 `modules/db_deepagent` 的 PostgreSQL 平台库读取、Milvus 检索及 Neo4j 图查询代码。检查为源码静态审计；**未查询在线三库的实际 schema、数据或部署配置**。因此“代码对齐”不等于实库验收通过。

结论：NL2SQL 存在三个 `source_id` 仍按 UUID 解析的阻断点；PG 发布就绪检查还留有一处旧 `job_id` 判断，实际已失效。Milvus/Neo4j 的 `publish_id` 与 PG 的 `publish_run_id` 目前值相同、字段名不同，不构成当前 503 的原因；先完成 [12.1 MetaWeave 发布运行标识统一改造](12.1_MetaWeave发布运行标识统一改造.md)，再按本文调整 NL2SQL 读取字段并修复其他契约错位。`workspace_id` 未发现 UUID 解析阻断。12.1 是本文的**开发前置任务**，两侧代码及存量数据的切换必须协调，不能单独上线新字段的写侧。

现行身份依据：[doc 5.1 §1](5.1_数据源工作区采集运行与发布运行模型.md) 将 `source_id`、`workspace_id` 和模板 ID 改为短 ID，运行 ID 保持 UUID；[doc 6.1](6.1_建表语句汇总.md) 与当前模型具体采用 `db_src_N`、`ws_N`、`coll_job_N`、`pub_job_N` 和两类运行 UUID。doc 4 的 `source_id` UUID 要求属于旧契约。

**旧链边界：**旧 `scripts/nl2sql_subgraph_cli.py:154-159` 调用的链路仍由 `src/tools/schema_retrieval/retriever.py:29-35` 获取固定客户端；`src/services/vector_adapter/milvus_adapter.py:137-148,199-210,260-266,307-313` 的检索没有 `source_id` 过滤，`src/services/db/neo4j_client.py:75-87,121-133` 按可跨源重复的 Table.id 寻路。在共享多源知识库中运行该旧脚本有串源风险。现行 [doc 2 D0](2_NL2SQL_Vue接入设计.md) 确定 Vue/Web 仅用 `db_deepagent`，旧父图仅作独立脚本对比；此风险不是 API v2 readiness 503 的成因，也不纳入本次三个 UUID 阻断点的修复。旧链若继续在共享多源环境使用，应另行决定源绑定改造或限制使用范围。

### 1.1 与 12.1 的交接

12.1 负责 MetaWeave 的 `rel/table_schema/dim_value/sql` 写侧字段改名与下游数据迁移方案。本文负责 NL2SQL 消费侧：`src/api/v2/backend.py:250-284,307-315,370-377` 要从 Milvus/Neo4j 读取 `publish_run_id`，`readiness.py:121-135,660-685,703-767` 的内部集合与检查文案应同步改名，`src/services/db/migrations/milvus.sql:30-86` 的结构说明及对应测试须更新。**字段名迁移不改变值**：仍按每一步的 PG 最近成功 `publish_run_id` 核对。现行读取旧字段是正确的旧接口；在 12.1 与本文的实现、存量数据处理同时就绪前，不单独切换任一侧。

### 1.2 发布版本核对的用途

`GET /api/v2/sources/{source_id}/readiness` 和创建会话都会调用完整就绪检查（`nl2sql/src/api/v2/router.py:285-310`、`src/api/v2/runs.py:215-230`）。检查先按源读取 PG 视图中每个步骤的最近成功 `publish_run_id`（`src/api/v2/backend.py:194-214`），再读取 Milvus 三类集合和 Neo4j 节点/边的实际发布版本（`backend.py:250-284,307-377`）。必需知识分别核对 `table_schema` 集合与 PG `table_schema` 步骤、Neo4j 图与 PG `rel` 步骤；两个步骤的运行 ID **不要求相等**（`readiness.py:660-686`）。可选 `dim_value/sql` 有数据时分别核对各自步骤；空集合只给警告（`readiness.py:703-776`）。目的在于拒绝残留旧批次、混批、缺少正式发布记录的知识，而不是要求三库共用一个发布运行 ID。

读取失败会得到 `knowledge_backend/dependency_unavailable`（503）；读到数据但版本不符会得到 `knowledge_inconsistent`，`ready=false`。后者在兼容且读完检查的 readiness GET 中作为 200 的检查结果返回；创建会话或执行查询会被拒绝，映射为 409 `source_not_ready`（`router.py:285-310`、`runs.py:115-136,217-219,601-604`）。会话保存各步骤的 `(workspace_id,publish_run_id)` 快照；新发布使快照变化时，旧会话查询返回 409 `knowledge_changed`（`readiness.py:829-847`、`runs.py:586-599`）。字段改名后这些行为应保持。

## 2. PostgreSQL：MetaWeave 平台库

### PG-1：发布就绪仍比较已不存在的 `job_id`（需修复）

**代码证据：**NL2SQL 从 `public.vw_workspace_latest_successful_publish` 关联 `workspace_info`，按源及步骤取得 `step_name`、`publish_run_id`、`published_at`、`workspace_id`（`nl2sql/src/api/v2/backend.py:31-39,194-214`）。当前视图也确实输出这些字段（`metaweave/db/rebuild_platform_schema.sql:1058-1114`）。但 `nl2sql/src/api/v2/readiness.py:460-479` 仍比较 `ts_current.get("job_id")` 与 `rel_current.get("job_id")`，并报告“同作业”、`counts={"job_id": 1}`。两条新格式记录均无 `job_id`，所以 `str(None) == str(None)`，检查恒通过。

**影响：**错误的就绪判断；不是目前 `knowledge_backend` 503 的直接原因。尤其不能把旧检查机械替换为“两个 `workspace_id` 相同”：现行 [doc 6.2 §10.2](6.2_MetaWeave改造实施方案.md) 允许同源不同步骤来自不同工作区，下游按源只保存一套内容。

**修改建议：**删除旧 `job_id` 比较、通过文案和计数。保留两个必需步骤各有源级最近成功记录、实际下游发布版本分别等于对应 `publish_run_id`、表集合及列归属一致的检查；知识快照继续记录每步 `(workspace_id, publish_run_id)`（`readiness.py:829-847`）。同步清理 `docs/2_NL2SQL_Vue接入设计.md` 全文的旧身份与发布契约，至少覆盖 §5.5、§5.5.1、§5.5.2、§9.1、§9.2、§10：来源改为短 ID，快照改为 `(workspace_id,publish_run_id)`，验收允许同源不同工作区分步骤发布，但实际下游版本须分别匹配；移除旧 `publish_info/is_current_publish` 及“同 job”限制。

### PG-2：登记与发布查询已对齐（无需按旧表改造）

`db_source_info.source_id` 为带 `db_src_N` CHECK 的 `text` 主键，`workspace_info.workspace_id` 为 `ws_N` 文本主键，`publish_run_id` 仍为 UUID（`metaweave/db/rebuild_platform_schema.sql:26-48,152-167,501-503`）。NL2SQL 登记查询读取的字段均存在（`nl2sql/src/modules/db_deepagent/source_registry.py:24-28,96-104`）；发布查询已使用新视图，而非旧 `publish_info`（`nl2sql/src/api/v2/backend.py:31-39`）。未发现 NL2SQL 将 `workspace_id` 解析为 UUID。

**验证建议：**部署环境以只读 SQL 核对视图存在、字段类型及指定源每步骤的返回记录；分别构造同源跨工作区发布与版本变化场景，确认 readiness 和会话快照按源级最新版本变化。该验证不应写入生产数据。

**维护注释建议：**修复上述契约时，顺带更正 `nl2sql/src/api/v2/readiness.py:147` 将发布记录称为旧 `publish_info`、`nl2sql/src/api/v2/webstore.py:330-339` 将会话来源称为 UUID 的注释。后者实际已按短 ID 校验（`webstore.py:68-72`），函数名 `valid_source_uuid` 虽属历史命名，并非运行阻断；本次不要求为此单独重命名。

## 3. Milvus

### M-1：检索适配器把短 `source_id` 解析为 UUID（阻断）

`nl2sql/src/modules/db_deepagent/services/milvus_retrieval.py:36-47,62` 调用 `UUID(source_id)`。对 `db_src_1` 会抛 `ValueError`。readiness 在 `nl2sql/src/api/v2/backend.py:219-239,248` 构造适配器时把异常转为 `ReadinessError`；`nl2sql/src/api/v2/readiness.py:481-495` 折叠为 `knowledge_backend/dependency_unavailable`。通用服务装配也在 `nl2sql/src/modules/db_deepagent/services/__init__.py:71-85,132` 做同类 UUID 校验；仅修复适配器仍无法运行问答。

**修改建议：**两处统一复用 `source_registry.normalize_short_source_id`，保持缺失/非法来源拒绝、服务来源不可变，以及六个检索/回查入口现有的 `source_id == ...` 按源过滤；补充短 ID 的 readiness、会话装配和检索用例。异常日志可记录类型与安全的上下文，避免 `ReadinessError` 细节只在响应层被吞掉。

**配套修订：**`nl2sql/src/modules/db_deepagent/cli.py:1014,1023` 的 `--source-id` 帮助仍提示 UUID，服务装配的 `services/__init__.py:40,72-85` 也保留旧表述；修复校验时同步更正。现有 `src/tests/db_deepagent/unit/test_milvus_retrieval.py:20-21`、`test_join_graph_outcomes.py:24-25` 和 `integration/test_milvus_source_isolation.py:27-28,389-397` 以 UUID 作为合法来源。应将合法夹具改为 `db_src_1/db_src_2`，将 UUID 输入列为非法来源用例，删除“大写 UUID 可规范化”的预期。

### M-2：当前读写字段匹配，发布值可与 PG 核对；36 字符长度不是当前缺陷

MetaWeave 的 `table_schema_embeddings` 使用 `entity_id = source_id:object_id`，当前写 `source_id` 和 `publish_id`（`metaweave/metaweave/core/table_schema/models.py:35-40,68-89`）；`dim_value_embeddings` 和 `sql_example_embeddings` 也写短来源及发布运行 UUID（`metaweave/metaweave/core/loaders/dim_value_loader.py:709-721`、`metaweave/metaweave/core/sql_rag/loader.py:434-445`）。NL2SQL 当前读取 `publish_id`，按平台 `publish_run_id` 核对其值（`nl2sql/src/api/v2/backend.py:250-284`、`readiness.py:660-685,703-767`）。现状可按值比较；按 12.1 更名后须按 §1.1 同步改读侧并迁移已有集合。检索所用集合名与 MetaWeave 配置相同。

此前将 `source_id VARCHAR(36)` 列为增长风险并不准确：当前 PG 序列为 `bigint`（`metaweave/db/rebuild_platform_schema.sql:16-20`），`db_src_` 加最多 19 位正整数共最多 26 个 ASCII 字符，小于 36；`table_schema` 的限长定义见 `metaweave/metaweave/core/table_schema/models.py:20-31`，其余两类集合也为 36。**在当前 ID 生成规则下无需为此修改集合 schema。** 若未来改用更长 ID，应同时评估三类集合及派生主键长度。

**验证建议：**只读核对线上 Milvus database、三个集合的实际字段、主键、向量维度与配置，并按 `db_src_N` 枚举 `source_id/publish_id`，确认与 PG 源级最近成功发布相符；源码静态对齐不能证明旧集合已经迁移。

## 4. Neo4j

### N-1：图服务把短 `source_id` 解析为 UUID（阻断）

MetaWeave CQL writer 校验短来源、UUID 发布运行，并以 `source_id:逻辑 id` 写 Table/Column 实体键和节点、边归属（`metaweave/metaweave/core/cql_generator/writer.py:83-92,103-115,266-347`）。NL2SQL 图服务却在构造时用 `UUID(source_id)`（`nl2sql/src/modules/db_deepagent/services/join_graph.py:28-38,58-71`）。即使 Milvus 与通用装配修复，问答图服务仍会拒绝 `db_src_N`。

**修改建议：**复用同一个严格短 ID 校验函数；保留按 `Table.entity_id` 定位及 `source_id:逻辑键` 拼接。测试双源同名表的存在性与两种寻路方式。

**维护注释建议：**同步更正 `nl2sql/src/modules/db_deepagent/services/join_graph.py:11` 中“带 UUID 的 entity_id”说法；实体键当前以前缀 `db_src_N` 构造。

### N-2：路径内节点和边的归属尚未逐一核对（待实库验证的完整性风险）

寻路起终点按本源 `entity_id` 定位，但 APOC 与 `shortestPath` 查询遍历 `JOIN_ON` 时未逐一限制中间节点和边的 `source_id`，返回路径时也未核对（`nl2sql/src/modules/db_deepagent/services/join_graph.py:138-193,211-253`）。MetaWeave 当前 writer 使用本源端点建边，正常受管发布应满足隔离；本项**不表示已发现线上跨源边**，也不是本次 readiness 503 的已证实原因。

**修改建议：**先只读检查图库中 `JOIN_ON` 的两端与边归属；在 NL2SQL 路径处理加入全路径归属核对，异常路径拒绝返回。归属判定应使用节点的 `source_id/entity_id` 和边的 `source_id`，不能使用结果中的 `src_table/dst_table`：`join_graph.py:234-238` 在缺少 `id` 时会回退为裸表名 `name`，该值无法证明来源。可让 readiness 对 `JOIN_ON` 端点归属做相同检查。目前 readiness 主要检查边的 `publish_id` 和 `HAS_COLUMN` 端点（`nl2sql/src/api/v2/backend.py:343-377`）。

### N-3：字段和值的对应关系已对齐

writer 当前使用 Neo4j 属性名 `publish_id`，值为 `publish_run_id` UUID；NL2SQL 也读取 `n.publish_id`、`r.publish_id` 并与 PG 的 `publish_run_id` 比较（`nl2sql/src/api/v2/backend.py:307-315,370-377`、`readiness.py:674-685`）。readiness 用短来源剥离实体键前缀（`backend.py:66-70`）。当前值契约一致；按 12.1 改名时须同步迁移所有节点、关系及读取语句，不能只改发布 `rel` 的一个参数名。

**验证建议：**只读核对线上 `Table`、`Column`、`HAS_COLUMN`、`JOIN_ON` 的 `source_id`、`entity_id`、`publish_id`，以及实体键唯一约束；再与 PG 对应步骤的 `publish_run_id` 对照。

### N-4：节点属性与重复规范键尚未完整检查（条件性风险）

`nl2sql/src/api/v2/backend.py:307-342` 读取 `entity_id/id/publish_id` 并把规范键放入集合，`readiness.py:580-606` 比较集合；目前未核对 Table/Column 的 `full_name/database/schema/name` 与逻辑键是否一致，也没有在集合去重前报告重复规范键。[doc 2 §5.5](2_NL2SQL_Vue接入设计.md) 对这些检查有明确要求。正常受管 writer 会写入相应属性并构造实体键；风险主要出现在遗留数据、手工改图或约束缺失时，**不是当前 503 的已证实原因**。

**修改建议：**在线上只读核验中增加节点属性与逻辑键一致性、规范键重复及 `entity_id` 唯一约束检查。若要兑现 doc 2 的完整 readiness 契约，再在 backend 枚举阶段读取并校验这些属性、保留重复计数；此项与三个 UUID 阻断点的最小修复分开实施。`metaweave/metaweave/core/cql_generator/keyspace.py:53-57` 的 UUID 来源注释也应随短 ID 修订。

## 5. 建议实施与验收顺序

1. 先按 12.1 完成 MetaWeave 写侧 `publish_id` → `publish_run_id` 的改造与数据迁移方案；再按本文 §1.1 完成 NL2SQL 读侧代码与联合验收。开发顺序不代表单独上线顺序，实际切换需协调 PG、Milvus、Neo4j 的版本和数据；当前文档修订不执行切换。
2. 修复 M-1、N-1 及通用 `build_services` 的短 ID 校验，确保 readiness 和问答均能构造服务。
3. 修复 PG-1，按 doc 6.2 的源级发布口径更新检查与旧文档，不新增“同工作区”限制。
4. 将旧 UUID 测试夹具迁为短 ID 并覆盖 UUID 输入拒绝；使用隔离环境覆盖 `db_src_N` 的 readiness、创建会话、提问、Milvus 六入口、Neo4j 两种寻路、跨工作区分步骤发布及版本变化拒绝旧会话。
5. 对线上三库执行只读结构和归属核验；只有实际发现旧 schema、残留批次或跨源边时，另拟数据迁移/清理方案。本文件不授权修改线上数据或启停服务。

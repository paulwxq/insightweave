# 7.1 维度值字段自动识别与 Dim 配置生成方案

编写日期：2026-10-27。状态：**需求与修改建议，尚未实施。本文仅记录讨论结果，不代表代码已支持。**

## 1. 需求与边界

在 JSON 采集步骤调用 LLM 判断表类型时，同步识别维度表中适合用于维度值检索的字段。例如产品表的主键为 `product_id`，业务名称为 `product_name`，应推荐 `product_name` 作为维度值字段。后续 Dim 采集步骤读取这一推荐，自动填写 `dim_tables.yaml` 的 `embedding_col`。

用户已明确的要求：

- 允许推荐不完全准确，结果可供人工检查和修改。
- **允许识别不出字段，允许部分甚至全部维表的字段推荐为空。** 不要求每个维表都有推荐，不为保证 YAML 非空而强行填充。
- 不采用规则兜底硬选字段；缺乏足够依据时，LLM 应明确返回空结果。
- 增加 `dimension_value_confidence` 表示字段推荐的置信度，不增加 `dimension_value_reason`。
- 采用方案 C：每张维表最多推荐一个维度值字段，与现有 Web 配置及发布链路的单列限制一致。本次不扩展多列支持。
- `dim` 继续只依赖同一工作区的 JSON 画像，不新增对 Domain、Markdown 或源库的依赖，也不在 Dim 步骤新增 LLM 调用。

## 2. 当前实现

### 2.1 JSON 步骤

`metaweave/metaweave/core/metadata/json_llm_enhancer.py` 已支持在 LLM 调用中根据表结构、样例数据和物理约束判断 `fact / dim / bridge / unknown`，并将分类合并到 JSON 的 `table_profile`。当前尚无维度值字段推荐。现有分类契约须区分响应与存储两层：

- **LLM 响应**使用 `table_category`、`confidence` 和 `reason`。
- **JSON 画像存储**使用 `table_profile.table_category`、`table_profile.confidence`、`table_profile.classification_reason` 和 `table_profile.classification_source`。合并函数将响应的 `reason` 写入 `classification_reason`，并将 `classification_source` 设为 `"llm"`；读取画像时不能使用 `table_profile.reason`。

现有合并逻辑还保留 `rule_based_classification` 并更新 `inference_basis`。新增维度值字段推荐时应沿用这些既有行为。

分类有“分类与注释组合任务”和“仅分类任务”两类提示词入口，实施时须同时覆盖。

### 2.2 Dim 步骤

`metaweave/backend/data_sources/dim_config_step_service.py` 检查同一工作区 JSON 目录的成功采集 marker，并将画像文件列表交给 `DimTableConfigGenerator`。

`metaweave/metaweave/core/dim_value/config_generator.py` 筛选 `table_profile.table_category == "dim"` 的表，按数据库分组，生成：

```text
output/<source_id>/<workspace_id>/dim/dim_tables.yaml
```

当前所有表的 `embedding_col` 都初始化为 `null`。Dim 不读取维表实际数据、不调用 LLM，也不向向量库发布数据。无维表时可以成功生成 `databases: {}`；所有画像都不可读时失败。

维度值的实际读取与向量化由后续 `dim_value` 发布完成。已有发布校验要求所选配置满足加载条件；本方案允许采集阶段保留空字段，不等于允许未配置字段直接发布。

## 3. 目标数据流

```text
JSON 采集
  同一次 LLM 调用：表类型分类 + 维度值字段推荐
  校验并保存到 JSON 画像
        ↓
Dim 采集
  读取同一工作区 JSON
  筛选维表，将推荐映射到 embedding_col
        ↓
dim/dim_tables.yaml
  有推荐则自动填入，无推荐则保留 null
        ↓
用户按需检查、修改 → dim_value 发布按现有规则校验和加载
```

不新增 LLM 请求轮次。字段推荐随 JSON 画像生成，Dim 可以反复读取相同画像生成配置。

## 4. 数据契约建议

### 4.1 LLM 输出

保留现有表分类属性，增加字段列表及独立置信度：

```json
{
  "table_category": "dim",
  "confidence": 0.95,
  "reason": "以产品为实体，主要记录产品描述属性",
  "dimension_value_columns": ["product_name"],
  "dimension_value_confidence": 0.92
}
```

无法识别字段时返回：

```json
{
  "table_category": "dim",
  "confidence": 0.95,
  "reason": "表主要记录实体描述属性",
  "dimension_value_columns": [],
  "dimension_value_confidence": null
}
```

| 属性 | 含义与约束 |
| --- | --- |
| `confidence` | 现有表类型分类置信度，含义不变。 |
| `dimension_value_columns` | 推荐字段名列表，仅允许 0 或 1 个元素；无推荐为 `[]`；必须使用真实字段名，保留大小写。不更名为单数字段，但不表示支持多字段推荐。 |
| `dimension_value_confidence` | 对唯一推荐字段的模型自评置信度；有有效推荐时为 `0～1` 的有限数值，无推荐时为 `null`。 |

字段置信度不是经统计校准的准确率，也不能沿用表分类置信度作为默认值。不设自动填充的置信度阈值：合法推荐可作为初稿写入，无法判断则由模型返回空列表。

### 4.2 JSON 画像存储

建议将两个新属性保存在 `table_profile` 下，与分类结果一起落盘：

```json
{
  "table_profile": {
    "table_category": "dim",
    "classification_source": "llm",
    "classification_reason": "以产品为实体，主要记录产品描述属性",
    "confidence": 0.95,
    "dimension_value_columns": ["product_name"],
    "dimension_value_confidence": 0.92
  }
}
```

上例仅展示相关字段，不替换其他画像属性。`classification_reason` 来自 LLM 响应的 `reason`；新增推荐字段不能遗漏或覆盖既有分类理由、来源及规则分类等属性。开启 LLM 分类并合并结果时，非维表的两个维度值推荐属性统一保存空列表与 `null`，避免保留与当前分类矛盾的旧推荐。

统一采用“缺失即无推荐”，不要求所有画像物理包含两个新属性：

- 开启 LLM 分类时，由分类结果合并逻辑写入推荐；未识别出字段或推荐不合法时写入 `[]` 与 `null`。
- 关闭 LLM 分类时，不为本功能单独调用模型，新生成的基础画像不写两个推荐属性。分类与注释均关闭的早退路径也无需补写。
- 旧画像缺少两个新属性时，同样按“没有推荐”处理。Dim 生成器和配置读取接口在读取时将缺失属性解释为 `[]` 与 `null`，分别输出 `embedding_col: null` 和界面的“无推荐”；不因此回写输入画像。
- 当前受管 JSON 步骤和 CLI `--step json` 都对从 DDL 与源库新建的画像调用 `enhance_document`，不读取旧画像重新分类。`enhance_json_directory` 虽有定义，但仓内无生产调用方，本次不新增或改造旧文件原地增强入口，也不安排历史推荐清理任务。
- 分类失败时（包括 LLM 初始化或请求失败、响应无法解析、分类字段缺失导致合并失败），沿用现有基础规则分类及失败统计，不采纳该响应中的字段推荐，也不补推荐默认属性。由于本次生产链路的输入是新建基础画像，此时两个属性缺失，下游按“无推荐”处理。只有分类成功后才合并推荐；分类成功但推荐本身非法时，按 §5.2 写入 `[]` 与 `null`，不反过来判定分类失败。

基础 `TableProfile.to_json_dict` 不新增推荐默认属性；新增属性的主动写入落点是 LLM 分类结果合并逻辑，画像规范化和序列化负责保留已存在的属性。

### 4.3 YAML 输出

沿用现有加载配置字段 `embedding_col`，不增加同义字段或置信度配置键。JSON 画像是推荐及其置信度的结构化来源；生成 YAML 时，在每张表前写入只读说明注释，让直接查看文件的人也能检查推荐。加载器忽略注释，不改变加载配置契约。配置弹窗的可见性另按 §4.4 落实，不能仅靠文件注释完成。

```yaml
databases:
  order_db:
    tables:
      # 模型原始推荐: [product_name]；推荐置信度: 0.92
      public.product:
        embedding_col: product_name
      # 模型原始推荐: [customer_name]；推荐置信度: 0.30
      public.customer:
        embedding_col: customer_name
      # 模型原始推荐: 无；推荐置信度: 不适用
      public.some_dimension:
        embedding_col: null
```

映射规则：一个有效推荐字段输出单列字符串，无推荐输出 `null`；不得生成列表或逗号分隔的多列配置。模型返回多个字段时按 §5.2 整组清空，不截取第一个。未识别出维度值字段的维表仍应保留在表清单中。没有识别到任何维表时，仍允许 `databases: {}`。

核心层 `DimTableConfig.embedding_cols_list` 和 `DimValueLoader` 虽支持逐列处理，但现有 Web 链路仅支持单列：配置读取将列表和逗号串视为未指定，PUT 仅接受单列字符串，发布预检拒绝未指定字段的表。`dim_value` CLI 入口已移除，不能把核心层能力等同于当前可用发布能力。本方案保持 Web 单列契约，不扩展 GET、PUT、弹窗或预检的多列支持。

生成器既有文件头须同步修订：将“需人工填写 embedding_col”改为“按画像推荐自动填入单个维度值字段；无法识别时留空，可人工检查和修改”，删除三种格式说明中的多列列表、逗号串及对应示例，只保留单列字符串和 `null` 示例，并明确 Web 每表仅支持一个字段。不能只新增逐表置信度注释而保留旧的多列引导文案。

### 4.4 人工检查途径与注释生命周期

人工检查必须同时支持配置弹窗和直接查看 YAML 文件：

- **配置弹窗**：每张表展示“当前配置字段”“模型原始推荐字段”“推荐置信度”。原始推荐为空时显示“无推荐”，置信度显示“—”；有效弱推荐显示实际数值，例如 `0.30`，不与无推荐混淆，不设阈值阻断。推荐缺失、画像不可读或推荐不合法时不编造分数；必要时显示“推荐信息不可用”。
- **人工修改后**：原始推荐及其置信度保持只读；当前配置不同于原始推荐时标注“当前配置与模型推荐不同”，不能将原推荐置信度解释为对人工修改结果的评分。原始推荐只展示校验通过的单个字段或“无推荐”。
- **会话内新增表**：推荐仅随 GET `dim-config` 的已保存表清单返回。通过 `/objects` 在本次弹窗会话中新加入的行，不额外请求推荐，也不从 `/object-columns` 推断推荐；显示“推荐未加载，保存后重新打开可查看”，置信度显示“—”，不将其标为模型“无推荐”，也不据此显示与模型推荐不同。用户仍须按既有单列配置规则选定字段后保存；保存本身不自动推荐或补填字段。保存后重新打开弹窗，由 GET 获取该表的推荐信息，即使画像已有推荐也不要求新增时立即展示。
- **API 来源**：配置读取接口按当前工作区 JSON 画像读取并按 §5.2 校验推荐，返回独立的只读推荐属性。它们不是配置提交字段，不参与保存校验，也不修改现有用于配置写入的版本冲突机制。读取推荐失败不得使本来可编辑的 YAML 配置无法打开。原始推荐明确指当前工作区 JSON 中的模型结果，不宣称是某次历史配置生成时的快照。
- **容错边界**：仅新增的 JSON 画像推荐读取与解析段允许降级为“推荐信息不可用”。既有 `_require_workspace` 的工作区及 Dim 成功 marker 检查、数据源登记检查、YAML 配置读取与有效性检查保持原顺序和错误响应，包括合法的 404；不得将这些检查包进推荐读取的容错块或吞掉原异常。先完成既有配置读取校验，再附加可选推荐信息。
- **文件注释**：生成时逐表写入模型原始推荐与分数，无推荐时写“无/不适用”。文件头明确注释仅描述生成时的模型推荐，手工修改配置不会自动更新注释，注释不参与发布校验。

现有 `DimValueConfigDialog.vue` 使用结构化配置接口，不展示 YAML 原文；`dim_value_config_api.py` 保存时使用 `yaml.dump` 重建文件，不保留原注释。因此，注释方案有实现和维护成本，不能称为零成本，也不能替代弹窗展示。

本次不引入通用 YAML 注释保留机制：Web 编辑保存沿用重建行为，不要求保留生成时的逐表注释；保存后的文件头应明确说明“Web 编辑保存，模型推荐及置信度请在配置弹窗查看”。弹窗始终从结构化画像获取推荐信息，不解析注释。后续重跑 Dim 再按最新画像生成逐表注释。

## 5. 提示词与校验建议

### 5.1 提示词

在现有分类任务中追加条件任务：仅当表被判断为维表时，推荐适合作为业务检索入口的名称、标签或别名字段。

- 优先选择能代表实体的业务名称，例如产品名称、地区名称、客户名称。
- 区分实体标识与业务名称；不因 `product_id` 是主键就将其当作名称字段。
- 每张维表最多返回一个最具代表性的字段。存在多个可能字段时，能明确择优就推荐一个；无法判断最合适字段时返回空列表，不返回多个候选。
- 不选择无关时间戳、度量、纯技术标识或任意字符串字段来凑数。
- 只能从已提供的字段中选择；无法判断时返回 `[]` 和 `null`。
- 输出推荐置信度，不输出字段推荐理由；现有分类 `reason` 继续保留。

### 5.2 程序校验与容错

采用确定的整组降级规则：新增推荐不合法时，将 `dimension_value_columns` 整组清空为 `[]`，将 `dimension_value_confidence` 置为 `null`，并记录提示日志。不保留部分合法字段，不因可选推荐失败而使原本有效的表分类整体失败。原有分类契约校验继续保持。

两类置信度有意采用不同处理方式：既有表分类 `confidence` 保持原有逻辑，缺失时默认 `0.9`，越界时截断到 `0～1`；新增 `dimension_value_confidence` 不设置默认分数、不截断越界值，也不沿用表分类置信度。无维度值字段推荐时统一为 `null`，不用 `0` 代替“没有推荐”；非空推荐的置信度缺失或不合法时，按整组清空规则处理。实施时不得为对齐旧逻辑而给新字段补默认分数或截断越界值。

- 校验字段列表类型、长度及字符串元素；列表仅允许 0 或 1 个元素，长度大于 1 即非法，即使是重复的同名字段也不先去重接纳。列名全集取自当前表 JSON 画像的 `column_profiles` 对象的键，推荐字段必须在这些键中真实存在；不另查源数据库或其他产物，不自动改变大小写匹配另一个字段。JSON 合并与 Dim 读取均使用这一来源。
- 校验置信度为有限数值且在 `0～1`，拒绝布尔值、NaN、无穷值等非法结果。
- 字段列表类型错误、长度大于 1、存在非法元素或不存在的字段，或非空推荐的置信度缺失、不合法时，执行上述整组清空规则。即使其中有合法字段也不保留，不自动截取首项，避免擅自改变模型推荐后继续沿用原置信度。
- 字段列表为空时统一将置信度设为 `null`；LLM 分类结果合并时，非维表统一清空两个属性。关闭分类的新基础画像允许属性缺失，不要求为满足这一规则补写空值。
- 不对缺失置信度编造默认值，不在没有推荐时通过规则补选字段。
- Dim 读取旧画像或外部画像时也须校验推荐字段及置信度；推荐不合法时，整组不采用，该表输出 `embedding_col: null`，并记录提示日志，不回写输入画像。旧画像缺少两个新属性按“没有推荐”兼容，不视为非法推荐。

上述整组清空及提示日志规则为已确定的实施和验收口径。“识别不出来可以为空”的要求保持不变，不得通过容错或兜底逻辑强制填充。

## 6. 修改入口与实施顺序

| 位置 | 建议修改 |
| --- | --- |
| `metaweave/metaweave/core/metadata/json_llm_enhancer.py` | 扩展组合与仅分类提示词、响应校验；分类成功后合并推荐或空结果。分类失败不采纳推荐、不补默认属性，保留既有规则分类和失败统计；关闭分类及早退路径不补写默认属性。不新增旧文件原地增强入口。 |
| `metaweave/metaweave/core/metadata/metadata_document.py`、`models.py` 等画像规范化与序列化入口 | 确保已存在的推荐属性在规范化、重建或序列化时保留，允许属性缺失；仅修改实际受影响路径。基础 `TableProfile.to_json_dict` 不新增推荐默认属性。 |
| `metaweave/metaweave/core/dim_value/config_generator.py` | 读取推荐并映射 `embedding_col`，兼容缺少新字段的旧画像，生成逐表推荐与置信度注释；按 §4.3 替换旧文件头中“需人工填写”的表述，删除多列格式说明与示例，保留单列和空值示例。 |

| `metaweave/backend/data_sources/dim_config_step_service.py` | 保持 JSON 前置检查、目录备份、临时文件校验与原子替换；按需补充有推荐/无推荐的数量摘要。 |
| 现有 JSON 增强、画像规范化和 Dim 生成测试 | 验证新字段从 LLM 响应到 JSON 再到 YAML 的完整链路及空结果兼容。 |
| `metaweave/backend/profile_loading/json_loader.py` 对应发布测试 | 增加含推荐属性的 JSON 发布兼容回归，覆盖输入校验、已知字段映射和发布入库；维持新推荐属性不入库的既有行为，不新增数据库列。 |

建议先明确和验证 JSON 契约，再扩展 LLM 输出与合并，最后调整 Dim 生成、配置读取接口与弹窗并进行联动验证。无需新增平台数据库字段，不新增步骤，不改变采集拓扑和发布加载配置结构。配置弹窗的最小只读推荐展示属于本次必要范围；其他页面的置信度展示不在本次范围内。

## 7. 重跑与人工编辑边界

当前 Dim 重跑会先备份目录，再重新生成配置；既有人工编辑不会自动合并。实施本需求后，若沿用现有行为，新配置将来自最新 JSON 推荐，无推荐的表仍为 `null`。

此前讨论过“保留人工配置优先于自动推荐”的建议，但**尚未确定纳入本次范围**。如需同时实施，应另行明确人工编辑的识别、失效字段处理、已删除表处理和备份策略，不能仅根据旧 YAML 非空就将其认定为人工配置。否则无法区分旧自动推荐与人工修改，可能持续保留过期推荐。

可将 YAML 当前 `embedding_col` 与 JSON 画像中的最新 `dimension_value_columns` 归一化后做 diff（单字符串转为单元素列表，`null` 对应空列表），用于提示“当前配置与最新模型推荐不同”。但 **diff 不等于人工修改判据**：例如旧推荐为 `product_name`，JSON 重跑后改为 `product_alias`，而 Dim 尚未重跑，此时 YAML 与最新画像不一致，却没有发生人工编辑；反之，人工选择了与推荐相同的字段也不会产生差异。自动生成的 YAML 只保证与生成当时的画像推荐一致。未来若需要可靠识别人工修改，应结合生成时的推荐基线或显式编辑记录另行设计；本次不增加该机制，也不根据 diff 自动决定保留旧值。

本方案的基础实现不擅自加入配置合并机制，沿用现有备份与重新生成语义；开发说明和验收需明确重跑的覆盖行为。

## 8. 验收建议

1. 产品表被分类为维表时，可在同一次分类调用中返回 `product_name`；JSON 保存推荐与独立置信度，Dim 生成对应的 `embedding_col`。
2. 组合分类提示词和仅分类提示词均支持新属性；不增加额外 LLM 调用。
3. 维表无法识别字段时，JSON 为 `[]` / `null`，YAML 保留该表且 `embedding_col: null`；全部维表均无推荐也允许 Dim 成功。
4. 无维表时允许 `databases: {}`；所有 JSON 均不可读的既有失败行为保持。
5. 自动生成的 `embedding_col` 均为单列字符串或 `null`，保留推荐字段原始大小写，可被 Web GET、保存与发布预检按既有单列契约处理：有效单列字符串正常展示、保存和参与发布校验；`null` 显示为未指定，保存及发布仍按既有未配置规则拦截，须人工补齐或移除对应表。
6. 字段列表类型错误、长度大于 1（包括重复字段）、存在非法元素或不存在的字段，或非空推荐的置信度缺失、不合法时，JSON 合并结果必须为 `dimension_value_columns: []` 和 `dimension_value_confidence: null`，并记录提示日志；即使其中有合法字段也不保留、不截取首项，不影响原本有效的表分类。Dim 读取此类非法推荐时输出该表的 `embedding_col: null` 并记录提示日志，不回写画像。不虚构字段，不混用分类置信度。
7. 关闭 LLM 分类时，新基础画像不写推荐属性，包括分类与注释均关闭的早退路径；旧画像缺少属性与此使用同一“无推荐”口径。Dim 输出 `embedding_col: null`，配置弹窗显示“无推荐”，不回写画像。开启分类但初始化、请求、解析或分类合并失败时，保留既有规则分类及失败统计，不采纳响应中的推荐，新画像不补推荐属性；分类成功但推荐非法时仅清空推荐，不判定分类失败。分类成功的非维表写入空推荐。本次不验收不存在的旧画像重新分类生产路径。
8. 已存在的新属性经过 JSON 规范化和落盘后仍保留，缺失属性不被强制补写，基础 `TableProfile.to_json_dict` 不新增默认属性；Dim 只依赖同工作区 JSON，既有 marker、manifest、备份和原子落盘机制正常。
   同时验证 LLM 响应的 `reason` 仍映射为画像的 `classification_reason`，`classification_source` 仍为 `"llm"`，既有规则分类保留逻辑不受新增属性影响；读取画像使用存储字段名。
9. 空字段采集成功与发布准入保持区分；`dim_value` 仍按现有配置校验要求决定能否发布。
10. 生成 YAML 包含逐表原始推荐及置信度注释；弱推荐与无推荐可区分，加载器解析结果不受注释影响。文件头明确注释为生成时信息，不能视为对人工修改结果的评分；旧的“需人工填写”表述已替换为自动推荐、无法识别留空及可人工修改的说明，仅展示单列和空值示例，不再引导使用列表或逗号串配置。
11. 配置弹窗可直接查看原始单字段推荐与置信度，无需用户查找 JSON 文件；人工改选字段后显示与原推荐不同，不重新给人工配置评分。非法多字段推荐不得作为有效推荐展示。旧画像或推荐读取失败时仍可编辑已有配置，并准确显示无推荐或信息不可用。
    会话内新增表按 §4.4 显示“推荐未加载”及置信度“—”，不扩展 `/objects`、`/object-columns` 或新增请求获取推荐，不误标为模型无推荐或与推荐不同；按现有规则手工选定字段并保存后，重新打开弹窗才获取推荐，不要求新增时立即展示画像中的推荐。
12. Web 保存不提交只读推荐属性，不改变配置校验和版本冲突机制；重建 YAML 后文件头提供弹窗检查途径，不要求保留旧逐表注释。重开弹窗仍能读取画像推荐；重跑 Dim 恢复按最新画像生成的逐表注释。
13. JSON 发布兼容：其余内容合法的画像在包含有效单字段推荐及置信度、包含空推荐 `[]` / `null`、缺少两个新属性这三种情况下，均正常通过 `json` 发布校验和入库，不因新属性报错。回归测试覆盖 `_validate_document`、`_table_row` 及发布入库路径：两个新属性不映射为数据库列，不改变既有表画像和列画像字段的入库结果；已有字段校验仍有效，不为兼容新属性而放宽。
14. 配置 GET 的推荐容错仅作用于 JSON 画像读取与解析：既有配置有效而推荐读取失败时仍可打开配置；工作区不存在、Dim marker 缺失或失败、数据源登记缺失、YAML 缺失或无效时仍返回既有错误，不得被转换为成功响应中的“推荐信息不可用”。

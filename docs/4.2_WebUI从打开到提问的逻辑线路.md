# 4.2 WebUI 从打开到提问的逻辑线路

记录日期：2026-10-18。状态：**按当前代码核对后的调用链说明**。

本文按使用顺序说明三件事：打开 WebUI 看到左下方聊天记录、点开其中一条、继续提问。每一步给出前端组件 → HTTP 接口 → 服务端处理 → 落库/落盘位置的对应关系。字段与表结构的静态说明见 [4.1_Web对话历史与Store_Checkpoint_结果目录的查找关系.md](4.1_Web对话历史与Store_Checkpoint_结果目录的查找关系.md)。

## 1. 全程一图

```text
打开 /query 页面
  └─ GET /api/v2/sessions                    ← 左侧列表（只读 Web 会话登记）
点开一条记录
  └─ GET /api/v2/sessions/{sid}              ← 会话详情（登记行）
  └─ GET /api/v2/sessions/{sid}/turns        ← 历史问答（web_turns 行）
继续提问
  └─ POST /api/v2/sessions/{sid}/query       ← 同步执行一轮（D4）
       ├─ 校验登记 → 复核来源 → 锁 + pending
       ├─ Runner：thread_id 续聊 checkpoint
       ├─ SQL 执行 → result_ref → results/<result_ref>/
       ├─ 归档 qa / sessions / threads / runs 副本
       └─ 收尾钩子：写 web_turns + 更新登记 + 清 pending
查看结果表格
  └─ GET /api/v2/sessions/{sid}/results/{result_ref}   ← 读 rows.jsonl
```

前端三个关键文件：`frontend/src/modules/nl2sql/composables/useChat.ts`（会话与提问状态）、`frontend/src/modules/nl2sql/sessionList.ts`（列表共享状态）、`frontend/src/components/AppSidebar.vue`（侧栏装配）。文件名不带路径的均相对 `insightweave/` 仓库根。

## 2. 阶段 0：新建会话（列表行的来源）

入口「新建查询」→ `POST /api/v2/sessions`（`nl2sql/src/api/v2/router.py:185`）→ `create_web_session`（`nl2sql/src/api/v2/runs.py:210`）：

1. 数据源就绪检查通过后生成标识：`session_id = "s_" + uuid4().hex`（`runs.py:232`）、`creation_id`。
2. 取会话锁、查标识碰撞后，按「通用绑定在先、Web 登记在后」的写序往 `db_deepagent.store` 写两行（`runs.py:276-289`）：

| 命名空间（`prefix` 列） | `key` 列 | `value` 内容 |
| --- | --- | --- |
| `db_deepagent.sessions` | `session_id` | 通用绑定：`current_thread_id=None`、`thread_seq=0`、`source_id`、`carried_evidence=[]` |
| `db_deepagent.web_sessions.guest` | `session_id` | Web 登记：`title="新对话"`、`source_id`、`last_active_at`、`turn_count=0`、`state="active"`、`pending_run_id=creation_id` |

此时还没有 thread_id、没有 result_ref。左侧列表只认第二行。

## 3. 阶段 1：打开页面，看到左下方聊天记录

```text
QueryView 挂载（QueryView.vue:96 onMounted，:127 refreshSessions）
  └─ refreshSessions()                        sessionList.ts:17
       └─ GET /api/v2/sessions?limit=30       client.ts:159
            └─ router.list_sessions           router.py:200
                 └─ webstore.list_session_infos（webstore.py:480）
```

- 服务端枚举 `prefix = 'db_deepagent.web_sessions.guest'` 的行：**`key` 列就是 session_id**，`value` 里取 `title`、`source_id`、`last_active_at`、`state`。
- 枚举时对登记做元数据核对调度（`router.py:220` `_schedule_reconcile`）：发现登记与 turn 日志不一致时，锁内重算 `turn_count`/`title`/`last_active_at`。
- **这一步只读 store 登记行**：不查 checkpoint，不扫 results/sessions 目录。
- 前端把 `SessionInfo[]` 存入 `sessionList.ts` 的共享状态，侧栏 `ConversationList` 与查询页共用同一份，避免重复请求（`sessionList.ts:2-4` 注释）。
- **`guest` 不是用户**：命名空间来自硬编码常量 `WEB_SESSIONS_NS = ("db_deepagent", "web_sessions", "guest")`（`webstore.py:36`）。系统没有用户表、没有登录态，服务端从不询问"当前用户是谁"——所有请求都用同一个常量，所以所有人看到同一份列表（`webstore.py:509` 的 owner/origin 校验也只认这对固定值）。将来做多用户，改的就是这一个常量的来源（例如换成 `("db_deepagent", "web_sessions", <user_id>)`）；写入端 `put_registration` 用同一常量，同步改即可，其余查询逻辑不动。

## 4. 阶段 2：点开一条记录

```text
点击列表项（ConversationList.vue:46 emit('open', session_id)）
  └─ AppSidebar.openSession → router.push(/query/:sessionId)   AppSidebar.vue:34-35
       └─ watch(route.params.sessionId)                        QueryView.vue:83-90
            └─ chat.openSession(sessionId)                     useChat.ts:254
                 ├─ ① GET /api/v2/sessions/{sid}    会话详情
                 └─ ② GET /api/v2/sessions/{sid}/turns?limit=50&offset=…
```

**① 会话详情**（`router.py:237`）：`Store.get(("db_deepagent","web_sessions","guest"), session_id)` 取登记单行，核对 `owner=="guest"` 且 `origin=="web"`（`webstore.py:334-335`），返回 `turn_count`、`continuable` 等展示信息。`session_metadata_invalid` 时前端单次重读，仍失败进入只读历史模式（`useChat.ts:254` 内重试分支）。

**② 历史轮次**（`router.py:270` `list_turns`）：`Store.search(("db_deepagent","web_turns", session_id))`，即 `prefix = 'db_deepagent.web_turns.<session_id>'` 的行：

- `key` = 该轮 `request_id`；
- `value` = `{question, answer, saved_at, display:{elapsed_ms, evidence:[{sql, result_ref, row_count, source_truncated}]}}`（投影规则见 `webstore.py:110-136` `normalize_turn_display`）。

前端取尾页 50 条并自动补齐到最新（`useChat.ts:202` `loadTurns`），渲染为问答气泡。此时 evidence 里的 `result_ref` 只是字符串引用，尚未用于读文件。

## 5. 阶段 3：继续提问（核心链路）

```text
前端 ask()（useChat.ts:363）
  └─ POST /api/v2/sessions/{sid}/query        client.ts:190
       └─ submit_query（router.py:316）：限流 + 容量名额
            └─ execute_web_query（runs.py:508）
                 └─ run_agent_query（runs.py:780）
                      └─ DbAgentRunner.run
```

### 5.1 execute_web_query 的五步前置（runs.py:517-660）

1. **读 Web 登记行并校验**：存在、owner/origin 对、`source_id` 与请求一致、`state=active`、无遗留 `pending_run_id`（有则保守失效会话，不自动重放）。
2. **轻量复核**：数据源指纹 / 知识快照与登记不一致 → 失效会话（`source_changed` / `knowledge_changed`），拒绝续聊。
3. **完整就绪检查**（30 秒缓存）。
4. **锁 + pending 保护**：`request_id = "req_" + uuid4().hex`（`runs.py:515`）先以 `pending_run_id` 写入登记行。若进程中途死掉，下一请求读到遗留 pending 会保守失效会话——宁可让用户新建，也不重放结果不确定的一轮。
5. **锁交接给 Runner**：外层持有的会话锁直接传入 Runner，同线程持锁至终态收尾，消除释放-重取间隙（`runs.py:654-660` 注释）。

### 5.2 run_agent_query：每轮独立装配（runs.py:780）

配置 → 注入登记 → `build_services` → 打开平台池（连接 `lg_persist`，`search_path=db_deepagent`）→ PostgresSaver/PostgresStore → 组装 Agent → 构造 `QaArchive` → **核对通用 `db_deepagent.sessions` 行**（缺失或 `source_id` 不一致即拒绝，`runs.py:820-827`）→ `DbAgentRunner.run`。

### 5.3 Runner 单轮内部（nl2sql/src/modules/db_deepagent/runner.py）

| 步骤 | 做什么 | 落到哪 |
| --- | --- | --- |
| 解析线程 `_resolve_thread`（`runner.py:489-525`） | 读 `("db_deepagent","sessions")` 行的 `current_thread_id`；没有则造 `dbda:<session_id>:1`；`parse_thread_id` 校验归属，跨会话拒绝 | 决定本轮 checkpoint 的 `thread_id` |
| 续聊状态 | 以 `thread_id` 读/写 checkpoint；轮换条件（消息数 ≥ `thread.rotate_after_messages` 或手动）满足时 `new_seq = max(max_seq, thread_seq)+1`，session 不变 | `db_deepagent.checkpoints` / `checkpoint_blobs` / `checkpoint_writes`，`thread_id` 列 |
| 执行 SQL | 工具 execute_sql → `sql_pipeline` → `ResultStore.save()`：`result_ref = "res_" + uuid4().hex`（`result_store.py:416,438`），先写 rows.jsonl 再原子写 meta.json（`result_store.py:432-482`） | `<workspace>/results/<result_ref>/{rows.jsonl, meta.json}`；`result_ref` 同时记入状态账本 `db_executions`（分析为 `db_analyses.output_result_ref`）与证据列表 |
| P3 归档（`runner.py:797-806`） | `write_qa`：`{run_id, thread_id, question, status, answer, evidence, stats}`；失败轮走 `write_run_errors` | `Store.put(("db_deepagent","qa",<sid>), request_id, …)` |
| P3 轨迹 | upsert sessions 行（`current_thread_id`、`thread_seq`、`last_active_at`）+ threads 行 | `("db_deepagent","sessions")` / `("db_deepagent","threads",<sid>)` |
| P4 落盘（`runner.py:905-916`） | 该轮完整结果副本 `result.model_dump()`，排他创建不覆盖 | `<workspace>/sessions/<sid>/runs/<request_id>.json`；审计事件由 middleware 追加 `audit.jsonl`（`request_audit.py:62`） |
| 收尾钩子（`runs.py:349` `_make_finalize_hook`） | 终态再次轻量复核来源：不通过则写安全摘要轮 + 失效会话；通过则 `write_turn` + 回读校验 → 更新登记（`turn_count+1`；标题仍为「新对话」时取首问前 40 字；刷新 `last_active_at`；清 `pending`） | `Store.put(("db_deepagent","web_turns",<sid>), request_id, …)` + 重写登记行 |

收尾钩子返回后，`_project_result`（`runs.py:693`）把结果投影为 `WebQueryResult`，HTTP 200 同步返回（D4）。

## 6. 阶段 4：前端展示与查看结果表格

- `ask()` 成功后**不重读历史**：刚答完的一轮直接用响应渲染；已保存的上一轮在下次提问/重开会话时转入本地历史（`useChat.ts:373-390` 注释）。同时并行刷新会话详情（`turn_count`）与会话列表（`useChat.ts:390`）。
- 答案卡片使用响应里的 `evidence[]`（SQL 摘要 + `result_ref` + 行数）。
- 用户点开结果表格时才按引用读文件：`GET /api/v2/sessions/{sid}/results/{result_ref}`（`client.ts:207`）→ `router.py:345` → `ResultStore(Path(cfg.workspace.root)).read_rows_cells(...)` → 读 `results/<result_ref>/rows.jsonl`。

### 6.1 本轮展示的两条数据路径：内存与磁盘，全程不查 store

查询返回后在界面上看到的内容，来自两条互不相干的路径，**store 表两头都不参与**：

```text
路径一（result_ref 引用）：内存
  POST /sessions/{sid}/query 的同步响应体 WebQueryResult
    .evidence[].result_ref
      ← Runner 内存对象 DbAgentResult.evidence 的直接投影（dto.py:277）
  DTO 注释明确定位（dto.py:268-270）：
  「不内嵌 preview/rows/columns；UI 按 evidence.result_ref 调用结果 API 取页」
  ——响应带引用，不带表格数据。

路径二（表格数据）：磁盘
  EvidenceBlock.vue:89 调 getResult(sessionId, resultRef, offset, 100)
    → GET /sessions/{sid}/results/{result_ref}（router.py:345）
      → ResultStore.read_rows_cells 读磁盘 rows.jsonl，分页返回
        → 前端格式化成表格
```

store 里那份 result_ref 引用是写给**以后**的场景：重开会话（web_turns/qa 提供引用）、元数据校正、维护清理保护。本轮收尾时 store 写入晚几秒也无妨——展示不依赖它。

## 7. ID 查找链速查

设 `session_id = s_…`，`request_id = req_…`，`result_ref = res_…`，`thread_id = dbda:<session_id>:<seq>`：

```text
session_id
 ├─ 左侧列表        → store[("db_deepagent","web_sessions","guest"), key=session_id].value
 │                    （title / source_id / last_active_at / turn_count / state / pending_run_id）
 ├─ 历史问答        → store[("db_deepagent","web_turns",<sid>), key=request_id].value
 │                    （question / answer / display.evidence[].result_ref，新轮次）
 ├─ 旧轮次归档      → store[("db_deepagent","qa",<sid>), key=request_id].value
 │                    （thread_id / run_id / status / evidence[].result_ref）
 ├─ checkpoint 线程 → store[("db_deepagent","sessions"), key=session_id].value.current_thread_id
 │                    → checkpoints.thread_id（db_deepagent schema）
 ├─ 运行副本        → <workspace>/sessions/<sid>/runs/<request_id>.json（+ audit.jsonl）
 └─ 结果文件        → <workspace>/results/<result_ref>/meta.json + rows.jsonl
                      （meta.json 反写 session_id / thread_id / request_id / result_ref）
```

机器上的实际根目录（`DB_DEEPAGENT_WORKSPACE` 未设置、从 `nl2sql` 目录启动时）：`/opt/projects/insightweave/nl2sql/var/db_deepagent/`。

## 8. result_ref 的生命周期：文件先落地，store 后登记，展示不走 store

以真实会话 `s_f87cdbc4bd2c4435a68b1025959ffe1b` 的第 1 轮为例，2026-10-18 实测时序：

| 时刻 | 动作 | 证据 |
| --- | --- | --- |
| 17:07:43.915 | SQL 执行完成，`ResultStore.save()` 生成 `result_ref`，`rows.jsonl` + `meta.json` 原子落盘 | 文件 mtime、`meta.json.created_at` |
| （中间约 3 秒） | 模型拿 20 行预览 + result_ref 字符串 → 生成答案 → 提交 final answer | |
| 17:07:47.069 | Runner 收尾归档，store 里才第一次出现这个 result_ref（qa 行；web_turns 行随后） | store 行 `created_at` |

三条结论：

1. **文件是本体，store 是引用**。`result_ref` 在 SQL 执行瞬间生成（`res_` + uuid），文件当场落盘；store 各处的 result_ref 只是收尾时补写的引用。反向情况（store 有引用而文件不存在）正常流程不应发生——清理程序受"仍被引用不删"保护（见 8.1 末段）。
2. **本轮展示不查 store**（第 6.1 节）：result_ref 走内存响应，表格走磁盘文件。store 写入延迟只影响"下一轮/重开"场景。
3. **字符串流转 ≠ 读文件**。以下场景只是把 result_ref 当字符串读出来：左侧列表（完全不涉及）、打开会话/翻历史（渲染卡片）、checkpoint 续聊（账本随状态回上下文，恢复动作不读文件）。

### 8.1 真正读结果文件的场景（仅 4 类）

| # | 场景 | 读取者 | 读什么 | 代码位置 |
| --- | --- | --- | --- | --- |
| 1 | 同一轮内模型要更多行/列统计 | `read_result` 工具 | `rows.jsonl`（≤200 行） | `result_tools.py:40-95` |
| 2 | `analyze_result` 分析前校验输入引用 | `load_meta` | `meta.json` | `result_tools.py:149,184` |
| 3 | 跨轮占位符引用（`input_result_refs`）／沿用证据（`reused_from`）展开 | sql_pipeline | `meta.json` + 按需读行 | `sql_pipeline.py` |
| 4 | 用户点开结果表格（本轮或重开会话后） | results API → `read_rows_cells` | `rows.jsonl` 分页 | `router.py:345`、`EvidenceBlock.vue:89` |

- 结果目录清理（`maintenance.py:607-624`）：现行实现为收集「仍被引用的 result_ref 集合」做删除保护（被 qa/分析引用且未过 `result_retention_days=30` 的不删）。**2026-10-19 决策：移除引用保护**——改为超过 30 天即删除；30 天后表格由快照兜底，原始明细仅剩 meta + 前 200 行（docs/3.1 §7）。实施前本段仍描述现行行为。

所有文件读取都强制归属校验 `_require_session`（`result_store.py:513-514`）：`meta.json` 的 `session_id` 必须等于请求会话，跨会话直接拒绝。

### 8.2 模型可见的数据边界：预览 + 引用 + 字符预算

execute_sql 返回给模型的不是完整结果，而是有界投影（`sql_tools.py:161-173`）：

```json
{
  "evidence_id": "E-…",
  "result_ref": "res_…",
  "columns": ["…"],
  "saved_row_count": 12345,
  "source_truncated": false,
  "preview_rows": [["…"]],
  "preview_truncated": true,
  "elapsed_ms": 456
}
```

`preview_truncated` + `saved_row_count` 明确告诉模型"你只看到预览，总共有多少行"；模型据此自行决定后续动作：

| 后续动作 | 适用 | 边界 |
| --- | --- | --- |
| `read_result(result_ref, columns?, offset, limit)` 按页翻原始行（`result_tools.py:40-95`） | 需要看具体行 | 每页 ≤ `read_max_rows`（200），返回带 `next_offset` 可连续翻页；输出仍受字符预算截断 |
| `analyze_result(operation, inputs, params, allow_pushdown)` 服务端算结论（聚合／TopN／占比／比较／去重／描述） | 要结论不要原始行 | 只返回统计结论；本地算不动时允许下推业务库重查（带"非原快照"警告） |
| 重写 SQL 再 `execute_sql` | 重新查询 | 合法选项，产出新 result_ref |

**输出预算的配置与代码分工**：

| 配置项 | 值 | 定义位置 | 作用 |
| --- | --- | --- | --- |
| `results.max_tool_output_chars` | 12000 | yaml `:118` | 所有工具输出的字符总预算；yaml 注释"保证不触发 SDK 大结果转存" |
| `results.preview_rows` | 20 | yaml `:116` | execute_sql 返回给模型的预览行数 |
| `results.read_max_rows` | 200 | yaml `:117` | read_result 单次最多行数 |
| `business_db.max_saved_result_rows` | 10000 | yaml `:35` | 单次查询最多保存行数，超出置 `source_truncated` |

要点：`max_tool_output_chars` 的**数值在 yaml，代码只写约束**——`config.py:181` 声明 `Field(gt=0)`，无默认值；yaml 缺项则配置加载直接报错，不会静默回退。所有工具（result_tools / schema_tools / guard_tools）统一经 `finalize_output(payload, services.config.results.max_tool_output_chars)` 截断，改 yaml 一处全局生效。另有字段级硬编码截断：`executed_sql` 截 3000 字符（`sql_tools.py:32`），与输出总预算分层，互不冲突。

## 9. 轮次账本对账：turn_count、web_turns、qa、run_errors

四个数字的统计口径不同：

| 指标 | 统计什么 | 存放位置 |
| --- | --- | --- |
| `turn_count`（登记字段） | **所有**产生过问答的轮次，失败也算（失败轮写安全摘要答案） | ≈ `web_turns.<sid>` 行数（校正时直接按其行数重算，`webstore.py:660`） |
| `qa` 行数 | 只有**成功归档**的轮次（执行过 SQL，或完成答案引用了沿用证据） | `db_deepagent.qa.<sid>` |
| `run_errors` 行数 | 失败的轮次 | `db_deepagent.run_errors.<sid>` |

正常对账关系：**qa + run_errors = web_turns = turn_count**；全程无失败时 qa 行数恰好等于 turn_count，有失败轮就少——少的那几行在 run_errors 里。

真实例子（`s_bc4aff2356f34f97beca7b34056360d3`，2026-10-18 实测）：`turn_count=5`、web_turns=5、qa=4、run_errors=1（失败轮："订单状态有哪几种取值？"），4+1=5 对账成立。

两个附带事实：

- qa／run_errors 是 **Runner 层归档**（CLI 与 Web 共用），与 Web 登记是两套账。库里有多个 `s_xxx` 会话只有 run_errors、无 Web 登记行——那是脚本/CLI 会话，不是"丢了登记的 Web 会话"。
- qa 行与 web_turns 行靠 **`key`（request_id）** 一一对齐；排序用 store 行自带的 `created_at` 列。

## 10. 手工从数据库点开一条会话（对照前端接口）

登记行（第 3 节查到的 JSON）里**没有对话内容**——没有问答文本、request_id、thread_id、result_ref。点开一条记录 = 拿该行 `key`（session_id）继续三步：

```sql
-- 第 1 步：问答内容（对应 GET /sessions/{sid}/turns）
SELECT key, value->>'question', value->>'answer', value->'display'->'evidence'
FROM db_deepagent.store
WHERE prefix = 'db_deepagent.web_turns.<session_id>'
ORDER BY value->>'saved_at';

-- 第 2 步：旧轮次缺 display 时，去 qa 归档补（对应 checkpoint/result_ref 入口）
SELECT key, value->>'thread_id', value->'evidence'->0->>'result_ref'
FROM db_deepagent.store
WHERE prefix = 'db_deepagent.qa.<session_id>';

-- 第 3 步：按需取文件（results/<result_ref>/）与 checkpoint（thread_id 列）
```

用 `s_f87cdbc4bd2c4435a68b1025959ffe1b` 实测（2026-10-18）：第 1 步返回 2 轮，第 1 轮无 display（旧行）、第 2 轮 evidence 指向 `res_a3aeaba5…`；第 2 步两轮都有 thread_id `dbda:s_f87cdbc4…:1` 和同一个 result_ref；第 3 步 `meta.json` 反写四个 ID，其中 `request_id=req_39b84be7…` 是**第 1 轮**。

两个推论值得记住：

- **result_ref 与轮次是多对多**：一份数据可被多轮引用（上例第 2 问复用第 1 问的 COUNT 结果，没有重新执行）；一轮复杂提问也可产生多个 result_ref（evidence 是数组）。要知道"文件是哪轮写的"，看 `meta.json.request_id`，不是"哪轮引用了它"。
- **轮次的主键是 `key`（request_id）**，qa、web_turns、磁盘 `runs/<request_id>.json` 三处靠它对齐。

## 11. 三条设计要点

1. **session 与 thread 是两层**：session 是对话（左侧列表一行、store 四个命名空间的键），thread 是 checkpoint 线程（`dbda:<sid>:<seq>`）。正常续聊 seq 恒为 1，轮换后 seq+1 而 session 不变。
2. **result_ref 在执行中才诞生**（SQL 真正落表时），随后出现在三处：checkpoint 状态账本、qa 归档、web_turns 的 `display.evidence`。左侧列表阶段完全见不到它。
3. **pending_run_id 是崩溃保护**：执行前写入登记行、收尾清除；读到遗留 pending 即保守失效会话。这是「不会把执行到一半的一轮当历史重放」的保证来源。

# 10.1 采集作业步骤依赖与并行调度建议

编写日期：2026-11-04。状态：**并行方向已确认，待实施；已补充审核后的日志隔离、展示顺序、状态收集和中断收尾要求。**

本文讨论 Web 采集作业的 `db、ddl、json、md、domain、dim、rel、sql` 八个步骤。目标是在保留现有产物校验、失败阻断和运行记录语义的基础上，按依赖关系并行执行独立步骤。

## 1. 当前执行方式

页面展示的完整步骤序列为：

```text
db → ddl → json → md → domain → dim → rel → sql
```

当前后端先通过拓扑排序整理步骤顺序，再使用普通 `for` 循环同步调用各步骤 worker。一个步骤执行结束并记录结果后，才启动下一个。因此，**同一次采集运行的不同步骤目前是串行执行的**。

拓扑排序保证上游先于下游，但不会自动产生并行执行。部分步骤内部已经按表使用线程池，这与本文讨论的“不同步骤之间并行”是两个层次。

代码依据：[collection_run.py](../metaweave/backend/jobs/collection_run.py) 中的 `_STEP_DEPS`、`_ensure_managed_step_order()` 和 `execute_collection_run()`；表级线程池见 [generator.py](../metaweave/metaweave/core/metadata/generator.py)。

## 2. 实际依赖关系

| 步骤 | 实际消费的上游产物 | 主要输出 | 必须等待的条件 |
| --- | --- | --- | --- |
| `db` | 无；直接查询源数据库 | `db/database.json` | 数据源及配置有效 |
| `ddl` | 无；直接查询源数据库 | `ddl/*.sql`、清单 | 数据源及配置有效，不依赖 `db` 产物 |
| `json` | `ddl/` 产物，同时访问源库采样 | `json/*.json`、清单 | DDL 成功且产物校验通过 |
| `md` | `json/` 画像 | `md/*.md`、清单 | JSON 成功且产物校验通过 |
| `domain` | `md/` 文档 | `domain/db_domains.yaml` | MD 成功且存在有效文档 |
| `dim` | `json/` 中的维表分类及字段推荐 | `dim/dim_tables.yaml` | JSON 成功且存在可读画像 |
| `rel` | `json/` 画像、`domain/db_domains.yaml`，同时访问源库采样 | `rel/` 中的 JSON 和 Markdown 关系报告 | JSON、Domain 成功且产物有效 |
| `sql` | `md/` 文档、Domain YAML、Rel Markdown 报告 | `sql-rag/` 中的 SQL 样例及相关输出 | MD、Domain、Rel 成功且产物有效 |

需要特别说明：

1. **`db` 是独立分支。**其他七个步骤不读取 `db/database.json`，DDL 不需要等待 DB；主链也不需要等待 DB。
2. **`dim` 只依赖 JSON。**它不等待 MD、Domain；Rel、SQL 也不读取 Dim 产物。这里的 Dim 是生成维表配置，不是执行发布阶段的值向量化。
3. **当前 Web 的 Rel 明确要求 Domain 成功。**该前置检查在业务域筛选参数解析之前执行；关闭业务域筛选，也不会自动解除这个要求。此次建议保留该依赖。
4. **MD 的实际输入是 JSON。**现有调度表还声明了 `DDL → MD`。完整执行时该依赖已包含在 `DDL → JSON → MD` 中，但只选部分步骤时仍涉及现有排序及失败阻断行为，实施时应保留兼容。

各步骤依据：

- [DB worker](../metaweave/backend/data_sources/db_step_service.py)、[DDL worker](../metaweave/backend/data_sources/ddl_step_service.py)、[JSON worker](../metaweave/backend/data_sources/json_step_service.py)。
- [MD worker](../metaweave/backend/data_sources/md_step_service.py)、[Domain worker](../metaweave/backend/data_sources/domain_step_service.py)、[Dim worker](../metaweave/backend/data_sources/dim_config_step_service.py)。
- [Rel worker](../metaweave/backend/data_sources/rel_step_service.py)、[SQL worker](../metaweave/backend/data_sources/sql_step_service.py)。

## 3. 建议的并行结构

下面只画主链和分支；完整依赖仍以第 2 节为准：

```text
db（独立执行）

ddl → json ┬→ md → domain → rel → sql
           └→ dim
```

完整执行时的推进方式：

1. 开始时，DB 和 DDL 都具备启动条件，可以同时执行。
2. DDL 成功后启动 JSON，无须等待 DB 完成。
3. JSON 成功后，MD 和 Dim 都具备启动条件，可以同时执行。
4. MD 成功后启动 Domain，无须等待 Dim 完成。
5. Domain 成功且 JSON 已成功后启动 Rel。
6. Rel 成功且 MD、Domain 已成功后启动 SQL，无须等待 Dim 完成。
7. 等本次所有已选步骤进入终态后，汇总整体运行状态。

以上是依赖允许的并行关系；实际启动还受并发上限约束。不要按“整批全部完成，再启动下一批”的方式实现，否则耗时较长的 DB 或 Dim 仍可能拖住本来可以继续的主链。

全量八步依赖图的最大并行宽度为 **3**：如果 JSON 完成时 DB 尚未结束，DB、MD、Dim 可以同时执行。上限设为 2 时，其中一个就绪步骤需要等待；不能把上限 2 理解为等同于无上限。

在忽略调度开销、资源竞争且并发容量充足的理想情况下，完整运行耗时约为：

```text
max(
  T_db,
  T_ddl + T_json + T_md + T_domain + T_rel + T_sql,
  T_ddl + T_json + T_dim
)
```

这里表示并发容量充足时的理论调度收益，不代表实际上限为 2 时的耗时承诺。Dim 通常只是读取画像并生成配置，若 DB、Dim 耗时较短，整体加速幅度也会较小。

## 4. 调度改造建议

### 4.1 按依赖就绪启动步骤

以现有 `_STEP_DEPS` 为基础，将串行循环调整为有并发上限的依赖调度器：

- 分别维护待执行、执行中、已完成步骤。
- 对本次已选步骤，只在其同选上游全部成功并完成结果提交后，才允许启动。
- 任一步骤完成后，立即检查是否有新的步骤可以启动。
- 保留请求顺序作为多个就绪步骤之间的调度优先级，不再将该顺序理解为严格的时间先后关系。
- 同选上游失败或被阻断时，按既有规则阻断受影响的后继；其他独立分支继续执行。

采用一个调度线程统一收集 Future 完成结果，更新待执行、执行中和终态表，并决定后续任务启动。worker 不直接修改共享终态表，避免“追加结果”和“判定下游”跨线程竞争；无需另建共享状态锁框架。

阻断文案保持 `_blocked_by_same_request_upstream()` 的优先级，不按任务完成先后取第一条失败消息：Rel 按 JSON → Domain，SQL 按 MD → Domain → Rel；MD 同选 JSON 时只看 JSON，未同选 JSON 时只看 DDL。对下游作出终态判定前，等待其本次同选依赖全部进入终态，再按上述规则选文案。

需要把“执行一个步骤”的完整流程抽出，包含认领、上下文装配、worker 调用、异常处理、产物清单、marker 和状态写回。完成通知必须发生在上述流程结束之后。

**worker 返回成功还不等于下游可以启动。**下游会读取成功 marker；必须先完成产物校验、清单和成功 marker 写入、步骤状态提交，再释放下游。状态或 marker 未能可靠写入时，不得仅凭内存中的成功结果放行。

### 4.2 保留部分执行和旧产物复用规则

- 不自动补选上游，不改变用户本次选择的步骤集合。
- 上游也在本次选择中时，下游必须等待本次上游，不能提前读取旧产物；本次上游失败后也不能回退使用旧产物。
- 上游未在本次选择中时，继续由 worker 检查工作区已有产物是否成功、完整、有效。
- 保留现有 MD 在部分选择情况下的 DDL 排序及阻断语义，避免并行改造顺带改变原有行为。

例如，只运行 Dim 时可以在前置检查通过后复用已有 JSON；同时运行 JSON 和 Dim 时，Dim 必须等待本次 JSON 成功。

### 4.3 并发控制和运行隔离

建议本阶段先采用步骤并发上限 2，达到上限时按请求优先级等待空位。这是在并行收益与资源占用之间的取舍；暂不增加页面参数或动态限流机制，后续根据实测调整。

这一优先级可能让 Dim 延后主链：例如 DB 仍占另一名额，Domain 完成后 Dim、Rel 同时就绪，按当前完整请求顺序先执行 Dim。本阶段接受该行为，不增加关键路径优先策略。

实施时还应核对：

- 每个执行任务独立装配上下文、使用数据库会话，不跨线程共享 SQLAlchemy Session。
- 复用现有步骤认领与工作区互斥逻辑；新调度器不替代已有的跨运行、采集与发布之间的访问保护。
- 各步骤继续只备份和更新自己的产物目录，已经释放给下游的上游产物不能被本次运行继续改写。
- 全量执行时，使用 LLM 的 JSON、Domain、Rel、SQL 位于主链，步骤之间不会叠加 LLM 调用。源库负载仍可能叠加，例如 DB 与 DDL、JSON、Rel 或开启校验的 SQL 重叠；还需考虑步骤内部的表级并发。
- 部分执行时不能沿用上述 LLM 互斥结论。例如只选 JSON 和 Domain、且各自已有上游产物有效时，两者可以并行调用 LLM。步骤上限 2 只限制本次运行的步骤数量，不是源库连接数或 LLM 请求数的全局上限。
- 运行结束时等待所有已启动任务完成，不因某一分支提前结束就提前汇总或释放运行中限制。

### 4.4 日志上下文隔离（必改）

当前 [logger.py](../metaweave/metaweave/utils/logger.py) 的 `_CURRENT_STEP` 是进程级可变字符串，仅在任务内调用 `set_operation_step()` 仍会互相覆盖。标准 API 日志配置目前不消费该值：LogRecordFactory 和 StepFilter 只在 CLI script 日志模式安装，Web/API 日志仍按模块分文件，不能把全局 step 覆盖描述为当前 API 日志已按步骤串写。

本次保留此项改造，是为了消除共享代码的并发状态错误：将 step 改为 `ContextVar`，在任务结束时恢复上下文。CLI 表级线程池原先通过全局共享取得 step，改为 ContextVar 后若不传播上下文会回归，因此隔离与传播必须同批交付。

线程池不会自动继承提交者的 ContextVar。复用 [logging_manager.py](../metaweave/services/logging_manager.py) 已有的 `submit_with_context()`，覆盖步骤线程池、MetadataGenerator 表级线程池和 SQL 校验线程池；每个任务分别复制，不能共用同一个 Context。SQL `validate_batch()` 当前使用 `executor.map()`，改为逐条提交时按输入顺序保存 Future、按该顺序取结果，保留 SQL 与结果及 `r.index` 的对应关系。

调用范围包括 `collection_run.py` 的步骤设置入口，以及 [execution.py](../metaweave/metaweave/core/metadata/execution.py) 的 `execute_generate_domains()`、`execute_generate_dim_config()`、`execute_generate_sql_rag()`、`execute_cql()`、`execute_rel()`、`execute_ddl_json_md()` 六个入口。当前 Web 受管 worker 直接调用生成器或关系发现管线，不再经过这些 `execute_*()` 函数；保留各入口现有标签映射和 SQL 阶段切换，不将 Web 的 `domain` 统一改成 CLI 的 `generate-domains`。

script 模式继续通过 LogRecordFactory 和 StepFilter 按步骤分流，过滤器依据记录生成时确定的 `record.step`；API 模式继续按模块分流，不新增按步骤分文件能力。无需引入新的日志系统。

### 4.5 中断风险与收尾

当前采集运行没有自动启动恢复；API 已有的启动扫描只处理删除任务。进程中断后，采集步骤可能遗留 pending/running，`finalize_run()` 会拒绝汇总，进而继续影响重复执行及删除准入。并行会增加一次中断可能遗留的 running 步骤数量，但不能据此认定中断概率翻倍。

本阶段沿用已有 [resolve_orphaned_run.py](../metaweave/scripts/resolve_orphaned_run.py)：先确认所有可能执行该运行的进程已停止，再预览并按脚本要求显式收尾，将 running 置为 failed、pending 置为 blocked，保留已有终态并汇总运行。实施交付时验证此流程可处理多个遗留 running 步骤。

若所有步骤均已进入终态、仅整体运行尚未汇总，可使用脚本的 `--finalize-only` 模式，仅汇总而不修改步骤状态；仍有任一步骤为 pending/running 时，该模式拒绝处理，需要按上述普通收尾流程处理。

本次不新增自动接管、心跳或租约机制，也不能在每次 API 启动时直接将全部 running 判失败；多进程部署下，其他进程可能仍在执行。

### 4.6 运行详情展示顺序

采用启动时间线口径：继续使用 `list_run_steps()` 的 `started_at、step_name` 排序，前端按返回顺序展示；同一启动时间按步骤名排序，未启动或被阻断且无启动时间的步骤沿用现有查询排列，不代表执行计划。修正 [run_detail.py](../metaweave/backend/jobs/run_detail.py) 中“固定顺序”的注释，不新增计划顺序字段或数据库字段。

采集执行确认区改为步骤标签列表，标签仍按计划（拓扑）顺序排列，去掉串行箭头，并提示“按依赖调度，可并行执行”；结果区说明“按启动时间排列，未启动步骤的排列不代表执行顺序”。确认区与结果区采用不同排序是有意设计，无需对齐；结果列表和步骤详情切换使用同一响应顺序，不从中反推依赖关系。发布页面保持现有语义。

## 6. 验证与验收

自动化测试应使用可控制完成时机的假 worker，通过事件或屏障确认先后关系，避免主要依赖固定休眠时间判断并发。

应覆盖以下场景：

1. **完整执行：**DB 与 DDL 可以重叠；JSON 等待 DDL；MD 与 Dim 可以重叠；Domain 不等待 Dim；Rel、SQL 各自等待所需上游。
2. **分支失败：**DB 或 Dim 失败不阻断主链；MD 失败阻断 Domain、Rel、SQL，但不阻断 Dim；JSON 失败阻断其所有同选后继。多上游失败时，改变完成顺序也不能改变既有阻断文案优先级。
3. **部分执行：**只选 Dim、只选 SQL、JSON 与 Dim 同选、DDL 与 MD 同选但不选 JSON，以及 JSON 与 Domain 同选等情况，保持现有产物复用和阻断规则。
4. **结果提交：**上游 worker 已返回但 marker 或状态尚未提交时，下游不能提前启动；结果提交故障不能导致错误放行。
5. **并发上限与结果收集：**让 DB 持续运行至 JSON 完成，此时 MD、Dim 均就绪，上限 2 只允许再启动一个；空位释放后推进另一任务。多个任务同时完成时，每个结果仅处理一次，不重复提交或遗漏步骤。
6. **运行汇总：**独立分支仍在执行时，整体保持运行中；所有步骤终态后继续使用既有汇总规则。
7. **现有互斥：**其他运行占用、发布占用及删除状态检查继续有效。
8. **页面验证：**能够同时显示多个运行中步骤，执行期间继续禁用重复执行及参数修改；刷新后恢复真实状态。结果和详情切换顺序与 API 的启动时间排序一致，同时间及无启动时间的步骤按既有查询规则排列；采集确认区不再用箭头暗示串行。
9. **日志隔离：**交错输出两个步骤的日志，覆盖步骤线程、表级线程及 SQL 校验线程；step 不互相覆盖，任务结束后恢复上下文，现有入口标签和 SQL 阶段切换不变。script 按步骤分流正确，API 仍按模块分流，不要求出现步骤日志文件。
10. **中断收尾：**构造包含多个 running、部分 pending 和已有终态的遗留运行，验证现有人工脚本保留终态、正确收尾并汇总；只预览时不修改数据。验证 `--finalize-only` 对全部步骤已终态的运行仅作汇总，对仍有 pending/running 步骤的运行拒绝处理且不修改数据。
11. **SQL 校验保序：**让后提交的校验先完成，验证返回结果仍与输入 SQL 顺序及回填的 `r.index` 一一对应，同时保留步骤上下文。

手工测试时保留各步骤开始、结束时间，核对独立步骤是否实际重叠，并对比改造前后的产物与状态。仅凭页面上的步骤排列不能判断是否实现了并行。

## 7. 本次结论

推荐保留主链 `DDL → JSON → MD → Domain → Rel → SQL`，让 DB 独立运行，并在 JSON 成功后启动独立的 Dim 分支。通过有并发上限的依赖调度器推进步骤，不以整个批次完成作为下一步的启动条件。

本文仅记录方案，尚未修改执行代码。实施完成后应同步更新相关执行约定和本文章节状态。

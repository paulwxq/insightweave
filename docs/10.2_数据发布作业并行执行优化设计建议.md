## 1. 现状、问题与结论

**有条件可行。**当前八个发布步骤之间未发现消费其他发布步骤写入结果的硬依赖；独立性来自实际输入链路核对，不来自数据库类型。可以把一次发布运行拆成三个资源通道并行推进，各通道内部保留原顺序。但不能直接把串行循环换成线程池上线：必须补齐源级发布互斥、输入稳定性、原子认领、可靠状态提交及异常收尾。

推荐“依赖就绪调度 + 资源通道容量限制”，第一阶段退化为三个有序通道。数据库只是资源分类，不能成为依赖判定依据。暂不引入工作流平台、跨库两阶段提交、自动故障接管或任务级自动重试。

收益主要来自 Milvus 的 Embedding/加载与 Neo4j 生成/导入、平台 PostgreSQL 内容写入的重叠。没有基准耗时证据，不能承诺加速倍数；Dim 还会读取业务源库，平台 PostgreSQL 写入与源库读取应区分。

## 2. 当前完整执行流程与模块关系

### 2.1 作业、版本、运行、步骤及执行器

- 工作区隔离采集文件；发布作业保存允许步骤和默认配置；不可变 revision 固定配置版本；每次实际执行新建 `publish_run_id`，只为所选步骤创建 `publish_run_step`。
- `job_params.py` 定义白名单与参数；`run_request.resolve_run_request()` 处理 default/custom、版本子集与覆盖，禁止临时参数污染版本；Dim/Domain 有效清单冻结到步骤行。
- 真正编排器为 `publishing/publish_service.py::execute_publish_run()`；`_execute_step()` 是单步执行包装，`_PUBLISHERS` 映射八个业务函数。PG 函数直接写平台库，其余函数构造各自 loader；不存在三个现成的独立数据库队列。
- API 使用 FastAPI `BackgroundTasks` + `_run_in_thread()`/`asyncio.to_thread()`，属于同进程后台任务，没有持久消息队列保证重启后继续执行。见 [workspaces.py](../metaweave/backend/api/routers/workspaces.py) 的 `create_publish_run_route()`。

### 2.2 执行过程

1. `create_publish_run()` 定位作业、revision、工作区、启用数据源；按“源 → 工作区 → 作业”锁序执行删除/访问守卫。
2. 解析配置，`precheck.normalize_publish_steps()` 去重并固定排序为 `db、ddl、json、domain、table_schema、dim_value、rel、sql`。集中预检全部所选步骤，不合格整单 400，无运行和业务写入。
3. 同一事务建立 pending run 与所有所选 pending step，提交后返回 202，注册后台调用。
4. 后台读步骤并重新固定排序，run 由 pending 置 running。普通同步 `for step_name in steps: _execute_step(...)`，前一步返回才进入下一步。**固定排序决定先后，同步循环保证串行；数据库锁不是本运行串行的根本机制。**
5. 单步设置日志 step，复查 source/marker/文件/冻结参数；不就绪记 blocked。`_claim_publish_step()` 在源/工作区锁下检查其他运行的同工作区同名 running 步骤，随后置 running。
6. 外部库 publisher 构造 loader、加载并关闭连接；PG 四步直接使用平台 session。成功步骤保存输入/目标 manifest；failed 通常保存输入清单；现有 blocked 路径不保存清单。各路径分别写回终态。PG 内容及 success 同事务；外部库写入后单独事务记录 success。不生成发布 marker。
7. 即使一步 failed/blocked，现有循环也继续其他步骤；没有发布阶段“上游失败就全部阻断”。全部步骤进入终态后 `finalize_run()` 汇总。

关键源码：[publish_service.py](../metaweave/backend/publishing/publish_service.py) 的上述函数；[precheck.py](../metaweave/backend/publishing/precheck.py) 的 `check_step()`、`STEP_INPUT_DIRS`；[run_repository.py](../metaweave/backend/jobs/run_repository.py) 的 `create_run()`、`finish_step()`、`finalize_run()`。

## 3. 实际输入、写入及依赖核对

下表是发布阶段契约，采集阶段生成输入的依赖不等于发布步骤间依赖。

| 发布步骤 | 实际输入和额外访问 | 目标/替换范围 | 是否读取另一发布步骤结果 |
| --- | --- | --- | --- |
| db | 当前工作区 `db/database.json`、登记源 | 平台 PG `db_profile`，每源整行替换 | 未发现 |
| ddl | 受管 `ddl/*.sql` 和清单 | PG `table_definition`，本源 DDL 类型替换 | 未发现 |
| json | 受管 JSON、登记快照及 schemas | PG `table_profile` + `table_column_profile`，本源替换 | 未发现 |
| domain | 冻结 `domain.domains`、MD 候选清单/对应文档、登记快照；仍需 Domain marker | PG `table_domain`，本源替换 | 未发现；不读已发布 JSON/DDL 表 |
| table_schema | 工作区 JSON + MD 受管输入、Embedding | Milvus 表结构集合，本源 upsert 后清旧 | 未发现；不是读取 PG table_profile |
| dim_value | 冻结 `dim_value.tables`、Dim marker/产物准入、JSON 候选字段、登记连接、**实时源库维度值**、Embedding | Milvus 维度集合，本源 upsert 后清旧 | 未发现；不读已发布 domain/table_schema |
| rel | 工作区 JSON、Domain YAML、Rel JSON/MD、登记及配置；生成辅助 CQL | Neo4j 本源节点替换，亦清理所有无 source_id 节点 | 未发现；不读 PG table_domain 或 Milvus |
| sql | 当前工作区 sql-rag JSON、Embedding | Milvus SQL 集合，本源 upsert 后清旧 | 未发现；不再调用 Rel/Domain 发布，不连接源库 |

### 3.1 证据及重要边界

- PG 四个 `_publish_*()` 均在源/工作区锁下删除本源对应内容并插入新数据，成功状态在同一 session commit。JSON 内部先插入表级画像、flush，再插入列画像，必须保持原子单步，不把这两张表分成并行节点。
- [models.py](../metaweave/backend/persistence/models.py) 中 `TableColumnProfile` 外键依赖 `TableProfile` 并级联删除；`TableDomain` 没有指向 JSON/DDL 内容表的外键，不能凭表名推断 `json → domain` 发布依赖。
- [domain_loader.py](../metaweave/backend/profile_loading/domain_loader.py) 的 `domain_rows_from_config()` 及 `precheck._domain_effective_check()`、`_dim_value_check()`执行候选/配置校验；不能只看 `STEP_INPUT_DIRS` 就认定 Domain 只读 YAML、Dim 只读 dim/。7.2 有效清单替代共享 YAML，未额外增加 JSON/MD 成功 marker 的要求，继续保留现有最小准入。
- [table_schema_loader.py](../metaweave/backend/profile_loading/table_schema_loader.py) 调用 `prepare_managed_table_schema_input()` 直接读文件；[dim_value_loader.py](../metaweave/backend/profile_loading/dim_value_loader.py) 注入登记源六项连接参数；[sql_loader.py](../metaweave/backend/profile_loading/sql_loader.py) 只定位工作区文件。三者均生成独立 Milvus alias，关闭本连接不会主动断开其他 loader。
- `_publish_rel()` 短事务检查输入，事务外备份/生成 CQL，再调用 [CQLLoader](../metaweave/metaweave/core/loaders/cql_loader.py)。`load()` / `_execute_replacement_transaction()` 在单个图事务中清理、写入、计数核验；失败可回滚，提交状态未知时仍需人工核对或重发。其无归属节点全局清理意味着不同源的 Neo4j 操作也不能无条件并行。
- [repository.py](../metaweave/backend/publishing/repository.py) 的 `collection_inputs_in_progress()` / `rel_publish_in_progress()` 保护同工作区 JSON/Domain/Rel 采集与 Rel 发布；这是文件写读互斥，不是 PG JSON/Domain 发布到 Neo4j 的依赖边。
- Domain 发布可使用本次冻结清单，而 Rel 仍使用文件 Domain YAML；两者可能不同。这是现有契约，并行不会使它们自动一致；不能声称一次发布具有统一业务域快照。

结论限于当前八种 loader。新增步骤或修改 loader 读取平台内容表时，必须重新核对并增加数据依赖，不能沿用“跨库独立”的结论。

## 4. 推荐架构与任务排序

### 4.1 一个调度器、三个资源通道

单个协调线程维护 pending / in-flight / terminal，使用有限线程池执行完整 `_execute_step()`；Future 完成后立即检查可启动节点，不按整批屏障推进。每个 worker 独立 session、配置深拷贝、loader 和连接，不传递 ORM 实例到其他线程。

第一阶段固定策略：

- PG 通道：`db → ddl → json → domain`，只包含本次已选步骤，容量 1。
- Milvus 通道：`table_schema → dim_value → sql`，只包含本次已选步骤，容量 1。
- Neo4j 通道：`rel`，容量 1。
- 每运行总步骤并发上限 3；部署初始开关默认 serial，灰度启用 parallel。通道首步骤可同时就绪；上限调低时按既有全局固定顺序选择就绪节点。

这些箭头表示**前驱终结后继续的顺序约束**，不是前驱必须成功的数据依赖。比如 db 失败仍继续 ddl，table_schema 失败仍可执行 dim_value/sql。等待前驱持久化到终态后释放通道；写回未知时停发，不能把异常返回当终态。只选 ddl/domain 时，PG 按 ddl 后 domain，不补选 db/json。

源行锁是跨通道的共享临界区：每步 claim、Rel prepare 都要取源锁，PG 内容事务持源/工作区锁直至内容和状态提交，可能是最长持锁者。因此“通道同时就绪”不保证业务加载立即重叠，线程已提交或 started_at 已写入也不能证明外部 I/O 重叠。第一阶段保留该锁序与事务边界，不能为了加速提前释放保护内容一致性的行锁。

建议短事务采用可配置的 `SET LOCAL lock_timeout`（初始 30 秒，压测后调整）。复查/claim/prepare 在实际内容写入前超时，回滚后以独立短事务记 blocked、原因 `publish_lock_timeout`；已进入 PG 内容写入事务的超时回滚后记 failed。状态写回仍失败则走控制面故障收尾，不自动重复认领或调用 loader。观测区分 ready、提交、claim 开始/完成、外部 I/O 开始/完成及持锁时间。

### 4.2 DAG 与资源约束应区分

计划结构包含 `step、data_dependencies、order_predecessors、resource_key、priority`。当前 `data_dependencies` 为空；通道顺序由已选集合过滤原顺序后建立相邻 `order_predecessors`，无需强制把不同通道连接起来。图构建应验证未知节点、环和资源配置冲突。

将来若 B 确实读取 A 发布的输出，声明 A→B 数据边，只在 A **持久化 success** 后放行 B；A failed/blocked 时阻断 B。多个依赖未全部终态前不决定阻断原因，按计划优先级给稳定文案；独立节点继续。资源令牌只控制容量，不传播业务失败。第一阶段不提供用户自定义 DAG API，计划由服务端静态版本构造。

Milvus 相邻顺序边是第一阶段保留旧顺序的策略，不能当作永久业务依赖。未来经容量验收放开同运行不同集合并发时，必须发布新的计划版本，移除这些人为顺序边，仅保留真实数据边与资源令牌；只增加容量不会解除顺序边。活动运行沿用原计划，不中途改边。

普通拓扑排序再同步循环不能实现并行；每库一个线程但缺少跨通道依赖判断也不构成通用 DAG 调度器。

## 5. 并发上线前必须补齐的保护

### 5.1 按源互斥发布，保护真实替换范围

当前 `_claim_publish_step()` 只拦同工作区、同名、另一个 running run，不能拦同源其他工作区。Milvus 两次不同 publish_id 的交错 upsert/删旧可互相清理；PG 行锁只串行某次事务，也不能保证整次发布运行不交错。

第一阶段采用保守可实现的策略：**同一 source_id 同时仅允许一个 pending/running 发布运行，不同库通道在该运行内部并行。**创建时在既有源行锁下查询所有关联工作区/作业的活动发布运行，冲突返回 409 和运行定位信息；创建新 pending 与检查同事务。运行正常汇总到终态才释放占用，状态未知/进程中断仍占用，离线收尾后释放。所有运行入口必须使用同一规则；禁止仅用进程内锁，禁止跨外部 I/O 长持 PG 行锁。

source_id 隔离只覆盖本平台受管入口，不覆盖调试 CLI、人工脚本或另一个平台部署。上线期间停用绕过入口的写操作；无法确保单一写入方时禁止启用并行。不同源的 Neo4j 写入初期使用**部署级、跨进程 Neo4j 目标互斥**，覆盖 validate/load 的 schema 与数据操作；可用 PG session advisory lock，独立连接在 try/finally 中释放，锁键由目标实例/数据库生成稳定标识。竞争时等待需有超时与明确失败原因；不得用 Python hash() 产生跨进程键。该锁不替代删除任务准入，两者需遵守同一目标互斥协议。

目标锁失效处理不能只靠 try/finally。参考 `backend/deletion/task_lock.py::ensure_lock_connection_alive()`，在每次目标 schema/数据操作前后探测原专用连接，不重连并冒充仍持有原锁；失锁停止后续操作，不宣告 success。探测不能撤回已发出的请求，也不能消除探测后立即断线的窗口，因此仅靠 advisory lock 不足以提供故障下的严格互斥。

为避免新执行者在旧请求仍在途时接管，新增持久目标保留记录（建议 `publish_target_guard` 表：规范化目标键、owner_kind、owner_id、reserved_at；名称虽含 publish，但发布与删除统一使用）。取得目标 advisory lock 后，在短事务中检查/建立 owner；已有其他 owner 时不得外部写入，即使能取得 advisory lock。正常完成全部在途操作且终态可靠提交后才清 owner；失锁、进程崩溃或状态未知保留 owner 和活动运行/任务，不自动超时接管。新执行者因此被持久记录挡住，须人工确认旧执行者与外部请求已结束、核对目标结果后清理保留记录。原任务 advisory 锁失效时，删除侧继续遵守“不由旧执行者改写任务终态”的现有规则，目标保留记录同样不由失锁执行者清除。该表及脚本支持是上线前置，不声称当前已有此能力。

### 5.2 输入稳定性

当前预检和实际读取之间有窗口，marker/manifest 不是不可变文件快照。Rel 有专用保护，并不代表八步输入都已经冻结。

第一阶段统一采用工作区保留规则：创建发布时持“源 → 工作区”锁，拒绝该工作区有 pending/running 采集运行；建立 pending 发布后，采集创建与认领、文件配置保存、受管产物覆盖等写入口必须在同样锁下反查 pending/running 发布并拒绝写入，直至整体终态。两个方向都检查，涵盖已排队采集及发布尚未开始的窗口。不同工作区文件不互锁；同源登记连接/schema/禁用等影响加载的修改同样在源锁下检查活动发布后拒绝。

此规则需要落到所有写入口，不能仅改前端或认领一个步骤。保留集中预检、执行期复查、Rel 专用 marker/指纹检查；不添加跨目录采集时间新鲜度比较。主配置运行期间保持不变，运维变更须排空活动发布；未来需要热更新时另行设计完整配置快照。外部直接改文件不在 API 锁保证范围，运维必须禁止。

新增 API 拒绝约定：活动发布阻止采集创建/配置保存时返回 409 `workspace_publish_active`；活动采集阻止发布创建时返回 409 `workspace_collection_active`，携带阻塞运行定位信息。已创建的采集步骤在认领复查遇冲突时记录 blocked，不再创建一份替代运行。前端显示“工作区存在进行中的采集/发布，请完成或收尾后重试”，保留本地草稿，不自动排队、不自动重发。这些是建议新增的错误码，不是现有实现。

文件稳定不等于源库维度值稳定：Dim 读取实时数据，跨表不承诺同一数据库快照。本方案保留现有语义；需要统一业务时点快照时必须另立需求。

### 5.3 原子认领与资源预算

现有 `mark_run_running()` / `mark_step_running()` 采用先读再改，`_claim_publish_step()` 还忽略后者 bool；重复投递同一 run 可能形成双执行。应改条件 UPDATE（pending→running）并检查 affected rows；认领与冲突检查在锁内完成。只有本次认领成功才执行 publisher。`finish_step()` 应限定合法来源状态，避免重复完成覆盖终态；禁止把终态步骤直接改回 pending 重放。

每运行 3 并发不等于全局 3。初始部署通过集中运行名额限制活动运行数，并限制 Neo4j 目标为 1、同一 Milvus 目标的加载数和 Embedding 请求预算；不同源首次创建同集合时需目标级 DDL 互斥或预建集合。推荐先将受管发布全局活动运行名额设为 1 验证单运行收益，再按容量压测逐步放开不同源。多进程名额必须使用数据库锁/持久记录，不能每进程各计一次。源库连接、Embedding 限流、Milvus flush/索引和平台连接池均需监控，不能无限增大线程池。

全局名额明确采用**创建时原子准入**，不建立持久等待队列：创建事务先取全局准入 transaction advisory lock（独立稳定命名空间），再按源→工作区→作业锁序检查同源/工作区冲突及全部 pending/running 发布运行数量。集中预检通过且名额有余才同事务创建 pending run/step；pending 行即占用名额，不另持一个跨运行 session 锁。全局准入锁必须先于所有源行锁，不在创建事务中等待目标锁；只用于短期串行化创建，不覆盖外部 I/O。

满额返回 409 `publish_capacity_exhausted`，不生成额外运行；前端显示“发布容量已满，请稍后重试”，不自动排队或重复提交。名额只在 run 终态提交或离线收尾终态提交后由活动计数自然释放；全部 step 终态但 run 尚未汇总仍占名额。全局上限为 1 时，一个孤儿 pending/running 会阻塞**所有源**的新发布，须人工收尾，不能只描述为影响本源。目标保留记录另行释放，离线运行收尾脚本不能不核验外部请求便直接清除它。

## 6. 状态、异常、重试与取消

### 6.1 持久化及汇总

复用 step 的 pending/running/success/failed/blocked 与 run 的 pending/running/success/partial_success/failed，不因并行新增 success 类型。`finalize_run()` 已拒绝未终结步骤：全部 success 为 success；至少一 success 且存在 failed/blocked 为 partial_success；无 success 为 failed。这里是步骤结果汇总，不保证目标库当前内容全属于本次运行。

PG 内容写入及 success 继续同事务。外部库和 PG 无分布式事务，不能保证外部写入与状态原子一致。当前 `_record_terminal()` 捕获并吞掉数据库异常，导致 `_execute_step()` 可能返回 success 而持久步骤仍 running；必须改为显式提交结果或抛出状态写回异常。协调器只认可已提交状态，Future 返回成功不能替代数据库事实。

状态提交失败属于控制面故障：停止新调度，等待已启动任务结束并尽力记录，不无条件 finalize；保留运行占用和异常告警。独立 worker 的未捕获异常（含执行期复查/认领位于现有 try 外）也必须被协调器收集，尝试将未终结步骤写为 failed，未启动步骤 blocked；若库不可用则留待恢复。线程池始终 join，不能汇总或释放占用后让旧 worker 继续写入。

### 6.2 现有重试与幂等边界

当前没有发布作业级自动重试/取消 API。loader 内存在连接、Embedding 重试（如 table_schema `_embed_all()`、Dim `_retry()`、SQL `_process_batch()`），Neo4j driver `execute_write()` 有自身事务重试语义，不等于平台任务可任意重放。

| 目标 | 现有安全性与限制 | 建议重试方式 |
| --- | --- | --- |
| PG | 每步事务内按源替换；失败回滚；JSON 两层记录同事务 | 错误确认后新建运行，所选失败步骤重发，不重置旧步骤 |
| Milvus | 稳定业务主键 upsert，publish_id 标识批次；全量成功才按源删除其他批次；没有整步事务，部分写入可见 | 确认无旧执行者及无同源发布后，以新 run_id 对该步骤完整重发；禁止只重试失败批次后直接清旧 |
| Neo4j | 单图事务清理/写入/计数核验；回调内异常经 `_RolledBackWorkError` 包装，通常确认回滚而不触发 driver 瞬态重试；回调之外提交阶段的可重试异常仍可能让 driver 重执行事务；未知提交不能推断未写入 | 持源及目标互斥核对后重发全源图；新运行记录新 provenance |

稳定主键不等于 exactly-once；SQL ID 还有截断哈希碰撞的既有风险，不在本次调度改造中声称解决。输入或 Dim 源值改变时，新建运行发布的是新内容，不是原输入的确定性重试。自动任务重试本期关闭，后续须具备不可变输入、attempt 记录及外部结果核验才讨论。

### 6.3 取消与进程中断

本期不新增运行取消入口，关闭页面不取消后台任务。不能调用 Future.cancel() 就声称外部写入已取消，也不强杀运行中的线程。

进程退出/失联时，先确认所有可能的旧执行者已停止，再用 [resolve_orphaned_run.py](../metaweave/scripts/resolve_orphaned_run.py) 的 publish 模式预览并人工应用：running→failed，pending→blocked，已有终态不变；全部步骤终态但 run 未汇总可 `--finalize-only`。脚本不核验/撤销外部写入；先核对结果再新建运行重发。源占用以数据库活动运行状态为准，不能仅因内存线程消失自动释放。

若阻塞来自采集侧孤儿 pending/running 运行，确认旧执行者停止后，使用同一脚本的 `collection` 模式预览及收尾；否则第 5.2 节的发布创建拒绝会持续生效。

未来若需要取消，须引入持久取消请求，在停止派发后等待在途结束；已成功不回滚，未启动记 blocked 并注明用户取消，或单独迁移 cancelled 状态及 API/UI/约束/汇总。本期不混入该状态迁移。

## 7. 一致性、兼容与风险

1. 三库没有全局事务；串行也有新旧混合，并行会改变混合窗口及可见顺序。保留 6 的“每源当前内容、按步替换、失败不覆盖成功历史视图”的契约，不能把最新成功历史视图当作目标内容完整性证明。NL2SQL 可能在发布中读到不同代数据；本期不承诺原子切换，验收必须接受此现有一致性等级。若业务要求整次可见性原子切换，则应暂停该上线并改为版本化内容与统一读版本，不用三队列方案冒充解决。
2. Domain 冻结清单与 Rel 文件 Domain 可能不同；采集输入允许来自多个 collection_run，继续记录逐文件来源，不能合并为虚构统一采集运行。
3. 串行开关使用原全局顺序，保留 default/custom、子集、不自动补选、运行状态和既有 API 字段；新保护与状态修复在 serial 下也启用。开关及计划按创建时冻结并持久化，后台不重读部署开关改变该运行计划；进程重启不自动续跑旧 pending/running。
4. UI 确认区以步骤标签及资源分组说明“按约束调度”；结果沿用 `list_run_steps()` 的 started_at、step_name 排序，支持多个 running，不用展示排列推断依赖。失败/部分成功须指出可能已有外部内容更新。
5. 日志 `_CURRENT_STEP` 当前为进程全局字符串，`StepFilter` 读取实时全局值。与 10.1 协同改为 ContextVar、token 恢复、Filter 用 record.step；复用 `services/logging_manager.py::submit_with_context()` 传播到线程任务，不能同一 Context 同时运行两次。API 目前按模块记录，不能误称已发生 API 步骤文件串写；保留 CLI 线程传播测试避免回归。
6. 锁序分两条互不嵌套的入口：创建发布为“全局准入 transaction advisory 锁 → 源→工作区→作业→运行行锁”，不在创建事务取目标锁；执行时删除先持任务 advisory 锁，再按“目标 advisory 锁 → 目标保留行短事务 → 源→工作区→作业→运行/任务行锁”推进，发布跳过任务 advisory 锁。目标保留行事务先提交后再开层级行锁事务，不能反向嵌套；多目标按规范化目标键排序，或逐目标处理不同时持有。任何入口不得在持有源/工作区行锁时等待目标锁。各通道 claim/prepare 与 PG 内容事务共用源锁，等待按第 4.1 节处理；全局名额不消除该串行点。目标锁连接与业务 session 分离，外部 I/O 不长持行锁。

## 9. 测试与验收标准

调度单测使用事件/屏障控制 worker，禁止主要依赖 sleep；真实数据库集成测试使用隔离测试源和目标，不操作生产内容。

1. 全量八步：三个通道可重叠；PG 与 Milvus 各通道始终最多一个 worker、保持原相对顺序；完成一个任务立即推进可就绪后继；总上限 1/2/3 均正确。
2. 所有有意义的子集、乱序请求、default/custom：选择范围不变，不补选；只跑 Rel 不要求先跑 PG Domain/JSON；只跑 SQL 不要求先发布 Rel；保留输入准入错误码。
3. 普通业务失败不阻断仅有顺序约束的后继；未来模拟数据边失败应仅阻断数据后继。全部步骤终态才汇总，部分成功及无成功分别按既有公式。
4. 同一 run 重复后台调用、重复 step 投递、两进程同时认领：publisher 只执行一次，终态不能被旧结果覆盖。
5. 同源不同工作区、不同发布作业并发创建：至多一个 pending/running 获准；冲突不留额外运行。不同源发布遵守全局名额和 Neo4j 目标锁；首次建 Milvus 集合不竞争失败。
6. 采集与发布同时创建、采集已 pending、配置保存与发布同时认领、登记变更：验证双向锁检查，无检查后写入窗口；无关工作区读操作不受限；删除状态守卫继续有效。
7. PG 内容失败回滚且状态不 success；JSON 表/列一致。Milvus 批次失败/未确认/清旧失败保留准确统计，不声称旧内容完整；新运行完整重发可收敛。Neo4j 中途失败旧图保留，未知提交按未知处理，计数核验有效。
8. 注入外部提交成功但 PG 状态失败、认领数据库故障、多个 Future 同时异常、汇总失败：停止派发、在途 join、不虚报 success；运行占用保持，恢复脚本正确收尾。
9. 终止进程构造多个 running + pending + success；离线脚本预览不改数据，应用保留终态，finalize-only 拒绝未完成步骤；确认旧执行者停止前禁止重发。
10. 日志交错、线程上下文恢复、CLI 嵌套线程池、API 模块日志均正确；页面刷新显示多个 running 与稳定的响应顺序。
11. 串行/并行对相同冻结文件对照：目标业务内容与数量一致（排除 run_id/时间），跨库无遗漏。Dim 使用固定测试数据，另测运行中数据变化只承诺现有实时读取语义。
12. 性能验收记录 ready/claim 等待/业务 I/O 各阶段、源行锁持有时间及三通道起止、总耗时、平台/源库连接峰值、Embedding 限流、Milvus/Neo4j 锁等待及失败率；独立耗时 worker 确实重叠，真实负载下无错误率恶化才扩大灰度。不设缺乏基准的固定加速倍数。

13. 跨进程集成测试必须使用至少两个独立进程和数据库连接，以屏障对齐准入：同源不同工作区争抢、不同源争全局名额、发布与采集同时创建。上限 1 时至多一个 pending/running，失败请求无额外 run/step，409 错误码及运行定位正确；成功终态/离线收尾后容量释放。模拟孤儿 pending 时验证不同源也被容量拒绝。
14. 长时间持源行锁，确认其他通道 claim/Rel prepare 等待、超时按阶段记 blocked/failed；解除锁后观测真实业务 I/O 重叠，不能只凭 Future 或 started_at 证明并行。状态写回也失败时不虚报已终结。
15. 目标锁连接断开及平台库重启：旧执行者停止后续写入、在途结果未知不报 success；另一进程即使取得 advisory lock，也被持久 owner 拒绝。验证发布/删除统一锁序、不死锁；人工核验旧请求结束后才能清 owner，不允许旧执行者覆盖新终态。
16. 分开注入 Neo4j 回调内异常与提交阶段瞬态异常：前者核对回滚与包装结果，后者允许 driver 重执行或提交未知，不误作确认未写入。未来移除 Milvus 人为顺序边的计划版本需测试容量放开确实重叠，旧运行仍按原计划串行。

## 10. 实施顺序与回滚

1. 先补充串行基线测试、观测耗时，核验全部入口及部署目标；确认运维没有绕过受管入口的写入。
2. 实现 schema 迁移及计划快照、源/工作区和目标保留、全局名额准入、原子认领、可靠状态提交和日志隔离，仍 serial，先验证安全闭环。
3. 实现计划及三个有序资源通道，开关默认关闭；全局活动运行名额先为 1，完成失败/中断和跨进程锁测试。
4. 在测试源及隔离库灰度 parallel，完成第 9 节验收，比较实际收益；通过后逐步放开不同源运行名额，保留每源互斥和 Neo4j 目标锁。
5. 同步 6/6.2、运维说明及 UI 执行约定；再考虑同 Milvus 不同集合并发或更细资源预算，不提前放开。

回滚：关闭新运行的 parallel 开关；活动运行排空后回退调度代码，不强停外部写入。进程已丢失则先离线收尾，核对外部内容后用 serial 新建运行重发失败/未知步骤。保留新增审计列和目标保留表，不在回滚时删除仍使用的数据；离线收尾与目标 owner 核验释放分别完成。调度回滚不恢复目标内容，必须单独核对三库；不执行集合 drop 或全库清理。只要部署中仍有新版并行运行，不部署不识别互斥协议的旧写入进程。

## 11. 设计边界及需确认事项

当前没有阻碍文档设计继续的不可验证硬依赖。实施前需确认：业务接受发布中的跨库混合可见性；初期全局名额 1 与同源运行 409 符合使用方式；同源互斥包含 pending 占用，进程在返回 202 后、后台启动前崩溃也需人工收尾才能释放整个源，运维接受此操作成本；全局名额为 1 时，孤儿运行会阻塞所有源，运维接受全局准入 409 与人工处理成本；同工作区采集/发布双向保留将拒绝创建、认领或配置保存，业务接受第 5.2 节的 409 提示及不排队体验；目标锁失效后持久 owner 阻止自动接管，运维接受核验外部请求后人工释放；取消/自动恢复不在本期；生产目标容量以实测确定。这些是上线验收条件，不是已经获得业务确认。若要求原子可见性或绕过平台写入无法停止，应暂停实施并升级设计。

- **修改建议**：明确审计载体（新增运行级字段/独立表，或仅写日志）；若确需新增，修正“无必须新增”的表述。

### 7. 【建议】Milvus 通道的 `order_predecessors` 与容量 1 耦合，未来放开容量需同步删除

- **位置**：§4.2（第 80 行）、§10（第 193–194 行）。
- **源码依据**：`table_schema → dim_value → sql` 在 §3 已确认无数据依赖；三集合名称也不同（`configs/metadata_config.yaml:523-552`）。当前串行仅由“容量 1 + 相邻 order 边”造成。
- **原因**：未来放开同一 Milvus 目标加载数时，若保留这些 order 边，三步骤仍会被串行，无法获得预期收益；文档未明确这些边是第一阶段降级产物。
- **修改建议**：注明容量放开时改为仅资源令牌、不保留 order 边；§9 增加开关切换后的调度断言。

### 8. 【建议】§9 缺少跨进程创建/名额/锁的集成测试项

- **位置**：§9 第 4、5 条（第 178–179 行）。
- **源码依据**：源级互斥、全局名额、输入保留的关键是跨进程数据库锁；当前 #5 只写“并发创建”未区分线程/进程，#4 只覆盖重复投递/认领。
- **原因**：线程内测试无法暴露两个独立数据库连接/进程同时通过预检和创建窗口的问题。
- **修改建议**：增加两条独立数据库连接或两个进程的并发创建测试（同源不同工作区、不同源达到名额、发布与采集同时创建），断言至多一个 pending/running 且无额外运行、锁等待可控。

### 9. 【建议】§6.2 对 Neo4j driver 重试的表述可更精确

- **位置**：第 124–130 行。
- **源码依据**：`_execute_replacement_transaction()` 将回调内异常统一包装为 `_RolledBackWorkError`（普通 `Exception`，`cql_loader.py:449-465`），driver 的瞬态重试通常不会重试回调内异常；提交阶段在包装外的瞬态失败仍可能触发 driver 重试。`Neo4jConnectionManager.initialize()` 未设置 `max_transaction_retry_time=0`（`services/db/neo4j_connection.py:36-46`）。
- **原因**：文档“事务回调可能重试”作为保守结论成立，但容易让实施者误判“回调内失败会被自动重试”，影响重试/幂等测试设计。
- **修改建议**：区分“提交阶段可能重试”与“回调内异常已被包装、通常按确认回滚处理”，并据此调整 §9 第 7、8 条的注入用例。

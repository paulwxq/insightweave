**失败原因与修复。** verify 步骤没有把 `github.token` 传给核验程序，它只能匿名读取本次运行的记录，私有仓返回 404。修复提交 `b2994363389da036a77ec924b41fe22ee4508f9c` 让 verify 步骤传入令牌，并让核验程序在缺少令牌时于任何查询之前停止；新增 2 个单元测试和 2 项结构检查。

**由此得到的一条规则。** 控制代码或工作流修复后，要发出新的请求（重跑通知运行）。重跑绑定旧控制提交的私有运行，不会读到新代码。

**部署后核对**（对照部署前快照，全部通过）：

- `deployment.json`：phase 为 ready，current 为 `b750cef7afa4-d45330068597-1`，previous 为 `e70391fd4e92-44232946662-1`。
- frontend、nl2sql、metaweave 已换成新镜像并健康；postgres、neo4j、milvus、attu 的容器 ID 和启动时间未变。
- 快照清单的 `source_sha` 等于合并提交；三个应用运行中的镜像与清单一致；前端产物含提交号前 7 位。
- 首页、`/query`、`/api/v2/health`、`/openapi.json` 均返回 200；没有维护标记和候选检查容器。

## 5. 验证范围

- 公开仓云端 CI：PR 与 main 上的 `InsightWeave CI`（五个套件加 `ci-required`）。
- 生产机完整 `ci.sh` 演练两次：`64c27cd`（2026-11-23）和 `eb5da77a`（2026-11-24），都到候选清单为止，不调用 `deploy.sh`。

- 暂停自动发布、手动回退、恢复自动发布：按 doc 15 §8.5 完整走了一遍，见 §10。

## 6. 与设计的已知偏差

- **触发令牌**：实际使用的是经典 PAT（范围 `repo`），不是 doc 15 §6.1 设计的“仅限部署仓、Actions 读写”的细粒度令牌。这是维护者知情的选择；权限范围比设计宽。首次运行证明它可以触发部署。
- **私有仓代码的审核**：首版只经过替身测试和作者自审，首次真实运行暴露了 §3 的缺陷。该缺陷的修复经过独立复核。
- **演练的候选清单**：第一次演练（`64c27cd`）没有留存候选清单文件；第二次演练（`eb5da77a`）已留存。

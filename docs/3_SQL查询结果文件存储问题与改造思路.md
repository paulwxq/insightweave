# 3. SQL 查询结果文件存储问题与改造思路

记录日期：2026-10-17。状态：**问题分析与改造方向讨论，尚未详细设计或实施**。

本文记录 db_deepagent 当前查询结果落盘的实现、面向多用户平台的局限，以及可考虑的改造思路。本文不提供数据库 DDL、最终接口、迁移脚本或开发计划，不代表已确认采用某个存储实现。

关联文档：[0_项目整合讨论与共识.md](0_项目整合讨论与共识.md)、[2_NL2SQL_Vue接入设计.md](2_NL2SQL_Vue接入设计.md)。

## 1. 问题背景与范围

InsightWeave 将由单机开发与验证逐步走向统一 Vue、多数据源及多用户使用。用户提出：SQL 查询结果持续以“每个结果一个目录、两个文件”的方式保存，在并发和数据积累后，读取、清理、容量管理及多实例共享需要重新考虑。

本次关注的是 **Agent 查询结果的内部持久化**，不是日志、MetaWeave 的采集 output，也不是要求 Vue 回放历史表格。

当前已确认的 Vue 范围保持不变：

- 当前页面新执行的查询可以展示答案、SQL 与表格。
- 查看历史记录，每轮只返回问题和答案，不返回 SQL、表格或结果引用。
- Agent 多轮上下文继续使用 checkpoint；结果存储调整不能破坏续聊、证据沿用及后续分析。

即使历史界面只显示问答，Agent 仍可能读取上一轮查询结果进行计算，因此不能简单删除结果持久化。

## 2. 当前代码实际保存什么

### 2.1 三类存储各自承担职责

| 存储 | 当前内容 | 主要用途 |
| --- | --- | --- |
| LangGraph checkpoint | 消息、SQL 校验与执行账本、分析账本、证据和结果引用等；工具消息可能含预览或部分读取结果 | 恢复 Agent 状态并继续多轮运行 |
| LangGraph Store | 会话/线程记录，按条件归档的问题、结构化答案、SQL 证据和 result_ref 等 | 会话定位、问答归档、引用追踪 |
| 项目自定义 ResultStore | 实际保存的结果行，以及 SQL、列、归属和完整性元数据 | 结果分页、计算、值引用及证据复用 |

**ResultStore 与 LangGraph Store 是不同的组件。** 当前 checkpoint 的结构化执行账本不保存完整 rows；工具消息中即使出现了一些行，也不是完整结果的稳定存储契约。

依据：[状态结构](../nl2sql/src/modules/db_deepagent/state.py)、[ExecutionRecord 等模型](../nl2sql/src/modules/db_deepagent/schemas.py)、[Runner](../nl2sql/src/modules/db_deepagent/runner.py)、[问答归档](../nl2sql/src/modules/db_deepagent/persistence/archive.py)。

### 2.2 当前文件结构与写入流程

默认 workspace 为 `var/db_deepagent`，可由 `DB_DEEPAGENT_WORKSPACE` 覆盖。在 NL2SQL 模块目录启动时，默认结果位置为：

```text
nl2sql/var/db_deepagent/results/
└── res_<唯一编号>/
    ├── meta.json
    └── rows.jsonl
```

- `meta.json`：result_ref、session_id、thread_id、request_id、run_id、数据源指纹、实际 SQL、模板 SQL、列信息、已保存行数、截断标记、时间、校验摘要及来源关系。
- `rows.jsonl`：每行一个结果行数组，按现有编码规则处理 Decimal、日期等值；不能将它视为对任意数据库类型的完全无损备份。
- 保存时先写临时目录，再原子重命名；这已避免直接暴露半写入的目录，但并不意味着文件与 checkpoint/Store 归档形成了同一个事务。

[SQL 管线](../nl2sql/src/modules/db_deepagent/services/sql_pipeline.py)执行成功后调用 `ResultStore.save()`，将 result_ref 写入执行账本，只向模型返回有限预览。[保存实现](../nl2sql/src/modules/db_deepagent/services/result_store.py)负责生成上述文件。分析工具也可能将派生计算结果保存为新的 result_ref，目录数量不只取决于用户提问次数。

当前配置的普通查询最大保存行数为 10,000，初始预览为 20 行；这是行数限制，不是结果字节数或平台总容量限制。具体值见 [运行配置](../nl2sql/src/modules/db_deepagent/config/db_deepagent.yaml)。

### 2.3 文件用于当前执行链，不只是历史展示

[结果工具](../nl2sql/src/modules/db_deepagent/tools/result_tools.py)通过 ResultStore 继续读取数据，并执行聚合、Top N、比较等操作；[SQL 管线](../nl2sql/src/modules/db_deepagent/services/sql_pipeline.py)也可以引用先前结果中的列值。保留 result_ref 的意义是访问当时已保存的数据，而不是每次重新查询变化后的业务库。

因此，当前设计采用了“执行状态与结果数据分离”的方式；文件是结果数据的一种实现选择，并非 checkpoint 的技术要求。

## 3. 面向平台运行的主要问题

以下分析来自代码结构，尚未压测；不据此断言某个并发数或目录数一定达到瓶颈，也不将所有文件存储方案一概判定为不可用。

### 3.1 分页前仍加载整个文件

`ResultStore._read_encoded_rows()` 读取整份 rows.jsonl、计算摘要并解析全部行，`read_rows()` 随后才按 offset/limit 切片。

请求一小页也可能承担整个结果的读取和解析成本。结果较宽、并发较高或同一结果反复翻页时，磁盘读取、CPU 和内存开销都值得关注。完整性检查也使用整文件读取，不只是分页接口的问题。

### 3.2 清理依赖目录扫描

[维护模块](../nl2sql/src/modules/db_deepagent/persistence/maintenance.py)遍历结果目录并读取 meta.json，再按会话组织清理。结果长期积累后，扫描、元数据读取和排序的成本会增长，容量统计及按源/会话定位也需要额外工作。

### 3.3 多实例共享与运维成本

如果不同服务实例使用各自的本地磁盘，实例 A 保存的结果不保证能由实例 B 读取。增加共享文件系统可以解决部分可见性问题，但还需安排容量、权限、备份、清理协调与故障处理；当前实现没有交付这些部署能力。

相对 workspace 还要求启动工作目录稳定；未来部署与迁移必须保留实际结果位置，不能只备份 PostgreSQL 就认为所有可复用结果都已备份。

### 3.4 文件与数据库归档分开提交

结果文件、checkpoint、Store 归档在不同步骤保存。运行中断或归档失败可能留下文件或不完整引用，需要识别孤儿结果、恢复失败状态和安排清理。原子重命名解决单份结果的可见性，无法自动解决整个运行的跨存储一致性。

### 3.5 有保留期，但不能仅凭天数控制总量

当前配置包含 checkpoint 30 天、问答归档 180 天、结果 30 天；维护代码还会保护仍被 checkpoint、携带证据或归档引用的结果。读取保护信息失败时也可能跳过删除。

这套保护不能省略，否则会破坏后续分析和证据复用；但也意味着“配置 30 天”不代表结果最多只占用 30 天的数据量。平台化仍需考虑总容量、按源/会话配额、单结果字节上限、清理执行频率及长期引用释放。

## 4. 建议改造方向：独立的数据库结果存储

建议优先评估将 ResultStore 的底层数据迁至 PostgreSQL 独立结果表。保留现有执行状态与结果数据分离的原则，不把完整表格塞进 checkpoint 或每轮工具消息，也不简单将所有结果作为一个巨大的 LangGraph Store value。

### 4.1 元数据与结果数据分开

概念上区分两类数据：

- **结果元数据**：引用、源/会话归属、SQL、列定义、行数、完整性信息、生成时间及生命周期。
- **结果数据块**：按有序块或行段保存实际值，按 result_ref 和范围定位读取。

具体采用逐行还是分块、块大小与索引如何设计，留待详细设计和实测决定。可评估 JSONB 保存结构可变的行块，但不能假设“改成数据库 + 单个巨大 JSONB”自然解决所有读取和并发问题。[PostgreSQL JSON 文档](https://www.postgresql.org/docs/current/datatype-json.html#JSON-DESIGNING)也建议将 JSON 文档大小控制在可管理范围。

分页应只读取所需范围。完整性校验可以考虑结果级与块级配合，避免每读一页都扫描全部结果，同时保留现有值编码与来源校验语义。

### 4.2 与现有两类数据库职责区分

建议使用 **NL2SQL 的持久化数据库**中新建的独立结果表/存储区域，并评估连接池与资源隔离。不要写入业务源库，也不要通过只读的数据源登记连接写入 MetaWeave 平台库。

- `PLATFORM_DB_*` + `SOURCE_CREDENTIAL_KEY`：只读取得登记数据源连接并解密。
- LangGraph 持久化连接：checkpoint、Store，以及未来经设计的新结果存储。

使用同一个 PostgreSQL 数据库不等于结果表、Store 和 checkpoint 自动成为一个事务。详细设计仍需明确结果写入完成标记、失败补偿、引用建立时机及孤儿结果处理。

### 4.3 尽量保留上层服务契约

保留 result_ref 及保存、读取元数据、分页、完整性验证、列值读取和删除等业务语义。Agent、工具与后续 Vue API 通过统一结果存储接口访问，不依赖某个磁盘路径或直接访问结果表。

主要改造集中在 ResultStore 的底层实现、装配和维护流程；SQL 管线、分析工具、结果占位符和证据复用需要做兼容验证，不能只替换 save/read_rows 就认定完成。

### 4.4 容量与保留策略一起处理

数据库存储也不会无限扩容。应同时评估结果行数/字节数限制、按会话或源的配额、并发写入限制、过期清理、仍被引用结果的保护及存储指标。当前只有 guest，若以后增加真实用户，再引入用户维度配额。

随着数据量扩大，可进一步评估分区清理；当前不预设必须分区。只有在数据规模确有需要时再讨论对象存储等方案，避免此次同时引入多套基础设施。

## 5. 改动范围与待讨论事项

初步判断为**中等规模的存储改造**，不是重写 Agent；尚不能在没有详细设计、兼容测试与数据规模信息时给出确定工期。

需讨论并明确：

1. 是否采用 PostgreSQL 作为首选结果后端，以及是否与现有 LangGraph 持久化库同库部署。
2. 已有文件结果是否需要迁移。保留旧 result_ref 时需要迁移或兼容读取；不能删除文件后认为 checkpoint 会补出原数据，也不能靠重新执行 SQL 伪造旧快照。
3. 结果保留时长、总量限制，以及引用长期存活时的处理方式。
4. 多源/并发压力下的性能目标和验证数据，作为存储方式与分块方案的依据。
5. 改造与 Vue 接入的顺序：建议在多实例平台验收前完成存储方案评审；doc 2 中的结果 API 应依赖存储服务契约，避免绑定文件实现。

本稿建议先确认方向，再单独编写详细设计；不在本稿直接决定表结构、增加存储配置开关或执行数据迁移。

## 6. 与 doc 2 审核的关系

doc 2 描述 Vue 接入的产品范围、Web 适配、平台选源和多轮/历史边界；本文描述结果存储的内部实现问题。审核 doc 2 时，应检查它是否把现有文件实现误写成已确定的长期平台架构，或遗漏结果存储改造对资源生命周期、源归属和 API 契约的影响。

本文不改变已经确认的 D3：**Vue 历史只返回问题和答案，不返回 SQL 或表格。** 不能借结果存储改造扩大历史界面范围。

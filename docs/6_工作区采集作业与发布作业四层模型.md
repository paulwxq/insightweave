## 1. 四层关系

```text
source_id                         数据来源
  └─ workspace_id                 文件产物的隔离与共享边界
       ├─ collection_job_id       保存采集步骤和默认参数
       │    └─ collection_run_id   一次实际采集
       └─ publish_job_id          保存发布步骤和默认设置
            └─ publish_run_id     一次实际发布
```

| 层次 | 身份与职责 | 是否产生新 ID |
| --- | --- | --- |
| 数据源 | `source_id` 标识受管数据来源；一个工作区归属一个数据源。 | 登记数据源时产生。 |
| 工作区 | `workspace_id` 标识一个独立产物目录；同一工作区中的运行可以复用上游文件。 | 创建工作区时产生。 |
| 作业 | `collection_job_id` 与 `publish_job_id` 分别保存可复用的步骤和默认参数，并各自管理配置版本；两者都归属一个工作区。作业 ID 不承担产物目录隔离。 | 首次保存对应作业时产生，修改配置时保持不变。 |
| 运行 | `collection_run_id` 与 `publish_run_id` 分别标识一次实际执行，记录本次步骤、参数、状态及实际输入。 | 每次执行都产生新的运行 ID。 |

`source_id` 字段名保持不变，其数据库类型由现状 UUID 改为 `text`，数据库来源使用序列生成的 `db_src_1`、`db_src_2` 等短 ID；不迁移旧 UUID。运行 ID 继续使用 UUID；`workspace_id` 沿用 `ws_1` 一类短 ID。采集作业使用 `coll_job_1`、发布作业使用 `pub_job_1` 一类短 ID；已讨论的建表语句及存量表处置范围集中记录在 [6.1_建表语句汇总.md](6.1_建表语句汇总.md)。本文不再另设一个与 `publish_run_id` 并列的 `publish_id`。

## 2. 工作区与目录

创建工作区时必须选择一个已登记的 `source_id`；一个数据源可以有多个工作区，一个工作区只属于一个数据源。WebUI 创建工作区后建立 `./output/<source_id>/<workspace_id>/`。其下按步骤或产物类型组织 `db/`、`ddl/`、`json/`、`md/`、`domain/`、`dim/`、`rel/`、`sql/`、`cql/` 等子目录。目标步骤名 `dim` 与目录 `dim/` 一致，步骤名 `sql` 与目录 `sql/` 一致；现有步骤名 `dim_config`、目录 `dim_config/` 和 `sql-rag/` 均须随改造更名。创建工作区可以先于创建作业和执行运行。采集作业、发布作业都引用同一个工作区身份，不再各自创建一套隔离的产物目录。

同一工作区可以有多个采集作业。例如完整采集作业生成 `json`，修复作业只重新生成 `rel`；修复运行可以读取工作区已有的 `json`。另一个工作区即使绑定同一数据源，也不直接复用这些文件。生产、测试等用途可以使用不同工作区。

同一工作区内的采集作业先后更新同一步骤目录时，以该目录顶层唯一的当前采集结果 marker 判断本期产物是否可用，具体规则见 §4.1。marker 中的 `collection_run_id` 表示目录产物的采集来源，可据此查询采集作业及其配置版本。manifest 只记录实际处理的文件或下游目标，不要求文件校验值、独立产物版本或快照。写入前按下文统一规则备份当前步骤目录的旧文件；备份失败时记录告警并删除旧文件，继续生成，不因备份失败阻断运行。现有执行冲突保护继续保留，本期不扩展复杂并发写入或历史重放机制。

## 3. 采集作业的保存与运行

创建采集作业时先选择工作区，再保存允许执行的采集步骤和默认参数。当前明确的参数是 Domain 生成的 `--generate-domains --description` 默认输入；工作区内已有 `db_domains.yaml` 时，其 `database.description` 仍按 [5.4_Domain采集步骤变更方案.md](5.4_Domain采集步骤变更方案.md) 作为生效值。保存作业不要求当时已有产物。

打开采集作业后，可以“按默认配置执行”，也可以“手工选择步骤执行”。手工运行只可选择该作业当前配置允许的步骤子集，临时修改参数只影响本次运行，不能从运行页面保存回作业。每次执行生成新的 `collection_run_id`；后端验证步骤后进行拓扑排序，纠正违反依赖关系的顺序；对同一轮可执行且互无依赖的步骤，优先采用请求传入顺序。只排序本次选中的步骤，不自动补选其上游步骤；未选上游的可用性仍须按工作区产物检查。运行记录保存引用的采集作业版本、实际步骤、有效参数和逐步骤结果。

采集步骤白名单为 `db`、`ddl`、`json`、`md`、`domain`、`dim`、`rel`、`sql`。本次所选步骤之间的依赖边为：`ddl → json`，`ddl、json → md`，`md → domain`，`json → dim`，`json、domain → rel`，`md、domain、rel → sql`；`db` 无依赖。每轮从当前可执行的步骤中选请求传入顺序最靠前者；`dim` 与 `rel` 无相互依赖，无需强行规定先后。典型完整链路为 `db ∥ ddl → json → md → domain → (dim ∥ rel) → sql`。此阶段只排序，未来是否并行执行另议。

**现有能力与改造复用：**后端 `normalize_collection_steps()` 已实现单个请求中多个步骤的非空、白名单、去重和依赖拓扑排序。例如收到 `md、ddl` 时，会先排 `ddl` 再排 `md`；未同时选中的依赖步骤不会被自动补选。这套排序规则在本次改造中直接复用，不需要新增或重写排序模块。当前 WebUI 先用 `executionOrder()` 排序，再逐个发送只含一个步骤的请求；这是现有页面的调用方式。引入统一的 `collection_run_id` 时，运行入口应把本次所选步骤作为一组交给现有后端排序函数，再执行并记录各步骤结果。前端排序可继续用于页面交互，但不能取代后端已有的校验。

编辑并保存采集作业的执行配置时，新增不可变版本；已有运行继续指向原版本。定时配置绑定指定的采集作业版本，新版本保存后不自动切换原定时配置。采集作业的配置版本不等于工作区产物版本。

## 4. 发布作业的保存与运行

创建发布作业时**先选择工作区**，再保存允许或默认发布的步骤及适用的默认设置；作业可以在产物尚未齐备时先保存。发布作业读取的是该工作区当前通过校验的采集产物，不要求绑定唯一的采集作业或唯一的 `collection_run_id`：不同发布步骤可能读取不同采集运行留下的文件。

发布步骤与采集步骤并非全部一对一。例如 `table_schema` 可依赖 `json` 和 `md`，`dim_value` 需要采集步骤 `dim` 在 `dim/` 中生成的 `dim_tables.yaml`，还需要其中的表及字段配置有效。保存“发布 `dim_value`”只表示发布意图，不保证此刻已经可以发布；具体输入由步骤到产物的依赖规则和工作区实际状态决定。

手工执行发布时，可以采用作业默认步骤，也可以在该发布作业允许的步骤内选择子集。执行前展示当前产物、来源与校验结果；缺少或不合格的已选步骤应明确阻断，不能在后台悄悄缩减用户确认的范围。后端对所选步骤按固定顺序执行，每次实际发布生成新的 `publish_run_id`。临时选择和参数调整只影响本次运行；编辑并保存发布作业的默认配置才形成新的发布作业版本。定时配置绑定指定版本，更新作业不自动改变已有定时任务。

`publish_run_info` 记录本次发布作业及版本、触发方式和整体状态，工作区经发布作业查询；`publish_run_step` 记录本次各步骤的实际输入、来源采集运行、有效参数、结果和错误。一次发布的输入可能来自当前工作区内的多个采集运行，不能只用一条 `context_collection_run_id` 代表全部输入。目标表结构及 manifest 格式见 [6.1_建表语句汇总.md](6.1_建表语句汇总.md)。

各工作区、各步骤最后一次成功发布通过 6.1 §12 的 `public.vw_workspace_latest_successful_publish` 查询；已发布内容行的实际写入来源按 6.1 §10.1 保存。后续失败不覆盖此前成功记录，本期不另设 current 标记或汇总表。接受下游替换中途失败后可能出现新旧混合的局限，以失败步骤的状态和消息提示重新发布。

**下游发布范围已确认：同一数据源只保留一套当前内容，继续沿用现有按源主键及替换方式。**工作区只隔离文件，不进入 PostgreSQL 内容主键或 Milvus、Neo4j 的发布隔离身份。同源不同工作区向同一目标发布时，后一次成功发布按对应步骤原有范围更新当前内容；未发布的步骤不随之替换。工作区成功发布视图保留各工作区的历史，不表示每个工作区在下游仍各有一份内容。源级最后成功发布在同源工作区中按 `source_id + step_name` 选择最近成功步骤；内容行仍以自身 `publish_run_id` 记录实际来源。五张内容表的主键及完整目标 DDL 见 6.1 §14～§18。

### 4.1 当前工作区产物的判定

1. 仅检查当前 `workspace_id` 中所选发布步骤实际依赖的采集产物目录，不查询其他工作区，也不要求该工作区全部历史运行成功。例如 `dim_value` 检查 `dim/`；Rel 发布需要的 JSON、Domain、Rel 可以由当前工作区内不同采集运行生成。
2. 每个所需采集产物目录只读取顶层唯一的 `.coll_run_id_...` 当前结果 marker，不按文件名时间排序。marker 为 `success` 时继续检查必要文件；为 `failed` 或没有采集结果 marker 时，该目录视为未采集成功，不允许发布。`.backup/` 中的历史 marker 不参与判定，也不自动读取备份中的旧产物。
3. 发布过程只读取采集 marker，不生成发布 marker；发布结果保存在 `publish_run_info`、`publish_run_step` 及相应 manifest 中。发布过程中生成的 `cql/` 等辅助目录不属于需要预先存在采集成功 marker 的目录。
4. 在 marker 判定之后，保留现有必要文件、内容、配置及依赖产物是否齐备的校验，并将原 `job_info` 状态读取适配为本工作区的采集产物判断。跨步骤采集完成时间的新鲜度检查取消，具体见 §4.3；不新增强制校验值、完整产物版本或跨工作区检查。缺少 marker 表示当前目录不具备发布条件，不据此改写历史采集运行记录。
5. marker 由专门的读取逻辑识别；普通产物扫描和文件 manifest 一律忽略名称以 `.` 开头的文件及目录，避免把 marker、`.backup/` 和临时文件当作待发布产物。

### 4.2 manifest 的本期用途

manifest 是运行步骤表中的可空 JSON 清单，不是另一个文件。`input_manifest` 在实际读取文件后记录工作区相对路径及其所在目录采集 marker 对应的 `collection_run_id`；`output_manifest` 在采集步骤成功后记录本次实际生成并通过检查的文件；`target_manifest` 记录发布实际写入或尝试写入的下游目标，发布结果由步骤的 `status` 和 `message` 表达。

有对应内容时填写，未执行、尚未取得清单或没有文件输入时可为 SQL `NULL`。manifest 用于查看本次运行实际处理范围，不作为 §4.1 的发布准入依据，不要求校验值、文件快照或完整历史追溯。用户编辑文件后，来源采集运行只说明目录产物的生成来源，不表示当前文件仍是该运行的原始输出。具体 JSON 格式见 6.1 §11。

### 4.3 发布页展示采集产物时间，取消自动新鲜度检查

WebUI 在每个发布步骤后展示其对应采集产物目录的生成时间，取自该目录唯一采集 marker 中的完成时间，按 `Asia/Shanghai` 展示。该时间是采集步骤产物的生成时间，不是文件修改时间、整次采集运行结束时间或发布时间。一个发布步骤依赖多个采集目录时，按目录分别标注时间，供用户自行判断是否需要重跑采集步骤。

**发布时不自动比较各采集步骤的完成时间，不据此产生“产物过期”告警，也不据此阻断发布。** 现有 Rel 发布中“Rel 完成时间必须严格晚于 JSON、Domain”的新鲜度检查在本次改造中移除，不降级保留为自动告警，也不新增时间差阈值。

必要文件、内容和配置检查通过时，允许使用较早生成的 Rel 和较新生成的 JSON、Domain 发布；关系结果可能未反映上游最新变化。例如重新采集后出现新的关联关系，但没有重跑 Rel，发布后的图关系可能遗漏这些变化。是否重跑由用户根据页面展示的采集时间判断，系统不因时间先后自动告警或阻断；关系端点缺失等已有内容校验仍保留，不能理解为所有新旧产物组合都可以发布。

取消新鲜度检查不影响 §4.1 的必要检查：采集 marker 缺失或为失败、必要文件缺失、内容或发布配置无效时，仍按原约定处理。采集执行顺序继续按步骤依赖关系排序；执行顺序校验与发布前比较历史产物时间是不同功能。现有发布过程中对重跑或编辑的冲突检查按 §5 适配保留。

## 5. 发布前的编辑与检查

`domain`、`rel`、`dim_value` 等产物可能需要在发布前人工编辑。其中 `dim_value` 的 `dim_tables.yaml` 要为相关表指定有效的 `embedding_col`；文件缺失、空表或未配置完整时应阻止该步骤发布。用户编辑并保存工作区文件，是**准备工作区产物**，不等于修改发布作业的默认步骤，也不自动创建新的发布作业配置版本。

本期沿用现有编辑保存和发布前校验流程。例如 `dim_value` 的配置未完成时，用户先编辑，再重新发起发布。不新增独立的人工确认版本或确认失效管理；调度和自动重新审核不在本期范围。

现有代码对重跑和文件编辑已有的冲突检查继续沿用，并按新工作区模型适配。manifest 记录实际读取的文件，不承担输入锁定。本期不新增通用的输入快照、强制校验值复核或旧发布重放机制；若以后需要精确恢复当时文件内容，再单独设计。

## 6. 采集结果标志、整体状态与文件备份

**采集 marker 唯一性：每个采集步骤目录顶层最多保留一个采集 marker，`.backup/` 中的历史 marker 不计入。写入新 marker 前清除顶层已有的采集 marker；正常备份时，旧 marker 随旧产物移入 `.backup/`。发布直接读取唯一的当前采集 marker，不按时间排序；没有 marker 则不可发布。** 清除旧 marker 只针对采集 marker，不清理其他点号开头的文件。文件名中的时间戳用于记录完成时间及发布页展示，不承担新旧选择或自动新鲜度判定职责。

采集步骤结束后，在该步骤的产物目录写入一个空的结果标志文件，记录本次 `collection_run_id`、完成时间（年月日时分秒毫秒）和该步骤的 `success` 或 `failed`。标志只代表所在目录对应采集步骤在该次运行中的结果；`pending`、`running` 不写标志，`blocked` 表示步骤被阻断、未实际执行，也不写标志，仅在步骤表记录状态及原因。进程意外退出而没有标志可以接受，后续发布按 §4.1 将缺少采集 marker 的目录视为不可用。文件名示意为 `.coll_run_id_<uuid>_<yyyyMMdd-HHmmssSSS>_success` 或 `.coll_run_id_<uuid>_<yyyyMMdd-HHmmssSSS>_failed`。时间戳统一使用 **`Asia/Shanghai`（UTC+08:00）**，采用 24 小时制，毫秒固定三位；文件名不额外添加时区后缀，也不随部署机器的默认时区变化。采集标志不替代运行步骤表及 manifest。

发布作业不写结果标志文件；发布步骤的成功、失败或阻断状态均由 `publish_run_step` 记录，整体状态由 `publish_run_info` 记录。发布实际读取的文件和处理的下游目标分别写入 `input_manifest`、`target_manifest`。发布生成或改写 `cql/` 等工作区文件时，仍适用下文的文件备份规则。

`collection_run_info` 与 `publish_run_info` 的整体终态均包括 `success`、`partial_success`、`failed`：所选步骤全部成功为 `success`；至少一个成功且至少一个失败或被阻断为 `partial_success`；没有步骤成功且运行已结束为 `failed`。`pending`、`running` 仍表示未结束。各步骤实际结果保存在相应的 run_step 表中。

采集或发布过程需要改写工作区文件时，对发生写入的步骤目录进行备份；发布仅写入外部目标而未改写工作区文件时，不执行目录备份。以一次目录更新为一个备份单元：在该目录的 `.backup/` 下创建 `bak_yyyyMMdd_HHmmss_SSS/`，将当前目录中除 `.backup/` 自身外的全部文件和目录移入其中，文件名保持不变；名称以 `.` 开头的文件也要备份，包括以前的结果标志。仅新增结果标志文件不触发再次备份。备份时间戳与标志文件统一使用 `Asia/Shanghai`（UTC+08:00）；时间戳重名时不得覆盖已有备份。备份失败时记录告警，删除未成功移入备份的旧文件后继续生成；不把不完整备份当作完整版本。此规则允许备份失败时失去旧产物；其余生成失败、并发写入和旧版本保留细节仍需设计。

## 7. 与此前方案的差别及待决问题

| 问题 | 第 5.3 节方案 | 本文方案 |
| --- | --- | --- |
| 产物隔离 | `job_id` 对应目录。 | `workspace_id` 对应目录。 |
| 作业种类 | 一个采集作业承载目录与采集配置。 | 工作区下分别保存采集作业和发布作业；两者只保存配置。 |
| 跨作业复用 | 不同 `job_id` 默认隔离。 | 同一工作区的不同采集作业及发布作业可共享产物。 |
| 产物追溯 | 需区分作业配置版本与采集运行。 | 还需区分多个采集作业共同更新工作区时，每份产物实际来自哪次运行。 |

本期实施边界与后续事项：

1. 当前产物采用 §4.1 的工作区目录与采集 marker 规则，manifest 格式采用 6.1 §11；不再把完整产物版本管理作为本期前置。
2. 实施时按现有发布步骤核对依赖目录、必要文件和配置检查，适配原 `job_info` 读取；移除跨步骤采集时间的新鲜度检查，以发布页时间展示代替，不产生自动过期告警；不扩大为跨工作区或完整历史一致性检查。
3. 更细的并发写入、备份保留期限、人工确认版本与定时重新审核属于后续能力，不阻塞本期改造。
4. 采集与发布运行之外的调度表，以及作业版本启用、停用等未来管理需求；第 5.2 节的旧模板建表语句不再作为本方案的实施依据。
5. 已确认工作区只隔离文件，下游同源只保存一套内容，五张 PostgreSQL 内容表保留现有主键组成，仅将其中 `source_id` 改为 `text`。生产、测试等同源工作区向同一套 PostgreSQL、Milvus 或 Neo4j 发布时，也按源及步骤既有范围更新，不提供工作区独立的下游内容副本。

## 8. 断代实施时的一次性旧数据清理

这项工作属于实施清单，不改变四层模型。PostgreSQL 先将本次改造范围内的旧表全部按统一批次改名留存，全部完成后再创建新表，不直接删除旧表。旧表命名采用 `<原表名>_old_<yyyyMMdd_HHmmss>`，同批次使用相同时间戳并检查重名；同时处理与新 DDL 同名的旧索引、序列等对象，避免新建冲突，详见 6.1 §10.0、6.2 §12。改名后的旧数据不迁移、不复用，应用只读写新表。

首次按新方案登记数据源、采集和发布之前，还须清理本项目在以下位置留下的旧 UUID 数据，不迁移至新 ID，也不让旧数据继续参与新方案的查询和发布。下表的清理不包含删除上述已经改名留存的 PostgreSQL 旧表。

| 位置 | 一次性处置 | 新格式需要同步检查的内容 |
| --- | --- | --- |
| Neo4j | 清空本项目旧子图的节点及关系；共享实例中其他项目的数据不在范围内。 | 节点和关系的 `source_id`、`entity_id = <source_id>:<逻辑 id>`、CQL 来源头及其解析和校验，均接受新短 ID；新实体由重新采集、发布生成。 |
| Milvus | 清空本项目各受管集合中的旧发布记录；集合结构需变更时按目标结构重建。 | `source_id` 字段值及派生的实体、维度值、SQL 样例主键使用新短 ID；同步检查字符串长度约束、原 UUID 校验以及按源过滤、替换逻辑。 |
| `output/` | 删除本项目旧 UUID 数据源及旧 `job_id` 目录下的产物，不复用为新工作区内容。 | 新产物只写入 `output/<source_id>/<workspace_id>/`，按本文的新步骤目录组织；新方案产生的 `.backup/` 不属于这次旧数据清理。 |
| NL2SQL 会话及结果存储 | 本项目旧会话全部作废，一次性清理相关 checkpoint、Store 会话及归档记录、`result_snapshots` 和对应本地结果文件；不迁移、不恢复，也不重新绑定到新数据源。 | 同步适配 API、Runner、WebStore 等处对短 `source_id` 的校验和会话绑定，并将原 `public.publish_info` 的读取适配为新发布模型。新数据源使用新会话。 |

新短 ID 与旧 UUID 是不同的身份值。例如新发布以 `source_id = 'db_src_1'` 过滤时，不会匹配旧 UUID 的节点或向量记录；正常的“按源整份替换”无法自动清除旧格式残留。此次清理应在新方案首次使用前一次性完成并核验，不加入每次发布或应用启动流程。清理对象是本项目的管理数据和派生产物，不是登记连接所指向的源数据库业务表。

NL2SQL 的清理范围包含其配置持久化库和 schema（当前实现使用 `db_deepagent` schema）中本项目的 `checkpoints`、`checkpoint_blobs`、`checkpoint_writes`、`store`、`result_snapshots` 等关联历史记录，以及配置工作区下对应的本地结果文件；不能仅清理 MetaWeave 的 `output/`。即使重新登记的是同一个数据库，也不复用绑定旧 UUID 的会话。上述存储通过字符串、JSON 或序列化状态保存会话及来源信息，不代表每张表都有独立的 `source_id uuid` 列；不因 ID 格式变化而统一改列或重做 NL2SQL 会话模型。底层表结构按实际需要处理；若仅清空历史记录，则保留框架初始化和版本管理元数据。

这项联动包含旧数据清理和新代码适配两部分：当前 NL2SQL 仍有 UUID 格式校验，也直接读取将被改名退出业务的 `public.publish_info`；只清空旧会话而不调整这两类逻辑，新短 ID 的会话创建、查询及发布就绪检查仍会失败。

本文只记录四层模型、运行规则及实施范围，不表示相关数据库、API、目录版本机制、旧数据清理或调度功能已实现。

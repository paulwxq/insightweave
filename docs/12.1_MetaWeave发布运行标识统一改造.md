# 12.1 MetaWeave 发布运行标识统一改造

## 1. 目标与边界

本任务由 MetaWeave 模块实施：把 Neo4j 图属性以及三个 Milvus 集合的发布运行字段从 `publish_id` 改为 `publish_run_id`。目标字段仍保存同一个发布运行 UUID，**不改变值、来源短 ID、实体主键或发布选择规则**。[doc 5.1 §5.2](5.1_数据源工作区采集运行与发布运行模型.md) 已把四处下游存储列为目标。PG `publish_run_info.publish_run_id` 及 `db_profile/table_definition/table_profile/table_column_profile/table_domain.publish_run_id` 已是目标名称（`metaweave/db/rebuild_platform_schema.sql:502,635,721,769,881,969`），不需要在 PG 为此改名。

此文档是 [12.2 NL2SQL 与 MetaWeave 三库读取契约对齐](12.2_NL2SQL与MetaWeave三库读取契约对齐.md) 的**开发前置任务**。12.1 负责发布写侧和下游存量数据方案；12.2 负责 NL2SQL 读侧及其他契约错位。两侧与存量数据需联合切换，不能先单独部署只写新字段或只读新字段。本任务不修复当前 `db_src_N` 被按 UUID 解析导致的 readiness 503。

### 2.1 `output/<source_id>/<workspace_id>/` 文件边界

本地当前 `metaweave/output/db_src_1/ws_1/` 中，`db/ddl/json/md/domain/dim/rel/sql/` 顶层采集产物及 marker 未检出 `publish_id` 或 `publish_run_id`。例如 `md/manifest.json:12` 保存的是 `source_collection_run_id`，各采集步骤的 `.coll_run_id_...` 文件名标识采集运行；这类文件无须因发布字段改名而重写。历史 `.backup/` 中有以 MetaWeave 平台表为采集对象的 DDL/JSON/MD，可能提及 `publish_run_id`，但属于当时采集到的源库结构内容，不是本任务的发布字段写入点。

**例外是 `cql/`：它位于同一 `output` 工作区下，却由 `rel` 发布生成，并非采集 `rel/` 步骤生成。**当前 `metaweave/output/db_src_1/ws_1/cql/import_all.orders.cypher:40,250,831,1010,1136` 明确包含 `publish_id` 参数键、Table/Column 节点属性及 HAS_COLUMN/JOIN_ON 关系属性。发布服务先生成文件，再交给 CQLLoader 执行（`metaweave/backend/publishing/publish_service.py:1327-1337,1412-1443`）；目录归属见 `metaweave/metaweave/core/clean_targets.py:130-135`。改 writer 后，新生成的 CQL 必须写 `publish_run_id`；现有主文件及 `.backup/` 中旧脚本不能作为新契约再次导入。保留历史备份可以，但要在迁移方案中明确禁止旧脚本回放或先转换。文件名 `import_all.<db>.cypher` 和工作区目录名无需改变。

## 3. 采集运行 ID 不在本次改名范围

`collection_job_id` 是采集作业（可复用配置）的短 ID，`collection_run_id` 是一次采集执行的 UUID，语义不同。一次运行只归属一个作业及其一个配置版本：`collection_run_info` 以 `(collection_job_id, revision_no)` 外键指向 `collection_job_revision`（`metaweave/backend/persistence/models.py:306-343`）。一个作业可以先后产生多个运行，每次执行生成新的运行 ID（`metaweave/db/rebuild_platform_schema.sql:329-336`、`metaweave/backend/jobs/collection_run.py:374-395`）；因此是**作业一对多运行**，不是两个 ID 一一映射或互相改名。发布侧相应地使用短 `publish_job_id` 和 UUID `publish_run_id`（`models.py:525-526`）。当前活跃代码和 SQL 没有用 `collect_id` 或 `collect_run_id` 作为上述三类 Milvus 集合、Neo4j 图的属性。

采集运行身份主要留在 PG `collection_run_info/collection_run_step`、工作区目录 marker（`metaweave/backend/workspace_files/markers.py:3`）和发布 `input_manifest.files[*].collection_run_id`（`metaweave/backend/jobs/manifests.py:35-53`）。PG 视图 `vw_workspace_latest_successful_publish` 从该清单汇聚 `source_collection_runs`（`metaweave/db/rebuild_platform_schema.sql:1087-1113`）；MD 产物清单还使用 `source_collection_run_id`（`metaweave/backend/data_sources/md_step_service.py:239`）。这些是**采集来源追溯**，不等同于下游内容的发布版本。本次不新增 `collection_run_id/collect_id` 到 Milvus 或 Neo4j，也不改采集链的字段名。

## 4. 目标重建与联合验收

1. 切换前只读盘点目标 Milvus database、三个集合 schema 与记录、Neo4j Table/Column 节点和 HAS_COLUMN/JOIN_ON 关系的实际字段；源码定义不能证明在线数据结构已一致。
2. 按项目未上线、不迁移历史数据的既定前提（`docs/6_工作区采集作业与发布作业四层模型.md:7`、`docs/10.2_数据发布作业并行执行优化设计建议.md:226`），首选在演练环境重建三个 Milvus 共享集合，并对盘点出的**所有来源**分别受管重发相应步骤；只改 Python 字段名会使集合 schema、写入和删旧条件失配。Neo4j 可在核验后按源受管重发，或对现有节点和关系做一次属性更名。实际重建、更名和重发前须确认目标没有待执行或执行中的发布、删除任务及调试加载；操作期间不启动同目标的新写入，遗留运行按现有流程收尾。受管发布互斥不覆盖外部集合重建或调试加载（`metaweave/backend/publishing/publish_service.py:269-292`、`metaweave/backend/deletion/cleaners.py:24-41`）。若某个目标含必须保留且无法重发的数据，再另行制定迁移方案；本期不预设集合级搬迁和长期双字段兼容。旧 CQL 主文件和备份的回放边界见 §2.1。数据操作需另行实施和验证。
3. 与 12.2 的 NL2SQL 读侧改名统一切换。写侧改名、重建与重发完成后，如 NL2SQL 仍读取 `publish_id`，readiness 暂时不兼容；可能在字段读取阶段报 `knowledge_backend/dependency_unavailable`，也可能在后续核对中报不一致，具体取决于实际结构与先前检查。此时尚未完成联合切换，不能将单侧中间态当作最终验收结果。按源、按步骤核对实际存储的 `publish_run_id` 与 PG 最近成功记录：Milvus `table_schema/dim_value/sql` 各对各自步骤，Neo4j 对 `rel`；不同步骤的 UUID 可以不同，不新增跨步骤相等要求。
4. 调试入口可能生成未登记到 PG 的随机批次 UUID（`metaweave/metaweave/core/metadata/execution.py:569-589`、`metaweave/metaweave/cli/loader_cli.py:178-181`）。改名后仍要明确其调试性质，避免把它误作正式发布运行并污染受管目标。双写或双读仅在具体切换方案确有过渡需求时使用。

## 1. 背景与问题

### 1.1 问题场景

运行执行中后端进程死亡（崩溃、被回收、机器重启等）时，平台库中该运行整体滞留 `running`/`pending`，且不会再有任何执行者更新它们（"僵尸运行"）。2026-11-05 事故记录：运行 `d1f8c7e3` 执行 rel 步骤期间后端进程被回收，rel 卡 `running`，导致后续同工作区新运行的 rel 步骤认领冲突被阻断（"该工作区此步骤可能正在执行（其他运行占用）"），sql 级联阻断，新运行整体 failed；最终由 CLI 脚本手工收尾解决。

僵尸运行的后果：

1. **阻断同工作区重跑**：步骤认领的互斥查询要求冲突方"步骤 running 且运行整体 running"（[collection_run.py](../metaweave/backend/jobs/collection_run.py) `_claim_step`），僵尸运行持续命中该条件。
2. **阻断删除准入**：删除准入按未终态集合（pending/running）筛选运行（[deletion/repository.py](../metaweave/backend/deletion/repository.py)），僵尸运行阻断数据源/工作区删除。
3. **界面误导**：运行详情对非终态运行每 3 秒轮询，僵尸运行永远显示"运行中"。

### 1.2 现有手段与其不足

doc 8.1 §5.4 已提供 CLI 收尾脚本 [resolve_orphaned_run.py](../metaweave/scripts/resolve_orphaned_run.py)：默认只读预览，`--apply --confirm-executors-stopped --reason <原因>` 实际收尾（步骤 `running→failed`、`pending→blocked`，按汇总裁决写整体终态，处理说明写入运行与被迁移步骤的 message）。

不足：只能登录服务器执行命令行，操作门槛高、依赖运维在场；界面上没有任何入口。本文把同一能力收敛为 Web 功能。

### 1.3 目标与非目标

**目标**：

- 运行详情面板（[RunPanel.vue](../frontend/src/components/RunPanel.vue)，采集/发布通用）在非终态运行时显示「终止」按钮；
- 点击后经确认弹窗调用后端接口，执行与 CLI 脚本完全一致的收尾逻辑；
- 收尾后互斥解除，可立即重跑失败步骤；运行定格为终态（全部成功→`success`；有成功且非全部→`partial_success`；无成功→`failed`）。

**非目标**（明确不做）：

- **不做真取消**（取消正在执行的运行：协作式中断、线程取消、心跳/租约自动接管）。doc 10.1 §4.5 已议定本期不做自动接管；真取消是另一个独立特性。本功能**只修改状态记录，不停止任何线程**。
- **不做进程探测/终止**：与 CLI 一致，"执行者已停止"是人工确认，后端不扫描进程、不 kill。
- **不改产物**：不删除文件、不改 marker、不清理已发布内容（与 CLI 语义一致）。
- **不做多后端实例跨进程活性检测**（见 §4.6 限制）。

## 2. 现状代码事实

本节全部为已核对的代码事实（含 Codex 一轮审核复核），是设计的出发点。

1. **收尾脚本逻辑**（[resolve_orphaned_run.py](../metaweave/scripts/resolve_orphaned_run.py)）：
   - `preview()` 只读：输出运行/步骤现状、计划变更（`running→failed`、`pending→blocked`）、计划整体终态、`actionable`；
   - `apply_resolution()`：按 doc 8.1 §5.1.1 锁序 **源 → 工作区 → 作业 → 运行 → 全部步骤** 加 `FOR UPDATE` 锁（`populate_existing` 防缓存旧值），加锁后复查运行仍未终态（幂等），逐**未终态**步骤改状态并写入处理说明（已终态步骤不追加说明），说明追加到运行 message，`finalize_run()` 汇总裁决后单事务提交；
   - 未终态集合 `_UNFINISHED = ("pending", "running")`；`--finalize-only` 模式仅汇总、拒绝改未结束步骤；
   - 采集/发布共用一套逻辑，按 `RunSpec`（`COLLECTION_RUN`/`PUBLISH_RUN`）参数化；
   - **`--confirm-executors-stopped` 仅校验旗标存在，不做任何执行者探测**——CLI 的安全性同样完全依赖操作人确认。
2. **运行执行模型**：运行在**同一 uvicorn 进程**内由 FastAPI `BackgroundTasks` 线程执行（[workspaces.py](../metaweave/backend/api/routers/workspaces.py) `_run_in_thread`，doc 6.2 §6.3"同进程线程执行"）。**当前没有任何"在执行运行"注册表。**"单实例部署"是部署前提，不能由代码本身证明（见 §4.6）。
3. **运行状态机**：创建即 `pending`（`create_collection_run`，run_id 由函数内部 `new_run_id()` 生成）；执行器入口检查 `run.status != "pending"` 则跳过执行（`execute_collection_run`）；`mark_run_running()` 仅允许 `pending→running`（[run_repository.py](../metaweave/backend/jobs/run_repository.py)）。**注意：这些都是普通读取与更新（无 `FOR UPDATE`），不构成原子认领，不能当作与收尾并发时的独立安全屏障**——对已通过入口检查、正在执行的执行器没有任何约束力（§4.5 竞态 E）。
4. **汇总裁决**（`rollup_run_status()`，doc 6.2 §6.4）：全部 `success`→`success`；有 `success` 但非全部→`partial_success`；无 `success`→`failed`。`finalize_run()` 要求全部步骤已到终态，否则抛错。
5. **互斥解除条件**：步骤认领冲突查询要求冲突方**运行整体也是 `running`**；收尾把整体改为终态后，互斥自动解除（2026-11-05 事故记录中已按此恢复）。
6. **运行详情接口与前端**：`GET /api/collection-runs/{id}`、`GET /api/publish-runs/{id}`（workspaces.py）。[RunPanel.vue](../frontend/src/components/RunPanel.vue) 是采集/发布通用的**纯展示**面板；3 秒轮询由 composable [useRunPolling.ts](../frontend/src/composables/useRunPolling.ts) 持有（RunExecuteView / JobDetailView / WorkspaceHomeView 使用），终态停止。**因此终止成功后的立即刷新必须由持有运行数据的调用方触发，不能只改展示组件。**
7. **前端既有确认弹窗**：[DeleteResourceDialog.vue](../frontend/src/components/DeleteResourceDialog.vue) 等提供危险操作的样式与交互模式（危险按钮、确认输入）可复用；"必填原因 + 勾选承诺"的字段逻辑需自行实现，不是现成可复用件。
8. **步骤终态写回无条件**（[run_repository.py](../metaweave/backend/jobs/run_repository.py) `finish_step`）：直接赋值 `step.status`/`step.message`，不要求原状态仍未结束。**含义：存活 worker 的后续写回会覆盖收尾结果**——这正是必须拒绝"收尾本进程存活运行"的根本原因（§3、§4.2）。

## 3. 核心安全问题：收尾者与执行者同进程

CLI 并没有"天然保证"：脚本只校验人工旗标，不探测执行者（§2.1）。CLI 的实际安全来源是**操作人可以直接查证进程生死**（ps、日志），且脚本进程与被收尾的执行者必然不是同一进程。

Web 化之后性质变了：**提供收尾接口的后端进程，恰恰可能就是正在执行该运行的进程**（§2.2 同进程线程执行）。若运行正在本进程真实执行，而接口把它收尾为终态，会发生：

- 存活 worker 继续运行，稍后经 `finish_step` **无条件覆盖**步骤终态与 message（§2.8），与收尾结果互相矛盾；
- 运行整体已被汇总裁决，执行器后续再写状态时运行已是终态，审计记录混乱；
- 互斥被错误解除，同工作区新运行可能与存活 worker 并发写同一套产物目录。

因此 Web 入口必须回答"这个运行是不是本进程正在执行的"。答案：**在执行者注册表**（§4.2）。注册表命中的运行，接口拒绝收尾；未命中的，按 CLI 同等语义（人工确认承诺）放行。

## 4. 设计方案

### 4.1 共享逻辑抽取：CLI 与 Web 共用一份实现

把 `resolve_orphaned_run.py` 的核心逻辑抽取为共享模块 `backend/jobs/run_resolution.py`：

- `preview_resolution(session, spec, run_id) -> dict`（现 `preview()` 主体，kind 参数改为直接传 `RunSpec`）；
- `apply_resolution(session, spec, run_id, reason, *, finalize_only=False, origin="离线收尾") -> dict`（现 `apply_resolution()` 主体，新增 **`origin` 参数**：note 前缀来源标识，CLI 传「离线收尾」、Web 传「Web 终止」，其余 note 结构不变）。

锁序、复查、状态迁移、note 结构、汇总裁决**全部保持不变**。不引入通用回调框架，只加这一个参数。

`scripts/resolve_orphaned_run.py` 改为薄封装：解析参数 → 解析 `kind` 为 `RunSpec` → 调用共享模块 → 打印 JSON。CLI 行为与输出结构不变；既有测试 `test_resolve_orphaned_run.py` 预期仅需调整 import 即可通过（**实施时实测确认**）。

**理由**：收尾逻辑含锁序纪律（doc 8.1 §5.1.1）与状态机约束，任何"Web 重写一份"都会引入两份实现漂移风险。

### 4.2 在执行者注册表（本进程活性判定）

新增模块级注册表 `backend/jobs/active_runs.py`：

```python
# 结构示意，非实现
_LOCK = threading.Lock()
_ACTIVE: set[tuple[str, UUID]] = set()   # (kind, run_id)，kind ∈ {"collection", "publish"}

def register(kind, run_id): ...      # 加锁添加
def unregister(kind, run_id): ...    # 加锁移除（幂等）
def is_active(kind, run_id) -> bool: ...
```

**注册生命周期（三条规则）**：

1. **提交前注册（消除创建窗口）**：创建路由改为调用辅助函数——先 `new_run_id()` 生成 run_id 并 `register`，再调用创建函数（创建函数改为**接受外部生成的 run_id**，现行为内部生成，collection_run.py `run_id = new_run_id()`，发布侧同样处理，实施时核对），最后 `background.add_task` 交付执行。创建失败或交付失败时在 `except` 中 `unregister` 并向上抛错。
   **不变式：可能被本进程执行的运行，在其运行行对他人可见（提交）前已注册**（交付失败后的注销是设计允许的例外——该运行永不会执行，无需拦截）。不存在"已创建未注册"窗口。
2. **执行结束注销**：`_run_in_thread()` 包装函数（或各 `execute_*_run` 最外层）的 `finally` 中 `unregister`。
3. **接口入口一次活性检查**：收尾端点首先 `is_active(kind, run_id)`，命中即 409 拒绝，不加任何数据库锁。

**为什么一次入口检查足够（单进程前提下）**：

- 运行只执行一次：`execute_*_run` 只执行创建时传入的那一个新建运行，不扫描、不接管旧记录，run_id 不会再次进入注册表；
- 注册严格先于可见性与交付：执行器开始执行 ⇒ 已交付 ⇒ 已注册 ⇒ 入口检查必命中 → 409；
- 注销只发生在执行结束之后（finally，含异常退出）：正常结束时运行已到终态，收尾请求走幂等返回（§4.3）；**异常退出时终态未必已提交**（§2.3 的入口检查非屏障；执行器无外层兜底——执行计划不一致直接抛出、汇总失败仅记录日志后返回，`execute_collection_run`），注册表不再拦截、允许收尾——这正是"进程存活但执行者已死"的恢复路径。

**不做"加锁后复检"**（v1 设计已删除）：复检查询的是**同一个**注册表，漏注册的执行路径同样查不到；且数据库行锁与进程内集合之间没有顺序关系，"锁内注册表状态稳定"不成立。同源第二次查询不增加任何保证。

**已知边界（如实记录）**：

- 后台任务已交付、**进程仍存活**、任务却未进入包装函数（极端异常）：注册残留 → 该运行收尾请求持续 409，直到进程重启。这是可接受的保守方向：**宁可误拒，不可误放**。（进程崩溃不属于本场景——崩溃即注册表消亡，重启后按 §4.6 正常收尾僵尸。）
- 其他进程/外部执行者（部署前提之外）：注册表不可见，唯一防线是人工确认勾选；误用后果见 §4.5 竞态 E。

### 4.3 API 端点

在 [workspaces.py](../metaweave/backend/api/routers/workspaces.py)（`prefix="/api"`）新增两个端点：

```text
POST /api/collection-runs/{collection_run_id}/resolve
POST /api/publish-runs/{publish_run_id}/resolve
```

端点命名用 `/resolve`（与脚本名 `resolve_orphaned_run` 一致）：本功能只收尾状态记录、不终止任何执行，名称应准确表达能力；前端按钮文案仍为「终止」（用户既定需求），确认弹窗负责说明真实语义（§4.4.2）。

请求体：

```json
{
  "reason": "后端进程被回收，rel 中断收尾",   // 必填，非空串；写入运行与被迁移步骤 message
  "confirm_executors_stopped": true          // 必填 true；人工承诺（等同 CLI 的 --confirm-executors-stopped）
}
```

响应（200，实际收尾后）：

```json
{
  "changed": true,
  "final_status": "partial_success",
  "steps": [{"step": "rel", "to": "failed"}, {"step": "sql", "to": "blocked"}],
  "note": "Web 终止：原状态 running；处理时间 …；执行者已停止（人工确认）；处理原因：…；实际外部写入结果未核验",
  "run_id": "…", "job_id": "…", "workspace_id": "…"
}
```

（`apply_resolution` 现返回 `source_id` 而非 `workspace_id`；Web 响应字段按上表映射，`workspace_id` 取自运行所属作业。）

错误与边界映射：

| 场景 | 状态码 | 说明 |
| --- | --- | --- |
| 运行不存在 | 404 | 与现有运行详情接口一致 |
| `reason` 为空/全空白 | 400 | 与 CLI 的 `--reason` 必填一致 |
| `confirm_executors_stopped != true` | 400 | 人工承诺缺失 |
| 运行在本进程执行中（注册表命中） | 409 | 文案："该运行正在本进程执行中，不能收尾；若确认执行已中止，请重启后端后重试"（覆盖 §4.2 注册残留场景） |
| 运行已是终态 | 200，`changed: false` | 幂等，返回 `message: "无需处理：运行已是终态 …"`；兼容并发重复提交与页面状态滞后，前端按成功刷新即可 |

并发：两人同时点终止 → 行锁串行化，后到者在锁内看到终态 → `changed: false`（沿用现有脚本逻辑）。

**不提供 dry_run/预览参数**（v1 设计已删除）：弹窗打开时用户尚未填写原因，与 `reason` 必填存在直接交互矛盾；且计划变更规则简单固定，前端按规则展示即可（§4.4.2），最终裁决由后端在锁内作出。少一个参数，少一条代码路径。

### 4.4 前端设计

#### 4.4.1 按钮位置与可见性

[RunPanel.vue](../frontend/src/components/RunPanel.vue) 运行头部区域（状态徽标旁）新增「终止」按钮，危险样式：

- 仅当 `run.status === 'pending' || 'running'`（即现有 `pendingState`）时可见；
- 采集/发布弹窗共用该面板，一次实现两侧生效；
- 可点性门控（§4.7，v4）：`executor_active === true` 时禁用并显示提示，`false` 可点；
- 运行到终态后轮询自然停止，按钮随刷新消失。

#### 4.4.2 终止确认弹窗（新组件 `TerminateRunDialog.vue`）

复用既有危险确认弹窗的样式与交互模式（§2.7）。**打开时不调用任何接口**，按固定规则从已加载的运行详情直接展示计划：

1. 警告说明（固定文案）：

   > 终止仅用于**执行进程已不存在**的中断运行。本功能只修改运行与步骤的状态记录，不停止线程、不删除产物文件、不改 marker、不清理已发布内容。若运行正在本进程执行中，后端将拒绝本操作。

2. 计划变更（按固定规则从当前步骤状态计算展示）：
   - 每行：`步骤：当前状态 → 变更`，规则为 `running → 失败`、`pending → 被阻断`、其余 `保持不变`；
   - 整体终态按汇总裁决规则文字说明："全部成功→成功；有成功且非全部→部分成功；无成功→失败；**实际终态以提交时后端裁决为准**"。
3. 「处理原因」多行输入框（必填）；
4. 勾选项（必选）：「我已确认执行该运行的进程已停止」；
5. 按钮：「取消」/「确认终止」（原因非空且已勾选才可点）。

确认后调用接口；成功则关闭弹窗，并**由持有运行数据的调用方（轮询 composable 所在处，§2.6）立即刷新一次**运行详情，不等下一轮 3 秒轮询；409 时弹窗内展示拒绝文案并保留弹窗。

#### 4.4.3 API 客户端

`frontend/src/api/` 新增 `resolveRun(kind, runId, {reason, confirm_executors_stopped})`，类型定义同步补充（`ResolveRunRequest`/`ResolveRunResponse`）。

### 4.5 竞态分析

| 竞态 | 处理 |
| --- | --- |
| A. 收尾请求 vs 运行创建 | 注册严格先于提交，且端点先查注册表（§4.2 规则 1、§4.3）：提交前命中注册表 → 409，提交后 → 409；仅完全未知的 run_id 返回 404。无窗口 |
| B. 收尾 pending 运行 | 本进程创建后未执行前：已注册 → 409（本期不提供"创建后撤回"，属真取消范畴）。**pending 僵尸**（进程崩溃于创建后、执行前）：注册表随进程消亡 → 放行，全部步骤 `pending→blocked`，汇总 `failed` |
| C. 僵尸运行（running 滞留） | 注册表为空 → 人工确认后放行（CLI 同等语义）。主路径 |
| D. 两个收尾请求并发 | 行锁串行化；后到者锁内见终态 → `changed: false` 幂等返回 |
| E. 存活执行者 | **本进程**：已注册 → 409，不可能误收尾。**其他进程**（部署前提之外）：注册表不可见，唯一防线是人工确认；误用后果如实记录——存活 worker 的 `finish_step` 无条件覆盖步骤终态与 message（§2.8），状态被反复改写、审计混乱，需重新收尾并人工核对 |
| F. 运行结束与收尾并发 | 执行中必注册 → 409；正常结束（已注销、终态已提交）→ 锁内复查见终态 → `changed: false` 幂等；异常退出（已注销、终态未必提交）→ 注册表放行 → 允许收尾，正是"进程存活但执行者已死"的恢复路径。三种结局都安全。（v1 中"收尾先提交则执行器入口 pending 复查跳过"的论证已删除：入口复查是普通读取，对已通过检查、正在执行的执行器没有约束力） |
| G. 注册残留 | 进程存活但任务未进入包装函数 → 注册残留 → 持续 409 至进程重启（保守方向，可接受）；进程崩溃则注册表随之消亡，重启后按僵尸正常收尾（§4.6） |

### 4.6 限制与已知边界

1. **部署前提（显式声明）**：单 worker 进程，且除创建路由的后台任务外**无其他运行执行入口**。这是部署约束而非代码可证事实；满足该前提时注册表判定完备。多实例支持依赖心跳/租约，doc 10.1 §4.5 已议定本期不做；跨实例场景由人工确认勾选兜底（与 CLI 语义相同）。
2. **后端重启即清空注册表**：重启后本进程无在执行运行，滞留库中的 `running`/`pending` 运行均可被收尾——这正是期望行为（僵尸收尾的主路径）。
3. **不核验外部写入结果**：note 中保留"实际外部写入结果未核验"（与 CLI 一致）——收尾只改平台库状态；中断步骤的产物目录状态由后续重跑按各步骤自身机制处理（如 rel 的 `.backup`，doc 23.2），本文不对"重跑必能修复全部半成品"作泛化承诺。

### 4.7 执行者状态透出与终止按钮门控（v4 增补）

把 §4.2 注册表读出来给 UI，让用户在点击前就能分辨"正在本进程执行"与"疑似中断遗留"。注册表、收尾逻辑、409 语义零改动。

**后端**：两个既有运行详情接口（§2.6：`GET /api/collection-runs/{collection_run_id}`、`GET /api/publish-runs/{publish_run_id}`）响应新增 `executor_active: bool` 字段，取值 `active_runs.is_active(kind, run_id)`（§4.2 模块的纯读取，不加数据库锁）。增量字段，不改变既有字段。

**前端门控（RunPanel「终止」按钮，§4.4.1）**：

| `executor_active` | 按钮 | 提示 |
| --- | --- | --- |
| `true` | 禁用（不隐藏） | 「该运行正在本进程执行中，不能终止；若确认执行已中止，请重启后端后重试」——与 §4.3 409 文案一致，兼作 §4.2 注册残留场景（持续 `true` 至进程重启）的逃生口 |
| `false` | 可点 | 无附加提示。`false` 仅表示本进程无执行者，不是"执行进程已死"的证明；弹窗勾选确认（§4.4.2）仍是最后防线 |
| 字段缺失 | 可点（退化为 v3 行为） | 后端 409 仍兜底。前后端同仓同发，缺失属异常态；门控失效不应锁死恢复入口 |

**新建 pending 运行**：提交前注册（§4.2 规则 1）⇒ 运行行可见的时刻必已注册；此后只要执行尚未结束（含排队等待），详情返回 `true`、按钮禁用——与 §4.5 竞态 B"本期不提供创建后撤回"一致。若首次读取前注册已注销（交付失败注销、执行器入口检查提前返回等 §4.2 允许路径），详情返回 `false`——该运行不会再被本进程执行，允许收尾。

**状态单调性**：运行只执行一次、注册先于可见（§4.2 不变式），对页面上已可见的运行，`executor_active` 只会 `true → false`（执行结束注销），不会回跳；弹窗打开期间不存在"运行突然变活"的竞态。弹窗保留 409 处理（§4.4.2）作为纵深防御，成本为零。

**明确不做（防过度设计）**：不做进程/线程级存活探测与跨进程活性检测（§1.3、§4.6.1 既定边界）；不新增独立状态查询端点（复用既有详情接口与 3 秒轮询）；`executor_active` 不参与收尾端点任何判定（409 仍由收尾端点自查注册表作出）。

## 5. 与 CLI 的语义对照

| 维度 | CLI 脚本 | Web 收尾 |
| --- | --- | --- |
| 核心逻辑 | 共享模块 `run_resolution.py` | 同一共享模块 |
| 命名 | `resolve_orphaned_run.py` | `POST .../resolve`（按钮文案「终止」） |
| 计划展示 | 默认只读预览（不加 `--apply`） | 无 dry_run；弹窗按固定规则从已加载状态展示，最终以后端锁内裁决为准 |
| 人工承诺 | `--confirm-executors-stopped` 旗标 | 请求字段 + 弹窗勾选（语义相同：均不探测执行者） |
| 处理原因 | `--reason`（必填） | `reason`（必填，400 拒绝空值） |
| 执行者活性 | 操作人自行查证（脚本进程与执行者天然不同进程） | 本进程注册表强制拦截；跨进程由人工确认兜底 |
| 仅汇总模式 | `--finalize-only` | **不提供**（界面只暴露收尾主路径；需要时仍可用 CLI） |
| note 前缀 | 「离线收尾」 | 「Web 终止」（`origin` 参数） |

## 6. 测试方案

### 6.1 单元测试（后端，fake session 沿用 `test_resolve_orphaned_run.py` 模式）

1. 共享模块抽取后，既有 CLI 测试全部保持通过（import 调整，实测确认）；`origin` 参数体现在 note 前缀；
2. 注册表：注册/注销/幂等注销/并发注册注销；
3. **注册时序**：创建辅助函数先生成 run_id 并注册、再调用创建函数、再交付任务（fake 断言调用次序）；创建失败/交付失败 → 已注销；
4. 执行结束注销：包装函数正常返回与抛异常两条路径均注销；
5. 收尾逻辑：pending 僵尸运行 → 全部步骤 `pending→blocked`，汇总 `failed`；幂等（终态再收尾 → `changed: false`）；锁内复查（加锁后运行已变终态 → `changed: false`）。

### 6.2 API 测试（两个端点）

1. 200 成功路径（note 前缀为「Web 终止」，响应含 run_id/job_id/workspace_id）；
2. 400：空 reason、缺 confirm；
3. 404：运行不存在；
4. 409：注册表命中（注册后调用）；
5. 200 `changed: false`：终态运行；
6. 详情接口 `executor_active`（§4.7，v4）：注册后 `true`、注销后 `false`。

### 6.3 前端测试

1. RunPanel：`pending`/`running` 显示终止按钮，终态不显示；
2. TerminateRunDialog：打开不调接口；按固定规则展示计划变更；原因为空或未勾选时「确认终止」禁用；409 时展示拒绝文案且弹窗保留；
3. 成功后由调用方触发一次立即刷新；
4. 按钮门控（§4.7，v4）：`executor_active: true` 时按钮禁用并显示提示；`false` 可点；字段缺失不门控。

### 6.4 手工验收（演练库 `metaweave_rehearsal_final`）

5. CLI 脚本回归：命令行收尾另一条僵尸运行，行为与改造前一致。

## 7. 裁定结果（Codex 建议 + 主设计裁定；**用户已确认**，2026-11-05）

| 问题 | Codex 建议 | 裁定 | 理由 |
| --- | --- | --- | --- |
| 端点命名 | `/resolve` | **采纳** | 本期只修复状态、不停止线程，名称应准确表达能力；与脚本名 `resolve_orphaned_run` 一致。按钮文案保留「终止」（用户既定），弹窗说明真实语义 |
| 重复收尾响应 | 200 `changed: false` | **采纳** | 沿用脚本幂等行为，正常处理并发与页面状态滞后 |
| 首期范围 | 采集＋发布同时 | **采纳** | 收尾逻辑本就按 RunSpec 参数化、RunPanel 通用，人为限制首期只加分支不减风险 |
| 无鉴权 | 接受 | **采纳** | 内部工具定位；原因＋勾选防误操作，不构成权限体系，本期不引入鉴权 |

# 101. 输出目录清理策略备忘录

> 整理日期：2026-10-20
> 范围：MetaWeave 采集/发布各步骤对 `output/` 下各子目录（db/ddl/json/md/domain/dim_config/rel/cql/sql-rag）的清理与备份行为，依据当前代码逐处核验（涉及文件均在文中标注行号，后续代码变更以此备忘录为快照、以代码为准）。

## 1. 总结论

- **全项目唯一的备份机制是 `rel/` 目录的 `.backup/`（且是"移动"不是"复制"）；其余所有目录都是直接删除旧文件，无任何 bak/副本机制。**
- 清理语义收敛在两个原语上，各目录只是调用时机不同；递归清空的 `clear_dir_contents()` 在生产代码中零调用。
- 个别产物的保护不靠备份，靠两类手段：**延迟删除**（确认能产出替代物后才删）与**原子写入**（临时文件 + `os.replace`）。

## 2. 两个清理原语（`metaweave/utils/file_utils.py`）

| 函数 | 动作 | 使用方 |
|---|---|---|
| `clean_top_level_files()`（`file_utils.py:57`） | **只删目录顶层普通文件（含隐藏文件），保留全部子目录及其内容**；要求目标在项目根内，目录不存在则创建 | 所有 metadata/db 步骤的标准 clean 语义 |
| `clear_dir_contents()`（`file_utils.py:32`） | 递归删除所有文件+子目录（保留目录本身） | **无任何生产调用方**；docstring 明确声明它不是 metadata/db 的 `--clean` 语义 |

`core/clean_targets.py` 的预警文案与该语义一致（`_dir_target` note："删除目录顶层全部文件，保留子目录"）；pipeline 计划目标与运行期实际目标经 `verify_clean_target`（`core/metadata/execution.py:484`）比对一致后才执行清理。

## 3. 按目录的清理动作与备份行为

受管目录均为 `output/<source_id>/<job_id>/<子目录>/`；CLI 默认为 `output/<子目录>/`（可被 `output.*_directory` 配置覆盖）。

| 目录 | 清理动作 | 触发时机 | 生成新文件时对旧产物的处理 |
|---|---|---|---|
| `db/` | 删顶层文件，保留子目录 | 受管采集 `clean` 为真时落盘前；`meta_load --clean` 入库成功后 | **不备份，直接删**。两处刻意"延迟删除"：`meta_load` 先把画像入库成功才删文件；受管采集在源库版本校验通过后才清——即确认能产出替代物后才删，但失败时旧文件同样已删 |
| `ddl/` | 删顶层文件，保留子目录 | Web 固定清理；CLI `--clean` | **不备份，先删后生成**（清理与生成在同一 try 内，生成失败旧文件已没了） |
| `json/` | 删顶层文件，保留子目录 | Web 固定清理；CLI `--clean` | **不备份，先删后生成**；步骤状态提交失败时额外删掉本次新写的 `manifest.json`（`_discard_manifest`）。单文件写入原子（`save_json_document` → `atomic_write_json` 临时文件+`os.replace`） |
| `md/` | 删顶层文件，保留子目录 | Web 固定清理；CLI `--clean` | **不备份，先删后生成**；失败时删 `manifest.json`。单文件写入为 `save_text` 直接 `open("w")` 覆写，**非原子** |
| `domain/` | 删顶层文件，保留子目录 | Web 固定清理；CLI `--clean` | **不备份，先删后生成**。`write_to_yaml` 直接 `open(yaml_path, "w")` 覆写，**非原子** |
| `dim_config/` | 删顶层文件，保留子目录 | Web 固定清理；CLI `--clean` | **不备份，先删后生成**。但生成落 `mkstemp` 唯一临时文件，核验通过才 `os.replace` 到 `dim_tables.yaml`，**原子** |
| `rel/` | 删顶层文件，保留子目录 | Web 固定清理；CLI `--clean` | **✅ 全项目唯一有备份的目录，且仅 Web 受管链路**：重跑时旧 `{db}.relationships_global.{json,md}` 先**移动**（`Path.replace`，非复制）进 `rel/.backup/`，移动前先 `shutil.rmtree` 旧 `.backup/`（**只保留最近一份**）；之后照常清顶层。CLI `--step rel --clean` **不备份**，直接清。恢复 `.backup` 为纯手工操作，无 UI |
| `cql/` | 删顶层文件，保留子目录 | rel 发布锁内固定清理；CLI `--clean` | **不备份，先删后生成**。写盘为 `open(output_file, "w")` 直接覆写，**非原子** |
| `sql-rag/` | 加固版清顶层：`_clean_sql_top_level_files`，目录内出现**符号链接或非常规条目直接抛错拒绝清理**；开启校验时**先成功取得源库连接才清理**，连接失败不删旧产物 | Web 固定清理，生成 SQL 样例前 | **不备份，先删后生成**。写盘 `open(output_file, "w")` 直接覆写，**非原子** |
| 整工作区 `output/<source_id>/` | **唯一的递归删除点**：`shutil.rmtree` 整棵子树（含所有 job 目录） | 仅在删除数据源登记且勾选删除输出时执行；失败则保留登记记录 | **不备份，整树直接删** |

## 5. 语义差异与注意点

1. **Web 受管 vs CLI**：Web 侧 ddl/json/md/domain/dim_config/rel/sql 是"每次运行必清顶层"（设计上每次生成完整集合，不保留上次已消失对象的文件）；CLI 侧同一批步骤必须显式 `--clean` 才清。
2. **子目录会被保留**：`clean_top_level_files` 不删子目录，所以 `rel/.backup/` 能在多轮重跑后幸存；反之，若某目录曾产生子目录，clean 也不会清掉它。
3. **清理时机**：大多在生成**前**（新产物未落盘时旧产物已删，失败即目录为空/半空）；两个例外是 `meta_load --clean`（入库成功后才清）和 sql 步骤（连库成功才清）——这两处刻意把清理放在"确认能产出替代物"之后。
4. **"备份"与"原子写"是两种不同保护**：
   - 备份（仅 rel）：旧产物可回滚，但 `.backup` 只留最近一份、恢复靠手工。
   - 原子写（json 产物、`database.json`、`dim_tables.yaml`）：磁盘上永远是一个完整文件（旧或新），但旧版本内容被直接替换，无回滚。
   - 直接覆写（ddl/md/domain/cql/sql-rag 单文件）：既无备份也无原子性——正常流程下是"写新文件"而非"覆写旧文件"（顶层已先清空）；仅同一次运行内重试同名对象时才会覆写半途文件。
5. **删除数据源无备份**：勾选删除输出时整个 `output/<source_id>/` 直接 rmtree，如需留存副本须先手工拷贝。

# 8.1 数据源与工作区删除及发布知识清理方案

状态：设计建议，待审核；本次仅编写文档，未实现删除改造。

## 1. 目标与范围

提供数据源、工作区、采集作业、发布作业的删除入口，处理层级依赖、运行并发、采集文件以及 PG / Milvus / Neo4j 中的已发布知识。

当前未启用登录：所有访问页面的用户均可使用删除按钮；后端不增加登录、管理员或创建人校验，操作者允许为空。确认弹窗用于说明影响和避免误点，不是权限机制。

本方案推荐采用“业务对象逻辑删除、源级知识物理清理”：删除作业或工作区后不再可见、不可执行，但保留版本和运行记录以满足当前画像的 publish_run_id 外键及历史追溯，不能据此自动回滚到上一次发布的知识；删除整个数据源时清理该源全部已发布知识和采集目录，保留最小登记及运行历史用于追溯。这里的“删除”不意味着把所有历史数据库行一并擦除，页面必须明确说明。历史彻底销毁、回收站和恢复功能不属于本期。

不做旧数据兼容和迁移；表结构按项目既有显式建表方式调整，不编写旧数据回填逻辑。新增状态字段的建表默认值用于正常创建对象，不作为兼容运行时回退。

本期只改 MetaWeave 后端和管理前端。

## 2. 当前代码事实

### 2.1 包含关系与文件归属

```text
数据源 db_source_info
└── 工作区 workspace_info
    ├── 采集作业 → 配置版本 → 采集运行 → 步骤记录
    └── 发布作业 → 配置版本 → 发布运行 → 步骤记录
```

- 平台表定义：`metaweave/backend/persistence/models.py`、`metaweave/db/rebuild_platform_schema.sql`。
- 作业关联工作区，版本关联作业，运行关联版本，步骤关联运行，存在实际外键约束。
- `workspace_info.source_id` 当前只是文本字段，没有数据源外键；不能假定数据库已保证完整层级关系。
- 采集产物位于 `output/<source_id>/<workspace_id>/`，同一工作区内多作业共享目录和步骤产物，不是每个采集作业一套目录。
- 发布版本中的 Domain / Dim 默认参数在 `publish_job_revision.step_config`；本次运行有效参数在 `publish_run_step.step_config`。删除共享 YAML 不能替代删除作业，也不能抹掉数据库中的配置快照。

### 2.2 发布结果按源共享，不能按工作区目录推断归属

| 存储 | 当前数据 | 实际隔离及来源 |
| --- | --- | --- |
| PG | `db_profile` | 每个 `source_id` 一行，含 `publish_run_id` |
| PG | `table_definition` | 源、schema、对象、定义类型组成当前内容标识，含 `publish_run_id` |
| PG | `table_profile`、`table_column_profile` | 源、schema、对象及字段的当前画像，含 `publish_run_id` |
| PG | `table_domain` | 源、schema、表、领域的成员关系，含 `publish_run_id` |
| Milvus | 表结构、维度值、SQL 样例向量 | 记录含 `source_id`、`publish_id`；`publish_id` 对应发布运行 UUID |
| Neo4j | Table / Column 节点及 HAS_COLUMN / JOIN_ON 关系 | 生成器写入 `source_id`、`publish_id`，发布按源替换图 |

默认 Milvus 集合名为 `table_schema_embeddings`、`dim_value_embeddings`、`sql_example_embeddings`，取自 `metaweave/configs/metadata_config.yaml`。实现必须读取实际配置，不硬编码默认名称。

同一数据源不同工作区发布同一类内容，会覆盖或清理该源此前内容。向量加载器 upsert 后按 `source_id` 和不同 `publish_id` 清理旧批次；它们不是可随时恢复的完整历史快照，失败也可能已写入部分数据。因此，不能通过“删除一个发布作业后自动切换到上一次成功运行”恢复实际知识。

依据：`backend/profile_loading/*_loader.py`、`metaweave/core/loaders/{table_schema,dim_value,cql}_loader.py`、`metaweave/core/sql_rag/loader.py`、`metaweave/core/cql_generator/writer.py`。

### 2.3 已有删除入口及缺口

数据源详情页 `frontend/src/views/DataSourceDetailView.vue` 已有删除按钮和弹窗，调用既有数据源 DELETE 接口。服务入口为 `backend/data_sources/registration_service.py::delete_registered_source`：

1. 有任何工作区时拒绝删除。
2. 可选先删除源输出目录，再清理 PG 内容和登记记录。
3. `repository.py::purge_source_profiles` 清理 db_profile、table_definition、table_profile，字段画像通过 CASCADE 删除，但未覆盖 table_domain。
4. 没有清理 Milvus、Neo4j；先删文件再提交 PG 也不能保证一起成功。

因此不是单纯“增加四个按钮”，而是复用并替换已有数据源删除语义，补齐其他层级及外部存储清理。

PG 中多个画像表的 publish_run_id 外键引用发布运行，不能直接物理删除有当前画像引用的发布运行。`table_definition`、`table_domain` 的外键需同时检查 SQL 建表脚本，不能只看 ORM 是否声明。

### 2.4 旧删除契约明确替换，不保留双轨入口

§2.3 描述的是当前旧实现，以下为本期必须替换的内容：

- 原 DELETE `/api/data-sources/{source_id}` 同步 204 改为异步 202，响应删除任务及进度地址；前端等待任务 success 才提示删除完成。
- 废止 delete_output 查询参数与“同时删除 output 目录”勾选；源删除固定清理该源采集树，不允许选择保留文件。显式携带旧参数的请求返回 400 invalid_request，不能由 FastAPI 默默忽略未知参数，也不提供旧行为兼容分支。
- `frontend/src/api/dataSources.ts::deleteDataSource` 移除 deleteOutput 布尔入参，改为接收确认 ID 并返回任务；`DeleteSourceDialog.vue` 移除勾选、旧 confirm 事件参数，改为范围确认与任务展示；`DataSourceDetailView.vue` 同步修改调用。
- `registration_service.delete_registered_source` 替换旧同步删除逻辑，不再因“无工作区”物理删除登记行；旧 remove_db_source 不再作为任何生产删除入口，旧“先删目录再提交登记 DELETE”分支删除。有无工作区均走同一逻辑删除任务。
- 清理已发布数据使用独立 POST，不通过 delete_output 或其他开关复用旧同步 DELETE。

## 3. 推荐的删除规则

### 3.1 删除范围定案建议

| 操作 | 退出日常使用的对象 | 物理清理 | 明确保留 |
| --- | --- | --- | --- |
| 删除采集作业 | 该采集作业 | 无 | 版本、运行、共享采集文件、已发布知识 |
| 删除发布作业 | 该发布作业 | 无 | 版本、运行及参数、已发布知识 |
| 删除工作区 | 工作区及其所有采集/发布作业 | 该工作区采集目录 | 历史版本/运行、源级已发布知识、其他工作区 |
| 删除数据源 | 数据源及全部下属工作区和作业 | 该源全部 PG 画像、Milvus 向量、Neo4j 图、源采集目录 | 最小登记及历史版本/运行、删除任务记录 |

理由：采集文件属于工作区，发布知识属于数据源。删除作业表示停止管理和执行该作业，不代表撤销其发布成果；删除工作区也不应隐式撤销整个数据源的共享知识。

删除工作区会同时删除其 YAML、marker、备份等目录内容；已保存的版本参数和已发布知识仍在。若仍需发布，应通过其他有效工作区重新采集。普通运行日志不作为本期删除对象：共享日志可能混有其他数据源内容，按现有日志保留规则处理。

数据源删除清理的只是平台及知识存储中的登记、衍生内容，绝不连接源业务库执行 DROP、DELETE 或修改业务表。不会删除 Milvus 集合、Neo4j 数据库或整套 PG schema。

### 3.2 增加独立的“清理已发布数据”操作

在数据源详情页提供“清理已发布数据”，按 source_id 一次清理上述五张 PG 内容表及三类向量、该源图数据，但保留有效的数据源、工作区、作业、版本和采集目录，便于重新发布。

本期不提供按工作区、作业、单次运行或任选步骤撤销发布。这些操作与当前按源覆盖及跨步骤依赖不匹配；不根据历史 manifest 猜测当前应删除的对象。

清理任务只限制管理写入，不阻止资产页读取；清理按存储分步生效，各存储清空时间点不同：向量或图已清理时，PG 画像仍可能尚存。PG 画像删除事务提交前，资产页仍可能显示旧的 db_profile、table_profile；提交后按现有无画像状态展示，不承诺受理任务后立即隐藏画像。

源级清理过程中禁止该源采集/发布和配置变更；完成后解除限制。不能把 is_active 当删除状态：禁用可恢复且不代表数据已清理。

#### 独立知识清理的管理页面展示

独立清理保持 deletion_state=active，不改变 is_active；页面不能只依据这两个字段判断是否可操作。直接复用同源 `clear_source_knowledge` 任务派生展示，不新增主表清理状态字段：

- pending / running：数据源详情显示“清理中”，展示任务 ID、步骤进度和入口；pending 的细节文案为“等待执行”。
- 未解决的 failed：详情显示“清理失败”、失败步骤和原因，并按 §7.2 的规则提供原任务重试。
- success：任务结果显示“清理完成，可重新发布”，解除本任务的管理写入限制；不显示“知识已就绪”，也不永久把源标成“已清空”（后续可能重新发布）。

数据源列表同步展示“清理中 / 清理失败”简要标记和任务入口；详情中的采集、发布、编辑等写入口同步禁用并说明原因，直接 API 仍按 §7.3 返回 source_knowledge_frozen。服务端按 §7.0 在源列表/详情附带统一 deletion_task 摘要，完整进度通过任务详情读取，不让前端逐个源请求探测。原任务重试沿用同一任务 ID，成功后不再作为阻断任务。

当前 `backend/data_sources/repository.py::latest_source_activity` 的 last_published_at 为 `max(PublishRunInfo.created_at)`，包含失败等状态，并非最后成功发布时间或当前画像存在证明。保留字段及历史值，不因清理清空；列表列名明确为“最近一次发布运行”，提示为“发布运行创建时间，不代表当前画像或 RAG 数据仍存在”。对应采集列如展示同类统计，应同样标为运行时间。

当前内容以资产页实际 PG 画像及本次清理任务结果查看；任务进度不等同于全存储实时存在性检测。本期不增加新的知识就绪探针或状态体系。

### 3.3 状态与历史

四类主表新增 `deleted_at timestamptz NULL`。源、工作区另加 `deletion_state`，取 `active / deleting / delete_failed / deleted`，表示涉及文件或外部系统的流程；作业删除在单个 PG 事务内完成，只需 deleted_at。

- 普通列表、分页总数、首页统计、候选选择器排除 deleted_at 非空对象。
- deleting / delete_failed 的对象留在管理页面，显示进度和重试入口，但不能继续创建下级或运行。
- 普通详情/编辑/运行接口对已删除对象返回 410 `resource_deleted`，不能因已知 ID 绕过列表限制。
- 历史运行查询仍能返回原来的名称、版本与参数，注明来源对象已删除；只读访问不恢复执行能力。
- 不恢复删除对象，不复用 ID；删除完成后允许重新创建同名对象，新对象由序列分配新 ID，与旧版本、运行、文件及发布来源没有继承关系。名称复用与恢复、ID 复用是不同概念。
- 源完成删除后按 §3.5 的字段清单保留最小登记，并同步调整 SQL/ORM 的可空性及条件校验；不保留连接目标，不使用可连接占位值。

`workspace_info.deletion_state` 为 NOT NULL、默认 active；SQL 与 ORM 同步声明取值域和时间一致性 CHECK：

```sql
CHECK (deletion_state IN ('active', 'deleting', 'delete_failed', 'deleted')),
CHECK (
    (deleted_at IS NULL AND deletion_state IN ('active', 'deleting', 'delete_failed'))
    OR (deleted_at IS NOT NULL AND deletion_state = 'deleted')
)
```

工作区单独删除和源删除级联完成均必须在同一更新中写入合法的 deleted_at/deletion_state 组合；源删除过程中尚未完成的工作区可以保持原状态，操作限制由父源状态守卫承担，最终提交必须统一置 deleted。

### 3.3.1 父级删除期间的子对象展示与准入

子对象的可操作状态必须由自身及全部父级共同计算，不能只过滤作业自己的 deleted_at：

- 源处于 deleting / delete_failed，或工作区处于 deleting / delete_failed 时，未打 deleted_at 的下属工作区/作业仍在该父对象页面的列表中展示，标记“父级删除中”或“父级删除失败”，只读查看，不允许新建下级、改名、编辑配置、创建版本、执行或持久化配置文件。
- 全局工作区/作业列表也保留这些尚未完成删除的对象及父级状态提示，运行按钮禁用；不只在详情页禁用。列表计数包括尚未逻辑删除的这些行，避免列表总数与实际展示不一致。删除成功后按 deleted_at 退出普通列表。
- 列表/详情响应提供服务端计算的 effective_state、blocked_by（父级类型及 ID）和 blocked_reason，前端不通过额外异步请求猜测状态。历史版本/运行只读可查看；候选选择器不允许选择这些被冻结的父级或作业。
- 所有写接口在层级锁内检查父级状态。对父级 deleting / delete_failed 返回 HTTP 409 `parent_resource_unavailable`，附父级与任务 ID；当前对象已 deleted_at 非空时返回 410 resource_deleted。直接调用创建运行 API 同样受限，不能绕过禁用按钮。
- 源级知识清理虽不删除父级，也应通过既定冻结规则禁用其子级写入；不伪装成已删除，不影响只读历史。

父级失败时只提供父级原删除任务的重试入口，不能让用户另删一个子作业或修改配置绕过冻结。父级删除成功事务须同步标记下属对象，不能留下可操作的孤立子对象。

### 3.4 名称唯一性只约束未删除对象

当前 SQL 与 ORM 存在三条全量唯一约束：工作区 `(source_id, workspace_name)`、采集作业 `(workspace_id, job_name)`、发布作业 `(workspace_id, job_name)`。逻辑删除保留行后，这些约束会永久占用名称。本期明确替换成以下部分唯一索引，而不是保留原约束再叠加索引：

```sql
CREATE UNIQUE INDEX workspace_info_active_name_idx
ON public.workspace_info (source_id, workspace_name)
WHERE deleted_at IS NULL;

CREATE UNIQUE INDEX collection_job_info_active_name_idx
ON public.collection_job_info (workspace_id, job_name)
WHERE deleted_at IS NULL;

CREATE UNIQUE INDEX publish_job_info_active_name_idx
ON public.publish_job_info (workspace_id, job_name)
WHERE deleted_at IS NULL;
```

同步移除 SQL 建表脚本中的 `workspace_info_source_name_key`、`collection_job_info_workspace_name_key`、`publish_job_info_workspace_name_key` 三条原 UNIQUE 定义，ORM 的对应 UniqueConstraint 替换为带 `postgresql_where` 的唯一 Index。本项目不做旧数据迁移，因此直接修订建表定义，不提供线上旧约束迁移流程；不能只改服务层查重。

- 创建及改名的服务层查重均仅检查 deleted_at IS NULL；同步修订唯一冲突的异常识别，使并发同名写入仍返回原有名称冲突错误，而非通用 503。
- deleting / delete_failed 尚未完成删除，deleted_at 仍为空，继续占用名称。工作区与下属作业在删除成功的同一事务设置 deleted_at 后才释放；作业单独删除在其提交时释放。不能因任务失败提前释放名称。
- 采集作业与发布作业各自独立查重，保持现有大小写和字符串比较语义，不新增名称规范化规则。历史行之间可同名，历史展示和关联始终依赖 ID。
- 数据源 display_name 当前没有唯一约束，保持允许重名，不给它增加名称唯一索引。已删除的父级仍不能接收新工作区/作业；复用名称仅适用于有效父级。

确认文案补充“删除完成后可重新创建同名对象，新对象不继承原配置与运行历史”；历史详情同时展示名称与 ID，避免同名新旧对象混淆。

### 3.5 数据源删除完成后的字段清单

“最小登记”采用以下确定规则；只在源删除任务全部清理成功的最终 PG 事务应用。deleting / delete_failed 期间保留清理所需登记，不提前抹掉重试信息；单独清理已发布数据不改这些连接字段。

| db_source_info 列 | 删除完成后的值 |
| --- | --- |
| source_id | 保留原 ID，作为历史来源标识 |
| display_name | 保留原显示名称，便于追溯；仍要求非空，不要求唯一 |
| description | NULL，避免保留用户填写的连接或业务说明 |
| db_type | 保留 postgresql，作为历史类型标签，不表示可连接 |
| host、port、db_name、username | 全部 NULL，不保留连接目标和账号，不填 localhost、0 或假库名 |
| password_ciphertext | NULL，不保留密文或占位密文 |
| sslmode、db_version、selected_schemas | 全部 NULL，不保留连接选项、版本和范围 |
| is_active | false |
| created_by_user_id | 保留原值（当前通常 NULL） |
| created_at | 保留原值 |
| updated_at | 最终删除完成时间 |
| deleted_at | 最终删除完成时间，非空 |
| deletion_state | deleted |

SQL 与 ORM 将连接字段 host、port、db_name、username、password_ciphertext、selected_schemas 改为可空。增加显式条件约束：deleted_at IS NULL 时上述字段必须非 NULL，继续执行现有非空字符串、合法端口、非空 schema 数组及无 NULL 元素等校验；deleted_at 非空时连接字段及 sslmode/db_version/description 必须为 NULL，is_active 必须 false，deletion_state 必须 deleted。注意 PostgreSQL CHECK 的 NULL 不会自动失败，不能仅保留旧 CHECK 就认为有效源仍受保护。display_name、db_type 的约束保持，SQL 与 ORM 同步。

读取顺序固定为“删除/冻结状态 → 启用与连接完整性 → 解密/建连”。MetaWeave 先返回已删除或管理写入受限错误，不能先解密空密码，再将异常归类为 503。历史展示不复用要求完整连接字段的普通数据源响应模型；使用只含 ID、名称、删除标记的历史来源摘要。历史版本/manifest 可能仍记录当时库名或文件信息，本方案不是所有历史敏感信息的彻底擦除。

源的 deletion_state 为 NOT NULL，SQL 与 ORM 同步 CHECK：deleted_at IS NULL 时 deletion_state 只能为 active/deleting/delete_failed；deleted_at 非空时必须为 deleted。删除状态、连接字段的条件约束同时生效。不再增加独立的知识访问状态或知识清理时间字段；清理任务是否进行中或失败待重试，直接依据删除任务表判断。

## 5. 并发与执行流程

### 5.1 删除准入与锁

pending 和 running 都视为未结束，不能只检查 running：

- 删作业：存在该作业未结束运行则 409。
- 删工作区：工作区内任意采集或发布未结束则 409。
- 删数据源或清理知识：源下任意工作区未结束运行则 409。

仅 pending / running 阻断删除；success、partial_success、failed 均为运行终态，不阻断。删除预览与 409 响应返回全部阻断运行的类型、ID、状态、所属作业、创建/开始时间和详情入口，不能仅返回“有任务运行中”。

源删除/知识清理弹窗收到阻断运行清单后，每 3 秒以最新删除预览重新检查，同时提供“重新检查运行状态”按钮；检查失败保留原清单并明确提示，不能当作阻断已解除。服务端返回空清单后清除旧阻断列表和请求错误，提示可重新确认，并停止本轮检查；不得自动提交删除。弹窗关闭后停止检查，丢弃旧请求返回结果。阻断项链接携带 run_id，直接定位该次运行详情。前端检查仅用于及时展示，最终删除准入仍由服务端事务内复查决定。

删除接口不自动取消、强杀或修改运行终态。遗留运行按 §5.4 的本期离线故障处理闭环解除阻塞，不再依赖一个尚未建设的管理功能。

统一锁顺序：源行 → 工作区行（按 ID 排序）→ 作业行。删除事务中复查范围和未结束运行，再写删除状态。新建工作区、作业、版本、运行、步骤认领及会写文件的配置接口，都必须在相应锁与状态校验后提交，防止“检查完无运行又创建新运行”。现有工作区步骤锁并不足以替代此约定。

不持有 PG 行锁等待网络清理；提交 deleting 状态后再访问外部存储。实际执行前复查状态；后台遗留任务不得向删除范围继续写入。

### 5.1.1 统一加锁必须覆盖既有入口

当前 `backend/publishing/repository.py::lock_db_source_row` 只有定义，没有调用；采集/发布步骤认领及三类配置写回目前主要只锁工作区，创建运行没有对应的层级锁，`job_service.add_revision` 则先锁作业。这些现状不能直接当作已满足统一锁顺序。

新增共用层级锁辅助函数，统一采用源 → 工作区 → 作业 → 运行/任务行；同层多个对象按稳定主键顺序加锁（两类作业再固定 kind 顺序）。仅处理源的操作锁到源即可；创建新对象时锁其已存在的父级，无须锁尚未插入的行。禁止持有下级行锁再调用源锁辅助函数，包括原有仓储函数内部的隐式 FOR UPDATE。

只有工作区/作业/运行 ID 时，可先用普通 SELECT 查出父级 ID，这一步只用于定位，不作准入结论；随后从源开始加锁，重新读取并校验父子关系、对象状态、冻结状态和目标仍存在。不得为了查 source_id 先锁工作区/作业；发现定位信息已变化或目标已删除则退出，不在锁内反向追锁。

| 入口 | 必须修改的加锁点 |
| --- | --- |
| `backend/workspaces/service.py::create_workspace` | 锁源、复查未删除/冻结，再插入工作区；首次 mkdir 属于本地目录短操作豁免，保留在创建事务内，失败回滚 |
| `backend/jobs/job_service.py::create_job` | 锁源 → 工作区，复查后插入作业和首版 |
| `backend/jobs/job_service.py::add_revision` | 普通查询定位父级，改为锁源 → 工作区 → 作业，再执行 max+1 和版本插入；替换现有先 lock_job 的顺序 |
| `backend/jobs/collection_run.py::create_collection_run` | 锁源 → 工作区 → 采集作业，复查引用版本和有效配置，同一事务创建 pending run/step |
| `backend/publishing/publish_service.py::create_publish_run` | 锁源 → 工作区 → 发布作业，锁内复查准入和预检结果，再创建 pending run/step |
| `collection_run.py::_claim_step`、`publish_service.py::_claim_publish_step` | 原工作区锁改为源 → 工作区，按需再锁作业/运行，复查状态后认领；锁内不得调用 LLM 或外部存储 |
| `publish_service.py::_publish_db / _publish_ddl / _publish_json / _publish_domain / _publish_rel` | 核查并替换所有直接工作区 FOR UPDATE，先锁源再锁工作区；PG 内容落库前复查，禁止从这些路径反向取得源锁 |
| `publish_service.py::_publish_table_schema / _publish_dim_value / _publish_sql` | 外部写入不持层级行锁；短事务校验/取得执行所需快照后关闭 session，再调用 loader；步骤和整体运行保持 running，完成写入后另开短事务记录成功 |
| `backend/profile_loading/domain_config_api.py::write_domain_config` | 源 → 工作区，锁内复查未删除、无清理冻结和既有写入条件，再按原原子替换流程保存 |
| `backend/profile_loading/dim_value_config_api.py::write_dim_value_config` | 同上；即使前端已不提供持久化入口，后端 PUT 仍需保护 |
| `backend/profile_loading/rel_config_api.py::write_rel_config` | 同上，保留原指纹并发校验，不能用层级锁替代 409 rel_regenerated |
| 源/工作区/作业的修改名称、启停等写入口 | 源级修改先锁源；子级修改按完整层级顺序锁定并复查，不能绕过冻结 |
| 删除提交、重试、失败收尾、离线遗留运行收尾 | 同样先锁源，再按需要锁工作区/作业/运行或任务；任务状态和父级冻结状态在同事务更新 |

以上是必须逐项改造的调用点，不是只新增一个函数后由实施者按需使用。状态写入、版本插入等下层仓储函数由上层事务持锁调用，不自行建立相反顺序。采集实际产物写入及 marker 收尾依靠“运行 pending/running 全程阻断删除”保护，并复查父级状态，不能先把运行置终态再写文件。

**锁的生命周期。** 层级行锁只用于短事务准入、状态变更及 PG 落库。删除任务在提交冻结和认领后释放所有行锁，再访问 Milvus / Neo4j / 文件系统；每步记录进度时另开短事务。不跨外部 I/O 持有源、工作区、作业或任务行锁。首次工作区 mkdir 和三类配置保存的本地短文件原子替换是已明确的有限例外；不包含递归删目录、LLM 或外部存储调用。

`_publish_dim_value` 当前在 platform_session 内解密并调用 Milvus loader；必须先在短事务提取所需配置和凭据、完成准入，再退出 session 后 validate/load/close，不允许在原 with 块直接加源锁后跨外部 I/O 持有。三类向量发布均保持运行未终态至最后一次写入完成，再短事务收尾；删除由 pending/running 准入阻断。

原 `_publish_rel` 的工作区锁事务包住文件生成与 Neo4j 调用，改造时不能简单在外层再套源锁；需拆成锁内校验/认领 → 提交 → 执行 → 短事务复核并记结果，保留已有产物指纹和失败语义。三类配置文件保存可保留其原有短文件原子替换临界区，但不允许将该锁扩展到 LLM、向量加载或图发布过程。

### 5.2 作业与工作区删除

作业：锁内校验无未结束运行，设置 deleted_at，提交即可；历史表不物理级联删除。

工作区：锁内校验后置 deleting，下属作业立即禁止使用；创建删除任务。删除工作区目录成功后，在 PG 事务中标记工作区及所有下属作业 deleted_at，工作区置 deleted。文件失败则 delete_failed，阻止新写入并允许重试。目录已不存在视为成功。

工作区单独删除的状态明确如下（不适用于整源删除的源级冻结）：

| 阶段 | 工作区 deletion_state | 工作区 deleted_at | 源状态 |
| --- | --- | --- | --- |
| 首次提交 / 重试提交 / 执行中 | deleting | NULL | active，保持不变 |
| 失败（含启动扫描或重试检查判中断） | delete_failed | NULL | active，保持不变 |
| 全部成功 | deleted | 非空，同步标记下属作业 | active，保持不变 |

工作区重试将任务改 pending 与工作区 delete_failed → deleting 放在同一短事务；不能等任务最后成功才更新页面状态。失败/成功同样与任务终态原子提交。工作区流程不修改源状态；同源任务互斥仍按 §7.1 执行。

工作区删除后，其已有成功发布仍可作为源级知识来源；仅凭工作区退出列表不能把实际尚存的知识判成未发布。

### 5.3 数据源删除与源级清理

1. 锁内校验无未结束运行，在同一 PG 事务创建持久化任务；源删除同时置源 deletion_state=deleting，独立知识清理保持源 active。任务提交后即限制该源的 MetaWeave 管理写入。
2. 清理 Milvus 三类目标集合中的该源记录。
3. 清理 Neo4j 中该源节点及其关系。
4. 在 PG 单事务删除该源全部画像内容，记录任务步骤进度；此时任务尚未完成，不提前开放管理写入。
5. 源删除还需删除源采集根目录；单独知识清理跳过文件步骤。
6. 全部成功后，在同一 PG 事务中将源及所有尚未删除的下属工作区同时设置 deleted_at 和 deletion_state=deleted，并给尚未删除的下属作业设置 deleted_at；已删除对象保留原删除时间。不得只给工作区写 deleted_at 而遗留 active/deleting/delete_failed。源同时按 §3.5 清除连接字段；独立知识清理将任务置 success，允许后续重新发布。

| 动作与阶段 | 源 deletion_state | MetaWeave 管理写入依据 |
| --- | --- | --- |
| 源删除提交 / 重试 / 执行中 | deleting | 源状态与 pending/running 任务阻断 |
| 源删除失败或判中断 | delete_failed | 源状态与未解决 failed 任务阻断 |
| 源删除全部成功 | deleted | deleted_at 阻断 |
| 独立知识清理提交 / 重试 / 执行中 | active | pending/running 清理任务阻断 |
| 独立知识清理失败或判中断 | active | 未解决 failed 清理任务阻断 |
| 独立知识清理全部成功 | active | success 任务不再阻断 |

任务与相应对象状态在同一短事务更新。失败只允许重试原动作、不提供取消：例如源删除卡在目录时，MetaWeave 仍显示失败并阻止该源新写入，直到重试成功。

每一步可幂等重试，已经不存在的记录/目录视为成功。访问失败、权限错误不能当成“不存在”。任意失败保留任务与目标对象，显示具体失败存储和重试按钮，不提示“删除成功”。

PG、Milvus、Neo4j、文件系统之间不存在同一事务；不承诺失败时自动恢复已删除部分。清理任务期间禁止相关管理写入。

### 5.4 遗留运行的解除阻塞方式（本期必须实现）

**问题确认。** `backend/jobs/collection_run.py` 和 `backend/publishing/publish_service.py` 的后台入口只执行本次提交的运行，进程重启后不扫描或接管遗留 pending / running。采集步骤认领明确忽略其他 pending；这是执行冲突与删除准入的有意区别，不能通过让删除也忽略 pending 来修复。`backend/jobs/home.py` 当前状态计数没有 pending，但最近运行列表仍可能包含它，不能笼统说该运行在所有页面均不可见。

**本期选择：提供小型离线维护脚本，不增加在线“强制失败”按钮。** 当前没有执行者身份、心跳或租约，单凭状态、运行时长、后端刚刚重启或当前进程里找不到任务，均不能证明其他进程已停止执行。仅把数据库状态改为失败也不能终止线程、子进程或已经发出的外部写入。在线安全终止及执行租约不在本期扩展。

已实现 `metaweave/scripts/resolve_orphaned_run.py`，只处理显式指定的一条采集或发布运行，参数包括 kind、run_id、必填 reason；`--database` 可明确指定平台库，输出回显目标库名。默认只预览；实际变更要求 `--apply --confirm-executors-stopped`，不提供按时长自动判断、批量一键失败或删除时隐式调用。

对于全部步骤已结束、仅整体状态漏收尾的记录，增加 `--finalize-only`：要求非空步骤且全部为 success/failed/blocked；遇到未结束或未知步骤状态则拒绝，不能把该模式降级为步骤强制失败。预览展示源/工作区/作业/运行 ID、整体与逐步骤状态/时间、计划最终状态与拒绝原因。应用时按源 → 工作区 → 作业 → 运行 → 步骤加锁并刷新已有 ORM 对象，按原规则汇总，仅更新整体终态、结束时间并追加处理说明；缺失的历史开始时间保持空值，步骤结果与 manifest 不变。使用说明及隔离实库测试方法见 [运行状态修复说明](../metaweave/docs/operations/run_status_repair.md)。

运维操作顺序：

1. 安排维护窗口，停止接收新的采集/发布请求；停止所有连接同一平台库、可能执行这些任务的 API 实例、后台执行进程及相关子进程。确认旧执行者不会继续写 PG、Milvus、Neo4j 或采集目录；不能只关闭浏览器或停止一个实例。
2. 使用脚本预览删除弹窗列出的运行 ID，核对范围及步骤状态。脚本的确认参数是运维承诺，不是它自动探测到执行者已停止；这一前置条件不能省略。
3. 确认无执行者后应用收尾：在源 → 工作区 → 作业 → 运行行的锁顺序下复查，只有运行仍为 pending / running 才可处理。步骤 running 改为 failed，步骤 pending 改为 blocked；保留原有 success / failed / blocked 步骤和所有参数、manifest。为本次变更的步骤填写 finished_at，并在步骤及运行 message 记录原状态、处理时间和必填原因，明确“执行者已停止，实际外部写入结果未核验”。
4. 脚本必须显式写入运行 message 及本次变更步骤的 message（含原状态、处理原因、执行者已停止及外部写入未核验）；`finalize_run` 不写 message，不能依赖它自动记录原因。随后全部步骤收尾后复用 `run_repository.finalize_run` 按既有规则汇总运行终态、填写 finished_at：有成功且有失败/阻断为 partial_success，无成功为 failed；若步骤原本全部成功，只是运行汇总未完成，则可汇总为 success。不要为了统一显示 failed 而覆盖真实成功步骤。变更在一个 PG 事务中提交；遇到已有终态则不修改、返回“无需处理”，重复执行幂等。
5. 脚本不删除文件、不重写采集 marker、不清理发布内容，也不声称已经回滚。中断可能留下部分产物或已写入知识；需要继续使用时重新采集/发布核验，需要删除时重试本方案的删除/源级清理流程。
6. 恢复服务后重新预览并执行删除；若出现新的 pending / running，仍按正常准入拒绝，不能沿用上一次预览放行。

本期上线必须同时交付该脚本、使用说明和测试；不能只在报错中让用户“联系运维手改数据库”。没有运维停止执行者的条件时，继续阻断是预期行为，不提供不安全的绕过按钮。

**补齐可见性。** 首页采集、发布状态统计均增加独立 pending（“等待执行”）计数并同步响应模型、前端类型与展示，不混入 running。作业运行列表保留 pending / running 的可见状态；删除弹窗直接展示阻断项，即使该运行已不在最近列表也能定位。无需为了本问题增加完整运行管理页面。

## 6. 各存储清理实现

### 6.1 PG

使用参数绑定，严格 `WHERE source_id = :source_id`：依次删除 table_column_profile、table_profile、table_definition（包含所有 define_type）、table_domain、db_profile。也可依赖现有字段画像 CASCADE，但显式列出范围便于统计核验。

保留发布运行，避免触发 publish_run_id 外键冲突，也保留审计来源。修复现有 purge_source_profiles 遗漏 table_domain 的问题；不得保留旧接口绕开新清理流程。

### 6.2 Milvus

复用实际加载器使用的连接和配置定位三类 collection，目标身份必须包含 `vector_database.providers.milvus` 的 host、port、database 以及 collection；其中 database 即 `providers.milvus.database`（环境变量 MILVUS_DATABASE）。清理、计数核验与任务目标配置指纹必须显式携带解析后的 `providers.milvus.database`（当前配置默认值为 `nl2sql`），不能省略该维度，也不能仅凭同名 collection 判断目标。使用精确过滤：

```text
source_id == "db_src_68"
```

source_id 来自服务端校验过的对象，不能使用客户端传入的任意表达式。删除该源所有 publish_id，包括失败发布留下的部分数据，不只清最近成功批次。

复用项目现有 `delete_by_expr` 能力，按 SDK 实际支持的读一致性执行剩余数量核验；删除响应的数量不等于查询端已确认不可见。缺失集合属于无数据，连接失败不是。禁止 drop collection、truncate、删除其他源或清理所有空 source_id 数据。

### 6.3 Neo4j

使用参数化 Cypher：

```cypher
MATCH (n) WHERE n.source_id = $source_id
DETACH DELETE n
```

同一事务额外清理由该源标记但端点未被删除的关系，并核验该源节点/关系均为零。`DETACH DELETE` 还会删除与目标节点相连的关系；确认页说明这一语义，跨源引用该节点的边也不可能保留为悬空边，其他源节点必须保留。

不能直接复用 CqlLoader 的 `_CLEAN_NODES`：现有表达式额外包含 `n.source_id IS NULL`，会扩大删除范围。本功能只清目标源，不处理旧数据或无归属图数据。

### 6.4 文件

目录解析函数明确区分：

| 删除范围 | 必须使用的函数 | 实际目录 |
| --- | --- | --- |
| 一个工作区 | `resolve_workspace_root(source_id, workspace_id)` | `output/<source_id>/<workspace_id>/` |
| 整个数据源 | `resolve_source_workspace_dir(source_id)` | `output/<source_id>/` |

两个函数均在 `metaweave/core/clean_targets.py`。后者名字虽含 workspace，实际解析整个源树，严禁用于单工作区删除。当前受管步骤目录使用 dim/、sql/，不是旧 dim_config/、sql-rag/。

仅删除明确归属的采集树。校验规范短 ID、根目录包含关系；拒绝符号链接逃逸，不能根据客户端路径或 input/output_manifest 执行任意删除。

不删其他工作区、共享配置、程序目录、全局日志、源业务数据库。父级数据源删除可一次清理整个源采集树；工作区删除只能清其子树。

### 6.5 历史展示与本期边界

历史成功步骤表示“当时发布成功”，不代表内容现在仍存在。清理不修改历史运行终态，清理任务本身展示已清理的存储、步骤和时间；MetaWeave 页面不得仅凭历史成功记录提示本次清理未生效。保留现有发布历史视图供追溯，不提供历史知识版本恢复。

## 7. 删除任务与 API

新增 `resource_deletion_task`，最小字段：task_id、action（delete_source/delete_workspace/clear_source_knowledge）、target_id、source_id、workspace_id（可空）、status（pending/running/failed/success）、step_results JSONB、error_message、created_at、queued_at、started_at、finished_at、requested_by_user_id（当前可空）。

时间字段契约：`created_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP`、`queued_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP`，SQL 建表与 ORM 的 nullable/server_default 同步声明。首次插入二者使用同一插入事务的数据库当前时间（可由两个默认值生成），不得显式写 NULL 或使用应用进程时间；只有插入任务成功提交后才能返回 202。queued_at 的非空由数据库保证，不在保护期查询中用 NULL 兜底或将 NULL 判成超时。

每次重新入队在条件更新为 pending 的同一事务显式设置 `queued_at=CURRENT_TIMESTAMP`，保留原 created_at；字段默认值不会在 UPDATE 时自动刷新。保护期使用数据库当前时间与 queued_at 比较，未满 15 秒禁止收口，满 15 秒后仍须按 §7.2 探锁并复查。

step_results 记录各存储/目录的状态、实际目标配置标识、计数、错误；不保存密码。首次任务固定服务端解析的目标存储配置指纹。重试发现目标变化时，在重新入队前返回 409 `deletion_targets_changed`，details 包含 `previous` / `current`（Milvus host、port、database、三个集合，Neo4j URI、database 及各自指纹），此时不派发清理、不改变任务状态。前端弹出原/当前目标对比，突出变化项；返回或关闭确认不执行任何清理，用户点击“确认继续删除/清理”后才提交确认。源级完整删除只覆盖用户本次确认的目标配置；切换到不同服务时，原目标中尚未清理的数据会保留，不能宣称自动发现或清理历史集群。

`POST /api/deletion-tasks/{task_id}/retry` 保持无请求体重试兼容；确认目标变化时提交 `{"target_confirmation":{"previous_fingerprint":"<原目标指纹>","current_fingerprint":"<当前目标指纹>"}}`。后端在任务执行锁与源行锁内重新读取配置，同时核对两个指纹；任一变化则重新返回最新对比，不能用一次确认允许任意后续配置。确认通过后，在同一个重试事务中更新 `_targets`、归档 `_target_changes`（确认时间、原/新目标及原步骤结果）、清除当前步骤结果和旧错误并重新入队，新目标从第一步重新清理。实际执行仍核对配置指纹，确认到执行之间配置变化同样停止，不沿用旧目标的成功状态。工作区删除只清理目录，不进入存储目标确认流程。

本期可复用现有 FastAPI BackgroundTasks 执行方式，但任务先入 PG。进程重启后未完成任务按 §7.2 标记可重试中断，启动不自动接着删除；不依赖内存保存进度，不引入分布式任务平台。相同目标的重复请求返回已有任务，不创建并行删除。

### 7.0 任务找回：对象响应附带摘要

采用对象列表/详情附带摘要，不新增按条件搜索删除任务的接口，不依赖 localStorage、页面内存或最初 DELETE 的 202 响应保存任务 ID。

- 数据源列表和详情响应增加 `deletion_task`（对象或 null）：返回同源 pending/running 或未解决 failed 任务的摘要，覆盖 delete_source、delete_workspace、clear_source_knowledge 三种 action。工作区任务必须携带 workspace_id，以便说明“工作区 A 删除中”，不能据此把整个源显示为删除中或禁用兄弟工作区写入。
- 工作区列表和详情响应增加相同字段：只返回目标为该工作区的 delete_workspace，或覆盖该工作区的 delete_source / clear_source_knowledge 任务；不得附上兄弟工作区的删除任务作为本工作区阻断项。
- 摘要固定包含 task_id、action、status、source_id、workspace_id（可空）、target_id、error_message（可空）。删除状态与范围提示按 §7.3 计算，任务摘要存在不等于整源冻结。
- 摘要由服务端根据任务表获取。当前活动任务优先，否则返回尚未解决的失败任务；不返回已成功任务或已解决的旧失败记录作为当前任务。同源提交互斥及只重试原任务的规则保证不会有多个未解决任务；不添加第二套“当前任务 ID”主表字段。
- 前端每次首次加载或刷新对象列表/详情，先从摘要恢复 task_id，再调用 GET /deletion-tasks/{task_id} 获取完整进度、can_retry 和原因并恢复轮询。可重试性仍由 §7.2 计算，不要求对象列表逐行探执行锁。浏览器重开后同样可找回失败任务。
- deleting/delete_failed 对象的只读列表/详情必须继续返回摘要，不能提前隐藏或统一返回 410；删除完成后才按既定 deleted_at 规则退出普通列表、详情返回 410。若轮询已经成功则展示完成结果并刷新对象列表；不为了重新打开已完成任务增加历史任务中心。

实现落点：`backend/api/schemas.py`、数据源/工作区列表及详情服务、`frontend/src/api/types.ts` 与对应页面同步任务摘要契约；分页列表批量查询关联任务，避免逐行独立查询。沿用 §3.2 已规定的独立清理任务摘要，统一为本节 deletion_task，不同时维护另一份不同格式的字段。

### 7.1 同源互斥与执行认领

“先查有没有任务，再插入”不能作为互斥保证。所有三类删除/清理任务的 source_id 均 NOT NULL，在 SQL 建表脚本和 ORM 同步声明以下**部分唯一索引**（PostgreSQL 的条件唯一通过索引实现）：

```sql
CREATE UNIQUE INDEX resource_deletion_task_one_active_source_idx
ON public.resource_deletion_task (source_id)
WHERE status IN ('pending', 'running');
```

该索引覆盖不同工作区删除与源级删除/清理，刻意将同源不同工作区删除任务也串行化，减少本期并发组合；仅约束删除/清理任务创建和重试，不阻止兄弟工作区普通采集、发布等写入。源行锁用于统一业务准入，部分唯一索引是数据库最终防线，二者都保留。

- 提交：源锁下复查所有活动任务及失败冻结，再插入 pending 任务、更新对象冻结状态，同事务提交。唯一冲突需在 savepoint 或事务回滚后查询冲突任务，不能在已失败事务中继续 SELECT；同 action/target 返回已有任务，不同目标返回 409 deletion_in_progress 并附冲突任务 ID。
- 失败：failed 不占活动索引，但不解除已有冻结。锁源后若有未解决的失败任务，则新动作也返回 409，仅允许重试该失败任务；不能通过换 action、换工作区或再点删除创建另一条任务绕过冻结。源级 failed 和工作区级 failed 均按此同源互斥处理。
- 认领：后台执行前用 `UPDATE ... SET status='running', started_at=... WHERE task_id=:id AND status='pending' RETURNING task_id` 在短事务内原子认领。只有返回一行的执行者可以进入清理；返回零行则退出，不重复执行。父级状态检查按 §5.1.1 的锁顺序在同一短事务完成，先提交认领再做外部 I/O。
- 重试：锁源后检查无其他活动任务，按本节目标变更确认流程完成核对，将同一失败任务以条件更新从 failed 改回 pending；同时按 §5.3 恢复源删除/知识清理的执行态；工作区删除按 §5.2 将工作区置 deleting（源知识状态不变）。将 queued_at 更新为本次入队数据库时间，重置本次 started_at/finished_at 并清除旧错误；不新建任务，原步骤和目标在切换目标时归档保留。与其他请求冲突仍由部分唯一索引兜底。
- 执行锁：每个任务执行者在认领前非阻塞取得独立的 task_id session advisory 锁，持有至执行和收尾结束。未取得则不认领、不执行；连接断开释放。中断判定与重试按 §7.2 处理。旧执行者若丢失锁连接必须停止后续清理，不得自行重连继续；已发出的外部调用可能完成，故步骤仍须幂等，不能承诺跨存储恰好执行一次。

**执行锁键与连接约定（所有调用共用一份实现）。** 在 `backend/deletion/task_lock.py` 封装 `task_lock_key` 和锁连接上下文，执行者、详情探测、启动扫描、重试全部调用，不自行散写 SQL：

```python
from hashlib import sha256
from uuid import UUID

def task_lock_key(task_id: UUID | str) -> int:
    canonical_id = str(UUID(str(task_id)))
    payload = ("metaweave:resource_deletion_task:v1:" + canonical_id).encode("ascii")
    return int.from_bytes(sha256(payload).digest()[:8], "big", signed=True)
```

使用单 bigint 形式的 `SELECT pg_try_advisory_lock(%s)` 与 `SELECT pg_advisory_unlock(%s)`，均绑定上述有符号 64 位键。禁止 Python hash()、各处自行截 UUID 或混用双 int 键。固定测试向量验证 UUID 对象、大小写 UUID 字符串规范化后键一致，不同进程结果相同。散列极低概率冲突最多导致无关任务暂时不能获锁，不能放宽成无锁执行。

执行锁使用连到**同一平台库**的专用物理 PG 连接（例如 psycopg.connect，autocommit=True），不从普通 SQLAlchemy 业务连接池借出长期占用，不经事务级连接池代理。整个任务含 Milvus/Neo4j/文件 I/O 期间保持该连接；同一源最多一个活动任务，不代表全局只占一条连接，不同源并行任务各占一条，部署连接数预算需计入。此处不增加额外任务调度器。

该连接只持 session 锁，不承载业务事务，不长期保持事务快照；任务状态、进度仍经普通短事务提交。try/finally 在原连接显式解锁后关闭，获取失败也关闭。详情探测、扫描、重试同样使用短生命周期专用连接，不能解锁后把曾持 session 锁的连接放回普通池轮转。连接故障按现有失败/中断规则处理，禁止重连后假定旧锁仍持有；后续写入前确认专用锁连接仍有效，失效即停止后续动作。

任务 advisory 锁的非阻塞获取在进入层级行锁事务前完成；失败立即退出，不持下级行锁等待它。进度/完成/失败写入只用短事务，任务执行锁不授权绕过父级状态复查。

### 7.2 重启后的中断识别与重试

本期明确增加启动恢复扫描，但**只修复状态，不自动执行清理**：

1. pending 认领保护期定为 **15 秒**，从 queued_at 算起，首次入队与每次重试都由数据库写入新值；created_at 保留原任务创建时间，不用于重试保护期。所有接口/启动扫描按同一数据库时钟判断，不用各实例本地时间。
2. 应用启动扫描按状态区分：running 非阻塞取得 task_id 执行锁后，按层级锁顺序复查仍为 running，才条件更新为 failed，原因“执行已中断，等待人工重试”；pending 在保护期内直接跳过，即使锁空闲也不判失败。pending 超过保护期且能取得执行锁，锁内复查仍为 pending 且最新 queued_at 仍已过期，才标 failed，原因“认领等待超时，可重新派发”。保留步骤进度和目标配置；已有终态不修改，其他实例持锁则跳过。超过保护期只表示允许重新派发，不证明原进程死亡；这是尚未认领的调度保护规则，不能用于 running 的超时接管。
3. 同一事务按 §5.3 状态表将对应源/工作区置失败冻结：源删除为 delete_failed，知识清理保持源 active，工作区删除为工作区 delete_failed；失败任务按 §7.3 的 action/目标范围继续阻止管理写入，工作区删除失败不得冻结兄弟工作区。中断标失败释放活动唯一索引，但按 §7.1 仍禁止另建任务绕过失败冻结。提交后释放执行锁。
4. 管理页面显示失败原因及“重试”。重试接口接受 failed；若任务仍为 pending / running（启动扫描遗漏、运行中进程稍后退出等），接口先检查 pending 保护期，未到期则 409 task_pending_claim；其余按上述状态/锁规则复查，活跃锁未释放则 409 task_still_running，不能一直只返回原任务而没有解除路径。确认中断后先标 failed，再按 §7.1 将同一任务改回 pending，提交后安排后台认领。
5. 不提供定时强制超时接管。多实例同时扫描/重试由任务执行锁、源行锁、条件更新及部分唯一索引共同保证幂等；扫描失败记录日志并保留状态，页面仍能通过第 4 条显式重试，不因扫描失败失去恢复入口。

任务详情按下表计算可重试性，前端轮询即可发现遗留任务，无需其他实例重启：

| 状态 | 判断 | can_retry / 页面提示 |
| --- | --- | --- |
| pending，距本次 queued_at 未满 15 秒 | 不以空闲锁判断中断 | false，“正在排队” |
| pending，已满 15 秒 | 非阻塞探 task_id 执行锁 | 取得锁则 true，“认领等待超时，检查并重试”；未取得则 false，“正在认领” |
| running | 非阻塞探 task_id 执行锁 | 取得锁则 true，“检查并重试”；未取得则 false，“仍在执行” |
| failed / success | 无需探锁 | 分别 true / false |

探测取得锁后立即释放，不认领、不改任务状态，不能把锁带回连接池。取得锁说明探测时无人持执行锁，对 pending 不等于进程已死亡。重试接口不能相信详情响应：必须重新取得任务执行锁、按层级行锁顺序复查状态及最新 queued_at；入队时间已更新则重新遵守保护期，锁被占则 409 task_still_running。探锁连接故障返回依赖不可用，不默认可重试。

超过保护期后，原 BackgroundTasks 回调仍可能延迟到达；它与新回调必须使用同一任务执行锁和 pending → running 条件认领，不得绕过认领直接清理。收口与重新入队在源锁下串行：原回调若先认领成功，重试不得接管；若收口先完成，回调只能在任务重新 pending 后参与同一任务的原子认领，最多一个执行者实际清理。不以旧回调是否还存在作为正确性前提。此处不引入额外调度器或进程心跳。


建议 API（遵循现有 /api 前缀）：

| 方法与路径 | 作用 |
| --- | --- |
| GET `/data-sources/{id}/deletion-preview` | 源删除范围、阻断运行、目标存储 |
| DELETE `/data-sources/{id}` | 替换既有删除实现；202 返回任务 |
| POST `/data-sources/{id}/published-data/clear` | 源级知识清理；202 返回任务 |
| GET `/workspaces/{id}/deletion-preview` | 工作区影响范围 |
| DELETE `/workspaces/{id}` | 工作区级联删除；202 返回任务 |
| DELETE `/collection-jobs/{id}` | 采集作业逻辑删除；204 |
| DELETE `/publish-jobs/{id}` | 发布作业逻辑删除；204 |
| GET `/deletion-tasks/{task_id}` | 删除进度 |
| POST `/deletion-tasks/{task_id}/retry` | 复查准入后重试失败/中断任务 |

预览不是执行授权快照：执行时必须重新检查依赖和运行。工作区/数据源确认 ID 在请求体中传入；同源所有清理任务互斥，源级清理与下属工作区删除也互斥。

### 7.3 统一错误码与管理写入准入

| 场景 | HTTP | 稳定错误码 | 使用方 |
| --- | --- | --- | --- |
| 管理对象不存在 | 404 | resource_not_found | MetaWeave |
| 管理对象已删除 | 410 | resource_deleted | MetaWeave |
| 范围内有 pending/running 作业运行 | 409 | resource_has_unfinished_runs | MetaWeave |
| 父级 deleting/delete_failed，子级写入被阻断 | 409 | parent_resource_unavailable | MetaWeave |
| 同源 action=clear_source_knowledge 任务 pending/running 或失败待重试，管理写入被阻断 | 409 | source_knowledge_frozen | MetaWeave |
| 同源另一删除任务占用或失败待原任务重试 | 409 | deletion_in_progress | MetaWeave |
| pending 尚在 15 秒认领保护期 | 409 | task_pending_claim | MetaWeave |
| 重试时任务执行锁仍被持有 | 409 | task_still_running | MetaWeave |
| 请求含废止的 delete_output 或确认参数非法 | 400 | invalid_request | MetaWeave |
| 删除依赖读取或锁服务确实不可用 | 503 | deletion_dependency_unavailable | MetaWeave |

管理写入按以下范围和顺序判断，不把任意同源任务都视为整源冻结：

1. 源已 deleted_at 非空/状态 deleted，返回 410 resource_deleted；源 deleting/delete_failed 阻断整个源的管理写入，下属写接口返回 409 parent_resource_unavailable。自身或其他祖先已经逻辑删除的对象也仍优先返回 410。
2. 源存在 action=clear_source_knowledge 且 status 为 pending/running 或未解决 failed 的任务，阻断整个源的管理写入，返回 409 source_knowledge_frozen。任务查询必须显式过滤 action，不能只按 source_id 和状态匹配。
3. 仅有 action=delete_workspace 的任务，按目标 workspace_id 限制该工作区及下属对象：deleting/delete_failed 时子级写入返回 409 parent_resource_unavailable，删除成功后已删除对象返回 410。兄弟工作区正常采集、发布、配置保存和创建作业；源本身及新建其他工作区也不因该任务被整源冻结。

以上覆盖创建工作区/作业/版本/运行、配置写回及普通修改，前端按钮和服务端层级锁内复查使用同一作用域。删除任务自身的提交、认领、进度和重试按 §7.1 专门准入：同源任务互斥仅限制新增/重试删除清理任务，不等于冻结该源所有普通写操作。已删除优先于冻结，状态异常不默认放行。

MetaWeave 同步错误响应模型、前端文案及重试提示。任务后台失败通过任务详情体现，不伪装成请求阶段 503；HTTP 202 只表示已受理。

### 8.1 统一访问守卫与列表过滤的实现载体

新增轻量共用模块 `metaweave/backend/access_guards.py`，由业务服务调用，路由只负责错误映射，不在三十多个端点复制判断。不引入全局 ORM 隐式过滤器或权限框架。

- 各 repository 保留明确命名的 `get_*_raw` 能力，按主键读取包含逻辑删除的行，供定位、历史和删除任务使用；不要将全部 session.get 一刀切改为排除历史。
- 守卫提供 `require_source / require_workspace / require_job`，普通访问按层级读取并判断：不存在 404，目标或祖先 deleted_at 非空/状态 deleted 返回 410 resource_deleted。守卫读取包含已删除行，才能区分“已删”和“不存在”，不能用过滤后的 get_active_* 将两者都变成 404。
- 只读守卫允许 deleting/delete_failed 详情返回对象和 deletion_task。写入守卫增加 §7.3 的父级及 action 范围检查，分别返回 parent_resource_unavailable / source_knowledge_frozen。写服务在 §5.1.1 的层级锁取得后再次调用同一校验逻辑；仅入口读一次不替代锁内复查。
- 在 `metaweave/backend/data_sources/repository.py`、`metaweave/backend/workspaces/repository.py`、`metaweave/backend/jobs/job_repository.py`、作业列表/统计仓储查询中收口普通列表的 deleted_at 过滤。跨层列表对作业、工作区、源逐级过滤已删除祖先；仍展示尚未完成删除的 deleting/delete_failed 对象并计算禁用原因。分页 total、名称查重、首页计数和候选列表复用相同有效行条件，避免结果与总数不一致。
- `metaweave/backend/api/routers/{data_sources,workspaces,assets,asset_objects}.py` 对应服务、三类配置读写服务、采集/发布创建及执行服务均接入守卫。资产只读入口按源检查删除状态，源删除成功返回 410；独立知识清理或 deleting/delete_failed 不额外屏蔽资产读取，仍按实际 PG 内容显示。执行相关接口不能因走了不同服务直接 session.get 而漏检。
- 实施时对这几类路由做一次入口清单核对，并搜索直接 `session.get`、旧 `_require_workspace` 等调用：普通访问接共用守卫，历史/删除内部路径明确使用 raw；不是要求禁止所有原始查询。创建接口和候选接口同时检查祖先，不能只保护 PATCH/PUT。

### 8.2 历史来源摘要的响应落点

在 `metaweave/backend/api/schemas.py` 新增 `HistorySourceSummary`：source_id、display_name、deleted（布尔）。不含连接字段，不要求完整连接配置；历史解析不解密、不建连。

- `CollectionRunDetail` 及继承的 `PublishRunDetail` 增加 `source_summary: HistorySourceSummary`，由 `metaweave/backend/jobs/run_detail.py::_run_detail` 沿运行 → 作业 → 工作区 → 数据源 raw 解析后填充。前端运行详情使用该字段展示来源及已删除标记。
- `JobItem` 增加同名摘要，由作业详情服务填充，供保留的版本历史只读访问显示。普通作业详情仍通过守卫、已删除返回 410；只有明确的版本列表/版本详情/运行历史接口可对已删除作业 raw 读取，返回的配置版本不含连接模型。
- 独立的版本列表/详情响应同样在外层增加 source_summary，schemas 中的 RevisionListResponse 及单版详情响应同步定义；若单版当前直接返回版本项，则扩展该响应项，不要求前端先请求一个已被 410 拦住的普通作业详情来取得摘要。

历史接口是明确白名单：按 ID 的运行详情、版本列表/详情、作业运行历史允许已删除父级的只读访问；其他普通详情、编辑、运行创建、资产和配置接口不借此放宽。历史代码不调用普通守卫，也不得复用普通数据源详情响应模型。保留行若异常缺失应返回实际历史来源缺失错误，不伪造名称或连接信息。

先完成后端范围、锁和失败恢复，再接按钮。开发期间不对真实业务数据源试删；测试边界按以下规定执行，不能笼统假设所有存储都可通过 database 名隔离。

### 8.3 删除功能的测试环境边界

- 正式 Neo4j 为 Community 单库部署，不支持在该实例新建隔离数据库。图清理、跨源隔离及故障重试主要使用 fake 驱动单测：核对参数化 Cypher、source_id 范围、执行顺序、异常与计数；正式图仅可只读核验标签、归属字段及数量，不执行测试性 DELETE、DETACH DELETE、DROP 或发布覆盖。
- 本次新增或改动的 live 删除测试必须显式开启（例如 METAWEAVE_DELETION_LIVE=1），且实际解析后的 PG database 必须精确为 `metaweave_rehearsal_final`（PLATFORM_DB_NAME）。门控在 fixture 创建源、写文件或调用 loader 之前执行；仅存在 PLATFORM_DB_* 配置不算获准。默认运行单测不访问真实存储。
- `PLATFORM_DB_NAME=metaweave_rehearsal_final` **只隔离 PG，不隔离 Neo4j 或 Milvus**。PG 演练测试继续注入 fake 图/向量适配器；不得因 PG 演练门控通过就调用正式图清理。若需要真实图删除演练，只能另配明确的专用演练 Neo4j 实例，校验其连接目标不是正式实例；未提供该实例时跳过图 live 用例，不为通过测试修改正式图。
- Milvus live 可使用独立演练 database，通过 MILVUS_DATABASE 和上述配置指定。测试明确校验该 database 与正式配置不同，所有写入、清理及核验使用该 database 中的专用测试源；不改正式 database，不删除整个共享集合。
- 文件测试使用临时输出根目录，PG 使用演练库，图使用 fake 或独立演练实例，向量使用 fake 或独立演练 database。集成测试在缺少任何所需隔离条件时跳过，不回退到默认连接。

这些规则只约束测试，不改变正式删除功能按管理员确认的目标 source_id 清理正式知识的业务行为。

## 9. 验收清单

验收中的跨源隔离、部分写入残留、外部存储故障及重试（尤其第 5、7、8 条）优先通过 fake 驱动/适配器单测完成。真实 PG/Milvus/图演练严格按 §8.3 门控；正式 Neo4j 只读核验，不能把验收要求解释为允许对正式图试删。


1. 无登录条件下四类删除入口均可用，前后端无身份依赖。
2. 采集/发布作业删除后不再可选、可编辑或可执行，历史版本与有效参数仍可追溯，文件与已发布数据不变。
3. 删工作区级联退出所有下属作业，删除对应采集树，不清该源发布知识，不影响兄弟工作区。
4. 删数据源覆盖所有下属对象及五张 PG 内容表、三类向量和图，绝不修改源业务库。
5. 两个数据源含同名库/schema/表时，只删除指定 source_id；Neo4j 不误删无 source_id 或其他源节点。
6. 任意范围内存在 pending/running 运行时拒绝删除；并发创建运行、作业、工作区与删除之间无穿透。
7. 失败发布留下的向量/图数据也能按源清理，不依赖最近成功运行集合。
8. Milvus / Neo4j / 文件分别故障时任务显示失败，未误报完成；重复请求、进程重启后重试幂等。
9. 历史运行引用不产生外键冲突；删除发布作业不触发虚假的历史回滚或知识恢复。
10. 源删除成功后普通列表不再出现该源，用已知 ID 打开详情、编辑或执行均返回 410 resource_deleted，连接字段按 §3.5 清空；独立知识清理保留源、工作区、作业和采集文件，任务成功后允许重新发布。
11. 目录不存在和集合不存在可幂等成功；网络不可达、权限拒绝、路径逃逸必须失败。
12. 普通列表、计数、首页统计过滤一致；deleting/delete_failed 仍有进度/重试入口；已删除 ID 的写接口返回 410。
13. 原有执行、发布校验、版本参数查看功能保留；删除弹窗明确说明保留历史和已发布数据的范围。
14. success / partial_success / failed 不阻断删除；遗留 pending / running 必须明确列出，不因首页或最近列表缺失而无法定位。首页两类运行均独立统计 pending。
15. 离线收尾脚本默认只预览，实际修改须显式确认执行者已停止并提供原因；只处理指定的 pending / running 运行，终态不被覆盖。步骤 running → failed、pending → blocked，成功步骤及参数/manifest 保留，运行按原规则汇总并记录原因和结束时间。
16. 收尾重复执行幂等、事务失败无部分提交，不改 YAML/marker 或发布内容；维护结束后可重新通过删除准入。在线活跃执行不得仅凭超时或当前进程无任务被判为无主。


17. 创建工作区/作业/版本/运行、步骤认领、三类配置写回与删除并发时，均遵循 §5.1.1 顺序；重点覆盖原 add_revision 先锁作业和原配置保存先锁工作区的路径，无锁顺序反转。
18. 两连接并发提交同源不同动作/工作区任务，数据库最多保留一条 pending/running；不同源互不阻断。failed 任务保持冻结且只可重试原任务，不能换目标绕过。
19. 同一 pending 任务被两个执行者同时认领，仅条件更新返回行的一个执行；中断 running 的重试必须取得任务执行锁，活跃执行锁未释放时返回 409，不按超时强制接管。
20. 将 Milvus/Neo4j/目录清理故意阻塞时，不占用源/工作区/作业/任务行锁；状态查询和其他源操作仍可进行，冻结检查继续拒绝本源新写入。

21. 有效父级内，删除完成后可新建同名工作区/同类作业，分配新 ID，不继承历史；deleting/delete_failed 仍占名。SQL 与 ORM 无残留全量名称唯一约束，服务层查重不把历史行算作冲突。
22. 两连接并发创建或改名为相同有效名称时，仅一个成功，另一个返回既有名称冲突错误；采集/发布两类名称范围独立，数据源显示名仍可重复，历史来源始终按 ID 区分。

23. 删除完成后 db_source_info 按 §3.5 逐列保留/置空；有效源仍强制完整连接字段。已删除源的空密码不进入解密路径，不返回伪造的 503，历史来源摘要仍正常展示。
24. 重启扫描跳过 15 秒保护期内 pending；过期 pending 与 running 分别按 §7.2 在取得执行锁并复查后标为可重试失败，不自动清理；其他实例持锁的任务不变。未被扫描处理的遗留任务也可通过重试接口完成中断识别，失败冻结与步骤进度保留。

25. 父级 deleting/delete_failed 时，子工作区/作业在父级及全局列表仍可见、只读、不可选作执行目标；直接调用创建运行/版本/配置写回接口均 409 parent_resource_unavailable，历史查看保留，删除完成后统一退出普通列表。
26. 数据源 DELETE 无论有无工作区均返回 202 任务、保留逻辑登记且固定清理源树；旧 delete_output 请求明确拒绝，前端无旧勾选。工作区删除使用双参数 resolve_workspace_root，兄弟目录不变；源删除才使用 resolve_source_workspace_dir。

27. 刚返回 202 或刚重试入队的 pending 在 15 秒内不得出现重试按钮，滚动启动扫描不得将它标失败。过期且锁空闲的 pending、锁空闲的 running 可显示“检查并重试”，无需其他实例重启；点击重新复查 queued_at/锁，保护期返回 409 task_pending_claim，锁竞争返回 409 task_still_running。覆盖原回调延迟到达、并发重试及 queued_at 更新竞争，最多一个执行者认领，详情探锁不认领。
28. 三个向量发布函数不跨外部调用持层级行锁或 platform_session；实际写入完成前保持 running，之后短事务收尾。离线收尾的运行及修改步骤 message 含原因与未核验说明。



29. 独立知识清理时源 active，仍按 pending/running 或未解决 failed 任务拒绝 MetaWeave 管理写入；任务全部成功后解除。
30. 工作区重试立即显示 deleting，失败回 delete_failed，成功写 deleted_at；不修改源状态。

31. 独立清理保持源 active/is_active 原值，pending/running 在详情和列表显示清理中，未解决 failed 显示清理失败及原因、原任务重试；写入口禁用且直接请求仍 409，成功解除本任务限制。
32. last_published_at 清理后保留历史值，列名与提示明确为发布运行创建时间；包含失败运行时不标成“最近成功发布”，不作为当前画像存在证明。资产页按实际 PG 内容展示，不新增实时知识检测。

33. 工作区 A 删除中或失败时，A 的子级写入受限，兄弟工作区 B 仍可采集、发布、保存配置和创建作业；新建其他工作区不受误阻断。同源新删除任务仍按任务互斥拒绝，不能将两种准入混用。
34. clear_source_knowledge 任务 pending/running/未解决 failed 时整个源管理写入返回 source_knowledge_frozen；源删除状态按父级规则阻断。测试覆盖同 source_id 不同 action 和 workspace_id，防止仅按同源任务状态错误冻结。

35. queued_at 在 SQL/ORM 均 NOT NULL 且有数据库时间默认值；首次插入与 created_at 同时生成，显式 NULL 被拒绝。重试在改 pending 的同一更新中刷新 queued_at、保留 created_at；刚返回 202 的任务不因空值或应用时钟差异被误判超时。

36. 源删除、工作区删除、独立知识清理在 pending/running/未解决 failed 时，刷新页面或重开浏览器后，均能从源/工作区响应的 deletion_task 找回任务并恢复进度、重试入口；不依赖首次 202 或本地缓存。源附带工作区 A 任务时不冻结 B，B 的详情不误附 A 的任务；成功旧任务不继续阻断。

37. 普通详情/编辑/运行/配置及资产路由均经共用守卫，已删除祖先不会因 session.get 仍返回行而漏过；404 与 410 可区分。列表、分页 total、查重、统计过滤一致，deleting/delete_failed 的只读任务找回不被误拦。
38. 已删除父级的运行详情、版本列表/详情和运行历史仍可只读访问，均能按响应契约展示 source_summary，不要求调用普通详情、不解密空凭据；历史白名单不能被用来创建运行或修改配置。

39. 默认单测使用 fake，不连接正式存储；live 未显式开启或实际 PG 库非 metaweave_rehearsal_final 时，在任何写入前跳过。即使 PG 门控通过，也不访问正式图写接口；缺独立演练 Neo4j 时跳过图 live。
40. Milvus 清理指纹、delete 和计数均包含相同 database 维度；同实例不同 database 存在同名集合和 source_id 时，只影响目标 database。演练使用独立 database，不能默默回退到正式或 default。

41. 执行者、详情探锁、启动扫描和重试均调用同一 task_lock_key，使用固定命名空间 SHA-256 前 8 字节有符号 bigint；固定向量及跨进程测试结果一致，UUID 字符串大小写不改变键。
42. 执行锁专用连接 autocommit、不经普通业务池长期借出；任务阻塞于外部 I/O 时普通池仍可用，完成/异常/探锁失败均关闭连接，不残留 session 锁或长事务；部署连接预算包含每个并发任务一条专用连接。

43. 源删除成功事务同步将尚未删除的下属工作区设置 deleted_at 和 deletion_state=deleted，保留已删除对象原时间；workspace_info 的 SQL/ORM CHECK 拒绝 active 搭配非空 deleted_at、deleted 搭配空 deleted_at 及非法枚举，源级联与工作区自删均不撞约束。

## 10. 审核时重点确认

本方案的核心取舍是：删除作业/工作区不撤销发布，源级清理负责物理删除知识，历史保留以保护来源关系。若产品要求“删除必须彻底擦除历史”，需要另行选择物理删除路线，并同时处理发布外键、当前知识归属、历史可用性和跨存储失败恢复；不能仅把本方案中的 deleted_at 改成 DELETE SQL。

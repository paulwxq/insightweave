# 5.3 采集作业的创建、运行与版本管理方案

记录日期：2026-10-20。状态：**上一轮讨论方案，尚未实施；本文只讨论采集作业，不定义发布流程。**

后续 [6_工作区采集作业与发布作业四层模型.md](6_工作区采集作业与发布作业四层模型.md) 改由 `workspace_id` 隔离产物，本文保留由 `job_id` 隔离产物的方案供比较，不能与第 6 章同时作为实施依据。

本文承接 [5.1_数据源工作区采集运行与发布运行模型.md](5.1_数据源工作区采集运行与发布运行模型.md)、[5.2_采集模板与发布模板表结构.md](5.2_采集模板与发布模板表结构.md) 的讨论，提出新的采集作业模型。前两篇中的 `workspace_id` 隔离产物、独立采集模板等目标设计，与本文方案不同；实施时需以最终确认的方案统一修订，不能同时作为建表依据。现有代码仍采用旧的 `job_info` 逐步骤状态结构，本文所列字段均为待实施设计。系统尚未上线，允许断代修改，不要求历史数据迁移或向下兼容。

## 1. 身份与职责

```text
数据源 source_id
  ├─ 采集作业 job_id（独立产物目录、可保存的默认配置）
  │    ├─ 配置版本 1
  │    ├─ 配置版本 2
  │    ├─ 采集运行 collection_run_id = R1（引用版本 1）
  │    └─ 采集运行 collection_run_id = R2（引用版本 2）
  └─ 采集作业 job_id（另一个独立产物目录）
```

| 身份 | 职责 | 生命周期 |
| --- | --- | --- |
| `source_id` | 标识数据源；一个作业只绑定一个数据源。 | 数据源登记时创建。 |
| `job_id` | 标识可保存、可修改的采集作业，同时隔离该作业的文件产物。 | 首次保存作业时创建，后续修改和运行均复用。 |
| `revision_no` | 标识同一 `job_id` 下的一版默认步骤与参数。 | 首次保存为版本 1；每次修改并保存执行配置时递增。 |
| `collection_run_id` | 标识一次实际采集，包括手工运行和定时触发。 | 每次执行都生成新的 UUID。 |

产物目录继续使用 `./output/<source_id>/<job_id>/`。同一 `job_id` 下的运行可以复用目录中先前运行留下的上游产物；不同 `job_id` 的目录相互隔离。**版本号标识配置，不单独创建一套产物目录，也不代表文件快照。**`job_id` 是否改用 `job_1` 形式的短 ID，可在字段定稿时确定；不影响本节的身份关系。

## 2. 创建并保存作业

1. 用户选择一个数据源，为作业填写名称、用途说明，选择允许执行的采集步骤，并设置默认参数。当前明确需要保存的参数是 `--generate-domains --description` 对应的默认生成描述；以后新增步骤参数时按步骤扩展。
2. 首次点击“保存作业”后，创建 `job_info` 记录、版本 1 的 `job_revision` 记录，并建立 `./output/<source_id>/<job_id>/` 目录。创建作业不以执行采集为前提。
3. `job_info` 保存**当前默认配置**，其中 `default_domain_description` 保存上述参数，供打开作业和默认运行时读取；`job_revision` 保存该版本的不可变配置快照。两者在保存作业时保持一致。
4. 已创建作业的 `source_id` 不允许修改。要改用另一个数据源，应新建作业，避免一个 `job_id` 的目录混用不同数据源的产物。

`default_domain_description` 是作业的**生成输入默认值**，不是 `db_domains.yaml` 中当前生效的 `database.description` 的副本。具体读取优先级见第 6 节。

## 3. 执行作业

打开一个已保存的作业后，提供两个执行入口：

| 入口 | 步骤与参数 | 是否改变作业配置 |
| --- | --- | --- |
| 按默认配置执行 | 采用当前版本保存的步骤及默认参数。 | 否。 |
| 手工选择步骤执行 | 只能在当前版本允许的步骤内选择子集；可临时修改本次步骤参数。 | 否；本次修改不能从运行页面保存回作业。 |

每次点击执行都生成新的 `collection_run_id`。后端先验证所选步骤属于该版本允许范围，再对**本次选中的步骤**按固定依赖顺序排序；不要求执行全部步骤，也不按前端传入顺序执行。某些步骤可以读取同一作业目录里其他运行生成的上游产物，因此只重跑失败步骤属于正常操作。

`collection_run_info` 保存本次运行的 `job_id`、`revision_no`、触发方式、整体状态等信息；`collection_run_step` 为本次选中的每个步骤保存一行，记录步骤名、**实际生效参数**和执行状态。未选步骤不写成“本次执行成功”。即使用户临时覆盖参数，运行记录仍应准确反映本次使用的值。

## 4. 修改作业与版本管理

- 修改允许执行的步骤或默认参数并保存时，保留原 `job_id` 和产物目录，新增一条不可变的 `job_revision`；`job_info.current_revision_no` 指向新版本，并更新其当前默认配置。改名或修改用途说明是否也生成配置版本，可在表结构定稿时决定；建议仅影响执行行为的变更生成新版本。
- 旧 `job_revision` 不被覆盖。旧 `collection_run_info` 始终引用启动时采用的版本号；同时保留本次实际步骤和参数，才能区分“作业默认值”与“手工临时覆盖值”。
- 保存新版作业不会修改已经完成的运行记录，也不会自动清空旧产物。若旧产物与新版步骤不兼容，运行前需校验依赖；产物的具体版本识别和失效规则另行设计。
- 启动运行时一次性确定 `job_id`、`revision_no` 和实际参数；运行过程中即使又有人保存了新版本，本次运行也继续使用启动时确定的配置。

## 5. 建议的数据表职责与主要字段

本节只确定表的职责与字段方向，**不是最终建表语句**。`job_info` 不再沿用现状的“一行一个 `(job_id, step_name)` 最近状态”；步骤执行结果转移到运行表。

| 表 | 建议主要字段 | 含义 |
| --- | --- | --- |
| `job_info` | `job_id text` 主键、`source_id text`、`job_name text`、`job_desc text` 可空、`current_revision_no integer`、`collection_steps text[]`、`default_domain_description text` 可空、`created_at`、`updated_at` | 一行一个作业，保存身份和当前默认配置；创建作业时即可写入。 |
| `job_revision` | `(job_id text, revision_no integer)` 联合主键、`collection_steps text[]`、`default_domain_description text` 可空、后续其他步骤默认参数、`change_note text` 可空、`created_at` | 每次保存执行配置形成一份不可变快照，不设置用于改写历史配置的 `updated_at`。 |
| `collection_run_info` | `collection_run_id uuid` 主键、`job_id text`、`revision_no integer`、`trigger_type`、`status`、`message` 可空、`created_at`、运行起止时间 | 一行表示一次采集运行；以 `(job_id, revision_no)` 关联具体作业版本。 |
| `collection_run_step` | `(collection_run_id uuid, step_name text)` 联合主键、`step_config jsonb` 可空、`status`、`message` 可空、`created_at`、`updated_at` | 一行表示本次选中的一个步骤；`step_config` 记录本次实际生效的参数，故障或跳过原因由状态与消息表达。 |

`job_info.collection_steps`、`job_info.default_domain_description` 是当前版本的便捷读取字段；对应的 `job_revision` 是历史版本的依据。保存时应在同一数据库事务内更新这些字段和 `current_revision_no`，避免当前配置与版本快照不一致。创建数据库记录和目录还需处理部分失败：不能向用户展示一个“已保存成功”却没有可用目录的作业。

运行步骤表已完整表达本次选了哪些步骤，因此暂不在 `collection_run_info` 重复保存同一份步骤列表。运行总表与步骤表共同构成“本次执行的步骤和参数”记录；若以后需要保留未经规范化的原始请求，可另增请求快照字段。

## 6. Domain 描述参数与 YAML 的关系

本节沿用 [5.4_Domain采集步骤变更方案.md](5.4_Domain采集步骤变更方案.md) 关于 YAML 生效值的原则，同时增加**作业默认输入**：

1. 当本作业尚无 `domain/db_domains.yaml` 时，“按默认配置执行”的 Domain 步骤使用本次引用版本中的 `default_domain_description` 作为生成输入；手工执行可临时覆盖。默认值未填写时是否回退到 `db_source_info.description`，待界面与校验规则确定。
2. 首次生成后，`db_domains.yaml` 的 `database.description` 是该作业当前生效的数据库描述。之后主动重跑 Domain 可以更新领域和表归属，但不因 `job_info` 默认参数变化而覆盖 YAML 中的 `database.description`。
3. 修改作业的 `default_domain_description` 只改变后续运行可用的默认生成输入，不等同于编辑既有 YAML。编辑当前生效描述应走 YAML 的显式保存流程。
4. 已有 YAML 时，手工运行页面覆盖 `--description` 的交互需要特别限定：不能让用户以为该输入会覆盖 YAML，实际却被忽略。建议此时展示 YAML 当前值，并引导通过显式编辑保存；具体界面和请求规则待确认。

因此，`job_info.default_domain_description` 与 5.4 中反对保存的 `job_info.db_desc` **语义不同**：前者是作业默认生成参数，后者曾被当作生成后描述的另一份生效来源。实施时需据此修订 5.4 中与模板和作业默认参数有关的旧表述，保留其 YAML 生效值与备份规则。

## 7. 定时运行

定时配置绑定指定的 `(job_id, revision_no)`，每次触发生成新的 `collection_run_id`，按该版本的默认步骤和参数运行。保存作业新版本后，手工默认运行采用新版本；已有定时配置继续使用原版本。完成新版本验证后，再明确切换定时配置引用的版本，避免一次编辑悄悄改变定时任务的执行内容。

调度表达式、启停状态等属于独立的调度配置；本章尚不定义调度表。`job_revision` 固定的是步骤与默认参数，不冻结数据源数据或共享目录中的产物，所以相同版本的多次定时运行仍可能得到不同结果。

## 8. 尚待细化的边界

1. **产物来源。**同一 `job_id` 下的运行共享目录。仅有 `job_id` 和配置版本号不足以说明某个步骤实际读取了哪次运行留下的文件；需要设计产物清单、版本或校验值，以及上游产物变更后的依赖校验。
2. **作业配置字段。**目前只明确 `--generate-domains --description`。新增参数时需确定校验、保存位置及运行时覆盖规则，避免 `job_info` 当前配置和 `job_revision` 快照含义不同。
3. **版本边界。**作业名称、用途说明等非执行字段是否进入版本，及旧版本能否作为手工运行入口，需在交互设计时明确；本章默认手工入口采用当前版本，调度可以继续引用旧版本。
4. **Domain 首次输入。**作业默认描述为空时的数据源描述回退规则，以及已有 YAML 时手工参数的展示和禁用方式，仍需确定。

本文记录采集作业方案，不表示相关表、API、页面或调度能力已经实现。

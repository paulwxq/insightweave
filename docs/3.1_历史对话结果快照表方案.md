# 3.1 历史对话结果快照表方案

记录日期：2026-10-19。状态：**方案草案（讨论稿），未实施、未定 DDL 终稿**。

本文是 [3_SQL查询结果文件存储问题与改造思路.md](3_SQL查询结果文件存储问题与改造思路.md) §4 方向的一个**最小改造变体**：新增一张"结果快照表"承接 meta 与最终结果的前若干行（由 `thread.snapshot_max_rows` 控制，默认最多 200 行），解决"结果文件按保留期清理后，对话历史中的表格无法查看"的问题。执行链与模型完全不动。关联文档：[4.1_Web对话历史与Store_Checkpoint_结果目录的查找关系.md](4.1_Web对话历史与Store_Checkpoint_结果目录的查找关系.md)、[4.2_WebUI从打开到提问的逻辑线路.md](4.2_WebUI从打开到提问的逻辑线路.md)。

## 1. 问题与目标

**现状**：结果以文件保存（`<workspace>/results/<result_ref>/{meta.json, rows.jsonl}`），按 `result_retention_days`（现 30 天）+ 引用保护定期清理；而 qa／web_turns 的历史引用长期存在。文件一旦清理，历史里引用的表格就再也打不开（当前行为：读取报错）。

**目标**：**即使目录文件被删除，对话历史记录中依然能看到表格**——meta 信息（SQL、列、行数）+ 表格数据（页面默认展示 10 行；快照保存行数由 `thread.snapshot_max_rows` 控制，默认最多 200 行）；文件存在时可查看结果，并通过本次改造导出全部已保存行的 CSV。历史窗口本身由 web_turns 保留期决定（既有配置 180 天，**已决策调整为至少 365 天**——以 `archive_retention_days` 为准），见 §7。

**适用范围（2026-10-19 决策）**：上述承诺适用于**本方案上线后的新对话轮次**。上线前产生的存量 result_ref **不迁移、不补录**——R2（result 清理）启用后，超过 30 天的存量目录将被删除，对应旧历史表格随之失效；当前为测试阶段，历史数据可丢，此取舍已明确接受（决策记录见 §9.1）。

**非目标**：不改变执行链与模型的任何行为；不做配额；不选型 NAS/MinIO；不迁移存量数据。

## 2. 方案总览

一张快照表 + 两个触点：

```text
触点一（写）：轮次收尾钩子复核通过后，
  对本轮实际展示的证据列表 display.evidence（由 result.evidence 投影）中每个带 result_ref 的条目落一条快照
  （meta + 由 thread.snapshot_max_rows 控制的前若干行，默认最多 200 行；与页面证据区一致，不区分是否被最终答案引用、不区分轮次成败——均指正常收尾分支，见 §4）
触点二（读）：历史展示路径（results API）加一个回退分支：
  文件在 → 从 result 目录读取；页面最多展示 api.max_display_rows（默认 200）行，将 rows.jsonl 中全部已保存行转换为 CSV 导出
  文件缺失 → 从快照表读取 + data_from_snapshot 标记；将快照行转换为 CSV 导出
```

执行链（execute_sql／analyze_result／probe／pushdown、ResultStore 全部）、模型与工具、checkpoint／Store 归档：**零改动**。

**两条铁律（方案定稿约束）：**

1. **历史读取同源配对**：查看历史对话时优先读 result_ref 目录（meta.json + rows.jsonl 一起取），目录不存在**或 meta.json／rows.jsonl 任一缺失**才读快照表（meta_jsonb + rows_snapshot 一起取）——任何情况下不允许 meta 与 rows 取自不同来源；
2. **执行/读取路径不读写快照表**：db_deepagent 模块（Runner、工具、ResultStore）在执行与读取的全过程不读写快照表；快照表的写入只发生在 Web 层收尾钩子，读取只在 Web 层历史回退分支，维护作业（persistence/maintenance.py）**仅做保留期删除**。

**快照的关键语义：存档而非缓存。** 设计动机：结果文件会按保留期被清理，而历史引用长期存在——如果只有文件，清理后历史表格就再也打不开。因此 Web 层收尾钩子把结果文件的前若干行写入快照表的 `rows_snapshot` 字段；实际写入行数为 `min(saved_row_count, thread.snapshot_max_rows)`，`thread.snapshot_max_rows` 是本方案新增参数，默认 200。这样即使目录文件被删除，对话历史中依然能看到已保存的快照行。**存储行数可配置、显示规格归前端**：WebUI 表格默认展示 10 行，本方案实施后展开上限由 `api.max_display_rows` 控制（默认 200，`config.yaml`；前端从 results API 响应读取，见 §3.2）；本方案的 CSV 导出能力实施后，导出行数由数据来源决定，不受该展示上限约束。注意 `preview_rows`（20）是 execute_sql 给**模型**的预览行数，与 Web 表格显示无关，不参与本方案的参数统一。

## 3. 表设计（草案 DDL）

库与 schema：`lg_persist` 的 `db_deepagent` schema，独立建表。

```sql
CREATE TABLE IF NOT EXISTS result_snapshots (
    result_ref      text PRIMARY KEY,          -- res_<32hex>，沿用现有生成规则
    session_id      text NOT NULL,
    request_id      text,                      -- 结果最初产生它的轮次（取值 = 结果自身元数据的
                                               --   request_id；跨轮复用不更新；触发快照写入的当前
                                               --   轮次与此不同时不影响本字段——轮次↔结果关系由
                                               --   web_turns.display.evidence 承载，见 §6）
    thread_id       text,
    saved_row_count int  NOT NULL,             -- 原结果已保存行数；源查询超出保存上限时由
                                               --   source_truncated 标记（meta_jsonb 内）
    rows_snapshot   jsonb NOT NULL,            -- 最多 snapshot_max_rows（默认 200）行；
                                               --   页面预览 10 行、"查看全部"按页加载
    snapshot_row_count int NOT NULL,           -- 冗余行数（= rows_snapshot 数组长度）；读取方
                                               --   免 detoast 整个 jsonb 即知快照规模
    meta_jsonb      jsonb NOT NULL,            -- 文件 meta.json 的副本（双写，见 §5.1）：columns、
                                               --   executed_sql、sha、时间、guard_evidence…；
                                               --   文件不可用后为唯一 meta 来源。注意 meta_jsonb
                                               --   .rows_sha256 是**源文件**哈希，不用于校验
                                               --   rows_snapshot（v2 cells，二者不保证一致）
    created_at      timestamptz NOT NULL DEFAULT now(),  -- 快照写入时间（**非结果生成时间**——
                                               --   结果生成时间见 meta_jsonb.created_at）
    last_referenced_at timestamptz NOT NULL DEFAULT now()  -- 最近一次被轮次写入/复用的时间（§7 清理依据）
);
CREATE INDEX IF NOT EXISTS idx_result_snapshots_session ON result_snapshots (session_id, created_at);
CREATE INDEX IF NOT EXISTS idx_result_snapshots_request ON result_snapshots (request_id);
CREATE INDEX IF NOT EXISTS idx_result_snapshots_lastref ON result_snapshots (last_referenced_at);
```

设计要点：

1. **一行 = 一个 result_ref**。入表范围 = 正常收尾分支实际写入并展示的证据列表（write_turn 的 `display.evidence`；由 `result.evidence` 投影而来，`runner.py:709` 组装：本运行全部 **purpose=query** 的执行记录 + 分析记录），**与页面证据区一致**——含未被 findings 引用的执行与分析结果。两个容易误读的边界：① 下推（purpose=pushdown）**执行记录**不产生独立证据条目，但 analyze_result 下推产出的**分析结果文件**会成为分析证据的 result_ref、随之入表；② 探针（purpose=probe）不产生证据条目、不入表——其文件在现行引用保护下受保护（`_protected_refs` 不按 purpose 过滤），R2 移除保护后随 30 天清理；
2. **幂等去重 + 最后引用时间**：`INSERT … ON CONFLICT (result_ref) DO UPDATE SET last_referenced_at = now()`（其余字段保留首次写入）。跨轮复用只写一次数据，但**引用时间随每次复用刷新**。**存量取舍（已决策）**：方案不做存量迁移／补录——上线前产生的 result_ref 没有快照，R2 启用后到期即删、对应旧历史表格随之失效（测试阶段可接受，见 §9.1）；
3. **快照行数** = `min(saved_row_count, thread.snapshot_max_rows)`。`snapshot_max_rows` 为新增可配置参数（放 `thread` 段、默认 200，见 §3.1；实现注：`ThreadConfig`（同为严格模型）新增字段**须带默认值 200**，避免未含该键的旧配置加载失败）；它是**写入时**参数——调小不追溯已存快照，调大不回补历史，只对之后的新快照生效；实际行数同时冗余写入 `snapshot_row_count` 列（见 §3 DDL）；
4. **行数如实标注**：`saved_row_count` 存**原结果已保存行数**（源查询超过保存上限时由 `source_truncated` 标记，源数据可能更多），任何消费方都不把快照冒充全量；
5. 常用过滤字段（session_id / request_id / created_at）提为真列，长尾元数据进 `meta_jsonb` 兜底；
6. **快照表只表示结果本身**：一行 = 一张最终展示的结果表，不区分"首次产生"与"后续复用展示"。轮次↔结果的对应关系由 `web_turns.display.evidence` 天然承载（每轮的 evidence 列表即该轮展示过什么），**不另设 (session_id, request_id, result_ref) 关系表**——`request_id` 列仅记首次来源，跨轮复用的反查局限见 §6。

### 3.1 配置新增

```yaml

  # —— 保留期家族（对话 365 / 执行 30，均为下限口径）——
  archive_retention_days: 365            # 对话家族（web_turns／qa／run_errors）：至少 365 天
                                         #   （2026-10-19 由 180 调整，docs/3.1 §7）
  snapshot_max_rows: 200                 # 历史快照保留的最大行数；写入时截断，调整不追溯存量

```

（`checkpoint_retention_days: 30`／`result_retention_days: 30` 维持不变，同段。）

显示侧默认展示 10 行（`PREVIEW = 10`，前端模块内常量）；当前最大展示行数由前端硬编码的 `MAX_ROWS = 200` 控制，本方案实施后改由 §3.2 的 `api.max_display_rows` 控制（默认 200）。`preview_rows`（20）仅控制 execute_sql 给模型的预览行数，与 Web 表格无关，语义不变。

**参数位置（2026-10-19 决策）**：`snapshot_max_rows` 放 **`thread` 段**（与保留期家族同段），**不放 `results` 段**——results 段头注释声明"本段参数均只约束给模型的数据量"，快照参数放入会与之矛盾；放 thread 段后该声明保持为真。实现注：`ThreadConfig`（与 ResultsConfig 同为严格模型）新增字段须带默认值 200，避免未含该键的旧配置加载失败。

### 3.2 前端展示上限（`config.yaml`）

本方案实施后，对话结果表格最多显示多少行由 `nl2sql/src/configs/config.yaml` 新增的 `api.max_display_rows` 控制（默认 200；缺失或非法按 200）：

```yaml
api:
  max_recent_sessions: 5
  max_display_rows: 200       # 对话结果表格最多显示的行数（仅前端展示上限）
```

- **只是展示上限**：不是结果保存上限，也不是 `thread.snapshot_max_rows`（快照存储上限）或 `results.read_max_rows`（模型工具单页上限）。
- **传递方式**：results API 成功响应新增同名 `max_display_rows`；前端 `ResultPageData` 读取它，不新增配置接口。
- **前端行为**：默认展示 10 行（`PREVIEW = 10`），展开最多 `max_display_rows` 行；stats 行显示“已显示 X / 共 N 条 · 当前最多展示 M 条样例数据”。
- **不影响 API 分页**：服务端 `limit` 仍为默认 100、最大 500；`max_display_rows` 只约束前端展示，不截断 API 的 `limit`。

## 4. 写入：轮次收尾钩子

执行侧写入不变：`ResultStore.save` 照旧在执行时把 `meta.json` + `rows.jsonl` 写入 result_ref 目录（meta 双写的原因与评估见 §5.1）。本节只描述**新增**的快照写入。

位置与顺序：`_make_finalize_hook`（`runs.py:349`）内有**两个 `write_turn` 点**——① 一致性未确认分支（`runs.py:426`：`write_turn` 不带 display，`unsafe_projection` 清空证据、页面不展示任何证据表格）；② 正常收尾分支（`runs.py:456`：`write_turn` 带 `display_from_result(result)`）。快照写入**只挂在分支 ②**：在 `write_turn` 写入并回读确认 `history_saved is True` 之后执行。两个限定缺一不可——

- **分支限定**：分支 ① 的轮次页面不展示任何证据表格，无快照需求；若照字面在两个分支都插入，会把页面不展示的 evidence 写进快照，违背"与页面证据区一致"；
- **状态不限**：分支 ② 内无论本轮 status 为 completed 还是 failed——真实执行后失败的轮次会归档进 qa、web_turns 带 `display.evidence`，页面照常展示证据表格，快照照常写入。

```text
for e in 回读轮次 rec2 的 display.evidence:   -- 实际展示的证据（非 result.evidence 原始列表）
    if e.result_ref is None: continue
    try:                                     -- 单条隔离：任何异常（KeyError/OSError/ResultStoreError）都不中断其余证据
        meta = results.load_meta(e.result_ref, session_id=session_id)   -- 归属校验 + meta 副本
        page = results.read_rows_cells(e.result_ref, session_id=session_id,
                                       offset=0, limit=快照行数)            -- 单元格信封（≤ snapshot_max_rows）
        INSERT INTO result_snapshots (…, request_id = meta.request_id,
            snapshot_row_count = len(page.rows),
            rows_snapshot = page.rows, …)
            ON CONFLICT (result_ref) DO UPDATE SET last_referenced_at = now()
            -- request_id 取结果自身元数据（最初产生它的轮次），不是当前触发写入的轮次；
            -- 其余字段保留首次写入（幂等；引用时间随复用刷新，见 §3 要点 2）
    except Exception as exc:
        WARN(固定标记, e.result_ref, exc 类型)；continue   -- 记 ref 后继续下一条
```

- **失败告警 + 单条隔离**：快照写入按证据**逐条独立 try/except Exception**（不止 `ResultStoreError`——`ResultMeta.from_json` 对缺失字段直接抛 `KeyError`，`result_store.py:371-391`），单条失败以 WARN 级日志记录（固定标记 + session_id／request_id／result_ref + 异常类型）后**继续下一条**。告警后在 `result_retention_days` 窗口内（现行 30 天）文件仍在，人工补写一条 INSERT 即可救回；不做自动重试/补写——若该结果后续被其他轮次沿用，对应轮次的钩子会自然补写快照（幂等，见 §3 要点 2）；
- **写入方式**：**按证据逐条 INSERT**（与单条隔离一致；不做多行合并——多行 INSERT 一行失败会整条回滚，与逐条隔离矛盾）；
- **顺序与失败隔离（对 pending）**：快照写在 `write_turn` 回读之后、`put_registration`（清 pending）**之前**；快照失败**不得阻断 put_registration**——清 pending 照常执行（否则会话被保守失效，代价远大于丢一张表）；
- **可观测**：成功记录写入条数；失败 WARN 带三键（见上）；指标接入归详细设计。
- **载荷契约**：`rows_snapshot` 存 `read_rows_cells` 的单元格信封（每格 {kind, value}），与文件分支的 Web 响应同构——回退分支直通返回、不做二次转换。用 cells 而非 `read_rows` 的解码值，是因为后者经过"Python 值解码 → 再序列化"往返，Decimal/大整数会丢精度（`result_store.py:630-634` docstring 明示的接口差异）；
- 复用证据（`reused_from`）：文件多数仍在，正常入表；若文件已被清理则跳过该条（复用窗口超出保留期的极端情况，如实记录）；
- **失败轮同样写快照（限正常收尾分支）**：真实执行后失败的轮次走正常分支，其证据表格页面照常展示——快照照常写入，清理后不能失效。一致性未确认分支（unsafe，页面无证据表格）与 **`display.evidence` 为空**的轮次不写快照——判据是实际展示的证据是否为空；"归档进 run_errors"只是常见伴随现象（复用了证据的失败轮也可能归档 run_errors 且带 display），不作为判据；
- **明确选择：入表范围 = Web 历史实际展示的全部 evidence（`display.evidence`，由 `result.evidence` 投影），而非仅 findings 引用的子集**——否则页面展示、快照未覆盖的表格会在文件清理后失效。

## 5. 读取：历史展示路径的精确路由

`GET /sessions/{sid}/results/{result_ref}`（历史查看表格的唯一入口，4.2 §6.1 路径二）。

**回退判定——只看文件是否存在，不看文件是否"完好"：**

1. 结果目录不存在，**或**目录中缺少 meta.json、rows.jsonl 任一文件 → 放弃目录读取，按 `session_id + result_ref` 查询快照表；
2. 两个文件都存在 → 走现有文件读取与校验（归属、sha256、编码）。此分支若出现**归属不符、哈希校验失败或编码错误，保留相应错误原样返回，不当作文件缺失**、不回退快照——存在但损坏的文件必须暴露，不能被悄悄解释成"已过期"；
3. **缺失判定的实现方式（不可省略）**：现实现的 `result_not_found` 错误类型是**过载**的——三个来源都归入该类型：`_require_dir`（:497-501，目录不存在）、`_read_meta`（:506-511，meta.json 不可读含权限问题或 JSON 损坏）、`_read_raw_lines`（:538-539，rows.jsonl 不可读）——过载面比"仅 _read_meta"更宽，因此**不能**靠捕获该错误类型判定缺失。回退判定必须使用**显式路径存在性检查**（目录存在且两个文件均在），在调用 ResultStore 读取之前完成；检查逻辑放 API 层或为 ResultStore 增加只读辅助方法，详细设计定稿。快照查询以 `session_id` 作为查询谓词，即同时完成归属校验（跨会话取不到数据）；
4. **TOCTOU 窗口的处理**：第 1 步的存在性检查与后续 `read_rows_cells` 之间存在时间窗——维护任务可能恰好在窗口内删除目录，导致读取抛出 `result_not_found`。处理：文件分支捕获该错误后**复检路径一次**——路径现已不存在 → 视为"文件缺失"，转快照分支（与规则 1 同语义）；路径仍存在 → 保留错误（说明是 meta 不可读类失败，非缺失，不回退——与规则 2"损坏不冒充过期"同原则）。

**快照分支：**

| 查询结果 | 行为 |
| --- | --- |
| 表中有快照 | 在快照保存行数内**正常分页**（offset/limit/next_offset 按快照边界计算，单元格信封直通、与文件分支同构）+ meta + `data_from_snapshot: true` + `snapshot_rows_available`（快照可用行数）|
| 表中无快照 | 现行为（结果不存在/已清理）——未被快照覆盖的中间结果与功能上线前的旧结果 |
| 快照查询本身失败（连接失败/超时等） | **503 `DEPENDENCY_UNAVAILABLE`**——查询失败 ≠ "无快照"，可重试；绝不让查询失败伪装成 404（区分方式：快照表未建属部署态，按 §7.2 视为无快照走 404＋WARN；表在而查询失败走 503） |

快照分支的三个行数语义分明，前端据此渲染：

- `saved_row_count`：**原结果已保存行数**（源查询超过保存上限时 `source_truncated = true`，源数据可能更多）；
- `snapshot_rows_available`：快照可用行数 = **`snapshot_row_count` 列**（写入时固化的实际行数，冗余存储以免读取时 detoast 计数；不受后续 `snapshot_max_rows` 配置调整影响）；
- 本次返回行数：本页实际行数。

**前端展示契约（与后端同批上线，非可选项）**：`data_from_snapshot = true` 时，前端以 `snapshot_rows_available` 作为**快照可用总数**并展示"仅保留快照"提示；表格实际展示仍受 §3.2 的 `max_display_rows` 限制，超出部分通过导出获取。`saved_row_count` 仅作"原结果已保存 N 行"的标注，**不作为可浏览总数**。API 分页边界 = 快照实际行数（耗尽时 `next_offset = null`，不出现"还有更多"的暗示）；前端表格加载上限见 §3.2。

**导出契约**：一个导出按钮，按结果来源执行**同一格式（CSV）、两种行为**。**不设"导出全部／导出部分"等用户选项**——行为差异只由数据来源（文件／快照）决定，不由用户选择。导出端点负责**JSONL／快照 → CSV 的转换**。端点：`GET /api/v2/sessions/{sid}/results/{result_ref}/export`；CSV 使用 UTF-8 BOM + `\n` 分隔：

- 文件存在 → 读取 `rows.jsonl` + `meta.json`，转换为 CSV 后返回**全部已保存行**（不受 `api.max_display_rows` 展示上限限制；现为新增能力，现行前端由浏览器拼接已加载行导出 CSV，当前最多 200 行，将被本契约取代），文件名形如 `<result_ref>.csv`；
- 文件缺失 → 将 `rows_snapshot`（单元格信封）转换为**同构 CSV**（同表头、同行序，行数 ≤ 快照实际行数 `snapshot_row_count`——写入时固化；历史快照可能按更大的旧配置写入），文件名形如 `<result_ref>.snapshot.csv` 以示区别；
- **CSV 转换规则**：首行为表头（meta.columns 的列名，两分支同源同序）；数据行的取值以文本形式写入（保存时的编码语义，§6.8；Decimal／date 已编码为字符串）；引号、逗号、换行的转义遵循 RFC 4180；
- **`data_from_snapshot` 不写入导出文件内容**——两种分支的行数据均保持原样，"仅含快照行"通过**文件名**与**界面提示**（"完整结果文件不可用，导出内容为保留快照，共 M 行"）表达；
- 导出端点形态（扩展现有端点 vs 独立流式端点）与 CSV 格式细节（BOM、换行符、空值文本形式）在详细设计中确定；
- **导出与分页共用的读取规则（导出不做完整性校验）**：导出端点先核对 Web 会话登记归属（`webstore.get_registration` + `core_ownership_ok`）；文件分支用 `ResultStore.load_meta` 做会话归属校验（`_require_session`），随后直接读取 `rows.jsonl` 原始行转换为 CSV——**不执行 `rows_sha256` 校验**，文件里有什么就导出什么；文件缺失时按 §5 回退快照（`session_id + result_ref`）。错误码沿用 `RESULT_NOT_FOUND`／`RESULT_ENCODING_ERROR`／`DEPENDENCY_UNAVAILABLE`；`RESULT_INTEGRITY_ERROR` 不适用于导出（哈希不符不阻断下载）。页面读取路径（§5 上文）现有的 SHA 校验保持不变。

**`data_from_snapshot` 的精确定义**：表示"完整结果文件当前不可用（缺失或已清理），本响应的数据来自快照表"。它**不断言文件不可用的原因**——可能是保留期清理，也可能是意外丢失；原因排查交给运维与维护日志，不由读取接口判定。

- **同源配对**：文件分支的 meta 与 rows 都来自目录（meta.json + rows.jsonl），快照分支的 meta 与 rows 都来自表（meta_jsonb + rows_snapshot），任何情况下不交叉取用（铁律 1，评估见 §5.1）；
- 不需要维护任何清理标记位——回退判定完全由当次读取的文件状态决定；
- 前端提示（与后端同批上线，见上方展示契约）：快照分支展示"完整结果文件不可用，当前展示保留快照（快照 M 行 / 原结果已保存 N 行）。导出仅包含快照行。"；stats 行"共 N 条"取 `snapshot_rows_available`，原保存行数仅出现在提示中。

**模型侧：写入路径零改动；读取路径按 R2 取舍调整。** `execute_sql` 载荷不加字段、docstring 不改；`read_result`／`analyze_result` 优先读文件。**R2 的已知取舍**：现状下存活线程引用的结果文件受引用保护，模型可长期 `read_result`（`read_result`／`analyze_result` 均无年龄检查）；R2 后文件 30 天到期即删，长会话中模型将**无法读取 30 天前的结果**（可重新执行查询获取新数据）。缓解：`read_result` 文件缺失时回退快照（可读 `thread.snapshot_max_rows` 控制的快照行，默认最多 200 行，带截断标记；是否纳入**首次实施范围**见 §9.11）——`analyze_result` 不回退（基于截断数据分析有正确性风险，按现有"结果已过期"语义报错）。web_turns 历史回放路径不受影响（快照兜底）。

### 5.1 设计裁决：meta.json 双写评估

需求回放：曾考虑"meta.json 不写入 result_ref 目录、只存快照表"。评估结论：**不采纳，meta.json 继续由 ResultStore 写入文件（双写：文件 + 快照表）**。

理由——执行路径对 meta 的依赖是结构性的：

1. `ResultStore` 每次读取都先加载 meta：归属校验 `_require_session`（session_id 比对）、`rows_sha256` 完整性校验、`read_rows` 的列投影（注意：`read_rows_cells` 无 columns 参数、不做列投影，是单元格直通），全部以 meta 为前提（`result_store.py:508-537`）；
2. `read_result`／`analyze_result` 的读取与分析**最终都经 ResultStore 加载 meta** 做归属与完整性校验（`read_result` 经 `read_rows` 内部路径，`analyze_result` 在入口显式 `load_meta`）——不逐行引用行号；
3. 若文件不再携带 meta，这些校验只能改从快照表取——执行路径就必须知道快照表，**违反铁律 2**；或者为执行再造一个独立的 meta 存储，等价于把 ResultStore 后端整体换掉（doc 3 §4 完整方案），开发代价与风险同"最小改造"定位冲突。

**代码量评估**：不再估行数——改造范围以 §8 清单为准（含 CSV 导出端点与前端适配）。`ResultStore` 与执行链零改动这一性质不变。

**双写一致性**：文件 `meta.json` 由 `ResultStore.save` 在执行时写入（执行事实源）；快照表 `meta_jsonb` 由收尾钩子在答案确认后从文件读出复制（历史兜底源）。文件存续期内两者内容一致；文件清理后，表为唯一 meta 来源——与 `rows_snapshot` 配合，同源配对（铁律 1）在两个分支上都成立。

## 6. 全链路：q/a 的 key 如何关联快照表

关联键不变：**轮次 = `request_id`，结果 = `result_ref`**。

```text
对话历史（web_turns.<sid>，key = request_id）
  └─ display.evidence[].result_ref
       └─ result_snapshots（PK = result_ref，request_id 真列）
            ├─ 文件存在 → results API 完整分页／导出 CSV（源：rows.jsonl）
            └─ 文件缺失 → rows_snapshot 分页 + data_from_snapshot（历史兜底；快照行数由 thread.snapshot_max_rows 控制，默认最多 200 行；页面默认展示 10 行）
```

| 想做什么 | 键 | 查法 |
| --- | --- | --- |
| 从一轮问答找它展示过的结果 | `request_id` | **查 `web_turns.display.evidence`**——每轮的 evidence 列表天然承载轮次↔结果关系；快照表的 `request_id` 只记首次来源，**不能**用于此反查（复用场景会漏） |
| 从历史卡片渲染表格 | `result_ref` | results API 精确路由（§5） |
| 从快照反查它最早来自哪一轮 | `request_id` 列 | 表内直接过滤——语义 = **结果最初产生的轮次**（取自结果自身元数据；跨轮复用不更新） |
| 跨轮复用 | `result_ref` | 机制不变，快照幂等（ON CONFLICT 保留首次写入） |

前端与 Web API 契约增量：results API 响应新增 `data_from_snapshot`／`snapshot_rows_available` 字段、新增 CSV 导出端点；前端 `ResultPageData` 类型同步扩展（doc 2 §4.5／§6 与 doc 4.2 §6.1 需同步）。快照表对模型、工具、checkpoint、Store 归档完全不可见。

## 7. 保留期与清理

**两个家族，两类周期**（2026-10-19 决策）：

| 家族 | 成员 | 保留期 | 时间基准 | 清理方式 |
| --- | --- | --- | --- | --- |
| 对话家族 | web_turns（问答文本）、qa／run_errors（账目）、快照行 | **≥ 365 天**（建议 365；以 `archive_retention_days` 为准，2026-10-19 由 180 调整） | web_turns／qa 按行时间（saved_at／created_at）；快照按 `last_referenced_at`（随复用刷新） | 既有维护作业（`db_deepagent maintenance cleanup`） |
| 执行家族 | checkpoint 线程、result 文件目录 | **≥ 30 天**（建议 30；以 `checkpoint_retention_days`／`result_retention_days` 为准） | checkpoint 按线程级判定（`max(最后活跃, 退役, 最新 checkpoint 时间)`）；result 目录按生成时间 | 同上 |

- **result 目录：至少保留 30 天，到期即删、无引用保护（有意偏离）**。现行代码（doc 5 §13.5 第 4 点**修订前**）规定"不被 qa 归档引用时才删除"；本方案起**移除该保护**——理由：快照表已兜底历史展示与表格查看，引用保护的历史使命由快照（meta 全量 + 由 `thread.snapshot_max_rows` 控制的前若干行，默认最多 200 行）部分承接。代价：保留期过后无法回看全量原始明细（快照行与 meta 仍可审计）。`result_retention_days` 的定位由此明确为**全量原始明细的下载/审计窗口**，与历史展示无关，建议 30 天、具体以配置为准；
- **web_turns／qa／run_errors：至少保留 365 天**（`archive_retention_days` 180→365，以配置为准）。原默认 180 天为讨论中认定的过短窗口，统一调整为至少一年——历史对话（问答文本与结构化账目）的可见窗口延长至一年；
- **快照行：至少 365 天，与对话家族同周期**（修订此前草案的"长期保留"；以 `archive_retention_days` 为准）。以 `last_referenced_at` 为清理基准（随每次复用刷新——即"**最后一次被新对话轮次引用**的时间"；用户重新打开对话、查看表格属纯读操作，**不会续期**），由维护任务随同清理；对话过期消失时，快照一并清理，不留孤儿数据；
- **checkpoint：至少保留 30 天**（建议 30，以 `checkpoint_retention_days` 为准），维持既有设计不变。

**范围边界与出处**：store 侧清理机制的设计定义于 `nl2sql/docs/v4/5_db_deepagent详细设计.md` **§13.5「清理」**（含 doc 7 §2 线程级判定增补），实现于 `persistence/maintenance.py`（已完成、25 个单测通过），经 `db_deepagent maintenance cleanup` 手工触发，**当前无任何自动调度**（触发方式为运维待决项，§9.10；**当前阶段以手工执行为准**）。**本文档不重新定义该既有清理机制本身**（`_scan_result_metas` 及其服务的会话发现／残留判断保留不动）；本方案对它的全部改动限于四点，均为显式决策——① 保留期数值调整（`archive_retention_days` 180→365）；② result 目录清理移除引用保护；③ result 清理从逐会话循环移出，改为独立的全局时间扫描步骤（§7.1 R2）；④ 新增快照行清理步骤（§7.1 R3）。实施清单见 §8。注意：doc 5（设计文档）已按本方案同步更新（保留期 365、result 到期即删），**代码尚未实施**——"设计已改、代码未改"的窗口期内，运行行为仍以现行代码为准。

**与快照的关系**：快照行入表后，"历史可看"与 result 文件彻底解耦——文件 30 天清理不影响表格（快照兜底）；快照与对话同寿（365 天），到期随维护清理，不留孤儿数据。

### 7.1 维护作业改造需求与现状

**现状（已完成、已测试，非本方案新增）**：`db_deepagent maintenance cleanup` 一个作业覆盖四段清理——checkpoint 线程（30 天，线程级判定 + 当前线程/待恢复任务保护）、qa／run_errors 归档（`archive_retention_days`，现 180）、web_turns 文本（同参数，现 180）、result 目录（`result_retention_days` 30 天 + 引用保护）。安全设计齐备：默认 dry-run、`--apply` 实删、`CleanupReport` 报告、会话锁、扫描预算；25 个单测通过。**当前无任何自动调度，需手工触发**（触发方式见 §9.10）。

**改造需求（三项；涉及数值均为下限口径，均可在配置文件 `db_deepagent.yaml` 中调整）**：

| # | 改造 | 类型 | 位置与内容 |
| --- | --- | --- | --- |
| R1 | `archive_retention_days` 180→365 | **仅配置**，无代码改动 | yaml `thread` 段一行——**该参数在配置文件中可配置，调整无需改代码**。影响面：qa／run_errors 归档清理与 web_turns 文本清理**同时**变为**至少 365 天**（两者共用该参数——即对话家族的统一）。回归要点：saved_at／created_at 落在 180–365 天区间的行不再被清理（旧行为会清） |
| R2 | result 目录清理改为**独立的全局时间扫描步骤**（移除引用保护与归属校验） | **新增步骤 + 移除逐会话 result 删除段** | `_scan_result_metas` **保留不动**——它同时服务于会话发现（`maintenance.py:227`）与疑似创建残留判断（`:371`），本方案不改其行为。新增步骤：直接遍历 `results/` 下匹配 `_RESULT_REF_RE`（`res_[0-9a-f]{32}`，与 ResultStore 同一正则）的目录——非规范名（如 `res_notes`）不会被误删，`.tmp-*` 临时目录亦不在范围（另行处理）——**不以 meta 为前置条件（meta 可读且 `created_at` 可解析时优先采用其时间，否则回退文件系统时间——见同格时间来源）、不按会话归组、无引用检查、无归属校验、不取会话锁**；目录年龄超过 `result_retention_days` 即删除整个目录——**至少保留 30 天**（建议 30，以配置参数为准）。**时间来源（不依赖 meta）**：meta 可读且 `created_at` 可解析时优先采用（与复用保留期判定同源）；meta 缺失／损坏、`created_at` 解析失败或为未来时间时，回退目录／文件系统 mtime（未来时间夹紧为 0，随时间推移自然到期）——保证任何 res_* 目录都有可判定的年龄，不完整目录同样到期可删，不再永久残留。**并发语义（显式声明）**：不取会话锁，删除与并发读取存在竞态——正在分页/导出该结果的请求可能收到 `result_not_found`；这是过期清理的可接受语义（30 天窗口内文件始终可读，过期后才可能消失）。**保留不变**：dry-run／apply 模式、报告。**实施顺序依赖**：须与快照写入路径（§4 收尾钩子）同批上线——快照表已建但钩子未上线时，新轮次不会写入快照，结果目录到期删除后其历史表格仍会失效；表存在性门禁只防漏建表，不能替代钩子写入。**取舍（需知）**：现状下存活线程引用的结果文件受保护、模型可长期 `read_result`；R2 后该能力消失，缓解选项见 §9.11（`read_result` 快照回退，可选增强） |
| R3 | 新增快照行清理步骤 | **新增功能** | 位置：**会话循环之外**的独立步骤（与 R2 全局扫描同级；**不得**置于会话循环内——无 session_id 谓词的 DELETE 放循环内，会对每个会话重复执行一次全局删除）。规则：`DELETE FROM result_snapshots WHERE last_referenced_at < :archive_before`——**:archive_before 由作业统一计算**（`reference_now − archive_retention_days`，与 qa／web_turns 段同源，支持 `--before` 模拟时间），**不使用数据库 now()**，dry-run 语义与其他段一致。**索引**：`idx_result_snapshots_lastref (last_referenced_at)`（见 §3 DDL），无全表扫描。特性：① 以"最后一次被新对话轮次引用"起算**至少 `archive_retention_days`**（建议 365 天；复用会刷新 `last_referenced_at`，自动顺延、上不封顶；**查看历史不续期**）；② 钩子失败的孤儿快照同样有界（创建起至少保留至该期限）；③ 刚写入的快照不会被命中，与收尾钩子写入无并发冲突。`CleanupReport` 增加 `snapshot_deleted` 计数；dry-run 语义与现有各段一致 |

**R2 实删的上线条件**：先通过 `maintenance init-platform` 建好 `db_deepagent.result_snapshots` 表，再启用 R2 的目录实删。维护作业每次执行 R2 前只核对一次该表是否存在；表不存在或无法确认时，跳过本次 R2 实删并在报告中说明原因。无需逐个目录查询是否已有快照。此核对只防止整批目录在快照表缺失时被删除；单条快照写入失败仍按下文的已知取舍处理。

**验收要点（三项改造共用）**：

- R1：`saved_at`／`created_at` 在 180–365 天区间的 web_turns／qa 行**不再被清理**（对照旧行为）；
- R2：年龄超过 30 天的 res_* 目录**无论 meta.json 是否可读都会被删除**（对照旧行为：meta 缺失目录现行实现直接跳过、**实际永久残留**；被 qa 引用者受保护保留至 ~180 天）；30 天内不删；dry-run 只报告不删除；
- R2 上线条件：`result_snapshots` 表不存在或无法确认时，R2 不实删目录并报告原因；建表后才按保留期实删，不逐个目录查快照；
- R2 并发：过期目录删除期间，正在读取该目录的请求返回 `result_not_found`（可接受语义，作为用例断言）；
- R2 结构：`_scan_result_metas` 行为不变（会话发现／残留判断的回归用例照常通过）；逐会话循环不再包含 result 删除；
- R3：`last_referenced_at` 超过 `archive_retention_days`（建议 365 天）的快照行被删、未满不删；`--before` 语义与 qa／web_turns 段一致（以基准日期判定）；步骤在会话循环外**仅执行一次**；`EXPLAIN` 走 `idx_result_snapshots_lastref` 索引；dry-run 不删；
- 通用：dry-run 全程只读；`--apply` 报告与实际删除一致；全部用例需在会话锁与预算约束下验证。
- **已知取舍（2026-10-19 决策）**：快照写入失败的轮次，其表格会在 30 天后随 R2 删除而消失——已接受：单条损失可容忍、发生概率低、WARN 告警提供 30 天人工补救窗口。R2 删除前**不逐个目录检查快照记录**；仅核对一次快照表是否已建，以避免漏建表导致整批历史表格失效。

**R2 设计说明——结构、并发语义与无 meta 依赖（2026-10-19 第二次修订）**：

- 原评审建议仅移除 qa 引用保护；经进一步讨论，决策升级为两层：① 移除引用保护；② result 清理**从逐会话循环中移出**，改为独立的全局时间扫描步骤；
- **`_scan_result_metas` 保留不动**：它同时服务会话发现（`maintenance.py:227`）与疑似创建残留判断（`:300`、`:371`）——这两处需要 meta 的 session_id 归属，与清理无关；R2 的全局扫描不复用它（自己遍历目录）；
- 逐会话循环中的 result 删除段**移除**（引用保护随之消失）——其职责由全局步骤接管，避免两套删除逻辑并存；
- **并发语义**：全局步骤不取会话锁（无法枚举该拿哪些锁）；只删除已过期目录，因此不会影响 30 天窗口内的任何读取；过期目录被删时，正在读取它的并发请求可能收到 `result_not_found`——这是过期清理的可接受语义，不是误删；
- 时间来源：优先 meta.created_at（可读且可解析时，与复用保留期判定同源）；缺失／解析失败或为未来时间时回退目录／文件 mtime（未来时间夹紧为 0）——保证任何 res_* 目录都有可判定的年龄；
- **实施顺序依赖**：快照写入路径须与 R2 同批上线，且 R2 实删前必须建好快照表；未建表时跳过 R2 实删（见本节上线条件）。

**不在本节范围**：web_turns 保留期本身（已定 365 天，§7）；快照补写命令（§9.8）；维护任务触发方式（§9.10）。

### 7.2 快照表的创建、核对与降级行为

- **建表**：纳入 `maintenance init-platform`——在 PostgresSaver／PostgresStore `setup()` 之后执行 §3 的 DDL（`CREATE TABLE IF NOT EXISTS`，幂等），与既有六张表同一入口、同一命令；
- **启动核对**：**不加入** `PLATFORM_TABLES` 的阻断式核对（六表缺失会让装配直接报"缺少表、先运行 init-platform"，`cli.py:140-144`），避免代码先于 DDL 上线时服务无法启动。采用：启动/装配时对快照表做存在性检查，缺失则 WARN 告警并**继续启动**，但 **query 入口拒绝新查询**（503／未就绪，提示先执行 `init-platform`）——避免产生“服务已接收、收尾钩子静默跳过”的无快照轮次；R2 也不得实删，直至执行 init-platform；
- **表不存在时的行为**：

| 场景 | 行为 |
| --- | --- |
| 新查询入口（query） | **拒绝新查询**，返回 503／未就绪并提示先执行 `init-platform`；避免产生无快照轮次 |
| 收尾钩子写入 | 运行中表被意外删除时：WARN 日志跳过，不阻断本轮返回（正常升级窗口由 query 入口拒绝，不依赖此路径） |
| 历史回退分支（results API） | 视为"无快照"→ 按现行 404 语义返回（`RESULT_NOT_FOUND`）；同时 WARN 告警提示表缺失 |
| R2 result 目录清理步骤 | 不实删目录，并在报告中说明快照表缺失；仅在表存在时执行 R2 实删 |
| R3 快照清理步骤 | 报告"快照表不存在，跳过该段"，**不使整个 cleanup 失败**（R2 按上行跳过实删，其他清理段照常执行） |

- **升级顺序**：先执行 `init-platform` 建表，再启动 Web 服务并启用 R2 实删。若忘记建表，Web 服务可以启动，但 query 入口拒绝新查询、R2 不实删；补建表后重启 Web 服务，恢复接收新查询；维护作业下次运行时自行核对表存在，即可恢复 R2 实删。无需支持 Web 服务运行中自动恢复。不能把"服务可启动"理解为"可以在未建表时清理 result 目录"或"可以接收新查询"；
- 启动告警／指标的接入方式归详细设计。

### 7.3 快照写入的依赖接线（现状缺口与注入方案）

**现状缺口（已核实）**：`_make_finalize_hook(webstore, readiness, source_id, holder)`（`runs.py:349`）的闭包里没有 cfg、`ResultStore`，也没有平台池访问途径——快照写入需要的三样能力它都拿不到：① `load_meta`／`read_rows_cells` 需要 `ResultStore`；② 快照表 INSERT 需要 lg_persist 的数据库连接；③ 快照行清理（R3）由维护作业承担，与钩子无关。相关事实：`run_agent_query` 每轮经 `_open_platform_pool`（`runs.py:756,811`）开池、`runner.run()` 返回后的 `finally` 才关闭（`runs.py:859-867`）——钩子在该窗口内执行，池是活的，但钩子创建时确实没拿到它；`WebRuntime` 的池字段 `_platform_pool` 私有且仅在 `get_store()`（`runtime.py:123,136-154`）惰性构建后才存在。

**接线方案（2026-10-19 定稿：方案 A——钩子构造点移入 `run_agent_query`）**：

1. **构造点后移**：`_make_finalize_hook` 的调用从 `execute_web_query` 移至 `run_agent_query`（services／平台池装配完成之后、Runner 构造之前）——钩子在构造时即可绑定本轮全部依赖，“成品 hook”问题消失；
2. **注入 `snapshot_writer`**：构造时绑定经**本轮平台池**执行 result_snapshots 写入的可调用——钩子不感知池与 SQL 细节，fake 可替换测试；
3. **注入 `results`（ResultStore）**：绑定 `services.results`，供 `load_meta`／`read_rows_cells`（文件读取，不需要任何数据库连接）；
4. **不引入新依赖**：不为钩子新建平台池、不每证据建连接；原拟的 `WebRuntime.get_platform_pool()` 公开访问器**仅 B 方案（外层构造＋回填）需要**，A 方案下不需要——若将来采用 B 再加。

**A 方案的依赖传递（必须补全）**：`run_agent_query` 目前只收到 `session_id`／`question`／`request_id`／`source_id`／`registration`／`finalize_hook`／`session_lock`，而 `_make_finalize_hook` 还需要 `webstore`、`readiness` 与 `holder`。落地时二选一：① 由 `execute_web_query` 将 `webstore`／`readiness`／`holder` 一并传入 `run_agent_query`（`holder` 必须传回，`_project_result` 依赖其中 `history_saved`）；② `run_agent_query` 内自行构造 `WebStore`／获取 readiness，但 `holder` 仍须由调用方传入或返回。§8 的“钩子调用方不变”仅指 Runner 仍调用钩子；`_make_finalize_hook` 的构造点与 `run_agent_query` 的签名会变化。

**明确不做（三条）**：

- **不为钩子新建平台池**——复用本轮已打开的池（钩子执行窗口内池必然存活，时序见本节“现状缺口”）；
- **不为每个证据新建连接**——快照写入复用本轮已打开的平台池连接，按证据逐条执行 INSERT（与 §4 单条隔离一致）；
- **钩子内不做 `load_base_db_agent_config()` 重复装配**——ResultStore 经注入获得（若走注入缺位后备，可如 `router.read_result` 处理器同款惰性自建，`router.py:377` 先例）。

**实施顺序依赖**（与 §7.1 R2 相同）：快照写入（钩子）与 R2 删除**同批上线**，且 R2 实删前必须先建好快照表。存量结果不补录，其目录到期删除后的历史表格失效属于 §1 已接受的取舍；新轮次则由收尾钩子写入快照。

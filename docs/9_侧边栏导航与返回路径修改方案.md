# 9 侧边栏导航与返回路径修改方案

编写日期：2026-11-02。状态：**已确认，待实施。** 2026-11-02 经多轮审核修订，修订内容见第 13 节。

本文落实 2026-11-02 对运行中 WebUI（`http://127.0.0.1:5174/`）的导航核对结论。核对时使用的示例数据是数据源「订单库pg」（`db_src_16`）、工作区 `ws_68`、采集作业 `coll_job_9`。这些名称和 ID 只用于说明路径，不是接口契约。

本文只改导航、路径和返回，不新增路由，不改作业、版本、运行和数据资产的业务规则。

## 1. 与既有文档的关系

路由、页面状态、接口和作业模型仍以 [6.3 WebUI 设计稿索引与实现约定](6.3_WebUI设计稿索引与实现约定.md)、[6 工作区采集作业与发布作业四层模型](6_工作区采集作业与发布作业四层模型.md) 和 [6.2 MetaWeave 改造实施方案](6.2_MetaWeave改造实施方案.md) 为准。

本文替换 6.3 中下列导航约定，6.3 已在对应位置加了指向本文的说明：

- §3.2「返回路径」四条。
- §3.3 侧边栏里两个全局作业子菜单的显示名称，以及工作区内部二级导航在页面上的落实方式。
- §4 路由表里两个全局作业列表的页面名称。路由本身不变。

两文冲突时：导航、路径、返回以本文为准；路由、接口、作业状态仍以 6.3 和 doc 6 为准。设计稿 35、37 的侧边栏和标题随本文改名，实现时不照抄设计稿里的旧名称。

6.3 §3.3 已规定工作区内部存在「概览 / 采集作业 / 发布作业」。组件 `frontend/src/components/WorkspaceNav.vue` 已按这个结构写好，但没有任何页面引用它。本文要求把它挂到工作区内部页面，而不是再在侧边栏增加一层。

## 2. 要改的几件事

1. **侧边栏**继续只有「数据资产」「数据源管理」「工作区管理」三个业务入口。两个子菜单保留，改名为「全部采集作业」「全部发布作业」。进入这两个全局页时子菜单必须展开，且不能被收起。
2. **工作区内容区**增加固定的区内切换：概览、采集作业、发布作业。工作区详情、区内作业列表、新建、作业详情、执行页都使用这一排。
3. **路径**从第二层页面开始显示，按资源从属**固定**，不随进入方式变化。落地页不显示。
4. **右上角「返回」**回到用户来的地方。来源由路由 query 里唯一的 `from` 参数记录。目标与路径上一段不同时，按钮文案写明去向。不再使用浏览器历史。
5. 创建、删除、保存及「不存在」提示后的跳转，统一按第 7.6 节处理。
6. 去掉画像页上指向不存在地址的「重新采集画像」。

## 3. 现状

2026-11-02 按当时前端代码和运行页面核对，行为如下。

### 3.1 侧边栏高亮是对的，子菜单和名称会误导

`frontend/src/components/AppSidebar.vue` 的高亮范围：

| 入口 | 高亮条件 |
| --- | --- |
| 数据资产 | `/data-assets` 及其子路径 |
| 数据源管理 | `/data-sources` 及其子路径 |
| 工作区管理 | `/workspaces`、`/workspaces/...`、`/collection-jobs`、`/publish-jobs` |
| 数据采集作业 | 仅 `path === '/collection-jobs'` |
| 数据发布作业 | 仅 `path === '/publish-jobs'` |

因此「工作区管理 → 工作区详情 → 数据采集作业 → 作业详情」四步都亮「工作区管理」。这是预期结果：侧边栏表示模块，不表示层数。工作区详情、作业详情、执行页、数据库画像、对象列表都不进入侧边栏。

点击「工作区管理」文字跳转到 `/workspaces` 并展开子菜单的行为已经实现，后续改造需保留。

问题有三个：

- 侧边栏「数据采集作业」和区内页面标题「数据采集作业」是两个页面。前者是 `/collection-jobs`，不带工作区；后者是 `/workspaces/:workspaceId/collection`。发布侧同样重名。
- `workspacesExpanded` 只在侧边栏组件创建时赋值一次。应用挂载时路由尚未完成首次导航，这个初始值经常是收起。父项高亮是计算属性，会跟着路由变化。结果是打开或刷新 `/collection-jobs`、`/publish-jobs` 时，「工作区管理」已高亮，子菜单仍是收起的，当前子项看不见。
- 展开箭头是 `span role="button" tabindex="0"`，放在「工作区管理」的 `<a>` 里面。链接内再放可交互控件是无效结构，读屏器和键盘行为都不可靠。

### 3.2 返回目标多数写死，只有三处走浏览器历史

| 页面 | 当前返回目标 |
| --- | --- |
| 工作区列表 | 固定 `/data-sources`。从侧边栏进入时，上一页并不是数据源管理 |
| 工作区详情 | 固定 `/workspaces`，丢掉进入列表时的 `source_id`、`db_type`、`page` |
| 区内采集/发布列表 | `/workspaces/:workspaceId` |
| 作业详情 | 区内作业列表，不区分用户是从全局列表进来的 |
| 执行页 | 该作业详情 |
| 全局作业列表 | `/workspaces` |
| 新建工作区 | `/workspaces`，只保留当前表单里的 `source_id` |
| 数据库画像 | `/data-assets` |
| 数据源新建、修改、详情 | `/data-sources`。修改页的路径上一段是数据源详情，返回却跳过它 |
| 对象列表 | 历史里有上一页就 `router.back()`，否则 `/data-assets` |
| 新建作业 | 历史里有上一页就 `router.back()`，否则对应的区内作业列表 |
| 对象详情 | 仅当上一页是对象列表时 `router.back()`，否则直接进入带 `schema_name` 的对象列表。已经接近目标行为 |

从「全部采集作业」点「作业详情」后，地址变成 `/workspaces/ws_68/collection/jobs/coll_job_9`，「返回」进入该工作区的采集列表，全局列表上的数据源、工作区、关键字和页码都不再存在。

对象列表只要历史里有上一页就后退，直接打开对象列表再返回，可能回到另一个模块。

### 3.3 筛选写入 query 时会重建整条 query

`WorkspacesView.vue` 的 `writeQuery` 每次只用 `db_type`、`source_id`、`page` 重建 query。页内改一次筛选，地址上任何其他参数都会被抹掉。`from` 要保留，这里必须改。数据源列表和全局作业列表也是用同样方式写 query，但它们不需要保留 `from`。

另外两处会丢失来源参数：

- `JobDetailView.goRun()` 进入执行页时，query 只写 `revision_no` 和 `mode`。
- 其余在同一页内改参数的代码已经用 `...route.query` 展开现有 query，不会丢参数：作业详情的 `page`、`run_id`、`step`，执行页的 `mode`、`run_id` 和「改用最新版本」链接，区内作业列表的 `q`，全局作业列表的翻页，对象列表。这是后面要保持的约束，见第 7.7 节。全局作业列表的筛选和关键字写入是重建 query，不展开；它不带 `from`，不用改。

`DataSourcesView.vue` 里「相关工作区」链接用新对象构造 query，需要增加 `from`。`BlockingRunList.vue` 进入作业详情的链接只带 `run_id`，没有来源，按默认上一级处理，不用改。

### 3.4 页面出口与任务进度入口的现状去向

除了「返回」按钮，还有保存、删除、「不存在」处理和任务进度入口。它们有的离开当前页，有的只打开弹窗或刷新当前页；当前均不新建 `from`：

| 出口 | 当前去向 |
| --- | --- |
| 保存新作业成功 | 作业详情 |
| 作业详情删除作业成功 | 区内作业列表 |
| 区内或全局作业列表删除作业成功 | 关闭弹窗，留在当前列表刷新 |
| 创建工作区成功 | 工作区详情 |
| 工作区详情删除工作区成功 | `/workspaces`，不带筛选 |
| 工作区列表删除工作区成功（含恢复的任务） | 关闭弹窗，留在当前列表刷新 |
| 工作区列表、详情的「查看工作区删除进度」 | 当前页打开工作区删除任务弹窗 |
| 工作区列表、详情的「前往数据源处理删除任务／知识清理任务」 | 跳转对应的 `/data-sources/:sourceId`，不带来源 |
| 数据源详情的任务进度按钮 | 当前页按任务类型打开数据源删除、知识清理或工作区删除任务弹窗 |
| 数据源列表删除数据源成功 | 关闭弹窗，留在当前列表刷新 |
| 数据源详情删除数据源成功 | `/data-sources` |
| 数据源详情完成知识清理或工作区删除任务 | 关闭弹窗，留在当前详情刷新 |
| 工作区不存在 | `/workspaces?notice=not_found` |
| 作业不存在，或作业不属于该工作区 | 区内作业列表，附 `notice=not_found` |
| 执行页的 `revision_no` 对不上任何版本 | 不跳转，停在执行页，横幅提示修正地址或从作业详情重新进入 |

### 3.5 画像页有一条死链

`frontend/src/views/DatabaseProfileView.vue` 的「重新采集画像」指向 `/data-sources/:sourceId/collection-jobs/new`。路由表没有这个地址。打开 `/data-sources/db_src_16/collection-jobs/new` 会进入「页面不存在」。

一个数据源可以有多个工作区、多个采集作业，画像页不能猜哪一个作业该被重新执行。

## 4. 侧边栏

### 4.1 菜单结构

```text
首页
数据资产
数据源管理
工作区管理
  ├─ 全部采集作业
  └─ 全部发布作业
系统设置（仍为待开放，不可点）
```

「首页」继续保留，不在本文改造范围内。新建查询、会话历史、系统设置都不改。

子菜单文案只改显示名称，路由不变：

| 显示名称 | 路由 |
| --- | --- |
| 全部采集作业 | `/collection-jobs` |
| 全部发布作业 | `/publish-jobs` |

全局列表页的一级标题与菜单一致，改为「全部采集作业」「全部发布作业」，去掉标题里的「(全局)」。页内说明仍写明这是跨数据源、跨工作区的列表。

### 4.2 高亮

| 条件 | 高亮 |
| --- | --- |
| `/data-assets` 及其子路径 | 数据资产 |
| `/data-sources` 及其子路径 | 数据源管理 |
| `/workspaces`、`/workspaces/...` | 工作区管理。两个子项都不高亮 |
| `/collection-jobs` | 工作区管理，以及「全部采集作业」 |
| `/publish-jobs` | 工作区管理，以及「全部发布作业」 |

工作区内部的采集或发布页面不得高亮「全部采集作业」或「全部发布作业」。

### 4.3 展开与收起

点击「工作区管理」文字后跳转并展开已实现，需保留。下面新增或调整的是强制展开的计算、与手动状态的关系，以及箭头的结构和交互。

展开状态分成两个，互不覆盖：

| 状态 | 来源 | 谁能改 |
| --- | --- | --- |
| 强制展开 | 当前路由是 `/collection-jobs` 或 `/publish-jobs`，由路由计算得出，不存储 | 不能改 |
| 手动展开 | 组件内保存的布尔值，初始为收起 | 只有两个动作能改：点击箭头切换；点击「工作区管理」文字时设为展开 |

子菜单实际是否展开 = 强制展开 或 手动展开。

- 强制展开必须由当前路由实时计算，不能只在组件创建时读一次路由。打开、刷新、深链进入这两个路由时，子菜单展开。
- 强制展开不写入手动状态。
- 离开全局作业页时：
  - 点击「工作区管理」文字，这次点击就是手动展开，覆盖进入前的状态，子菜单保持打开。
  - 用侧边栏其他入口，或其他方式离开，子菜单恢复为进入前的手动状态：进入前是收起的就收起，进入前手动展开过的就仍展开。
- 处于强制展开时，箭头保持 `aria-expanded="true"`，同时 `aria-disabled="true"`，样式变灰。点击、Enter、Space 都不改变状态，也不触发跳转。这样当前子项始终可见。
- 不处于强制展开时，点击箭头只切换手动状态，不改变路由。
- 位于 `/workspaces/:workspaceId/...` 时，不因为路径里含有 collection 或 publish 而强制展开。

**结构。** 箭头不能放在「工作区管理」的 `<a>` 里面。改成一个行容器内并排两个控件：

```text
行容器（承担选中背景和悬停样式）
  ├─ <a>  工作区管理
  └─ <button>  展开/收起箭头
```

- 选中背景、圆角和悬停色放在行容器上，使视觉效果与现在一致。
- 焦点顺序先链接，后箭头。
- 箭头按钮的无障碍名称沿用「展开或收起工作区管理子菜单」，键盘操作为 Enter 和 Space。

## 5. 工作区内部切换

在下列页面的页头下方放同一排切换，复用 `WorkspaceNav.vue`：

| 页面 | 路由 | 高亮项 |
| --- | --- | --- |
| 工作区详情 | `/workspaces/:workspaceId` | 概览 |
| 采集作业列表、新建、详情、执行 | `/workspaces/:workspaceId/collection` 及其子路径 | 采集作业 |
| 发布作业列表、新建、详情、执行 | `/workspaces/:workspaceId/publish` 及其子路径 | 发布作业 |

高亮由当前路径决定：概览只在路径恰好等于 `/workspaces/:workspaceId` 时高亮；采集、发布使用路径前缀，使新建、详情和执行都高亮所属项。

这需要改 `WorkspaceNav.vue` 的接口：删除 `current` 属性，只保留 `workspaceId`，由组件按当前路径判断。各页面不再传 `current`。

无障碍语义：

- 当前路径与链接目标完全一致时，该链接设置 `aria-current="page"`。
- 当前在这一项的子路径上（新建、详情、执行），该链接设置 `aria-current="true"`，同时有视觉高亮。不得再对这些子路径设置 `aria-current="page"`，因为链接目标是列表，用户实际不在那一页。

三个链接的目标：

| 项 | 目标 |
| --- | --- |
| 概览 | `/workspaces/:workspaceId` |
| 采集作业 | `/workspaces/:workspaceId/collection` |
| 发布作业 | `/workspaces/:workspaceId/publish` |

区内切换属于层级跳转，按第 7.3 节第 3 条处理 `from`。区内列表自己的关键字 `q` 不带到另一类作业列表。

从采集作业详情点「发布作业」，进入该工作区的发布列表，而不是某个发布作业详情。反向相同。

以下页面不放这排切换：工作区列表、新建工作区、两个全局列表、数据源页面、数据资产页面、首页和查询页。

`WorkspaceNav.vue` 文件头注释里「采集与发布作业不是全局菜单」已过时。注释改为：区内这三项必须带 `workspace_id`；侧边栏另有不带工作区的「全部采集作业」「全部发布作业」。

## 6. 路径导航

### 6.1 放在哪里

以下落地页不显示路径：

- `/data-assets`
- `/data-sources`
- `/workspaces`（带筛选或带 `from` 时也不显示）
- `/collection-jobs`
- `/publish-jobs`
- `/`、查询页、系统设置占位

其余页面都显示路径。最后一段是当前页，不可点，设置 `aria-current="page"`；前面每一段都是链接。容器使用 `nav`，`aria-label="页面路径"`。

页头结构（自上而下）：

```text
路径
标题块                                  返回
区内切换（仅工作区内页面）
```

路径放在标题块上方，在页头左列。「返回」保留在现有右侧操作区，按钮顺序和样式以实施时的当前代码为准；本方案仅调整其目标和文案，不按旧设计稿回退近期按钮顺序、尺寸及右置调整。区内切换放在整个页头下方，独占一行。

名称用页面已经加载的显示名：数据源 `display_name`、工作区 `workspace_name`、作业 `job_name`。对象段使用 `schema_name.object_name`。

名称到达之前，路径里任何一段都不显示 ID：

| 段 | 名称到达前显示 |
| --- | --- |
| 当前段 | 该页标题 |
| 上级的工作区名 | 工作区 |
| 上级或数据资产页里的数据源名 | 数据源 |
| 上级的作业名（执行页） | 作业 |

这些上级段在名称到达前仍然是可点击的链接，因为链接目标只需要路由里已有的 ID。页面正文里现有的「工作区 {名称}（{ID}）」文案不属于路径，不在本文改动范围。

视觉沿用现有文字色：链接 `#66788F`，当前段 `#17293F`，分隔符使用 `/`，字号 13px。不新增一套导航样式。

### 6.2 路径固定，不随进入方式变化

路径的可见文字只由资源从属决定：同一个页面，从数据源进入、从侧边栏进入、从全局列表进入，路径文字完全相同。

链接地址允许不同：第 6.4 节规定，「工作区管理」这一段在 `from` 指向工作区列表时，链到那条带筛选的列表，否则链到 `/workspaces`。所以工作区详情上，「返回」和路径里的「工作区管理」落在同一个地址，按钮可以稳定地只写「返回」。验收比较路径时只比较可见文字，不比较链接地址。

原因：侧边栏在这些页面上高亮的是「工作区管理」，路径起点也必须是它；路径回答「我在哪」，「返回」回答「我从哪来」，两者不需要一致。数据源名称不进入工作区内页面的路径，工作区页头已经显示它所属的数据源。

### 6.3 各页面的路径

| 页面 | 路径 |
| --- | --- |
| 数据库画像 | `数据资产 / {数据源名}` |
| 对象列表 | `数据资产 / {数据源名} / 对象列表` |
| 对象详情 | `数据资产 / {数据源名} / 对象列表 / {schema}.{对象名}` |
| 数据源详情 | `数据源管理 / {数据源名}` |
| 新建数据源连接 | `数据源管理 / 新建数据源连接` |
| 修改数据源连接 | `数据源管理 / {数据源名} / 修改` |
| 新建工作区 | `工作区管理 / 新建工作区` |
| 工作区详情 | `工作区管理 / {工作区名}` |
| 区内采集作业列表 | `工作区管理 / {工作区名} / 采集作业` |
| 新建采集作业 | `工作区管理 / {工作区名} / 采集作业 / 新建采集作业` |
| 采集作业详情 | `工作区管理 / {工作区名} / 采集作业 / {作业名}` |
| 执行采集作业 | `工作区管理 / {工作区名} / 采集作业 / {作业名} / 执行` |
| 发布侧四个页面 | 与采集侧对称，「采集作业」换成「发布作业」 |

步骤详情抽屉不单独占路径段，仍算作业详情页。未知路由页保持现有「返回首页」「工作区管理」入口，不加路径。

### 6.4 每一段的链接目标

| 段 | 目标 |
| --- | --- |
| 数据资产 | `/data-assets` |
| 数据库画像里的 `{数据源名}` | `/data-assets/:sourceId/profile`（在画像页本身是当前段，不可点） |
| 对象列表 | `/data-assets/:sourceId/objects`，保留 `schema_name` |
| 数据源管理 | `/data-sources` |
| 数据源页面里的 `{数据源名}` | `/data-sources/:sourceId` |
| 工作区管理 | 当 `from` 指向 `/workspaces…` 时，直接使用校验后的该地址及其 query（恢复筛选和页码），不再附加当前页面的 `from`；否则是 `/workspaces` |
| `{工作区名}` | `/workspaces/:workspaceId` |
| 采集作业、发布作业 | `/workspaces/:workspaceId/collection`、`/publish` |
| `{作业名}` | `/workspaces/:workspaceId/collection|publish/jobs/:jobId` |

工作区内页面里的路径链接按第 7.3 节第 3 条处理 `from`。其中「工作区管理」使用已保存的工作区列表地址时，该地址已经是完整目标，不再套用附加 `from` 的规则；即使目标本身没有内层 `from`，也不补入当前外层来源，已有内层 `from` 则保留、不覆盖。

## 7. 返回与来源

### 7.1 返回的含义

「返回」回到用户来的地方；没有记录来源时，回到路径中的上一段。

不得再读 `window.history.state.back`，不得调用 `router.back()` 作为这些页面的返回实现，也不得依赖浏览器历史推断路径。

按钮文案规则只有两条，先后判断：

1. 返回目标取自 `from` 的值，并且目标与路径上一段不同，或页面是带 `from` 的落地页（工作区列表）：文案写明去向，见下表。
2. 其他情况，即返回目标是默认上一级：一律写「返回」。

| `from` 的值 | 文案 |
| --- | --- |
| `/data-sources`（含筛选） | 返回数据源管理 |
| `/data-sources/:sourceId` | 返回数据源 |
| `/collection-jobs`（含筛选） | 返回全部采集作业 |
| `/publish-jobs`（含筛选） | 返回全部发布作业 |
| `/workspaces…` | 返回。因为它与路径里的「工作区管理」是同一个地址 |

此表只在返回目标取自 `from` 时使用，默认上一级不查此表。例如数据源详情、新建数据源、修改数据源连接的返回目标是默认上一级，文案都是「返回」。数据源详情现在的「返回数据源管理」改为「返回」，上一级名称由路径表示。

### 7.2 `from` 参数

`from` 是页面地址上的一个 query，值以用户离开页面的站内地址为基础生成，保留筛选、分页及合法的内层来源，不保存一次性提示参数 `notice`。它只存在于前端路由里，不提交给任何后端接口。

**值与编码规则。** `from` 的值整段当作一个不可拆分的字符串：

- 值以来源页的 `route.fullPath` 为基础；新建 `from` 时，通过共用来源函数移除来源地址当前层的 `notice`，其他筛选、分页和合法的内层 `from` 保留。没有 `notice` 时原样使用 `route.fullPath`；需要移除时用 query 对象或 `URLSearchParams` 重建，不手拼地址。内层 `from` 如果存在，已经编码过一次。
- 写入：通过路由的 query 对象（或 `URLSearchParams`）写入，由它负责编码。禁止把值手拼进地址字符串；禁止先 `encodeURIComponent` 再交给 query 对象，那会二次编码。
- 读取：每一层都用 `URL` 或 `URLSearchParams` 解析，不手写 `decodeURIComponent`。校验作用在解析后的值上，不比较编码后的字符串。
- 追加或修改其他参数（包括 `notice`）：把目标地址解析成路径和 query 对象，再用 query 对象写回，不在字符串末尾拼 `&notice=not_found`。
- 线上形态取决于路由如何编码，本文不规定，也不写进验收。

一层示例。从 `/collection-jobs?source_id=db_src_16&workspace_id=ws_68&q=订单&page=2` 进入作业详情时，作业详情的 `route.query.from` 解析后等于这个完整地址。验收断言是：作业详情自己的 `route.query` 里只有 `from`，没有 `workspace_id`、`q`、`page`。作业详情用 `page` 表示运行历史页码，若漏出来，历史会被翻到第 2 页。

两层示例。工作区列表的地址是 `/workspaces?source_id=db_src_16&from=%2Fdata-sources%2Fdb_src_16`（内层 `from` 已编码一次）。作业详情的 `route.query.from` 解析后就是这个字符串；再用 `URLSearchParams` 解析它，得到内层 `from` = `/data-sources/db_src_16`。内层值带自己的 query 时（例如 `/data-sources?status=active&q=pg`），其中的 `&` 在内层已经被编码，不会漏到外层。

**白名单。** 只接受下列站内地址，其他一律忽略：

| 形式 | 说明 |
| --- | --- |
| `/data-sources`，可带 query | 数据源列表及其筛选 |
| `/data-sources/:sourceId`，不带 query | 数据源详情 |
| `/workspaces`，可带 query | 工作区列表及其筛选 |
| `/collection-jobs`，可带 query | 全部采集作业及其筛选 |
| `/publish-jobs`，可带 query | 全部发布作业及其筛选 |

**校验。** 值必须以 `/` 开头，不以 `//` 开头，不含反斜杠和控制字符，用 URL 解析后同源、路径匹配白名单，解码后长度不超过 2000 字符。数据源两种形式内部不得再含 `from`。其余任何情况都视为没有 `from`，返回按默认上一级处理。

**嵌套。** 只有工作区列表自己的地址上可能带 `from`（来自数据源页面）。它的子页面把这个带 `from` 的列表地址整体作为自己的 `from`，所以值里最多嵌套一层。校验函数按上面的长度上限兜底。

内层 `from` 必须再校验一次，规则同上。内层不合法时只丢掉内层：外层的工作区列表地址仍然有效，只是这条来源链少了「返回数据源」。丢弃内层时，传给下一页的值也要用去掉内层后的列表地址。

### 7.3 谁写入，怎么传递

三条规则：

1. **只有下面「写入点」表里的入口才新建 `from`。** 以该入口所在页面的 `route.fullPath` 为基础，按第 7.2 节移除 `notice` 后保存，保留筛选、分页和合法的内层 `from`。这里只明确剔除 `notice`，不泛化删除其他 query，也不要求各列表页展示提示后立即清除当前地址上的 `notice`。其他任何链接都不得把 `from` 改写成当前页地址。
2. **工作区内部的下钻一律原样传递。** 工作区详情 → 区内列表 → 作业详情 → 执行页之间的链接、区内列表行内链接、工作区详情「最近运行」里的「作业详情」、新建作业、保存成功后的跳转，都把当前页地址上的 `from` 原样带到下一页，不新建，也不改写成当前页的地址。例如从数据源详情进入工作区列表，再进入作业详情时，`from` 原样保留进入工作区时按上一条保存的列表来源；该值以工作区列表的 `route.fullPath` 为基础，已去掉当时的 `notice`。按第 7.2 节逐层解析，外层是带 `source_id=db_src_16` 的工作区列表，内层来源是 `/data-sources/db_src_16`，不要求某一种斜杠编码形式。作业详情返回区内列表时仍带上这条工作区列表来源，工作区详情才能回到带筛选的列表。执行页自己的 `revision_no`、`mode`、`run_id` 不写进作业详情；作业详情的 `page`、`run_id`、`step` 不写进作业列表。
3. **路径链接和区内切换。**
   - 「工作区管理」段按第 6.4 节直接采用已保存的工作区列表目标，不再叠加当前页面的 `from`。下面两条适用于其他路径段和区内切换。
   - 先按第 7.4 节求出本页「返回」按钮的实际目标。路径段目标与该实际目标是同一页时，原样带上 `from`。「同一页」按路由路径判断，不比较 query。例如执行页的作业名（目标是作业详情），区内作业列表页的工作区名（目标是工作区详情），以及从数据源进入时作业详情、新建作业页的「采集作业」（目标是区内列表）。这些路径段与「返回」去同一页，两者带的来源一致。
   - 路径段目标与「返回」实际目标不是同一页，或点击区内切换时，只在 `from` 指向工作区列表 `/workspaces…` 时保留它；`from` 指向全局作业列表时丢弃。例如从全部采集作业进入作业详情或新建作业页，「返回」去全局列表，路径中的「采集作业」去区内列表，所以点击该路径段时丢弃全局来源。之后再进入其他作业，不再出现「返回全部采集作业」。点击工作区名或区内切换同样处理，发布侧对称。

写入点（表中的来源地址均按第 7.2 节移除 `notice`）：

| 页面上的入口 | `from` 的值 |
| --- | --- |
| 数据源列表「相关工作区」 | 数据源列表当前地址，含筛选 |
| 数据源详情「查看该数据源的工作区」「新建工作区」 | `/data-sources/:sourceId` |
| 工作区列表「进入工作区」「新建工作区」 | 工作区列表当前地址，含它自己的 `from` |
| 全部采集/发布作业的「作业详情」 | 全局列表当前地址，含筛选和页码 |
| 全局列表的新建作业弹窗确认，进入新建页 | 同上 |
| 侧边栏任一入口、首页入口 | 不写 |

侧边栏进入的落地页地址上没有 `from`，所以从侧边栏进入的流程里不会出现来源。

### 7.4 各页怎么认 `from`

每个页面只认下表中的值，不认或没有时返回默认上一级。

| 页面 | 认的 `from` | 没有或不认时的返回目标 |
| --- | --- | --- |
| 数据资产、数据源管理、全部采集作业、全部发布作业 | 不认 | 无返回按钮 |
| 工作区列表 | `/data-sources…`、`/data-sources/:sourceId` | 无返回按钮 |
| 新建工作区 | `/workspaces…`、`/data-sources…`（列表形式当前无写入点，仅防御性认可）、`/data-sources/:sourceId` | `/workspaces`；当前表单已选择数据源时，以该数据源的 `source_id` 筛选列表，未选择则不带 |
| 工作区详情 | `/workspaces…` | `/workspaces` |
| 区内作业列表 | 不认 | 工作区详情 |
| 采集作业详情 | `/collection-jobs…` | 区内采集列表 |
| 发布作业详情 | `/publish-jobs…` | 区内发布列表 |
| 新建采集作业 | `/collection-jobs…` | 区内采集列表 |
| 新建发布作业 | `/publish-jobs…` | 区内发布列表 |
| 执行页 | 不认 | 作业详情 |
| 数据库画像 | 不认 | `/data-assets` |
| 对象列表 | 不认 | 该数据源的画像页 |
| 对象详情 | 不认 | 该数据源的对象列表，保留 `schema_name` |
| 数据源详情、新建数据源连接 | 不认 | `/data-sources` |
| 修改数据源连接 | 不认 | 该数据源的详情页（路径上一段）。保存成功后仍进入 `/data-sources`，与现状一致 |

认到 `from` 时，返回直接跳到 `from` 的值，不额外附加任何参数。返回恢复来源页的筛选、分页及合法的内层来源，不恢复写入时已经剔除的一次性 `notice`，地址里也不会多出来源参数。

新建工作区页 query 中的 `source_id` 用于表单初始预选，与 `from` 分开处理。无有效且被本页认可的 `from` 时，页头「返回」和表单「取消」沿用当前 `cancel()` 的行为，以表单当前选择作为返回列表的筛选；认到 `from` 时直接使用该来源，不追加或替换其 `source_id`。

返回目标是默认上一级且上一级在工作区内（例如执行页回作业详情）时，`from` 原样带过去，保证下一次返回仍然有效。

「认」按类型匹配：采集作业详情不认 `/publish-jobs…`，发布作业详情不认 `/collection-jobs…`。

### 7.5 几个边界

- **工作区列表改筛选。** 用户从数据源 A 进入列表，再把筛选改成数据源 B 或清空，「返回」仍回到进入时记录的来源。所以 `writeQuery` 必须把 `from` 带在新 query 里，不重建时丢弃它。
- **工作区列表不显示路径。** 它是落地页，所以在 `from` 存在时只显示带去向文案的「返回」，如「返回数据源」。
- **全局列表上的任何筛选写入**不需要保留 `from`，它们不会带 `from`。
- **直接打开深链**（没有 `from`）：返回走默认上一级，路径不变。
- **刷新**：`from` 在地址上，刷新后仍然有效。
- **区内切换的目标**不带 `q`；见第 5 节。

### 7.6 创建、删除、保存和「不存在」

各出口以下表规定为准；标注使用某页返回目标的，复用该页返回规则，其余按表中的固定去向或专门规则处理。

| 动作 | 去向 |
| --- | --- |
| 创建工作区成功 | 工作区详情，来源按下面「创建工作区后的来源」的四种情况决定 |
| 工作区详情删除工作区成功（含恢复的任务） | 工作区详情的返回目标：`from` 指向 `/workspaces…` 就回到那里，否则 `/workspaces` |
| 工作区列表删除工作区成功（含恢复的任务） | 关闭弹窗，留在当前列表刷新，不跳转 |
| 保存新作业成功 | 作业详情，`from` 原样传递 |
| 作业详情删除作业成功 | 作业详情的返回目标。从全局列表进来则回到全局列表 |
| 区内或全局作业列表删除作业成功 | 关闭弹窗，留在当前列表刷新，不跳转 |
| 工作区不存在 | 工作区详情的返回目标，附 `notice=not_found` |
| 作业不存在，或作业不属于该工作区 | 作业详情页的返回目标（作业所在层的列表），附 `notice=not_found` |
| 执行页的 `revision_no` 对不上任何版本 | 不跳转。停在执行页，保持现有横幅提示，不改地址 |
| 保存数据源成功 | `/data-sources`，与现状相同 |
| 数据源列表删除数据源成功 | 关闭弹窗，留在当前列表刷新，不跳转 |
| 数据源详情删除数据源成功 | `/data-sources`，与现状相同 |
| 数据源详情完成知识清理或工作区删除任务 | 关闭弹窗，留在当前详情刷新，不跳转 |
| 数据源不存在、对象不存在 | 与现状相同：`/data-sources`、`/data-assets`，附 `notice=not_found` |
| 工作区列表、详情的「查看工作区删除进度」 | 当前页打开工作区删除任务弹窗，不改变地址 |
| 工作区列表、详情的「前往数据源处理删除任务／知识清理任务」 | 跳转对应的 `/data-sources/:sourceId`，不附加 `from` |
| 数据源详情的任务进度按钮 | 当前页按任务类型打开对应任务弹窗，不改变地址 |

任务进度入口保持现状，不新增第 7.3 节的来源写入点；任务完成后的去向按上表区分所在页面和任务类型，不统一改成跳转列表。

**缺作业时用父页规则，不是执行页按钮的规则。** 执行页自己的「返回」目标是作业详情；但作业不存在时，作业详情也不存在，不能再回到它。所以作业缺失的重定向用的是作业详情页的返回目标：从全局列表进来回到全局列表，否则回到区内同类作业列表。执行页和作业详情页缺作业时，去向相同。

**创建工作区后的来源。** 创建成功进入工作区详情时，工作区详情上的 `from` 按进入新建页时的 `from` 决定，只有下面四种情况，按顺序判断：

1. `from` 是 `/workspaces…`：保持原样，不合成。
2. `from` 是数据源列表，或与新工作区同一数据源的详情：合成为新工作区所属数据源的工作区列表，并嵌套保留这个地址：

   ```text
   /workspaces?source_id=<新工作区的 source_id>&from=<原 from>
   ```

3. `from` 是另一个数据源的详情（用户在表单里改选了别的数据源）：合成为 `/workspaces?source_id=<新工作区的 source_id>`，不保留嵌套的 `from`。
4. 没有 `from`，或其他不认的值：不带 `from`。

第 2 种情况让从数据源详情点「新建工作区」的链路，与从「查看该数据源的工作区」进入的链路一致：返回到带该数据源筛选的列表，再返回数据源详情。工作区详情仍然只认 `/workspaces…`。

第 1 种情况有一个已知取舍：用户在新建页把数据源改选为 B，而 `from` 仍是进入时的 `/workspaces?source_id=A…`。保持原样，返回会回到用户出发的那个 A 列表，新工作区不在这个筛选里。这不算错，也不再为它增加重算规则。

**追加 `notice`。** 一律通过 query 对象，在目标自己的 query 之外追加，不覆盖目标的筛选，不拼字符串。

### 7.7 改地址的代码必须保留现有 query

**同一页内改参数**的 `router.push` 和 `router.replace`，必须展开现有 query，再覆盖自己的键：

```text
query: { ...route.query, 自己的键: 新值 }
```

不得改成只写自己的参数。已经符合的写法要保持：

- 作业详情：运行历史页码 `page`、`run_id`、`step`。
- 执行页：`mode`、`run_id`、「改用最新版本」链接的 `revision_no`。
- 区内作业列表：关键字 `q`。
- 对象列表的筛选和全局作业列表的翻页。

**跨页跳转不展开。** 进入另一个页面时，新地址只带目标页需要的参数加 `from`，不展开当前页的 query。原因：当前页的参数对目标页可能有别的含义，例如执行页把 `run_id` 当成要打开的运行，作业详情上正在看的那次运行不应被带进去。

需要改的两处：

- `JobDetailView.goRun()` 是跨页跳转：新地址只含 `revision_no`、`mode` 和当前地址上的 `from`，不展开作业详情的 `page`、`run_id`、`step`。

## 10. 四条路径的结果

### 10.1 数据源 → 相关工作区 → 工作区详情 → 作业 → 执行

「相关工作区」和过滤后的工作区列表是同一页 `/workspaces?source_id=...`，不增加菜单项。

从数据源详情进入时，列表带 `from=/data-sources/db_src_16`，页头有「返回数据源」。进入 `ws_68` 的采集作业详情后，侧边栏只亮「工作区管理」，路径为：

```text
工作区管理 / {工作区名} / 采集作业 / {作业名}
```

「返回」依次到：该工作区的采集列表 → 工作区详情 → 过滤后的工作区列表（筛选、页码都在，「返回数据源」仍在）→ 数据源详情。

要让这条链路成立，进入作业详情时地址上的 `from` 必须仍是工作区列表地址（含它自己的 `from`），不能在区内被改写，见第 7.3 节第 2 条。

从数据源详情点「新建工作区」同样如此：创建成功后，工作区详情的来源合成为该数据源过滤后的工作区列表（第 7.6 节第 2 种情况），之后的返回链与上面一致。

从工作区列表点「新建工作区」时，成功后工作区详情的来源保持进入时的列表地址（第 7.6 节第 1 种情况）。若用户在新建页改选了别的数据源，返回仍回到进入时的那个列表，新工作区不在该筛选里，这是已知取舍。

### 10.2 全部采集作业 → 作业详情 → 执行

「选择数据源」仍是全局列表上的筛选卡，不是新页面。

作业详情的侧边栏不亮「全部采集作业」。路径与从其他入口进来完全相同：

```text
工作区管理 / {工作区名} / 采集作业 / {作业名}
```

页头的「返回全部采集作业」回到 `/collection-jobs` 并带上原来的筛选和页码。执行页的「返回」先回作业详情，再从详情返回全局列表。用户点路径里的工作区名、「采集作业」或区内切换后，`from` 被丢弃，后续返回按工作区路径走，不再回到全局列表。从全局列表进入新建采集作业页后，点击路径里的「采集作业」同样丢弃全局来源。

### 10.3 全部发布作业

与第 10.2 节对称，路由和文案使用发布侧。

### 10.4 数据资产 → 数据库画像 → 对象列表 → 对象详情

侧边栏始终只亮「数据资产」。路径固定，如第 6.3 节。对象详情的「返回」进入对象列表；对象列表的「返回」进入画像；画像的「返回」进入数据资产。不再跟随浏览器历史。

## 1. 已达成共识的身份与名称

| ID 字段 | 目标值示例 | 中文名 | 归属 | 含义 |
| --- | --- | --- | --- | --- |
| `source_id` | `db_src_1`；未来可有 `file_src_1` | 数据源 ID | — | 统一的数据来源身份；数据库来源对应一条受管连接，一个来源下可以创建多个工作区。 |
| `workspace_id` | `ws_1` | 工作区 ID | `source_id` | 采集产物的隔离与共享边界。生产、测试等用途可以使用不同工作区。 |
| `collection_template_id` | `coll_tmpl_1` | 采集模板 ID | `workspace_id` | 保存可复用的采集步骤与步骤参数，供手工或定时运行使用。 |
| `collection_run_id` | UUID | 采集运行 ID | `workspace_id` | 一次实际采集，记录本次执行的步骤、参数、触发信息与结果。 |
| `publish_template_id` | `pub_tmpl_1` | 发布模板 ID | `workspace_id` | 保存可复用的发布步骤集合，供手工或定时发布使用。 |
| `publish_run_id` | UUID | 发布运行 ID | `workspace_id` | 一次实际发布，记录各步骤的发布结果及实际读取的采集产物。 |

`source_id` **字段名保留**，其值由 UUID 改为带来源类型前缀的递增短 ID；`workspace_id` 和两类模板 ID 也使用递增短 ID，两类运行 ID 保持 UUID。“采集运行”是 `collection_run_id` 的中文名称。“作业”容易同时指模板、定时安排和一次执行，因此在此模型中不单独用“作业 ID”表示运行。**目标模型没有独立于 `publish_run_id` 的 `publish_id`**；现有 `publish_id` 的语义本来就是一次发布尝试，目标名称为 `publish_run_id`，不是在其下再新增一层运行 ID。

## 2. 工作区与采集运行

```text
数据源 source_id
  ├─ 工作区 workspace_id（例如生产）
  │    ├─ 采集运行 collection_run_id = R1
  │    ├─ 采集运行 collection_run_id = R2
  │    └─ 发布运行 publish_run_id = P1
  └─ 工作区 workspace_id（例如测试）
       └─ 采集运行 collection_run_id = R3
```

- `source_id` 标识数据来源；当前 `db_src_...` 对应数据库连接，未来可以有 `file_src_...` 等来源。它**不直接决定采集产物的共享范围**；同一来源下不同工作区的运行不得相互读取或复用采集产物。
- 工作区由独立的 `workspace_info` 记录表示，保存所属 `source_id`、名称、用途说明及创建／更新时间；创建工作区不以先运行采集步骤为前提。同一数据源下工作区名称唯一。
- 同一 `workspace_id` 下的运行可以复用上游产物。例如 R1 生成 `json`，R2 只执行 `rel`，R2 可以读取 R1 留下的 `json`。因此一次运行不一定重新生成工作区内的全部产物。
- 每次手工执行或定时触发都生成新的 `collection_run_id`。故障后在原工作区内只重跑失败步骤，仍是一条属于该工作区的新采集运行；本次步骤和参数可以与上次不同。
- 一次采集运行在 `collection_run_info` 中有一行，选中的每个步骤在 `collection_run_step` 中各有一行；未选步骤没有记录，已选但因本次上游失败未启动的步骤记为 `blocked`。运行表记录整体状态，步骤表记录各步骤状态与本次实际使用的参数。
- 运行需要记录**本次实际执行**的步骤、参数、触发方式、触发人、时间和各步骤结果。未在本次执行的旧产物不应被记作本次运行新生成的产物。
- 工作区的核心职责是隔离和复用产物；它本身不承诺每次运行都采用相同的步骤或参数。

## 3. 模板与定时运行

- 采集模板定义可复用的步骤及需固定的运行参数；发布模板定义可复用的发布步骤集合。模板不是产物隔离边界，也不是一次运行记录。
- **定时采集运行必须关联采集模板；定时发布运行必须关联发布模板。**每次定时触发仍分别生成新的 `collection_run_id` 或 `publish_run_id`。
- **手工采集和手工发布可以关联模板，也可以不关联模板。**不使用模板时，由用户手工选择步骤和参数。故障后手工只重跑部分步骤属于正常场景。
- 运行历史应保存当次实际使用的步骤、参数及采集产物版本，并记录所关联的模板；后续编辑模板不能改写过去运行的含义。采集运行的步骤集合由 `collection_run_step` 行体现，额外运行参数快照由其可空的 `step_config` 记录。当前模板表不设置 `revision`；产物版本关联、手工选择采集模板后是否允许临时覆盖参数，以及定时表达式如何与模板绑定，尚待详细设计。
- 采集和发布也可以被看作一个包含人工审核环节的过程；两类模板是否合并仍在讨论。5.2 目前保留两张模板表作为待确认的建表方案。

工作区主表、两张模板表及采集／发布运行表的目标建表语句和字段注释见 [5.2_采集模板与发布模板表结构.md](5.2_采集模板与发布模板表结构.md)。

## 4. 发布运行与采集来源

- 每次发布生成新的 `publish_run_id`，归属于一个 `workspace_id`。同一次发布所选步骤的结果归在该发布运行之下；历史发布运行保留。
- 目标表以 `publish_run_info` 每次发布一行、`publish_run_step` 每个已选步骤一行记录运行及步骤结果。创建发布时以 `context_collection_run_id` 关联同一工作区内的一次采集运行，标识流程上下文；定时发布如何选择这次运行仍待设计。
- 发布可能读取同一工作区内**不同采集运行**产生的步骤产物。例如 P1 可以读取 R1 的 `json` 和 R2 的 `rel`，所以只记录 `workspace_id`，甚至只记录一个 `collection_run_id`，都不足以说明发布输入。
- 目标追溯能力是：从 `publish_run_id` 查到各发布步骤实际读取的采集产物版本，以及这些产物所属的工作区与生成运行。`publish_run_step.input_manifest` 为每步实际输入预留记录位置；具体版本标识、字段结构、依赖记录和产物保留方式待设计。
- 发布模板决定预设的发布步骤集合；发布运行记录本次实际执行的内容和读取的产物版本。定时发布必须关联发布模板，手工发布可选择关联。

## 5. 与当前实现的对应关系

| 当前实现 | 目标概念 | 当前差距 |
| --- | --- | --- |
| `source_id` 是 UUID | 字段名仍为 `source_id`，值为 `db_src_1` 等带类型前缀的短 ID | 平台库、API、路径及下游对 UUID 的类型与格式校验需要统一修改。 |
| `job_id` 是 UUID，产物位于 `output/<source_id>/<job_id>/` | 短 ID `workspace_id` 与 `output/<source_id>/<workspace_id>/` | 名称和类型均需修改；工作区的显式模型与目录版本组织尚待设计。 |
| 无独立工作区主表；`job_info` 在步骤运行后才有记录 | `workspace_info` 独立保存工作区身份与元数据 | 需支持先创建工作区，再执行采集或发布；表结构见 5.2。 |
| 同一 `job_id` 可以反复执行，但没有逐次执行 ID | 一个 `workspace_id` 对应多个 `collection_run_id`；每次执行新建一个运行 ID | `collection_run_id` 是新增身份，不能由 `job_id` 改名或与其一一对应。 |
| `job_info` 每个 `(job_id, step_name)` 一行，只保留最近状态 | `collection_run_info` 每次运行一行、`collection_run_step` 每个已选步骤一行 | 旧表由两张运行表替代；工作区最近步骤状态及发布准入如何从运行历史计算仍待设计。 |
| 每次发布新建的 `publish_id` | `publish_run_id` | 需要统一 API、平台库和下游来源标记中的名称；不另建第二个发布运行 ID。 |
| `publish_info` 每个 `(publish_id, step_name)` 一行，含 `job_id` 和 `is_current_publish` | `publish_run_info` 每次发布一行、`publish_run_step` 每个已选步骤一行，归属 `workspace_id` | 旧表由两张运行表替代；实际输入版本和“当前发布”的目标范围仍需设计。 |
| 无采集／发布模板与调度 | `collection_template_id`／`publish_template_id` 及定时触发 | 模板、运行配置快照和调度机制均未实现。 |

身份关系可概括为：**当前 `job_id` 的角色由目标 `workspace_id` 承担；一个工作区对应多个 `collection_run_id`（每次执行一个）**，不做旧值映射。现有采集页面一次点击会按步骤分别发起请求（[CreateCollectionJobView.vue](../frontend/src/views/CreateCollectionJobView.vue)）；目标模型需要把这次用户操作归为**一个**采集运行，并在其下记录多个步骤结果。现有发布服务每次预检通过后生成一个 `publish_id`（[publish_service.py](../metaweave/backend/publishing/publish_service.py)），因此它与目标 `publish_run_id` 是语义对应关系。

### 5.1 当前 UUID 列的逐表清单

以下按当前平台库 [SQLAlchemy 模型](../metaweave/backend/persistence/models.py) 列出**受短 ID 设计影响的现有 PostgreSQL `uuid` 列**。其中多数改为 `text`，旧 `job_info` 的相关列则随整张表被替代，不做逐列改型。此清单是断代改表的范围，不要求转换现有行。

| 平台表（`public`） | 现有 UUID 列 | 目标对应关系 |
| --- | --- | --- |
| `db_source_info` | `source_id`（主键） | `source_id text`，如 `db_src_1` |
| `job_info` | `source_id`、`job_id`（与 `step_name` 组成主键） | 旧表由 `collection_run_info`、`collection_run_step` 替代；运行表用 `workspace_id text` 关联工作区，新建 `collection_run_id uuid`；`source_id` 经工作区查询，不在运行表重复保存。 |
| `db_profile` | `source_id`（主键）、`job_id` | `source_id text`；`workspace_id text` |
| `table_definition` | `source_id`（联合主键组成部分）、`job_id` | `source_id text`；`workspace_id text` |
| `publish_info` | `source_id`、`job_id` | 旧表由 `publish_run_info`、`publish_run_step` 替代；发布运行表用 `workspace_id text` 关联工作区，并关联流程上下文的 `context_collection_run_id uuid`；不重复存储 `source_id`。 |
| `table_profile` | `source_id`（联合主键组成部分）、`job_id` | `source_id text`；`workspace_id text` |
| `table_column_profile` | `source_id`（联合主键及外键组成部分） | `source_id text`；与 `table_profile.source_id` 保持同一类型 |
| `table_domain` | `source_id`（联合主键组成部分）、`job_id` | `source_id text`；`workspace_id text` |

现状合计有 **8 列 `source_id`、6 列 `job_id`，共 14 列受影响**。旧 `job_info`、`publish_info` 中各两列随原表撤换；其余现有表中 6 列 `source_id` 保留字段名并改为 `text`，4 列 `job_id` 以 `workspace_id text` 承接。新的 `collection_run_id`、`publish_run_id` 分别用于目标运行表，不是把旧 `job_id` 改名得到。

下列现有 UUID 列**不改为短字符串**：`db_profile`、`table_definition`、`table_profile`、`table_column_profile`、`table_domain` 的 `publish_id` 在目标结构中改名为 `publish_run_id`，值仍为 UUID；旧 `publish_info.publish_id` 的语义由新运行表中的 `publish_run_id` 承接。`created_by_user_id`、`run_by_user_id` 等用户身份列不属于本轮短 ID 规则。新建的 `collection_run_id`、`publish_run_id` 均为 UUID。

### 5.2 非 PostgreSQL UUID 列的关联字段

这些字段目前存放 UUID **字符串**，并非 PostgreSQL `uuid` 列，但断代修改时也需要统一值格式或名称：

| 存储 | 现有字段 | 目标变化 |
| --- | --- | --- |
| Milvus `table_schema_embeddings`、`dim_value_embeddings`、`sql_example_embeddings` | `source_id`（当前 `VARCHAR(36)`）、`publish_id`（当前 `VARCHAR(36)`） | `source_id` 的值改为 `db_src_1` 等；`publish_id` 改名为 `publish_run_id`，值继续是 UUID。由 `source_id` 拼出的 `entity_id`、`col_id`、`example_id` 也随之变化。 |
| Neo4j `Table`／`Column` 节点及 `HAS_COLUMN`／`JOIN_ON` 关系 | `source_id`、`publish_id` 属性 | 来源值改为短 ID；发布属性改名为 `publish_run_id`；由 `source_id` 拼出的 `entity_id` 同步调整。 |
| NL2SQL Web 会话登记 | `source_id` 字符串 | 保留字段名，值与来源登记统一为短 ID；现有 UUID 格式校验需调整。 |

Milvus 字段可见 [集合结构规范](../nl2sql/src/services/db/migrations/milvus.sql)，Neo4j 属性可见 [CQL 生成器](../metaweave/metaweave/core/cql_generator/writer.py)。本节只盘点受 ID 值影响的存储字段，不表示已确定工作区在发布目标中的隔离方式。

## 6. 尚待决策的边界

1. **发布后的生产／测试隔离。**当前 `is_current_publish` 按 `(source_id, step_name)` 保证唯一（[models.py](../metaweave/backend/persistence/models.py)），发布时也按源切换 current（[repository.py](../metaweave/backend/publishing/repository.py)）。工作区级的采集产物隔离不自动带来下游 PostgreSQL、Milvus、Neo4j 及消费端的隔离。需决定测试工作区能否发布到生产所用目标，以及发布目标和 current 的隔离范围。
2. **产物版本和目录。**目标目录以 `output/<source_id>/<workspace_id>/` 为边界。需定义每次运行的产物版本、上游引用和保留策略；仅增加 `collection_run_id` 字段不足以追溯同一工作区内不同运行的产物。
3. **模板与手工调整。**需定义关联采集模板的手工运行能否临时覆盖步骤／参数、如何显式保存模板修改，以及定时安排如何绑定模板。当前目标表不设模板版本号，运行历史须保留实际配置快照。
4. **步骤依赖与状态。**同一工作区内的下游步骤可能读取旧运行的上游产物。需确定上游重跑后下游何时失效、失败运行是否保留先前可用产物、工作区的“当前结果”如何计算，以及并发执行与发布如何防止读取变化中的产物。

本文只确定概念和讨论边界，不预设以上问题的实现答案。

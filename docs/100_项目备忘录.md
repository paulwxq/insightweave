# 项目备忘录

## 已知问题：对话结果表格首次加载可能超过展示上限

- **状态**：已实施。对应 [3.1 历史对话结果快照表方案](3.1_历史对话结果快照表方案.md) §3.2–§3.3 的 `api.max_display_rows` 改造；首次请求可能多取行的现象仍被接受。
- **原因与表现**：前端要收到首次 results API 响应后才知道 `max_display_rows`。首次请求会以回退值 200 计算请求行数，因此仍可能取回 100 行。若服务端配置为 10 或 50，页面按配置只展示 10 或 50 行，但内存中可能已有 100 行。
- **导出行为**：服务端 CSV 导出端点已实现；文件存在时导出 `rows.jsonl` 全部已保存行，文件缺失时导出快照表中的行，与页面展示上限无关。
- **后续**：接受首次请求可能多取行的现状。

## 待办：发布步骤由后端统一排序后执行

- **需求**：后端接收用户勾选的发布步骤后，先按后端定义的固定顺序排序，再逐步执行。前端传入顺序不能决定实际执行顺序；手工发布和将来的模板定时发布都适用同一规则。
- **执行范围**：只排序并执行本次请求中选中的步骤，不因排序而补充未选中的步骤。例如请求传入 `rel、db、domain`，执行计划应为 `db、domain、rel`，不执行其他步骤；仍须通过现有的发布预检。
- **代码现状**：`frontend/src/views/PublishView.vue` 提交前会按 `SELECTABLE_STEPS` 的固定顺序排列选中步骤；`metaweave/backend/publishing/publish_service.py` 的 `normalize_publish_steps()` 目前只校验并按首次出现去重，`publish_steps()` 随后按请求顺序执行。因此，绕过前端直接调用后端或由定时任务触发时，执行顺序尚无后端保障。
- **后续实现**：在后端发布执行入口增加统一的步骤排序功能，确定唯一的发布顺序；校验和去重后生成执行计划，预检与实际发布使用同一计划。模板记录的步骤顺序也应与该后端规则一致。验证同一组步骤以不同顺序提交时执行计划相同，且未选中的步骤不会被执行。

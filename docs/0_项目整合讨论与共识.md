# 0. MetaWeave 与 NL2SQL 项目整合讨论与共识

记录日期：2026-10-16

本文汇总本次讨论，重点记录已经明确的架构方向，并区分建议、候选方案和待定事项。本文是整合前的讨论记录，不代表目录迁移、功能开发或正式命名已经完成。

## 1. 项目现状与长期定位

| 模块 | 当前能力 | 后续方向 |
| --- | --- | --- |
| MetaWeave | 元数据处理、知识数据构建与维护；FastAPI 后端、Vue 前端 | 扩展到元数据整理 |
| NL2SQL | 自然语言查询 SQL；FastAPI 后端、Streamlit 前端 | 扩展到数据分析 |

两个模块已经相对完整。整合的目标是形成一个统一的产品入口，同时保留业务模块的独立性。

## 2. 已达成共识的主要方向

### 2.1 统一 Vue WebUI，页面按业务模块组织

采用一个 Vue 主应用，承载 MetaWeave 和 NL2SQL 的页面。

- 主应用负责整体布局、导航、登录状态及通用界面能力。
- MetaWeave 页面模块负责元数据相关操作。
- NL2SQL 页面模块负责问答、SQL 与结果展示、对话历史等交互。
- 业务页面和接口调用按模块维护，整体作为统一前端构建和部署。

用户已经明确同意“一个 Vue 主应用 + 两个页面模块”的建议。当前不采用两个完整 Vue 应用再通过微前端或 iframe 拼接的方案。

前端模块可以保留独立调试入口；独立调试不等于必须独立构建和部署整个前端应用。

### 2.2 保留两个后端的业务边界

MetaWeave 与 NL2SQL 保持各自的代码目录和业务职责。

- MetaWeave 负责元数据采集、加工、文件产物和知识发布维护。
- NL2SQL 负责知识检索、自然语言查询、SQL 执行及后续数据分析。

当前优先考虑两个独立 FastAPI 服务，分别使用不同端口，并保留各自的 `.venv`、依赖、配置和调试入口。这是讨论中的推荐落地方式；统一 FastAPI 的替代方案也有讨论，尚未另行确认切换。

### 2.3 两个业务模块通过知识数据协作

按照用户说明，当前两个模块没有必须通过 API 相互调用的业务内容。

- MetaWeave 的多个处理步骤需要共享文件产物，这属于 MetaWeave 内部的存储与执行要求。
- NL2SQL 不需要访问上述文件，而是读取 MetaWeave 维护的 Milvus、Neo4j、PostgreSQL 知识数据。
- 不为了统一前端而人为增加 MetaWeave 与 NL2SQL 之间的业务 API 调用。

这里的“读取”描述的是 NL2SQL 对 MetaWeave 维护的知识数据的消费关系，不代表 NL2SQL 的对话历史等自身业务状态不需要持久化。

### 2.4 平台统一登录 session

用户已经明确：登录 session 会统一。

需要区分两类会话：

| 类型 | 职责归属 |
| --- | --- |
| 登录 session：识别当前用户及登录有效性 | 平台公共身份能力 |
| NL2SQL 对话 session / `thread_id`：组织问答及历史 | NL2SQL |

统一登录不要求把问答历史迁到用户管理模块。业务后端仍需要检查当前用户对具体资源的访问权限。

## 3. 推荐的目录与运行方式

建议在一个更大的项目目录中，采用平行布局：

```text
insightweave/             # 平台根目录，已创建于 /opt/projects/insightweave
├── frontend/             # 统一 Vue 前端（目录名已确认）
├── metaweave/            # 元数据业务模块及 FastAPI
└── nl2sql/               # 查询分析业务模块及 FastAPI
```

统一前端目录名已确认采用 **`frontend/`**。该名称常规、含义明确，表示平台的前端职责，不要求必须存在对应的 `backend/` 目录；两个后端继续按业务模块命名为 `metaweave/` 和 `nl2sql/`。此前讨论中的 `webui/` 为目录占位名，后续目录示例和迁移说明统一使用 `frontend/`。目录名称与平台品牌名分别确定，平台品牌名仍待确认。

`frontend/` 负责页面交互、状态管理和接口调用；元数据处理、SQL 生成与执行等业务逻辑由两个后端模块负责。

如果后续确认独立建设用户和权限模块，可增加平行的 `identity/` 目录。用户与权限模块的目录名称及该模块是否作为独立服务运行，尚未最终确定。

开发时，Vue 和两个 FastAPI 可以分别使用不同端口。推荐通过 Vite 开发代理提供统一接口路径；正式部署时，通过反向代理提供同一个对外域名：

```text
浏览器 → 统一域名
           ├── /                  → Vue WebUI
           ├── /api/metaweave/*    → MetaWeave FastAPI
           └── /api/nl2sql/*       → NL2SQL FastAPI
```

以上接口前缀是建议，并非已经确定或实现的路由。代理可以转换到后端现有路径。

### 3.1 统一 Git 管理，独立依赖环境

采用单仓库（monorepo）：在 `insightweave/` 根目录管理一个 Git 仓库，`frontend/`、`metaweave/` 和 `nl2sql/` 作为普通子目录，不各自初始化 Git，也不使用 Git submodule。这样前端与后端的配套修改可以一起提交，平台版本保持一致。

统一 Git 不影响各模块独立安装依赖、启动和部署：

```text
insightweave/
├── .git/                 # 规划中的平台唯一 Git 仓库
├── .gitignore
├── frontend/
│   ├── package.json
│   └── node_modules/     # 前端依赖，重新安装，不提交
├── metaweave/
│   ├── pyproject.toml
│   ├── uv.lock
│   └── .venv/            # MetaWeave 独立 Python 环境，重新创建，不提交
└── nl2sql/
    ├── pyproject.toml
    ├── uv.lock
    └── .venv/            # NL2SQL 独立 Python 环境，重新创建，不提交
```

- 复制项目时排除原项目的 `.git`，保留源码、依赖声明、锁文件及配置。原仓库保留作为历史参考，新平台从初始提交开始是当前建议；如需导入原历史，另行处理。
- 两个 Python 后端在各自目录下执行 `uv sync --locked` 创建环境；需要开发或可选依赖时，按各项目的依赖定义补充安装参数。虚拟环境中的启动脚本及可编辑安装可能引用旧路径，因此不直接复制 `.venv`。
- 前端保留依赖清单和对应锁文件，使用其现有包管理器重新安装 `node_modules`。
- `.env`、`.env.*` 等本地配置需要复制到对应的新模块目录，保留实际配置值供本机运行；不在对话、日志或报告中输出密钥内容。
- 日志目录及日志文件、`output/` 目录及其全部产物均需原样复制，即使已被 `.gitignore` 忽略也不能漏掉。复制保留与 Git 是否跟踪是两件事，Git 忽略规则不作为此次复制的过滤依据。
- 提交依赖声明、锁文件和不含真实凭据的配置样例；根 `.gitignore` 统一忽略各层级的 `.venv/`、`node_modules/`、缓存、日志和含真实凭据的本地配置，并保留 `.env.example` 等安全模板可被跟踪。已有模块级 `.gitignore` 可继续保留。

以上是管理约定，本次文档更新不初始化 Git、不安装依赖、不执行项目复制。

## 4. 用户与权限模块的讨论

用户提出：将用户管理、权限管理做成独立于 MetaWeave 和 NL2SQL 的小模块。

这是适合当前方向的候选设计，但需要区分：

- 独立代码模块：职责与代码独立，未必单独启动服务。
- 独立认证服务：有自己的进程和接口，业务后端接入其身份验证能力。

建议职责如下：

| 部分 | 建议职责 |
| --- | --- |
| 用户与权限模块 | 用户、登录退出、session、角色及权限授予 |
| MetaWeave | 执行数据源管理、采集、发布等操作的权限检查 |
| NL2SQL | 执行数据源查询、对话访问等权限检查 |
| Vue WebUI | 统一登录及管理界面，根据权限展示菜单和操作 |

集中 session 和统一令牌两种机制均有讨论。此前建议优先考虑集中 session，但具体存储、验证方式和认证入口尚未定案。

即使后续增加公共认证 API，也不改变两个业务模块目前无需相互调用业务 API 的关系。

## 5. 讨论过的统一 FastAPI 替代方案

### 5.1 一个 FastAPI 直接调用两个 Python 模块

该方案属于模块化单体：代码可以分开维护，对外由同一个 FastAPI 进程处理请求。

需要接受的条件是：同一个 Python 进程不能分别使用两个 `.venv`。统一服务需要能够兼容两者依赖的运行环境，并统一协调启动、资源关闭和发布。

### 5.2 一个 FastAPI 转发到两个独立后端

该方案保留两个业务后端的独立运行环境，但增加一个网关或聚合服务，需要维护请求转发、超时、错误及可信身份传递。

如果只是按路径分流，反向代理通常足以完成，不必为此增加一个 FastAPI 服务。

以上两种方案均为讨论过的替代选择，尚未确认为当前实施方案。

## 7. 整合时需要保留的数据契约

两个模块没有业务 API 调用，并不意味着没有耦合。MetaWeave 写入、NL2SQL 读取的数据结构构成主要协作契约，包括：

- 数据源标识及检索范围。
- Milvus 集合、字段、向量维度等定义。
- Neo4j 节点、关系和标识规则。
- PostgreSQL 中共享知识数据的结构及含义。
- 知识发布期间和发布完成后的读取行为。

前期查看发现：MetaWeave 已有 `source_id` 管理，NL2SQL 当前查询请求尚未包含数据源参数，部分检索代码也预留了后续按 `source_id` 过滤的改造。这是后续整合需要核实和处理的内容，不是本次已经完成的工作。

## 8. 平台命名讨论

建议平台名称覆盖“数据知识整理、查询与分析”的长期定位，不限定于元数据或 SQL。

讨论中的优先候选为 **InsightWeave**，中文候选为 **知数**。

- `Insight` 表示洞察、深入理解。
- `Weave` 表示编织，不是“编制”。
- 名称寓意是将数据、关系和知识编织起来，形成洞察。
- 它延续 MetaWeave 的命名风格，但英文稍长，中文不适合逐字翻译。

候选展示方式：

> InsightWeave · 知数  
> 数据知识与智能分析平台

上述名称尚未得到用户最终确认，也未进行名称占用或商标核查。现阶段无需因此重命名两个业务模块。

## 1. 部署系统与七镜像口径

- 宿主是 Windows Docker Desktop，使用 **Linux 容器**，目标平台固定为 `linux/amd64`。
- Debian WSL2 运行 Runner、Git 和发布脚本；各容器的发行版由 Dockerfile 的 `FROM` 决定，不自动继承 WSL 的系统或已安装软件。
- 两个后端使用 **Debian 12 Bookworm + Python 3.12.16**；前端构建阶段使用 **Debian 12 Bookworm + Node.js 22**，运行阶段使用 **Debian 13 Trixie + Nginx 1.30.6**。
- 部署产物是三个自建应用镜像、三个官方数据库镜像及一个上游 Attu 镜像，共 **七种部署镜像、七个常驻容器**，统一放入同一份 Compose。Node/Python/Nginx 基础镜像是构建输入，不单独作为额外服务运行。
- 本机三个应用使用 `insightweave/frontend:<release_id>`、`insightweave/metaweave:<release_id>`、`insightweave/nl2sql:<release_id>` 标签；不推送到 GHCR 或 Docker Hub。Compose 对三个应用设置 `pull_policy: never`，使用预先构建并核对 ID 的本地镜像。

数据库使用厂商镜像原有系统和服务，不为了发行版一致而重新打包 PostgreSQL、Neo4j 或 Milvus。

用户确认：本次 Docker 部署开发和测试前，会预先停止原有 Neo4j、Milvus 及其 Attu 管理容器，以及原有 Vue 前端和两个后端服务，不与新 Compose 同时运行，避免这些原有服务造成端口冲突；由用户停止原服务，部署脚本仍执行端口占用预检。

**端口映射以 [doc 13 §4 的清单](13_项目Docker容器化与本地CI_CD发布设计.md) 为准：**仅发布 `127.0.0.1:18080:80`（frontend）、`127.0.0.1:3000:3000`（Attu）、`127.0.0.1:7474:7474` 和 `127.0.0.1:7687:7687`（Neo4j）、`127.0.0.1:6432:5432`（PG）。本机客户端通过 `127.0.0.1:6432` 访问 PG；容器内应用仍连接 `postgres:5432`，`PLATFORM_DB_PORT`、`LANGGRAPH_DB_PORT` 均为 5432，不沿用宿主映射端口。其余服务端口不发布，尤其不映射 Milvus `19530/9091` 和内嵌 etcd `2379`；Attu 通过 Compose 内部地址 `milvus:19530` 访问数据。Docker 内部端口与开发服务端口、宿主端口是不同约定，不因宿主 80 已占用就修改 Nginx 内部 80。

**外部业务库 Host:Port 保持原值。**独立 Docker 环境文件仅调整内部基础服务：`PLATFORM_DB_HOST=postgres`、`PLATFORM_DB_PORT=5432`、`PLATFORM_DB_NAME=metaweave`；`LANGGRAPH_DB_HOST=postgres`、`LANGGRAPH_DB_PORT=5432`、`LANGGRAPH_DB_NAME=lg_persist`；`MILVUS_HOST=milvus`、`MILVUS_PORT=19530`、`MILVUS_DATABASE=nl2sql`；`NEO4J_URI=bolt://neo4j:7687`、`NEO4J_DATABASE=neo4j`。双方内部服务凭据与 Compose 配置一致。原业务库 `DB_HOST`/`DB_PORT`、已登记源地址及本地开发 `.env` 不随之改写；完整分界表见 doc 13 §5.2。原地址若是回环地址而在容器内不可达，按 doc 13 §4 报告并人工处理，不自动替换地址。

### 1.1 访问 GitHub、镜像仓库和依赖源的本机代理

本机 Windows 已有代理服务。coding AI 遇到 GitHub、Docker Hub、PyPI、npm 或 Debian 软件源连接失败时，先检查并配置对应执行环境的代理，不需要增加代理容器。**本次验证记录：端口 7890，WSL 代理 `http://172.29.128.1:7890`。这是当前本机实值，不是稳定部署常量。**具体区别：

| 发起请求的位置 | 使用的代理地址/配置位置 | 验证边界 |
| --- | --- | --- |
| WSL 中的 Git、curl、Runner、uv/npm | `http://172.29.128.1:7890` | 已按当前默认网关解析，之前通过该 HTTP 代理访问 GitHub 返回 200 |
| Windows Docker Desktop 拉取镜像 | 在 Docker Desktop 的 Proxies 设置中选择已有系统代理，或配置 Windows 本机代理 `http://127.0.0.1:7890` | Windows 侧配置地址；实际选项及拉取结果须核对，不以 WSL 的 curl 成功代替 |
| Dockerfile RUN 内的 apt/pip/uv/npm | `http://host.docker.internal:7890`，通过构建代理参数传入 | 已在本机 `default` builder 验证下载和 HTTPS 访问，见 §8.2；环境变化后重新验证 |

`172.29.128.1` 是当前 WSL 默认网关，来自实际解析，不是要求开发者自行猜测的占位地址。WSL 网络重建后若变化，再更新本机配置。容器内的 `127.0.0.1` 指该容器，不能拿它访问 Windows 上的代理。HTTPS 请求也使用上述 `http://` 代理 URL，由代理转发 HTTPS 连接。

该 IP/端口是用户要求保留的本机验证记录，不是凭据。将来仓库转公开前复核是否将机器网络信息替换为通用示例；真实部署配置及凭据仍不入 Git。

本机配置使用两个独立输入，`ci.sh`/Runner 启动环境读取它们，不在受 Git 管理的脚本中硬编码 IP：

| 变量 | 配置位置和语义 |
| --- | --- |
| `INSIGHTWEAVE_WSL_PROXY_URL` | 不受 Git 管理的本机环境；当前可填 `http://172.29.128.1:7890` |
| `INSIGHTWEAVE_BUILD_PROXY_URL` | 不受 Git 管理的本机环境；本次 builder 已验证 `http://host.docker.internal:7890`，配置值仍由本机提供 |

`deploy/env/deploy.env.example` 的代理变量只声明变量名和空值，不保存当前网关作为默认值。未配置时明确按直连验证，在相关子进程中避免沿用其他继承代理却误报“直连”；一旦配置就检查 URL 和对应网络可达性，失效时报告该网络阶段失败，不静默猜网关、换地址或修改系统代理。日志只输出启用状态和脱敏主机/端口，不打印带认证信息的完整 URL。

启用 WSL 代理时，先由本机配置提供 `INSIGHTWEAVE_WSL_PROXY_URL`，再导出标准变量：

```bash
: "${INSIGHTWEAVE_WSL_PROXY_URL:?请先配置本机 WSL 代理 URL}"
export http_proxy="$INSIGHTWEAVE_WSL_PROXY_URL"
export https_proxy="$INSIGHTWEAVE_WSL_PROXY_URL"
export HTTP_PROXY="$http_proxy"
export HTTPS_PROXY="$https_proxy"
export no_proxy="localhost,127.0.0.1,::1,postgres,neo4j,milvus,metaweave,nl2sql,attu,host.docker.internal"
export NO_PROXY="$no_proxy"
```

Runner 必须在注册/启动前获得代理环境；服务方式的实际配置和重启步骤见 [doc 13 §4.2](13_项目Docker容器化与本地CI_CD发布设计.md#runner-proxy)。不能只设置项目自定义变量而不提供 Runner 识别的标准代理变量。本地 API/数据库访问及发布冒烟应绕过代理。

### 1.2 镜像拉取代理与构建下载代理分别处理

**拉取镜像、解析 FROM：**由 Docker Desktop/实际 builder 所在环境访问 Registry。WSL 中 export 成功不代表 Docker Desktop 自动继承；`docker pull` 失败时，检查 Docker Desktop Settings 中的 Proxies（不同版本可能位于 Resources 下），确认用于镜像拉取的代理选项。现有拉取正常时保留当前配置，不为了补文档主动重启 Docker Desktop。不要把 `~/.docker/config.json` 的容器代理项当成 Docker Desktop 拉取代理设置。依据：[Docker Desktop 代理设置](https://docs.docker.com/desktop/settings-and-maintenance/settings/#proxies)、[Docker CLI 代理适用范围](https://docs.docker.com/engine/cli/proxy/)。

实施阶段按 §2 的固定引用拉取，例如：

```bash
docker --context default pull --platform linux/amd64 docker.io/library/postgres:18.1@sha256:1090bc3a8ccfb0b55f78a494d76f8d603434f7e4553543d6e807bc7bd6bbd17f
```

**镜像构建中的下载：**基础镜像已经可取得，但 `RUN apt-get`、pip/uv 或 npm 下载失败时，单独配置构建代理。由 `ci.sh` 使用已验证的容器侧代理地址传入 Docker 预定义代理参数；不把代理写成 Dockerfile `ENV`，不烘焙进运行镜像。以下是 Dockerfile、release_id 和容器侧代理均已准备后的调用示意：

```bash
: "${INSIGHTWEAVE_BUILD_PROXY_URL:?请先配置已验证的构建代理 URL}"
build_proxy_url="$INSIGHTWEAVE_BUILD_PROXY_URL"
docker --context default buildx build --builder default --platform linux/amd64 --load \
  --build-arg HTTP_PROXY="$build_proxy_url" \
  --build-arg HTTPS_PROXY="$build_proxy_url" \
  --build-arg NO_PROXY="localhost,127.0.0.1,::1,postgres,neo4j,milvus,metaweave,nl2sql,attu,host.docker.internal" \
  -f nl2sql/Dockerfile -t "insightweave/nl2sql:$release_id" .
```

其他两个应用复用同一传参规则。Docker 的这些代理参数无需在 Dockerfile 额外声明 `ARG`；不要通过 RUN 打印代理环境或把它改写进配置文件。`--build-arg` 用于 RUN 下载，不能解决更早的 FROM 拉取失败。依据：[Docker 构建代理参数](https://docs.docker.com/build/building/variables/#proxy-arguments)。

### 1.3 coding AI 的验证顺序

1. 在 WSL 验证本机配置的 `INSIGHTWEAVE_WSL_PROXY_URL` 和 GitHub/依赖源访问；记录中的 `172.29.128.1:7890` 失效时，由维护者更新本机配置，不自动固化或猜测新值。
2. 用固定引用验证 Docker 实际拉取；Registry 元数据能读取不代表镜像层一定下载完整。
3. 在实际 builder 中验证容器侧代理及 apt/uv/npm 下载，再构建完整应用；不能用 WSL 的测试替代。
4. 启动后的七个服务不使用代理；按 §1.4 单独验证两个后端的 LLM/Embedding 和外部数据源直连；APOC 按 §2.2 在启动前离线准备。本机已有代理不增加部署镜像或容器数量。

上述正式部署命令仍是实施示例；§8.2 已执行独立的临时构建验证，没有修改 Docker Desktop 或系统代理配置。

### 1.4 运行期网络检查清单

离线测试、镜像构建及健康接口成功，不代表模型 API 可访问。任务 3/4 在实际运行容器中，对当前启用的 profile/endpoint 做下列检查，不只验证 GitHub：

| 运行容器/目标 | 要检查什么 | 是否使用 HTTP 代理 |
| --- | --- | --- |
| MetaWeave → 实际 LLM、Embedding endpoint | 按运行配置解析真实主机/端口，验证 DNS、TCP、TLS 和供应商支持的只读元数据接口 | 直连，不设置运行期代理 |
| NL2SQL → 主模型、摘要/时间解析等启用的 LLM，以及 Embedding endpoint | 对启用的实际 endpoint 验证；相同主机可合并网络检查，不把构建下载成功当作模型接线成功 | 直连，使用实际 SDK 验证，不能仅测容器 curl |
| Neo4j → 本地 APOC 插件 | 按 §2.2 在启动前准备并校验 `/plugins/apoc.jar`；运行时加载已有文件 | 不下载、不配置代理；部署准备所需的外部文件下载由 Runner 完成 |
| 两个后端 → 内部 PG、Neo4j、Milvus/API | 使用 Compose 服务名和内部端口连接 | 直连，HTTP 客户端的 `NO_PROXY/no_proxy` 保留内部服务名 |
| 后端 → 外部受控测试 PostgreSQL | 按 doc 13 §9.3 验证容器路由、VPN 可达性、目标 TCP 端口及数据库驱动握手 | PostgreSQL 使用数据库协议直连，`HTTP_PROXY` 不会替它转发 PostgreSQL TCP |

**用户确认的运行约束：七个服务运行时均不使用代理。**代理只用于 Runner 访问 GitHub、镜像拉取、确有需要的构建下载及部署准备阶段的外部插件文件下载；优先从固定镜像提取内置 APOC，见 §2.2，不增加“Neo4j 首次带代理启动”的例外。代理不写入运行镜像或后端 env 文件。Compose 应显式将 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY` 及其小写形式设为空字符串，覆盖 Docker CLI 可能自动注入的容器代理配置；仅仅“不写代理项”不一定能避免继承。验收时确认运行容器这些变量均无有效值，并通过实际 SDK 检查直连。

MetaWeave 和 NL2SQL 各有一个独立的 Python 依赖环境，对应各自应用镜像，不是两套生产部署。两个生产依赖集合均未安装 `socksio`；当前无 SOCKS 运行需求，不增加该包。Runner 测试子进程若继承宿主的 SOCKS 环境，按 §5.4 移除相关变量，不修改用户全局代理。

验证优先使用供应商支持的非计费接口，不自动发起付费问数/生成/Embedding 请求。若没有这样的接口，记录已验证的网络层和未验证的认证/功能边界：TLS 成功或收到 401/403/404 只能说明相应连接阶段可达，不能报告模型调用已成功。对实际需要的运行期访问仍未通过时，交付记录不得宣称业务链路已验收。这里只补网络检查，不新增探测服务或模型调用流程。

### 2.2 APOC 离线准备、首次启动与重启

**采用“启动前准备插件，服务整个生命周期无代理”的方式。**不能把 `NEO4J_PLUGINS` 等同于“首次下载一次”：已实际拉取并核对 §2 固定 digest 的 `neo4j:5.26.19-community`，其 `/startup/neo4j-plugins.json` 指向 `/var/lib/neo4j/labs/apoc-*-core.jar`，入口脚本优先复制镜像内文件；找不到本地文件时才进入网络下载分支。入口每次启动都会处理该变量，不能只凭 `/plugins` 已持久化就保证不再安装/下载。该镜像已经内置 `apoc-5.26.19-core.jar`，本次不需要额外在线下载 APOC。

实施顺序与边界：

1. **任务 1 核对固定镜像的实际内容。**使用 §2 的 `NEO4J_IMAGE` 完整 digest 引用，检查 `/var/lib/neo4j/labs/` 中是否存在唯一匹配的 APOC Core JAR，记录文件名、版本和 SHA256。已有本机标签的检查不能替代所选 digest；发现镜像没有 JAR 时明确停止，不让 Neo4j 启动脚本自行联网补齐。
2. **首次 bootstrap 在启动 Neo4j 之前准备 `/plugins` 卷。**用同一个官方镜像启动短时 `--rm --network none --entrypoint sh` 容器，只挂载目标插件卷，不挂载 `/data`，不启动 Neo4j 服务。将已核对的内置 JAR 复制为 `/plugins/apoc.jar`，设为 Neo4j 用户可读并核对 SHA256；不增加镜像种类或常驻容器。重入时已有文件同 SHA 则直接通过，不覆盖未知文件或保留多个 APOC 版本。
3. **正式 Compose 挂载已准备的 `/plugins` 卷，显式设置 `NEO4J_PLUGINS: ""`。**同时清空六个代理变量，按当前镜像配置 `NEO4J_dbms_security_procedures_unrestricted: "apoc.*"`，补上原自动插件安装逻辑曾代设的必要配置。没有准备好 JAR 或校验失败就在启动前报错，不自动回退到在线安装。
4. **运行验收及重启。**首次启动验证 APOC 版本及应用需要的过程；以相同配置重启，再确认 JAR 的 SHA 不变、APOC 可用、代理变量为空。后续应用 release/rollback 不重新准备或升级该数据库插件，复用已有卷；Neo4j/插件版本升级仍是独立显式操作。
5. **仅在固定镜像确实缺少所需插件时讨论外部下载。**优先核实本项目是否需要它；确需下载时，由 Runner 在部署准备阶段通过本机代理取得与固定 Neo4j 版本匹配的官方 JAR，固定版本和校验值后再放入同一卷。插件缺失不自动扩大为 APOC Extended 等新依赖，也不让常驻 Neo4j 临时带代理启动。

自动化沿用现有计划中的 `deploy/scripts/deploy.sh`，增加局部函数 `prepare_neo4j_plugin()`：只在 bootstrap 需要首次启动 Neo4j 时调用；运行中的既有 Neo4j 只读核验插件，不写其插件卷。任务 4 之前的任务 1/3 可使用等价手工 Docker 命令验证，无需提前依赖尚未实现的发布脚本。`deploy/scripts/smoke.py --scope infra` 检查实际 APOC 能力，`deploy/tests/test_deployment_contract.py` 断言正式 Compose 未启用自动插件安装、运行代理已清空。

### 5.3 uv 和生产安装命令

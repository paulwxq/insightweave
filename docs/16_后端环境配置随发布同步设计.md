# 后端环境配置随发布同步设计

## 1. 目标与现状

本设计适用于项目开发阶段的本机 Docker 部署。

每次发布，Runner 都读取本机开发工作区中最新的 `metaweave/.env` 和 `nl2sql/.env`，叠加 Docker 部署专用配置，生成本次发布使用的两份后端环境文件。发布成功后，正式文件分别位于 `/home/iw-runner/insightweave-runtime/config/metaweave.env` 和 `/home/iw-runner/insightweave-runtime/config/nl2sql.env`。

目前 Compose 已通过 `METAWEAVE_ENV_FILE` 和 `NL2SQL_ENV_FILE` 向容器注入宿主机配置。私有发布仓从公开仓检出固定源码，执行离线测试、镜像构建、预检和部署。这条链路目前缺少从本机开发文件生成部署配置的一步。 [部署入口设计](15_公开项目与私有部署仓库联动及CI_CD改造方案.md) · [Compose 配置](../deploy/compose.yaml)

每次开发环境发布都在镜像构建前同步，配置在 Compose 创建后端容器时生效。实值文件保存在宿主机的受限目录。构建以干净 Git 检出为上下文，公开 CI 使用测试哑值，Docker 镜像排除 `.env`。 [部署手册](../deploy/README.md) · [Docker 构建排除规则](../.dockerignore)

## 2. 配置来源和覆盖顺序

下表用 `$DEV_ROOT` 表示开发工作区绝对路径，由维护者在本机 Runner 上一次性配置 `INSIGHTWEAVE_DEV_PROJECT_ROOT`，当前应指向 `/opt/projects/insightweave`。`$DEPLOY_ROOT` 沿用现有部署根目录，本机为 `/home/iw-runner/insightweave-runtime`。每次发布开始时分别读取两份源文件一次，本次发布全程使用这次生成的结果。

| 服务 | 开发输入 | Docker 专用覆盖 | 正式生成文件 |
| --- | --- | --- | --- |
| MetaWeave | `$DEV_ROOT/metaweave/.env` | `$DEPLOY_ROOT/config/overrides/metaweave.env` | `$DEPLOY_ROOT/config/metaweave.env` |
| NL2SQL | `$DEV_ROOT/nl2sql/.env` | `$DEPLOY_ROOT/config/overrides/nl2sql.env` | `$DEPLOY_ROOT/config/nl2sql.env` |

每次都从开发输入重建完整配置。同一份开发 `.env` 或 Docker 覆盖文件里有多次赋值时，以文件中最后一次赋值为准，`KEY=` 也可覆盖前面的值。再合并两份文件，Docker 覆盖文件的同名变量优先。开发文件里删除的变量会从下一份生成文件移除，覆盖文件显式定义的变量仍按覆盖值生效。

| 变量 | 维护位置 |
| --- | --- |
| LangSmith 开关、Endpoint、项目和密钥，LLM 供应商配置，以及其他普通应用变量 | 对应模块的开发 `.env` |
| 平台 PostgreSQL 和 LangGraph 持久化连接、容器内部 Neo4j 和 Milvus 连接、浏览器访问的 CORS 和 Host 设置 | 对应服务的 Docker 覆盖文件，按本机 Docker 的服务地址和凭据配置 |
| `SOURCE_CREDENTIAL_KEY` | 两个服务的 Docker 覆盖文件使用同一密钥。保留已有数据时，密钥必须与平台注册的数据源加密凭据匹配 |
| `DEPLOY_CONTROL_TOKEN`、`DEPLOY_CONTROL_ENABLED` | Docker 覆盖文件。按开发部署的控制接口要求设置 |
| `NL2SQL_LOG_LEVEL` | 在开发 `nl2sql/.env` 设置。日常发布使用 `INFO`，排障时设为 `DEBUG` |
| `DB_*` 等已配置的外部业务库连接 | 默认沿用开发文件。若某个部署环境使用不同的业务库，只把确认有差异的字段列入对应覆盖文件 |

覆盖文件只填写由 Docker 部署管理的变量。`deploy.env` 中的两个 `*_ENV_FILE` 分别指向表中的正式生成文件。覆盖文件、候选文件和正式生成文件由 `iw-runner` 持有，文件权限 `0600`，私有目录权限 `0700`。两份开发 `.env` 的访问范围限于维护者和 Runner，例如使用 `0640` 配合受控组，或设置仅供 `iw-runner` 读取的 ACL。以 `iw-runner` 身份确认两份开发文件可读。

## 3. 发布顺序与失败处理

### 3.1 只改配置时的发布入口

修改开发 `.env` 或 Docker 覆盖文件后，经维护者授权，完整重跑对应的私有部署运行。当前 `main` 对应的来源 CI 的**最新 attempt 必须已完成且成功**，且私有运行必须绑定这个 attempt。若最新 attempt 失败或仍在执行，先处理或等待来源 CI。待最新 attempt 成功，再使用绑定该 attempt 的私有运行。要求选定的私有运行已结束、现场为 `ready`、没有未决发布，且运行使用实现本方案的控制提交。仅需配置更新时，可对已成功的私有部署完整重跑。

```bash
gh run rerun <PRIVATE_RUN_ID> --repo paulwxq/insightweave-deploy
```

完整重跑使用新的私有 run attempt，按现有规则生成新的 `release_id`，重新读取两份开发 `.env`，并执行完整的来源核验和发布流程。受控手动发布同样使用新 ID 和本次生成的候选配置。请求应用新配置时若复用当前 ID，直接报配置错误。 [发布追踪与重跑](../deploy/README.md#追踪重试与暂停)

### 3.2 候选配置到正式配置

日常 `release` 以使用 `format: raw` 的 Compose 快照作为 `current` 基线。发布前核对当前快照和候选快照中两个后端的 `env_file` 格式，任一快照未使用 raw 时在预检报错。`bootstrap` 登记基线之前做同样的核对：它登记的快照就是此后发布的 `current`。

1. **来源核验后、镜像构建前生成候选配置。** 私有发布入口在首次 `recheck` 和源码 SHA 校验通过后执行同步程序。程序同时读入两份开发文件和各自的 Docker 覆盖文件，完成合并和格式校验后，把两份文件写入本次 `release_id` 对应的 `$DEPLOY_ROOT/config/.pending/` 子目录。用临时目录完成两份写入后再发布为完整的候选目录。文件缺失、无法读取、解析失败或无法安全写入 raw 文件的值都在这一步报告。
2. **按现有流程构建并重新核验来源。** `ci.sh` 继续执行离线检查、三镜像构建和隔离预检。私有发布入口在部署前复核来源后，仅将候选配置目录的路径交给 `deploy.sh release`。每次完整重跑生成独立的候选目录，并重新读取当时的两份开发文件。
3. **用候选配置预检和创建容器。** `deploy.sh release` 取得现有部署锁，核对候选目录归属本次发布且包含两份受限文件。目标配置预检、创建候选容器和验收时，把 Compose 的 `METAWEAVE_ENV_FILE` 和 `NL2SQL_ENV_FILE` 指向候选文件。排空旧容器使用正式配置。依赖预检、排空、健康检查和两阶段冒烟沿用现有入口。目标配置预检在写入 `deploying` 和维护标记前完成。
4. **验收通过后更新正式配置。** 在同一把部署锁内，把上一组正式文件完整写入 `$DEPLOY_ROOT/config/.pending/<release_id>/previous/`，确认备份落盘后，在 `state/deployment.json` 以 `pending_config_release_id` 记录本次 ID。登记成功后逐个原子替换两份正式文件。两份文件均更新成功后，将新 `current`、`ready` 及清除待恢复 ID 写入同一次状态更新，然后清理临时目录。待恢复信息只记录 ID，配置值留在受限文件内。

**配置变更日志。** 在替换正式文件前，按服务比较已经合并 Docker 覆盖的候选 env 和当前正式 env。新发布写入 `ready` 后，在现有发布日志中为两个服务各记一行，只包含服务名和新增、修改、删除的变量名。两份配置相同时记录「无变化」。

### 3.3 本次发布失败恢复

所有恢复分支共用 `use_formal_app_config()`，在执行恢复预检、排空或调用 Compose 前，先清除候选路径覆盖，将 `METAWEAVE_ENV_FILE` 和 `NL2SQL_ENV_FILE` 切回两份正式文件。有待恢复 ID 时，先从登记的备份恢复整组正式文件，再运行恢复操作。异常收尾如需调用容器控制接口，也使用正式路径。恢复完成后在实际容器中核对生效值。

| 失败时机 | 处理 |
| --- | --- |
| 同步、构建、部署前复核或预检失败 | 结束本次发布并清理候选配置，运行中的开发容器继续使用原版本和正式 env |
| 容器切换或冒烟失败 | 恢复分支使用正式 env 路径，按现有流程恢复原版本。原版本镜像身份和冒烟核验通过后写回 `ready` 并清理候选目录 |
| 更新正式配置时发生可处理的错误 | 从登记的备份恢复两份正式文件，再走原版本自动恢复分支。应用核验通过后写回 `ready`，清除待恢复 ID 并清理备份 |
| 进程被强制终止或自动恢复失败 | 保留备份及待恢复 ID，继续以 `deploying` 或 `recovery_required` 处理。进程强制终止时以实际容器与入口状态为准 |

人工恢复沿用 `deploy.sh rollback <current_release_id>`。该入口在现有部署锁内读取 `pending_config_release_id`，核对并从上述目录恢复完整的两份正式文件，再按现有流程恢复 `current`。如果备份缺失、配置恢复失败或应用核验失败，保留未就绪状态和可用备份，供人工核验。配置恢复后到应用验收通过前，继续使用未就绪状态。只有成功发布或成功恢复后才清理备份。私有入口的退出清理也须保留状态仍引用的目录。

`rollback` 在替换容器前核对所选 Compose 快照中的两个后端均使用 `format: raw`，保证回退时按字面值读取正式 env。

临时备份仅用于本次发布失败恢复。正常的配置调整修改开发 `.env` 或覆盖文件后按 §3.1 重新发布。

**解析器与 Runner 准备。** 同步工具独立固定 `python-dotenv==1.2.4`。两个应用各自按其 `uv.lock` 构建。Runner 通过 `INSIGHTWEAVE_ENV_SYNC_PYTHON` 指定同步步骤的解释器绝对路径，本机可使用 `/home/iw-runner/.venv-smoke/bin/python`。准备 Runner 时在该解释器对应的环境一次性安装依赖。构建前以 `iw-runner` 身份检查指定解释器可执行，并验证 `dotenv` 导入及版本。来源核验、状态读写、清单和冒烟各自沿用现有的 `PYTHON_BIN` 选择。 [NL2SQL 依赖锁](../nl2sql/uv.lock) · [MetaWeave 依赖锁](../metaweave/uv.lock)

**读取源文件。** 两份开发 `.env` 和覆盖文件沿用 dotenv 写法。使用 `dotenv.parser.parse_stream()` 读取，跳过空行和注释。发现 `Binding.error` 或无 `=` 的裸键时终止发布。`KEY=` 表示显式空值。读取时采用无插值语义，`$` 和 `${NAME}` 保留字面值。

**生成和注入。** 生成文件每行写一个 `KEY=value`，其中 `value` 使用解析后的字面值。Compose 使用 `env_file` 的 `format: raw` 读取生成文件，确保 `$`、`${NAME}`、引号和反斜杠按字面传入容器。首版支持单行值。同步程序在生成候选文件前校验实际换行、回车或 NUL，发现后立即报错并在调用 `ci.sh` 前停止。报错只包含文件、行号、变量名和原因。

`env_file` 的 `format: raw` 要求 Docker Compose v2.30.0 或以上。 [Docker Compose 规范](https://docs.docker.com/reference/compose-file/container-spec/#format)

**读取生成文件。** 变更日志、控制令牌和数据源加密密钥的比较使用同一套 raw 规则读取候选 env 和正式 env。每行按第一个 `=` 分隔，等号之后直到行末的字符都属于值，保留首尾空格、`#` 和引号。`python-dotenv` 用于读取开发 `.env` 和 Docker 覆盖文件。

**状态写入。** `state_write()` 在已有部署锁下原子更新，默认保留 `pending_config_release_id`。`on_exit` 写入 `recovery_required` 时也携带该字段。成功发布、成功恢复，或维护者核验后明确确认备份已无恢复用途时，才可显式清除。私有入口清理对应目录前须确认发布操作已经结束，且状态已无该 ID 的引用。状态读取失败时保留该目录。

**控制令牌。** 首次准备开发栈时以 Docker 覆盖文件中的控制令牌为准。日常发布由 `deploy.sh` 在持锁期间、目标配置预检前比较两个候选服务各自的 `DEPLOY_CONTROL_TOKEN` 与对应正式值。有任何差异时在切换前拒绝发布，以满足旧容器排空和现有 `apps_smoke` 的要求。令牌轮换属于单独的维护操作。

**数据源加密密钥。** 日常发布复用控制令牌的比较逻辑，持锁检查两个候选服务的 `SOURCE_CREDENTIAL_KEY` 与对应正式值完全一致。保留原卷重新初始化时，用已有容器实际注入的原正式值核对候选，避免把手写 dotenv 的引号当成密钥字符。发现差异或无法确认原密钥时，在变更正式文件或状态前停止。两个服务使用同一密钥，密钥轮换属于单独的维护操作。`bootstrap` 与 `release` 在变更前还要求两个候选服务的密钥非空且彼此相同。核对时只记录结果。 [数据源密码加解密](../metaweave/backend/security/source_password.py)

**部署配置校验。** 同步程序负责文件读取和 env 格式校验。应用配置交给现有 `deploy/scripts/release_manifest.py` 的 `TARGET_CONFIG_CHECKS`，由目标镜像加载各自的应用配置并检查控制开关和令牌。LangSmith 变量按普通应用配置同步，生效状态由各自镜像里的 SDK 判定。捕获并过滤可能携带配置值的 Compose 输出。

两个仓库作为同一次开发改动实施。按 §2 设置 `INSIGHTWEAVE_DEV_PROJECT_ROOT` 和覆盖文件，并准备 Runner 依赖。工作区路径和候选目录都是发布必填项，缺失或无效时报错。 [部署入口与控制提交](15_公开项目与私有部署仓库联动及CI_CD改造方案.md)

**首次初始化与自动发布的衔接。** 先按 [Doc 15 §8.5](15_公开项目与私有部署仓库联动及CI_CD改造方案.md#85-维护者的简短操作程序) 暂停自动发布并等未决任务结束，再让两个仓库就绪：公开仓 `main` 含本方案的实现，私有仓 `main` 含新的 `release_local.sh`，Runner 按私有仓 README 配好 `INSIGHTWEAVE_DEV_PROJECT_ROOT`、`INSIGHTWEAVE_ENV_SYNC_PYTHON`。然后用已核验的新版源码按 §4.1 完成 `bootstrap` 和凭据验收，验收通过后再恢复通知。暂停期间没有发出部署请求时，恢复通知后按 Doc 15 §8.5 完整重跑当前 `main` 的来源 CI，由新的成功事件创建绑定新控制提交的私有发布；不要重跑旧的私有部署运行，它仍使用原控制提交（Doc 15 §7.2）。此后的日常发布按 §3.1 进行。

### 4.1 初始化开发栈

初始化沿用 Doc 13 §6 的 `bootstrap` 入口。经维护者授权暂停自动发布，等待未决发布结束，再以 `iw-runner` 身份在同一个 Bash 运维终端执行各步。将 `SOURCE_DIR` 设为已核验且实现本方案的干净源码检出绝对路径。`RELEASE_ID` 必须唯一，符合 `[A-Za-z0-9][A-Za-z0-9_.-]*`，以英文字母或数字开头。`PROJECT` 取该开发栈的 Compose 项目名，本机为 `insightweave-local`。本机运维说明中的手动构建步骤可用于准备检出和构建环境。 [Doc 13 §6 首次部署和初始化](13_项目Docker容器化与本地CI_CD发布设计.md#6-首次部署和初始化)

1. **准备本次候选 env、镜像和清单。** 使用与日常发布相同的生成程序，核对两个后端使用同一把数据源加密密钥，再从同一检出构建镜像。新开发栈和已有开发栈都要执行这一步的核对；`deploy.sh bootstrap` 在任何变更之前还会对两份正式 env 做同样的核对。

   ```bash
   set -euo pipefail
   "$INSIGHTWEAVE_ENV_SYNC_PYTHON" "$SOURCE_DIR/deploy/scripts/prepare_app_env.py" \
     --dev-root "$INSIGHTWEAVE_DEV_PROJECT_ROOT" --deploy-root "$DEPLOY_ROOT" \
     --release-id "$RELEASE_ID"
   CANDIDATE_DIR="$DEPLOY_ROOT/config/.pending/$RELEASE_ID"
   CANDIDATE_MANIFEST="$SOURCE_DIR/deploy/candidate-$RELEASE_ID.json"
   test -s "$CANDIDATE_DIR/metaweave.env"
   test -s "$CANDIDATE_DIR/nl2sql.env"
   # 两个后端必须使用同一把数据源加密密钥（§2）；关闭命令追踪，不把密钥写进终端记录
   (
     set +x
     candidate=$(sed -n 's/^SOURCE_CREDENTIAL_KEY=//p' "$CANDIDATE_DIR/metaweave.env")
     nl2sql_candidate=$(sed -n 's/^SOURCE_CREDENTIAL_KEY=//p' "$CANDIDATE_DIR/nl2sql.env")
     if [ -z "$candidate" ] || [ "$candidate" != "$nl2sql_candidate" ]; then
       printf '%s\n' '候选 SOURCE_CREDENTIAL_KEY 缺失或两个服务的值不一致' >&2
       exit 1
     fi
   )
   (cd "$SOURCE_DIR" && MANIFEST_OUT="$CANDIDATE_MANIFEST" bash deploy/scripts/ci.sh "$RELEASE_ID")
   ```

2. **准备空状态。** 新开发栈直接进入下一步。若已有开发栈，先确认现场 `ready` 且无待恢复配置。在同一维护终端持有 `state/.lock`，按手册设置指向当前快照的 `DC` 命令数组，在写维护标记前执行下列与旧容器的比对。比对时关闭命令追踪，只输出匹配结果。 [进入维护并排空](../deploy/README.md#1-固定操作对象并进入维护)

   ```bash
   (
     set +x
     candidate=$(sed -n 's/^SOURCE_CREDENTIAL_KEY=//p' "$CANDIDATE_DIR/metaweave.env")
     for service in metaweave nl2sql; do
       if ! current=$("${DC[@]}" exec -T "$service" sh -c 'printf "%s" "${SOURCE_CREDENTIAL_KEY-}"' 2>/dev/null); then
         printf '%s\n' "$service: 无法核对当前 SOURCE_CREDENTIAL_KEY" >&2
         exit 1
       fi
       if [ "$current" != "$candidate" ]; then
         printf '%s\n' "$service: SOURCE_CREDENTIAL_KEY 不一致" >&2
         exit 1
       fi
       printf '%s\n' "$service: SOURCE_CREDENTIAL_KEY 一致"
     done
   )
   ```

   比对通过后，按现有维护步骤关闭入口并等待排空。用 `"${DC[@]}" stop frontend metaweave nl2sql attu` 停止三个应用容器和 Attu，保留 Compose 项目名和所有数据卷。仍在持锁的维护终端执行以下命令，把两份原正式 env 与 `state/deployment.json` 归档到同一受限目录。移动原状态文件后，`bootstrap` 读取到空部署状态。

   ```bash
   BACKUP_DIR=$(mktemp -d "$DEPLOY_ROOT/state/.before-bootstrap.XXXXXX")
   install -m 0600 "$DEPLOY_ROOT/config/metaweave.env" "$BACKUP_DIR/metaweave.env"
   install -m 0600 "$DEPLOY_ROOT/config/nl2sql.env" "$BACKUP_DIR/nl2sql.env"
   mv -- "$DEPLOY_ROOT/state/deployment.json" "$BACKUP_DIR/deployment.json"
   ```

3. **安装正式 env 并初始化。** 将候选文件安装到正式路径。已有部署在持锁的维护终端完成文件安装，再释放外层锁，由 `deploy.sh bootstrap` 自行取锁。整个过程保留维护状态，任一步失败即停止并保留备份。

   ```bash
   install -m 0600 "$CANDIDATE_DIR/metaweave.env" "$DEPLOY_ROOT/config/metaweave.env"
   install -m 0600 "$CANDIDATE_DIR/nl2sql.env" "$DEPLOY_ROOT/config/nl2sql.env"
   ```

   已有部署用 `flock -u 9` 释放维护终端持有的外层锁。然后执行。

   ```bash
   DEPLOY_ROOT="$DEPLOY_ROOT" ENV_FILE="$DEPLOY_ROOT/deploy.env" PROJECT="$PROJECT" \
     PYTHON_BIN=/home/iw-runner/.venv-smoke/bin/python \
     CANDIDATE_MANIFEST="$CANDIDATE_MANIFEST" \
     bash "$SOURCE_DIR/deploy/scripts/deploy.sh" bootstrap "$RELEASE_ID"
   ```

   `bootstrap` 使用原数据卷，并按现有契约执行幂等初始化。完整且符合契约的对象继续使用。允许创建的缺失对象按 Doc 13 §6 的规则处理，结构冲突则停止供维护者核验。初始化成功后，核对 `phase=ready`、`current` 指向使用 raw 的首个快照、`previous` 为空，以及两份正式 env 已注入。保留了已有加密凭据时，执行下列一次性只读检查。它从当前快照选中 MetaWeave 容器，查询平台库的一条密文并调用现有解密函数，退出码表示结果。 [平台库会话](../metaweave/backend/persistence/platform_db.py)

   ```bash
   CHECK_RELEASE_ID=$(/home/iw-runner/.venv-smoke/bin/python -c \
     'import json,sys; print(json.load(open(sys.argv[1]))["current"])' \
     "$DEPLOY_ROOT/state/deployment.json")
   CHECK_COMPOSE_DIR="$DEPLOY_ROOT/releases/$CHECK_RELEASE_ID"
   docker --context default compose --project-name "$PROJECT" \
     --project-directory "$CHECK_COMPOSE_DIR" -f "$CHECK_COMPOSE_DIR/compose.yaml" \
     --env-file "$DEPLOY_ROOT/deploy.env" exec -T metaweave python - <<'PY'
   try:
       from sqlalchemy import text
       from backend.persistence.platform_db import load_platform_settings_from_env, platform_session
       from backend.security.source_password import decrypt_password

       with platform_session(load_platform_settings_from_env()) as session:
           session.execute(text("SET TRANSACTION READ ONLY"))
           ciphertext = session.execute(text("""
               SELECT password_ciphertext
               FROM public.db_source_info
               WHERE password_ciphertext IS NOT NULL AND password_ciphertext <> ''
               ORDER BY source_id
               LIMIT 1
               """)).scalar_one_or_none()
       if ciphertext is None:
           print("已有数据源凭据解密检查失败（无样本）")
           raise SystemExit(1)
       decrypt_password(ciphertext)
   except Exception:
       print("已有数据源凭据解密检查失败")
       raise SystemExit(1) from None
   print("已有数据源凭据解密检查通过")
   PY
   ```

   检查通过后可清理本次候选目录，经维护者确认再恢复自动发布；恢复通知与首次自动发布的先后见 §4「首次初始化与自动发布的衔接」。正式 env 成为后续受保护变量比较和变更日志的基准。

**已有开发栈初始化失败的恢复。** 保持自动发布暂停。在部署锁内核对实际容器状态。若应用入口已经开放，先重新进入维护并等待排空。确认后，从 `BACKUP_DIR` 恢复两份原正式 env 及原 `state/deployment.json`，保留备份直到验收完成。用恢复后的 `current` 确定原镜像和 Compose 快照，保留维护标记并释放外层锁，再从该版本对应的已核验运维检出执行现有 `deploy.sh rollback <原 current>`。恢复后核对镜像、实际容器配置和冒烟，再由维护者决定是否恢复自动发布。 [手动回退流程](../deploy/README.md#手动发布回退)

## 5. 验收

- **解析和合并。** 对缺失文件、非法行、裸键、`KEY=`、更新和删除键写单元测试。验证同一文件内最后一次赋值生效，包括最后赋为空值，并验证 Docker 覆盖优先且两个服务互不串用。比较解析结果与容器内的完整值，覆盖 `$`、`${NAME}`、`#`、单双引号和末尾反斜杠。设定同名 Runner 环境变量后，`${NAME}` 仍应为字面值。验证实际换行、回车和 NUL 在同步阶段报错，并在调用 `ci.sh` 前停止。
- **发布入口与安全性。** 用私有仓 `tests/test_release_local.py` 验证同步发生在来源复核之后、构建之前，并在部署前复核通过后交接候选路径。验证同步程序使用指定解释器，核验步骤使用其原有解释器，同步解释器或依赖有误时在构建前报错。覆盖最新来源 attempt 未完成、失败和私有运行仍绑定旧 attempt 时的拒绝路径。验证仅配置变更使用新的 `release_id`，申请应用候选配置时复用当前 ID 报错。用哑值验证日志和发布产物仅记录允许公开的字段。
- **配置变更日志。** 验证新增、修改、删除和无变化的记录，确认源变量改动被 Docker 覆盖后按无变化处理。用含首尾空格、`#`、引号或多个等号的 raw 值核对比较，并使用哑值确认日志仅含变量名。成功变更日志随本次发布写入 `ready` 后输出。
- **失败与恢复。** 在 `deploy/tests/test_deploy_sh.py` 验证源文件缺失、目标预检失败、令牌或数据源加密密钥不一致和候选冒烟失败。在第一份正式文件替换后、第二份替换前注入退出，验证 `on_exit` 把 `deploying` 转为 `recovery_required` 时保留待恢复 ID。另覆盖进程强制终止、状态停留在 `deploying` 时的人工恢复。恢复后核对两份正式文件、容器内的实际配置、`ready`、`current` 和容器镜像。
- **配置发布与 DEBUG 闭环。** 在隔离环境从 INFO 开始，仅改开发 `nl2sql/.env`，走 §3.1 发布至 DEBUG，再改回 INFO 后发布一次。两次均核对容器的环境变量，并在该容器中使用同一份日志配置完成初始化后，核对 `nl2sql` 的有效级别及 `nl2sql_file` handler 的级别。实际排障时按 Doc 22 在原入口复现一次，按同一个 `request_id` 和工具调用核对 `TOOL_INPUT`、对应 `TOOL_OUTPUT` 或异常堆栈，排障结束再发布恢复 INFO。 [Doc 22 日志验收](../nl2sql/docs/22_db_deepagent工具调用日志增强方案.md#14-普通发布保持-info按需临时-debug)
- **部署验收。** 核对两阶段冒烟、现场 `ready` 和 `finalize` 成功。若本次修改了 LangSmith 配置，必须在容器重建后，用对应容器里的 SDK 核对追踪状态与预期一致。追踪开启时须确认密钥已配置。验收只报告状态。
- **首次发布的回退基线。** 在隔离环境验证已有开发栈先归档原状态和 env，按同一项目名重新运行 `bootstrap` 后，原数据卷及测试记录仍可用。用 §4.1 的只读命令解密一条已有的数据源凭据。验收 `bootstrap` 成功后 `previous` 为空，第一次 `release` 后 `previous` 指向本次初始化的 raw Compose 快照。回退后核对容器中的 `$`、`#` 和开头引号按字面保留。用普通 `env_file` 的测试快照验证预检拒绝替换容器。
- **初始化失败恢复。** 在正式 env 已安装后注入 `bootstrap` 中途失败。按 §4.1 恢复备份和原版本，核对原配置、容器镜像并用同一条只读命令验证原数据源凭据。

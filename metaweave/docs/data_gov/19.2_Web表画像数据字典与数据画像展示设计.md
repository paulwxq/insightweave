# 19.2. Web 表画像数据字典与数据画像展示设计

状态：设计草案，待讨论。日期：2026-10-03。

## 1. 本稿范围

本文确定 **对象详情页在 Web UI 中展示什么、内容从何而来、各指标如何解释**，并给出承载已发布 JSON 画像的两张平台库表。页面上部为“基本信息／对象定义 SQL”两个 Tab，默认显示基本信息；中下部为“数据字典／数据画像／样例数据”三个 Tab，默认显示数据字典。上部基本信息和下部数据字典、数据画像来自已发布 JSON 画像；对象定义 SQL 与样例数据来自平台库已发布的 `table_definition.define_text`。两张字段表均直接显示完整列，不使用字段行展开或悬停隐藏详情；列多时允许横向滚动。对象可以是普通表、视图或物化视图，页面文案需说明实际对象类型。

Web UI 的具体设计请参考 `docs/data_gov/ui/数据源管理到发布/` 下的 13～17 号 HTML、PNG 原型，以及 14.1 号级联搜索栏展开态 PNG；对应关系与交互口径见 §3.7。本文说明展示内容、数据来源及必要的交互数据口径；具体布局和视觉样式以这些 UI 原型为准。

本文 §6 确定 JSON 画像的目标表结构，§7 设计 JSON 从受管作业目录发布到平台库的输入、映射与提交路径，§8 设计对象列表与详情读取 API；页面布局与视觉细节按 §3.7 所列 UI 原型实施。本文的“页面展示”指未来从平台库读取**已发布的当前画像及当前 DDL 定义**，不意味着 Web 直接读取采集工作区中的 JSON/DDL 文件，也不把采集成功等同于已发布。DDL 与 JSON 各自发布，页面不能假定二者来自同一作业。DDL 样例块只按当前 `SAMPLED_RECORDS` 格式设计和验收，不承担旧标记或旧记录结构的兼容。`md + 同名 json → Milvus table_schema` 留给 doc 19.3。

现有 [数据库画像页](../../frontend/src/views/DatabaseProfileView.vue)展示的是整库 `db` 发布数据；本稿讨论的是单个表、视图或物化视图的详情，包含已发布 `json` 画像和已发布 DDL 定义。两者的名称和数据来源应保持清楚。

## 2. 依据与 JSON 实际结构

以 2026-10-03 最新的受管作业目录为样本：

```text
output/b4a87275-7c37-4feb-bf1c-e5a8446c174f/
  b23ac4f7-c9d8-42c5-b625-bf935dfd5194/json/
```

`manifest.json` 列出 7 个 JSON 3.0 对象文件，共 23 个字段，其中 `mv_category_sales` 是物化视图。本文不以全局旧目录 `output/json/` 的文件作为当前受管格式依据。单个文件的主要节点如下：

| JSON 节点 | 含义 | 本页用途 |
| --- | --- | --- |
| `object_info` | 库、Schema、对象名、对象类型、对象注释、注释来源和总行数 | 上部“基本信息”Tab |
| `profiling` | 画像抽样方式与抽样行数 | 上部“基本信息”Tab 的抽样行数、数据画像 Tab 的抽样提醒 |
| `column_profiles` | 以字段名为键的结构、注释、语义及统计 | 两个 Tab 的字段表 |
| `table_profile` | 表分类、分类来源、物理约束、索引与候选唯一列组 | 上部“基本信息”Tab 的分类、字典的结构事实、画像的分析结果与结构参照 |
| `sample_records` | JSON 内保存的少量真实样例行 | 本版样例数据 Tab 不读取此节点；只从已发布 DDL 的 `SAMPLED_RECORDS` 注释块读取 |

代码依据为 `TableMetadata.to_dict()`、`TableProfile.to_json_dict()`、`MetadataProfiler._profile_table()`、`JsonLlmEnhancer._merge_classification_result()` 和 `MetadataDocument`。JSON v3 **没有**单独的 `object_info.total_columns` 或每列 `column_name`：字段数由 `column_profiles` 的键数计算，字段名就是其键；这两个旧字段不能作为设计前提。

### 2.1 表分类不是空值占位

`--step json` 先由规则画像生成 `table_profile.table_category`，随后按 `json_generation.table_classification.llm_enabled` 决定是否进行 LLM 增强。当前主配置将其设为 `true`；最新受管样本的 7 个对象都有分类，`classification_source` 均为 `llm`。关闭 LLM 后保留规则分类，规则无法判定时可能为 `unknown`。只有未能形成表画像等特殊情形，`table_profile` 才可能是 `null`。

有效分类值为 `fact`、`dim`、`bridge`、`unknown`。它是画像**判断**，不是数据库物理对象类型；物理类型仍取 `object_info.object_type`。LLM 分类可与规则分类不同，例如最新 `screenings` 的最终分类为 `fact`，其 `rule_based_classification` 为 `dim`。基本信息把分类与置信度合并显示，不单列分类来源；数据画像 Tab 仍直接显示判断理由与规则备份，不能把分类显示成数据库约束事实。

### 2.2 对象定义 SQL 与样例数据的已发布来源

两个新展示区域都按 `source_id`、`schema_name`、`object_name`、`define_type='ddl'` 查询平台库 `public.table_definition` 的当前行；实际字段名是 `define_type`。该四元组是主键，一行的 `define_text` 保存整份已发布 DDL 原文，`job_id`、`publish_id`、`loaded_at` 标识其发布来源。上部“对象定义 SQL”和下部“样例数据”必须从**同一行**的 `define_text` 派生，不分别读取作业目录、当前源库或 JSON 的 `sample_records`。

两个 Tab 的共同取数查询明确为：

```sql
SELECT db_name, object_type, define_text, job_id, publish_id, loaded_at
FROM public.table_definition
WHERE source_id = :source_id
  AND schema_name = :schema_name
  AND object_name = :object_name
  AND define_type = 'ddl';
```

| 展示位置 | 唯一数据来源 | 从 `define_text` 中展示的内容 |
| --- | --- | --- |
| 上部“对象定义 SQL”Tab | 上述查询命中的 `table_definition` 行 | 只移除末尾 `/* SAMPLED_RECORDS ... */` 块后的定义文本；视图或物化视图的 `/* OBJECT_METADATA ... */` 块随原文保留，不显示样例块 |
| 下部“样例数据”Tab | **同一行** `define_text` 中的 `/* SAMPLED_RECORDS ... */` 块 | 解析块内直接记录数组 `records`，以记录表格最多显示前 5 行；不显示定义 SQL |

这两个区域都**不以 JSON 文件或 JSON 画像表的 `sample_records` 为数据来源**。`source_id` 来自当前数据源，`schema_name`、`object_name` 来自当前对象身份；查询不按 `db_name` 或 `job_id` 另选一版历史 DDL，但命中行的 `db_name/object_type` 必须与当前 JSON 对象核对。若无匹配行，两个 Tab 一起进入“暂无已发布 DDL 数据”的空状态；若身份不兼容，按 §8.2 的专门状态展示。

当前 `OutputFormatter.generate_ddl()` 先生成对象定义、注释和独立索引语句，末尾按 `output.ddl_options.sample_records` 的设置附加 `/* SAMPLED_RECORDS\n{...}\n*/`。块内 JSON 固定使用 `object_type`、`object_name` 和直接记录数组 `records`；记录的每个键都是字段名，包括可能出现的 `data`。视图和物化视图还会生成含对象及字段注释的 `OBJECT_METADATA` JSON 注释块。当前两个块均未防止内容中的 `/*`、`*/` 干扰 SQL 注释边界，DDL 回读还会把真实字段名 `data` 误当作旧包装；实施本稿时须按 §8.2/§8.3 修复。页面只解码当前 `SAMPLED_RECORDS` 样例块；独立的旧 `SAMPLE_RECORDS` 注释块只用于识别并拒绝，不当作“无样例块”，也不因普通正文含该字样就拒绝。DDL 是工具生成的对象定义文本，不承诺等同源库原始、完整的建表脚本；普通表、视图与物化视图共用“对象定义 SQL”名称。

未找到上述四元组对应的行时，两个新 Tab 均显示“暂无已发布 DDL 数据”，不回退到采集工作区；这只说明**未发布**，不推断是否已经采集。平台库物理表不存在或查询失败属于服务错误，不显示成普通空状态。DDL 与 JSON 当前行可能来自不同发布作业；页面应标注各自的发布来源或时间，避免把 DDL 样例行误称为当前 JSON 画像样本。

## 3. 对象详情页：上部两个 Tab，下部三个 Tab

页面从上到下依次为：**始终可见的对象标题及画像发布来源说明 → 三级级联搜索栏 → 上部“基本信息／对象定义 SQL”Tab → 下部“数据字典／数据画像／样例数据”Tab**。两组 Tab 独立切换：上部默认“基本信息”，下部默认“数据字典”；切换下部 Tab 不会改变上部当前选择。对象类型为 `table` / `view` / `materialized_view` 时，分别标为表 / 视图 / 物化视图，页面不把视图误称为普通表。对象标题下的来源说明行始终显示“JSON 画像发布于：<时间>”，时间取 `json_publish.published_at`，按本地时区显示并标注时区；无当前发布时显示“JSON 画像尚未发布”，检测到当前态不一致时显示“JSON 画像发布状态不一致”，不能继续显示旧时间。上部“对象定义 SQL”另标其 DDL 加载时间；具体 API 路由留待后续章节确定。

详情页在 `ready`、`not_published`、`409 profile_inconsistent` 和仅 `object-ddl` 报错时，均保留从路由参数得到的对象标题、来源说明行与三级级联搜索栏。搜索栏的候选独立读取 `object-options`，按 §3.7 的 `ready/not_published/inconsistent` 状态显示选项或专用空态文案，不因详情正文为空而移除。

`object-detail` 返回 HTTP 200、`state=not_published` 时，来源说明显示“JSON 画像尚未发布”；上、下两组 Tab 区域显示同名空态，不渲染空的基本信息或字段表，不尝试展示 DDL SQL 或样例。`object-detail` 返回 `409 profile_inconsistent` 时，来源说明显示“JSON 画像发布状态不一致，暂无法展示”；清除前一对象或前一响应缓存的画像与 DDL 内容，两组 Tab 的画像和 DDL 内容区域均不显示，也不渲染空字段表。`object-ddl` 单独返回 DDL 相关 409 时仍保留有效的 JSON 基本信息、数据字典与数据画像，只在 SQL 与样例两个区域显示对应受控错误。

数据字典与数据画像两个字段表均直接展示各自的表格列；不使用行展开、详情抽屉或仅悬停可见的方式藏住已列出的内容。宽表使用明确可见的横向滚动条，固定字段序号与字段名两列，保证滚动时仍能辨认当前字段。两个字段表均按 `ordinal_position` 升序排列，不依赖 JSON 键的保存顺序。样例数据单独按记录行展示，不混入字段画像表。

### 3.1 上部“基本信息”Tab

“基本信息”Tab 按三列排列，显示以下 **12 项**。Schema 没有去掉，而是与对象名合并为一项“对象名”，显示为 `schema_name.object_name`。分类置信度也没有去掉，而是并入“表分类”，显示为“事实表(置信度92%)”这类形式。本 Tab 不再单列注释来源、分类来源和字段数。其中分类、行数、抽样数和画像生成时间虽然会随采集或发布变化，仍作为当前这张表的基本概况放在上部；页面应标明它们属于当前 JSON 发布快照，而非源库实时数据。**画像发布时间不计入这 12 项**，按 §3 的来源说明行显示 `json_publish.published_at`；它是平台库发布时间，不能拿第 12 项“画像生成时间”代替。切换到上部“对象定义 SQL”时，这 12 项暂时不显示；对象标题及来源说明仍始终可见。

| 信息项 | JSON 来源 | 展示口径 |
| --- | --- | --- |
| 数据库名 | `object_info.database` | 对象身份的一部分 |
| 对象名 | `object_info.schema_name`、`object_info.object_name` | 合并显示为 `schema_name.object_name`，例如 `public.orders`；不再单列 Schema |
| 对象类型 | `object_info.object_type` | 显示表 / 视图 / 物化视图 |
| 对象注释 | `object_info.comment` | 只展示注释正文；空值显示“暂无注释”。不展示 `comment_source` |
| 表分类 | `table_profile.table_category`、`table_profile.confidence` | 事实表 / 维度表 / 桥接表 / 未知，括号内附置信度，例如 `事实表(置信度92%)`。置信度由 0–1 转为整数百分比；置信度缺失时只显示分类名。`table_profile=null` 时显示“未生成”。不展示 `classification_source` |
| 主键字段 | `table_profile.physical_constraints.primary_key.columns` | 按原顺序显示完整列组；复合主键不只取第一列；明确的 `primary_key=null` 显示“无” |
| 外键数量 | `table_profile.physical_constraints.foreign_keys` | 按外键约束条数计数，复合外键仍计 1；完整空数组显示 `0` |
| 索引数量 | `table_profile.indexes` | 按索引条数计数，包括主键或唯一约束所支持的索引、独立唯一索引和普通索引；完整空数组显示 `0` |
| 约束数 | `table_profile.physical_constraints` | 主键有值计 1，加上 `foreign_keys` 与 `unique_constraints` 的条数；不把索引再次计为约束 |
| 采集时总行数 | `object_info.total_rows` | 标注采集时点，不称为实时行数；按千分位显示 |
| 画像抽样行数 | `profiling.sample_count` | 显示实际取得的样本行数；缺失时显示“未记录”，0 条与缺失区分；按千分位显示 |
| 画像生成时间 | `generated_timestamp` | JSON 顶层生成时间，API 按 UTC 六位小数、`Z` 结尾返回，页面按北京时间 `YYYY-MM-DD HH:mm:ss.SSSSSS` 显示，例如 `2026-09-25 11:02:04.000000`。该字段受 `output.json_options.include_generation_timestamps` 控制，缺失时显示“未记录”（doc 19.3） |

主键字段、外键数量、索引数量和约束数都从**当前已发布 JSON 画像**读取或计算，不从上部 SQL 文本解析，以免混用 DDL 与 JSON 的不同发布轮次。“约束数”只覆盖 JSON 已采集的主键、外键、唯一约束，不包括 `CHECK`、排他约束、字段可空性或默认值。`table_profile` 或所需结构节点缺失时显示“未生成”，不能按空值计 `0`；节点完整且明确无对应项时才显示“无”或 `0`。唯一索引不等于唯一约束，不能据此增加约束数。

### 3.2 上部“对象定义 SQL”Tab

从 §2.2 的 `table_definition` 当前 DDL 行取得 `define_text`，识别并移除**末尾完整的** `/* SAMPLED_RECORDS ... */` 注释块后，展示剩余的原文（仅裁去块本身与块前的尾部空行，其余逐字保留）：文件头、对象定义、字段或对象注释及独立索引语句均保留。视图和物化视图的生成 DDL 还包含 `/* OBJECT_METADATA ... */` 块，承载对象及字段元数据；**该块及其中的 JSON 随定义原文保留**，不能当作样例块剥离。SQL Tab **不得显示 `SAMPLED_RECORDS` 样例块标记、该块内的 JSON 或任何样例记录**；只切掉样例块，不重新生成 SQL，也不从 JSON 字段拼装“建表语句”。如果原文没有当前格式的样例块，仍展示定义部分；识别到独立的旧 `/* SAMPLE_RECORDS ... */` 注释块、当前标记起始但无法可靠识别完整结束边界，或出现多个样例块时，不能把原文直接显示出来，应给出“DDL 样例块格式异常，暂无法展示对象定义”的受控错误。旧标记检测针对 SQL 注释块本身，不能仅在整段正文中搜索 `SAMPLE_RECORDS` 字样。

生成器会为普通表写 `CREATE TABLE`，为视图和物化视图写对应的 `CREATE VIEW` / `CREATE MATERIALIZED VIEW`；主键、外键、唯一约束写在当前生成的普通表定义里，独立索引是否写出取决于 DDL 生成时的 `output.ddl_options.include_indexes`。由约束支持的索引不会再重复输出 `CREATE INDEX`。这份文本是**已发布的生成产物**，不是源库原始完整 DDL；当前生成链路也未覆盖 `CHECK`、排他约束等所有 PostgreSQL 约束。无需另建三张约束明细表，也不能把 SQL 页描述为“源库全部约束与索引”。

没有匹配的 `table_definition` 行时显示“暂无已发布 DDL 数据”；匹配行的库名或对象类型与当前 JSON 不同时显示“当前已发布 DDL 与 JSON 对象身份不一致，暂无法展示”；DDL 行与当前发布标记不一致时显示“已发布 DDL 状态不一致，暂无法展示”。这些状态均不展示 SQL 或样例，但不影响 JSON 基本信息、字典与画像。可展示时标出该行的 `loaded_at` 或发布标识，清楚区分本页 SQL 与 JSON 画像的发布时间。具体代码阅读区样式、复制交互与滚动方式以 UI 设计文档为准。

### 3.3 下部“数据字典”Tab：结构与说明

字段注释可能来自数据库、DDL 或 LLM：它是本次 JSON 发布快照中的描述性元数据，不等同于抽样统计，来源须可见。对象注释正文已在上部“基本信息”Tab 展示，不在下部另建一块重复区域；对象级 `comment_source` 不在基本信息中单列。

字段表直接显示以下列：

| 字段序号 | 字段名 | 数据类型 | 字段注释 | 注释来源 | 可空 | 默认值 | 主键约束 | 外键约束与目标 | 唯一约束 | 字段参与的索引 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |

| 页面列 | JSON 来源 | 展示口径 |
| --- | --- | --- |
| 字段序号 | `column_profiles[name].ordinal_position` | 按序号排序，不依赖 JSON 键顺序 |
| 字段名 | `column_profiles` 的键 `name` | 保留源库字段名原样 |
| 数据类型 | `column_profiles[name].data_type` | 完整保留 `numeric(10,2)` 等类型修饰 |
| 字段注释 | `column_profiles[name].comment` | 空注释显示“暂无注释” |
| 注释来源 | `column_profiles[name].comment_source` | 来源为空显示“未标注”；不是另一条注释 |
| 可空 | `column_profiles[name].is_nullable` | 显示“是 / 否”，表示数据库结构可空性 |
| 默认值 | `column_profiles[name].column_default` | `null` 显示“—”，其余保留表达式原文 |
| 主键约束 | `table_profile.physical_constraints.primary_key` | 命中 `columns` 时显示约束名及完整列组；复合主键标明“成员” |
| 外键约束与目标 | `physical_constraints.foreign_keys` | 命中 `source_columns` 时显示每个约束名、目标 Schema / 对象 / 字段；复合外键保持来源与目标列顺序 |
| 唯一约束 | `physical_constraints.unique_constraints` | 命中 `columns` 时显示每个约束名及完整列组；复合唯一约束标明“成员” |
| 字段参与的索引 | `table_profile.indexes` | 只列本字段直接参与的索引，每项显示“索引名（键列或 INCLUDE 列；唯一或非唯一）”；同字段参与多个索引时逐项显示。若 DDL 生成时包含对应定义，可在上部“对象定义 SQL”Tab 查看其 SQL |

“字段参与的索引”的匹配规则固定为：字段名出现在某索引的 `columns` 时标为“键列”，出现在 `included_columns` 时标为“INCLUDE 列”；不靠字段名是否出现在 `key_expressions` 或 `definition` 的文本中做模糊匹配。单元格示例：`idx_screenings_start_time（键列；非唯一）`；`screenings_pkey（键列；唯一；支持主键约束）`。`is_primary=true` 时标“支持主键约束”；其他 `is_constraint_backed=true` 的索引标“支持约束：<constraint_name>”。只有 `indexes` 为完整数组且该字段未参与任何索引时才显示“无”；索引节点缺失或 `table_profile=null` 时显示“未生成”。表达式索引可能只有 `key_expressions`，无法可靠归属某个字段；此时不强行填进字段行。主键或唯一约束背后的索引可在此列出现，须标明“支持约束”，不要让用户误以为又多了一项独立约束。上部 SQL 来自另行发布的 DDL，可能与当前 JSON 的索引快照不同；页面不把两者拼接成同一时点的完整索引清单。

真实主键只按 `primary_key.columns` 判断；不能因字段名含 `id`、语义角色为 `identifier`、抽样唯一度为 `1.0` 或存在候选唯一列组，就标记“主键”。唯一索引显示为“唯一索引”，不改写成“唯一约束”。索引属于数据库结构，即使 JSON 将它放在 `table_profile.indexes` 下，也应在数据字典 Tab 呈现。

### 3.5 数据画像表上方的抽样提醒

当前 `configs/metadata_config.yaml` 的 `sampling.enabled=true`、`sampling.sample_size=1000`；`MetadataGenerator` 在未配置 `sample_size` 时也默认使用 **1000**。`--step json` 将它作为 `DatabaseConnector.sample_data()` 的 `LIMIT` 上限；SQL 是 `SELECT * ... LIMIT %s`，没有随机抽样或固定排序。因此这里的“抽样”指**最多读取指定行数的样本**，不能写成“随机抽取”或“具有统计代表性”。

当前启用采样的 JSON 生成路径中，`OutputFormatter.build_json_document()` 用实际采样 DataFrame 的 `len(sample_data)` 写入每个对象 JSON 的 **`profiling.sample_count`**；字段统计由同一份数据计算。后续发布必须把这个实际行数带入平台库与对象详情 API，数据画像 Tab 从**当前已发布对象**的该字段读取提醒中的 `N`。不能用当前 YAML 的 `sampling.sample_size` 代替：它只是上限，采集后也可能变更。不能用 JSON `sample_records.records` 或 DDL `SAMPLED_RECORDS.records` 的长度代替：它们是另行截取的少量示例行，当前 `output.ddl_options.sample_records.count=5`。

当 `profiling.sample_count = N > 0` 时，在画像字段表正上方显示：

> **抽样统计说明：**下方的候选唯一列组、空值率、唯一度、不同值数及最小值、最大值，基于本次采集读取的 **N 条记录**分析或计算，仅反映采集时的样本。表分类和字段语义角色是画像判断；字段类型、可空性和物理约束来自数据库结构。

`N` 为本对象实际取得的行数，不称为“随机样本数”。即使 `N` 恰好等于 `object_info.total_rows`，两个值仍来自不同查询，页面不额外宣称完成了事务一致的全表统计。`profiling.sample_count=0` 时显示：“**抽样统计说明：**本次采集未取得样本记录（0 条），字段统计指标暂无可用数据；字段结构信息仍可查看。”这不等于断言源表为空。`profiling` 或 `sample_count` 缺失时显示：“**抽样统计说明：**本次画像未记录实际抽样行数，无法确认字段统计指标的样本规模。”无法确认口径的抽样统计显示“—”，不能拿配置上限或示例行数补出一个 `N`。

### 3.6 下部“样例数据”Tab

只读取 §2.2 所述同一条 `table_definition` 当前 DDL 行的 `define_text`，从末尾 `/* SAMPLED_RECORDS ... */` 注释块中解析 JSON。**只展示该块的样例数据，不展示 SQL 定义文本**。当前格式的 `records` 直接保存记录对象；块内 `object_name` 是 `schema_name.object_name` 限定名，须与当前 DDL 行的 `schema_name + '.' + object_name` 核对，块内 `object_type` 则与该行的 `object_type` 核对，不能将块内限定名与 DDL 行的裸 `object_name` 直接比较。每条记录的键都按真实字段名处理，`data` 也不例外，不把旧 `{label, data}` 包装作为本版输入。顶层身份字段不当作样例列；不读取 JSON 画像的 `sample_records`，也不直接查询源库。读取和切分规则与上部 SQL Tab 共用：两者必须来自同一版 `define_text`，SQL Tab 排除的正是样例 Tab 所使用的块。

将 `records` 渲染为表格：字段名作列标题，每条记录占一行，保留记录值原貌；字段较多时横向滚动。**最多显示前 5 条**，实际不足 5 条则按实际条数显示，不能补假数据。当前 DDL 配置 `output.ddl_options.sample_records.enabled=true`、`count=5`，但页面仍以已发布块中的实际记录为准，不把配置值写成实际条数。以 §2 所列受管作业的 `ddl/orders.public.users.sql` 为数据例，展示 `user_id`、`user_name` 两列及 5 行数据；不把 `object_type`、`object_name` 当作额外列。17 号 UI 原型展示的 `public.orders` 是另一份演示数据（6 列、5 行），不规定实际页面必须显示哪个对象或字段数。页面标注“本页显示已发布 DDL 中的最多 5 条样例记录，仅供查看，不代表全表或数据画像的抽样规模”。

没有匹配 DDL 行时显示“暂无已发布 DDL 数据”；DDL 与 JSON 对象身份不兼容时显示“当前已发布 DDL 与 JSON 对象身份不一致，暂无法展示”；DDL 当前态不一致时显示受控错误，不展示旧正文；有行但没有 `SAMPLED_RECORDS` 块时显示“本次已发布 DDL 未包含样例数据”；块存在但 `records=[]` 时显示“本次已发布 DDL 包含 0 条样例记录”。出现旧格式标记、块 JSON 无法解析、`records` 不是对象数组、记录字段键集合不一致、身份与当前行不一致或块边界异常时显示受控的“样例数据解析失败”，不能悄悄改读 JSON 或把整份 `define_text` 输出到样例 Tab。读取受控失败不改变已发布数据。

14～17 的详情页共用 14.1 级联搜索栏。它在收起时的对象名称输入样式见四份 HTML；展开后的**可搜索对象名称下拉**以 14.1 PNG 为准。一级对象类型取当前 JSON 已发布对象的实际类型；选择类型后，二级 SCHEMA 只列该类型下存在对象的 Schema；选择 Schema 后，三级对象名称只列该类型及 Schema 下的对象，输入字符在候选名称中搜索。上游选择变化时清空不再有效的下游选择；没有候选时明确显示空状态。只有选定一个确切对象后，“搜索”才切换详情对象；输入的自由文本本身不能直接充当对象身份。候选名称输入采用约 250 毫秒防抖，过时响应不得覆盖较新的选择。切换对象后更新标题、两组 Tab 的 JSON 内容、DDL 来源和缓存；不得沿用前一个对象的 SQL 或样例记录。进入详情页时按当前 `schema_name/object_name` 回填选择；Tab 切换本身不改变对象选择。

前端列表路由固定为 `/data-assets/:sourceId/objects`，详情路由固定为 `/data-assets/:sourceId/objects/detail?schema_name=...&object_name=...`；Schema 和对象名由路由查询参数承载，点击列表对象名或详情级联搜索均进入该详情路由，刷新或复制地址后仍能打开同一对象。更换对象时两组 Tab 重置为“基本信息／数据字典”，两个字段表页码重置为 1，并清除前一对象的 DDL 响应；只在同一对象内切换 Tab 时，各字段表保留自己的当前页，SQL 和样例 Tab 复用本次详情页已获取的同一份 DDL 响应。重新进入详情或刷新页面会重新请求 JSON 详情；之后首次打开 DDL Tab 时重新请求当前 DDL。页面停留期间不自动感知重新发布，用户可从页面标明的时间判断内容新旧。

原型中的横向滚动与分页以实际数据为准：对象列表由服务端分页，改变筛选条件时回到第 1 页；字典、画像字段表使用详情接口返回的完整字段数组，在前端各按每页 10 行分页并保留可见的横向滚动，不再增加字段分页 API。样例最多 5 行，不显示分页栏，不为原型截图中的示意分页制造额外记录或空白页。DDL 未发布、DDL 与 JSON 身份不兼容、样例块缺失、JSON 未发布或当前态不一致等状态沿用本文各节的数据语义，不照搬静态原型的示例值。

## 4. 数量与缺失值的解释

`object_info.total_rows`、`profiling.sample_count` 和 DDL 样例块记录数是三个不同数量。最新 `orders` 的 JSON 总行数与画像抽样行数分别为 **500、500**，同作业 DDL 样例块保存 **5** 行。页面只把前两者用于基本概况与画像统计口径，把 DDL 块的实际记录数用于样例 Tab；不能把 5 显示为画像抽样规模，更不能把配置上限 1000 显示成该对象的实际样本数。DDL 与 JSON 可能独立重发，页面实际展示时应各按自己的当前发布行取值，不能假定三者总是来自同一轮采集。`statistics.null_rate` 和 `statistics.uniqueness` 由实际画像抽样行数计算，展示时从 0–1 转为百分比；不表示全表保证。数据与当前源库可能随时间变化，页面按 §8 的 API 分别标明 JSON 画像的生成或发布时间与 DDL 的加载时间。

对缺失值采用统一规则：未生成 / 不适用显示“—”或明确说明，数值零显示 `0` 或 `0%`。物理约束节点完整、对应列表为空或主键明确为 `null` 时才显示“无”；节点缺失时不得假定“无”。表分类 `unknown` 显示“未知”，与 `table_profile=null` 的“未生成”区分。

## 5. 真实样例值与访问边界

下部“样例数据”Tab 有意展示 `table_definition.define_text` 的当前 `SAMPLED_RECORDS` 块中的真实源库值，可能是姓名、文本内容等；对象定义 SQL Tab 必须把该块排除。JSON `sample_records.records` 和 `statistics.value_distribution` 不作为本版样例 Tab 的数据来源，也不作为对象列表 API 的字段返回。当前版本不做鉴权或按用户过滤，读取接口按请求返回对应对象的全部设计内容；不把样例块混进 SQL 文本，也不把整份 DDL 当成样例数据。上部 SQL 与下部样例数据共用同一次 DDL 读取结果，在用户首次打开其中一个 Tab 时请求并缓存，两个 Tab 分别展示各自内容。

`generated_timestamp` 是 JSON 生成时间，已按 doc 19.3 改为带时区的 UTC 来源并入 timestamptz 列；页面时间标注优先采用后续发布设计中语义明确的采集或发布时间，展示统一按北京时间（doc 19.3 §4）。DDL 行的 `loaded_at` 是已发布定义的加载时间，不等于 JSON 画像的生成或发布时间。

## 6. JSON 画像的平台库表结构

### 6.1 建表依据与存储口径

当前受管 JSON 3.0 的 `object_info`、`profiling`、`table_profile` 都以一个数据库对象为粒度，`column_profiles` 则以字段名为键、每字段一份。因此使用 `public.table_profile`（每源、Schema、对象一行）和 `public.table_column_profile`（每对象、字段一行）两张当前态表。字段名取自 `column_profiles` 的键，不能期待 JSON 另有 `column_name`。样本依据为 §2 所列最新 UUID 作业目录中的 7 份对象 JSON；字段结构还应以 `TableMetadata._to_json_dict()`、`TableMetadata._compact_v3_statistics()`、`TableProfile.to_json_dict()` 和 LLM 分类增强代码为准。

对象身份沿用现有 `table_definition` 的 `source_id + schema_name + object_name` 口径；`db_name` 只是采集时库名快照，`job_id`、`publish_id` 是当前行最后一次成功发布的来源，不作为内容历史主键。同一源下的各对象可单独读取，字段表通过同一对象身份关联表级行。JSON 与 DDL 可分别发布，因此这两张表不能与 `table_definition` 按 `job_id` 强行合并为同一轮数据。

页面直接展示或可能筛选的单值指标使用 `text`、`boolean`、`bigint`、`integer`、`numeric` 等列：例如字段类型、可空性、语义角色、空值率、唯一度和分类置信度。判断依据是字符串列表，用 `text[]` 保存；一个对象可能有多个外键、唯一约束、索引、候选唯一列组，且每项内部字段不同，用 JSONB 保留完整明细，页面服务层按字段名投影出 §3.3/§3.4 的对应列，不另存一套易与原明细漂移的字段级副本。`statistics.min/max` 在当前 JSON 中已是异构类型的字符串，故存为 `text`，不强行转换成同一种数值或时间类型。数值比例采用 `numeric(8,6)`，足以保留当前产物的精度；显示时才转换为百分比。

JSON 的 `sample_records` 整体保留为 JSONB，供未来用途；**本版样例数据 Tab 仍只读取已发布 DDL 的 `table_definition.define_text`**，对象列表接口也不返回真实样例值。当前 `build_json_document()` 优先从同作业 DDL 样例块提取 `sample_records`，只有提取不到记录时才从本次采样 DataFrame 截取；现有 DDL 回读还会将看起来像数字的字符串转换为数字，可能改变类型或丢失前导零。因此 `json_sample_records` 既不保证与 DDL 块原文逐值同型，也不能作为原始源库值的权威副本；未来使用该列前须重新核对采集转换口径。§8.2 已要求实施时修正当前格式将真实 `data` 字段误作历史包装层的缺陷，该修正适用于 JSON 采集链路，但不以本稿变更数字转换规则。`generated_timestamp` 为带时区的 UTC 时间点，入库为 `timestamptz(6)`（doc 19.3）；`loaded_at` 是平台库写入时间，使用 `timestamptz`。下列 DDL 不设置 CHECK 约束。

### 6.2 PostgreSQL 建表语句

```sql
CREATE TABLE public.table_profile (
    source_id                  uuid NOT NULL,
    schema_name                text NOT NULL,
    object_name                text NOT NULL,
    db_name                    text NOT NULL,
    object_type                text NOT NULL,

    publish_id                 uuid NOT NULL,
    job_id                     uuid NOT NULL,
    metadata_version           text NOT NULL,
    generated_timestamp      timestamptz(6),
    loaded_at                  timestamptz NOT NULL DEFAULT now(),

    object_comment             text,
    object_comment_source      text,
    total_rows                 bigint,
    column_count               integer NOT NULL,

    sample_method              text,
    sample_count               bigint,

    has_table_profile          boolean NOT NULL,
    table_category             text,
    category_confidence        numeric(8, 6),
    classification_source      text,
    classification_reason      text,
    classification_basis       text[],
    rule_table_category        text,
    rule_confidence            numeric(8, 6),
    rule_inference_basis       text[],

    primary_key_name           text,
    primary_key_columns        text[],
    foreign_key_count          integer,
    index_count                integer,
    constraint_count           integer,
    foreign_keys              jsonb,
    unique_constraints        jsonb,
    indexes                   jsonb,
    unique_column_sets        jsonb,

    json_sample_records       jsonb,

    PRIMARY KEY (source_id, schema_name, object_name)
);

CREATE TABLE public.table_column_profile (
    source_id             uuid NOT NULL,
    schema_name           text NOT NULL,
    object_name           text NOT NULL,
    publish_id            uuid NOT NULL,
    column_name           text NOT NULL,
    ordinal_position      integer NOT NULL,

    data_type             text NOT NULL,
    is_nullable           boolean NOT NULL,
    column_default        text,
    column_comment        text,
    comment_source        text,

    semantic_role         text,
    semantic_confidence   numeric(8, 6),
    semantic_basis        text[],

    null_count            bigint,
    null_rate             numeric(8, 6),
    unique_count          bigint,
    uniqueness            numeric(8, 6),
    sample_min            text,
    sample_max            text,
    value_distribution    jsonb,

    PRIMARY KEY (source_id, schema_name, object_name, column_name),
    FOREIGN KEY (source_id, schema_name, object_name)
        REFERENCES public.table_profile (source_id, schema_name, object_name)
        ON DELETE CASCADE
);

CREATE UNIQUE INDEX table_column_profile_object_order_idx
    ON public.table_column_profile
       (source_id, schema_name, object_name, ordinal_position);
```

字段序号的唯一索引同时服务对象详情的顺序读取，并防止同一对象出现重复序号；它不是 `CHECK` 约束。序号为正整数的规则仍由 §7.2 的发布输入校验承担。

### 6.3 JSON 字段映射与缺失值

| 入库字段 | JSON 来源 / 生成规则 | 依据 |
| --- | --- | --- |
| `metadata_version`、`generated_timestamp` | 顶层 `metadata_version`、`generated_timestamp` | 版本用于识别产物格式；时间必须带时区并归一为 UTC（doc 19.3），缺失时为 `NULL` |
| `db_name`、`schema_name`、`object_name`、`object_type`、`object_comment`、`object_comment_source`、`total_rows` | `object_info` 相应字段 | 对象身份、结构说明与采集时总行数；`source_id` 来自受管数据源，不从 JSON 猜测 |
| `column_count` | `column_profiles` 的键数 | JSON v3 没有单独的总字段数字段；本版发布加载器按 §7.2 拒绝空对象，成功发布时此值至少为 1 |
| `sample_method`、`sample_count` | `profiling.sample_method`、`profiling.sample_count` | `sample_count` 是画像实际抽样行数，不是配置上限，也不是样例记录条数 |
| `has_table_profile`、分类及规则备份列 | `table_profile` 是否非 `null`；其 `table_category`、`confidence`、`classification_source`、`classification_reason`、`inference_basis`、`rule_based_classification` | `unknown` 是明确的分类结果，不能与 `table_profile=null` 混同；规则备份拆为可直接读取的类别、置信度和依据 |
| 主键列、`foreign_keys`、`unique_constraints`、`indexes`、`unique_column_sets` | `table_profile.physical_constraints`、`indexes`、`unique_column_sets` | 保留完整约束、索引及候选列组；主键名称与列组单独存放，便于基本信息直接读取 |
| `foreign_key_count`、`index_count`、`constraint_count` | 对外键数组、索引数组及主键/外键/唯一约束明细计数 | 对应 §3.1；约束数只含 JSON 已采集的主键、外键、唯一约束，索引不重复计入 |
| `json_sample_records` | 顶层 `sample_records` 整体 | 保留 `sample_method` 和 `records`；通常由 DDL 样例块回读而来，当前回读对数字样式字符串有类型转换，不保证保留 DDL 原值；不作为本版样例数据 Tab 的来源 |
| 字段发布版本、身份、类型、默认值、注释 | 本次发布的 `publish_id`，以及 `column_profiles` 的键及其 `ordinal_position`、`data_type`、`is_nullable`、`column_default`、`comment`、`comment_source` | 字段行的 `publish_id` 与所属对象行相同，用于读取时识别混入旧轮次的字段；`column_name` 来自键名 |
| 字段语义列 | `column_profiles[name].semantic_analysis` | 角色、置信度和判断依据分列，便于 §3.4 直接展示 |
| 字段统计列 | `column_profiles[name].statistics` | 空值数/率、不同值数/唯一度、最小/最大值独立成列；只有取值分布保留 JSONB |

`table_profile=null` 时 `has_table_profile=false`，所有分类、约束、索引和候选列组列为 `NULL`，不能写成“无”或 `0`。`physical_constraints.primary_key` 明确为 `null` 时，`primary_key_name=NULL`、`primary_key_columns` 存空数组；若 `physical_constraints` 或 `primary_key` 键缺失，则 `primary_key_columns=NULL`，表示无法确认。`foreign_keys`、`unique_constraints`、`indexes` 明确为空数组时分别存 `[]`，相应可确定的计数为 `0`；节点缺失时存 `NULL`，相关计数不得补零。`constraint_count` 只在主键、外键、唯一约束三部分均可判定时计算。字段统计节点或单项指标缺失时，对应列保留 `NULL`，不把缺失值改写为零。

字段表只存结构与字段自身画像；某字段参与的主外键、唯一约束、索引和候选唯一列组由同一对象行的完整明细按 §3.3/§3.4 规则投影。复合列组顺序和一个字段参与多项明细的信息因此不会丢失。对象行保存 `publish_id`、`job_id`、`loaded_at`；字段行只额外复制 `publish_id` 这一版本标识，插入时必须与所属对象行相同。读取时逐行比较字段 `publish_id`、对象 `publish_id` 与当前 JSON `publish_info.publish_id`；字段行数相同但版本不同也按内容不一致处理。子表外键只保证画像两表内部存在关联，不自行保证版本相等；它不指向 `db_source_info`，删除数据源时仍须显式处理该源的 `table_profile` 当前行。JSON 发布必须在同一事务内替换该源的对象及字段当前内容，防止残留已删除对象或旧字段；具体发布预检与提交顺序见 §7.4。

## 7. 受管 JSON 发布到 MetaWeave 平台库

### 7.1 写入目标与数据库连接信息

本节的“加载”指在 Web 发布页选择 `json` 后，把该作业的对象 JSON 写入 **MetaWeave 平台 PostgreSQL** 的 `public.table_profile`、`public.table_column_profile`，并登记 `publish_info(step_name='json')`。它不调用 `rag_load`，不写 Milvus，也不重新采样源数据库。采集成功只产生工作区文件与 `job_info(json)`，**不会自动入库**；用户另行发布才改变平台库当前画像。

平台库连接信息由 `backend/persistence/platform_db.py` 的 `load_platform_settings_from_env()` 读取：`PLATFORM_DB_HOST`、`PLATFORM_DB_USER`、`PLATFORM_DB_PASSWORD` 必填；`PLATFORM_DB_PORT` 缺省为 `5432`，`PLATFORM_DB_NAME` 缺省为 `metaweave`，`PLATFORM_DB_SSLMODE` 可选。Web API 的 `backend/api/main.py:create_app()` 在未注入设置时先调用 `load_project_env()`，读取**项目根目录 `.env`**，且 `override=False`，所以进程中已设置的同名环境变量优先；随后把 `PlatformSettings` 放入 `app.state.platform_settings`，发布路由通过现有依赖取得它，再用 `platform_session(settings)` 开平台库会话。部署时也可直接注入这些环境变量。本文不记录实际主机、账号或密码值。

`configs/metadata_config.yaml` 的 `database` 段和 `db_source_info` 的 host、username、加密密码描述的是**被采集的源库**，不能作为 JSON 发布的写库连接参数。发布只读取 `db_source_info` 的 `source_id`、`db_name`、`selected_schemas`、`is_active` 等登记信息做归属与范围核对，不解密源库密码、不连接源库。表结构由管理员按 §6 的 SQL 创建；应用启动当前不会自动建表。

### 7.2 输入目录、清单和发布资格

受管 JSON 默认位于**项目根目录**的 `output/<source_id>/<job_id>/json/`；例如 §2 的实际样本是 `output/b4a87275-7c37-4feb-bf1c-e5a8446c174f/b23ac4f7-c9d8-42c5-b625-bf935dfd5194/json/`。目录由 `metaweave/core/clean_targets.py:resolve_json_output_dir(source_id, job_id)` 统一解析，两级 ID 均规范化为 UUID，并核对项目根边界、预期路径及各级符号链接。发布不得使用全局 `output/json/`、浏览器提交的任意路径、其他 `job_id` 或其他 `source_id` 的目录；也不从 `configs/metadata_config.yaml` 的相对输出配置重新猜目录。

目录内的对象文件名是 `<db_name>.<schema_name>.<object_name>.json`，另有 `manifest.json`，其当前内容为 `{"files": ["<db>.<schema>.<object>.json", ...]}`；`files` 不包含清单自身。发布资格先查该 `job_id` 属于本 `source_id`、登记源仍启用、`job_info(job_id,'json')` 最近状态为 `success`；**不要求 DDL 已发布**，因为采集依赖与发布步骤独立。预检接口沿用现有 `GET /api/data-sources/{source_id}/collection-jobs/{job_id}/publish-check`，新增 `json` 行，`output_ready` 至少核对目录、非空清单及清单/对象文件集合，`publishable` 还须结合成功状态；它是只读检查，不生成发布 ID。当前 `publish_service.py` 和 `PublishView.vue` 的发布白名单仍仅为 `db/ddl`，加入 `json` 是本设计的待实施改动。

真正发布时，对目录做完整、整批输入校验：`manifest.json` 和每个声明文件都须是普通文件而非符号链接；清单文件名非空、唯一、严格三段式，声明集合与目录实际对象 `.json` 集合双向一致，拒绝缺件、多件、混库和重复对象；文件须为 UTF-8 JSON，根节点用 `MetadataDocument.from_dict()` 校验 v3，再核对文件名、`object_info.database/schema_name/object_name` 与登记源的 `db_name`、当前 `selected_schemas`。对象类型只接受当前生成器支持的 `table/view/materialized_view`。任何对象失败，整批拒绝，不用剩余文件缩小该源的当前画像。现有 `read_managed_json_input()` 只返回对象摘要，受管 MD 准备链依赖该返回契约；实施时新增返回**已校验文档内存快照**的共享读取函数，旧函数作为摘要包装继续保持原签名和返回值。JSON 发布映射只消费这份快照，不另读磁盘、维护第二套清单规则；MD 原有调用不因本次改造改变行为。不得访问 `JsonLoader` 的私有缓存或只依赖其按库名前缀枚举时会忽略的文件。

`MetadataDocument.from_dict()` 尚未严格检查 §6 所有入库列的类型和数值范围，也会接受空的 `column_profiles: {}`。本版 JSON **发布加载器**须额外要求每个对象的 `column_profiles` 为非空对象；任一对象为空即整批受控拒绝，不插入 `column_count=0` 且没有字段行的画像。该规则只属于本版发布映射，不改 `MetadataDocument.from_dict()` 或受管 MD 既有的共享读取契约。加载器还必须补齐静态校验：身份与字段名非空；`ordinal_position` 为**正整数**且同一对象内不重复，允许 PostgreSQL 删除字段后留下序号空档，不要求从 1 连续；其他计数为非负整数（均拒绝布尔值）；`is_nullable` 为布尔；置信度/比例是有限且在 0–1 内的数；判断依据为字符串数组；约束/索引/候选集合为预期对象数组；`statistics.value_distribution` 为预期对象；`generated_timestamp` 若存在必须带时区（UTC 六位小数、`Z` 结尾或等价偏移），无时区输入拒绝（doc 19.3）。缺失的可选节点按 §6.3 留 `NULL`，明确空数组保留空数组，**畸形非空值不得静默改写为 `NULL`、`[]` 或 `0`**。所有字段行都由 `column_profiles` 键集合生成，不丢弃无法映射的字段。

入库前还须核对同一对象内的结构引用：主键、唯一约束、候选唯一列组的 `columns`，外键的 `source_columns`，以及索引的直接键列 `columns` 和 `included_columns`，都只能引用该对象 `column_profiles` 中的字段；外键来源列与目标列必须非空且等长。表达式索引的 `key_expressions` 是表达式文本，不能按字段名强行校验；外键目标对象可能不在本次选中范围内，不要求它出现在本批 JSON 中。发现无效引用时整批拒绝，不能等页面投影时悄悄遗漏。原始样例值和取值分布可能含敏感数据；错误响应和普通日志仅报文件名、字段路径与错误类别，不输出 JSON 内容、样例值或平台库凭据。

### 7.3 JSON 标签到表字段的逐项映射

以下“标签”指 JSON 对象的键；`source_id`、`job_id`、`publish_id` 由受管请求与发布事务提供，**并不存在于每个对象 JSON 内**。表级和字段级行使用同一 `source_id + schema_name + object_name` 身份；字段行的 `column_name` 来自 `column_profiles` 的键，不能从 JSON 中寻找同名属性。

| `public.table_profile` 字段 | JSON 标签或计算来源 |
| --- | --- |
| `source_id` | 本次发布请求的数据源 ID，须与 `job_info` 的工作区归属一致 |
| `schema_name`、`object_name` | `object_info.schema_name`、`object_info.object_name`；与文件名逐字核对 |

### 7.4 发布事务、失败语义与代码接入

Web 继续使用 `POST /api/data-sources/{source_id}/collection-jobs/{job_id}/publications`，请求 `steps` 新增 `json`；前端发布页将其改为可选，并以预检结果决定当前作业能否勾选。发布编排把 `json` 加入后端白名单、预检和执行映射。一次请求可同选 `db/ddl/json`，沿用现有按步骤分别提交及逐步返回结果的语义；JSON 不因 DDL 是否**已发布**而被阻断，也不发布 MD 或 `table_schema`。一次发布请求共用 `publish_id`，但每个成功步骤各写自己的 `publish_info` 行，DDL 与 JSON 的当前内容可以来自不同请求和作业。

预检时同时记录 `job_info(json).updated_at` 运行标识与 `db_source_info.updated_at` 登记版本，并从当时登记行读取 `db_name/selected_schemas` 做输入校验。从 §7.2 的目录读入并映射完整对象/字段内存快照后，提交事务先锁定 `db_source_info` 源行，复查登记存在且启用、`updated_at` 仍与预检时相同、工作区仍属该源、`job_info(json)` 仍为 `success` 且运行标识未变。登记修改即使只改显示名称，也保守拒绝本次提交，用户可重新发布；不能把旧登记范围下校验过的文件写成新登记范围的当前画像。锁与提交须沿用现有 DDL/db 发布的同一平台库会话；采集侧 `start_step` 在写入 `running` 并刷新步骤行 `updated_at` 前取得同一源行锁，故新一轮重跑不能在发布终态复查与提交之间越过。`finish_step` 不取得该源行锁，不作为这一并发防护的依据。任一标识已变时拒绝本次 JSON 写入，即使文件解析曾经成功；文件读取期间发生重跑而导致缺件/混合文件时，也作为本次输入失败处理，不把部分结果入库。

成功事务中只翻转该源 **`json`** 的旧 `publish_info` current 标记；删除该源旧 `table_profile` 行（字段行由 §6.2 的 `ON DELETE CASCADE` 清除），插入本批全部对象行与字段行，再插入 `publish_info(step_name='json', status='success', is_current_publish=true)`，一次提交。对象行与每条字段行都写相同的本次 `publish_id`；先写对象行再写字段行，以满足两表的外键。平台库插入失败时整个成功事务回滚，旧画像和旧 current 保持不变。下一次成功发布按本批**完整集合**替换，旧作业已有而本批没有的对象和字段都删除；绝不逐对象部分覆盖。删除数据源时，现有清理事务也要显式删除该源 `table_profile` 行，并由级联清理字段行，不保留孤立画像。

输入损坏或写库失败沿用现有发布语义：本次步骤记 `failed`，尽可能单独插入非 current 的 `publish_info` 失败记录，**不翻旧 current、不删除旧画像**；源在锁下已删除或禁用时沿用 404/409 出口，不伪造失败发布。发布预检未通过时不生成 `publish_id`；执行阶段发现步骤重跑，则在逐步结果中报告未就绪并写非 current 失败记录；同请求已成功提交的其他步骤维持成功。日志不输出原始 JSON 或异常中可能包含的真实样例值。具体冲突分类应加入新画像表主键/外键，保留 `publish_info_current_idx` 冲突与其他约束错误的现有区分。

源登记版本变化在执行阶段按本次 `json` 步骤受控失败处理：结果文案为“数据源登记信息已变化，请重新发布”，写非 current 失败记录，保留旧画像与旧 current；不得误报“平台库不可用”。源已删除或禁用仍沿用上段的 404/409 出口。若与同请求其他步骤组合发布，已提交成功的步骤不回滚。

## 8. 对象列表与详情读取 API 设计

### 8.1 现有接口边界与新增接口

现有 `GET /api/data-assets` 和 `GET /api/data-assets/{source_id}/profile` 只读取 **`db` 当前发布**及 `db_profile`，支撑数据库资产目录和整库画像页；两者的响应、统计数和“已发布”判断均不改成 JSON 口径。当前数据库画像页末尾的“查看当前库表的画像”仍是禁用占位，后续页面接入可把它指向新增对象列表；还应从数据源详情页提供入口，因为某个源可能已发布 JSON、尚未发布 db，不能让这类对象只能靠手输 URL 访问。`GET .../publish-check` 与 `POST .../publications` 的 `json` 扩展已在 §7 设计，仍沿用现有路径；这里不新建第二套发布 API。

新增**独立对象读取路由**，以下 `source_id` 由路径解析为 UUID，`schema_name`、`object_name` 为查询参数且按数据库标识原样精确匹配（不自动转小写）。用查询参数承载对象名，避免引用名中含有路由分隔符时误匹配其他路径；不接受 `job_id` 或任意文件路径作为读取参数。对象列表与详情只读平台库的当前发布行，不访问采集工作区或源库。

| 方法与路径 | 用途及返回边界 |
| --- | --- |
| `GET /api/data-assets/{source_id}/objects?page=1&page_size=50&object_type=...&schema_name=...&keyword=...` | 该源**当前 JSON 发布**的对象分页列表，供 13 号原型的筛选、表格与分页使用。只返回身份、对象类型/注释、分类、字段数、采集时总行数、物理主键有无状态和 JSON 来源时间等摘要；不返回字段统计、`json_sample_records`、取值分布、DDL 或样例值。`object_type`、`schema_name` 精确筛选，`keyword` 仅按对象名称模糊筛选；`page_size` 上限 100，按 `schema_name, object_name` 稳定排序。无 JSON 当前发布时返回 `state=not_published`、空列表，不拿 `db_profile` 的对象计数伪造对象行。 |
| `GET /api/data-assets/{source_id}/object-options?object_type=...&schema_name=...&keyword=...` | 供 14～17 共用的 14.1 级联搜索栏读取候选。只从该源当前 JSON 对象集合返回去重的 `object_types`、按所选类型收窄的 `schemas`、按所选类型与 Schema 及名称输入收窄的 `objects`（对象身份包含 `schema_name/object_name/object_type`）；不返回画像指标、DDL 或样例值。`keyword` 只筛对象名称候选，不改变前两级选项；不要求前端遍历分页对象列表拼候选。 |
| `GET /api/data-assets/{source_id}/object-detail?schema_name=...&object_name=...` | 一次返回 §3 的基本信息、数据字典和数据画像所需的**已发布 JSON**对象行与全部字段行，以及独立的当前 DDL 发布摘要（有无对应 `table_definition` 行、`publish_id/job_id/loaded_at`）。只核对 DDL 当前标记、版本和对象身份，不读取或解析 `define_text`；DDL 异常不阻断有效的 JSON 详情。返回页面需要的字段极值、完整约束、索引和候选列组；不返回当前页面不用的 `json_sample_records` 或 `value_distribution`。 |
| `GET /api/data-assets/{source_id}/object-ddl?schema_name=...&object_name=...` | 用户在本次详情页首次打开上部“对象定义 SQL”或下部“样例数据”Tab 时，从**同一条**当前 `table_definition(define_type='ddl')` 行读取一次 `define_text`，在后端拆成 `definition_sql`、`sample_columns` 与 `sample_records`（最多 5 行），连同 DDL `publish_id/job_id/loaded_at` 和本次读取的 `json_publish_id` 一起返回。前端只在本次详情页停留期间按对象身份及 DDL `publish_id` 复用该响应：SQL Tab 只显示 `definition_sql`，样例 Tab 只显示 `sample_columns/sample_records`；不读取 JSON 画像的样例节点。 |

列表 `state` 取 `ready/not_published/inconsistent`；`ready` 时带 `json_publish={publish_id,job_id,published_at}`、`total/page/page_size/items`。详情分别给出 `json_publish`、`ddl_state`、`ddl_publish`、`profile`（§6 的表级字段，排除 `json_sample_records`）和 `columns`（§6 的字段级标量，排除 `value_distribution`，另附字段相关结构明细），不能把两类发布来源合成一个时间或 ID；字段数组按 `ordinal_position` 升序。DDL 接口返回 `{state, json_publish_id, ddl_publish, definition_sql, sample_state, sample_columns, sample_records}`：`sample_columns` 是样例表头；`sample_records` 只含最多 5 条记录对象，不包含 SQL；`definition_sql` 只含剥离样例块后的文本。前端按 Tab 分开显示，不把整个响应原样渲染到页面。`json_publish.published_at` 明确取该源当前成功的 `publish_info(step_name='json', is_current_publish=true).created_at`，按 UTC ISO 8601（六位小数、`Z` 结尾）返回，不取 `table_profile.loaded_at`；JSON 顶层 `generated_timestamp` 经库表同名列返回 UTC 六位小数、`Z` 结尾文本；各表 `loaded_at` 同为 UTC 六位小数、`Z` 结尾文本（doc 19.3）。列表与详情不把 JSON 当前发布等同于 `db` 或 DDL 当前发布。

`total` 是当前列表筛选后的对象数；无筛选条件时等于该源当前 JSON 发布的对象总数。列表标题旁按 §3.7 随筛选状态调整文案，不新增第二个计数接口或字段。列表“主键”状态只从 `table_profile.physical_constraints.primary_key` 投影为“有 / 无 / 未生成”，不能由字段名或候选唯一列组推断。候选接口沿用 JSON 当前发布校验，无当前发布时返回空候选和 `not_published`；本版候选集合不分页、不额外限条，但只返回简短对象身份，且必须基于**全体当前 JSON 对象**由服务端筛选，不能从列表当前页推导。

### 8.1.1 新接口的响应契约

新增接口统一使用 `snake_case` 字段名。`json_publish.published_at` 取当前成功 JSON 发布行的 `publish_info.created_at`，按 UTC ISO 8601（六位微秒、`Z` 结尾）返回；`loaded_at`、`generated_timestamp` 同为 UTC 六位微秒、`Z` 结尾文本；数值返回 JSON 数字，缺失值返回 `null`，明确的空集合返回 `[]`。四个接口的成功响应固定如下，表中省略的表级与字段级单值字段仍按 §6/§7.3 逐项返回，不允许只返回示意字段。

| 接口 | HTTP 200 响应字段 | 本版状态与空值 |
| --- | --- | --- |
| `objects` | `state, source_id, json_publish, total, page, page_size, items`；每项含 `schema_name, object_name, object_type, object_comment, table_category, column_count, total_rows, primary_key_state, generated_timestamp` | `primary_key_state` 为 `present/none/unknown`，分别显示“有 / 无 / 未生成”；无 JSON current 时 `state=not_published`、`json_publish=null`、`total=0`、`items=[]`；可检测到 JSON 当前态不一致时 `state=inconsistent`，同样令 `json_publish=null`、`total=0`、`items=[]`，`page/page_size` 回显已校验的请求值。`total` 在 `ready` 时为筛选后的数量。 |
| `object-options` | `state, source_id, json_publish, object_types, schemas, objects`；`objects` 每项含 `schema_name, object_name, object_type` | 无 JSON current 时 `state=not_published`、`json_publish=null`，三个候选数组均为空；可检测到当前态不一致时 `state=inconsistent`、`json_publish=null`，三个候选数组均为空；无匹配候选时仍为 `ready`，对应数组为空。一级类型按 `table/view/materialized_view` 固定顺序，Schema 与对象名按原始名称稳定排序。 |
| `object-detail` | `state, source_id, schema_name, object_name, json_publish, ddl_state, ddl_publish, profile, columns`；`profile` 返回 §6 的对象行字段，排除 `json_sample_records`；`columns` 返回 §6 的字段行字段，排除 `value_distribution`，并按下段增加字段相关明细 | 无 JSON current 时 `state=not_published`、`json_publish/profile/ddl_publish=null`、`ddl_state=not_published`、`columns=[]`；可检测到 JSON 当前态不一致时返回 HTTP 409 `profile_inconsistent`，没有 HTTP 200 的 `state=inconsistent` 或 `columns`；JSON 可用但 DDL 无对应行时 `ddl_state=not_published`，DDL 身份不匹配时 `ddl_state=incompatible`，DDL 有孤立或错版行时 `ddl_state=inconsistent`、`ddl_publish=null`。这三种 DDL 状态均不影响有效 JSON 内容。 |
| `object-ddl` | `state, json_publish_id, ddl_publish, definition_sql, sample_state, sample_columns, sample_records` | `state` 为 `ready/not_published/incompatible`；非 `ready` 时 `definition_sql=null`、`sample_state=null`、`sample_columns=[]`、`sample_records=[]`。`ready` 时 `sample_state=ready/no_sample_block/empty`，后二者的样例数组为空但 `definition_sql` 仍可显示。 |

字段相关明细固定为 `columns[].physical_constraints={primary_key_state,primary_key,foreign_keys,unique_constraints}`、`columns[].indexes`、`columns[].unique_column_sets`，由所属对象行的 JSONB 明细按 §3.3/§3.4 规则投影；每项保留原始完整名称与复合列组。`primary_key_state` 取 `present/none/unknown`：主键节点有值且命中当前字段时为 `present`，主键节点完整但当前字段未命中时为 `none`，节点缺失或 `table_profile=null` 时为 `unknown`；`primary_key` 仅在 `present` 时返回完整约束对象，其他情况为 `null`，由状态区分“无”与“未生成”。`foreign_keys`、`unique_constraints`、`indexes`、`unique_column_sets` **各自**在上游节点缺失时为 `null`，节点完整但当前字段未命中时为 `[]`；主键节点缺失不能清掉仍然完整的外键或唯一约束明细。`physical_constraints` 对象保留这四个键，即使各项均为 `unknown` 也不整体改成 `null`。对象详情仍返回表级完整约束与索引，方便显示对象级概况；字段投影只服务页面，不重复持久化。

```json

  "source_id": "<source_id>",
  "schema_name": "public",
  "object_name": "orders",
```

对象名称 `keyword` 在列表与候选接口中均作不区分大小写的子串匹配，`%`、`_` 等输入字符作为普通字符而非数据库通配符；对象详情仍按原始大小写精确匹配。列表或候选发现 JSON 当前态不一致时以 HTTP 200 返回 `state=inconsistent` 和空列表/候选，不返回部分数据；`object-detail` 发现 JSON 当前态不一致时返回 HTTP 409 `profile_inconsistent`，DDL 当前态不一致仅体现在其 `ddl_state=inconsistent`，不阻断 JSON 详情，也不在详情中解析 DDL 样例块。`object-ddl` 遇到 DDL 孤立或错版行、DDL 块解析失败时分别返回 HTTP 409 `definition_inconsistent`、`definition_invalid`。这些 409 沿用 `backend/api/errors.py` 的错误响应体 `{ "code": "...", "message": "..." }`，仅增加相应错误码；若需补充非敏感信息，可使用现有可选的 `details` 字段，不返回 DDL 原文或样例值。不存在的数据源或当前 JSON 中确实不存在的对象返回 HTTP 404 `not_found`；请求参数非法沿用 HTTP 422 `invalid_request`；平台库不可用沿用 HTTP 503 `platform_unavailable`。`object-ddl` 只服务当前 JSON 中存在的对象，DDL 缺失才返回 HTTP 200 `state=not_published`，不能把对象不存在误当成 DDL 未发布。

### 8.2 查询一致性与空状态

对象列表和详情先核对该源 `publish_info(step_name='json', is_current_publish=true, status='success')`，再读同源的 `table_profile`、`table_column_profile`；对象行的 `publish_id/job_id` 必须与 JSON 当前发布一致，每条字段行的 `publish_id` 必须与所属对象行相同，字段行数与 `column_count` 一致。能检测到的当前态错误包括：已有 JSON current 却没有任何对象行、对象或字段版本不符、某对象字段行数不符、同源同步骤出现多个 current；此时不能静默显示旧画像。四个读取接口先做源级检查：当前成功 JSON 发布标记至多一条；有标记时，该源至少有一条画像对象行。若已有 current 却没有任何对象行，列表和候选返回 `state=inconsistent` 及 §8.1.1 规定的空集合，详情与 `object-ddl` 返回 `409 profile_inconsistent`，均不得按对象缺失返回 404。详情对**本次读取已检测到的**对象或字段版本错误、字段数不符等当前态错误也返回 `409 profile_inconsistent`；只有源级当前态有效、且未检测到其他不一致、目标对象确实不在当前对象行集合中时才返回 404。**本版没有保存发布时的预期对象总数**：如果仅有部分对象行连同其字段行在发布后丢失，而剩余行的版本和字段数都正确，读取接口无法从现有当前态区分“对象原本不在本批”与“发布后丢失”，不得宣称能检测这种情形；本版不为此扩展共享 `publish_info` 或新增第三张画像表。数据源已登记但禁用时允许查看既有已发布画像，与现有只读资产页一致；不存在的数据源返回 404。

对象详情仅从 `table_definition` 读取**同身份**的 DDL 摘要，不解析 `define_text`。先核对该源 `ddl` 当前成功发布标记与该行 `publish_id`：当前标记缺失且无对应行，或有当前标记但无对应行时，`ddl_state=not_published`、`ddl_publish=null`，页面两个 DDL Tab 显示“暂无已发布 DDL 数据”；当前标记缺失却有孤立行，或行的 `publish_id` 与当前标记不符时，`ddl_state=inconsistent`、`ddl_publish=null`，两个 DDL Tab 显示“已发布 DDL 状态不一致，暂无法展示”，不返回旧正文。版本有效后，若 DDL 行的 `db_name` 或 `object_type` 与当前 JSON 对象行不同，`ddl_state=incompatible`，两个 DDL Tab 显示“当前已发布 DDL 与 JSON 对象身份不一致，暂无法展示”，不返回 SQL 或样例。以上 DDL 状态都不阻断 JSON 基本信息、字典和画像；`object-ddl` 请求遇到孤立或错版行时才返回 `409 definition_inconsistent`。`object-ddl` 从同一当前 DDL 行的 `define_text` 一次派生 SQL 与样例，响应标注实际 `ddl_publish`；页面在本次详情页停留期间复用该响应，让两处 Tab 显示同一版本。刷新页面或重新进入对象详情后重新请求 JSON 详情，并在首次打开 DDL Tab 时重新请求当前 DDL；停留期间不轮询，也不自动感知他人的重新发布，页面保留 JSON 与 DDL 各自的生成或发布时间供用户判断新旧。

DDL 样例块只解码当前 `/* SAMPLED_RECORDS ... */` 格式：只允许末尾一个完整块，顶层 `object_name` 必须等于已发布 DDL 行的 `schema_name + '.' + object_name`（例如块内 `public.orders` 对应行内 `schema_name='public'`、`object_name='orders'`），顶层 `object_type` 必须等于该行 `object_type`；`records` 必须是记录对象数组。每条记录的所有键均为真实字段名，字段名为 `data` 时也不得当作包装层。各记录的字段键集合须相同，列顺序取首条记录的键顺序，值保留原貌，最多截取 5 行。标记检测还须识别独立的旧 `/* SAMPLE_RECORDS ... */` 注释块，但**不解码、不展示**旧记录结构；已发布正文出现旧标记、块边界不完整或多个样例块时，`object-ddl` 返回受控 `409 definition_invalid`，SQL 与样例均不展示。旧 `{label, data}` 包装只随旧标记一起拒绝；当前块的真实字段恰好名为 `label`、`data` 时不能仅凭键名判成旧包装。检测旧标记不能退化为搜索正文中的任意同名字串。DDL 接口的 `state` 为 `ready/not_published/incompatible`；有 DDL 但无样例块、明确 `records=[]` 时，`sample_state` 分别为 `no_sample_block`、`empty`，SQL 仍可展示。DDL 行解析失败不回退到工作区或 `json_sample_records`。

实施本稿时须修复两类当前代码缺陷。第一类是 JSON 注释块的 SQL 分隔符：`OutputFormatter._build_sample_records_block()` 与 `_build_view_object_metadata_block()` 共用一个序列化辅助函数，先 `json.dumps()`，再将**整个序列化结果中的每个 `*`** 写成 JSON 等价的 `\u002a`，最后包入 SQL 块注释；`json.loads` 后必须还原原值。整体转义 `*` 后，正文不含裸 `*`，因而既不会出现 `/*`，也不会出现 `*/`，避免 SQL 注释提前结束或嵌套，以及 `}*/` 使现有非贪婪正则提前截断。不得改回按 `*/`、`/*` 先后做字符串替换：`*/*`、`/*/*`、`100%*/*` 等相邻序列会在两趟替换时静默改值；单趟按序列替换也可能在相邻边界重新拼出危险标记。**仅把 `/*` 的斜杠写成 `\/` 同样不够**，因为 `\/*` 仍含连续的 `/*`。普通表不生成 `OBJECT_METADATA` 块。第二类是记录结构：`DDLLoader._parse_sample_records()` 和 `OutputFormatter._extract_sample_records_from_ddl()` 都只按当前直接记录结构读取，不再凭字段名 `data` 拆包装或跳过整条记录。JSON 生成优先回读同作业 DDL 样例块；本次修复 `data` 拆包，但不改变现有“数字样式字符串转数字”的行为。

当前 DDL 回读入口还须将独立的旧 `/* SAMPLE_RECORDS ... */` 标记判为受控输入错误，不能在移除 `SAMPLE_BLOCK_PATTERN` 的旧格式解码分支后把它当作“没有样例块”并继续发布；依赖 DDL 的 JSON 步骤也不能以无块回退掩盖该错误。展示层对先前已发布的旧正文仍检测该标记并返回 `409 definition_invalid`，不解析旧包装，也不泄露旧块内容。DDL 发布的 `read_ddl_definitions()` 会调用 `DDLLoader.parse_content()`，因此必须先保证该解析链能接受当前生成器写出的含 `data` 字段、样例值含 `/*` 或 `}*/`、以及 View/MV 对象或字段注释含这些序列的文件，再验收 Web SQL/样例展示。生成、DDL/JSON 步骤和 Web 展示复用当前格式的块边界识别与 JSON 解码规则；展示层额外校验“末尾唯一块”。旧标记仅检测并拒绝，不保留旧格式解码或包装分支。

列表、候选、详情和 DDL 四个新增读取接口各自在**一笔只读 `REPEATABLE READ` 事务**内完成本次所需的多次查询。进入新建的 `platform_session()` 后，在任何 ORM 查询或 `session.get()` 之前，首次取得连接时一次调用 `session.connection(execution_options={"isolation_level": "REPEATABLE READ", "postgresql_readonly": True})`；本项目使用的 PostgreSQL 方言支持这两个连接特性，不再另发 `SET TRANSACTION READ ONLY`。两项设置均须早于首次数据查询。已执行查询、Session 已持有连接时，再调用 **`Session.connection(execution_options=...)`** 会发出 `SAWarning` 并忽略新选项，可能继续使用 `READ COMMITTED`；若直接对已开始事务的 **`Connection.execution_options(isolation_level=...)`** 修改，则抛 `InvalidRequestError`。这是两条不同 API 路径，不能把一种失败模式写成另一种。实现和回归测试仍须在同一笔实际查询事务内分别执行 `SHOW transaction_isolation` 与 `SHOW transaction_read_only`，断言结果为 `repeatable read`、`on`，防止连接特性未按预期生效；不能只检查代码调用顺序。这样同一响应里的 current 标记、对象行、字段行、DDL 摘要，以及列表的 `total` 与当前页都来自同一数据库快照，避免发布替换期间拼出新旧内容。不改 `platform_session()` 的全局隔离级别，也不要求不同 HTTP 请求之间共享快照。DDL 的 SQL 与样例仍由同一次 `object-ddl` 请求、同一行的同一份 `define_text` 产生；其响应同时返回本次快照的 `json_publish_id`，前端发现与正在显示的详情版本不同时先刷新详情，不继续展示旧详情与新 DDL 的组合。

### 8.4 本版访问口径

按本版决定，**不增加鉴权或按用户/数据源过滤**：请求指向已登记数据源和已发布对象时，接口按上述响应契约返回该对象的全部设计内容，包括 DDL SQL、最多 5 条真实样例和画像字段极值。不要增加登录、权限表、401/403 分支，也不修改现有 CORS 或 `frontend/src/api/http.ts` 的凭据处理。列表仍只返回摘要，详情和 DDL 接口分别返回各自约定的完整内容；“默认返回全部”指不做用户权限裁剪，不是把所有表字段塞进每一个列表响应。doc 16 §1 与验收 12 中旧的“未来 DDL 读取须先鉴权”前置要求已同步修订；本版接口以本节为准。

## 9. 本稿的页面、表结构、加载与 API 验收口径

1. 对象详情页标题始终标明对象身份，标题下的来源说明行显示当前 JSON 画像发布时间或明确的未发布/不一致状态；上部为“基本信息／对象定义 SQL”两个 Tab，默认基本信息；下部为“数据字典／数据画像／样例数据”三个 Tab，默认数据字典。上部基本信息仍包含 12 项：Schema 并入对象名，分类置信度并入表分类，并展示画像生成时间；发布时间不计入 12 项，也不以生成时间替代。不单列注释来源、分类来源和字段数。主键字段、外键数量、索引数量和约束数按已发布 JSON 的结构事实显示；两组 Tab 独立切换。
2. 数据字典与数据画像的字段表按 `ordinal_position` 排列。物理约束、外键目标、字段参与的索引、候选列组、语义判断依据和统计详情直接显示在对应字段表列中；画像表的约束与索引列标注为结构参照。字段级主键状态区分“有 / 无 / 未生成”，主键节点缺失不隐藏同字段已知的外键或唯一约束。列多时横向滚动，不用隐藏字段详情的交互。上部对象定义 SQL 展示生成的定义及索引语句，不宣称覆盖源库所有约束。
3. `orders.order_id` 不会因候选唯一键或抽样唯一度 `1.0` 被标为真实主键；`screenings.screening_id` 显示真实主键；`mv_category_sales` 明确标为物化视图。
4. LLM 开启、关闭、分类为 `unknown` 和 `table_profile=null` 时，基本信息分别显示实际分类（含置信度）或“未生成”，不单列分类来源，也不制造分类或约束事实。
5. 对象定义 SQL 与样例数据按 `source_id + schema_name + object_name + define_type='ddl'` 读取同一条 `table_definition` 当前行；SQL Tab 展示只去掉末尾当前 `SAMPLED_RECORDS` 块（含块前尾部空行）的 `define_text`，绝不显示样例块；视图或物化视图的 `OBJECT_METADATA` 块保留在 SQL 原文中。样例 Tab 只解析当前直接记录数组，按记录表格最多显示 5 行，绝不显示 SQL 定义。字段名 `data` 仍按真实字段展示；样例值含 `/*` 或 `}*/` 时，新生成的 DDL 能完成发布与展示，解析后保留原值。独立旧 `SAMPLE_RECORDS` 块在发布时受控拒绝；已发布旧正文在 Web 返回 `409 definition_invalid`，SQL 与样例均不展示，不把旧块当作“无样例块”。缺行、缺块、空记录和解析异常各有明确状态，均不回退工作区或 JSON 样例节点。
6. 总行数、画像抽样行数和 DDL 样例行数不混用；缺失统计不显示为零；样例行只在样例 Tab 展示，具体值分布不展示。DDL 与 JSON 来源时间可能不同，页面分别标明，不把 DDL 样例行称为画像样本。
7. 抽样提醒紧贴数据画像字段表上方；有实际样本时，提醒中的数量取当前已发布对象的 `profiling.sample_count`，不取配置上限 1000 或 DDL 样例行数 5。0 条及缺失抽样行数分别展示明确文案，不能暗示源表为空或伪造样本数。
8. 平台库按 §6 建立对象级和字段级两张当前态表，不设 CHECK 约束；JSON 中常用标量指标可直接按类型读取，复杂明细不丢失。字段行带与所属对象行相同的 `publish_id`；`table_profile=null`、明确空数组与缺失节点入库后仍可区分；样例数据 Tab 不改读 `json_sample_records`。
9. Web 发布可选择当前作业的 `json`，从 `output/<source_id>/<job_id>/json/` 的清单和对象文件整批加载到平台库；连接仅使用 `PLATFORM_DB_*`，不解密或连接源库。发布后对象行的 `publish_id/job_id` 与 `publish_info(json)` 一致，字段行的 `publish_id` 与对象行一致；页面读取当前发布行而非工作区文件。
10. 缺件、多件、混库、v3/身份/字段类型错误或采集步骤重跑时不产生部分 JSON 当前态；失败发布保留旧成功画像。重复发布替换该源全部对象和字段；删除数据源后两表没有该源行。受管 JSON 样例值和取值分布不会出现在发布错误响应、普通日志或对象列表 API 中。
11. 对象列表与详情只读 JSON 当前发布；详情字段有序，JSON 与 DDL 分别标注来源。DDL 孤立、错版或样例块解析失败不阻断有效 JSON 详情；孤立或错版行在详情中表示为 `ddl_state=inconsistent`，请求 `object-ddl` 时才返回相应 409。单个 `object-ddl` 请求从同一条当前 DDL 行拆出 `definition_sql` 与最多 5 条 `sample_records`，前端在本次详情页停留期间复用后分别显示在对应 Tab；SQL 展示不含样例块，样例展示不含 SQL，也不回退到 JSON 样例节点。已发布内容不一致时不显示拼接数据；但在不保存预期对象总数的本版设计下，不宣称能识别部分对象行连同字段行在发布后丢失的情况。
12. 新对象读取接口按本版约定无需鉴权，按请求返回完整设计内容；既有资产目录/整库画像 API 的路径、字段和 `db` 当前发布语义保持不变。实施新增 `json` 发布响应枚举后，既有 db/ddl 预检和发布回归仍通过。
13. 页面按 §3.7 对照 13～17 号 HTML/PNG 与 14.1 号展开态 PNG：13 号对象列表支持对象类型、Schema 和名称筛选及服务端分页；只在 `state=ready` 时标题计数显示当前源对象总数或筛选后的结果数。`not_published` 与 `inconsistent` 在列表和级联候选各显示 §3.7 的专用文案，均不显示“共 0 个对象”。14～17 共用同一个详情页和三级级联搜索栏，类型变更会更新 Schema 与对象候选，Schema 变更会更新对象候选，名称下拉搜索只筛候选，选定对象并点“搜索”后才切换详情。切换对象重置两组 Tab 与字段页码，且不得显示前一对象缓存的 SQL/样例；同一对象的两组 Tab 独立，字典和画像各在前端按每页 10 条分页。刷新页面或重新进入详情会重新取当前快照，停留期间不自动刷新，页面显示相应时间信息。候选来自当前 JSON 发布的全体对象，不从某一页列表推导；样例表最多 5 条且不分页。
14. JSON 发布加载器对任一对象的 `column_profiles={}` 整批拒绝，不写入零字段画像；同时拒绝字段序号为 0、重复序号、约束或索引引用不存在字段及外键来源/目标列数不等的输入；字段序号有空档和外键目标对象未采集则允许。受管 MD 的 `read_managed_json_input()` 调用和摘要返回保持不变。
15. JSON 发布预检后的源登记版本变化或步骤重跑均不能覆盖旧当前画像；前者按“数据源登记信息已变化，请重新发布”受控失败。读取接口以各自的只读 `REPEATABLE READ` 事务保证同一响应内的发布标记、行与列表总数一致；在同一查询事务内实测 `transaction_isolation=repeatable read`、`transaction_read_only=on`，不能只依赖调用顺序。已有 JSON current 但对象行总数为 0 时，列表/候选返回 `inconsistent` 空集合，详情/DDL 返回 `409 profile_inconsistent`；字段行版本不符即判当前内容不一致。详情的 `not_published`、`409 profile_inconsistent` 及仅 DDL 接口报错时均保留路由对象标题、来源说明与级联搜索栏，候选按独立接口状态显示；`not_published` 时两组 Tab 区域显示空态而非空字段表，`profile_inconsistent` 时清除旧缓存、不显示画像与 DDL 内容，仅 DDL 接口报错时仍展示有效 JSON 画像。
16. 对象详情中 JSON 与 DDL 的 `db_name/object_type` 不一致时，JSON 内容照常展示，SQL 和样例两个 Tab 明确显示身份不兼容；无 DDL 时显示未发布，DDL 有孤立或错版行时显示状态不一致，三种状态不可混淆。对象接口的成功、空状态和 409 错误按 §8.1.1；当前 `SAMPLED_RECORDS` 中各记录字段键集合不一致按解析失败处理，不静默漏列。生成器、DDL 发布解析器、依赖 DDL 的 JSON 步骤和 Web 展示对字段名 `data`、样例值及 View/MV 对象或字段注释中的 `/*`、`*/`、`*/*`、`/*/*`、`100%*/*` 均完成全链路回归；两个块的序列化正文不得含裸 `/*`/`*/`，JSON 解码后保持原值。

本稿确认展示内容、来源口径、JSON 画像目标表结构、Web 发布到平台库的加载路径及对象读取 API 合约。`table_definition` 现有表用于 DDL 定义与样例块；页面具体布局由专门的 UI 设计文档决定。MD 与同名 JSON 加载到 Milvus 的 Web 发布设计归 doc 19.3。

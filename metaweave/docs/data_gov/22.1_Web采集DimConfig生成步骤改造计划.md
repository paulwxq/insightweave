# 22.1 Web采集DimConfig生成步骤改造计划

状态：**已实施**（代码与测试已完成，全量 pytest 2200 passed / 2 skipped；前端人工清单 F01–F02 待浏览器验收，F03 构建已通过，见 §10）。

本篇在 Web「数据采集与画像」中激活 `--generate-dim-config` 步骤（后台步骤名 `dim_config`）：页面可勾选执行，依赖**同一作业已成功的 JSON 产物**（json 步骤行 success + 受管 json 目录至少 1 个除 `manifest.json` 外的普通画像 `.json` 文件），产物写入 `output/<source_id>/<job_id>/dim_config/dim_tables.yaml`。生成逻辑复用 CLI 同款 `DimTableConfigGenerator`，不经过 CLI 包装层。

与 domain（[doc 21.1](21.1_Web采集Domain生成步骤与数据源描述编辑改造计划.md)）相比，本步骤**无 LLM、无描述弹窗、无 `db_desc` 列、无数据源描述同步、无平台库迁移**，是 doc 21.1 模式的裁剪版。步骤服务沿用 [doc 19.1](19.1_Web受管JSON与MD采集衔接设计.md) 建立的受管准备链模式，最近范本为 `domain_step_service.py`；作业汇总与发布准入沿用 [doc 20.1](20.1_表结构发布选项统一与空描述字段处理改造计划.md) §11.2 口径，本篇不改发布侧代码。

## 2. 目标与范围

### 2.1 需求到设计映射

| 需求 | 落点 |
|---|---|
| 1. 页面释放 `--generate-dim-config` 勾选；重跑时后端检查同作业 json 目录有 json 文件；新建作业须同时勾选 ddl/json 才释放 | §8.2（前端可用性）、§5.2（后端强制：json 行 success + 目录 ≥1 个除 `manifest.json` 外的普通画像 `.json`） |
| 2. 在当前脚本基础上复用函数实现 Web 执行（类似 `--generate-domains` 的接法） | §5：复用 `DimTableConfigGenerator`、`clean_top_level_files`、`set_operation_step`、`resolve_json_output_dir`，不调用 `execute_generate_dim_config` 的 CLI 包装层 |
| 3. 不过度设计；不处理脚本与 WebUI 执行的冲突，脚本将退化 | §2.2、§13.1 |
| 4. 参考 21.1 的结构与模式 | 全篇 |

### 2.2 明确不做

- **不改 CLI、不为 CLI 可用性背书**：`metaweave metadata --generate-dim-config` 保持现状（写 `output/dim_config/dim_tables.yaml`，非受管路径）；共享组件 `DimTableConfigGenerator` 只增加一个可选参数 `json_files`，缺省保持原扫描方式，CLI 当前行为不变（§5.3），但用户已明确脚本将退化，本篇不为"CLI 继续可用"新增任何保证或测试（§13.1）。
- **不做前端就绪接口**：不新增"json 就绪"查询接口，前端信号只到"步骤已登记/本次已选"粒度（§8.2），文件级校验由后端准备链强制。
- **不写 manifest.json**：dim_config 目录只落 `dim_tables.yaml`（§5.3）。
- **不做描述弹窗、无 `db_desc`、无平台库迁移**：本步骤没有任何需要落库的快照字段（§4）。
- **不做 json 变更复查**：不引入 md 式的运行标识（`updated_at`）结束复查（§13.2，与 doc 21.1 §13.2 同决策）。
- **不做读取侧 `O_NOFOLLOW` 加固**：生成器只读 `table_category` 与三段标识标量，内容不进入 LLM 提示词；准备链枚举跳过非常规文件即可（§13.3）。
- **不做 embedding_col 编辑与 dim_value 加载**：产物 `embedding_col` 恒 null，人工填写与 `rag_load --type dim_value` 的 Web 化属后续文档。
- **不改发布侧代码**：发布准入与候选列表按既有汇总口径自动包含 `dim_config` 行（§6.4）；dim_config 没有对应的发布勾选组。
- **准备链失败与同请求阻断暂不落库**：与 json、md、domain 的现状相同（§5.5，记在 [100 备忘录](100_备忘录.md) 第 3 条，本篇不实施）。
- **不加载主配置快照**：生成器不消费 config，输入/输出路径均由受管 resolver 决定（§5.2，与 md/domain 的一个有意差异）。

## 3. 当前代码现状（设计依据）

- **CLI 已实现完整生成链路**：`metaweave/core/metadata/execution.py:308` `execute_generate_dim_config` → `metaweave/core/dim_value/config_generator.py` `DimTableConfigGenerator(json_dir, output_path).generate()`（`config_generator.py:26-61`）：扫描 json 目录 `*.json`，筛选 `table_profile.table_category == 'dim'`，按 database 分组写出 `dim_tables.yaml`，`embedding_col` 恒 null；**零 dim 表时写空 `databases: {}` 骨架，不报错**（即使全部文件不可解析也同样产出空骨架——Web 侧由 §5.3 可读性底线拦截，审核修订 7）。纯 file-only：不连数据库、不调 LLM。
- **生成器自行重扫目录且不检查文件类型（本设计的关键约束）**：`_scan_dim_tables`（`config_generator.py:71`）对 `json_dir` 重新 `glob("*.json")` 并逐个 `load_json`，不做符号链接/FIFO 检查；`load_json`（`file_utils.py:132-152`）是普通 `open()`——**跟随符号链接（可读到目录外目标）、对 FIFO 在 `open` 处阻塞**。因此 Web 不能把"准备链筛过一遍的目录"交给生成器重扫（跳过只在就绪计数生效，生成照样读链接与 FIFO）；必须由准备链筛出普通文件列表、显式传给生成器（§5.2、§5.3）。
- **生成器构造无副作用**：`__init__` 只存两个路径（`config_generator.py:22-24`），不存在 domain 的"先清理后构造"约束（其 `__init__` 立即读旧 yaml）；本篇仍按"清理 → 构造 → 生成"执行，与 ddl/md/domain 同序。
- **清理语义与写盘的组合缺口（本设计的关键约束之二）**：`clean_top_level_files`（`file_utils.py:66-69`）只对 `is_file()` 为真的顶层项 `unlink`——**悬空符号链接（目标尚不存在的 symlink）与 FIFO/套接字等非正规文件都因 `is_file()` 为 False 而幸存**；`_write_yaml` 的 `write_text`（`config_generator.py:162`）跟随符号链接，会顺着幸存的悬空链接把 `dim_tables.yaml` 写到目录外；若写入路径是 FIFO，`open(..., "w")` 会**阻塞到出现读取端**；而核验的"拒符号链接"判定发生在写入**之后**，拦不住越界写，也拦不住阻塞。因此生成必须落 `mkstemp` 创建的唯一临时普通文件、核验通过后再 `os.replace` 到最终路径（§5.3）。
- **Web 采集步骤白名单与顺序**：`backend/jobs/collection_run.py:27` `_SUPPORTED_STEPS = (db, ddl, json, md, domain)`；`:57-68` `_ensure_managed_step_order`（偏序 ddl→json→md→domain，连续 `_move_after`"后继移到锚点紧后"）；`:87-104` `_blocked_by_same_request_upstream`（本次请求内上游 failed → 后继不执行、不登记）。**注意（审核修订 3）**：连续 `_move_after` 在链式依赖下与稳定拓扑排序等价，但 dim_config 引入第一个**分支**依赖（json 同时是 md 与 dim_config 的锚点）后即不保相对序——传入 `[md, dim_config, json]` 会产出 `[json, dim_config, md]`（md 被 `insert(锚点紧后)` 越过），与"不引入顺序约束的步对保持传入相对序"的意图矛盾；本篇因此把排序实现替换为拓扑排序（每轮选当前可执行且传入顺序最靠前者，§6.2）。
- **步骤服务最近范本**：`backend/data_sources/domain_step_service.py`——入口校验段 → 平台库读取段（源校验、工作区归属、上游步骤行）→ 本地文件段（目录枚举与 resolver）→ 会话 2 锁下 `start_step` → 清理 + 生成 → 核验 → 锁下 `finish_step`。dim_config 是其裁剪：去掉描述解析与两表同步、去掉 LLM 预检、去掉主配置快照构造（生成器不需要 config）。
- **json 受管目录含非画像文件 `manifest.json`（本设计的关键约束之三，审核修订 6）**：json 步骤成功后用 `atomic_write_json` 在同目录落清单（`json_step_service.py:61` `JSON_MANIFEST_NAME = "manifest.json"`、`:370` 写入），它是**普通文件**，会被朴素的 `*.json` 枚举命中；`read_managed_json_input` 按名排除它（`:106`）。dim_config 的目录枚举同样必须按名排除（§5.2），否则"画像文件全部缺失、只剩清单"会被误判为就绪——生成器跳过清单内容（无 `table_profile`）、产出 `databases: {}` 并记成功（审核以"目录内仅有 manifest.json"复现确认）。清单内容本身不校验（不比对 `files` 与实际文件集合），不在本篇范围。
- **日志零新增**：`OPERATION_STEP_MAP` 已有 `"generate-dim-config": "dim_config"`（`execution.py:37`），script profile 已有 `dim_config_filter`（`allowed_steps: ['dim_config']`）与 `dim_config_file`（`logs/script/dim_config.log`，`configs/logging.yaml:40/138`）。Web 步骤名取 `dim_config` 后，只需在 `OPERATION_STEP_MAP` 增 `"dim_config": "dim_config"`（与 doc 21.1 的 domain 同款，只进 map 不进 `METADATA_OPERATIONS`），`configs/logging.yaml` 零改动；`set_operation_step("dim_config")` 不抛 `KeyError`。
- **页面已有占位**：`frontend/src/views/CreateCollectionJobView.vue:39` 已有 `{ id: 'dim-config', label: '--generate-dim-config', enabled: false }`；`:95-103` 已有 domain 的动态可用性函数模式（`isStepEnabled` 按 id 分流）可直接扩展；`:206-224` `storedSelection`、`:260-265` 失去可用性自动清除、`:249-258` `selectAvailable` 全选快照，均为可复用机制。
- **任务表结构**：`job_info` 主键 `(job_id, step_name)`，step_name 无枚举约束，新增 `dim_config` 行无冲突；**不需要任何新列**（无描述快照）。
- **错误映射范本**：`backend/api/errors.py:200-211` `DomainPreparationError`（`PlatformUnavailableError` 子类）按 MRO 先于 `platform_unavailable` 命中、返回专用 503——本篇 `DimConfigPreparationError` 完全同款。编排层对 `DbStepConfigError` / `PlatformUnavailableError` 的"results 为空整体抛、已有结果计入 failed"分流（`collection_run.py:192-233`）不变。
- **作业汇总与发布**：`rollup_job_status` 汇总口径不变，dim_config 行自动参与；采集页「下一步发布」与发布候选列表按 `job_status === 'success'` 过滤，无需改代码。
- **CLI 产物路径解析与 Web 无关**：`resolve_dim_tables_yaml_path`（`file_utils.py:418`）的三级回退（`--dim-config` > `loaders.dim_loader.config_file` > 缺省）只服务 CLI 与 dim_value_loader；Web 产物路径由受管 resolver 决定（§5.4），不读该配置。

## 5. dim_config 步骤服务

新增 `backend/data_sources/dim_config_step_service.py`，对外暴露：

```python
DIM_CONFIG_STEP_NAME = "dim_config"
JSON_STEP_FOR_DIM_CONFIG = "json"
DIM_CONFIG_ARTIFACT_NAME = "dim_tables.yaml"
JSON_NOT_READY = "同一作业的 JSON 产物未就绪；请先执行 JSON 或指定已有 job_id"

class DimConfigPreparationError(PlatformUnavailableError):
    """Dim Config 准备阶段故障（本地文件段的非受控异常），doc 21.1 §5.2 同款。"""

def run_dim_config_step(config_path, source_id, job_id=None) -> dict:
    ...
```

- `config_path` 参数保留在签名中（与 db/ddl/json/md/domain 五服务一致，编排层统一传参），但本服务**不加载主配置快照**——`DimTableConfigGenerator` 只消费 `json_dir` 与 `output_path`，两者都由受管 resolver 给出；入口校验段因此只含 UUID 规范化与平台设置加载。这是与 md/domain 的有意差异，写入本节以避免"漏加载"误报。
- `job_id` 必填（与 md/domain 相同："新作业单选 dim_config 没有任何工作区可用"）。入口处 `job_id is None` 立刻抛 `DbStepConfigError(JSON_NOT_READY)`，不写行。

失败分类与 doc 21.1 §5.2 完全同构：依赖或配置类 → `DbStepConfigError`（源禁用 → `SourceDisabledError`）；平台库连接或读取异常 → 返回「平台库连接或读取失败（{类型}）」失败结果；本地文件段非 `ValueError` → `DimConfigPreparationError`（`PlatformUnavailableError` 子类，API 映射 503 `dim_config_preparation_error`）。三类都在 `start_step` 之前返回，不写 dim_config 行。

- 日志：**`configs/logging.yaml` 零改动**——script profile 的 `dim_config_filter`/`dim_config_file` 按 `allowed_steps: ['dim_config']` 过滤，Web 步骤名相同即复用（script 场景写 `logs/script/dim_config.log`）；API 进程不写该文件，请求内记录归 `logs/backend/metaweave.log`（无请求上下文回落 `logs/backend/platform.log`），与 domain 同口径。

### 5.2 准备链与依赖判定

按段执行，不得把平台库不可用归入配置错误，也不得把本地文件错误归入平台库故障：

- **入口校验段**：`normalize_source_id` 两级 UUID 规范化（`ValueError` → `DbStepConfigError`）；`load_platform_settings_from_env`（`ValueError` → `DbStepConfigError`）。不加载主配置（见 §5 开头说明）。
- **平台库读取段**（会话 1，无凭据，只读）：源校验四件（存在、`db_type == 'postgresql'`、连接字段完整、`is_active`，源禁用抛 `SourceDisabledError`）；`assert_workspace_owner` 的两类异常（`WorkspaceMissingError` / `WorkspaceSourceMismatchError`）单独捕获转 `DbStepConfigError(str(exc))`；**json 步骤行存在且 `last_status == success`**，否则抛 `DbStepConfigError(JSON_NOT_READY)`。段外层 `except DbStepConfigError: raise`、`except ValueError: 转 DbStepConfigError`、`except Exception` → 返回 `_failure(started, f"平台库连接或读取失败（{type(exc).__name__}）")`（不带 `job_id`、不写行），与 md/domain 相同。
- **本地文件段**（不依赖数据库连接）：
  1. `resolve_json_output_dir(source_uuid, job_uuid)` 并枚举 `*.json`：**排除 `JSON_MANIFEST_NAME`（`"manifest.json"`，从 `backend.data_sources.json_step_service` 导入常量，不另写字面量；审核修订 6）**——json 步骤成功后会在同目录落清单文件（`json_step_service.py:370`），它是普通文件但不是画像产物；不排除时"画像全部缺失、只剩清单"会被误判为就绪（生成器跳过清单内容、产出 `databases: {}` 并记成功，审核以"目录内仅有 manifest.json"复现确认）。**跳过非常规文件（符号链接/FIFO）并告警**，筛出排序后的普通画像 `.json` 列表 `json_files`。该列表一材两用——**既做就绪判定，也做生成输入**（§5.3 原样传给生成器，生成阶段不再 glob 目录）：列表为空（含目录不存在、目录为空、全部非常规、**仅剩清单**）→ 抛 `DbStepConfigError(JSON_NOT_READY)`。**不调用 `read_managed_json_input`**——那是 md 的严格解析粒度，dim_config 只要求"目录里有画像 json 文件"（需求粒度），清单内容也不校验（不比对 `files` 与实际文件集合，§13 不做项同款）；列表内个别坏文件由生成器跳过（`config_generator.py:80-82`），不整步失败。
  2. `resolve_dim_config_output_dir(source_uuid, job_uuid)` 解析产物目录（§5.4）。不清理、不写入，不构造生成器。
  - 受控 `ValueError`（resolver 的符号链接/越界/非对象节点）→ `DbStepConfigError(str(exc))`；其余异常（`OSError`/`PermissionError`/未预期程序错误）→ 记录「阶段 + 异常类型」（不带 `exc_info`、不写异常原文，doc 15 §8 脱敏要求）后抛 `DimConfigPreparationError(f"Dim Config 准备阶段故障（{阶段}：{类型}）")`，阶段取值：`json 目录枚举` / `dim_config 目录解析`。
- 同请求里 json 已经失败时不会进入这里：编排层先按 §6 阻断，本函数不被调用。

会话 2（锁下；只有准备链已通过才进入）：`lock_db_source_row` 取源行锁（返回 `None` → 抛 `DbStepConfigError("未找到指定 source_id 的数据源")`，编排层转 404）→ 复查 json 步骤行仍为 success（否则抛 `DbStepConfigError(JSON_NOT_READY)`）→ `start_step(session, job_uuid, source_uuid, DIM_CONFIG_STEP_NAME)`（**不传 `db_desc`**，仓储零改动；其末尾唯一一次 commit 提交 running 行）。`StepAlreadyRunningError` → 返回带 `job_id` 的 failed 结果，行保持 running（对齐 md/domain）。

### 5.3 生成与核验

- **清理 → 构造 → 生成（落临时文件）**：`clean_top_level_files(dim_config_dir)`（"每次完整集合"，与 ddl/md/domain 同款）→ `DimTableConfigGenerator(json_dir=json_dir, output_path=tmp_path, json_files=json_files)` → `result = generator.generate()`。其中 `tmp_path` 由 **`tempfile.mkstemp(dir=dim_config_dir, prefix=".dim_tables.", suffix=".tmp")`** 创建（返回的 fd 立即 `os.close`）：唯一文件名 + `O_CREAT|O_EXCL` 保证创建时刻就是**新建的普通文件**——预置的同名 FIFO/符号链接/套接字根本不会被选中作为写入路径（固定名方案会在 FIFO 上阻塞，§13.8）；隐藏文件名即使泄漏也会被下一次 `clean_top_level_files` 清掉。
- **临时文件 + `os.replace` 落盘（审核修订 2/4，§13.8）**：生成器**不直接写最终路径**。`os.replace` 前对 `tmp_path` 做一次 `os.chmod(tmp_path, 0o644)`（`mkstemp` 产物为 0600，与其他步骤产物的默认权限对齐）；核验通过才 `os.replace(tmp_path, dim_config_dir / DIM_CONFIG_ARTIFACT_NAME)`——`os.replace` 替换的是最终路径上的链接本身、**绝不跟随**，且同目录同文件系统为原子操作；核验失败或生成异常时 `tmp_path.unlink(missing_ok=True)` 清理（**所有失败路径都清理**：生成异常、核验失败、状态写回失败）。这样即使 `dim_tables.yaml` 是幸存的悬空符号链接，越界写也不会发生（原设计中它会把产物写到链接目标处，事后核验拦不住）。`DimTableConfigGenerator` 无需为此改动（`output_path` 指到临时文件即可）。
- **生成器增加可选参数 `json_files: list[Path] | None = None`**（审核修订 1，§13.3）：传入时 `_scan_dim_tables` 不再 `glob` 目录、只逐个读取该列表（跳过坏文件的既有逻辑不变）；`None` 时保持现状重扫——**CLI 不传此参数，行为逐字节不变**。Web 传入 §5.2 筛出的普通文件列表，符号链接与 FIFO 因此真正被排除在生成之外（不是只在就绪判定中被跳过）。生成器构造期不读旧产物（§3），无 domain 的顺序陷阱，但仍保持"清理 → 构造 → 生成"同序。
- 生成/写盘异常 → 清理临时文件、`finish_step(FAILED)`，消息 `Dim Config 生成失败（{异常类型}）`（不静默留在 running）；`finish_step` 自身失败时消息追加「作业状态更新失败（{类型}），请查看日志确认作业状态」，对齐 md/domain。**注意失败语义（审核修订 5）**：旧普通产物已随生成前的 `clean_top_level_files` 删除，失败时**不恢复**（与 ddl/md/domain 的"每次完整集合"一致）；`os.replace` 未发生，若旧路径是悬空符号链接则链接本身保持原状。
- **成功判定** `_verify_dim_config_output(tmp_path)`（核验对象是**临时文件**）：存在且为普通文件（拒符号链接）→ YAML 可解析为对象 → `databases` 为 mapping（**允许为空 mapping**：零 dim 表是合法结果，与 CLI 行为一致，§13.4）。不校验表清单内容，不做重渲染比对。核验通过 → `os.replace` 到最终路径；失败 → 清理临时文件并按 failed 写回。
- **可读性底线（审核修订 7，§13.4）**：`DimTableConfigGenerator` 新增只读属性 `last_readable_count`（本轮扫描中成功解析为 JSON 对象的画像文件数；`_scan_dim_tables` 内赋值，CLI 路径同样赋值但无人消费，行为不变）。准备链已保证 `json_files` 非空；生成后若 `last_readable_count == 0` 按核验失败处理——消息「所有画像 JSON 均无法解析，无法生成 Dim Config」、清理临时文件、记 failed。界线：**"有效画像中没有维表"（≥1 个可解析、只是都不是 dim）→ success（`databases: {}`）；"没有任何可读画像"（全部无法解析，多为产物损坏）→ failed**。个别坏文件仍跳过、不整步失败（部分可读即按可读部分生成）。
- 成功消息：`受管 Dim Config 生成完成（{len(databases)} 个数据库、{total} 个维度表）`，计数取自 `generate()` 的返回字典，不回读文件。
- 状态写回：锁下 `finish_step`；`SourceRegistrationMissingError` 与写回失败的消息格式对齐 domain（`domain_step_service.py:299-332`），无 manifest 清理环节。

### 5.4 产物目录 resolver

`metaweave/core/clean_targets.py` 增加 `resolve_dim_config_output_dir(source_id, job_id)`：`output/<source_id>/<job_id>/dim_config/`，与 `resolve_domain_output_dir` 同款——两级 UUID 规范化、逐级拒绝符号链接、项目根边界与预期路径核对；清理与写入共用。

### 5.5 准备链失败与同请求阻断暂不落库

与 doc 21.1 §5.6 口径相同：准备链在 `start_step` 之前的失败（三类）与同请求 json 失败的阻断都不写 `job_info`；因此前面步骤成功、dim_config 只出现在本次结果里时，作业汇总仍可能是 success，发布入口仍会打开。有 `job_id` 时把这类失败直接写成 `failed` 已记在 [100 备忘录](100_备忘录.md) 第 3 条，统一改，本篇不实施。

## 6. 编排：白名单、顺序与失败传播

1. **白名单**：`collection_run._SUPPORTED_STEPS` 增加 `DIM_CONFIG_STEP = "dim_config"`；`normalize_collection_steps` 与循环兜底两处报错文案改为"当前仅支持 db、ddl、json、md、domain、dim_config 步骤"，循环兜底保留"（收到: {step}）"后缀。
2. **顺序（审核修订 3/4：拓扑排序，保证是确定性规则而非普遍相对序）**：`_ensure_managed_step_order` 不再连续调用 `_move_after`，替换为拓扑排序——依赖边集合固定为 `ddl→json`、`ddl→md`、`json→md`、`md→domain`、`json→dim_config`（与既有四次 `_move_after` 的锚点关系一一对应，外加 dim_config 一条；`ddl→md` 边在 json 未选时仍生效，与现状一致），只保留两端都在本次选择内的边。**执行规则：每轮在当前可执行（入度为 0）的步骤中，优先选传入顺序最靠前（原始下标最小）者**。该规则确定性、可验收，是排序的唯一保证；**不承诺"所有无依赖关系的步对都保持传入相对顺序"**——该普遍性质在存在阻塞时不可满足：传入 `[md, dim_config, ddl]` 时仅有 `ddl→md` 一条有效边，md 被阻塞期间按规则 dim_config 先行，产出 `[dim_config, ddl, md]`（要求 md<dim_config、dim_config<ddl、ddl<md 同时成立本身成环，任何拓扑排序都做不到，审核修订 4）。示例：传入 `[md, dim_config, json]` 产出 `[json, md, dim_config]`（审核修订 3 的原始诉求成立）。对既有五步的链式依赖，该实现与连续 `_move_after` 结果一致（既有排序用例即回归护栏，§11 批次 2）；dim_config 与 md/domain 之间不引入依赖边，同请求未选 json 时 dim_config 没有有效边，由 §5.2 检查既有 JSON 产物（即使同请求重跑了 ddl，也不会自动重跑 json；前端按 §8.2 显示提示，不新增编排规则）。
3. **失败传播**：`_BLOCK_MESSAGES` 增加 `(JSON_STEP, DIM_CONFIG_STEP)`，文案「本次请求的 JSON 未成功，Dim Config 未启动；如需使用已有 JSON 产物，请单独重跑 Dim Config」。走现有通用扫描即可；**不复制 md 的"未选 json 时改看 ddl"特例**——本次没选 json 时不阻断，由 §5.2 检查既有 JSON 产物。阻断只把失败记入本次 `results`，不调用 `run_dim_config_step`，不清理目录，不写 dim_config 行。
4. **作业新建与发布准入零改动**：dim_config 不创建作业（`job_id` 必填）；请求首步骤为 dim_config 且无 `job_id` → `DbStepConfigError`（400），不写行。生成阶段 `finish_step` 写下的 `failed` 才会让整作业 failed；采集页「下一步发布」和发布候选列表仍按 `job_status === 'success'` 过滤，`rollup_job_status`、发布服务与前端发布判断都不改。准备失败不落行的缺口见 §5.5。

## 7. API 契约

- **创建采集作业：零新增字段。** `CollectionJobCreateRequest` 不变（`extra="forbid"` 不变）；`steps` 数组携带 `"dim_config"` 即启用。没有描述、同步标志一类的成对字段，不需要 `model_fields_set` 判定，路由与 `start_collection_job` / `start_db_collection` 的签名均不变（dim_config 不消费 `domain_description` 两参数）。

- **错误映射**：`backend/api/errors.py` 新增 `DimConfigPreparationError` handler → 503 `dim_config_preparation_error`「Dim Config 准备阶段故障，请查看日志」（子类先于 `PlatformUnavailableError` 命中，不回显异常原文；与 `DomainPreparationError` 同款）。其余全走既有映射：`DbStepConfigError` → 400、源禁用 → 409、平台库失败 → 503 `platform_unavailable`、「未找到指定 source_id 的数据源」→ 404。

## 8. 前端交互

### 8.1 步骤定义

- `STEP_GROUPS` 中 'b' 组的条目：**id 由 `'dim-config'` 改为 `'dim_config'`**（与后台 step_name、results 行、`storedSelection` 对齐，同 doc 21.1 §8.1 的 `'domains' → 'domain'` 处理）；label 保持 `--generate-dim-config`（纯静态文本，无描述链接）。
- 可用性由 §8.2 动态计算：`isStepEnabled` 扩展为 `domain` 与 `dim_config` 两个动态分支，其余条目（rel/cql/sql-rag 等）继续按静态 `enabled: false` 不可勾选。

### 8.2 可勾选规则（前端信号粒度）

```ts
// 可勾选 = 本次选择含 json（新作业还要求同选 ddl），或重跑作业 steps 含 'json'
const dimConfigAvailable = computed(() => {
  if (rerunJobId.value !== '') {
    return Boolean(selected.value.json) || rerunSteps.value.has('json')
  }
  return Boolean(selected.value.ddl && selected.value.json)
})
```

- **新建作业须同时勾选 ddl 与 json**（需求原话）：新作业中 json 单独勾选必然因缺 DDL 产物失败（后端 json 准备链强制），此时释放 dim_config 只会得到必失败选择，故新作业把 ddl+json 同时为选中作为释放条件。
- 重跑模式：本次勾选 json（本次重跑产出）或该作业 `steps` 含 `'json'`（读既有产物，页面已通过作业列表加载 `steps`，零新接口）即可勾选——重跑时 json 允许单独重跑（读既有 ddl 产物，`jsonWithoutDdlHint` 仅新作业提示），故不再要求同选 ddl。
- 不满足时勾选框禁用，步骤区显示提示（与 `domainHint` 同容器）：
  - 新作业未同选 ddl+json：「Dim Config 依赖同作业已成功的 JSON 产物；新建作业请同时勾选 DDL 与 JSON，或从已有 JSON 成功的作业重跑。」
  - 重跑作业无 json 且本次未勾 json：「该作业没有 JSON 步骤，无法运行 Dim Config；请先执行 JSON。」
- 重跑模式勾选了 dim_config 但未勾 json、且本次勾选了 ddl 时，显示使用流程提示（不阻断）：「Dim Config 读取既有 JSON 产物；本次 DDL 不会更新 JSON——如需基于本次 DDL 重新生成 JSON，请同时勾选 JSON。」该行为是 §6.2 顺序规则的既定结果，不新增编排规则。
- 失去可用性时自动清除已勾选的 dim_config（`watch(dimConfigAvailable, …)`，与 domain 同款）。
- 「全选」按点击瞬间的可用性快照执行（`selectAvailable` 既有机制自动覆盖新条目）；「清空」一律清除。
- **文件级校验不在前端**：「json 目录至少有 1 个除 `manifest.json` 外的普通画像 `.json`」由后端准备链强制（§5.2），实际失败以执行结果区消息呈现。

### 8.3 执行

- `createCollectionJob` **不新增参数**：`chosenSteps` 含 `'dim_config'` 即随 `steps` 携带；无弹窗、无描述字段，`domain_description` 的成对携带逻辑与 dim_config 无关。
- 执行结果区显示 dim_config 行（label 取 §8.1 的静态文本），成功/失败计数、作业汇总提示、发布入口均走既有 `job_status` 逻辑。准备链失败和同请求阻断不写 dim_config 行，汇总仍只看表里已有的步骤行（缺口见 §5.5），前端不为此写分支。
- 重跑页面：`storedSelection` 对 dim_config 增加与 domain 同款分支——作业 `steps` 含 `'dim_config'` 且该作业 `steps` 含 `'json'` 时预勾选；chips 与作业列表的步骤展示随 `steps` 数组自动出现 `dim_config`，无新增代码。

## 9. 错误与失败语义

准备链错误按本次请求是否已有步骤结果分流（既有编排行为，本篇不修改）：`results` 为空时整体抛出（400/409/503），已有结果时 HTTP 200 并把该步计入 failed。三类准备失败都不在服务内先写成 `failed`，不登记 dim_config 行。HTTP 200 只表示「返回了本次请求的执行结果」。「未找到指定 source_id 的数据源」一律转 404。

| 场景 | 呈现 |
|---|---|
| 无 `job_id` | 抛 `DbStepConfigError(JSON_NOT_READY)`；`results` 为空时 400，已有结果时 HTTP 200 计入 failed；不登记 |
| 平台设置加载抛 `ValueError`、UUID 非法 | 转 `DbStepConfigError`；分流同上；不登记 |
| 工作区不存在或不属于该源 | 两类异常转 `DbStepConfigError`，消息保留原文；分流同上；不登记 |
| 源禁用 | 抛 `SourceDisabledError`；`results` 为空时 409，已有结果时计入 failed；不登记 |
| 会话 1 平台库连接或读取异常 | 返回「平台库连接或读取失败（{类型}）」失败字典（不带 `job_id`、不写行）；`results` 为空时 503 `platform_unavailable`，已有结果时计入 failed（HTTP 200） |
| 本地文件段非 `ValueError`（如枚举 `PermissionError`） | 抛 `DimConfigPreparationError`（消息「Dim Config 准备阶段故障（{阶段}：{类型}）」；日志只记阶段 + 类型，不带 `exc_info`、不写原文）；`results` 为空时 503 **`dim_config_preparation_error`**（「Dim Config 准备阶段故障，请查看日志」），已有结果时计入 failed（HTTP 200）；不转 400 |
| 同请求 json 已失败 | 编排层阻断，不调用 `run_dim_config_step`；`results` 中 dim_config `status=failed`，消息为阻断文案；不登记；HTTP 200 |
| json 行非 success、json 目录无普通画像 `.json`（含仅剩 `manifest.json`）、resolver 受控 `ValueError`、锁下复查 json 不再 success | 抛 `DbStepConfigError`（`JSON_NOT_READY` 或 `str(exc)`）；分流同上；不调用 `start_step`，不登记 |
| 会话 2 `start_step` 抛 `StepAlreadyRunningError` | 返回带 `job_id` 的 failed 结果（消息「当前步骤可能已有作业正在执行」），行保持 running，HTTP 200 |
| 生成/写盘/核验失败 | `results` 中 `status=failed`（HTTP 200）；行已是 running，由 `finish_step(FAILED)` 改为 failed；临时文件已清理（§5.3），**不替换最终路径**——但生成前的 `clean_top_level_files` 已删除旧普通产物（"每次完整集合"语义，与 ddl/md/domain 一致），**旧产物不恢复**；若旧路径是悬空符号链接，链接本身保持原状（清理删不掉、`os.replace` 未发生） |
| 状态写回失败 | 消息追加「作业状态更新失败（{类型}），请查看日志确认作业状态」，对齐 md/domain |

## 10. 验收

**后端**

- A01 作业创建接受 `steps` 含 `dim_config`；未知步骤报错文案含 domain、dim_config 全清单。
- A02 任意传入顺序下，同请求执行序满足依赖边 `ddl→json→md→domain` 与 `json→dim_config`；排序规则为「每轮在当前可执行步骤中优先选传入顺序最靠前者」，同一输入产出唯一确定结果。**用例（审核修订 3）**：`[md, dim_config, json] → [json, md, dim_config]`（旧 `_move_after` 追加方案产出 `[json, dim_config, md]`，不符合）；**反例（审核修订 4）**：`[md, dim_config, ddl] → [dim_config, ddl, md]`——md 被 `ddl→md` 阻塞期间 dim_config 先行，属规则既定结果，**验收以规则为准，不以"所有无依赖步对保持相对序"为标准**（该性质在成环约束下不可满足）。既有五步的排序用例在重写后全部保持通过（回归护栏）。`_BLOCK_MESSAGES` 含 `(json, dim_config)`，本次 json 失败时 dim_config 不执行、不登记、消息为阻断文案。
- A03 dim_config 作为首步骤且无 `job_id` → 400，消息「同一作业的 JSON 产物未就绪；请先执行 JSON 或指定已有 job_id」；`job_info` 不出现 dim_config 行。
- A04 json 行非 success、json 目录不存在/为空、json 目录**仅有非常规文件**（符号链接/FIFO，无普通 `.json`）、**目录内仅剩 `manifest.json` 清单、或清单与非常规画像文件并存而无普通画像 `.json`（审核修订 6）**、`resolve_json_output_dir` / `resolve_dim_config_output_dir` 的受控 `ValueError`：a) `results` 为空 → 400、不登记；b) 本次已有步骤结果 → HTTP 200、`results` 中 dim_config `status=failed`、不登记；c) 同请求 json 本身失败 → 阻断文案、不调用 `run_dim_config_step`、不登记；d) json success 且有普通画像 `.json` → 进入生成；e) 请求携带的 `job_id` 不存在或不属于该源 → 转 `DbStepConfigError`，消息保留「指定的 job_id 不存在/不属于该数据源」，不写行。
- A05 产物落在 `output/<source_id>/<job_id>/dim_config/dim_tables.yaml`；生成前清理目录顶层中**跟随解析为普通文件的项**（`clean_top_level_files` 的 `is_file()` 跟随符号链接：普通文件与**指向现有文件的符号链接**都会被删除，`unlink` 作用于链接本身；**悬空链接、FIFO/套接字等非正规文件与子目录保留**——不是笼统的"顶层全部清空"，与下同的预置 FIFO 用例自洽）。越界路径与符号链接在 `start_step` 之前被 resolver 拒绝：抛 `DbStepConfigError`，不调用生成器，不清理、不写入该目录，不登记。**悬空链接用例（审核修订 2）**：`dim_tables.yaml` 预先为指向目录外不存在路径的悬空符号链接时，生成成功后最终路径被 `os.replace` 替换为普通文件，**链接目标位置（目录外）不出现任何文件**，临时文件不残留；核验失败时临时文件被清理、悬空链接保持原状不被写入。**预置 FIFO 用例（审核修订 4）**：目录内预置任何名字的 FIFO（含旧固定名 `.dim_tables.yaml.tmp`）时步骤照常成功、**不发生 `open` 阻塞**（用超时断言守护），FIFO 本身不被读取或写入；最终产物权限与 ddl/json 等步骤产物一致（0640/0644 档，非 mkstemp 的 0600）。
- A06 核验（对象为新落盘的**临时文件**，核验通过才 `os.replace` 到最终路径）：坏 YAML、`databases` 非 mapping、临时产物为符号链接 → failed 且不替换最终路径；**零 dim 表（`databases: {}`）→ success**，成功消息含 0 计数；正常产物 → success，目录内无 manifest.json，结果只含 `table_category == 'dim'` 的表且 `embedding_col` 为 null。**重跑失败用例（审核修订 5）**：目录内已存在旧的普通 `dim_tables.yaml`，本次生成或核验失败 → 旧产物已随生成前清理删除、**不恢复**（最终路径不存在），临时文件不残留，步骤行 failed；与 ddl/md/domain 的失败语义一致。**全部画像损坏用例（审核修订 7）**：目录内唯一画像 `.json` 内容损坏（无法解析为 JSON 对象）→ 就绪判定通过（文件存在且为普通文件），生成后按可读性底线记 failed，消息含「无法解析」，临时文件清理、最终路径不替换。
- A07 混合目录（普通 `.json` + 符号链接/FIFO 并存）：生成只读准备链筛出的 `json_files` 列表——**指向目录外的符号链接不进入产物**（断言产物不含目录外维表）、**FIFO 不被打开**（生成阶段不发生 `open` 阻塞）；列表内个别坏 json（解析失败/非对象）被生成器跳过，不影响其余表。必备用例："1 个普通维表 JSON + 1 个指向目录外维表 JSON 的符号链接"，产物只含目录内表。
- A08 平台库不可用与本地故障分离：模拟会话 1 平台库异常 → 「平台库连接或读取失败（{类型}）」失败字典，`results` 为空时 503 `platform_unavailable`；本地文件段非 `ValueError` → `results` 为空时 503 **`dim_config_preparation_error`**（不是 `platform_unavailable`、不是 400），已有结果时该步 failed 且消息含阶段与类型；日志含阶段 + 类型且不含异常原文。
- A09 汇总口径回归：生成阶段 `finish_step` 写下的 dim_config `failed` 行使作业 failed → 发布入口不可用、发布候选不出现；准备链失败与阻断不写行，汇总只看已有行（缺口见 §5.5，本篇不补）。dim_config 之外步骤全 success 且无 dim_config 失败行的作业不受影响。
- A10 dim_config 执行不改动 db/ddl/json/md/domain 的产物与状态行，不改写 `db_desc` 与数据源描述（本服务无此代码路径）。
- A11 日志路由（分进程验收）：a) `OPERATION_STEP_MAP` 含 `"dim_config"`，`set_operation_step("dim_config")` 不抛 `KeyError`；b) script profile：`configure_logging("script")` 下执行 dim_config 步骤 → 写 `logs/script/dim_config.log`（复用既有 filter/file，`logging.yaml` 零改动），CLI `--generate-dim-config` 仍写同一文件；c) API 进程：一次 Web 采集执行不产生 `logs/script/dim_config.log` 写入，记录归 `logs/backend/metaweave.log`（无请求上下文回落 `platform.log`）。

## 13. 边界与已知取舍

1. **CLI 互不影响与脚本退化**：CLI `--generate-dim-config` 仍写 `output/dim_config/dim_tables.yaml`（`resolve_dim_tables_yaml_path` 三级回退）；Web 产物在 `output/<source_id>/<job_id>/dim_config/`；两边互不读取、不迁移。共享组件 `DimTableConfigGenerator` 只增加可选参数 `json_files`（§5.3），缺省即现状扫描方式，CLI 行为自然保持；但按用户明确决定，脚本将退化，本篇**不为 CLI 与 WebUI 的并行使用/冲突做任何设计与测试**。产物头部注释复用生成器既有文案「此文件由 metadata --generate-dim-config 自动生成…」（`config_generator.py:142`），Web 产物同样携带——YAML 注释不影响 `dim_value_loader` 等任何消费方解析，且脚本将退化，**接受复用、不改文案**。
2. **json 变更复查（不做）**：与 doc 21.1 §13.2 同决策——准备链要求 json 行 success 可拦截"json 正在运行"的多数情形，但"准备链检查之后、读取文件之前"存在窄并发窗口（json 恰在此时清目录重生成），dim_config 可能读到部分/旧文件。按"结果传递、不做状态复查"暂不处理；如后续决定补充，实现为准备链记录 json 行 `updated_at`、结束锁下比对（与 json→md 同款，约 10 行）。
3. **生成输入为准备链筛选列表（审核修订 1）**：初版设计让生成器在 §5.3 重扫目录，准备链"跳过非常规文件"只在就绪计数生效——符号链接（含指向目录外）与 FIFO 仍会进入生成（FIFO 在 `load_json` 的 `open` 处阻塞），审核以"普通 JSON + 指向目录外的链接"复现确认。现改为：Web 把 §5.2 筛出的普通 `.json` 列表经新增的 `json_files` 可选参数显式传给生成器，生成阶段不再 glob；CLI 不传该参数，缺省扫描方式与现状逐字节一致。**残余窗口**：枚举之后、读取之前普通文件被替换为符号链接时，`load_json` 仍会跟随——与 §13.2 的 json 重跑窗口同类，按不过度设计暂不处理；`load_json` 本身不加固（CLI 共用，保持现状）。生成器只消费 `table_category` 与三段标识标量、内容不进 LLM 提示词，无需引入 domain 式 `O_NOFOLLOW` 读取加固（doc 21.1 §13.2）。
4. **零 dim 表为成功，零可读画像为失败（审核修订 7）**：生成器对无 `table_category == 'dim'` 的 json 集产出 `databases: {}` 骨架且不报错（CLI 同款行为）；Web 沿用，成功消息含 0 计数。**界线**："库内暂无维表"（≥1 个画像文件可解析、只是都不是 dim）是合法事实 → success；"没有任何可读画像"（`json_files` 全部无法解析，多为产物损坏）→ failed（§5.3 可读性底线），不产出成功假象。"画像全部缺失、只剩 `manifest.json` 清单"仍在 §5.2 就绪判定即拒绝（审核修订 6），不会走到这里。
5. **`embedding_col` 恒 null**：Web 采集只生成配置骨架；人工填写与 `rag_load --type dim_value` 的 Web 化（含发布侧接入）属后续文档，本篇不预留接口。
6. **准备失败暂不落库**：同请求阻断和 `start_step` 之前的失败都不写 `job_info`，与 json/md/domain 现状相同；统一改造见 [100 备忘录](100_备忘录.md) 第 3 条，本篇不实施。
7. **与 md/domain 无相互依赖边；排序保证是确定性规则而非普遍相对序**：dim_config 只声明 `json→dim_config` 一条边（§6.2）；三者读同一 json 产物、写各自目录。排序的保证是「每轮在当前可执行步骤中优先选传入顺序最靠前者」这一确定性规则（审核修订 4）：`[md, dim_config, json] → [json, md, dim_config]` 成立，但 `[md, dim_config, ddl] → [dim_config, ddl, md]` 中 md 与 dim_config 相对序颠倒也属既定结果——"所有无依赖步对保持相对序"在阻塞场景下成环、任何拓扑排序都不可满足，文档与验收均不以它为标准。
8. **产物悬空链接与临时文件落盘（审核修订 2/4）**：初版设计"清理后直接写最终路径"存在一个组合缺口——`clean_top_level_files` 只删 `is_file()` 为真的项，悬空符号链接与 FIFO 等非正规文件幸存；`write_text` 跟随链接把产物写到目录外，或在 FIFO 上阻塞，事后核验都拦不住（审核分别以临时目录复现确认）。现改为 §5.3 的"`mkstemp` 唯一临时普通文件 → 核验 → `os.replace`"：唯一名使**预置同名 FIFO/链接**这一整类问题在结构上不可能发生；`os.replace` 作用于最终路径的链接本身，越界写在结构上不可能发生。第一版修订曾用固定名 `.dim_tables.yaml.tmp` + 写前 `is_symlink()` 检查，仍会被预置 FIFO 卡住（`is_symlink()` 不命中 FIFO），审核修订 4 指出后改为 `mkstemp`。**残余窗口**：`mkstemp` 创建之后、`write_text` 之前临时文件被置换为符号链接时仍会跟随——能对受管目录做这种实时置换的写入方，与能在 json/md/domain 产物目录做同类操作的威胁面相同（各步骤的 `write_text`/`save_text` 均无此防护），按不过度设计统一不处理；如未来要收这类窗口，应在 `file_utils` 层统一引入 `O_NOFOLLOW` 写盘助手，而不是在 dim_config 单点加固。

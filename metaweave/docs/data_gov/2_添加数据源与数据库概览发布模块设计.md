## 1. 目标与范围

第一阶段完成一条可用的闭环：管理员在 Web UI 添加 PostgreSQL 数据源并选择 schema → 发起数据库概览采集 → `metadata --step db` 生成 JSON → 管理员发布 → Web UI 从平台库查看已发布的数据库概览。添加数据源与采集、发布是三个不同动作；仅登记数据源不等于已经采集或发布。

本阶段只发布**数据库级概览**。现有表/字段 JSON 画像的结构化入库与展示、关系图与向量加载、完整 pipeline 的 Web 编排、多种数据库类型及多用户并发编辑均留待后续阶段。第一版数据源类型仅支持 PostgreSQL，与当前元数据提取器的能力一致。

## 2. 技术栈与运行边界

| 层次 | 第一阶段选择 |
| --- | --- |
| 前端 | Vue 3 + TypeScript + Vite，提供数据源登记、作业状态、发布与数据库概览页面。 |
| Web API | Python 3.12+、FastAPI；负责校验请求、读写平台库和创建作业，不在 HTTP 请求中同步等待采集完成。 |
| 平台库 | 独立的 PostgreSQL **database**，默认库名 `metaweave`，可由环境变量修改；第一阶段的表建在 `public` schema。平台表使用 SQLAlchemy 2 建模和访问，底层 PostgreSQL 驱动使用 psycopg 3；建表与后续结构变更由管理员按设计文档中的 SQL 手工执行，不使用 Alembic。 |
| 作业执行 | 独立的通用 Worker 进程读取平台库中的待执行作业，按步骤名调用与 CLI 共用的同步执行函数，并更新作业状态；第一阶段一个 Worker、仅接入 `db`，不要求把 MetaWeave 业务代码整体改为异步。 |
| 凭据 | 平台库连接信息（含密码）以明文配置在服务端本机 `.env`，本阶段不对该密码再加密；管理员登记的数据源连接信息存平台库，**源库密码**可逆加密后保存，加密密钥不入平台库。 |

平台库必需的环境变量为 `PLATFORM_DB_HOST`、`PLATFORM_DB_PORT`、`PLATFORM_DB_NAME`、`PLATFORM_DB_USER`、`PLATFORM_DB_PASSWORD`，其中 `PLATFORM_DB_NAME` 默认 `metaweave`；另可选填 `PLATFORM_DB_SSLMODE`。它们不复用当前主配置中用于被分析库的 `DB_*`。`PLATFORM_DB_PASSWORD` 是应用连接**平台库**所用的密码，直接以明文字符串存放在本机 `.env`，不经 Fernet 加密；`db_source_info.password_ciphertext` 才是加密后的**源库**密码，两者不能混用。`SOURCE_CREDENTIAL_KEY` 也从服务端环境读取，专用于加解密源库密码，不用于平台库登录。本地 `.env` 已被 Git 忽略，不得提交；`.env.example` 只列变量名和占位值，不放真实密码或密钥。部署时改用环境注入或专用密钥管理。Web 页面与 API 不返回平台库凭据。

平台库是另一条独立连接链路：`backend/persistence/platform_db.py` 仅在 `PLATFORM_DB_SSLMODE` 有值时把它传入平台库连接参数；未设置或为空时不传 `sslmode`，也不在后端补默认值。平台库连接仍显式设置 `connect_timeout=10` 秒；超时只限制建连，不是整次采集或发布的总时限。平台库不读取源库主配置的 `database.*`。是否使用 TLS 取决于实际传入的模式或 libpq 自身行为；不应因为密码放在本机 `.env` 就推定网络传输已加密。此规则不改变现有 `ddl/json/rel` 等步骤的连接参数。

第一阶段不引入 Airflow、Celery 或 Redis。独立 Worker 可先以 PostgreSQL 作业表作为最小队列；后续吞吐量达到需要时再替换队列实现。作业不能寄托于 FastAPI 的进程内 `BackgroundTasks` 或增加 HTTP worker 数量。

平台依赖作为 `pyproject.toml` 的 `[project.optional-dependencies].platform` 显式声明，并按交付阶段扩充：先实施 [doc 3 的独立 `--step db` 脚本](<3_阶段一step db设计文档.md>) 时，首版直接声明 SQLAlchemy 2 和 `cryptography`（Fernet）；接入 Web API 时，再把 FastAPI 与 ASGI 服务运行依赖加入**同一个** `platform` extra。本文完整闭环交付时，该 extra 须包含上述平台运行依赖，不加入 Alembic。不能因为 `cryptography` 或 SQLAlchemy 恰好由其他包间接安装、出现在 `uv.lock` 中，就省去直接声明。`psycopg`、`python-dotenv` 与 `pgvector` 已是现有引擎的基础依赖，不因新增 `backend/` 重复归为平台专属依赖。CLI-only 环境按现有基础依赖安装；运行 Web API、Worker 或 `metadata --step db` 的环境显式安装平台 extra，例如 `uv sync --extra platform`。`uv` 默认同步不安装可选 extra；把 `backend*` 纳入包发现只会打包源码，不会自动安装平台依赖。

### 2.1 仓库目录与模块职责

沿用现有单仓库，现有 `metaweave/` 不搬迁。新增的后端 Python 包命名为 `backend/`，Vue 工程命名为 `frontend/`，两者与 `metaweave/` 平级；不建立一个包住前后端的 `platform/` 总目录。建议目录如下（只表示职责，不要求第一提交创建所有空目录）：

```text
./
├── metaweave/                 # 现有引擎：CLI、元数据采集、画像、加载
│   ├── cli/                   # 增加 --step db / --source-id 的 CLI 入口
│   └── core/metadata/         # 增加可供 CLI 和 Worker 共用的 db 采集逻辑
├── backend/                   # 新增 Python 包：平台后端
│   ├── api/
│   │   ├── main.py            # FastAPI 应用入口
│   │   └── routers/           # 数据源、作业、发布、概览接口
│   ├── data_sources/          # 数据源登记、连接测试、schema 发现
│   ├── persistence/           # 平台库连接、模型、数据访问
│   ├── security/              # 数据源密码加密与解密
│   ├── jobs/                  # 作业状态与独立 Worker
│   └── publishing/            # 数据库画像入库、版本切换
├── frontend/                  # 独立的 Vue 3 + TypeScript + Vite 工程
│   ├── package.json
│   └── src/{api,views,components,router}/
├── configs/                   # 保留现有 MetaWeave 配置
├── tests/                     # 增加 backend 与 db 步骤的测试
└── output/<source_id>/        # 按数据源组织的运行产物，不是前后端源码
```

平台库 `metaweave` 这个 database 须由管理员先创建；首张 `public.db_source_info` 表使用 [doc 3 §2](<3_阶段一step db设计文档.md>) 的 SQL 手工创建。后续 `job_info`、发布和画像表在各自功能开发时写明建表 SQL，由管理员确认目标库后手工执行；现有平台表若需修改，也在对应设计中写明变更 SQL 和执行前提。本项目不要求 Alembic、`alembic.ini`、`migrations/` 或自动表结构升级，也不维护平台 schema 版本表。`--step ddl` 生成的是**源业务库**的结构画像，可用于比较源库变化，但不是创建或更新平台 `metaweave` 库表的脚本；两者不能混用。

依赖方向为：`backend` 的应用服务调用 `metaweave.core` 的共享采集函数；`metaweave.core` 不导入 FastAPI、平台库或 `backend`。独立 `metadata --step db` 的 CLI 入口只在确认执行 `db` 的分支内延迟导入 `backend.data_sources.db_step_service.run_db_step()`；将来的 Worker 也按步骤名调用**同一个应用服务函数**，由它加载并校验主配置、读取平台库数据源和解密密码，再调用 `metaweave.core.metadata.db_step.execute_db()` 完成实际采集，Worker 不反向调用 CLI。该函数与文件边界详见 [doc 3 §5.1–5.2](<3_阶段一step db设计文档.md>)。`metaweave.cli.main`、`metadata_cli.py` 的模块顶层及 `backend/__init__.py` 不得提前导入平台 API/Worker、SQLAlchemy 或 `cryptography`；`backend.data_sources` 的导入路径不得反向导入 `metaweave.cli`，避免初始化时形成循环。未安装平台 extra 时，既有 CLI 命令与 `--help` 应照常可用；实际执行 `--step db` 若缺少平台依赖，应明确提示安装 extra 并在副作用前退出，不要求根据“是否安装了 extra”本身人为禁止运行。前端只访问 FastAPI，不直接连接 PostgreSQL。实施时须在现有 `pyproject.toml` 的包发现规则中纳入 `backend*`；`frontend/` 用自己的 `package.json` 管理 Node 依赖，不混入 Python 包。

## 3. 数据源登记与凭据

第一阶段表名以本文为准，与前序概要中的概念对应如下。`*_info` 保存登记或执行过程，`db_profile` 保存不可变的已发布画像；后者不按 `*_info` 命名是为了区分画像内容与过程记录。

| 前序概要用语 | 本文采用的表名与含义 |
| --- | --- |
| `data_source` | `db_source_info`：已登记的数据源。 |
| `job`、`job_step` | `job_info`、`job_step_info`：作业及其步骤的执行记录。 |
| `catalog_snapshot` | 不再对应单表；拆为 `publish_info`（发布结果记录）和 `db_profile`（成功发布的数据库画像）。后续表/字段画像也按发布版本关联。 |

### 3.1 `public.db_source_info`

`source_id UUID PRIMARY KEY` 由服务端在新增时生成，且作为该数据源的稳定身份；后续作业、发布记录及工作目录均引用它。数据库显示名称、host 或密码的修改不改变 `source_id`；若连接目标实际上变成另一套业务数据库，应新建数据源，避免历史画像归属混乱。

建议字段如下，正式 DDL 可在实施时补充长度约束和索引：

| 字段 | 类型/约束 | 用途 |
| --- | --- | --- |
| `source_id` | `uuid`，主键 | 数据源身份及 `output/<source_id>/` 目录名。 |
| `display_name` | `text`，非空 | Web UI 展示名。 |
| `description` | `text`，可空；由 doc 4 的 Web 登记阶段增量添加 | 管理员填写的纯文本说明；接口按去除首尾空白后最多 1000 字符校验，纯空白存为 `NULL`。 |
| `db_version` | `text`，可空；由 doc 6 增量添加 | 登记或修改保存时写入的源库版本展示字符串，如 `"18.6"`；由 `format_server_version()` 生成，不由客户端提交。本列添加前的旧行为 `NULL`。 |
| `db_type` | `text`，非空 | 第一阶段仅允许 `postgresql`。 |
| `host`、`port`、`username` | 文本/整数，非空 | 源库连接信息；这些字段不含密码。 |
| `db_name` | `text`，非空 | 源库数据库名；平台表列名固定为 `db_name`，不使用 `database_name`。 |
| `password_ciphertext` | `text`，非空 | 源库密码经服务端可逆加密后的密文。 |
| `sslmode` | `text`，可空，无数据库默认值 | 管理员填写或选择的源库连接选项；有值时经规范化后作为单独的 `sslmode` 参数传入（doc 18.1 修订：先规范化——去首尾空白、转小写——再作为单独参数传入），未填写时不传。 |
| `selected_schemas` | `text[]`，非空 | 管理员选定的采集范围；不允许空列表。 |
| `created_by_user_id` | `uuid`，可空 | 创建该数据源的平台登录用户 ID；尚无用户体系时留空。 |
| `created_at`、`updated_at` | 带时区时间 | 登记时间与修改时间。 |

`db_name` 和 `created_by_user_id` 已纳入 [doc 3 §2](<3_阶段一step db设计文档.md>) 的首版 DDL；API、仓储模型及采集代码均使用这两个列名和字段，不另设 `database_name`。`created_by_user_id` 表示**创建人**，不是最后修改人。接入登录后，由后端从已验证的登录身份写入，不接受前端自行指定；在尚无平台用户表或认证的原型阶段（包括手工登记）允许为 `NULL`，不伪造用户 ID。用户表建立后再决定外键约束；如果将来需要追踪最后修改人，另设计 `updated_by_user_id`，不复用创建人字段。

第一阶段以 PostgreSQL 18.x 源库作为开发和验收样本；数据源登记与 `db` 采集共用版本准入规则 **PostgreSQL 15.0 及以上**（`server_version_num >= 150000`）。14.x 及更早版本在登记前或采集的清理、统计前报明确的不支持错误；达到该门槛的版本均进入相同流程，实际 SQL 失败按普通失败处理，不再按是否为 18.x 设置第二套准入规则。版本号读取和校验使用 [doc 3 §4](<3_阶段一step db设计文档.md>) 定义的共享函数，Web 连接检查、创建数据源、手工登记与 `--step db` 不各自维护门槛。第一阶段不在 `db_source_info` 增设含义不明的 `status`：记录存在即表示已登记；连接测试结果是当次请求结果，采集与发布结果分别从 `job_info`、`publish_info` 读取，不把它们合并成数据源状态。若以后增加停用/启用能力，再单独定义状态枚举与操作语义。

源库密码需要在 Worker 连接时还原，不能做不可逆哈希。第一版使用应用层 `cryptography.Fernet` 加密：Web API 收到密码后加密写入 `password_ciphertext`，Worker 在内存中解密后连接；密钥由独立的 `SOURCE_CREDENTIAL_KEY` 环境变量提供，不与密文存放在同一个 PostgreSQL 库中。保管好密钥备份，否则密文无法恢复；后续可用 `MultiFernet` 轮换密钥。更新数据源时，未填写新密码表示保持原密文，不把现有密码回显到前端。密码不得出现在 URL、日志、异常响应、JSON 产物、可长期保存的明文配置快照中。

第一阶段的数据源登记允许填写可选的 `sslmode`：保存到 `db_source_info.sslmode`，连接测试、schema 发现及 `db` 采集均读取同一值；有值就作为独立的 `sslmode` 参数传给 psycopg（doc 18.1 修订：传入前规范化为小写并去首尾空白），没有值就不传，后端不补 `disable` 或其他默认值。~~应用不设 `sslmode` 取值白名单，也不在建连前另做模式合法性预检；管理员负责选择或填写连接选项，值若不被 libpq 接受，由连接尝试报告失败~~（doc 18.1 修订：`sslmode` 统一按 libpq 六模式值域校验并规范化为小写，非法值在**建连前**拒绝，不再交给 libpq 连接时报错）。界面可以自行决定初始展示值，但后端只依据提交并保存的值连接。连接参数必须分别传递，不能让一个字段的内容被解析为额外的 libpq 参数。既有 `ddl/json/rel` 等步骤本次仍沿用现有连接方式。必须说明一个驱动事实：未传 `sslmode` 时，libpq 在支持 SSL 的常见构建中默认 `prefer`，会先尝试 TLS、失败后可回退非 TLS；它不是 `disable`，也不保证始终加密。源库、平台库与浏览器访问 API 的 TLS 是不同链路；正式部署到不可信网络前须分别确认其传输保护。

数据源创建、修改、采集和发布 API 仅对管理员开放。第一阶段若尚未实现管理员身份认证，只允许服务绑定本机用于开发，不得将管理 API 对外开放；正式部署前必须补齐认证与授权，并对浏览器到 API 的链路使用 TLS，同时确认源库与平台库的连接模式及证书信任。源库账号建议为只读账号，连接测试与采集均应设置超时。

### 3.2 添加数据源的页面与 API

页面依次完成：填写 PostgreSQL 连接信息（`sslmode` 可选）→ 测试连接并取得可访问 schema → 选择一个或多个 schema → 保存数据源。页面若预填 `sslmode`，该值须像其他连接字段一样随请求提交并保存；若不填，则提交空值，不由后端补默认。连接测试失败应显示具体但已脱敏的错误，不保存未确认的密码。建议 API 契约：

连接检查取得 `server_version_num` 后，须在报告“连接成功”或返回可选 schema 前执行与 `--step db` 相同的 PostgreSQL 15.0 最低版本校验。低于门槛或版本号不可解析时，返回明确的 `unsupported_postgresql_version` 错误，并提示最低支持版本；创建接口即使此前连接检查成功，也要重新连接并再次校验版本，校验失败不写 `db_source_info`。手工登记工具同样在插入前检查。版本判定不依赖展示字符串，也不只在前端判断。

- `POST /api/data-sources/connection-check`：使用提交的连接信息测试连接并返回可访问 schema；不持久化密码。
- `POST /api/data-sources/{source_id}/connection-check`：用该数据源已保存的连接目标和原密码重测，不接收新的连接目标，不写库。见 [doc 6](6_数据源版本字段与修改连接设计.md)。
- `POST /api/data-sources`：校验所选 schema 后创建数据源并返回 `source_id`。
- `GET /api/data-sources`、`GET /api/data-sources/{source_id}`：列出及查看已登记信息；永不返回明文密码或密文。
- `DELETE /api/data-sources/{source_id}`：删除该登记记录；`delete_output=true` 时同时删除 `output/<source_id>/` 及其全部内容。不返回密码或密文，不存在返回 `404 not_found`。见 [doc 7](7_数据源查看与删除设计.md)。
- `PATCH /api/data-sources/{source_id}`：由 doc 6 落地。请求体与创建相同，仅密码可省略或为空；缺其他字段返回 `422`，不做字段级局部更新。密码留空只允许连接目标与原记录一致。修改保持同一个 `source_id`，只用于同一套业务数据库；换成另一套业务数据库时新建数据源。见 [doc 6 §5.2](6_数据源版本字段与修改连接设计.md)。

连接检查只能由管理员调用，并须设置连接超时。doc 4 的第一阶段 Web 入口使用同步 `def` 路由处理同步 psycopg/SQLAlchemy 操作，由 FastAPI 在线程池执行。本阶段仅供本机开发使用，不实现应用层并发限流，也不因限流规定 Uvicorn 进程数；若以后扩大使用范围，再根据实际负载评估容量控制。本阶段信任企业管理员填写的源库地址：连接测试和创建使用当次提交的 `host`、`port`，后续采集使用登记表中的 `host`、`port`，均原样作为独立 psycopg 连接参数；不增加目标 IP 禁止清单、服务端预解析 DNS 或固定 `hostaddr` 的逻辑，域名解析交给 libpq。连接检查与创建分别建立连接，创建时仍须重新检查版本和所选 Schema，不能把此前的测试结果当作创建成功的凭据。未实现身份认证时，API 仍仅绑定本机；若以后改变调用者或部署边界，再单独评估网络访问控制。

连接检查返回当前账号可访问、且适合管理员选择的业务 schema；源库存在其他无权限 schema，不要求整个发现过程失败。使用 `pg_catalog.pg_namespace` 重建发现查询时，除按 `has_schema_privilege(oid, 'USAGE')` 筛选外，还须排除 `pg_catalog`、`information_schema`、`pg_toast`，以及名称以 `pg_temp_` 或 `pg_toast_temp_` 开头的临时 schema；不能因为旧 `GET_SCHEMAS_SQL` 已有部分过滤，就默认新查询也继承这些规则。仅使用 `pg_is_other_temp_schema()` 也不够，因为它不排除当前会话的临时 schema。doc 4 的 Web 登记阶段须在 `metaweave/core/metadata/db_step.py` 增加 `discover_selectable_schemas(conn)`，并与已有 `validate_selected_schemas(conn, names)` 共用 `pg_namespace`/`USAGE` 查询及同一份系统、临时 Schema 排除规则：列表不展示的系统/临时 Schema，直接提交也必须拒绝。doc 3 最初的手工登记与显式校验口径由 doc 4 同步收紧；已有这类登记记录在后续采集时给出明确错误。

对管理员明确选入 `selected_schemas` 的每个 schema，创建/修改数据源时及每次 `db` 采集时都必须严格校验：先从 `pg_catalog.pg_namespace` 确认其存在，再以该 schema 的 OID 调用 `has_schema_privilege(oid, 'USAGE')` 校验访问权限。不存在（包括登记后被删除）与无 `USAGE` 权限须分别报错；只有存在、权限满足且对象查询成功后，零个对象才可记为“确实为空”。对象查询或其他统计查询失败也须报错/标记不可用，不得显示为 `0`。

现有 `GET_SCHEMAS_SQL` 使用 `information_schema.schemata`，该视图会过滤当前账号无权访问的 schema，因此单靠查询返回空列表、甚至改成“抛出 SQL 异常”，都不能区分“无权限”与“不存在”。现有 `DatabaseConnector.get_schemas()` / `get_database_objects()` 还会吞掉查询异常并返回空列表；`get_schemas(exclude_system=True)` 的 `exclude_system` 形参目前未生效。`db` 步骤和连接检查应使用不吞异常的查询入口，并实施上述显式存在性/权限校验；不能直接把旧方法的空列表当作可靠的零值。

## 4. `metadata --step db` 与工作目录

新增 `metaweave metadata --step db`，并在 metadata 共享执行层增加同一业务步骤。由于产物必须归属某个已登记的数据源，独立 CLI 执行该步骤时还必须指定 `--source-id UUID`，例如 `metaweave metadata --step db --source-id <UUID> --clean`；缺少或查不到该 ID 时执行前报错。Web UI 已经选定数据源，由 Worker 在内部传递 `source_id`，不要求用户填写 CLI 参数。`db` 步骤的配置来源按下表固定，不笼统继承主配置的“通用采集选项”。Web Worker 与 CLI 调用同一共享步骤函数，不在 FastAPI 请求线程中拼接并运行 shell 命令。独立 CLI 仍可用于手工采集、单步补跑与排障，不只是测试入口；它本身不创建或更新 Web 作业表。当前共享请求主要基于 `config_path` 读取配置；实施时须从平台库读取数据源、在内存中解密密码并构造任务专属配置，不能为了复用 CLI 把明文密码落入临时 YAML。

第一阶段的独立 `metadata --step db` 是**平台绑定的 CLI 入口**，不是脱离平台库的离线采集命令。即使管理员手工执行，也须先通过 Web/API 在平台库登记数据源，并在执行环境提供平台库连接与 `SOURCE_CREDENTIAL_KEY`；其他既有 metadata 步骤仍可按原方式独立运行。平台库不可用、`source_id` 未登记、密钥缺失或密码无法解密时，`db` 必须在清理工作目录及连接源库之前失败，不得回退到主配置、`.env` 中的 `DB_*` 或临时 CLI 凭据。本阶段不提供第二套源库凭据来源。

`db` 的 CLI 与 Worker 必须使用同一条主配置读取、校验及任务配置构造链路：先按现有 `load_config()` 语义读取主配置并完成环境变量替换，再对已加载配置运行共用校验（现有 LLM 路径预检和废弃关系配置节点检查），最后按下表用数据源登记值在内存中构造 `db` 的有效配置。可将现有 `load_main_config_snapshot()` 中的校验部分抽为 `validate_main_config(config)`，供文件加载入口和已有内存配置的入口复用；不得让 Worker 直接传入未经同等校验的配置。这里的 LLM 检查属于主配置整体的合法性检查，**不表示** `db` 会调用 LLM 或使用 `llm.*` 作为采集参数。两个入口对同一份主配置和同一数据源登记，应在采集、清理之前得到相同的校验结论。

| `--step db` 的配置/参数 | 第一阶段来源与行为 |
| --- | --- |
| 数据库类型及 `database.host/port/database/user/password` | 仅从 `db_source_info.db_type/host/port/db_name/username/password_ciphertext` 取得；密码在内存中解密，不回退到主配置中的 `DB_*`。源库类型与连接目标由数据源登记决定。 |
| `database.schemas` | 仅使用 `db_source_info.selected_schemas`；登记及采集时按 §3.2 校验。 |
| 源库连接的 `sslmode` | 仅取 `db_source_info.sslmode`；有值则经规范化后作为 `sslmode` 参数传入（doc 18.1 修订：先规范化——去首尾空白、转小写——再作为单独参数传入），空值则不传，不由后端补默认。连接测试与 Worker 采集保持一致。 |
| `database.pool_min_size/pool_max_size` | 如复用现有 `DatabaseConnector`，从 `--config` 指定的主配置读取；未配置时沿用连接器默认值 `1/5`。这些连接池参数不覆盖源库身份。 |
| `database.include_object_types/exclude_tables` | `db` 概览计数不使用，详见下方对象统计口径；仍只作用于其原有画像生成步骤。 |
| `sampling.*`、`llm.*` | `db` 不采样、不调用 LLM，这些节点不作为 `db` 的业务参数。 |
| `output.*` | 不决定 `db` 的输入、输出或清理目标；固定使用 `output/<source_id>/db/database.json` 及其所在目录。现有步骤仍按原有配置运行。 |
| `--config/-c` | 独立 CLI 沿用主配置路径入口，但不能让其中的连接身份、schema 或输出目录覆盖上述数据源登记与固定路径；Web Worker 使用相同的有效配置来源规则。 |
| `--schemas/-s`、`--tables/-t` | 对 `db` 不允许覆盖已登记的范围；显式传入时报用法错误（exit 2），不执行采集或清理。 |
| `--source-id`、`--clean` | 前者仅 `db` 必填、只允许一次；后者可选，独立 CLI 默认 `false`，Web `db` 作业明确设为 `true`。 |

其他只服务于既有生成步骤的显式 CLI 参数（例如 `--max-workers`、`--domain`、`--cross-domain`、`--domains-config`）及 `--generate-*` 模式，也不得与 `--step db` 混用；一律在副作用前报用法错误（exit 2），不能沿用“告警后忽略”的宽松规则。未列入上表的主配置节点不因为存在于 YAML 中就自动成为 `db` 的可覆盖参数。

第一阶段 `db` 步骤的接线清单如下；它**只把 `db` 接入独立 metadata CLI 与 Web Worker，不把其他既有步骤改造成多数据源作业**：

1. `metaweave/cli/metadata_cli.py`：在 `--step` Choice、帮助文本与执行分支中加入 `db`，让它调用专门的共享 `db` 执行函数，不落入现有 `ddl/json/md` 分支；数据源适配器仅在该分支延迟导入。新增 `--source-id`；参照 `--step` 的单次传入保护，在任何清理或采集副作用之前拒绝重复传入、非 UUID、`db` 缺失 `source_id`、不存在的 `source_id`，以及非 `db` 步骤传入 `--source-id`（用法/配置错误，退出码 2）。更新 `_MODE_SCOPED_PARAMS`、`_PARAM_DISPLAY` 及模式判断，为 `db` 明确参数作用域；对上表不允许的显式参数直接报错，不能依赖现有“作用域外参数只告警后忽略”的行为。
2. `metaweave/core/metadata/execution.py`：将 `db` 加入 `METADATA_OPERATIONS` 与 `OPERATION_STEP_MAP`，并扩展 `MetadataExecutionRequest` 或等价请求，使共享函数收到 `source_id` 和内存中的任务专属配置/数据源上下文，而不是只靠 `config_path`。把主配置校验从文件读取中拆出，确保 CLI 与 Worker 在构造任务配置前共用上述校验，不能为 Worker 新开绕过校验的执行入口；两者共用同一采集函数。日志步骤固定映射为 `db`，如需分步骤日志，还须同步 `configs/logging.yaml`。`METADATA_OPERATIONS` 不再等同于 pipeline YAML 的步骤集合，相关注释须一并修正。
3. `metaweave/core/clean_targets.py` 与实际清理执行处：为 `db` 增加接收 `source_id` 的专用目标解析和校验，计划目标、运行期核对、实际清理都必须指向同一 `output/<source_id>/db/`。不能仅向 `_METADATA_STEP_DIR_KEYS` 添加普通 `db_directory`：现有映射会从主配置的 `output.*` 推导目录，无法保证数据源隔离。清理只作用于当前数据源的 `db/`，沿用“不递归、只删目录顶层文件”的语义。
4. `metaweave/cli/pipeline_config.py`：第一阶段**不支持** `pipeline.metadata.db`，不将 `db` 加入 `METADATA_STEP_KEYS` 或 `METADATA_STEP_ORDER`；现有 pipeline YAML 没有 `source_id` 契约，配置 `db` 仍按未知步骤拒绝。Web 仅提交 `db` 作业，独立 CLI 则显式传 `--source-id`。以后若要纳入 pipeline，须先单独设计数据源身份、配置格式与其他步骤的路径隔离，不能因共享执行层认识 `db` 就自动开放 YAML 编排。
5. 源库连接构造：现有 `DatabaseConnector` 手工拼接 `conninfo`；新增 `db` 的连接检查与采集应共用参数构造逻辑，把登记的 `host`、`port`、`dbname`、`user`、`password` 及有值时的 `sslmode` 分别作为 psycopg kwargs 传入。API 不得绕过 `build_connect_kwargs(...)`（doc 18.1 更名）自行拼第二套参数，也不新增 `hostaddr` 参数。需要给连接池提供连接串时，使用 `psycopg.conninfo.make_conninfo()` 从这些独立参数构造，**不得用 f-string 将字段值拼进 conninfo 文本**。这样密码中的空格等特殊字符不会改变参数解析，`sslmode` 的内容也只会作为该参数的值，不会变成其他 libpq 参数；无值时不传 `sslmode`，连接器不写入全局缺省。~~不对 `sslmode` 增设应用白名单，连接失败由 libpq 报告~~（doc 18.1 修订：公共参数模块 `metaweave/db/postgres_options.py` 维护唯一一份六模式白名单，非法值建连前拒绝）；现有 `ddl/json/rel` 的连接行为保持不变。

目录固定为 `output/<source_id>/db/database.json`。`db` 是步骤名而非真实数据库名；`job_id` 不参与目录命名。第一阶段只保证 `db` 步骤的生成和清理目标位于当前数据源的 `output/<source_id>/db/`，CLI 与 Worker 共用同一条路径解析逻辑；执行清理前还须校验目标属于当前 `source_id`，仅校验“在项目根目录内”并不足够。相对路径仍以项目根目录为基准。该目录是当前工作区，不是按作业保留的版本库：下一次 Web `db` 作业开始时会先清理旧文件，即使本次随后失败，也不能指望从文件恢复上一次未发布的采集结果。`job_info` 保留历史执行状态；可回看的历史画像内容仅来自已成功发布到平台库的版本。

后续步骤接入多数据源作业时，现有 `ddl/md/json/rel/cql` 等步骤也必须逐项改造：将其输入、输出统一隔离到 `output/<source_id>/{ddl,md,json,rel,cql,...}/`，以支持跨天分步执行及人工编辑 MD；同时梳理主配置中显式的步骤目录、加载器输入、运行时推断路径、回退路径与 `clean` 目标，统一派生并验收，不能只改 `output.output_dir`。**这些改造是后续阶段的必做工作，不属于本阶段交付；本阶段保留既有步骤及独立 CLI 的当前路径行为，也不让它们借 `db` 的新入口误用数据源工作区。**

旧产物的过渡也留到上述后续阶段：现有 `output/ddl`、`output/md` 等目录原样保留，本阶段不自动移动、复制或清理；尤其不得把人工编辑的 MD 自动归到某个 `source_id`。后续启用其他步骤的 `source_id` 工作区前，必须先说明旧产物如何由用户确认数据源归属、按需迁移，以及未迁移时新工作区为何看不到它们；是否提供一次性迁移命令届时再定，不把它作为本阶段交付。doc 26 的默认 `configs/pipeline.yaml` 当前仍指向使用旧 `output/*` 路径的主配置，不能在本阶段悄悄改指某个数据源目录。未来若让 pipeline 执行多数据源步骤，须先补齐 `source_id` 契约并明确旧配置与新配置的过渡方式，不得静默改变现有默认 pipeline 的读写目标。

`database.json` 使用带 `schema_version` 的 JSON 契约，至少包含：`source_id`、数据库类型/名称/host/port、源库版本 `database.server_version`、采集时间、选中的 schema、各 schema 的普通表/分区表/视图/物化视图数量、分区子表数量、合计对象数量、数据库大小字节数与大小口径，以及数据库级 `record_count`。新生成文件的 `server_version` 为展示字符串（如 `"18.6"`），由已读取的 `server_version_num` 转换；不得包含密码。本阶段画像不记录 `sslmode` 等连接级选项或采集连接实际是否使用 TLS；登记表中的 `sslmode` 可能随后改变，而且其取值不能证明某次连接实际使用了 TLS。各 schema 及所选 schema 汇总使用相同的计数规则：

第一阶段生成的 `database.json` 固定写入整数 `schema_version: 1`；发布端只接受版本 `1`，缺失、非整数或其他版本均在画像入库前失败。按 doc 12，失败记录成功提交后也成为 current，当前读取显示发布失败、不展示旧画像；不沿用本文早期“不切换当前发布”的规则。以后扩展版本时应显式列出发布端支持的版本及转换/读取规则，不能仅凭 `schema_version <= 最大版本` 就接受未知的旧格式。

`server_version` 是增量画像字段，不改变 `schema_version: 1`。旧版 `schema_version: 1` 文件若没有该字段，发布端允许将已发布版本记为未知（`db_profile.server_version` 为 `NULL`），页面显示“未知”；不得从当前连接或登记表补填一个不属于该次采集的版本。新版 `--step db` 每次成功均写入非空的 `server_version`。`database.server_version_full` 与 `database.os_platform` 同样是增量画像字段，同样不改变 `schema_version: 1`：前者是该次采集 `SELECT version()` 的原串，后者是从原串解析出的安装平台展示串（族名 + 架构，如 `Windows x86_64`；解析不出为 `NULL`）。旧文件缺这两个键时按未知处理（两列为 `NULL`），页面显示“未知”，同样不得用当前连接或登记表的值补填；若该次 `SELECT version()` 读取失败，两个键写 `null` 而采集仍算成功（doc 13 §3.2）。

| 统计项 | `pg_catalog.pg_class` 判定条件 | 是否计入对象合计 |
| --- | --- | --- |
| 普通表 | `relkind = 'r' AND NOT relispartition` | 是 |
| 分区表 | `relkind = 'p' AND NOT relispartition`，只计顶层分区父表 | 是 |
| 视图 | `relkind = 'v'` | 是 |
| 物化视图 | `relkind = 'm'` | 是 |
| 分区子表 | `relispartition AND relkind IN ('r', 'p')`，包含叶子分区和中间层分区表 | 否，单独展示数量 |

对象合计严格等于前四类数量之和，不包含分区子表、序列（`S`）、外部表（`f`）、复合类型（`c`）等其他对象。此处统计的是**所选 schema 的对象概览**，不套用 `database.include_object_types` 或 `database.exclude_tables`：这两项配置控制现有画像生成范围，不能让它们改变源库概览的含义。因此页面应标为“对象总数（未按画像配置过滤）”，不得将其解释为已生成画像数或已发布的表画像数；后续若需对账，另列已画像/已发布数量。该对象数也不是当前账号拥有表级 `SELECT` 权限的对象数；schema 的 `USAGE` 校验不代替后续逐表画像或采样所需的表级权限检查。实现 `db` 统计时须查询 `relkind` 与 `relispartition`，不能直接沿用现有将 `r`、`p` 都映射为 `table` 的 `GET_DATABASE_OBJECTS_SQL` 分类结果。

数据库大小字节数取 `pg_database_size(current_database())`，表示**当前整库的磁盘占用**，不是所选 schema 的大小，也不等于上述四类对象大小之和；其中还涉及索引、TOAST、系统对象等存储开销。第一阶段不逐表执行 `COUNT(*)` 来计算全库行数：`database.json` 的数据库级 `record_count` 固定为 JSON `null`，发布到平台库后仍保持 SQL `NULL`，Web UI 显示“—（未采集）”，不得用 `0` 冒充已采集结果。统计值因权限或查询失败无法取得时应明确失败或标记未知，不能静默写 `0`。

Web 发起的 `db` 作业默认在执行前清理其 `db/` 目录顶层旧文件，不清理其他步骤目录，更不清理 Neo4j/Milvus。**现有独立 metadata CLI 与 pipeline 的 `clean` 默认均为 `false`**；本阶段先由 Web 作业入口对 `db` 明确设置 `clean=true`，不暗中改变其他现有步骤的默认语义。独立 CLI 执行 `--step db` 即使未指定 `--clean`，在重新写入 `database.json` 前也须删除该目录已有的 `.job_id` 调试标记，避免新文件误沿用旧 Web 作业 ID；这只使调试标记失效，不额外清理其他产物。是否将未来所有生成步骤默认改为 clean，需单独评估人工编辑文件的覆盖风险。

## 5. 作业执行与调试标记

Web 发起 `db` 采集时，FastAPI 只创建 `queued` 的 `job_info` 并返回 `job_id`；前端通过 API 查询状态，不监控 CLI 进程。另行编写并启动一个独立的 Worker Python 进程（可用 `backend/jobs/worker.py` 的函数和循环实现，不要求 `Worker` 类）：它领取作业，将 `job_info` / `job_step_info` 改为 `running`，按步骤名分派到 MetaWeave 的共享执行函数，最后根据返回结果写入 `success` 或 `failed`。第一阶段分派表只含 `db`；后续 `ddl` 等步骤完成 `source_id` 隔离后再逐项接入，同一个 Worker 可处理多种步骤，不重新实现画像算法，也不需要为每步各写一个 Worker。CLI 与 Worker 是同一业务函数的两个入口；独立运行 `metaweave metadata --step ...` 不写 `job_info`。一个 `job_id` 表示**一次执行**，不表示跨天逐步完成的整份工作区。第一阶段每个 `source_id` 最多允许一个 `queued` 或 `running` 作业；作业入队与同步发布都先锁定同一条 `db_source_info` 记录，以免发布读取文件期间又为该数据源启动采集。第一阶段不支持同一数据源排队多个作业。

| 表 | 第一阶段字段与职责 |
| --- | --- |
| `public.job_info` | `job_id UUID` 主键、`source_id` 外键、请求的步骤列表、`status`（`queued/running/success/failed/interrupted`）、`started_at`、`finished_at`、`worker_id`（主机/进程等排障标识）、本次领取标识、错误摘要及必要的日志定位信息。`worker_id` 只供排障，状态更新仍以本次领取标识防止旧执行者覆写；第一阶段不设置心跳或租约字段。步骤列表第一阶段通常仅含 `db`，为后续多步骤作业预留。 |
| `public.job_step_info` | `job_id` 外键、步骤名、执行顺序、状态、开始/结束时间、产物路径或数量、错误摘要；产物路径存相对项目根目录的路径（如 `output/<source_id>/db/database.json`），不存机器专属绝对路径，供作业详情查看每一步的结果。 |

`job_info` 只记录作业管理所需的信息；本阶段不增加任务配置快照或配置 JSONB 字段，密码和 API Key 也不写入作业记录。

作业的入队、领取与恢复遵循以下数据库契约：

1. 入队使用短事务：先对对应 `db_source_info` 行执行 `SELECT ... FOR UPDATE`，再检查该数据源没有 `queued/running` 作业，随后插入 `queued` 作业并提交。若同一数据源正在同步发布，入队会等待发布事务释放该行锁；不能绕开行锁先查后写。增加 `UNIQUE INDEX ON job_info(source_id) WHERE status IN ('queued', 'running')`，作为同表并发写入的最后防线；唯一约束冲突返回明确的“该数据源已有待执行或运行中作业”，不默默覆盖。
2. Worker 在短事务中使用 `SELECT ... FOR UPDATE SKIP LOCKED` 选取一条 `queued` 作业，并在同一事务将其更新为 `running`、写入本次领取标识、`RETURNING` 作业信息；提交后才执行耗时的 `db` 采集。不能先普通查询再单独更新，也不在采集期间持有数据库行锁。最终状态更新按 `job_id + 本次领取标识 + status=running` 条件执行，防止旧执行者覆写新状态。
3. 第一阶段只有一个 Worker，不做定时心跳、租约续写或自动超时重跑。Worker 重启时检查遗留的 `running` 作业；仅在确认原执行进程已经停止后，才将作业及运行中的步骤记为 `interrupted` 并释放同源占用。无法确认时保持占用，交由管理员处理；`queued` 作业仍可正常领取。以后增加跨主机多 Worker 时，再单独设计存活检测与租约，不让第一阶段为它承担复杂度。

`job_info` / `job_step_info` 是状态的权威来源。Web Worker 执行过的步骤目录另放固定文件名 `.job_id`，仅供开发排障，内容只含 `job_id`、`started_at`、最终 `status`（`success` 或 `failed`）；独立 CLI 没有 Web `job_id`，不生成此标记。异常中断时允许缺少该文件，不把 `interrupted` 写入调试标记。它不记录 `running`、结束时间或文件数量，也不作为 Web UI 或发布流程的权威依据。步骤开始时清除旧标记，正常结束时覆盖写入新标记；现有 `--clean` 遍历步骤输出目录顶层的所有普通文件，也会删除旧的隐藏文件 `.job_id`，不需要特殊清理逻辑。进程意外退出可能没有新标记，应以作业表及重启检查判断。写标记时使用临时文件加原子替换，避免读到半写入内容。

## 6. 发布、版本与数据库概览展示

本节已由 [doc 12](12_发布信息表与发布动作设计.md) 修订。早期“发布失败保留旧当前版本并继续展示”“发布期间锁定数据源行”“从 `.job_id` 推断发布作业”的规则不再适用；不得以本节旧版文字或 §7 的历史验收恢复这些规则。

发布是独立于采集的管理员动作。第一阶段只发布指定 `source_id/job_id` 工作区的 `db/database.json` 到平台 PostgreSQL，在 FastAPI 请求内调用共享加载函数并返回结果；阻塞操作在线程中执行，不引入发布 Worker，不执行采集或 LLM，不清理文件。发布前检查数据源存在且激活、作业归属正确及 db 步骤采集成功。作业身份来自请求与 `job_info`，不依赖 `.job_id`。文件读取不持有平台库事务，不增加显式发布锁或与作业入队共用的数据源行锁。

| 表 | 第一阶段字段与职责 |
| --- | --- |
| `public.publish_info` | 主键 `(publish_id, step_name)`，无外键；每次发布生成新 publish_id，记录 source_id、job_id、status（仅 success/failed）、is_current_publish、发布人、时间及受控错误摘要。同源同步骤至多一行 current。不存 running、逐文件清单、心跳或租约；完整 DDL 以 doc 12 为准。 |
| `public.db_profile` | publish_id 主键，无外键；保存 source_id、job_id 与数据库概览字段，完整表结构以 doc 9 为准。db 发布成功时与 publish_info 共用 publish_id，在同一事务写入；失败发布不生成画像。画像不保存密码、连接级选项或实际 TLS 状态。 |

db 成功事务完成“翻旧 current → 插入 success 发布记录 → 插入同 publish_id 的画像”。可捕获的文件、校验或入库失败回滚成功事务，再用独立短事务“翻旧 current → 插入 failed 发布记录”。**成功、失败都翻 current**；current 指向该 `(source_id, step_name)` 最后完成结果记录提交的一次发布，不按请求开始时间排序。历史成功画像仍保留，但不自动作为当前画像。当前索引冲突回滚并返回 `409 publish_conflict`，不自动重试或补写失败记录；无法持久化结果时不得宣称已记录成败，具体错误规则以 doc 12 为准。

数据库概览读取（例如后续 `GET /api/data-sources/{source_id}/profile`）的规则以 [doc 12 §4](12_发布信息表与发布动作设计.md#4-is_current_publish-语义) 为准，本节不重复维护状态分支。当前发布失败时显示失败，不回退历史成功画像。

失败后的正确处理是由管理员排查并重新发布，不做自动降级。采集失败与发布失败是两个不同状态；未发起新发布不会自行改变已提交的 current。请求前置拒绝、current 索引冲突或进程中断而未提交的尝试，也不会凭空成为 failed current。历史画像可供后续排障与历史查询，不在当前概览里冒充新结果。

具体发布端点、页面和实施范围见 doc 12；数据库概览读取接口、发布历史页面及多步骤接入仍按后续阶段分别实施，不因本节补充读取规则而扩大 doc 12 的开发范围。host/port 仅在管理员页面和管理员 API 展示；不在 db_source_info 重复保存 current_publish_id，也不新增版本切换或删除发布 API。

## 7. 实施顺序与验收

> 本节保留早期阶段规划与验收作历史背景，不是当前开发清单。涉及发布的行锁互斥、失败保留旧当前版本、仅 success 可为 current、外键及 `.job_id` 来源等旧验收已废弃，必须采用 §6 与 doc 12 的修订规则，不得直接据下文旧验收编写代码或测试。作业表与工作区按 doc 9 等后续实施稿执行。

1. 建立平台库连接配置，按各阶段设计中的 SQL 手工创建所需平台表；先实现凭据加解密和数据源连接测试/登记 API。
2. 开发 Vue 3 添加数据源页面，完成 schema 选择与数据源列表。
3. 实现 `--step db`、专属工作目录及 `database.json` 契约；复用 CLI/Worker 的同一执行函数，并增加严格错误处理。
4. 实现单 Worker 作业领取、状态持久化、Web 发起/查看采集与 `.job_id` 调试标记。
5. 实现发布事务、历史版本及数据库概览 API/UI。

最低验收用例：数据源 UUID 与目录一致；真实密码不出现在 API/日志/文件产物中，密钥缺失时拒绝解密；连接与权限失败不被显示为零对象；连接检查的 Web 可选列表不包含 `pg_catalog`、`information_schema`、`pg_toast`、`pg_temp_*`、`pg_toast_temp_*`，包括当前会话的临时 schema；未选中的无权限 schema 不阻断发现，而已选 schema 不存在、登记后被删除、无 `USAGE` 权限分别报错，确实为空的已选 schema 才记录零对象；一个顶层分区父表及 12 个叶子分区计为 1 个分区表、12 个分区子表，对象合计只增加 1；序列、外部表、复合类型及画像生成配置的过滤项不改变对象合计，整库大小取 `pg_database_size(current_database())` 而非所选 schema 大小；同一数据源重复采集只清理自身的 `db/`；采集 A 数据源并清理其 `db/` 时，B 数据源目录及文件保持不变；采集失败保留上次已发布画像；发布失败保留失败记录且不切换当前版本；页面展示来自平台库而非现场读取 `database.json`；同一数据源写入作业与发布互斥；`.job_id` 只含约定的三个字段且不参与页面状态判断。

版本与表模型验收：`db_source_info` 不含通用 `status` 或 `current_publish_id` 字段；`publish_info.status` 只接受 `success/failed`，同一 `source_id` 最多一条 `is_current_publish=true` 的成功记录；成功发布恰有一条同 `publish_id` 的 `db_profile`，失败发布没有画像。新发布全部成功后旧当前标记与新当前标记在同一事务内切换；失败时旧当前版本保持可见。`db_profile.job_id` 仅用于排障：成功 Web 作业留下有效 `.job_id` 时可填，独立 CLI 产物或标记缺失时为 `NULL`；`database.json` 缺少 `schema_version` 或写入 `0`、`2`、非整数时发布失败，保留此前的当前发布版本。

补充验收：未计算行数时，JSON `record_count` 为 `null`、平台库对应值为 `NULL`、页面显示“—（未采集）”；连接检查使用用户提交的 `host`、`port` 建连，域名由 libpq 解析，不做目标 IP 禁止清单、`hostaddr` 固定或应用层并发限流，正常私网 PostgreSQL 可连接。创建请求和后续 `db` 采集各自重新建连并检查版本与 Schema。本阶段仅管理员页面/API 展示 host/port，不提供公开的含连接信息目录接口；作业记录的 `worker_id` 与本次领取标识各司其职，步骤产物路径为项目根相对路径；连续两次 Web `db` 作业后工作区不保留首轮未发布 JSON，已发布画像仍可通过发布历史查看。

调试标记验收：`--step db --clean` 会删除旧 `.job_id`；独立 CLI 即使不带 `--clean`，重新写入 `database.json` 前也清除旧标记且不写新的 Web `job_id`；Web Worker 成功完成后写入当前作业标记。发布时标记缺失或不能核实归属，`db_profile.job_id` 留空而发布仍可成功。

路径兼容验收：本阶段执行 `db` 步骤前后，既有 `output/ddl`、`output/md`（含人工编辑文件）及其他旧步骤目录保持原样；默认 `configs/pipeline.yaml` 与现有 metadata 步骤的读写路径不因引入 `source_id` 目录而改变。

并发与恢复验收：Worker 按步骤名调用共享执行函数并负责写 `job_info` / `job_step_info` 状态，独立 CLI 不创建 Web 作业；第一阶段分派表仅含 `db`。两个 Worker 竞争同一 `queued` 作业时仅一个领取成功；同一数据源并发入队最多一个成功，`queued/running` 作业阻止同步发布；作业入队与发布并发时，共同的 `db_source_info` 行锁使两者串行，发布读取文件期间不会开始同源采集，且不会出现同源两次并发发布；发布请求意外中断后没有持久 `running` 记录，未提交的画像与版本切换均回滚。采集 Worker 异常退出后不依靠租约自动判死或重跑；重启检查发现遗留 `running`，确认旧进程停止后才记为 `interrupted` 并释放占用，无法确认时保持占用；其他数据源的作业和发布不受影响。

`db` 接线验收：`metadata --step db --source-id <UUID>` 与 Web Worker 产生同口径的 JSON；两入口对主配置中非法 LLM 路径或废弃关系配置节点给出相同的执行前错误，Worker 内存配置不得绕过校验，`job_info` 不保存配置快照；手工运行也须先登记数据源并提供平台库连接和 `SOURCE_CREDENTIAL_KEY`，平台库不可用、数据源不存在、密钥缺失或解密失败时不清理、不连接源库，且不回退到主配置、`.env` 的 `DB_*` 或 CLI 临时凭据；`--source-id` 缺失、重复、非法，或在非 `db` 步骤传入时均在副作用前拒绝；`--step db` 显式传 `--schemas`、`--tables`、其他不适用的步骤参数或混用 `--generate-*` 时以 exit 2 拒绝，不静默覆盖或忽略；主配置的源库连接、schema、对象过滤、采样、LLM 及输出目录均不能改变 `db` 的来源和统计口径，连接池参数可按上表使用；`db --clean` 只清当前 `source_id` 的 `db/`，不读写主配置推导的通用 `output/db/`；pipeline YAML 写入 `metadata.db` 被拒绝，其他 pipeline/metadata 步骤的既有行为不因本阶段改变。

连接验收：添加数据源页面与 API 可以提交可选 `sslmode`，连接测试、schema 发现、独立 CLI 与 Worker 的 `db` 采集均使用数据源记录中的同一值；有值时经规范化后作为单独参数传入（doc 18.1 修订：先规范化——去首尾空白、转小写——再作为单独参数传入），未填写时连接参数中没有 `sslmode`，不补应用默认。平台库的可选 `PLATFORM_DB_SSLMODE` 同理，未设置时不传；平台库连接仍有 10 秒建连超时，不读取源库主配置。~~不做应用层 `sslmode` 白名单校验：不被 libpq 接受的值在连接时失败~~（doc 18.1 修订：六模式值域校验，非法值在建连前拒绝）；包含空格或 `host=...` 等文本的值不得被拆成额外连接参数。域名原值直接作为 `host` 传入，由 libpq 处理解析和 `verify-full` 的证书名称校验；带空格或特殊字符的密码不会改变连接参数解析，也不会泄露到日志。现有 `ddl/json/rel` 的源库连接行为不变；正式部署前分别确认源库与平台库的实际 TLS 策略。

打包与依赖验收：构建出的发行包包含 `backend*`，但只安装基础依赖、不安装 `platform` extra 的环境仍可执行 `metaweave --help`、`metadata --help` 及既有 CLI 步骤；在确实缺少平台依赖的环境运行 `metadata --step db` 时明确提示安装 `platform` extra，且不因缺依赖产生清理或采集副作用。安装 `platform` extra 后，FastAPI、Worker、Fernet 加解密和 `db` CLI 入口均可导入并通过相应测试；任何平台模块不得通过顶层导入反向影响既有 CLI。

## 8. 后续阶段边界

后续再把 `json/` 表画像、字段画像及必要的关系信息按 `publish_id` 写入平台库，扩展发布范围和目录页面；再增加完整 `metadata/pipeline/rag_load` 的 Web 编排、更多数据源类型及目标库隔离。届时发布历史与源文件保留策略可以分别制定：删除旧工作文件不应影响已发布的页面，但若要从旧文件补跑加载或重放，仍需保留或重新生成相应产物。

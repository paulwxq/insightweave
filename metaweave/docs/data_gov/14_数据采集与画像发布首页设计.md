# 数据采集首页与画像发布首页设计

本次只增加两个浏览首页，并把侧栏导航接到这两个首页。采集执行页、画像发布执行页、按数据源挑选采集作业的页面都已经可用，本次不改它们的执行逻辑。

- 数据采集首页原型：`docs/data_gov/ui/数据源管理到发布/11.数据采集首页.html`、`11.数据采集首页.png`
- 画像发布首页原型：`docs/data_gov/ui/数据源管理到发布/12.画像发布首页.html`、`12.画像发布首页.png`
- 新建发布所进入的选作业页原型：`docs/data_gov/ui/数据源管理到发布/8.从数据源新建画像发布(选择采集作业).png`

日期：2026-09-29。状态：已按本文实施。

## 1. 目标与范围

### 1.1 目标

1. 新增**数据采集首页**：左侧选数据源，右侧列出该数据源的采集作业。选中一条作业后，「重新执行」打开已经做好的采集执行页，并带上该 `job_id`。「新建采集作业」打开已经做好的新建采集页，并带上当前选中的 `source_id`。
2. 新增**画像发布首页**：布局与上一页相同。选中一条发布后，「重新执行」打开已经做好的画像发布页，并带上该 `publish_id` 与其所属 `job_id`。「新建发布作业」打开已经做好的「从数据源新建画像发布（选择采集作业）」页，并带上当前选中的 `source_id`。
3. 侧栏按原型 11、12 的可见效果补上「数据采集」「数据画像」，并给导航文字前面换上这两张图里的图标。左上角品牌图形保持不动。

### 1.2 本次不改

| 不改 | 说明 |
| --- | --- |
| `CreateCollectionJobView.vue` | 新建页不预选步骤；带 `?job_id=` 时按该作业已保存且当前仍可选的步骤回填，并在同一 `job_id` 上执行。首页只负责把参数放进地址 |
| `PublishView.vue` | 不带 `publish_id` 时不预选；带 `publish_id` 时只勾选该次发布里当前仍可发布的步骤。首页只负责带上 `job_id` 与 `publish_id` |
| `CollectionJobsView.vue`、`PublishJobsView.vue` | 某个数据源自己的作业列表保持原样，分页大小、按钮文案都不改 |
| 采集与发布的执行接口 | `POST .../collection-jobs`、`POST .../publications`、预检 `publish-check` 都不改 |
| `job_info`、`publish_info` 表结构 | 不新增状态值，不把发布改成异步 |

### 1.3 与既有文档的关系

| 文档 | 本文如何使用 |
| --- | --- |
| doc 9 | 采集作业身份是 `job_id`；一个作业的每个步骤一行，`last_status` 只有 `running` / `success` / `failed` |
| doc 12 | 发布身份是 `publish_id`；`status` 只有 `success` / `failed`，没有 `running`。重新发布是新的 `publish_id`，不改旧行 |

与上述文档冲突时，表结构和执行语义以那些文档为准。本文只规定两个首页怎么读这些数据、怎么跳进现有页面。

## 4. 跳进已经做好的页面

选中的数据源来自左侧列表，选中的作业来自右侧单选。没选中作业时，「重新执行」不可用。数据源 `is_active=false` 时，「新建」和「重新执行」都不可用，与现有列表页的置灰规则一致；禁用数据源仍然可以出现在左侧，便于查看历史作业。

数据采集首页还有一条：选中作业的汇总状态是 `running` 时，「重新执行」不可用，「新建采集作业」仍然可用。原因是现有重跑只会提交 `db`，而 `start_step()` 在该步骤行仍为 `running` 时抛出 `StepAlreadyRunningError`，请求返回失败结果，消息是「当前步骤可能已有作业正在执行」。这只是响应失败，`job_info` 行保持 `running`：`db_step_service.py` 在 `start_step()` 拒绝后走 `_failure()`，不调用 `finish_step()`，不会把该行写成 `failed`。首页统计继续按库里的 `running` 计入「正在执行」，不要因为这次失败响应把该作业算进失败数。按钮用 `title` 标出这句现有消息，不新写一套文案，也不改采集执行页：直接打开带 `job_id` 的地址时，仍由后端按原规则拒绝，状态同样不变。画像发布没有 `running`，这条只约束采集首页。

| 首页按钮 | 现有页面 | 首页使用的地址 |
| --- | --- | --- |
| 新建采集作业 | `CreateCollectionJobView.vue` | `/data-collection/{sourceId}/new` |
| 重新执行（采集） | 同上 | `/data-collection/{sourceId}/new?job_id={jobId}` |
| 新建发布作业 | `SelectPublishJobView.vue` | `/profile-publishing/{sourceId}/new` |
| 重新执行（发布） | `PublishView.vue` | `/profile-publishing/{sourceId}/jobs/{jobId}/publish?publish_id={publishId}` |

这四个地址是新增路由，组件仍是上表已有页面，参数名仍是 `sourceId`、`jobId`，查询参数仍是 `job_id`、`publish_id`。除下面这一处「下一步」外，页面内部不改。

`AppSidebar.vue` 现在把凡是以 `/data-sources` 开头的地址都高亮为「数据源管理」。若首页沿用旧地址，点「新建」或「重新执行」后高亮会离开「数据采集」或「数据画像」。这不是预期。

高亮只看路径前缀，不看来路：

| 路径前缀 | 高亮 |
| --- | --- |
| `/data-sources` | 数据源管理。数据源管理、采集作业列表、发布作业列表上的原有链接都留在这里，不改那些链接 |
| `/data-collection` | 数据采集 |
| `/profile-publishing` | 数据画像 |

因此从首页进入执行页时，高亮留在对应菜单。从数据源管理进入同一组件时，高亮仍是「数据源管理」。

新建发布不能在中途换高亮。`SelectPublishJobView.vue` 现在的「下一步：发布数据画像」固定跳到 `/data-sources/{sourceId}/collection-jobs/{jobId}/publish`。从 `/profile-publishing/{sourceId}/new` 点下去，高亮会从「数据画像」变成「数据源管理」。这不是预期。这一处链接按当前路径前缀选择地址，不改选择页的其他行为：

| 当前页面 | 下一步地址 | 到达后的高亮 |
| --- | --- | --- |
| `/profile-publishing/{sourceId}/new` | `/profile-publishing/{sourceId}/jobs/{jobId}/publish` | 数据画像。不带 `publish_id`，执行页不预选步骤 |
| `/data-sources/{sourceId}/publish-jobs/new` | `/data-sources/{sourceId}/collection-jobs/{jobId}/publish` | 数据源管理。这是发布作业列表上的原有入口，地址保持不变 |

「返回」回退、「修改数据源」，以及采集新建页上的「下一步：执行画像发布」，仍然指向 `/data-sources/...`。那些是离开当前流程，本次不改；用户点了之后高亮按前缀表转到「数据源管理」。

行上的圆形选择只负责选中，不直接跳转。原型行尾的箭头同样只表示选中，不另开详情页。

## 5. 复用哪些现有数据

### 5.1 左侧数据源

直接使用已有 `GET /api/data-sources`。`DataSourceListItem` 已有 `source_id`、`display_name`、`db_type`、`host`、`port`、`db_name`、`is_active`。左侧副标题用 `{db_type} · {host}:{port} · {db_name}`。

这次列表请求失败时，沿用数据源页的 `state-block error-state` 和「重试」。「重试」再请求 `GET /api/data-sources`。此时不选数据源，右侧不出现作业列表，「新建」和「重新执行」不可用。

数据库类型下拉只列出当前登记数据源里实际出现的 `db_type`。现在登记只接受 `postgresql`，原型里的 MySQL、SQLite 是示例，不为此增加数据库种类。筛选在前端完成。当前选中的数据源被筛掉时，改为选中筛选结果的第一条；没有结果时右侧为空，两个操作按钮不可用。

默认选中筛选后的第一条数据源。

选中的数据源一旦换成另一条（点左侧另一条，或筛选把选中改成另一条），立刻做这三件事，两个首页相同：

1. 清掉右侧已选作业，页码回到第 1 页，并清掉上一数据源的作业列表和三张统计卡。按钮地址只用当前选中的 `source_id`，以及这次响应该数据源后用户重新选中的作业。不能带着甲数据源的 `job_id` 去拼乙数据源的地址。换到只有 1 页的数据源时，不能停在原来的第 3 页而显示出空白。
2. 这次首页请求返回之前，「新建」和「重新执行」都不可用。加载中不能用上一份列表里的作业执行。
3. 只采纳最后一次发出的那次请求的响应。更早请求的迟到响应整段丢掉，不更新列表、统计、选中，也不更新按钮所用的数据源。快速从甲切到乙时，甲的响应晚到也不能把甲的作业画出来。

筛选后选中的仍是原来那条数据源时，不重新请求，也不清掉已选作业。没有筛选结果时没有当前数据源，两个按钮不可用。

首页数字不是一直停在进入时的快照，也不定时刷新。进入该首页路由时请求一次，包括从执行页返回后再次进入。之后用户若留在页面上，作业在别处完成，卡片和列表不会自己变。两个首页都在右侧工具最左侧放「刷新」，样式沿用数据源列表的 `ds-refresh`。原型 11、12 没有这个按钮。它重拉当前数据源的首页接口，不换数据源，不先清空列表，也不把排序或页码重置到第 1 页。请求未返回时「刷新」不可用。新响应到达后更新三张卡、列表和该数据源的 `is_active`。页码仍停在原页；若原页超过新的总页数，则改到最后一页。总页数为 0 时停在第 1 页。原来选中的作业还在当前这一页则保持选中，不在当前页或不在列表里则清掉选中。「重新执行」只针对当前页上看得到的那条作业。这次请求仍遵守上面的「只采纳最后一次」：刷新过程中若换成另一条数据源，刷新的响应整段丢掉，并按切换规则清空旧列表、页码回到第 1 页。不使用 `setInterval` 或其它定时重拉。

用户翻页，或切换执行时间正序/倒序时，清掉已选作业。排序切换本身仍回到第 1 页。不把页面自动跳到选中行所在的那一页。

首页响应带上当前数据源的 `is_active`。进入页面、切换数据源和点击「刷新」都用这次响应更新按钮和左侧当前行的启停显示，不沿用进入页面时 `GET /api/data-sources` 里的旧值。数据源在别处被禁用后，点「刷新」必须让「新建」和「重新执行」变为不可用。左侧其他数据源的启停仍只在进入页面时由数据源列表决定。

首页请求失败时，错误样式沿用数据源列表的 `state-block error-state`，文案用接口返回的 message。不新做一套错误页。404 和临时失败分开处理。

`503 platform_unavailable` 以及其他非 404 失败：还没有成功结果时，右侧只显示错误和「重试」，「重试」再发同一次首页请求，「新建」和「重新执行」不可用，不留上一数据源的列表。已经有成功结果时，三张卡、列表、页码、选中和 `is_active` 保持上次成功的结果，按钮按那次结果继续可用，错误块放在这些内容上方。

`404 not_found`（数据源不存在）：清掉作业选择，「新建」和「重新执行」不可用。不保留可点击的旧按钮。错误文案用接口返回的「数据源不存在」，并说明左侧列表已过期，按钮改为「刷新数据源列表」，再请求 `GET /api/data-sources`。列表返回后，若当前 `source_id` 已不在其中，按筛选掉当前数据源的规则处理：改选剩余的第一条，没有剩余则右侧为空、两个操作按钮不可用。

### 5.2 不要改现有列表接口的响应

下面两个接口已经分别被「某数据源的采集作业列表」「选择采集作业」「某数据源的发布作业列表」使用：

- `GET /api/data-sources/{source_id}/collection-jobs`
- `GET /api/data-sources/{source_id}/publish-jobs`

它们的条目没有步骤状态，也没有首页要的三张统计卡。不要把状态塞进这两个响应：`CollectionJobItem`、`PublishJobItem` 以及对应的组装函数 `assemble_collection_jobs()`、`assemble_publish_jobs()` 会被现有页面继续原样消费。

首页另建只读查询，内部仍读取同一批表行：

- 采集：`list_source_step_rows()`（`backend/jobs/repository.py`）
- 发布：`list_source_publish_rows()`（`backend/publishing/repository.py`）
- 数据源是否存在、是否启用：`get_db_source()`

执行时间的口径与现有列表相同，避免两套时间：

- 采集：该 `job_id` 全部步骤行 `updated_at` 的最大值
- 发布：该 `publish_id` 全部步骤行 `created_at` 的最大值

步骤名的顺序也沿用现有列表：采集按 `created_at`、`step_name`；发布仍用 `listing.py` 里画像步骤与 RAG 步骤的划分，首页把两组按这个顺序拼成一行标签。

### 5.3 新增的只读接口

| 方法与路径 | 作用 |
| --- | --- |
| `GET /api/data-sources/{source_id}/collection-home` | 该数据源的采集作业、每条作业的汇总状态、三张统计卡 |
| `GET /api/data-sources/{source_id}/publish-home` | 该数据源的发布作业、每条发布的汇总状态、三张统计卡 |

数据源不存在返回现有的 `404 not_found`。平台库不可用返回现有的 `503 platform_unavailable`。这两个路径是固定段，不会和 `collection-jobs/{job_id}`、`publish-jobs/{publish_id}` 抢路由。失败时的页面表现见第 5.1 节：503 等临时错误在已有成功结果时保留该结果；404 禁用两个操作、清除作业选择，并提示刷新数据源列表。

响应只服务首页，不参与执行。下面是采集首页的形状；发布首页的 `counts` 换成 `{ "current": 0, "success_recent": 0, "failed": 0 }`，条目里的 `publish_id` 为实际 UUID。

```json
{
  "is_active": true,
  "counts": { "running": 0, "success_recent": 0, "failed": 0 },
  "items": [
    {
      "job_id": "…",
      "publish_id": null,
      "executed_at": "2026-09-28T14:49:23Z",
      "steps": ["db"],
      "status": "success"
    }
  ]
}
```

采集响应的 `publish_id` 固定为 `null`。发布响应必须同时给出 `publish_id` 和 `job_id`，因为现有发布页的地址需要这两个值。不要只返回原型说明文字里写的 `job_id`。

`status` 取值：

| 页面 | 允许的值 | 如何从多行收成一条 |
| --- | --- | --- |
| 采集 | `running` / `success` / `failed` | 该 `job_id` 任一步骤为 `running` 则整条为 `running`；否则任一步骤为 `failed` 则为 `failed`；否则为 `success` |
| 发布 | `success` / `failed` | 该 `publish_id` 任一步骤为 `failed` 则为 `failed`；否则为 `success` |

统计卡按**当前选中的数据源**计算，不跨数据源相加。两页的后两张卡相同，第一张卡不同。

采集首页的 `counts`：

- `running`：汇总状态为 `running` 的作业条数。只在进入页面、切换数据源和点击「刷新」时重算，见第 5.1 节。留在页面上时不会自己变成 0
- `success_recent`：汇总状态为 `success`，且执行时间落在当前时刻往前 30 天之内（含边界）的条数
- `failed`：汇总状态为 `failed` 的条数，不限 30 天。这对应卡片说明「需要关注并重试的失败作业」

画像发布首页不使用 `running`。`publish_info.status` 没有这个值，同步发布也不会留下运行中的行，所以不能做「正在执行的发布作业」，也不允许把这张卡实现成恒为 0。第一张卡改为现有列能算出的指标：

- `current`：该数据源上 `is_current_publish=true` 且 `status='success'` 的步骤行数。部分唯一索引保证每个步骤至多一行当前发布，因此这是当前成功的发布步骤数，不是 `publish_id` 的个数。现在只有 `db` 可发布，所以这个数是 0 或 1。当前行若是 `failed`，不计入这张卡。只查 `publish_info`，不查 `db_profile`
- `success_recent`、`failed`：与采集首页同一口径，只是对象换成发布作业

这张卡统计的是当前成功发布记录，不是当前可用画像。`backend/assets/catalog.py` 的 `assemble_asset_catalog()` 对 current 且 `success` 的发布还会核对 `db_profile`：画像缺失或 `source_id` 对不上时记为 `inconsistent`，不进入可用目录；画像页 `assemble_asset_profile()` 此时返回 `state=inconsistent`。发布首页不读 `db_profile`，所以这张卡可以是 1，而画像页仍不可用。不要把算法改成只统计 `state=ready` 的画像。

发布首页三张卡的文案固定为「当前成功发布」「成功执行的发布作业」「失败的发布作业」。第一张卡的说明固定为「该数据源当前成功的发布步骤数」。不要用「当前生效的发布」，以免和画像页的可用状态混在一起。不要沿用原型的「正在执行的发布作业 / 正在运行画像发布作业」。

排序和分页放在前端，与 `SelectPublishJobView.vue` 一样：默认按执行时间倒序，按钮再点一次改为正序并回到第 1 页。每页 10 条。接口一次返回该数据源的全部条目，不新增分页参数。翻页和切换排序都清掉已选作业。切换数据源或筛选改选另一条数据源时页码回到第 1 页。刷新不主动回到第 1 页；原页超过新总页数时改到最后一页。

作业行上的主文字使用真实的 `job_id` 或 `publish_id`（发布行以 `publish_id` 为主文字，因为重新执行认的是它）。不生成 `job_YYYYMMDD_HHMMSS` 这种展示名。

## 7. 对接时已经看到的问题

这些问题不阻止按第 4 节跳转，但实现时不能按原型示例字面照做。

1. **发布首页第一张卡不统计「正在执行」，也不统计可用画像**。`publish_info.status` 只有 `success` / `failed`，发布在请求内同步完成，没有运行中的行。因此不保留原型里的「正在执行的发布作业」，也不把它做成长期为 0 的卡片。第一张卡是 `current`：当前成功的发布步骤数，卡片名称是「当前成功发布」。它不查 `db_profile`。画像缺失时资产目录记为 `inconsistent`、画像页不可用，这张卡仍可以是 1。要做真正的「正在执行」必须另做异步发布和表结构，那不在本文范围，也不给 `publish_info` 增加 `running`。
2. **原型 12 的说明写成了「右侧选择发布作业（job_id）」**。现有发布页地址同时需要 `job_id` 和 `publish_id`。只带 `job_id` 会打开一个不预选步骤的新发布页，那是「新建」之后再选采集作业的路径，不是「重新执行」。首页重新执行必须带上 `publish_id`。
3. **原型里的作业名不是库里的标识**。现有页面展示 UUID。首页同样展示 UUID，不另造 `job_20260925_110204`。
4. **数据源已禁用时，现有执行页会拒绝执行**。首页在禁用数据源上直接禁用「新建」和「重新执行」，避免进入后再看到执行按钮不可用。历史作业仍可列出。
5. **侧栏「数据画像」容易和数据库画像页、页面大标题混淆**。这一项只打开 `/profile-publishing`。侧栏文字用图 11、12 上的「数据画像」；页面里的大标题仍是「数据画像发布」。
6. **现有某个数据源的发布列表按钮文案是「重新发布」**。首页按原型写「重新执行」，两者打开的是同一个 `PublishView`。本文不改那个列表页的文案，它的地址仍在 `/data-sources/...` 下，高亮仍是「数据源管理」。
7. **从首页进入执行页不能沿用 `/data-sources` 地址**。否则现有侧栏会把高亮改成「数据源管理」。首页四条按钮使用第 4 节的新前缀；原有入口不改。选择作业页的「下一步」也按当前前缀走，新建发布流程不能在这一步切回「数据源管理」。
8. **运行中的采集作业不能从首页重新执行**。`backend/jobs/repository.py` 的 `start_step()` 拒绝仍为 `running` 的步骤，请求返回失败，原 `job_info` 行仍是 `running`。采集首页对汇总状态为 `running` 的作业禁用「重新执行」，并标明「当前步骤可能已有作业正在执行」。不修改 `start_step()`，不把这次拒绝写成 `failed`，首页失败数也不计入这类作业。不在执行页上提前禁用「执行」。
9. **切换数据源不能沿用上一份作业列表**。点另一条数据源，或筛选把选中改成另一条时，按第 5.1 节立刻清掉已选作业和旧列表，加载中禁用「新建」和「重新执行」，并丢掉更早请求的迟到响应。否则可能一边显示甲的作业，一边用乙的地址执行。
10. **导航图标不安装 Lucide**。`frontend/package.json` 只有 `vue` 和 `vue-router`。图标按第 3 节用内联 SVG，不改依赖文件。窄屏不能再隐藏未高亮的导航链接，否则新增的两个入口无法切换。
11. **图标颜色不能跟随链接文字**。选中项图标是 `#2E7CD6`，文字是 `#17293F`。现有 `.nav-icon` 固定 `#3e7aca`，链接悬停和选中又共用 `#244e86`。按第 3 节给 `.nav-icon` 单独设两态，并同步改侧栏文字色；`currentColor` 只继承图标容器。
12. **「正在执行」不会在停留期间自己更新**。采集首页的 `running` 只在进入路由、切换数据源和点击「刷新」时重算。不定时轮询。发布首页同样用这个「刷新」，虽然它没有 `running`。
13. **页码和选中不能脱节**。切换数据源回到第 1 页。刷新保留页码，但不超过新的总页数。翻页、切换排序，以及刷新后选中行不在当前页时，清掉选中，不自动跳到该行所在页。
14. **刷新要带回数据源是否启用**。首页响应含 `is_active`。不能只靠进入页面时的数据源列表，否则别处禁用后本页仍会放出「新建」和「重新执行」。
15. **只有临时失败才保留上次成功的结果**。503 和其他非 404 错误沿用数据源列表的错误块。已有成功结果时列表和按钮保持那次结果；还没有成功结果时右侧只有错误，操作按钮不可用。404 不保留可点击按钮：清掉作业选择，禁用「新建」和「重新执行」，并提示刷新数据源列表。`GET /api/data-sources` 失败时同样用数据源页的错误块和「重试」，不选数据源，操作按钮不可用。

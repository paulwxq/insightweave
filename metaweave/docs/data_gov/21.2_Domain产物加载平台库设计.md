# 21.2 Domain 产物加载平台库设计

状态：**已实施**（代码、测试与平台库建表已完成；发布页浏览器验收见 §7 待人工执行）。

本篇把 Web 受管 Domain 产物 `output/<source_id>/<job_id>/domain/db_domains.yaml` 加载进平台库表 `table_domain`，使调用方能按 `schema_name` + `table_name` 查到该表属于哪些 domain。生成步骤见 [21.1](21.1_Web采集Domain生成步骤与数据源描述编辑改造计划.md)。本篇不改生成逻辑。

页面入口在发布页「b.) 对表进行抽样画像」增加 `domain`。该作业的 domain 采集已成功，且 `db_domains.yaml` 存在并为普通文件时可以勾选。预检不解析表映射行数。点击发布后，与 ddl、json 一样写入平台库。不新增命令行加载。

## 1. 现有加载命令没有这条能力

两条命令的目的地不同，都没有读 `db_domains.yaml`。

| 命令 | 现有类型 | 写入哪里 |
|---|---|---|
| `metaweave meta_load` | 仅 `--type db` | 平台库 `db_profile`（`metaweave/cli/meta_loader_cli.py`，`backend/profile_loading/db_loader.py`） |
| `metaweave rag_load` | `sql` / `table_schema` / `dim_value` / `cql` | Milvus 或 Neo4j（`metaweave/cli/loader_cli.py`，`metaweave/core/loaders/`） |

Domain 映射要留在平台 PostgreSQL，只由 Web 发布写入。不扩展 `meta_load`，也不放进 `rag_load`。现有 CLI 没有把这份 YAML 加载进平台库的命令。`metaweave/core/domains/resolver.py` 的 `DomainResolver` 会读同格式文件，供 `--generate-sql-rag` 使用，但缺文件只告警、非法条目会跳过。发布侧不复用它，因为文件打不开或内容不合法必须让本次发布失败。

读取路径只用受管产物 `output/<source_id>/<job_id>/domain/db_domains.yaml`。CLI `--generate-domains` 写的 `output/domains/db_domains.yaml` 不读、不迁移。

## 2. 产物里一张表可以属于多个 domain

`db_domains.yaml` 的结构是：

- `database.name`：库名
- `database.description`：库级说明，本篇不入库
- `domains[]`：每项有 `name`、`description`、`tables`
- `tables` 的每一项是三段式 `数据库.schema.表名`，例如 `orders.public.users`

提示词要求一张表最多归入 `llm_inference.max_domains_per_table` 个 domain（默认 3）。生成和发布都不核对该上限，模型多归入的成员关系仍然全部入库。当前样例里同一张表已经出现在多个 domain：

| 表 | 出现的 domain |
|---|---|
| `orders.public.users` | 用户管理、订单交易 |
| `orders.public.products` | 商品管理、订单交易 |
| `orders.public.categories` | 商品管理、销售分析 |
| `orders.public.cinema_halls` | 影院管理、排片放映 |

因此主键不能只有 `source_id + schema_name + table_name`。那样每个表只能留一行，后写入的 domain 会覆盖先写入的，查询结果不再完整。

查询方式不变：`WHERE source_id = ? AND schema_name = ? AND table_name = ?` 返回该表的全部 domain 行。一行就是一个 domain。

## 3. 表 `table_domain`

平台库 `public.table_domain`。`schema_name`、`db_name`、`job_id`、`publish_id`、`loaded_at` 与 `table_profile`、`table_definition` 相同：`publish_id` 是最后一次成功写入这行的发布，`loaded_at` 是这次写入的时间。第三段列名用 `table_name`，不用 `object_name`：查询按表名，这一列保存三段式名称的第三段，视图和物化视图也写在这里。

不设 `created_at` 与 `updated_at`。整份替换时两列总会写成同一次加载时间，和兄弟表的单列 `loaded_at` 重复。全仓没有 `create_at` 这个列名。

| 列 | 类型 | 约束 | 含义 |
|---|---|---|---|
| `source_id` | uuid | 主键 | 数据源 |
| `schema_name` | text | 主键 | 三段式名称的 schema |
| `table_name` | text | 主键 | 三段式名称的第三段 |
| `domain_name` | text | 主键 | domain 名称，含 `_未分类_` |
| `domain_desc` | text | 非空 | 该 domain 的 description |
| `db_name` | text | 非空 | 登记快照中的库名 |
| `job_id` | uuid | 非空 | 产生这份 YAML 的采集作业 |
| `publish_id` | uuid | 非空 | 最后一次成功写入这行的发布。同一 `job_id` 可以多次发布，只靠 `job_id` 分不出是哪一次 |
| `loaded_at` | timestamptz | 非空，默认 `now()` | 本次替换写入的时间 |

模型加在 `backend/persistence/models.py`。应用不自动建表，由开发在平台库执行下面的 SQL。不建外键。删源时是否删除这些行不在本篇，见 [100 备忘录](100_备忘录.md) 第 4 条。

```sql
CREATE TABLE public.table_domain (
    source_id uuid NOT NULL,
    schema_name text NOT NULL,
    table_name text NOT NULL,
    domain_name text NOT NULL,
    domain_desc text NOT NULL,
    db_name text NOT NULL,
    job_id uuid NOT NULL,
    publish_id uuid NOT NULL,
    loaded_at timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT table_domain_pkey
        PRIMARY KEY (source_id, schema_name, table_name, domain_name),
    CONSTRAINT table_domain_names_not_blank CHECK (
        length(btrim(schema_name)) > 0
        AND length(btrim(table_name)) > 0
        AND length(btrim(domain_name)) > 0
        AND length(btrim(domain_desc)) > 0
        AND length(btrim(db_name)) > 0
    )
);
```

## 4. 发布步骤里的写入

加载只发生在 `publish_steps` 选中 `domain` 时。`publish_id` 仍由现有 `publish_steps` 在前置检查通过后统一生成，再传给本步骤。不另做 `load_domain_mapping(source_id, job_id)`，也不让加载函数自己生成 `publish_id`。

`backend/publishing/publish_service.py` 的预检循环、产物分支、`_INSPECTORS` 登记和 `registrations` 快照写入都要改。`_PUBLISHERS` 不加入 domain，与 json 相同：`_publish_json` 也不在这个字典里。调用只走下面的专用分支。

- `check_publication` 的迭代元组现在是 `(DB_STEP, DDL_STEP, JSON_STEP, TABLE_SCHEMA_STEP)`。必须加入 `domain`，否则预检响应里没有这一步。
- 产物就绪不要走现有 `else`。该分支调用 `check_json_output_ready`。新增 `check_domain_output_ready(source_id, job_id)`。先用 `resolve_domain_output_dir` 得到目录，再判断其中的 `db_domains.yaml` 存在且是普通文件。目录路径上有符号链接时解析函数会拒绝，预检按产物不可用处理。不要在预检里数表映射行数。零行仍可勾选，留到发布时按本节记失败历史。文件或目录不可用时 `reason` 使用现有 `OUTPUT_REASON`（「产物不存在或不可用」）。
- `_INSPECTORS["domain"]` 与 JSON 检查器一样：先确认源存在、源仍启用、工作区属于该源，再返回 `job_info(domain)` 的 `last_status` 与 `updated_at`。不符时上抛现有异常。`publish_steps` 只调用本次所选步骤的检查器，作业准入只汇总状态；只发布 domain 时，这项校验发生在生成 `publish_id` 之前。检查器不读登记快照，也不校验 `db_type`。登记快照仍在步骤成功时由 `read_registration_snapshot` 读取。提交前的锁下复查保留。
- `publish_steps` 在 domain 步骤状态为 `success` 时，与 json 一样调用 `read_registration_snapshot`，把 `db_name`、`selected_schemas`、`updated_at` 写入 `registrations["domain"]`。现在这段只判断 `step_name == JSON_STEP`。domain 不写入 `registrations`，后面取快照会 `KeyError`。
- `_publish_domain(settings, source_id, job_id, publish_id, expected_run_marker, registration)`。`expected_run_marker` 是步骤行的 `updated_at`。`registration` 是上面的登记快照。`publish_id` 仍由 `publish_steps` 在前置检查通过后统一生成。分发时 domain 与 json 一样走专用分支，把 `registrations[step]` 作为第 6 个参数传入。现有 `else` 只向 `_PUBLISHERS[step]` 传 5 个参数；domain 掉进这个分支会 `TypeError`。db、ddl 仍走 5 参，不把通用分支改成一律 6 参。`_publish_domain` 不登记进 `_PUBLISHERS`。

产物读取与解析放在新文件 `backend/profile_loading/domain_loader.py`，职责仿 `json_loader.py`。这个文件提供 `_INSPECTORS["domain"]` 使用的检查函数、`check_domain_output_ready`，以及 YAML 的加固读取和解析。解析只返回待插入的行，不写平台库、不提交。`_publish_domain` 仍在 `publish_service.py`，负责锁、复查和事务。

先在锁外按登记快照解析 YAML。解析失败、零行、至少一行这三态，都先取得源行锁，按下面顺序复查。复查不符就按对应拒绝结束，不改表。登记变更和步骤标识已变不用解析失败文案，也不用「没有表映射」。工作区不符的步骤失败行使用 `INPUT_SUMMARY`。复查通过才按解析结果处理：解析失败用 `INPUT_SUMMARY`，零行用「没有表映射」，至少一行才改表。

1. 数据源仍存在，否则按现有源不存在错误拒绝。
2. 数据源仍启用，否则按现有源禁用错误拒绝。
3. `source.updated_at` 与登记快照的 `updated_at` 相同。不同则 `RegistrationChangedError`，走现有受控失败，不删除、不插入。库名、schema 范围或启停状态的变化都会改这个时间。
4. `assert_workspace_owner`：工作区仍属于该源。锁下失败时，先结束复查会话，再在 `_publish_domain` 内捕获 `WorkspaceMissingError` 与 `WorkspaceSourceMismatchError`，走 `_store_failure`，文案为 `INPUT_SUMMARY`，不改表。不要把这两种异常抛出 `_publish_domain`。`publish_steps` 的循环不捕获它们；抛出会让整个请求变成 404，已经提交的 db、ddl、json 不会回滚，调用方也拿不到 `publish_id`。预检阶段这两种异常仍上抛，由 API 返回 404「作业不存在或不属于该数据源」；那时还没有 `publish_id`。
5. `_verify_step_current_under_lock(session, job_id, "domain", expected_run_marker)`：domain 行仍为 `success`、步骤 `updated_at` 与预检标识相同，且整作业仍可发布。整作业已有失败或运行中的步骤时，这里抛出 `JobNotPublishableError`。它是 `PublicationStepNotReadyError` 的子类。`_publish_domain` 不要捕获它，让它抛给 `publish_steps`；循环会记失败行，文案为「采集作业存在失败或运行中的步骤，不能发布」。若被发布器里的宽 `except Exception` 吃掉，会被误报成 `WRITE_SUMMARY`。

这比 json 更严。json 在解析失败时直接 `_store_failure(INPUT_SUMMARY)`，运行标识只在解析成功后才查。domain 有意收紧：重跑会清空 domain 目录，空文件经 `yaml.safe_load` 得到 `None`，属于「YAML 不是对象」。若不先复查，这次重跑会被报成画像输入不可用。复查发现步骤标识已变时，失败原因是 `NOT_READY_MESSAGE`，不是 `INPUT_SUMMARY`，也不是「没有表映射」。登记版本变了，同样不进入这两种文案。源不存在、源禁用仍按现有错误上抛，不写失败记录。

复查在一个会话里完成。`_store_failure` 会另开事务并再次锁同一数据源行。会话还没退出就调用它，请求会停在第二把锁上。解析失败、零行、工作区不符，都先结束这个会话，再调用 `_store_failure`。源不存在或禁用时直接上抛，不写失败记录。登记变更、步骤标识已变、整作业不可发布仍在会话内抛出，会话退出后再按各自文案记失败行。至少一行的替换留在这把锁里，直到提交。写入失败也等该事务回滚后再调用 `_store_failure`。

步骤标识和登记版本都未变、且解析结果至少一行时，仍在这把锁的同一事务内：

1. `clear_current(session, source_id, "domain")`。这只改 `publish_info`：把该源上一条 domain 的 `is_current_publish` 设为 false。`table_domain` 没有 current 列，不靠它区分映射。不先做这一步，新的成功发布行会撞上「每个数据源每个步骤只能有一条 current」的唯一约束。
2. `DELETE FROM table_domain WHERE source_id = :source_id`，再插入本次解析出的全部行。每行的 `publish_id` 是本次发布，`job_id` 是产生 YAML 的采集作业，`loaded_at` 由数据库默认值填写。
3. `insert_publish_row(..., step_name="domain", status=success, is_current=True)`。
4. 提交。

标识未变、登记版本未变、但解析结果为零行时：不执行上面 1–4 步。先结束复查会话，再走 `_store_failure`，结果提示「Domain 产物没有表映射，请检查产物后重试」。原有 `table_domain` 和上一条 domain 当前发布都保持不变。

失败时走现有 `_store_failure`，且必须在复查会话已经退出之后：不把本次行标成 current，原有 domain 当前发布记录和 `table_domain` 内容保持不变，并留下一条失败的 `publish_info`。domain 失败不回滚同一次请求里已经成功的 db、ddl、json。

对外结果文案：

| 情况 | 文案 |
|---|---|
| 复查通过，且目录解析失败、文件打不开、不是普通文件、YAML 不是对象、`domains` 不是列表、domain 项结构非法、同名 Domain 描述冲突、库名不符、不是三段式、schema 不在登记范围，或表不在同一作业 MD 清单中、清单不可用、对应文件已不是普通文件 | 现有 `INPUT_SUMMARY`：「画像输入不可用或校验失败」 |
| 锁下复查发现工作区缺失或不属于该源 | 同样是 `INPUT_SUMMARY`，并且是本步骤失败行。预检阶段仍是 API 404 |
| 复查通过但没有表映射 | 「Domain 产物没有表映射，请检查产物后重试」 |
| 步骤运行标识已变 | 现有 `NOT_READY_MESSAGE`：「步骤尚未采集成功」 |
| 锁下复查发现整作业已有失败或运行中的步骤 | 现有 `JOB_NOT_PUBLISHABLE_MESSAGE`：「采集作业存在失败或运行中的步骤，不能发布」 |
| 登记 `updated_at` 已变 | 现有登记变更文案 |
| 平台库写入失败 | 现有 `WRITE_SUMMARY`：「平台库写入失败」 |

解析规则：

1. `_INSPECTORS["domain"]` 与 JSON 检查器一样，先确认源存在、源仍启用、工作区属于该源，再返回步骤 `last_status` 与 `updated_at`。不符则上抛，发生在生成 `publish_id` 之前。不读登记快照，也不校验 `db_type`。提交前仍按下面五步在锁下复查。
2. 读取 Domain YAML 前先调用 `resolve_domain_output_dir`。它逐级拒绝 `output/<source_id>/<job_id>/domain` 路径上的符号链接。`O_NOFOLLOW` 只作用于最后一级，挡不住上级目录是链接。然后用 `os.open(O_RDONLY|O_NOFOLLOW|O_NONBLOCK)` 打开该目录下的 `db_domains.yaml`，再用 `fstat` 确认是普通文件，然后才读内容。符号链接、FIFO 或其他非常规文件在打开时被拒绝，不跟随链接。目录解析失败、打不开、不是普通文件、顶层不是对象或 `domains` 不是列表，都记为解析失败，先按规则 7 做锁下复查；复查通过才用 `INPUT_SUMMARY`，不改表。预检只判断目录可解析且文件存在并为普通文件，不读内容。
3. `database` 必须是对象，`database.name` 必须是去空白后非空的字符串，并与登记快照的 `db_name` 一致。缺失、类型不对、空白或与登记库名不一致，都记为解析失败，先按规则 7 复查；复查通过才拒绝且不改表。锁外这一次比较不是最终依据。
4. 展开每个 domain 的 `tables`。`domains` 的每一项必须是对象；`name` 与 `description` 必须是去空白后非空的字符串，入库用去掉首尾空白后的值。`tables` 缺失或为空列表时跳过该 domain（样例中的 `_未分类_` 若没有表，就不产生行）。`tables` 不是列表，或其中有条目不是字符串，整次记为解析失败。这些结构非法都先按规则 7 复查，复查通过才用 `INPUT_SUMMARY`，不插入。不要留给建表语句里的 `NOT NULL` 与 `CHECK`：那些约束失败会变成 `WRITE_SUMMARY`，把产物问题报成平台库写入失败。`tables` 合法且非空时，该 domain 的每个表各插入一行，`domain_desc` 用去掉首尾空白后的 description。
5. 三段各自 `strip()` 后校验并入库。`orders.public. users` 入库的 `table_name` 是 `users`，不是带前导空格的原值。strip 后为空、不是恰好三段、首段不等于登记库名、或次段不在 `selected_schemas` 中，记为解析失败，先按规则 7 复查；复查通过才整次失败，不改表。段内空格保留，只去掉首尾空白。把 strip 后的三段用 `.` 连接，再加 `.md`，必须出现在同一作业 MD 清单的 `files` 里，并且该路径现在仍是普通文件。清单目录先用 `resolve_md_output_dir` 得到，再以同样的 `O_NOFOLLOW|O_NONBLOCK` 加 `fstat` 打开其中的 `manifest.json`。清单按 MD 成功时写入的文件名为准；成功后放进目录的同名文件不算。目录解析失败、清单缺失、读不出、不是普通文件，或 `files` 不是 `.md` 文件名列表，无法证明表名真实，同样整次失败。无论 YAML 有没有表映射，都先校验清单；清单不可用时不再判零行。这些都先复查，复查通过用 `INPUT_SUMMARY`，不删除旧映射。YAML 里没出现的真表不报错，这次没有 domain 行。不要求覆盖全部 MD 表，见 [100 备忘录](100_备忘录.md) 第 5 条。
6. 同一个 `domain_name` 去掉首尾空白后，`description` 也必须相同；空 `tables` 的条目也参与这次比较。描述不同则整次失败，先按规则 7 复查，复查通过用 `INPUT_SUMMARY`，不删除旧映射。描述相同则不是冲突。同一 `(schema_name, table_name, domain_name)` 按入库值重复出现时，只保留一行。
7. 解析失败、零行、至少一行，都先取得源行锁，按本节前面的五步复查。复查不符时：数据源不存在或已禁用，按现有错误上抛，不写失败记录；登记 `updated_at` 变化或 domain 步骤标识已变，按各自现有文案拒绝，不用 `INPUT_SUMMARY`，也不用「没有表映射」。工作区不再属于该源时，先结束复查会话，再在 `_publish_domain` 内捕获并记 `INPUT_SUMMARY` 失败行，不上抛成整个请求的 404。这些情况都不删除、不插入。
8. 复查通过但解析失败时，先结束复查会话，再走 `_store_failure`，文案为 `INPUT_SUMMARY`，不执行 `clear_current`、删除或插入。空文件经 `yaml.safe_load` 得到 `None`，标识未变时走这一条，不走「没有表映射」。复查通过且解析成功、清单也可用、但没有表映射（例如只有空的 `_未分类_`）时，同样先结束复查会话、不改表，文案为「Domain 产物没有表映射，请检查产物后重试」。清单不可用时即使没有表映射，也走上一句的 `INPUT_SUMMARY`，不用这句。原有映射及当前发布记录保持不变；即使原来没有映射，也不把空产物记为成功发布。Domain 生成依赖非空 MD 摘要，但现有生成成功校验只要求 `domains` 列表非空，因此不能把「存在空 domain」当作「存在表映射」。空文件在标识已变时不走本条，走规则 7 的 `NOT_READY_MESSAGE`。
9. 复查通过且至少一行时，在同一事务里先 `clear_current(session, source_id, "domain")`，再 `DELETE FROM table_domain WHERE source_id = :source_id`，然后插入本次全部行并提交。`clear_current` 只更新 `publish_info`。本次文件里不再出现的表或 domain 会从 `table_domain` 删掉。其他 `source_id` 的行不动。

查询示例：

```sql
SELECT domain_name, domain_desc
  FROM public.table_domain
 WHERE source_id = :source_id
   AND schema_name = 'public'
   AND table_name = 'users';
```

## 5. Web 发布页

发布页是 `frontend/src/views/PublishView.vue`。分组 b 现在只有 `ddl`、`json`。在 json 下面增加一项：

```ts
{ id: 'domain', label: 'domain' }
```

`SELECTABLE_STEPS` 增加 `'domain'`。页面说明由「db、ddl、json 发布到平台库」改为「db、ddl、json、domain 发布到平台库」。勾选规则与 ddl、json 相同：预检 `publishable === true` 才能勾选；不可发布时沿用现有原因文案，不显示「暂不支持发布」。全选只选当前可发布的步骤，因此 domain 未采集成功时不会被全选进去。

预检 `check_publication` 按 §4 改完预检之后，`domain` 可发布的条件是：

- `job_info(job_id, 'domain').last_status == 'success'`
- `resolve_domain_output_dir` 通过，且 `db_domains.yaml` 存在并为普通文件（`check_domain_output_ready`，不数表映射行数）
- 整作业 `assert_job_publishable` 通过

三者都满足时 `publishable = true`。文件不存在或不是普通文件时，原因文案为 `OUTPUT_REASON`。字面量联合类型都要加上 `"domain"`，少一处都会在响应校验失败：

- `backend/api/schemas.py` 的 `PublishCheckStep.step_name`
- `frontend/src/api/types.ts` 的 `PublishCheckStep.step_name`
- `backend/api/schemas.py` 的 `PublicationStepResult.step`（`PublicationCreateResponse` 的 `results` 使用它；发布路由 `response_model=PublicationCreateResponse`）
- `frontend/src/api/types.ts` 的 `PublicationStepResult.step`

后两处如果仍只有 `db`、`ddl`、`json`、`table_schema`，domain 结果返回时 FastAPI 校验失败，整个请求变成 500。同一次发布里已经提交的 db、ddl、json 不会回滚，调用方也拿不到 `publish_id`。

点击发布走既有 `POST .../publications`。`normalize_publish_steps` 的白名单加上 `domain`，未知步骤文案改为「当前仅支持 db、ddl、json、domain、table_schema 步骤」。选中 domain 时按 §4 走专用分支调用 `_publish_domain`，不走 5 参通用分支。`backend/publishing/listing.py` 与 `backend/publishing/home.py` 共用 `PROFILE_STEPS`。未列入该常量的步骤仍会经 `extra` 出现在画像步骤里，只是按名字排序。把 `domain` 加进 `PROFILE_STEPS` 是为了把它排在 `json` 之后，两处引用同一常量，改这一处即可。

发布结果区显示一行 `domain`，成功或失败与 ddl、json 同一套结果结构。

## 7. 验收

- 预检元组含 `domain`，产物检查不走 json 的 `else`。文件不存在或不是普通文件时不可勾选，原因是 `OUTPUT_REASON`。零行文件仍可勾选。
- 发布页 b 组在 json 下出现 domain。可发布时能勾选，结果区有一行 domain；不可发布时显示预检原因，不显示「暂不支持发布」。
- 发布结果的 `step` 含 `domain`，后端 `PublicationStepResult` 与前端同名类型都能通过响应校验。
- `domain/` 或 `md/` 路径上有符号链接，或 YAML、`manifest.json` 不是普通文件：目录由 `resolve_domain_output_dir`、`resolve_md_output_dir` 拒绝；文件由 `O_NOFOLLOW` / `fstat` 拒绝。标识已变时文案为 `NOT_READY_MESSAGE`；复查通过才是 `INPUT_SUMMARY`。预检时 domain 目录不可用的原因是 `OUTPUT_REASON`。这些情况都不改 `table_domain`。
- 非三段式、库名不符、schema 不在 `selected_schemas`、表不在同一作业 MD 清单中或对应文件已不是普通文件、domain 项不是对象、`name` 或 `description` 缺失或空白、`tables` 不是列表、表条目不是字符串：先做锁下复查。复查通过才整次失败、不改表，文案为 `INPUT_SUMMARY`，不是 `WRITE_SUMMARY`。成功后放进目录的 `fake.md` 不算采集产物。YAML 未收录的真表不导致失败。
- 重跑清空后的空文件：标识已变时文案为 `NOT_READY_MESSAGE`，不是 `INPUT_SUMMARY`，也不是「没有表映射」。标识未变时按解析失败，文案为 `INPUT_SUMMARY`。
- 空 `tables` 或缺少 `tables` 的 domain 不产生行。同一表同一 domain 按去掉首尾空白后的入库值重复出现时只留一行。一张表属于多个 domain 时留下多行。`orders.public. users` 入库为 `schema_name='public'`、`table_name='users'`。strip 后出现空段则整次失败。
- 两个同名 Domain 的描述分别为 A 和 B：整次失败，不改表，复查通过后文案为 `INPUT_SUMMARY`。描述相同则只按表与 Domain 去重。
- 运行标识已变：按 `NOT_READY_MESSAGE` 失败，不删旧映射。
- 锁下整作业已有失败或运行中的步骤：按「采集作业存在失败或运行中的步骤，不能发布」记失败行，不改表。
- 锁下工作区缺失或不属于该源：本步骤失败行，文案为 `INPUT_SUMMARY`，不改表；同请求已成功的步骤保持成功，响应仍带 `publish_id`。只发布 domain 时，检查器在生成 `publish_id` 之前发现工作区不符，仍是 404。
- 登记 `updated_at` 已变：按登记变更失败，不删旧映射。
- 复查通过但零行或解析失败：先结束复查会话，再记失败行，不改表。零行文案为「Domain 产物没有表映射，请检查产物后重试」。已有映射保留，并新增一条非 current 的失败发布记录。
- 零行 YAML 同时清单缺失或不可读：先校验清单。复查通过后文案为 `INPUT_SUMMARY`，不是「没有表映射」，不改表。
- 复查通过且至少一行：先 `clear_current`，再按 `source_id` 替换 `table_domain`。新行的 `publish_id` 是本次发布，`loaded_at` 是本次写入时间。
- 删源不在本篇验收。是否删除留下的 `table_domain` 行见 [100 备忘录](100_备忘录.md) 第 4 条。

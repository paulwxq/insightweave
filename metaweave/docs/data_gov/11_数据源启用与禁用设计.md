# 数据源启用与禁用设计

> 状态：设计稿，尚未实施。本文承接 [doc 3](3_阶段一step db设计文档.md) §2 的 `db_source_info` 表，为 [doc 9](9_db采集作业目录与数据库画像表设计.md) 的采集路径和 [doc 10](10_平台画像加载命令meta_load设计.md) 的加载路径补一个共同的前置条件。本阶段只实现"启用/禁用"这一个二元状态位，**不为数据源引入通用 `status` 字段**（doc 2 的验收已明确 `db_source_info` 不含通用 `status`）。

## 1. 目标与边界

`db_source_info` 增加一列 `is_active`（默认激活），并提供切换入口。禁用的数据源：

- 不能再创建新的采集作业（Web API 与 CLI 两条路径都拦）；
- 不能再把采集产物加载进平台库（`meta_load` 拦）；
- 已登记的连接信息、历史作业记录、已入库画像一律保留、照常可读——**禁用只拦"新动作"，不追溯、不撤回发布**。

本阶段不做：

| 不做的事 | 原因 |
| --- | --- |
| 权限校验 | **本阶段不做权限校验（任何能打开页面的人都能切换开关），后续接入用户体系再补**；代码注释与提交说明同样如此声明，不写假的权限判断 |
| 禁用原因、操作者、时间审计 | 没有用户体系（`run_by_user_id` 至今没有写入方），单列一张审计表属于过度设计 |
| 定时/自动禁用、批量启停 | 没有需求来源 |
| 与 `publish_info`／当前版本的联动 | 禁用不改变 `is_current_publish`，也不隐藏已发布画像；发布模块本身尚未实施 |
| 按 `is_active` 过滤列表 | 列表默认返回全部数据源，由页面用标签区分状态 |

## 2. 表结构与迁移

字段定义（本文是唯一出处）：

```sql
is_active boolean NOT NULL DEFAULT true
```

- 命名沿用 doc 2 的 `is_current_publish boolean NOT NULL DEFAULT false`：二元状态用 `is_* boolean`，不再引入 text `status` + CHECK（没有第三种状态，boolean 也无法表达非法值），避免与 doc 2 "不含通用 `status`" 的结论冲突。
- **已装环境**：仅当当前平台库的 `db_source_info` 尚无 `is_active` 列时，由**实施者**执行下面这条一次性 DDL，并确保本次加列时**所有既有记录都是激活状态**；已有该列的环境跳过，不重复加列、不重置已禁用记录（应用代码依旧不建表、不改表）：

```sql
ALTER TABLE public.db_source_info
  ADD COLUMN is_active boolean NOT NULL DEFAULT true;
```

PG 11 及以上，带常量默认值的 `ADD COLUMN` 只改元数据、不重写表；`DEFAULT true` 由数据库在加列时回填，既有记录**全部**变为激活，无需额外 `UPDATE`（实测：加列后既有行为 `true`）。执行后必须核对一次：

```sql
SELECT count(*) FILTER (WHERE is_active)      AS active,
       count(*) FILTER (WHERE NOT is_active)  AS disabled,
       count(*) FILTER (WHERE is_active IS NULL) AS nulls
FROM public.db_source_info;
```

期望 `nulls = 0`、`disabled = 0`、`active` 等于当前已登记的数据源数量。若核对发现 `NULL`（只可能来自有人手工改过 schema），先执行 `UPDATE public.db_source_info SET is_active = true WHERE is_active IS NULL;` 回填，再继续实施。

- **新环境安装顺序**（平台表一律由管理员手工执行，应用不建表、不改表；按顺序执行）：

  1. doc 3 §2 的 `CREATE TABLE public.db_source_info`（最新版建表 SQL 已包含 `is_active`）
  2. doc 4 §4 的 `ALTER TABLE public.db_source_info ADD COLUMN IF NOT EXISTS description text`
  3. doc 6 §3 的 `ALTER TABLE public.db_source_info ADD COLUMN IF NOT EXISTS db_version text`
  4. doc 9 §2、§3 的 `CREATE TABLE public.job_info`、`public.db_profile`
  5. 核对 `is_active boolean NOT NULL DEFAULT true`；仅缺列的已有环境执行本节的 `ALTER TABLE`，按最新版 doc 3 建表的新环境直接跳过加列
  6. 接入 Web 发布功能时，执行 [doc 12 §2](12_发布信息表与发布动作设计.md#2-表设计) 的 `CREATE TABLE public.publish_info` 及三个索引；已有该表的环境核对结构，不重复建表

  doc 3 §2 已同步 `is_active`，供新环境建表使用；本文的 `ALTER TABLE` 用于未加列的已有环境，两者不得重复执行。上面清单汇总当前相关阶段的手工安装顺序，各列、表与索引的具体定义仍以对应文档为准；不再将本阶段清单称为后续所有版本安装的“唯一依据”。`publish_info` 属于 doc 12 的交付，不要求只实施启用/禁用功能的环境提前建表。
- 不新增索引：列表与启停都按主键或全表读取，没有按 `is_active` 过滤的查询。
- **空值（`NULL`）处理**：该列 `NOT NULL`，应用写入路径不产生 `NULL`——`insert_db_source` 的字段字典不含 `is_active`（`backend/data_sources/registration_service.py:147` 调用处）因而走 DEFAULT，`update_db_source`（同文件 `:315`）只 `setattr` 显式列出的键、也不涉及该列（这同时是 §3"修改连接信息不会自动启用"的结构性保证）。数据库层面显式写 `NULL` 会被 `NotNullViolation` 拒绝（`INSERT` 与 `UPDATE` 均已验证）；唯一能造出空值的是手工执行 `ALTER TABLE … ALTER COLUMN is_active DROP NOT NULL` 这类**越出本设计的 schema 破坏**，它属于修复责任：由改坏 schema 的人把数据改回激活并恢复约束，**应用层不为它增加兼容逻辑**。两点后果说清楚：服务端判定写作 `not source.is_active`，因此那种情况下**会拦住作业**（fail-closed），不会放行；而列表/详情接口的响应模型是 `is_active: bool`（非可空），真读到 `NULL` 时会在响应校验处直接报 500（实测），**不是**静默展示成"已禁用"。因此本文只承诺"约束成立时前后端口径一致"，**不承诺约束被破坏后仍能正常展示**。

## 3. 语义：拦什么、不拦什么

| 动作 | 禁用后 | 说明 |
| --- | --- | --- |
| `POST /api/data-sources/{source_id}/collection-jobs` | 拦（409） | 见 §4、§5 |
| CLI `metaweave metadata --step db --source-id …` | 拦（exit 2） | 含 `--job-id` 复用与 `--clean`；与 API 共用同一处前置校验，因此不产生 `job_info` 行、不创建 `output/<source_id>/<job_id>/` 目录、不连接源库 |
| CLI `metaweave meta_load --type db …` | 拦（exit 2） | 不插入 `db_profile`；带 `--clean` 时也不清理输入文件 |
| 查看、列表、修改连接信息、测试连接、删除 | 不拦 | 否则被禁用的数据源无法修好再启用 |
| 历史作业列表、已入库画像的读取 | 不拦 | 不追溯 |
| 正在执行的作业 | 不中断 | `job_info` 不存心跳与租约（doc 9 §2），没有中断手段；服务层只在作业开始前检查 |
| 创建/修改接口里的 `is_active` | 不接收 | 新登记的数据源恒为激活；修改连接信息不会自动启用 |

补充约束：

- `is_active` **只由 §5 的启停接口修改**。创建接口与"修改连接信息"接口都在请求模型上禁止该字段，避免"改个 host 顺手把状态改了"的隐式行为。
- 切换要更新 `updated_at`（沿用 `backend/data_sources/repository.py` 中 `update_db_source` 的写法），`created_at` 不变。
- 禁用**不**校验该数据源是否还有作业在跑：允许禁用，只是不中断已经在执行的那一个。

## 4. 服务层与错误契约

`is_active` 只有一个读取点——数据源行本身。两条执行路径各自在**本路径既有的错误族**里表达"已禁用"，不引入跨模块的新异常层：两侧 CLI 的 exit 2 映射都已按族存在，新增异常类型反而要求两处 CLI 各改一个 `except` 分支。

**采集路径**（`backend/data_sources/db_step_service.py`）：

```python
class SourceDisabledError(DbStepConfigError):
    """数据源已禁用，不能执行作业。"""
```

在 `run_db_step()` 读取数据源之后的前置校验里判断（与 `db_type != 'postgresql'`、缺少连接字段同处）：`not source.is_active` → 抛 `SourceDisabledError`。位置必须在 `assert_workspace_owner()` 与 `start_step()` **之前**，这样被拦截时不会留下作业行或产物目录。

- **CLI**：`metaweave/cli/metadata_cli.py` 现有的 `except DbStepConfigError` 分支照旧捕获 → `click.UsageError` → **exit 2**，退出码映射不需要改。
- **API**：`backend/api/errors.py` 为这个子类单独注册 handler → **409 `source_disabled`**。父类 `DbStepConfigError` 的 400 `invalid_request` 映射不受影响（FastAPI 按异常的 MRO 选择最具体的已注册处理器）。

**加载路径**（`backend/profile_loading/db_loader.py`）：在 doc 10 §3 第 2 步读取数据源的位置判断，抛 `MetaLoadConfigError("指定数据源已禁用，不能加载画像")` → `meta_loader_cli.py` 现有分支 → **exit 2**。该判断必须位于读取 `database.json`、插入 `db_profile`、清理文件之前。

两条路径都**禁止用错误消息文本判断状态**（`str(exc) == "..."` 一类写法）：一律以异常类型为准。

## 5. API

| 方法 | 路径 | 请求 | 成功 | 失败 |
| --- | --- | --- | --- | --- |
| `PATCH` | `/api/data-sources/{source_id}/activation` | `{"is_active": true\|false}`；`extra="forbid"`，且 `is_active` 类型为 **`StrictBool`** | 200，返回更新后的 `DataSourceListItem`（含 `is_active`） | `404 not_found`、`422 invalid_request`（字段缺失、类型错误、多余字段）、`503 platform_unavailable` |

- **为什么单开端点、不复用 `PATCH /api/data-sources/{source_id}`**：后者是"修改连接信息"的入口，带着密码必填判定、`confirm_duplicate`、重复连接 409、`PasswordRequiredError` 一整套校验；只为切一个开关也要过一遍，语义混乱；而且页面上的开关是即时动作，不适合走"整表提交 + 保存"的流程。
- **`is_active` 必须用 `StrictBool`，不能用普通 `bool`**：Pydantic 的宽松 `bool` 会把 `"true"`、`"false"`、`"1"`、`"0"`、`0`、`1`、`"yes"`、`"no"`、`"on"`、`"off"`、`"TRUE"` 一律**静默转换**（实测 pydantic 2.12.5），只有 `null`、`2` 这类值才会报 422。那样本节的"类型错误返回 422"就名不副实：客户端把字段传错类型不会被发现，而这个布尔位直接决定"能不能跑作业"。用 `StrictBool` 后只接受 JSON 的 `true`/`false`，其余一律 422 `invalid_request`——这是 Pydantic 自带类型，不引入新的校验框架。
- 请求携带目标状态，天然幂等：重复提交结果一致。
- 响应模型：`DataSourceListItem` 与 `CollectionJobSource`（采集作业列表页的数据源概览）都增加 `is_active: bool`，页面据此置灰入口；不为此新增"查询状态"接口。
- 错误码 `source_disabled` 同时用于采集拦截（`POST /collection-jobs`），前端一个 code 一条文案。
- 相关但**不在本次范围**：创建/修改接口的既有字段 `confirm_duplicate`（`backend/api/schemas.py` 两处）仍是宽松 `bool`，语义上不会把"未确认"误判为"已确认"（误转换的方向是客户端自己要求确认），风险与状态位不同；是否一并收紧由后续单独决定，本文不改动它。DELETE 的 `delete_output` 是查询参数，URL 里本来就是字符串，保持宽松不影响契约。

**状态判定写法统一**：全文档一律使用**真值判定**——服务端 `not source.is_active`（§4）、前端 `!source.is_active` / `source.is_active ? '激活' : '已禁用'` / `filter(s => s.is_active)`。不写 `is_active === true`、`is_active === false`、`is_active == False` 这类严格比较：一是与 TypeScript 里 `is_active: boolean` 的非可空类型重复，二是三种写法混用会在边界值上分叉（严格比较会同时排除 `null`，真值判定把它归入"已禁用"），和 §7.1 的 `.off` 命名约定是同一类要求——**同一条语义在文档里只能有一种拼写**。

## 9. 验收

1. 实施者按 §2 对当前平台库执行 `ALTER TABLE` 并核对：`db_source_info` 出现 `is_active`，既有行全部为激活状态（`nulls = 0`、`disabled = 0`、`active` 等于已登记数量）；表中仍无通用 `status` 列。
2. 详情页切换开关：点"禁用"弹出 §6.1 的确认框；确认后开关变为禁用态，列表页该卡片标签变「已禁用」，三张指标卡数字随之变化；点"启用"不弹窗、立即生效。
3. 启停接口契约：**严格类型**——`{"is_active": "false"}`、`"true"`、`"1"`、`"0"`、`"yes"`、`"no"`、`0`、`1`、`null` 一律返回 422 `invalid_request` 且数据源状态不变，缺 `is_active`、带多余字段同样 422，只有 JSON 的 `true` / `false` 生效；**404**——`source_id` 不存在时返回 404 `not_found`；**503**——平台库写入失败时返回 503 `platform_unavailable`；**幂等**——对同一数据源重复提交同一状态，两次都返回 200 且最终状态一致，`updated_at` 随之变化、`created_at` 不变。
4. 禁用后 `POST /api/data-sources/{source_id}/collection-jobs` 返回 409 `source_disabled`，且不产生 `job_info` 行、不创建 `output/<source_id>/<job_id>/` 目录、不连接源库。
5. 禁用后 CLI `metaweave metadata --step db --source-id …` 以 exit 2 结束、消息含"已禁用"，`job_info` 无新行；带 `--job-id` 复用同样被拦。
6. 禁用后 CLI `metaweave meta_load --type db …` 以 exit 2 结束，`db_profile` 不新增行；带 `--clean` 时输入文件保持原样。
7. 不追溯：禁用后查询该数据源的作业列表、连接信息与已入库画像（`db_profile`）均正常返回，已发布版本不因禁用而变化。
8. 禁用后仍可查看、修改连接信息、测试连接、删除；修改连接信息不会把 `is_active` 改回 `true`，新建数据源始终为激活状态；**创建与修改接口的请求体带上 `is_active` 时返回 422**（`extra="forbid"` 拒绝），不存在"新建时直接建为禁用"或"保存连接信息时顺带改状态"的路径。
9. 禁用只影响此后发起的动作：禁用期间正在 `running` 的作业不中断；`is_active` 变化更新 `updated_at`、不影响 `created_at`。
10. 本阶段不做权限校验——任何能打开页面的人都能切换开关，文档与代码注释中均如此声明；日志与接口消息不包含密码或完整连接串。
11. **测试替身必须显式提供 `is_active`，不得用兜底掩盖遗漏**：内存构造的 `DbSourceInfo` 不会执行数据库默认值（`server_default` 只在 INSERT 时生效）。

    - `tests/unit/test_web_data_sources.py` 的 `make_source()`（L209-226）已经为 `created_at` 显式赋值正是这个原因（`updated_at` 没赋值是因为没人读它）；`is_active` 会被 `_source_item()` 读取，必须显式给出。
    - 同文件 L282 起的 `assert set(item) == {...}` 键集合断言会因新增字段而失败——这是**应该失败**的地方，把它更新为把 `is_active` 加入期望集合，**不要删掉或放宽该断言**。
    - **新建记录路径（与上面两条不同，别漏）**：创建接口产生的对象由 `insert_db_source` 现场构造，**不经过 `make_source()`**。而 `FakePlatformSession.commit()`（`tests/unit/test_web_data_sources.py:121-136`）目前只模拟了数据库的 `created_at` 默认值（L127-132）与 `updated_at` 归一化，**不会应用 `server_default=true`**，于是创建成功用例会在 `is_active=None` 上以响应校验失败（500）报错。修法是**让假会话也模拟这条默认值**——提交新行时置 `is_active = True`，位置与它模拟 `created_at` 的地方相同；**不是**给生产读取逻辑加兜底。将来新建的测试若自建假会话（例如 `test_source_activation.py`），同样要模拟该默认值。
    - `tests/unit/test_db_step.py` 里 8 处数据源替身（`SimpleNamespace`，L220、706、769、826、872、917、959、1009）与 `tests/unit/test_meta_loader_db.py` 的 L27、L212 都要显式给出 `is_active=True`。
    - 生产代码**不得**出现 `getattr(source, "is_active", True)`、`source.is_active or True` 一类兜底：替身缺字段必须表现为 `AttributeError`，缺值（`None`）在拦截判定里表现为"按已禁用处理"（fail-closed）、在响应序列化里表现为报错（§2），两种遗漏都要响亮失败，而不是"测试全绿但拦截从未生效"。

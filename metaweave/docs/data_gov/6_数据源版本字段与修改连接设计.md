# 数据源版本字段与修改连接设计

> 状态：已实施。本文是 [doc 4：阶段一 Web UI 添加数据源](4_阶段一webui添加数据源.md) 的增量，不重做登记闭环，也不提前实现采集、发布或画像。
>
> 与 doc 4 的差异只有三处：登记时把当次源库版本写入 `db_source_info.db_version`；数据源卡片调整三行展示；卡片提供“修改”，复用创建表单更新同一条数据源。doc 2 §3.2 已把 `PATCH /api/data-sources/{source_id}` 标为后续契约，本次把它落地为修改入口。

## 1. 修改需求

1. 在平台库 `public.db_source_info` 增加 `db_version`，保存源库版本的展示字符串。
2. 测试连接时继续读取并返回版本号。点击“创建数据源”时，服务端在同一次源库连接里校验 Schema，并把这次读到的版本号与所选 Schema 一起写入平台库。版本写入 `db_version`，Schema 仍写入 `selected_schemas`。
3. 数据资产页的数据源卡片调整三行文字：`host:port` 仍在第二行；原来第二行里数据库名的位置改为版本号；数据库名单独放到 `host:port` 的下一行。
4. 卡片上增加“修改”。点击后进入与创建相同的表单，把该数据源已保存的连接内容填入输入框，供管理员修改并保存回同一条记录。

本次不改数据库类型范围，仍只支持 PostgreSQL。不新增采集、发布、画像，不回显密码或密文。

## 2. 当前行为与本次落点

连接检查 `POST /api/data-sources/connection-check` 已经调用 `read_and_validate_server_version()`，并用 `format_server_version()` 返回 `server_version`（例如 `180006` → `"18.6"`）。创建接口会重新连接并再次校验版本，但 `registration_service.create_data_source()` 把该整数丢弃（变量名为 `_version`），插入 `db_source_info` 时没有版本列。

因此：

- 测试连接的读取逻辑保持不变，仍只返回版本和 Schema，不写平台库。
- 创建按钮不把浏览器里看到的版本文本原样提交。保存时服务端重新连接，用这一次读到的版本调用 `format_server_version()`，与通过校验的 `selected_schemas` 写入同一条插入。这样版本和 Schema 来自同一次成功连接，低版本仍然拒绝入库。
- 请求体继续 `extra='forbid'`，不接受客户端提交的 `db_version`。

`db_version` 存展示字符串，与 `database.json` 的 `database.server_version` 使用同一个 `format_server_version()`。不另存 `server_version_num`，也不在字符串前加 `PostgreSQL`。`db_type` 仍是 `postgresql`。

## 3. 表结构增量

平台表继续由管理员确认目标是平台库 `metaweave` 后手工执行，不引入 Alembic，也不在 API 启动时改表。现有行保留，`source_id` 不变。

```sql
ALTER TABLE public.db_source_info
    ADD COLUMN IF NOT EXISTS db_version text;
```

| 项 | 约定 |
| --- | --- |
| 列名 | `db_version` |
| 类型 | `text NULL` |
| 新登记、手工登记、本次修改保存 | 写入非空展示字符串，如 `"18.6"` |
| 本变更之前的旧行 | 保持 `NULL`，直到下一次修改保存成功后覆盖 |
| 约束 | 不加格式 `CHECK`。合法格式只来自 `format_server_version()` |

`NULL` 只表示“登记时尚未保存版本”。卡片把空版本显示为“版本未知”，不用 `—` 占住原来数据库名的位置，避免和主机行混淆。

手工登记工具 `scripts/register_db_source.py` 已经在插入前调用 `read_and_validate_server_version()`。本次让它保留返回值，用同一格式写入 `db_version`，避免新的命令行登记留下空版本。

## 4. 卡片展示

当前卡片正文顺序是：

```text
订单库pg
postgresql · orders
172.29.128.1:5432
包含订单、影院等数据。
public
```

调整后：

```text
订单库pg
postgresql · 18.6
172.29.128.1:5432
orders
包含订单、影院等数据。
public
```

| 行 | 内容 |
| --- | --- |
| 标题 | `display_name`，不变 |
| 第一行地址 | `db_type · db_version`；`db_version` 为空时显示“版本未知” |
| 第二行 | `host:port`，位置不变 |
| 第三行 | 单独一行 `db_name` |
| 其后 | 说明、Schema 标签、页脚，顺序不变 |

卡片页脚为两行。第一行左侧是登记时间，右侧是“修改”按钮。第二行左侧是“待采集”，右侧是“采集”按钮，与“修改”上下对齐；“采集”本阶段只占位，不接功能。右上角“已登记”为绿色，后面依次是“删除”“查看”。“查看”打开只读页，“删除”按 [doc 7](7_数据源查看与删除设计.md) 删除该登记记录。Schema 标签为绿色。页脚按钮不放进“已登记”标记里。

列表接口和创建成功响应都增加 `db_version: string | null`，供卡片直接渲染。空值只来自旧数据。同一响应同时增加 `sslmode: string | null`。它不显示在卡片上，但修改页要用它回填；未返回时，已保存的非空 `sslmode` 会在表单里变成“未指定”，留空密码保存会被当成连接信息已修改。

## 5. 修改数据源

### 5.1 页面

路由新增 `/data-assets/:sourceId/edit`，仍使用 `DataSourceForm`。创建页路由 `/data-assets/new` 保持不变。

| 场景 | 页面标题 | 主按钮 | 成功后 |
| --- | --- | --- | --- |
| 创建 | 创建数据源连接 | 创建数据源 | 回到数据资产页 |
| 修改 | 修改数据源连接 | 保存修改 | 回到数据资产页，列表显示更新后的版本、库名和 Schema |

进入修改页时按 `source_id` 读取已登记字段并填入：

- 填入：`display_name`、`host`、`port`、`db_name`、`username`、`sslmode`、`description`、已选 Schema。`sslmode` 取自该条响应；`null` 对应“未指定”
- 不填入：密码。密码框为空，占位文案为“不修改请留空”
- 数据库类型仍固定为 PostgreSQL，不可改
- `source_id`、`created_at`、`created_by_user_id` 不在表单中编辑

密码不回显，沿用 doc 2 的凭据规则：更新时未提交新密码就保持原密文。修改页因此不能在打开时自动测试连接。管理员点击“测试连接”后才发现 Schema。

测试连接和保存的密码规则：

- 密码框有内容：用框内新密码调用现有的 `POST /api/data-sources/connection-check`，保存成功后替换密文。
- 密码框为空，且 `host`、`port`、`db_name`、`username`、`sslmode` 都与已保存记录一致：调用按 `source_id` 的连接检查。该接口不接收连接目标，只解密原密码并重测已保存的目标；保存成功后密文不变。
- 上述五个连接字段有任一与已保存记录不一致，且密码框为空：不能测试，也不能保存。页面提示填写密码。若请求仍到达 `PATCH`，返回 `422 password_required`，文案为“连接信息已修改，请填写密码后重试”。这与缺字段的 `invalid_request` 分开。已存密码只会连回原目标，不能被拿去连接调用者指定的地址。
- 任一连接字段（含新密码、sslmode）变化后，清空本次测试结果和当前勾选，要求重新测试。修改页在进入时把响应里的 `selected_schemas` 另存为原始已选；回填连接字段不算用户修改，也不得清掉这份原始已选。当前勾选与原始已选分开保存。
- 测试成功后，Schema 列表用本次发现结果。修改页的当前勾选取原始已选与本次发现列表的交集，已不可选的名称不保留。创建页没有原始已选，仍由用户手选。至少仍须勾选一项才能保存。

保存前前端要求已经完成本次测试。后端不信任该结果，保存时再次连接，重新校验版本和 Schema，再写入。修改请求含 `confirm_duplicate`，缺省 `false`。查重命中其他记录时，错误码仍是 `duplicate_source`，不新增错误码。创建页提示保持“已有相同连接信息的数据源，请确认是否仍要新建。”，按钮为“确认仍创建独立数据源”。修改页提示改为“已有相同连接信息的数据源，请确认是否仍要保存。”，按钮改为“确认仍保存到当前数据源”。`PATCH` 响应里的 `message` 使用修改页这句，不写“新建”。用户确认后以同一份字段、`confirm_duplicate: true` 重试。

### 5.2 接口

| 接口 | 行为 |
| --- | --- |
| `GET /api/data-sources/{source_id}` | 返回与列表项相同的字段，含 `db_version`。数据源不存在返回 `404 not_found`。不返回密码或密文。 |
| `POST /api/data-sources/{source_id}/connection-check` | 修改页在密码为空、且连接目标未改时使用。无请求体。服务端只用该行已保存的 host、port、库名、用户名、sslmode 和原密码调用现有 `check_connection()`，返回 `server_version` 与 `schemas`。不写库。数据源不存在返回 `404 not_found`。 |
| `POST /api/data-sources/connection-check` | 创建页，以及修改页密码框有内容时继续使用。契约不变。 |
| `PATCH /api/data-sources/{source_id}` | 更新同一条记录。请求体与创建相同，仅密码可省略或为空；缺任一其他字段返回 `422 invalid_request`。不做字段级局部更新。数据源不存在返回 `404 not_found`。成功返回更新后的列表项，状态码 `200`。 |

修改保持同一个 `source_id`，只用于同一套业务数据库的连接信息变更，例如显示名、说明、Schema、密码、`sslmode`，以及同一逻辑库的地址、端口、库名或用户名调整。若要登记另一套业务数据库，新建数据源，不把旧 `source_id` 指过去；该 ID 也是 `output/<source_id>/` 和将来画像的身份。服务端无法从新的 host 或库名区分迁移和换库，因此接口不拦截 `host`、`port`、`db_name` 的修改。这与 doc 2 §3.1 的身份约定一致。

`PATCH` 不是局部更新。请求体必须带齐 `db_type`、`display_name`、`host`、`port`、`db_name`、`username`、`sslmode`、`selected_schemas`、`description`。`sslmode` 与 `description` 允许为 `null`，但键必须出现；省略键不是“沿用旧值”。创建模型里这两个字段的默认值是 `None`，修改模型不能直接继承该默认值，须把它们重新声明为必填且可为 `null`。只有 `password` 可以省略或为空，表示不更换密文。`confirm_duplicate` 仍可省略，缺省为 `false`。连接检查使用的就是这一份请求里的连接字段，不与库中旧值拼成一套。

`PATCH` 的顺序：

1. 校验字段格式。缺少 `sslmode` 或 `description` 键时返回 `422 invalid_request`。`display_name`、说明、Schema 名称规则与创建相同。
2. 按 `source_id` 读取当前行。不存在则返回 `404 not_found`，不查重、不解密、不连接。
3. 按 `(host, port, db_name, username)` 查重，排除当前 `source_id`。命中其他记录且 `confirm_duplicate` 不为 `true` 时返回 `409 duplicate_source`，不连接源库。
4. 若 `host`、`port`、`db_name`、`username`、`sslmode` 有任一与当前行不一致，且请求没有非空新密码，直接返回 `422 password_required`，不解密、不连接。五个字段都一致时才允许用原密码。
5. 确定本次密码：请求里的非空密码，或解密后的原密码。用它连接**本次请求中的目标**并校验版本和 Schema。目标与原记录一致时，该目标就是已保存目标。密钥缺失、密钥无效或密文无法解密时返回 `500 internal_error`，沿用 doc 4 对服务端凭据问题的归类，不新增错误码，不更新，响应和日志都不含密码或密文。
6. 在同一条记录上更新 `display_name`、连接字段、`selected_schemas`、`description`、`db_version`。`updated_at` 用 SQLAlchemy `func.now()` 写入，由数据库计算，与 `created_at` 的 `server_default=now()` 同一时钟。`source_id`、`created_at`、`created_by_user_id` 不变。只有提交了新密码才更换 `password_ciphertext`。
7. 版本或 Schema 校验失败时不更新任何列，包括 `updated_at`。

第 2、3 步共用一次平台库短会话：读出当前行的连接字段和密码密文后关闭会话，再做第 4 步的内存比较。源库校验期间不持有平台库会话。校验通过后另开短会话更新该行；若这时行已不存在，返回 `404 not_found`，不插入。这与 doc 4 的“查重会话、源库连接、写入会话分开”一致。

上述三个按 `source_id` 定位的接口，在记录不存在时都返回 `404`，响应体为 `{code: "not_found", message}`，不带 `details`。前端按该 `code` 显示“数据源不存在”。修改页加载时遇到 `not_found`，显示该提示并回到数据资产页，不进入表单。

修改页展示 `connection_failed` 时，在原有“源库连接或查询失败，请检查连接信息”之后追加“若源库密码已变更，请在密码框填写新密码后再测试”。创建页仍只用原来的 `connection_failed` 文案。

本阶段不给 `PATCH` 加行锁或乐观锁。两位管理员同时修改同一条时，后写入的内容覆盖先写入的内容。当前只有本机、无认证的单管理员使用，这样可以接受。将来若要防止互相覆盖，再按 `updated_at` 评估 `If-Match`。

创建接口的插入字典增加 `db_version`，值来自同一次 `open_source_connection()` 返回的版本。列表、创建成功、修改成功、单条查询共用同一个字段投影，其中包含 `db_version` 和 `sslmode`，不包含密码或密文。

## 7. 实施步骤

审核通过后按下面顺序改，不提前改代码。

1. 管理员在平台库 `metaweave` 执行第 3 节的 `ALTER TABLE`。执行前确认当前库和表，`IF NOT EXISTS` 只避免重复加列。
2. 改 ORM、仓储和登记服务：创建与手工登记写入 `db_version`；列表投影带上该字段。
3. 增加单条查询、按已存密码的连接检查、`PATCH` 更新。更新路径复用现有连接、版本门槛、Schema 校验和密码加密，不复制第二套连接逻辑。
4. 改前端类型、表单、路由和卡片。创建页行为保持：密码必填，测试成功后手选 Schema，再创建。
5. 跑 `tests/unit/test_web_data_sources.py` 及相关登记测试。再用页面走通：新建一条数据源后卡片显示版本和库名分行；点“修改”看到已填字段、密码为空；改说明或 Schema 并保存后，同一 `source_id` 的版本被当次连接结果更新。Schema 重测交集按 §8 手工确认，不新增前端测试脚本。

## 8. 验收

- 新建成功后，`db_source_info.db_version` 为当次 `format_server_version()` 的结果，`selected_schemas` 与勾选一致，两者在同一次保存中写入。
- 连接检查响应仍含 `server_version`，且检查本身不插入、不更新平台库。
- 低于 PostgreSQL 15.0 时创建和修改都不写库。
- 卡片第二行是 `host:port`，其上一行是 `postgresql ·` 加版本，其下一行是数据库名。
- “修改”打开同一表单。刷新修改页仍能按 `source_id` 填回非密码字段。打开不存在的 `source_id` 时提示并回到数据资产页，不进入表单。保存后 `source_id` 不变，列表不再多出一条。`updated_at` 由 `func.now()` 写入；单元测试的假会话不执行数据库时钟，真实平台库联调时确认该列已更新。
- 手工确认 Schema 重测：原始已选为 `public`、`sales`，改变连接字段并重新测试后，若本次只发现 `public`、`other`，页面只勾回 `public`。本次不为这一例添加前端测试框架。
- 密码框留空时保存不更换密文；填写新密码且测试、校验通过后才更换密文。接口响应、页面和日志都不出现明文密码或密文。
- 本变更前的旧记录在未修改前 `db_version` 为 `NULL`，卡片显示“版本未知”。

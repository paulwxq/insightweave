### 0.2 拍板决策

- **D1 合并原则**：WebUI 全链路只出现 rel，不出现 cql。采集页与发布页的 c 组均删 cql 行、放 rel 行（§3.1、§3.2）。cql 产物目录 `output/<source_id>/<job_id>/cql/` 由发布过程创建，无采集步骤行、无发布页条目。
- **D2 Neo4j 替换语义**：沿用全量清库重载——加载前 `MATCH (n) DETACH DELETE n`（cql_loader.py:229-240）后整份重载。已知代价：清库后加载中断留半图；MERGE 幂等，重跑发布即愈。**并发边界同为已知并接受**：源行锁按 source_id 互斥、跨源不互斥——两个数据源同时发布会在同一 Neo4j 上交替「全删再写」，本阶段以单源发布纪律约束，不加 Neo4j 实例级互斥（不做配置级单写者/发布队列，避免过度设计；随按源替换一并挂账备忘录）。开发阶段单 Neo4j 用途下接受；多源共存需求出现时再议按源替换（记 100_备忘录）。
- **D3 溯源属性**：仅 Table 节点写入 `source_id` + `publish_id` 属性；Column 节点、HAS_COLUMN 与 JOIN_ON 边不加（需求 10；列与边的溯源经所属/两端 Table 遍历可得）。全清语义下这两个属性是溯源信息而非清理键。
- **D4 md 写回策略**：整份重渲染，复用现有渲染代码——json→`Relation` 反序列化 + `_write_markdown` 拆出的公开纯渲染 `render_markdown_report`（渲染与写盘分离，§5.2）。不编写平行渲染器；一致性用"未编辑产物重渲染与算法直出逐字节一致（仅生成时间行除外）"的测试锁死（doc 19.1 重渲染比对同款模式）。
- **D5 手工编辑与重跑**：rel 采集步骤执行前，把现有 json+md 移入 `rel/.backup/` 子目录（写入前先清空，只保留上一份）；恢复为手工操作，不做 UI。编辑 API 用内容指纹做乐观并发：GET 返回指纹，PUT 必带，不匹配返回 409 `rel_regenerated`（doc 22.2 dim_config_regenerated 同款语义）。
- **D6 解冻宽松 / 执行严格分层**：解冻（前端预检）沿页面统一公式 = rel 步骤行 success ∧ 产物就绪 ∧ 作业级全 success（check_publication :304，与其它预检步骤同构——rel 加入后共 7 步）；「宽松」专指**产物就绪判定** = rel 目录顶层存在非忽略普通文件（需求 3 原文口径；`.tmp*`/`.backup` 忽略规则与执行预检共用，§6.2）——不查新鲜度/内容/指纹（分工表见 §6.2）。执行预检（发布服务）= 同作业 json/domain/rel 三步骤行均 success + 新鲜度（rel 行 updated_at 晚于 json/domain 行，§6.2）+ rel 内容指纹捕获（§6.2 第 6 条）+ 产物文件面核验。解冻后执行被拒时返回明确配置错误。**已知摩擦（显式接受）**：行 failed 的失败重跑残留旧产物（23.1 R6 故意保留）在页面即灰置（reason 步骤未成功），无需点发布才打回；「可勾选但点发布被 400 打回」的残余窗口仅剩行 success 而文件被外部改动/残缺的罕见态（消息指明缺什么）。不做「解冻 reason 分级」：那要把执行预检的新鲜度/文件面查询前移复制到 publish-check，两处逻辑漂移风险大于 UX 收益——分层的意义正是严格检查只在执行时做一次。
- **D7 手工关系条目 schema**：`discovery_method: "manual"`、`composite_score: 1.0`、`confidence_level: "high"`、`relationship_id: "rel_manual_<uuid4().hex[:10]>"`、`target_source_type: "manual"`、`source_constraint: null`、**`type` 由列数服务端推导写入（1 列 → `single_column`，多列 → `composite`），不取客户端值**（reader 第 2 步结构校验严格要求该字段，§1.1；与 §3.3「无类型下拉」同一口径——手工条目不可能缺字段或错值）、无 `metrics`、无 `constraint_name`。cql reader 八步校验零改动识别（§4.4 论证）。
- **D8 修改算法关系的实质字段即重标手工**：修改既有关系（含 FK 与推断）的表/列/类型/基数任一实质字段后，该条目 `discovery_method` 重标为 `"manual"`、`composite_score` 重置 1.0、`confidence_level` 重标 `"high"`、`target_source_type` 重标 `"manual"`、`source_constraint` 置 `null`、移除 `metrics` 与 `constraint_name`；`relationship_id` 保留原值——重标后非实质字段口径与 D7 完全一致。理由：分数、五维明细与键来源描述都必须与内容自洽——`target_source_type` 是序列化层从发现信息派生的算法溯源（primary_key/foreign_key/llm_inferred 等，writer.py:318-417），内容一经人工改动，原溯源即失义；cql 阈值过滤依赖分数语义。仅删除则直接移除，不影响其他条目。
- **D9 CLI 不背书**：`metaweave rag_load --type cql` 保持现状不改造，WebUI 模块完成后不保证其可用（需求 1）；`--step cql` 生成侧只接收共享层的可选参数（§5.4 provenance，缺省省略属性），既有行为不变。
- **D10 零关系放行**：发布时 rel 产物为空关系列表（或推断关系全部被阈值过滤）不阻断发布，成功消息附告警（与采集侧 D3 告警基调一致）。空列表既可来自采集，也可来自 PUT 删光全部关系（§4.2 允许空列表，A07/A09 的删除语义与 A19 的零关系发布由此衔接）。

## 1. 现状盘点与复用点

### 1.1 cql 生成链（`metaweave/core/cql_generator/`）

- `CQLGenerator.__init__(config_path, domain_resolver=None, config=None)`（generator.py:31）已支持快照注入（doc 26 §6.2 模式）与 `DomainResolver`；`cql_generation.composite_score_threshold` 缺省 0.9、显式非法值报 `ValueError`（generator.py:59-94）——需求 5 的阈值继承天然生效。
- `JSONReader.read_all()` 读 json 画像目录 + rel 目录；关系消费为八步校验链（reader.py:363-568）：ID 校验 → 结构校验 → 分数校验（FK 豁免）→ 同 ID 载荷冲突 → 阈值过滤（`composite_score >= threshold`，FK 直通）→ 重复 ID 去重 → 转换。**结构校验要求的字段**：`relationship_id`（非空字符串、无首尾空白）、`type`（严格 `single_column`/`composite`）、`from_table`/`to_table`（含非空 `schema`/`table`）、单列 `from_column`/`to_column` 或复合 `from_columns`/`to_columns`（非空列表、两侧等长）、`cardinality`（显式 ∈ {N:1, 1:1, M:N}）、`discovery_method`（非空字符串）。
- `CypherWriter.write_all`（writer.py:53-84）在 global 模式下**仅产出一个脚本文件** `import_all.{db}.cypher`：约束、表节点（`MERGE (n:Table {full_name})` + SET，:290 起）、列节点、HAS_COLUMN（:341-344）、JOIN_ON（`MERGE ... {relationship_id}` + SET，:348 起）全部章节合并在 `_write_import_all` 内（数据构造 :256-264）；generator 随后追加元数据文档。`_write_constraints`/`_write_table_nodes`/`_write_column_nodes`/`_write_has_column_rels`/`_write_join_on_rels` 五个分文件方法**全仓零调用（死代码）**，本次不参照也不更新。**行注入先例**：`_write_import_all` 的 JOIN_ON 数据构造处在 `to_cypher_dict()` 结果上补 `src_full_name`/`dst_full_name`（writer.py:261-264）——provenance 注入照抄此模式。
- rel 目录的读取 glob 为 `*.relationships_*.json`（reader.py:372，非递归）。

### 1.2 cql 加载链（`metaweave/core/loaders/cql_loader.py`）

- `CQLLoader(config)`：config 需含顶层 `cql_loader` 键（`input_file`、`neo4j.{uri,user,password,database}`、`options`）；主配置实际位于 `loaders.cql_loader`（metadata_config.yaml:503-511），发布侧注入时搬移一层（§6.5）。
- `validate()`：文件存在（glob 唯一匹配）+ Neo4j 连接测试，失败返回 False 不抛（:130-182）。
- `load(clean=True)` 现状：**先全清（:196-198）后解析（:202）**；解析出零章节时 `_load_by_section([])` 初始 stats 即 `success=True`（:296-303），空图也「加载成功」；加载后校验（:216-221 调 :575-643）对数量不符**只记 warning** 不改 success，统计头提取不到时静默跳过；`validate()`（:130-182）只查文件存在与连通。三处缺口由 §5.5 加固关闭。另有 `_get_graph_stats` 链式内联 MATCH 在零 JOIN_ON 时整条查询零行返回、Python 侧落全零兜底（:612-643）——有表有列的零关系发布会被误判数量不符，§5.5 一并修。注意 `_clean_database` 失败会抛出（不在内部 try 内），由发布侧宽兜底收敛。
- **驱动无关闭**：`validate()` 即创建 `Neo4jConnectionManager` 并 `initialize()` 建驱动（:155），`CQLLoader` 无 `close()`——校验失败、加载失败、成功路径全部泄漏驱动。底层 `Neo4jConnectionManager.close()`（services/db/neo4j_connection.py:51）幂等可用；发布侧 `finally: loader.close()` 先例在 table_schema（:861）与 dim_value（:1110）。§5.5 一并补齐。

### 1.3 rel 产物格式（23.1 已定，真实样本核对）

`output/<sid>/<jid>/rel/{db}.relationships_global.{json,md}`。json 顶层：`generated_by`/`database`/`metadata_source`/`json_metadata_version`/`json_files_loaded`/`database_queries_executed`/`generated_timestamp`/`statistics`/`relationships`。关系条目字段（样本并集）：`relationship_id`、`type`、`from_table{schema,table}`、`from_column`（复合为 `from_columns`）、`to_table`、`to_column(s)`、`discovery_method`（`foreign_key_constraint`/`physical_key_matching`/`logical_key_matching`/`llm_inferred`）、`target_source_type`、`source_constraint`、`composite_score`、`confidence_level`、`metrics`（仅推断）、`cardinality`、`constraint_name`（仅 FK）。

md 由 `RelationshipWriter._write_markdown`（relationships/writer.py:580-666）从 `Relation` 对象生成：头部（库名/生成方式/生成时间/关系总数）、统计摘要（外键/推断/复合/单列/高中置信度计数）、关系详情（`### N. schema.table.col → ...`、类型、源/目标列、关系类型、置信度、评分明细、推断方法）。md 无任何下游消费者（发布与 cql 生成只读 json），仅人读报告。

### 1.4 发布模式先例（`backend/publishing/publish_service.py`）

- 步骤白名单 `normalize_publish_steps`（:185-200，现支持 db/ddl/json/domain/table_schema/dim_value）→ 增补 `rel`。
- `publish_steps` 前置检查捕获各步骤运行标识（`updated_at`），提交前在源行锁下核对；`_publish_dim_value`（:1010-1114）为外部存储发布的完整先例：锁内做 源/启用/工作区/登记版本/步骤 marker 复查 → validate()（失败插 `is_current=False` 失败行）→ load() → 成功 `clear_current` + 插 current 行 → commit 释放锁。
- `_verify_step_current_under_lock(session, job_id, step, marker)` 可直接复用，rel 调三次（json/domain/rel）。
- 发布 ID：`publish_steps` 前置失败不生成发布 ID；同请求多步骤共享一个 `publish_id`——rel 的 Table 节点 `publish_id` 属性即取该值。

## 2. 总体流程

```
采集（23.1，不变）          发布（本设计新增）
─────────────────          ─────────────────────────────────────
json ─┐                    发布页预检（宽松，D6）：rel 行 success + 顶层非忽略
domain ─┼→ rel 步骤 →       │  文件 + 作业级全 success → rel 解冻可选
                           ┌→ 点击"编辑"（可选）：
       │  rel/{db}.json     │    GET rel-config（列表+指纹+表清单）
       │  rel/{db}.md       │    增/删/改关系 → PUT 写回 json + 重渲染 md
       │                    └→ 勾选 rel，点发布：
       │                         会话1 预检（三行 success + 新鲜度 + 产物核验 + 三 marker + rel 指纹）
       │                         本地段 无（生成放锁内，见 §6.3）
       │                         会话2 锁下复查（源/登记/三 marker + rel 指纹）
       │                           → 清空 cql 目录 → 生成 cql（含 provenance）
       │                           → 核验 cql 产物
       │                           → CQLLoader.validate() + load(clean=True)
       │                           → 发布行（成功 current / 失败非 current）
       └── json 画像目录 ──→ （cql 生成的 Table/Column 节点来源）
           domain yaml ───→ （cql 生成的 table_domains 属性来源）
```

**有意偏离及理由**：

| 偏离点 | 原型形态 | 实现形态 | 理由 |
|---|---|---|---|
| 字段选择控件 | 源/目标字段为单值下拉（rel-2/rel-4） | 列名多选 chips 按序配对：第 i 个源列对应第 i 个目标列、两侧等长校验；选 1 个即单列，类型由列数自动判定（无类型下拉） | 需求 7 手工关系须支持多字段（复合键）关联，单值下拉表达不了 |
| 基数选项 | 三选 N:1 / 1:N / 1:1 | {N:1, 1:1, M:N} | cql reader 契约拒绝 1:N（§1.1，doc 19）；M:N 为合法值，原型漏收 |
| 关联方向落库 | 两分段「源表→目标表 / 目标表→源表」 | 控件照原型保留；落库归一为 from/to 写序——选「目标表→源表」即两侧互换写入，N:1 断言 from 端为引用方（多侧）。前端不拦截也不自动换向：(方向, 基数) 组合按构造无歧义，预览行始终渲染落库形态 `from.列 → to.列 (基数)` 供核对；1:1 / M:N 两侧对称，方向仅决定写序 | 方向只是录入习惯，不引入第二套方向语义 |
| 修改态基数「原」角标 | 1:1 分段带「原」标记 | 不做角标；载入条目当前值为默认选中 | 「原」是原型对"该条目原基数为 1:1"的示意，非交互需求 |
| 统计标签分档 | 「1 外键约束 / 4 规则+LLM / 2 仅规则匹配」 | 按当前列表 `discovery_method` 实时派生：候选总数 / 外键约束 / 推断 / 手动新增 | 「规则+LLM」「仅规则匹配」是采集遥测（statistics 的 rule_only/llm_only/overlap，§4.3 不随编辑重算），编辑后会与列表脱节；按条目派生才随编辑联动，且能纳入「手动新增」档 |
| 低分告警口径 | 黄色告警条点名低分行（如 jaccard 0.5、置信度中） | 非 FK 且 `composite_score < 0.90` 的条目触发告警并高亮对应行 | <0.80 的关系采集写盘前已滤（§1.3），弹窗内剩余最低为 0.80–0.90 的 medium 档；0.90 是 high 分界 |
| 弹窗说明文案 | 「保存后将重新生成 CQL 并加载到 Neo4j 图库」 | 「保存后写回 rel JSON 与 MD；CQL 生成与 Neo4j 加载在发布 rel 时执行」 | 保存只落 json+md（§4.3）；CQL 属发布过程（D1），文案对齐实际语义 |
| 成功卡片分类计数 | 「1 条修改 · 1 条删除 · 1 条新增」 | 前端 PUT 前以本地列表对 GET 基线 diff 统计三类计数；「查看 rel json 文件」为前端格式化 JSON 预览（不新增端点） | 计数是编辑会话事实，服务端 PUT 只见最终列表 |

- 保存流程（两级）：表单输入须先经表单内「保存修改／+ 保存关系」进入本地列表——表单打开期间底部 [保存（写回 JSON 与 MD）] 禁用并提示「请先保存或取消当前关系编辑」（防未提交的编辑被静默丢弃的假成功）；[保存] 调 PUT 全量提交关系列表 → 成功展示保存成功卡片并刷新指纹；409 `rel_regenerated` 时提示「Rel 产物已重新生成，请重新加载」；500 `rel_write_failed` 时提示写回失败（消息注明 JSON 未写入）并允许直接重试——两阶段写回保证指纹未失效（§4.3）。
- 弹窗打开时 GET；采集作业重跑导致指纹失配的兜底同上。

## 4. rel 编辑 API（`backend/profile_loading/rel_config_api.py`）

路由挂 `backend/api/routers/publishing.py`（:96/:136 先例；**API 形态对称 dim-value-config**——三端点、GET 带指纹、PUT 失配 409。**锁策略有意不同**：dim_value 保存仅靠 dim_config 行 `updated_at` 乐观 409、不加锁（dim_value_config_api.py:251/:459）——其发布语义是现读配置、最后写者胜出；rel 发布要求「发布内容 = 预检核对内容」，PUT 须持源行锁在锁内冻结（§4.3））：

| 端点 | 说明 |
|---|---|
| `GET /api/data-sources/{source_id}/collection-jobs/{job_id}/rel-config` | 关系列表 + 内容指纹 + 表清单（schema.table 列表）+ database 名（前缀与段名对齐 dim-config 先例：publishing 路由挂 `/api/data-sources`（publishing.py:33），路径段为 `collection-jobs`（:93/:105/:117/:133）） |
| `GET .../rel-config/object-columns?schema=&table=` | 指定表的列名列表（来自 json 画像 `column_profiles` 键） |
| `PUT .../rel-config` | 全量保存关系列表（payload：`fingerprint` + `relationships[]`；成功响应回带**新指纹**——§3.3 保存后刷新指纹的数据来源） |

### 4.1 前置与读取（GET）

- 会话：源存在/启用、作业工作区归属（`assert_workspace_owner`）、**rel 步骤行存在且 success**（编辑面向正常采集产物；行缺失/failed 提示先重跑 rel）。
- 读取 `resolve_rel_output_dir(sid, jid)` 下 `{db}.relationships_global.json`（O_NOFOLLOW 加固读，dim_value 同款 `_read_regular_text` 模式）；文件缺失 → 404 口径的配置错误。
- 指纹 = rel json 文件内容 SHA-256 十六进制前 16 位。
- 表清单来自同作业 json 画像目录（`read_managed_json_input` 的对象集合，`schema.table` 列表）。

### 4.2 保存（PUT）校验链（本地段，按序）

1. 指纹核对：与当前文件不一致 → 409 `rel_regenerated`（编辑期间产物被重跑/他处修改）。
2. 列表逐条校验（**reader 兼容口径**，§1.1 字段全集）：
   - 匹配既有 id 的条目：**实质字段（from/to 表、列、类型形态、基数）是唯一客户端输入**——实质字段与原条目一致 → 非实质字段（`discovery_method`/`composite_score`/`confidence_level`/`metrics`/`target_source_type`/`source_constraint`/`constraint_name`）**一律以服务端原值覆盖回写**（D8「分数必须与内容自洽」的逆命题：内容未变则分数不得变——杜绝客户端改分影响 cql 阈值过滤）；实质字段有变更 → 按 D8 重标（manual、1.0、high、target_source_type=manual、source_constraint=null、去 metrics/constraint_name、保留 relationship_id）；
   - 新增条目（无既有 id）：按 D7 定型（服务端生成 `relationship_id = "rel_manual_" + uuid4().hex[:10]`）；
   - 未知 id（payload 携带既不在当前文件、又非留空待生成的 `relationship_id`）→ 400 `rel_config_invalid`「未知 relationship_id，请重新加载」——id 的合法来源仅 GET 回传（更新）与服务端生成（新增，D7），此规则防前端 diff 错乱把本地临时 id 写进产物；
   - 通用约束：`relationship_id` 全表唯一；**`type` 由服务端按列数推导写入（1 → `single_column`，>1 → `composite`），客户端值一律忽略**；两侧列数等长（且 ≥1）；`cardinality` ∈ {N:1, 1:1, M:N}；from/to 的 schema.table 必须在表清单内；列名必须在对应表的列清单内（防拼写错列）；**空列表 `[]` 合法**（用户可删光全部关系）——与 D10 衔接：statistics 四计数归零（不变式 0+0==0 成立）、md 重渲染为仅头部与统计、发布照常放行并附零关系告警。
3. 校验失败 → 400 `rel_config_invalid`（附首条错误明细，dim_value 三态拦截文案风格）。

### 4.3 写回

- **PUT 持源行锁写回**：进入即 `lock_db_source_row`（与发布 `_publish_rel`、采集 rel 步骤同一把源行锁），锁内完成指纹核对、逐条校验与两文件写回——与发布的锁下指纹复核及 CQL 生成互斥（§6.3），保证「发布核对通过后到生成结束，rel json 不会被编辑改写」；等锁的 PUT 在发布提交后才落盘，其内容归下一次发布。GET 只读不持锁。代价（已确认可接受）：发布在锁内跑 CQL 生成 + Neo4j 加载，期间同源编辑保存会等锁——开发阶段加载为秒级，等待可接受；「发布 vs 发布」互斥为 dim_value/table_schema 既有现状（Milvus 加载同在锁内），非本设计新增。
- **json 内容构造**：读原 json → 替换 `relationships` → 重算 statistics 基础计数，**口径对齐采集侧 `_calculate_statistics_v32`（writer.py:549-570）在 Relation 上的判定、落到 json 条目谓词**：
  - `total_relationships_found = len(relationships)`
  - `foreign_key_relationships` = `discovery_method == "foreign_key_constraint"` 计数（与采集侧 `relationship_type == "foreign_key"` 经序列化双射等价，writer.py:316-319；D8 改标 manual 的条目自然出桶，manual 与推断族均不计入）
  - `composite_key_relationships` = `type == "composite"` 计数；`single_column_relationships` = `type == "single_column"` 计数（对应采集侧 `is_composite` / `is_single_column`）
  - 不变式自检：composite + single == total
  （json 条目无 `candidate_origin`，rule_only/llm_only/overlap 三档无法从列表重算——保留遥测的根因，也是 §3.3 统计标签按 `discovery_method` 派生的原因）；**保留**算法遥测字段（`total_suppressed_single_relations`、`rule_only_*`/`llm_only_*`/`rule_llm_overlap_*`、`llm_total/success/failed_pairs`、`json_files_loaded`——描述算法运行，不随编辑重算）；其余顶层字段（`generated_by`/`generated_timestamp` 等）原样保留——**有意为之**：这些字段与 `json_files_loaded` 等遥测描述的是算法采集快照，编辑不冒充新采集；「产物已被编辑」由发布侧内容指纹（§6.2）与 md 头部重渲染时刻体现，不在 json 里另加编辑时间戳（无消费者，不加）。序列化参数与 `RelationshipWriter` 写盘一致（实施时对齐 `json.dumps` 参数）。
- **两阶段写回（部分写入防护）**：锁内先把 json 新内容与 md 重渲染文本（从新 json 内容反序列化 `Relation`（§5.2）→ `render_markdown_report` 取文本，D4——`database_name` 取 json 顶层 `database`、阈值取主配置快照 `decision.*`，§5.2；头部"生成时间"为重渲染时刻，"生成方式"取 `generated_by` 原值）**全部写入同目录临时文件**（`mkstemp`，统一 `.tmp` 前缀）；渲染或写临时文件任一失败 → finally 清理临时文件、返回 500 `rel_write_failed`——两份原文件未动、指纹仍有效，前端直接重试即可。随后 `os.replace` **先 md 后 json**（权威文件最后落盘）：任一替换失败 → 清理残留临时文件、返回 500 `rel_write_failed`（消息如实注明「JSON 未写入」）——此时至多 md 领先 json（md 无下游消费者），**json 未变 ⟹ 指纹有效 ⟹ 重试即恢复**（重试对 md 为幂等重渲染）；成功后由最终 json 计算新指纹回带。
- **失败面（不再表述为「无害」）**：不存在「json 已换、md 失败、旧指纹失效」的重试死锁——json 落盘成功即两份均已落盘；失败态要么零替换、要么仅 md 领先，两者皆可用原指纹重试恢复。崩溃残留的 `.tmp*` 由 §6.2 预检忽略规则兜底（与 `.backup` 同款），PUT finally 清理为第一道。

```

### 6.2 解冻与预检（D6 分层）

两道检查的分工（终稿固定；混淆会把「json 重跑后 rel 未重跑」做成页面上灰置，与宽松解冻矛盾）：

| | check_publication（UI 预检，页面加载/点击前刷新） | publish_steps 前置（仅当 chosen 含 rel） |
|---|---|---|
| rel 行状态 | inspector 取 status，按 :304 统一公式合成 publishable/reason | json/domain/rel 三行均 success（第 1 条） |
| 产物判定 | `check_rel_output_ready`（宽松：目录顶层有**非忽略**普通文件，忽略规则同右） | 文件面核验（恰两文件、可解析、库名，第 2 条；忽略 `.tmp*`/`.backup`） |

- `check_rel_output_ready`（前端预检用，宽松）：`resolve_rel_output_dir` 顶层存在**非忽略**普通文件 → `True`，否则 `False`——返回 **bool**，与 `check_dim_value_output_ready` / `check_domain_output_ready` 同构（reason 由 check_publication 的 elif 分支自拼固定文案「该作业没有 Rel 产物」，:288-294 / :297-298 同款），不引入 tuple 第三形态。**忽略规则与执行预检共用**（第 2 条）：`.tmp*` 前缀文件与 `.backup/` 子目录不算数（子目录本就不属「普通文件」，实际新增的是 `.tmp*` 排除）——PUT 崩溃残留的临时文件不会单独造成假就绪。check_publication 的 rel 条目沿其它预检步骤同构（加入后共 7 步：db、ddl、json、domain、rel、table_schema、dim_value）；目录不可用（符号链接 ValueError / 不可读 OSError）兜底降级为未就绪 + warning（check_domain/dim_value 同款，实施修订——否则会穿透 check_publication 使整页 500）：加入 :236-243 固定清单与 `_INSPECTORS` 注册，**插入位置固定在 DOMAIN 之后、TABLE_SCHEMA 之前**（与页面 STATIC_GROUPS 的 c 组位置一致；前端按 step_name 建字典消费、顺序仅影响 steps[] 展示，但与分组认知对齐免歧义——与 SELECTABLE_STEPS 末尾追加的请求序互不冲突），output 分支为**显式 `elif step_name == REL_STEP`**（不得落进 json 兜底的 else——dim_value :296 的同款教训）；`publishable = rel 行 success ∧ output_ready ∧ 作业级全 success`（:304 统一公式）。
- 执行预检（`publish_steps` 前置段，严格，失败 400 不生成发布 ID）：
  1. json/domain/rel 三步骤行均 success（缺一 → 「同一作业的 JSON/Domain/Rel 步骤未成功，无法发布 Rel」）；且**新鲜度**：rel 行 `updated_at` 须晚于 json 行与 domain 行的 `updated_at`——json/domain 在 rel 之后重跑（行仍 success）时 cql 会用新 json/domain + 旧 rel 生成，JOIN_ON 的 `MATCH` 匹配不到即静默丢边；过期 → 「同一作业的 {已重跑者} 已重跑，Rel 产物已过期；请重跑 Rel 后再发布」（多个过期者用「与」连接，23.1 会话 3 消息风格）；
  2. rel 目录恰好 `{db}.relationships_global.{json,md}` 两普通文件（`.backup` 子目录与 `.tmp*` 临时文件忽略——PUT 两阶段写回的崩溃残留兜底，§4.3）、json 可解析、`database` == 登记库名、`relationships` 为列表、`statistics` 为对象（23.1 采集核验的文件面子集）；
  3. json 画像目录 ≥1 个有效画像 json（cql 的 Table/Column 节点来源；`read_managed_json_input` 复用）；
  4. domain yaml 存在且 `verify_domain_artifact` 通过（table_domains 属性来源；与采集侧"即使 domain=null 也要 domain 产物"的 23.1 决策一致）；
  5. 主配置快照合法（含 `cql_generation.composite_score_threshold` 校验，generator 构造期完成）；
  6. 捕获锚点并经既有通道传递（防"锁下现读当锚点"的实现漂移）：
     - **rel 行 `updated_at` 走 `run_markers` 通道**：`inspect_rel_context` 返回 `(rel 行 last_status, rel 行 updated_at)`——dim_value 的 inspector 返回上游 dim_config 行 marker 是同构先例（inspect_dim_value_context，dim_value_loader.py:22-28）；
     - **json/domain 两行 `updated_at` 与登记快照打包为 `RelPrecheckSnapshot`**（`read_registration_snapshot` + 两行 marker），经 `registrations` 旁路携带——dim_value 借该字典携带登记快照的同一模式（控制流形状见下方「锚点捕获的控制流」：**循环外独立分支**，非循环内特例；json/domain 即使未入选，锚点也有入口）；
     - **rel json 内容指纹随 `RelPrecheckSnapshot` 携带**（`rel_fingerprint`，预检文件面核验段计算，与 §4.1 编辑 API 同口径 SHA-256 前 16 位）：行 marker 只反映采集重跑，编辑保存（§4.3 PUT）不动 `job_info`——内容变更只能由指纹捕获；
     - `_publish_rel` 签名对齐 dim_value 形态：`(settings, source_id, job_id, publish_id, run_markers[REL_STEP], registrations[REL_STEP])`。

  新鲜度判据说明：用**行时间戳排序**而非产物内锚点。table_schema 先例是内容锚定（md manifest 记录 `source_json_updated_at`，预检读 json 行 marker 传入核对，publish_service.py:251-256、`check_table_schema_output_ready` 第 3 参），但 rel json 无此类字段，补齐需改 23.1 产物格式；行排序达到同等保证——23.1 采集侧的锁下 marker 机制保证 rel 成功时读到的就是当时最新的 json/domain 产物，故「rel 晚于两者完成」即「rel 产物对应当前产物」。锁下无需复查排序：§6.3 的三个 `_verify_step_current_under_lock` 保证三行自预检未变，排序结论随之成立。**并发窗口封闭（实施修订）**：assert 与 capture 是两个无锁会话——上游重跑可能恰在其间提交，使 assert 以旧时间戳判过、capture 却锚定新 marker（锁下核对该新值「自预检未变」必然通过，旧 rel 便配新 json 发布）。故排序以**锚点 marker** 为准：`capture_rel_precheck_snapshot` 读取三行的同一会话内复查排序（`_assert_fresh_ordering` 二次调用），锚定的就是将锁下核对的那组时间戳。**等值边界（严格 `>`，不用 `≥`）**：`updated_at` 为 timestamptz 微秒精度、`func.now()` 取事务开始时刻（models.py:213-215、repository :110/:124）——正常链路下 rel 的会话 3 事务与上游提交之间隔着完整生成过程，等值不可能发生；若出现等值，唯一现实成因是并发乱序（上游重跑事务先 begin、`now()` 与 rel 同微秒、阻塞在源行锁后于 rel 提交）——此时 rel 确已过期，严格 `>` 拒绝并提示重跑 rel 是保守正确方向；改 `≥` 恰在该病态下放过过期产物，不采纳。**产品结论（显式）**：json/domain 重跑后，**仅用编辑弹窗 PUT 对齐内容不能解除过期**——PUT 是人工编辑、未经算法比对，不重建「rel 针对当前产物生成」的事实，指纹一致也与新鲜度无关（指纹防的是「预检后被改写」，新鲜度防的是「生成基线过期」，两道正交）；必须重跑 rel 采集步骤刷新行时间戳后方可发布（过期 400 的文案即「请重跑 Rel 后再发布」）。不做「PUT 成功时 touch rel 行 updated_at」的替代——那会伪造新鲜度并污染采集状态机（`updated_at` 归 start/finish_step 管理，100 备忘录 §3 口径）。

**锚点捕获的控制流（终稿固定；dim_value 三态拦截同位，publish_service.py:1201-1214 先例）**：`publish_steps` 预检循环 `for step_name in chosen:`（:1152-1177）只对入选步骤跑 inspector 填 `run_markers`/`registrations`——**仅选 rel 时 json/domain 两行不会被读**。故 rel 的锚点构造是循环外的独立分支：

```
（run_markers 循环 + 作业级准入/步骤状态两道闸之后、publish_id 之前）
if REL_STEP in chosen:                      # 与 json/domain 是否入选无关
    assert_rel_publish_strict(settings, source_id, job_id)
        # 第 1–5 条：三行存在性 + success 就地复查（读取三行做新鲜度比较时一并断言）
        #   + 新鲜度排序 + json 画像 ≥1 + domain yaml 核验 + 主配置快照合法；
        #   任一失败 → 400，不生成 publish_id
    registrations[REL_STEP] = capture_rel_precheck_snapshot(settings, source_id, job_id)
        # 第 2+6 条锚点：read_registration_snapshot + json/domain/rel 三行 updated_at
        #   + rel 文件面核验 + rel json 指纹

- cql 生成放锁内的理由：与 dim_value 的 Milvus 加载同位；生成是本地快速文件操作，且三 marker 复查与生成之间不留窗口。
- **指纹与锁的配合**：§4.3 的 PUT 持同一把源行锁写文件——锁下指纹复核通过后，到生成/加载/插行/提交全程，rel json 不可能被编辑改写（PUT 阻塞等锁；获锁时发布已提交，其内容归下次发布）。md 无下游消费者，不设指纹（json 与 md 的短暂不一致窗口及恢复办法见 §4.3 两阶段写回）。
- **锁内禁用 `_store_failure`**：其实现另开 `platform_session` 并对同一源行 `FOR UPDATE`（publish_service.py:384-386）——持锁会话内调用即对外层行锁自等待，请求挂死。锁内确定性失败（生成/核验不满足、`CQLScriptValidationError`、validate 拒绝、load 失败/异常）一律用当前 session 直接 `insert_publish_row` + `commit`（源存在/启用在锁下已复查，`_store_failure` 的登记重查在锁内属冗余）；需要 `_store_failure` 的宽兜底必须先让异常退出持锁会话（with 外围 except，table_schema :843-858 同款）。
- **current 撤销语义**（对照 dim_value 的 `if success or replacement_started: clear_current`（:1066-1069）与 table_schema 的保守异常转换（:812-817）与宽兜底 `revoke_current=replacement_started`（:857）、`_store_failure` 的 `revoke_current` 契约（:375-378)）：全清模式下"替换已开始"= 进入过 `load()`——stats 能返回意味着 clean 已提交；抛异常时是否已提交不可知，保守按已开始处理。`MATCH (n) DETACH DELETE n` 为单事务，clean 自身失败即回滚、图实际完好，此时撤销属保守方向：宁可显示无 current，不留指向已消失数据的 current，重跑发布即恢复一致。validate() 失败与 cql 生成/核验/loader 构造段异常发生在图未动之前，维持不撤销。**clear_current 的执行边界（钉死）**：仅在「未抛 `CQLScriptValidationError` 且 `load()` 主体已被调用」的路径执行——即 try 块正常返回（任意 result）或落入通用 `except Exception` 后的直通路径；`CQLScriptValidationError` 分支插行即 commit 返回，**永不触及 clear_current**（实现时该 except 必须列在通用 `except Exception` 之前——Python 按序匹配，写反会被宽分支截获、图未动却撤销 current）。其「不撤销」以 §5.5「clean 前抛出」为前提，两者绑定：章节核验若移到 clean 之后，不撤销即不再成立。**提交失败撤销**：`load()` 之后置 `replacement_started`——锁内 clear_current/插行/commit 段任何失败（含 commit 抛错、意外 ValueError）退出持锁会话后按该状态 `_store_failure(revoke_current=True)`；「宁可显示无 current，不留指向已消失数据的 current」对提交失败同样成立。
- 成功消息：`Rel 已发布到 Neo4j（{tables} 张表 / {columns} 列 / {relationships} 条关系）`（取 `CQLGenerationResult` 的 `tables_count`/`columns_count`/`relationships_count`——generator.py 构造处实有字段，无 fallback 需求；关系数为经阈值过滤后的值）。零关系（`relationships_count == 0`）时消息后附「；关系为空，请检查 Rel 产物与阈值配置」告警（D10）。

## 11. 边界与不做的事

- 不做 Neo4j 按源替换/多源隔离（D2 拍板全清；备忘录挂账）。
- 不做 Neo4j 实例级发布互斥：源行锁只按 source_id 互斥，多源并发发布同一 Neo4j 的交替全清重写不在防护范围，以单源发布纪律约束（D2；多源需求出现时随按源替换一并再议）。
- 不做备份恢复 UI（恢复=手工拷回 `.backup`）。
- 不为 `rag_load --type cql` 的持续可用背书（D9）。
- 不做 rel 产物的平台库表（Neo4j 即服务投影；读时 API 出现时再议）。
- 编辑弹窗不做批量导入/导出、不做关系可视化图谱。
- 不做 (方向, 基数) 组合的服务端语义校验：PUT 只保证 reader 结构合法（表/列存在、两侧等长、基数枚举）——「from 是否真是多侧」属数据分布事实，须 DB 采样才能判定，与 PUT 的 file-only 约束冲突；需求 7 本就定位手工关系为「未经算法比对」。录入正确性由预览行（始终渲染落库形态 `from.列 → to.列 (基数)`）与人工复核兜底（§3.3 偏离表），错误组合不会 400。

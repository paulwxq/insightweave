# 25.1 Web 采集 SQL 样例生成步骤改造设计

状态：**已按本设计完成 Web 采集步骤开发**。A13 的真实 PostgreSQL 锁并发冒烟尚待真机验收，现有替身测试不代表该项已通过。原 `metadata --generate-sql-rag` CLI 入口保留；`rag_load --type sql` 的受管发布改造已由 [25.2](25.2_Web发布SQL样例到Milvus设计.md) 落地（CLI 入口移除，Web 发布替代）。

把 `metadata --generate-sql-rag` 的“生成 Question-SQL → 可选 EXPLAIN 校验与修复”能力接入 Web「数据采集与画像」。页面步骤名、`job_info.step_name` 和 API `steps` 值统一为 `sql`；产物目录仍叫 `sql-rag`：`output/<source_id>/<job_id>/sql-rag/`。**本篇只设计 SQL 样例的 Web 采集与生成；`rag_load --type sql` 的路径及 Web 发布改造属于下一步修改计划，不在本篇实施、测试和验收范围内。**

## 1. 需求与路径口径

| 需求 | 设计 |
|---|---|
| SQL 可勾选 | 同一作业具备可读取的 MD、Domain、Rel 产物；新作业尚无 `job_id`，以本次勾选完整上游链暂时解锁，执行到 SQL 时按实际文件再次核验（§4、§7） |
| 输出与清理 | 固定写入 `output/<source_id>/<job_id>/sql-rag/`；每次启动生成前仅清理此目录顶层普通文件，保留子目录（§5） |
| 复用现有命令 | 直接复用 `QuestionSQLGenerator.generate`、`SQLValidator.validate_file`、`resolve_module_llm_config` 等业务函数，抽出可传入受管路径和配置快照的共享执行函数；Web 不通过 Click 命令行调用（§5） |
| 保留配置 | `sql_rag` 中生成数量、LLM、校验参数继续有效；SQL-RAG 的输入和输出路径固定在同一作业目录，不读取配置文件中的全局路径；取舍见 §8 |

**固定的作业路径。** 现有配置确有 `output.markdown_directory: output/md`，供原有非受管流程使用；改造后的 Web SQL 步骤必须忽略它，固定读取 `output/<source_id>/<job_id>/md/*.md`，不读取也不回退到 `output/md`。本需求先前写的作业根目录 `*.md`，按本次确认以 `md/*.md` 为准，与当前 Web MD 步骤的产物位置一致。Domain 文件固定为 `domain/db_domains.yaml`，Rel 报告固定为 `rel/<db_name>.relationships_global.md`；`domain/*.yaml`、`rel/*.md` 是需求的概括写法，实际读取锁定这两个文件名。

## 2. 代码现状与改造理由

- 页面 `frontend/src/views/CreateCollectionJobView.vue` 已有禁用占位项 `{ id: 'sql-rag', label: '--generate-sql-rag', enabled: false }`，前端排序/阻断表与后端 `collection_run.py` 均无 SQL 步骤。
- `metaweave/cli/metadata_cli.py::_run_generate_sql_rag` 已实现 Domain 文件解析、MD/Rel 目录选择、LLM 生成、可选 EXPLAIN 校验与修复、质量阻断；它依赖 Click 输出并读取 `sql_rag.generation.output_dir`。`metaweave/core/metadata/execution.py::execute_generate_sql_rag` 是 `metadata` 命令的 CLI 共享执行层，仍以配置文件中的全局目录为默认值。Web 不能直接沿用该默认路径，否则会读写 `output/domains`、`output/md`、`output/rel`、`output/sql-rag`。
- `QuestionSQLGenerator` 从 `db_domains.yaml` 读取 `database.name`、`domains[].tables`，按三段式表名在 MD 目录查找同名文件；Rel 文本由 `extract_relevant_relationship_sections` 从 `<db_name>.relationships_global.md` 提取。生成器目前会捕获单个 Domain 的异常并继续，只有最终产出至少一条样例时 `GenerationResult.success` 才为真。
- 当前 `QuestionSQLGenerator._build_md_context` 把 `tables: []` 解释为**全量 MD 上下文**。Domain 采集可能写出空表的 `_未分类_`，doc 24.1 的编辑器也允许保存任意空表 Domain。若对这些 Domain 生成 SQL，会将与该 Domain 无关的全部表送进提示词；`max_prompt_chars` 当前只告警，不截断也不阻止 LLM 调用。本篇改造时需移除这一空表回退（§4、§5.1），不能仅在前置检查中排除空表 Domain。
- `SQLValidator.validate_file` 对生成的 JSON 执行 EXPLAIN；开启修复时原地改写 JSON、删除未修复条目，并在同目录生成 `sql_validation_summary_<时间>.log` 及 `<样例文件>.backup`。这些都是本步骤的产物，须留在受管 `sql-rag/` 中。
- Web 采集每一步单独发起 `POST /api/data-sources/{source_id}/collection-jobs`。后端 `start_db_collection` 根据步骤依赖排序；前端 `runJob` 也按同一依赖表逐步调用。SQL 的前置关系必须在两处一致。

### 2.1 全局 `output/` 路径排查

| 当前入口 | 现有全局路径/回退 | 受管 SQL 步骤必须使用 |
|---|---|---|
| `resolve_domains_yaml_path`，由 `_run_generate_sql_rag` 调用 | `output.domains_directory` → `output.output_dir/domains` → `output/domains/db_domains.yaml` | `<作业目录>/domain/db_domains.yaml`，直接由受管 resolver 给出，不调用该全局解析链 |
| `resolve_md_context_dir`，由 `_run_generate_sql_rag` 调用 | `output.markdown_directory` → `output.output_dir/md` → `output/md`；CLI 的 `--md-context-dir` 也可覆盖 | `<作业目录>/md/*.md`，直接由 `resolve_md_output_dir` 给出，不调用该全局解析链 |
| `_run_generate_sql_rag` 的 Rel 目录 | `output.rel_directory` → `output/rel` | `<作业目录>/rel/<db_name>.relationships_global.md`，由 `resolve_rel_output_dir` 给出 |
| `QuestionSQLGenerator.__init__` 与 CLI `--clean` | `sql_rag.generation.output_dir` → `output/sql-rag` | `<作业目录>/sql-rag/`，由 `resolve_sql_rag_output_dir` 给出；清理和写盘使用同一个 Path |
| `execute_generate_sql_rag` 调用的 `verify_clean_target` | `metaweave/core/clean_targets.py::resolve_clean_target` 对 `generate-sql-rag` 仍按 `sql_rag.generation.output_dir` → `output/sql-rag` 核验清理目标 | Web 不调用该 CLI 共享执行层的全局路径校验；使用受管 SQL resolver 与 §5.2 的 `_clean_sql_top_level_files` |
| `SQLValidator.validate_file` 的输入、`.backup` 和 `sql_validation_summary_*.log` | 根据传入 `input_file` 派生，无单独的全局 `output/` 默认值 | 传入本次生成的受管 `qs_<db_name>_pair.json`；备份与报告自然留在同目录 |

`QuestionSQLGenerator` 的模块文档字符串和 `GenerationResult.output_file` 注释还写着 `output/md`、`output/sql-rag`；它们是旧路径说明，不是额外的文件访问入口，实施时应同步更新。另作范围备注：`metaweave/cli/loader_cli.py` 的 `rag_load --type sql` 仍会从 `sql_rag.generation.output_dir` 推断输入文件，可能读取全局 `output/sql-rag`。该加载路径由下一步修改计划处理，本篇不修改其代码，也不把它列入 25.1 的验收。

现有发布页已在 d 组保留禁用的 `sql` 展示行，`SELECTABLE_STEPS` 与 `check_publication` 的固定发布步骤清单均不含 SQL；发布记录的 `RAG_STEPS` 已含 `sql`。本篇只增加采集行，不修改发布页或发布预检的步骤清单；但新 SQL 行若为 `failed`，仍会按现有作业级准入阻断同作业发布，后续改造另见 `100_备忘录.md`。删除数据源时 `delete_source_workspace` 清理整个 `output/<source_id>/`，其中的 `sql-rag/` 无须单独接入删除流程。

## 3. 步骤身份与依赖

常量 `SQL_STEP_NAME = "sql"`。`sql` 仅表示采集步骤与 `job_info` 行；目录 `sql-rag`、CLI 参数 `--generate-sql-rag`、发布类型 `--type sql` 不改名。`job_info.step_name` 当前没有枚举约束，本篇不新增平台库字段或迁移。

同请求偏序新增 `sql: (md, domain, rel)`；仅对本次请求选中的两端建立排序边。由于 Domain 依赖 MD，Rel 依赖 JSON 与 Domain，前端新建作业须先勾齐可执行的上游链；重跑可只勾 SQL，复用同一 `job_id` 已有的三份成功产物。同次执行中 MD/Domain/Rel 任一以 `failed` 结果返回时，SQL 不启动，但结果展示有两条路径：后端收到包含多个步骤的同一请求时，由 `collection_run.py` 在响应 `results` 中追加一条 `sql: failed`，说明哪个上游失败；采集页按步骤逐个 POST 时，前端在收到上游 `failed` 结果后本地构造一条 `sql: failed` 展示结果，根本不发送 SQL 请求。两条路径都不清理旧 SQL 目录，也不写入或更新 `job_info` 中的 SQL 步骤行；这里的 `failed` 是本次结果，不是 SQL 行的 `last_status`。若上游请求直接抛出 HTTP 错误、没有返回结果，现有前端会结束逐步执行，不再构造后续 SQL 的阻断展示行。SQL 自身准备链在 `start_step` 之前失败的记录口径沿用现有采集步骤，统一修复另见 `100_备忘录.md`。

虽然当前生成函数只强制读取 Domain 与 MD，且 Rel 缺失时会退化为“未提取到关系段落”，**改造后的 Web SQL 步骤按本需求把 Rel 视为必需输入**。成功但零关系的 Rel 报告仍有效：要求文件格式正确，不要求报告包含关系详情条目。原 CLI 的可选 Rel 行为不作为本篇保留目标。

## 4. 输入就绪判定

共用只读核验函数为 `inspect_managed_sql_inputs(session, source_id, job_id, db_name, config) -> tuple[SqlInputSnapshot | None, list[str], str]`，供重跑页面就绪接口与 SQL 执行准备链、启动及结束复查调用。返回 `(snapshot, missing, message)`：就绪时 `snapshot` 携带受管路径、步骤 marker 和文件指纹，`missing=[]`、`message=""`；未就绪时 `snapshot=None`，其余两项说明缺少的上游和具体原因。由调用方在同一平台库会话中先核对数据源存在、启用及工作区归属；就绪接口将 `snapshot is not None` 转为 `ready`，不向前端返回快照。后端执行时不能依赖页面先前的检查结果。

1. 先校验工作区属于当前数据源，且同一 `job_id` 的 `md`、`domain`、`rel` 三行 `last_status == success`。若本次同选上游，由排序保证 SQL 执行时可查到成功行；只有旧文件、没有成功行不能绕过步骤状态。
2. MD：枚举受管 `md/` 顶层**全部 `*.md` 文件**，至少有一份；每份都必须是普通、非符号链接、可读 UTF-8 文件，文件名严格为 `<db_name>.<schema>.<object>.md`（三段均非空，库名等于登记源库名）。`manifest.json` 不算 MD。`_get_filename` 会直接拼接库名、schema 名、表名；PostgreSQL 允许引用标识符包含点，此时虽可生成四段以上的合法文件名，本篇仍按既有三段式约定拒绝，不新增含点标识符解析支持。为防 Domain 引用不存在的表，参与生成的 Domain 表名必须能在这批 MD 文件中命中；不能以“目录里有任意 MD”代替该核验。对顶层全部 `.md` 采用同一校验口径，是因为 `QuestionSQLGenerator._build_md_map` 会先 `glob("*.md")` 并读取全部文件，然后才按 Domain 选择上下文。
3. Domain：`domain/db_domains.yaml` 是普通、非符号链接文件；YAML 可解析为对象，`database.name` 等于登记源库名，`domains` 为非空列表。先校验每个 Domain 的 `name` 为非空字符串；`tables` 缺键按 `[]` 处理并跳过该 Domain，与发布侧 `read_domain_rows` 一致；显式 `null`、非列表或列表中含非字符串元素，均按未就绪拒绝。允许显式 `tables: []`，与采集和 doc 24.1 编辑规则一致。再按 `skip_uncategorized`、对应问题数是否大于 0、`tables` 是否非空筛选参与生成的 Domain；**空表 Domain 不参与 SQL 生成，也不能算作“具备 MD 上下文”**。参与生成的每个表名都须对应一份受管 MD。至少有一个参与生成的非空表 Domain，否则在清理 SQL 目录和调用 LLM 之前报“没有可生成 SQL 的业务域”，不把整份 MD 作为空表域的回退上下文。已有 `verify_domain_artifact` 会拒绝符号链接或非普通文件，要求 YAML 可解析为对象且 `domains` 为非空列表；本步骤仍需额外校验登记库名、各 Domain 的 `name`/`tables` 及表名与受管 MD 的对应关系，确保生成器实际消费的上下文有效。
4. Rel：`rel/<db_name>.relationships_global.md` 是普通、非符号链接、可读 UTF-8 文件，包含生成器现有报告头 `# 表间关系发现报告` 与匹配的 `database: <db_name>`。零关系报告合格。Rel JSON 不是本步骤的直接输入，不把它加入本篇的解冻条件。
5. 三类输入均只读，均经 `resolve_md_output_dir`、`resolve_domain_output_dir`、`resolve_rel_output_dir` 限定在受管工作区；对非常规文件、格式不符、错库名返回具体未就绪原因。记录上游三行的 `updated_at` marker，以及 **`md/` 顶层全部 `*.md` 的排序文件名清单和逐文件原始字节 SHA-256**、Domain YAML 的 SHA-256、Rel MD 的 SHA-256。开始 SQL 前和结束前在数据源锁下复查行仍为 success 且 marker 未变，并重新枚举 MD 清单、比对所有指纹；在最终复查前发生的 MD 新增、删除、改写，或 Domain/Rel 编辑改写，即使没有更新步骤行，也使本次 SQL 记 failed，不能把旧上下文生成的结果标为成功。页面就绪接口仅返回结果，不暴露这些指纹。

   **受管编辑的锁前提**：SQL 结束时在同一平台库事务中先取得 `lock_db_source_row`，再完成步骤行与文件指纹复查，并在释放源行锁前调用 `finish_step` 写入最终状态；复查与状态写入之间不得提交事务。Rel PUT 已在源行锁内写回 Rel MD；Domain PUT 也已按 [24.1 §5.2–5.3](24.1_Web发布页Domain配置编辑设计.md) 从读取指纹到 `os.replace` 及写回后核验持有同一源行锁。这样受管编辑不会在 SQL 复查通过后、标记成功前落盘。真实锁交错仍须按 §9 的 A13 待办验收。直接绕过接口修改工作区文件不遵守数据库锁，只能由复查时的指纹捕获，不能保证捕获复查后的外部写入。

   **有意收紧的边界**：现有 Rel 采集步骤只复查 JSON/Domain 步骤行的 `updated_at`，不核对文件内容；doc 24.1 §1.2 明确接受编辑 Domain YAML 后不更新步骤行、不追改 Rel。SQL 生成会实际读取这些可由编辑接口改写的文件，因此本篇在 SQL 步骤增加文件清单与内容指纹复查；**不追改 Rel 采集步骤，也不改变 24.1 已接受的 Rel 产物语义**。

## 5. SQL 步骤服务与共享执行函数

新增 `backend/data_sources/sql_step_service.py::run_sql_step(config_path, source_id, job_id=None)`，按现有 Rel 步骤模式分段：入口配置 → 平台库只读准备 → 本地输入与配置预检 → 锁下 `start_step` → 清理与生成/校验 → 产物核验 → 同一持锁事务内完成 marker/指纹复查及 `finish_step`。单独请求且无 `job_id` 时，明确报“同一作业的 MD、Domain、Rel 产物未就绪”；新作业同选上游时使用前面步骤创建的 `job_id`。

### 5.1 配置、连接与函数复用

- `load_main_config_snapshot` 只读一次。先以 `build_managed_output_snapshot` 深拷贝并覆盖登记源库名、schema 与受管 MD/Rel 路径；只有 `sql_rag.validation.enabled=true` 才解密登记源密码并用 `build_managed_ddl_config` 的连接参数构造 `DatabaseConnector`。LLM 生成始终使用 `resolve_module_llm_config(snapshot, "sql_rag.llm")` + `LLMService`。配置文件里的全局数据库连接字段不进入 Web 运行快照。
- `build_managed_output_snapshot` 对 `output` 只覆盖 `output_dir`、`ddl_directory`、`markdown_directory`、`json_directory`、`rel_directory`、`cql_directory` 六键，**不覆盖** `output.domains_directory`，也不修改 `sql_rag.generation.output_dir`；这两个全局路径仍可能留在深拷贝的快照中，不能作为 Web 作业路径。Domain YAML 必须使用下面显式传入的 `domains_path`；SQL-RAG 输出目录必须显式传入，并覆盖生成器配置副本中的 `output_dir`（或使用必填受管参数），构造后仍须断言实际目录，不得以快照已处理为由省略这些步骤。
- 从 `_run_generate_sql_rag` 中提取生成/校验的业务逻辑，形成不依赖 Click 的函数，例如 `run_sql_rag_generation(config_snapshot, *, domains_path, md_dir, rel_dir, output_dir) -> SqlRagRunResult`。Web 服务根据 `source_id`、`job_id` 构造四个路径并显式传入，自行管理清理、状态与失败；函数不得读取 `output.markdown_directory` 等全局目录作为回退值。Web 不经 shell/subprocess 调 CLI，也不调用 `execute_generate_sql_rag` 的全局路径校验。按已确认的需求，原 `metadata --generate-sql-rag` 不列入改造后的兼容目标；CLI 包装层可由实现决定是否沿用共享函数，但必须同步处置旧 CLI 测试；若命令不再可用，也须撤下仓库说明中的可用命令表述，见 §9–§10。
- `sql_rag.validation.enabled` 的分支目前在 `_run_generate_sql_rag`，不在 `SQLValidator` 内；提取共享函数时要把该分支一起移入。`enabled` 缺省按 true 计；`enabled=false` 时只生成 SQL，跳过 `SQLValidator` 构造、源库连接、EXPLAIN 与修复，按未校验结果做成功核验。
- 执行函数构造 `QuestionSQLGenerator` 时复制 `sql_rag.generation`，只将复制品的 `output_dir` 覆盖为受管 `sql-rag/`；或者为生成器新增必填的受管 `output_dir` 参数。构造后断言 `generator.output_dir == resolve_sql_rag_output_dir(source_id, job_id)`，防止遗漏覆盖后回退到 `output/sql-rag`。显式传入 Domain、MD、Rel 路径。校验时复用同一个 LLMService，给 `SQLValidator` 传同一份 `sql_rag.validation`、MD/Rel 路径和生成结果中的 `output_file`；`DatabaseConnector` 无论成功失败都在 `finally` 关闭。SQL-RAG 的四个受管路径均无配置回退。
- 修改 `QuestionSQLGenerator` 的空表行为：`generate()` 对任意 `tables: []` 的 Domain 直接跳过并记录名称、原因；`_build_md_context([])` 不再返回全量 `md_map`，以免别的调用路径重新触发旧行为。`_未分类_` 在 `skip_uncategorized=true` 时仍按原开关跳过；开关为 false 但其 `tables` 为空时，仍按空表规则跳过。仅当其 `tables` 非空且 `uncategorized_questions > 0` 时才会生成。原 CLI 不要求兼容旧的空表全量 MD 行为。
- 生成前预检配置节点类型、问题数、并发/重试/超时与修复批大小，LLM 配置也在清理前验证。启用校验时，清理前还须复用 `SQLValidator` 的键名校验，拒绝 `sql_rag.validation` 中的废弃键 `max_retries`、`readonly_mode`、`max_concurrent` 和已删除键 `modify_original_file`；可抽出其现有纯键名校验供准备链与验证器共用，避免等文件清理后才在验证器构造时抛 `ValueError`。`enabled=false` 时无需构造验证器。无效配置报明确的配置错误。连接池如需在清理前建立，应在失败时关闭；不应先删旧 SQL 产物再发现一个可预期的配置错误。

### 5.2 清理、产物与成功条件

新增 `resolve_sql_rag_output_dir(source_id, job_id)`，沿用其他受管 resolver 的 UUID、项目根和逐级符号链接校验；这只检查目录路径及其父级，**不检查目录内的条目**。开始生成前，对 `output/<source_id>/<job_id>/sql-rag/` 按以下顺序清理：

1. 经 resolver 校验后创建目录（若不存在），再枚举**全部顶层条目**，在删除任何文件之前逐个执行 `is_symlink()` 检查。只要存在符号链接，无论指向普通文件、目录还是悬空，均报“SQL-RAG 输出目录含符号链接”并停止；本轮不得已经删除其他旧文件。
2. 预检通过后，使用 `backend/data_sources/sql_step_service.py` 内的私有函数 `_clean_sql_top_level_files` 删除普通文件（含 `.json`、`.log`、`.backup` 和无扩展名文件），保留真实子目录，不清理别的作业目录。删除每个条目前再次检查是否为符号链接及是否为普通文件；发现符号链接立即停止，不调用会跟随符号链接的 `clean_top_level_files`。两次类型检查不能让绕过接口的并发目录改写变成原子操作，但不能省去删除前的复查。
3. 普通文件 `unlink` 失败时停止并把步骤记为 failed，不继续生成。此时之前已删除的文件不回滚。生成/校验产生的所有文件必须在本目录顶层。

预期主文件为 `qs_<db_name>_pair.json`；开启校验时还应有 `sql_validation_summary_<时间>.log`，开启修复时还会有 `qs_<db_name>_pair.json.backup`。生成失败或校验失败后允许留下**本次**已经写出的文件，SQL 行记 failed，后续重跑将先清理它们。不会因为文件已经写出就把步骤判为 success。

成功核验至少包括：生成器返回 success；实际主 JSON 是普通文件且位于本次受管目录；能解析为非空数组；每项 `question`、`sql` 为非空字符串；文件条数与实际保留条数一致。`validation.enabled=true` 时按校验后的文件再核验：未启用修复而存在任何无效 SQL → failed；启用修复时接受部分无效条目被删除，但最终必须至少保留一条有效样例，否则 failed。成功消息写明生成数、最终保留数、删除数和校验是否跳过。

`QuestionSQLGenerator.generate` 当前捕获单个 Domain 的生成异常并继续，以总产出条数判断生成是否成功。本篇确定沿用**部分成功**：某个 Domain 生成失败或零产出，不单独导致 SQL 步骤 failed；只要最终主文件至少保留一条符合上述生成/校验条件的样例，步骤即 success；所有 Domain 均未产出可保留样例时步骤 failed。日志及步骤结果消息须**分别**列出因空表/配置被跳过、生成失败和零产出的 Domain；跳过空表不是生成失败。`validation.enabled=false` 沿用配置含义：不连源库、不做 EXPLAIN，步骤成功只表示生成结果有效，不表示 SQL 已通过源库验证。

## 6. 后端编排与 API

- `backend/jobs/collection_run.py`：支持集合加入 `sql`，分发到 `run_sql_step`；`_STEP_DEPS` 加 `sql: (md, domain, rel)`；`_BLOCK_MESSAGES` 加对应三条。后端沿用 `backend/api/schemas.py` 的 `CollectionJobCreateRequest` / `CollectionJobCreateResponse`；前端 `createCollectionJob` 仍用 `dataSources.ts` 内联构造请求体，并使用现有 `CollectionJobCreateResponse` 响应类型，无须寻找或新增前端同名请求类型。示例请求为 `{"steps":["sql"],"job_id":"<已有作业 UUID>"}`；本篇不新增执行请求字段。
- 新增只读就绪接口 `GET /api/data-sources/{source_id}/collection-jobs/{job_id}/sql-readiness`，返回例如 `{"ready":false,"missing":["md","rel"],"message":"..."}`。先核对数据源存在、启用与作业归属，再执行 §4 的状态/文件核验；禁用源与执行路径一致，抛 `SourceDisabledError` 并返回 HTTP 409、`code=source_disabled`，不能返回 `ready=true`。不返回文件正文或数据库密码。平台库连接或读取失败沿用 HTTP 503、`code=platform_unavailable`，不能作为输入未就绪返回 400 或变成未分类 500。前端 `getSqlReadiness` 使用 `preferServerMessage=true`，接口失败时优先展示服务端具体原因。此接口只服务**已有作业**页面解冻与原因展示，不能取代 POST 内的执行时校验。新作业没有 `job_id`，无需为它预建工作区。
- `DbStepConfigError` 等既有错误按当前 API 映射：非法参数/依赖未就绪 400；平台库连接或读取故障沿用现有 `platform_unavailable` 503 口径。对于 `start_step` **之前**本地文件、配置准备或 LLM 预检中的非预期故障，新增 `SqlPreparationError(PlatformUnavailableError)`，在 `backend/api/errors.py` 注册专用处理器，返回 HTTP 503、`code=sql_preparation_error`，与 `DomainPreparationError`、`DimConfigPreparationError`、`RelPreparationError` 同款；不能把这类服务器故障报为 400。`start_step` **之后**的生成、LLM、校验、落盘故障返回 `sql` 的 failed 结果并调用 `finish_step(..., failed)`。状态写入失败须显式报告，不把失败伪装为成功。
- Web 的 `job_info.step_name` 和 API 步骤值均为 `sql`；业务日志按 API 请求上下文写入 `logs/backend/metaweave.log`，请求摘要写入 `logs/api.log`，不依赖全局 `set_current_step` 分流，也不新增 `sql.log`。若保留 CLI 包装层，其生成/校验段继续使用 `sql-rag-generate` / `sql-rag-validate` 标签，对应现有 `logs/script/sql_rag_generate.log` / `logs/script/sql_rag_validate.log`。

## 7. 页面交互

- 把 d 组占位项改为 `{ id: 'sql', label: 'sql', enabled: false }`；也可在旁展示对应 CLI 名称 `--generate-sql-rag`，但提交步骤 id 统一为 `sql`。执行结果区显示生成数、保留数和跳过校验的提示。
- **新作业**：`sql` 的暂时可勾选条件是本次已勾选完整上游链 `ddl`、`json`、`md`、`domain`、`rel`。上游实际产物此时尚不存在；执行到 SQL 时服务端按 §4 检查。撤销任一上游勾选时自动清除 SQL 勾选。SQL 自身的直接编排依赖仍是 MD、Domain、Rel；DDL/JSON 是这三步的间接依赖，页面解冻条件将其列入，是为了避免新作业明知缺上游仍允许勾选 SQL。
- **重跑已有作业**：对于未在本次勾选的 MD/Domain/Rel，`sql-readiness` 必须确认对应步骤行与实际文件已就绪；对于本次同选的上游，允许勾选 SQL，并在实际执行时重新检查。页面加载、上游选择变化、一次执行结束后刷新就绪状态；就绪请求失败时保持 SQL 不可勾选并显示错误，不能把接口失败当作可用。重跑作业原含 SQL 时，只有条件满足才预勾选。
- **为何使用独立就绪接口**：现有 Domain/Rel 的重跑解冻依赖 `rerunSteps`，它只能说明作业存在相应步骤行，不能确认文件仍在且格式可读。SQL 同时消费 MD、Domain、Rel 三类产物；若只按步骤名解冻，缺件要等点击执行、走到 SQL 准备链时才暴露，页面此前会错误显示为可勾选。已有作业因此在页面上做文件级就绪检查；后端当次核验仍在 LLM 生成前执行，避免缺件时调用 SQL 生成 LLM。
- 在 `frontend/src/utils/collectionStepOrder.ts` 与后端同样新增排序和同请求阻断消息。前端逐步发起 POST 时，SQL 请求携带前面步骤返回的同一 `job_id`；上游返回 `failed` 结果则由前端阻断本次 SQL、跳过 SQL POST，并在结果区构造 `failed` 展示结果。上游请求直接抛出 HTTP 错误时沿用页面现有的异常结束路径。服务端仍独立校验，防止绕过页面直接发请求。

| F01 | 新作业勾选与撤销上游、重跑已有作业加载 | SQL 动态解冻、自动清除、预勾选规则符合 §7；错误提示可读 |
| F02 | 点击执行后的逐步结果与重跑 | 使用同一 `job_id`；SQL 结果展示生成/保留数；发布入口仍按整体作业状态判定 |

后端新增步骤服务、配置覆盖、输入核验和编排的针对性测试；前端运行现有类型检查/构建并按 F01–F02 人工验收。测试应使用临时作业目录与替身 LLM/数据库连接，不调用真实外部服务。

**A13 真机验收待办（尚未完成）**：现有 `test_sql_final_check_and_finish_share_source_lock` 与 Domain PUT 的锁顺序测试只使用替身，验证调用顺序，未验证 PostgreSQL 的实际阻塞与事务可见性。后续在测试平台库使用独立会话，分别对 Domain PUT、Rel PUT 验证以下两种时序，不使用生产数据：

- PUT 先持锁写回并释放，SQL 随后取得锁：SQL 必须读到新文件，指纹复查失败，最终 `last_status=failed`。
- SQL 先持锁复查，PUT 尝试保存：PUT 必须等待 SQL 的 `finish_step` 提交并释放锁后才能落盘；不能在复查通过与最终状态提交之间写回。

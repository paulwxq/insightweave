# 数据源查看与删除设计

> 状态：已实施。本文是 [doc 6：数据源版本字段与修改连接设计](6_数据源版本字段与修改连接设计.md) 的增量。卡片上的“查看”“删除”按本文可用。不实现采集、发布或画像。数据源卡片的布局和视觉样式参考 [2.1.数据源管理首页](ui/2.1.数据源管理首页.html)；字段、状态标签和按钮行为以本文为准。不增加第二枚“可用”标签，“采集”保持禁用。删除确认窗按本文 §3 设计。

## 1. 需求

1. 数据源卡片右上角的“查看”打开该条数据源的只读信息页。页面仍在现有应用壳里：左侧导航不动，右侧内容区换成完整的数据源连接信息。
2. 查看页的版块顺序与“创建数据源连接”页相同，字段只展示、不能编辑，也没有“测试连接”和“创建/保存”。
3. 查看页同时放“删除”“修改”“采集”三个按钮。“修改”进入现有修改页。“采集”继续只占位，不接功能。“删除”删除这条数据源。
4. 卡片上的“删除”与查看页的“删除”做同一件事：删除当前这一条 `db_source_info` 记录。

不改数据库类型范围，仍只支持 PostgreSQL。不回显密码或密文，不连接源库，不删除源库里的业务数据。默认不删除 `output/` 下的任何目录。

## 2. 查看页

### 2.1 路由与外壳

新增路由 `/data-sources/:sourceId`，组件单独做只读页，不给 `DataSourceForm` 再加一种模式。创建页 `/data-sources/new` 和修改页 `/data-sources/:sourceId/edit` 保持不变。路由按 `/data-sources/new`、`/data-sources/:sourceId/edit`、`/data-sources/:sourceId` 的顺序声明，便于阅读。vue-router 4 按路径权重匹配，静态段优先于参数段，因此这个顺序不是把 `new` 识别成数据源编号的前提。

`App.vue` 已经是左侧 `AppSidebar`、右侧 `RouterView`。查看页只替换右侧内容，不新做一套导航。

进入页面时调用现有 `GET /api/data-sources/{source_id}`。不新增查询接口。路径参数是 UUID，手输 `/data-sources/not-a-uuid` 时后端的 `RequestValidationError` 返回 `422 invalid_request`，文案是“请求字段不合法”；前端现有映射会显示“请检查填写的信息。”这不适合一个打不开的链接。

查看页和修改页在加载时，`not_found` 与 `invalid_request` 都回到 `/data-sources?notice=not_found`，沿用列表上的“数据源不存在”，不显示空表单，也不显示“请检查填写的信息。”不改 `invalid_request` 的全局文案，创建和修改表单的字段校验仍用那句。不在路由上另加 UUID 正则。

其余加载失败留在查看页，不回列表。这包括 `platform_unavailable`、网络错误和无法识别的响应。页面显示该错误对应的现有文案，并提供“重试”和“返回数据源管理”。“重试”再次调用同一条 `GET`。“返回数据源管理”回到 `/data-sources`。数据加载成功前，不显示“删除”和“修改”；“采集”也先不出现。成功后再按第 2.3 节显示这三个按钮。不为此引入前端测试框架，用页面手测确认。

### 2.2 只读内容

版块与创建页对齐，控件换成文字。空值按下面的文案显示，不用空白输入框。

| 版块 | 展示 |
| --- | --- |
| 1. 数据库类型 | 只标明已登记类型为 PostgreSQL。不展示 MySQL 等“待开放”类型，也不提供选择 |
| 2. 连接信息 | `display_name`、`host`、`port`、`db_name`、`username`、`sslmode`、`db_version`。`sslmode` 为空显示“未指定”。`db_version` 为空显示“版本未知”。另显示登记时间 `created_at`，与卡片共用 `frontend/src/api/format.ts` 里的格式化函数，不在查看页再写一份 |
| 3. 已选 Schema | 用已保存的 `selected_schemas` 渲染标签。打开页面时不测试连接，也不重新发现 Schema |
| 4. 说明 | `description`。为空显示“未填写” |

页面不显示密码，也不显示 `password_ciphertext`、平台库凭据或密钥。`source_id` 显示在页面标题中数据源名称的下方，前缀为 `Source ID:`。

### 2.3 页内按钮

三个按钮放在页面标题右侧，从左到右为“删除”“修改”“采集”。

| 按钮 | 行为 |
| --- | --- |
| 删除 | 打开第 3 节的确认小窗。确认后调用删除接口。成功后回到数据源管理页，列表不再包含该条 |
| 修改 | 进入现有 `/data-sources/:sourceId/edit` |
| 采集 | 保持禁用，与卡片上的“采集”相同，不发请求 |

## 3. 删除

卡片“删除”和查看页“删除”共用同一个确认小窗，不用 `window.confirm`。小窗只有一句说明、一个默认不勾选的复选框，以及“取消”“确认删除”。尚未发出请求时，点“取消”、点遮罩或按 Escape 都只关闭窗口，不发请求。请求进行中，这三种关闭方式和“确认删除”一起禁用；已经发出的请求不取消，窗口保持打开，直到成功或失败有反馈。

说明文案为：确认删除数据源“{display_name}”？删除后不可恢复。请先确认该数据源没有正在执行的采集；采集过程中删除，可能留下不完整文件或新的孤立目录。名称取这条记录的 `display_name`，按纯文本显示。不要求用户再输入名称做二次确认。本阶段不检测采集是否仍在运行，这句只是提醒，不构成锁。

复选框文案：“同时删除此数据源在 output 下的目录及其全部内容”。它指的是项目里的 `output/<source_id>/` 这一整个子目录，包含其中的文件和更下层目录，不是整个 `output/`，也不是源库里的业务数据。删除数据源时一并删掉这个子目录里的生成文件是合理的：这些文件只为该数据源的采集工作区服务，登记记录删除后不再有对应的数据源；勾选后只影响这一处，源库里的业务数据和其他目录都不动。复选框默认不勾选。每次打开确认窗时，都把复选框重新设为不勾选，并清空上一次的错误。请求失败后窗口保持打开，保留当前复选框状态，方便按同一次选择重试。不勾选时这些文件继续留在 `output/<source_id>/`，只删除登记记录。这是一次性选择：登记删除后该目录成为没有登记记录关联的孤立目录，再次调用本接口会因记录不存在返回 `404`，不再清理它。本阶段只能由管理员手工清理，后续是否增加孤立工作区清理功能另行设计。

`DELETE /api/data-sources/{source_id}` 无请求体。查询参数 `delete_output` 缺省为 `false`。只删除平台库 `public.db_source_info` 中该 `source_id` 的一行。当前没有指向该表的作业或发布外键，因此不做级联。创建 `job_info`、`publish_info` 等外键之前，必须重新确定数据源删除策略；不得默认级联删除历史作业和发布画像。届时可选择禁止删除已有历史的数据源，或引入停用状态。本阶段不实现该策略。记录不存在返回已有的 `404 not_found`，响应只有 `code` 与 `message`，文案仍是“数据源不存在”。删除成功返回 `204`，无响应体。路由写成 `@router.delete("/{source_id}", status_code=204)`，不声明 `response_model`，函数内 `return Response(status_code=204)`。装饰器上的状态码让生成的 OpenAPI 把成功响应标成 `204`；只在返回值里写 `204` 时，文档仍可能显示默认的 `200`。返回 `Response` 是为了避免框架把空结果序列化成 `null`。当前 `apiRequest()` 对任何状态码都执行 `response.json()`，空体会进入 `invalid_response`，后端已删除成功时前端仍会提示失败。实施时在解析 JSON 之前判断 `response.status === 204`，直接返回 `undefined`。`deleteDataSource()` 的返回类型是 `Promise<void>`。不引入前端测试框架。Python 测试只验证后端返回 `204` 且响应体为空，不能证明前端不会进入 `invalid_response`。`npm run typecheck` 验证前端类型。构建按 doc 5，在 `frontend/` 执行 `VITE_API_BASE_URL=http://127.0.0.1:8001 npm run build`；该地址只用于本机验证。当前只有 `.env.development.local`，生产构建不会读取它，裸执行 `npm run build` 会因缺少 `VITE_API_BASE_URL` 失败。也可以把同一键写进被 Git 忽略的 `frontend/.env.production.local` 后再执行 `npm run build`。页面手测验证删除成功后不显示“平台服务返回了无法识别的响应。”

`delete_output` 为 `false` 时不碰 `output/`。该目录若已存在，会留下一个没有登记记录对应的目录。`delete_output` 为 `true` 时，只调用 `resolve_source_workspace_dir(source_id)` 得到 `output/<uuid>/`。不复用 `resolve_db_output_dir()` 的返回值，那个函数多一层 `db`，返回的是 `output/<uuid>/db`。该函数除了 `resolve_project_path()` 和 `ensure_path_in_project_root()` 之外，还要满足整目录删除的约束：结果必须严格对应规范化后的 `output/<uuid>`；路径上任一已有组成部分是符号链接，或真实路径与该预期路径不一致时，拒绝删除。`ensure_path_in_project_root()` 只保证落在项目根内，并会 `Path.resolve()`；`output/<A>` 若是指向 `output/<B>` 的符号链接，解析后仍在项目根内，递归删除就会删掉 B。这与 doc 2 “仅校验在项目根目录内还不够”一致。不修改 `ensure_path_in_project_root()` 本身，以免改变 `--step db --clean` 的现有范围。顺序固定为四步，本阶段不为此加锁。本阶段不支持同一数据源的并发删除；下面“记录不存在则返回 `404` 且不碰目录”的保证，以删除请求串行执行为前提。先查询登记记录；不存在则立即返回 `404`，不碰 `output/`。存在且 `delete_output=true` 时，才删除工作区；目录不存在视为已经删完。最后删除登记行。解析被 `ensure_path_in_project_root()` 拒绝，或路径正确但删除失败（例如权限不足、文件被占用），都不删除登记行，返回 `500`，错误码 `output_delete_failed`，文案“该数据源的输出目录删除失败，登记记录仍保留”。登记服务捕获路径校验失败和文件删除异常后，抛出 `OutputDeleteFailedError`；`errors.py` 只映射这个异常类型，不在路由里直接拼响应。目录删除不是原子操作，失败时该目录可能只被删掉一部分。用户可再次勾选并重试；此时登记行仍在，目录若已不存在就视为删完，再删登记行。文件系统和平台库不在同一个事务里，不为此做两阶段删除。若工作区已经删除，随后平台库删除或提交失败，返回已有的 `503 platform_unavailable`。登记记录可能仍在，工作区已经没有。平台库恢复后，用户可再次执行删除；目录不存在仍视为已经删完，再删登记行。不接受调用者提交的路径。不删除其他数据源的目录，也不删除 `output/ddl` 这类尚未按数据源隔离的旧目录。

`DELETE /api/data-sources/{source_id}?delete_output=true` 是唯一会删除整个 `output/<source_id>/` 工作区的入口。`--step db --clean` 的范围不变，仍只清理该数据源 `db/` 目录的顶层文件。

删除不解密密码，不连接源库，不写日志中的密码或密文。重复删除同一编号得到 `404`，不把第二次当成成功，也不删除已经留下的 `output/<source_id>/`。两个请求若并发执行，可能都先查到记录仍在，其中一个删掉登记行后，另一个仍会删工作区再返回 `404`。该副作用不在本阶段用行锁消除。本阶段也不能检测独立 CLI 是否正在执行 `metaweave metadata --step db --source-id <UUID>`。管理员不得在同一 `source_id` 的 `--step db` 执行期间删除数据源；否则 CLI 可能在删除之后重新写出 `output/<source_id>/db/database.json`，留下新的孤立目录，或与递归删除互相干扰，产生不完整文件。不为此增加进程锁或作业检测。未来接入 Web 作业后，存在 `queued` 或 `running` 作业的数据源应拒绝删除。

卡片上删除成功后，从当前列表去掉该条。查看页上删除成功后回到数据源管理页。请求进行中禁用“确认删除”，同时禁用“取消”、遮罩关闭和 Escape 关闭，避免窗口先关掉而请求仍在进行。失败时确认窗保持打开并显示该错误码对应的文案，复选框保持失败前的状态，不从列表移除卡片，查看页也不离开。查看页删除得到 `404 not_found` 时，关闭确认窗，回到数据源管理页并显示“数据源不存在”。卡片上得到 `404` 时，关闭确认窗，提示“数据源不存在”并重新加载列表。

## 4. 接口与跨域

查询继续用现有 `GET /api/data-sources/{source_id}`，字段集合不变。

删除是本次唯一的新接口。实施时在 doc 2 §3.2 的接口清单补一行：`DELETE /api/data-sources/{source_id}` 删除该登记记录；`delete_output=true` 时同时删除 `output/<source_id>/` 及其全部内容。不返回密码或密文，不存在返回 `404 not_found`。

`backend/api/main.py` 的 CORS `allow_methods` 在现有 `GET`、`POST`、`PATCH` 上增加 `DELETE`。`allow_headers` 仍只有 `Content-Type`。doc 5 的允许方法同步列入 `DELETE`。

doc 6 里“查看”“删除”本阶段只占位的那句，实施时改为指向本文，不再写占位。

doc 4 也要同步两处：§2 目录注释的 `views/` 现为 Home、DataAssets、CreateDataSource，补上 DataSourceDetail；§6.3 前端文件表补上 `DataSourceDetailView.vue`，路由一行补上 `/data-sources/:sourceId`。

## 7. 验收

- 查看页使用 `GET` 已有字段。不显示密码。数据源名称下方显示 `source_id`。
- `not_found` 与 `invalid_request` 回到数据源管理页。其他加载失败留在查看页，显示错误、“重试”和“返回数据源管理”；成功前没有“删除”和“修改”。这条用页面手测，不引入前端测试框架。
- 查看页没有可编辑输入框，没有“测试连接”和“保存”。
- “修改”打开 `/data-sources/:sourceId/edit`。“采集”保持禁用。
- 删除默认只去掉平台库中的这一行。源库数据保持不动。未勾选时，已有的 `output/<source_id>/` 原样留下。
- 勾选后只删除该数据源自己的 `output/<source_id>/` 及其全部内容。整个 `output/`、其他数据源目录和源库数据都不动。`output/<A>` 指向 `output/<B>` 时，删除 A 返回 `500 output_delete_failed`，文案为“该数据源的输出目录删除失败，登记记录仍保留”，登记行保留，B 保持不变。递归删除抛出 `PermissionError` 时，响应码和文案相同，登记行保留。
- 删除不存在的编号返回 `404 not_found`，响应不含密码或密文。
- 删除成功的响应是 `204` 且响应体为空，由 Python 测试断言。页面手测确认不出现“平台服务返回了无法识别的响应。”前端类型由 `npm run typecheck` 确认。构建在 `frontend/` 执行 `VITE_API_BASE_URL=http://127.0.0.1:8001 npm run build`，或先把该键写入 `.env.production.local`。
- 替身在实际提交前抛出 `SQLAlchemyError` 时，断言登记行仍在、工作区已经删除、接口返回 `503 platform_unavailable`。正文里的“登记记录可能仍在”仍然保留：数据库已经提交但调用方没有收到结果时，这次响应确认不了最终状态。平台库恢复后可再次删除。
- 首次查询平台库抛出 `SQLAlchemyError` 时，接口返回 `503 platform_unavailable`。`output/<source_id>/` 保持完整，且不调用目录删除函数。这两条都是 API 测试，不是让服务层返回 HTTP 状态码。
- 删除请求进行中，“确认删除”、取消、遮罩和 Escape 都不能关闭窗口。每次重新打开都是不勾选且没有上一次的错误。失败时确认窗保持打开，复选框状态不变，卡片仍在列表中。查看页删除得到 `404` 时回到数据源管理页并显示“数据源不存在”。
- 打开 `/data-sources/not-a-uuid` 或对应的修改页时，回到数据源管理页并显示“数据源不存在”，不显示“请检查填写的信息。”

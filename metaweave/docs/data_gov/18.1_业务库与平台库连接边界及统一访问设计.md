# 18.1. 业务库与 MetaWeave 平台库连接边界及统一访问设计

状态：连接参数代码改造已完成（2026-10-02）；Web JSON 采集仍由 [doc 18](18_Web受管JSON画像采集设计.md) 实施。本文只定义数据库角色、连接参数和访问边界，不实现 JSON 画像入库。§2—§3 记录连接改造前的代码现状与缺口，§4—§5 保留设计及验收口径，其中 doc 18 的 JSON 采集仍属后续工作。

## 1. 数据库角色与不可混用的规则

| 角色 | 用途 | 连接信息来源 | 典型读写 |
| --- | --- | --- | --- |
| **业务库（源库）** | 被采集、分析的 PostgreSQL 数据库 | Web/受管作业以 `source_id` 查询平台库 `db_source_info`，取该记录的连接字段；`source_id` 本身只是标识符，不是连接串 | `db` 统计、`ddl` 结构提取、`json` COUNT/采样、`rel` 评分、SQL 校验等读操作 |
| **MetaWeave 平台库** | 保存数据源登记、作业状态、发布记录和已发布画像的 PostgreSQL 数据库 | 服务端进程环境或项目 `.env` 中独立的 `PLATFORM_DB_*` | 读写 `db_source_info`、`job_info`、`publish_info`、`db_profile`、`table_definition`；画像页面只读这里 |
| **RAG 目标库** | 供检索/图查询使用的 Milvus、Neo4j | `configs/metadata_config.yaml` 的相应配置及环境变量 | `rag_load` 的向量/图数据；不是本篇所称平台 PostgreSQL，也不是业务库 |

`source_id` 只用于查找**业务库**登记信息及校验作业归属。平台库连接始终由 `PLATFORM_DB_*` 指定；不能把业务库的密码拿来登录平台库，也不能在 `source_id` 不存在、解密失败或业务库连接失败时回退到 `DB_*` 或平台库。两个角色可以恰好部署在同一台 PostgreSQL 服务器，但仍须按不同连接身份处理。

Web 的正常数据流是：`PLATFORM_DB_*` 连接平台库 → 用 `source_id` 查询 `db_source_info` 并解密登记的业务库密码 → 连接该业务库采集 → 写受管工作区文件 → 发布时读取文件并通过 `PLATFORM_DB_*` 写平台画像表 → Web 画像页通过 `PLATFORM_DB_*` 查询平台画像。`SOURCE_CREDENTIAL_KEY` 只用于解密登记的业务库密码，不是任一数据库的登录密码。

**现有 CLI 的过渡事实须单独说明。** `.env.example` 同时列有旧的 `DB_*` 和平台库 `PLATFORM_DB_*`；`configs/metadata_config.yaml:database` 通过 `${DB_*}` 配置**旧的未受管 CLI 所访问的业务库**，不是 MetaWeave 平台库。当前 `metadata --step json` 不接受 `--source-id`，故它确实访问业务库，但连接参数目前来自主配置；这与 Web 受管采集将按 `source_id` 选业务库的目标不同。不能因为两者都访问业务库，就说当前 CLI 已从 `source_id` 取参数。`meta_load --type db` 则只读受管文件、用 `PLATFORM_DB_*` 写平台库，不再连接业务库。

## 3. 已确认的问题与影响

1. **未发现已改造的 `db` 把平台库当业务库、或把业务库当平台库的调用。** `run_db_step()` 在平台会话中只取登记/作业数据，退出会话后 `execute_db()` 用登记字段连接业务库；发布及 Web 展示再使用平台会话。验收仍应使用**不同地址和不同账号**的两套测试库，防止同机测试掩盖混用。
2. **【已修复（2026-10-02）】DDL 的 `sslmode` 透传缺口。**（实施后：受管 DDL 快照显式覆盖登记 `sslmode` 含 `None`，`DatabaseConnector` 经公共模块规范化使用，见 §5.2 与 `test_ddl_step_service.py`；以下为修复前记录。） `build_managed_ddl_config()` 没把登记行的 `sslmode` 放进快照；`DatabaseConnector.__init__()` 也只用基本字段构造 conninfo。`build_source_connect_kwargs()` 支持 SSL 模式，但目前供连接测试、`db` 采集和手工登记工具使用，不能视为 DDL/JSON 已支持。登记源即使配置 `require`、`verify-ca` 或 `verify-full`，受管 DDL 连接也不会显式执行该要求；若无其他 libpq 设置，通常按默认 `prefer` 先尝试 SSL、失败后可能回退到非 SSL，且不执行登记值要求的证书验证。这可能使采集连接失败，或在源库允许非 SSL 时以低于登记要求的安全级别建连；**服务器只允许 SSL 本身不意味着 `prefer` 必然失败**。实际行为还可能受运行环境中的 libpq 连接设置影响，不能把当前连接视为符合登记要求。即使将来连接器支持 `sslmode`，受管快照仍必须**显式用登记值覆盖（含 `None`）**，避免主配置遗留的 `database.sslmode` 被错误继承到另一业务库。
3. **【实施后更新（2026-10-02）】平台库的可选 SSL 模式已接通。**（实施后：`platform_session()` 建引擎前同样复用校验函数，直接构造的 `PlatformSettings` 也不例外；“`DB_SSLMODE` 不作用于旧 CLI”仍为当前行为。） `load_platform_settings_from_env()` 读取 `PLATFORM_DB_SSLMODE`，`platform_session()` 仅在有值时传给驱动；不应把它误认作业务库 `db_source_info.sslmode`，也不应再造一套平台库 SSL 规则。`.env` 中单写 `DB_SSLMODE` 目前不会自动作用于旧 CLI：主配置 `database` 尚无 `${DB_SSLMODE}` 映射，`DatabaseConnector` 也未读取该字段。
4. **旧的 PostgreSQL 连接入口分散。** `services/db/pg_connection.py:PGConnectionManager` 供维度值加载器读业务库，手工用字符串拼 host/user/password，既未按登记源取值，也未传 `sslmode`；密码含空白/特殊字符时可能被错误解析。它不是当前 Web `db/ddl` 链路，但后续改造维度值加载时必须处理。
5. **旧 CLI 与受管入口的业务库选择规则尚未统一。** `--step json/rel` 和 SQL 校验只读主配置；这在旧脚本模式下是可解释的现状，**不是访问平台库**，但若直接把它们接入 Web，不注入按 `source_id` 构造的快照，就会采到配置文件指定的另一业务库。这是 doc 18 和后续步骤需要阻止的实际风险。
6. **【已修复（2026-10-02）】`sslmode` 曾无统一的应用层值域校验。**（实施后：API 输入、公共连接参数入口与平台库设置复用同一校验函数，见 §4.1；以下为修复前记录。） Web 表单使用固定选项的下拉框，正常页面操作不会输入拼错的模式。`backend/api/schemas.py:ConnectionFields.sslmode` 仍是普通可选字符串；直接调用 API、手工登记工具或配置平台库环境变量时可能填错，当前报错也未必能明确指出 `sslmode`。在 API 输入和公共连接参数模块复用同一个简单校验函数即可，无需为此增加采集作业的前置校验或改变作业状态流程。
7. **平台库目前没有应用级语句超时。** `backend/persistence/platform_db.py:platform_session()` 只设置 `connect_timeout=10` 秒，没有设置 `statement_timeout`；DDL 发布会在平台库事务中整批替换 `table_definition`，资产页会读取画像行。这些操作的执行时间不受建连超时约束；若数据库服务端另设语句超时，仍可能由服务端生效，不能将其当成本应用的配置保证。

## 4. 统一连接与访问模块的设计

### 4.1 两种身份，统一参数规则

保留两类**显式区分**的连接来源：`PlatformSettings` 只从 `PLATFORM_DB_*` 读取平台库参数；受管业务库先按指定 `source_id` 读取 `DbSourceInfo`，在服务端解密密码，再将已解析的连接字段传给公共参数模块。本阶段**不新增 `SourceConnectionSettings` 类型**。现有 `DbExecutionRequest` 继续表示 `db` 步骤请求，保留 `source_id`、`job_id`、采集选项及连接字段；`execute_db()` 从中显式取出连接字段交给公共参数模块，不将整个步骤请求当作通用连接类型，也不另建一套平行字段对象。**当前现状**：未受管 CLI 从主配置 `database` 读取业务库字段，`DatabaseConnector` 自行构造 conninfo。**本轮改造后**：未受管 CLI 暂仍从主配置取字段，但 `DatabaseConnector` 改为将字段传给同一个公共参数函数；公共函数只接收连接字段，**不增加 `source="legacy_config"` 一类来源参数、日志标记或自动选择配置来源的分支**。后续将步骤受管化时，再改由 `source_id` 解析登记行；受管入口缺少或找不到 `source_id` 时直接报错，不回退到主配置。若后续多个步骤确需共享不可变的连接值对象，再让各步骤请求持有该对象，避免重复定义连接字段。

连接参数的**公共构造规则**放在 `metaweave` 包内的独立纯模块，计划新增 `metaweave/db/postgres_options.py`（及包初始化文件）。它接收 host、port、dbname、user、password 和可选的 `sslmode`、`connect_timeout_seconds`、`statement_timeout_ms`；两个超时参数为 `None` 时不向 libpq 添加对应选项，不设默认超时。`db` 采集和连接测试显式传入现有 10 秒/60 秒超时，`DatabaseConnector` 的 DDL/JSON/REL 等既有路径本次不传超时。公共模块不依赖 `backend`、元数据生成器或顶层旧 `services/db`。`backend → metaweave` 已是当前依赖方向；把通用设施放入顶层 `services/db` 会让新代码长期依赖其中的旧 `PGConnectionManager` 所在包，而把它塞进 `metaweave/core/metadata/connector.py` 又会使平台库访问依赖采集层，因此均不选用。

公共模块返回独立的连接参数字典；需要连接串的调用方使用 `psycopg.conninfo.make_conninfo(**kwargs)`，不手工拼接含密码的连接串。`sslmode` 只接受 PostgreSQL libpq 的六个模式：`disable`、`allow`、`prefer`、`require`、`verify-ca`、`verify-full`（[PostgreSQL 官方说明](https://www.postgresql.org/docs/current/libpq-connect.html)）。公共模块维护**唯一一份**模式集合与规范化/校验函数：`None`、空串和纯空白表示未配置，省略该连接参数且不设应用默认；非空输入去除首尾空白、统一为小写，再按值域校验，非法值在建连前报配置错误。通过校验的值作为**单独参数**传入，不允许它改变 host 等其他连接字段。值域有效只说明输入合法，不替代证书、权限及实际连接检查。**省略 `sslmode` 只表示应用不指定，并非强制使用 `prefer`**：libpq 仍可能读取 `PGSSLMODE` 或 `PGSERVICE` 指向的服务文件设置；受管链路若要求确定的 SSL 策略，须在数据源登记中显式填写 `sslmode`，不能把未配置当作安全默认值。

新建和修改数据源时，登记服务与手工登记工具均保存规范化后的 `sslmode`；连接测试和采集在构造连接参数时使用同一校验函数。本项目尚未上线，本篇不设计历史登记值的兼容、展示差异或数据清洗。

连接日志允许输出 host、port、database、user，包括现有连接池创建时的 `database@host:port`，以便定位实际连接目标；受管作业还可用已有 `source_id`、`job_id` 关联诊断。公共参数模块及调用方不得记录密码、密码密文、密钥、密码长度、完整连接参数字典或 conninfo；连接异常若可能带出这些内容，先脱敏再记录。这沿用 doc 3 的连接日志口径，不要求删除现有的非密码连接字段日志。

`backend/api/schemas.py` 的创建、修改和连接测试请求调用同一校验函数，使非法值在请求校验阶段明确返回 422 `invalid_request`，不尝试连接、不保存登记；登记服务及手工登记工具存规范化后的值。公共连接参数入口也必须再次校验，覆盖绕过 API 的 CLI 和直接调用。平台库 `load_platform_settings_from_env()` 和 `platform_session()` 同样使用该函数，保证 `PLATFORM_DB_SSLMODE` 有效才建连；未配置时不传。两层调用**复用同一函数和集合**，不能分别复制六个字符串。平台库继续使用 SQLAlchemy `URL.create()` 与 `platform_session()`，业务库继续使用 psycopg/连接池：**共享参数契约，不强迫两类访问共用同一个 Session 或连接池**。连接选项只决定连哪里及如何建连；平台 ORM/repository 只管平台表，业务库 connector 只管源库查询。

这项值域校验**修订**了 [doc 2](2_添加数据源与数据库概览发布模块设计.md) §3/§7 和 [doc 3](3_阶段一step%20db设计文档.md) 中“应用不设 `sslmode` 白名单、交给 libpq 在连接时拒绝”的旧决定；实施时须同步修订那两篇文档及相关验收。旧设计用非法值 `require host=other` 测“参数不能被拆成两个字段”的用例，也须改成断言值域校验在建连前拒绝；密码特殊字符与合法 `sslmode` 仍要保留独立参数、安全构造的测试。doc 3 §3 允许连接日志输出用户名、禁止密码等敏感值，§5.1 要求删去密码长度日志；这两项日志要求继续有效，本文不修订它们。

现有 `metaweave/core/metadata/connector.py:build_source_connect_kwargs()` 的生产调用方只有 `backend/data_sources/connection_check.py`、`metaweave/core/metadata/db_step.py`、`scripts/register_db_source.py`，`tests/unit/test_db_step.py` 也直接导入它。**同一次改造**将这三处生产调用及相关测试切到 `metaweave/db/postgres_options.py`，删除 `connector.py` 中的旧函数；同时修改 `DatabaseConnector.__init__()`，让它把配置中的连接字段交给公共模块构造参数，再用 `make_conninfo(**kwargs)` 创建连接池所需的连接串，不再自行维护另一套参数拼装。公共模块是**本轮已改造的源库连接路径**唯一的参数构造实现，也是业务库与平台库共用的 `sslmode` 校验实现；不保留旧函数的委托包装或复制实现。旧 `services/db/pg_connection.py:PGConnectionManager` 尚未纳入本轮，待维度值加载改造时再迁入；平台库 `platform_session()` 保留 SQLAlchemy `URL.create()`，只复用 `sslmode` 规范化/校验，不改用源库的 psycopg 参数构造函数。

维持当前已生效的超时口径：`db`/登记连接测试到源库时建连 10 秒、每条 SQL 60 秒；平台库建连 10 秒，**本阶段有意不为平台库设置应用级全局 `statement_timeout`**。公共参数模块可以表达可选的语句超时，但不替任何调用方设统一默认值；平台库的大批量发布和画像查询可能执行较久，后续根据实际数据规模、耗时和失败恢复要求，再分别决定写入与读取的超时策略。`statement_timeout` 即使将来启用，也约束单条 SQL，不等于整笔事务或 HTTP 请求的总时限。DDL/JSON/REL 的超时现状另行评估，不能借统一模块悄悄改变为相同默认值。当前登记 API 和表只显式保存 `sslmode`，不含证书文件等扩展字段；若部署必须提供 `sslrootcert`、客户端证书或其他 libpq 选项，应先设计登记字段及密钥/文件管理，再加入白名单式映射，不能把任意配置字典直接透传为连接参数。

### 4.2 访问边界和注入点

- `backend/persistence/platform_db.py` 继续负责平台库设置与 SQLAlchemy Session，所有平台画像加载、发布、状态和页面读取都经它访问。它不读取主配置 `database`，也不接受 `source_id` 作为平台连接参数。
- 业务库连接入口接收**已经解析好的**连接字段，由公共参数模块构造 psycopg kwargs；需要连接池的调用方再用 `make_conninfo(**kwargs)` 序列化，并管理连接或连接池的生命周期。它不自行查平台库、不自行读 `.env`。受管入口负责先以 `source_id` 查登记、解密，再把该步骤需要的连接字段或连接对象及同一作业的输出目录快照交给执行层。
- `MetadataGenerator`、`RelationshipDiscoveryPipeline`、SQL 校验和维度值读取保留业务查询接口；后续受管化时注入源库连接对象，不让核心算法临时决定从平台库或主配置找凭据。`md`、CQL 生成等文件步骤不创建 PostgreSQL 连接。
- 输出文件不因文件名或 `source_id` 就自动成为平台画像；发布/加载入口校验文件与作业归属后，才通过平台库事务写入画像表。Web 页面读取平台库的已发布当前态，不绕到源库实时取画像。

## 5. 建议实施顺序与验收

1. **先固化 `db` 的双库边界。** 在测试中给平台库与业务库设置不同地址、库名和账号；断言 `source_id` 查询/`job_info` 只走平台连接，源库统计只走登记字段。分别在两端配置和不配置 `sslmode`，确认有值传入、无值省略；`DB_*` 故意指向第三个库时，受管 `db` 仍不访问它。此项以回归为主，不要求重写已正确的业务流程。
2. **提取公共参数构造并修复受管 DDL。** 新增 `metaweave/db/postgres_options.py` 和单一 `sslmode` 校验函数；同次迁移连接测试、`db` 采集、手工登记工具与相关测试的旧函数导入，删除 `connector.py:build_source_connect_kwargs()`，并检查全仓不再引用旧路径；**`DatabaseConnector.__init__()` 也在本轮改为经公共模块构造参数**，连接池仍用 `make_conninfo(**kwargs)`。`DbExecutionRequest` 保持步骤请求类型，由 `execute_db()` 显式传入连接字段，本阶段不新增与它平行的连接类型。接入 API 输入、登记服务和平台库设置，使非法模式在连接前失败；新建或修改登记时保存规范化后的值。DDL 快照覆盖登记源全部连接身份字段及可选 `sslmode`，`DatabaseConnector` 使用规范化后的值，连接日志遵循 §4.1 的非密码字段可见口径。用连接器测试替身核对最终参数：登记源为 `sslmode=require` 且主配置为其他值时，受管 DDL 必须传 `require`；登记源为 `None` 而主配置有 `sslmode` 时，受管 DDL 必须省略该参数，不能继承主配置。**DDL 链本次只补 `sslmode`，不引入建连或语句超时默认值。** 回归独立 DDL、JSON、REL、SQL 校验对无 `sslmode` 配置的既有行为；平台库的 `PLATFORM_DB_SSLMODE` 在合法/未配置时保持原有连接效果，且本阶段不新增应用级平台库语句超时。
3. **然后实施 doc 18 的 Web JSON 采集。** `source_id` 指向业务库、`PLATFORM_DB_*` 指向平台库，结果只落同作业 JSON 文件和 `job_info`；故意把 `.env` 旧 `DB_*` 指到另一业务库，证明它不会污染 Web 受管连接。JSON 发布/平台画像表加载另文实施。
4. **其余模块按各自受管化阶段改造。** `rel`、SQL 校验、维度值加载等在接入 `source_id` 时切换业务库参数来源，并删除该步骤从主配置选源库的旧入口；`md`/CQL 等文件步骤只切工作区输入。RAG 目标库继续按 Milvus/Neo4j 独立配置；不要把它们迁到 `PLATFORM_DB_*`。本设计不为已改造步骤保留旧入口或双轨兼容。

验收还需覆盖：错误的 `source_id`、解密失败或源库连接失败绝不回退到其他库；六种合法 `sslmode` 均被接受，`None`/空白值在两类连接中均省略该参数，大小写规范化一致；新建/修改时将 `Require` 或 ` require ` 规范化为 `require` 后保存和连接；受管 DDL 用登记源 `require` 覆盖主配置的其他值，登记源为 `None` 时不继承主配置的值，均断言最终连接参数，且不传两个可选超时时连接参数中无对应选项；`db`/连接测试仍显式传入既有超时值；`reqiure`、`require host=other` 等非法值在 API、CLI/直接调用及平台库环境配置中均于建连前被拒，API 新建/修改不保存无效登记；全仓不再导入或定义旧的 `connector.py:build_source_connect_kwargs()`，`DatabaseConnector` 也不再自行拼装源库连接参数；连接器日志可输出 host、port、database、user 等非密码字段，但不得输出密码、密文、密钥、密码长度、完整连接参数字典或 conninfo，可能带出这些内容的异常须脱敏；用户名/密码含空格或特殊字符仍作为单个参数；源库采集仅生成文件，平台画像必须经明确发布动作才可被 Web 读取。

## 6. 后续范围与待讨论项

### 已定边界

1. **未改造步骤与旧 CLI。** `--step json/rel` 等目前没有 `--source-id`，继续从主配置连接业务库只是当前代码事实。各步骤受管化时可直接要求 `source_id`，改为从登记信息取得该业务库的 host、port、库名、用户、密码等连接身份；库名仍须传给连接器和需要标识数据库的产物生成逻辑。无需为旧调用方式增加兼容参数或双轨运行。本篇不提前改动尚未受管化的步骤。
2. **主配置 `database` 与旧 `DB_*` 的去向。** `.env.example` 当前列有 `DB_*`，供尚未改造的脚本展开主配置 `database`；它们不是平台库参数。`database.database` 既是当前脚本连接业务库所需的库名，也被 MD、关系产物等文件处理逻辑使用；不能因为受管采集改用 `source_id`，就直接删除这个字段或整个 `database` 段。受管作业使用登记源的库名填充执行快照；未改造步骤仍按现状读取主配置。本篇不安排删除 `database.database`、其他仍被使用的配置字段或对应环境变量。将来若要清理旧 `DB_*`，先逐项核对所有使用者，并为文件处理逻辑明确提供库名来源，再另行修改配置。
3. **本轮参数范围。** 按 §4.1 统一现有 host、port、dbname、user、password、`sslmode` 与可选超时参数。

### 待讨论的扩展

1. **证书等扩展参数。** `sslrootcert`、客户端证书、`application_name` 等在出现明确部署需求时，连同登记表、API 与密钥管理一起设计。
2. **RAG 加载是否纳入后续受管化。** `rag_load` 写 Milvus/Neo4j，维度值加载还读业务 PostgreSQL；建议把它们列入后续单独阶段，而不当作 MetaWeave 平台画像发布，避免把三类存储混成一条连接链。

### 2.2 明确不做

- **不保留 CLI 的 sql 加载入口**：`metaweave rag_load --type sql` 从 `RAG_LOAD_TYPES` 移除，帮助文本同步；不为"脚本继续可用"新增任何保证或测试（§9）。`table_schema`（调试）/ `cql` 类型不变；`metadata --generate-sql-rag` 生成 CLI 保留（25.1 状态行）。
- **不做旧集合自动迁移/自动 drop**：开发环境若存在旧结构集合（无 `source_id`/`publish_id`），发布在集合核验处失败并提示手动删除；首次发布自动按新 schema 创建（§4.3）。
- **不做 sql-rag 产物编辑 API 与编辑弹窗**：SQL 样例是采集步骤的机器产物，没有 dim_value 那种"人工指定 embedding_col"的编辑需求，不复制 22.2 的配置编辑链路。
- **不做发布前三态拦截与内容注入**：sql-rag 没有任何编辑 API，唯一受管写入方是采集步骤本身、必刷新步骤行 `updated_at`，run_marker 锁下复查必然捕获；这与 dim_value（PUT 改 yaml 不更新步骤行）和 rel（rel_config_api PUT 改 json）是结构性差异，理由详见 §6.1。
- **不做异步/进度推送**：发布同步执行（同 table_schema/dim_value 现状）。
- **不做检索侧适配**：集合仅新增字段、无改名删除，检索 `output_fields` 不受影响；`example_id` 前缀变化不影响按向量检索的用法。连带影响记入 [100 备忘录](100_备忘录.md)（§14）。
- **不改 sql 采集步骤**：产物生成链（25.1）不变。
- **不改日志配置**：`configs/logging.yaml` 已有 `metaweave.core.sql_rag.loader` 模块路由（`:208`），本篇零改动；不加 script 侧 sql 发布日志文件（CLI 入口移除后 script 场景只剩测试直调，22.2 修订 10 同款立场）。

## 3. 当前代码现状（设计依据）

- **SQLExampleLoader 现状**（`metaweave/core/sql_rag/loader.py`）：`input_file` 单文件输入（`loader_cli.py:156-172` 在配置留空时从 `database.database` + `sql_rag.generation.output_dir` 推断 `qs_<db_name>_pair.json`）；集合 schema 五字段（`:206-245`）——`example_id` VARCHAR(256) 显式主键 `f"{db_name}:{sha256(question+sql)[:8]}"`（`:292-295`）、`question_sql` VARCHAR(16384)、`embedding` FLOAT_VECTOR、`domain` VARCHAR(256)、`updated_at` INT64；写入已用 `upsert_batch`（`:310`）；`ensure_collection(clean=clean)` 未传 `validate_schema`（`:177-180`，缺省关闭）。

## 4. Milvus 集合 schema 变更（用户已拍板）

### 4.1 新字段结构（集合 `sql_example_embeddings`，`sql_loader.collection_name` 不变）

| 字段 | 类型 | 说明 |
|---|---|---|
| `example_id` | VARCHAR(256)，**主键**（显式，`auto_id=False`，现状不变） | 构成改为 `source_id + ":" + sha256(question + sql)[:8]`（**需求 5a**：前缀由 `database.database` 改为 `source_id`）；最坏 36+1+8=45 字节，256 上限沿用 |
| `source_id` | VARCHAR(36) | 新增；发布源 UUID（ASCII，36 字节） |
| `publish_id` | VARCHAR(36) | 新增；本次发布 UUID |
| `question_sql` | VARCHAR(16384) | 不变；`{"question": ..., "sql": ...}` JSON 串（不含 domain，现状口径）；超长跳过判定改 UTF-8 字节口径（§7.3） |
| `embedding` | FLOAT_VECTOR(dim) | 不变；仍只对 question 文本计算 |
| `domain` | VARCHAR(256) | 不变；来自样例 `domain` 字段 |
| `updated_at` | INT64 | 不变；unix 秒 |

- **向量字段名未改**（仍为 `embedding`）：`ensure_collection` 的 `index_field_name` 缺省值即 `"embedding"`，本篇不传新参数，table_schema/dim_value 现行为零改动（与 22.2 修订 1 的 dim_value 场景相反，那里向量字段改名才需要新参数）。
- 索引参数不变：HNSW / COSINE / M=16 / efConstruction=200，建在 `embedding` 上。
- 同源内 question+sql 完全相同的样例产生相同 `example_id`，upsert 天然合并（去重）；不同源的相同样例因 `source_id` 前缀隔离，互不覆盖。

### 4.2 写入与替换语义（对齐 table_schema / dim_value，用户拍板"按源整份替换"）

1. 写入沿用 **`upsert_batch`（显式主键整行 upsert）**——发布重试幂等，同 `example_id` 不产生重复记录。
2. **`replacement_started`**：初始 False；**首个 upsert 调用之前置 True**（22.2 修订 16 / table_schema 同款——调用报错不能假定服务端未写入）；`delete_by_expr` 前确保已 True。开始替换后失败：撤销该源 `sql` 旧 current 并记失败行；**Milvus 中已写入的数据不回滚、不删除**——集合可能同时含本次（部分）与上次的数据，下次重跑凭相同 `example_id` 再次 upsert 补齐，不产生重复主键。
3. **仅当全部应处理记录成功**（`records_failed == 0` 且 `records_unconfirmed == 0`，数据类跳过 `records_skipped` 不影响，§7.3）才按表达式删除旧记录：`source_id == "<本源>" and publish_id != "<本次>"`（`delete_by_expr`），即按源整份替换；**任一批次失败即不执行删除**，已 upsert 的记录保留。多源共用同一集合互不影响。
4. `ensure_collection(collection_name, schema, index_params, clean=False, validate_schema=True)`：`load()` 的 `clean` 参数移除——Web 恒按源替换，CLI 移除后无整集合清空的调用方。

### 4.3 旧结构集合处理

- `validate_schema=True` 严格核验（doc 20.1 能力）：已有集合字段名/类型/主键不符 → 在 Embedding、写入**之前**失败，归类 `error_kind="schema_mismatch"`（§7.3）。
- 失败文案提示：`sql_example_embeddings 集合结构为旧版本，请手动删除该集合后重新发布`。**不自动 drop**（开发阶段旧集合仅存在于跑过 CLI 的环境，手动删一次即可；备忘录登记，§14）。
- 集合不存在时按新 schema 自动创建（`ensure_collection` 现有能力）。
- **手工删除与重建的操作口径（审核修订 26）**：实施落地后、首次 sql 发布前，若环境中存在旧结构集合，手动删除一次——方式二选一：Attu/控制台删除集合 `sql_example_embeddings`，或用 pymilvus 删除（与本项目 `milvus_client.ensure_collection` 的 clean 路径同惯用语：`Collection("sql_example_embeddings", using=<连接别名>).drop()`；开发环境随手执行即可，旧数据为历史 CLI 加载产物，删除即弃）。**重建无须也无手写建表语句**：删除后的下一次 sql 发布由 `ensure_collection` 按 §4.1 schema 自动建集合并建索引，schema 唯一权威在 loader 代码——不提供独立建表脚本，避免与代码漂移。

## 5. 发布预检与解冻

`publish_service.py` 新增常量 `SQL_STEP = "sql"`（与 25.1 的 `SQL_STEP_NAME` 同名同值，发布侧自有常量）。

- **`check_publication` 循环元组加入 `SQL_STEP`**（置于 `DIM_VALUE_STEP` 之后），并加**显式 elif 分支**（审核先例 22.2 修订 34：现有 if/elif 链末尾 else 兜底是 json 检查 `:328-330`，不加显式分支会把 sql 按 json 产物误判）。
- **inspector**：新增 `inspect_sql_context(session, source_id, job_id)`（范本 `inspect_rel_context`，`rel_loader.py:89`）——核对数据源存在、启用、工作区归属后，读 `job_info` 的 `sql` 步骤行，返回 `(last_status, updated_at)`；行缺失返回 `(None, None)`。**必须同步注册进 `_INSPECTORS`**（`publish_service.py:1413-1421` 加 `SQL_STEP: inspect_sql_context`）：该字典被两处 `_INSPECTORS[step_name]` 消费——`check_publication` 的取值在 try 块**外**（`:270`，先于 `:271` 的 try），缺注册即 KeyError 逃逸、**所有数据源**的发布预检 500（预检每次返回全部步骤，波及全量而非仅勾选 sql 的源）；`publish_steps` 的 run_markers 循环取值在 try 内（`:1443`），KeyError 被宽 `except Exception`（`:1460`）吞成 `PlatformUnavailableError` → 误报 503 `platform_unavailable`。与显式 elif（22.2 修订 34）同属「隐性登记点」陷阱，同规格对待：**循环元组、elif 分支、`_INSPECTORS` 注册三者必须同批落地**，缺一即全页故障。

## 6. 发布执行

### 6.1 控制流位置（为什么没有三态拦截与内容注入）

`publish_steps` 完整顺序不变：run_markers 循环（`inspect_sql_context` 读 sql 行 `updated_at`）→ 作业级准入 `_assert_job_admission`（409 `job_not_publishable`）→ 步骤状态检查（400 `step_not_ready`，sql 行须 success）→ **无 sql 拦截分支** → 生成 `publish_id` → 逐步骤执行。

不设 dim_value 式三态拦截、不设 rel 式指纹捕获与内容注入，理由（结构性差异，非省略）：

- dim_value 拦截 + 注入同一份内容，是因为 PUT 编辑保存改写 `dim_tables.yaml` 但**不更新步骤行**（22.2 修订 19），run_marker 对其免疫；rel 捕获产物指纹，是因为 `rel_config_api` PUT 可改写 rel json 同样不更新步骤行（23.2）。
- **sql-rag 没有任何编辑 API**：唯一受管写入方是 sql 采集步骤，而采集必经 `start_step`/`finish_step` 刷新步骤行 `updated_at`——重跑必被 §6.3 的 run_marker 锁下复查拒绝（t1≠t2）。预检与发布两请求之间的文件级 TOCTOU（产物被删/目录清空）由 loader `validate()` 的输入就绪检查兜底为步骤失败行。绕过接口直接改写工作区文件不遵守数据库锁，属既有接受边界（25.1 §4 同款声明：只能由复查捕获、不保证捕获复查后的外部写入）。
- 分发方式：`_PUBLISHERS[SQL_STEP] = _publish_sql`——**5 参通用分支**（table_schema 同款）。sql 不连源库、不依赖登记 `db_name`（输入按 `*.json` 通配而非 `qs_<db>_pair.json` 固定名定位），无需登记快照与注入配置；`publish_steps` 中 `registrations` 的 `(json, domain, dim_value)` 获取元组不加 sql（22.2 修订 47 反面论证了何时必须离开通用分支——sql 不属那种情形）。

### 6.2 受管 loader 构造：`build_sql_example_loader(source_id, job_id, publish_id)`

### 7.2 `validate()`

按序校验，任一失败返回 False（步骤失败行，§6.3 步骤 3）：

1. `source_id`/`publish_id` 已注入，且为 **`UUID` 对象或合法 UUID 字符串（36 位）之一**（发布链 5 参分发传入的是 `UUID` 对象，`publish_service.py:1573`；测试与直调常用字符串）——**loader 构造时统一规范化为字符串**（`str(...)`），`example_id` 前缀、`source_id`/`publish_id` 记录字段与删除表达式均使用规范化后的字符串，两种入参形态行为一致（审核修订 25）。
2. `input_dir` 已配置且目录存在、顶层至少一个非忽略 `*.json` 普通文件——目录枚举遇 `OSError` 时包为返回 False（不抛出，`loader.py` validate 侧同款，审核修订 28 回写）——与 `check_sql_output_ready` 同口径同忽略规则，**共用同一个枚举 helper，落点在 metaweave 侧**：`metaweave/core/sql_rag/loader.py` 模块级函数（如 `collect_sql_example_input_files(input_dir) -> list[Path]`——按文件名排序、忽略 `.tmp*` 前缀、仅取 `*.json` 普通文件、symlink/子目录不取），loader 的 `validate()`（存在性）与 `load()`（§7.3 第 1 条输入枚举）、backend 的 `check_sql_output_ready`（§5，导入调用）三方共用。**不得放 backend**：backend → metaweave 是单向依赖，放 backend 会让核心 loader 反向导入；放 loader 模块级即可，无须独立小模块（审核修订 13）。
3. `collection_name` 非空。
4. `options.batch_size` 为**正整数**——拒绝 bool（`isinstance(True, int)` 为真，须显式排除）、`0`、负数与非整数类型：负数使 `range(0, total, batch_size)` 空转，零批次下 `records_failed`/`records_unconfirmed` 均为 0，按 §7.3 第 6 条成功判据会**不写任何新样例却删光本源旧记录并标成功**（互斥等式也被无声破坏）；`0`/`False` 则触发 `range` ValueError 落入 catch-all 噪声失败。校验失败返回 False，不进入加载与删除（审核修订 15）。
5. EmbeddingService 初始化（`embedding` 配置）。
6. MilvusClient 初始化（`vector_database.active == "milvus"`、`providers.milvus` 非空等现有校验保留）。

### 7.3 `load()` 结果规则（重定义"成功"，修 §3"跳批仍成功"缺陷）

1. **输入读取**：入口先做 §7.2 第 4 条的 `batch_size` 防御性复查与**空 `input_dir` 受控失败**（直调 `load()` 时空串会被 `Path("")` 解析为项目根、枚举环境漂移——`error_summary` 写明未配置即返回，审核修订 28 回写；防不经 `validate()` 直调 `load()` 的路径——dim_value A15 防御性双保险同款），不合规则返回 `success=False`、**`error_kind=None`（不归 input：配置错误无产物文件、重跑采集不能解决，落入表②会误导，审核修订 23）**、`error_summary` 写明 `options.batch_size 必须为正整数`，零写入；**该分支 `error_file` 置 None**（返回结构中的 `<error_file>` 仅文件类 input 失败填值，审核修订 24）；正常 Web 路径已由 `validate()` 先拦（§6.3 步骤 3 通用文案），此分支仅约束直调返回契约。随后枚举 `input_dir` 顶层全部 `*.json` 普通文件（经 §7.2 第 2 条的共享枚举 helper——`.tmp*` 前缀忽略、symlink/子目录/其他后缀不消费，与 §5 解冻条件同口径），逐份 UTF-8 读取、解析为 JSON 数组并合并（单份空数组文件不单独报错，以合并总数判定）；每项 `question`、`sql` 必须为非空字符串，`domain` 缺省 `""`（非字符串值按 `""`）。任一文件无法读取/解析、非数组、存在非法项，或合并后总条数为 0 → 返回 `success=False`、`error_kind="input"`、`error_file`/`error_summary` 填首个问题文件与原因摘要——零写入（`replacement_started=False`）。**目录即输入**：受管链路下即主文件 `qs_<db>_pair.json`；手工放入的额外 `.json` 一并加载（§11 已知边界）。
2. **长度预检与数据类跳过（先于向量化，不影响 success）**：对合并后的每条样例先序列化 `question_sql`，超过 **16384 UTF-8 字节**（字节口径，修 §3 字符口径隐患）→ 计入 `records_skipped` + warning（含字节数）后剔除；`domain` 超过 256 字节同样处理（防字段超限把整批写入打成 unconfirmed）。不做截断——SQL 与问题文本语义上不可截。**预检必须置于向量化之前**（审核修订 16）：① 分类确定性——超长样例无论 Embedding 服务健康与否恒计 `records_skipped`，不因所在批次向量化失败被误计 `records_failed`；② 隔离性——超长 question 恰是最可能令 Embedding 调用整体失败（token 上限）的输入，先剔除避免连带同批正常样例计 failed；③ 跳过项不支付向量化成本。
3. **分批向量化（仅对未跳过样例，`batch_size`）**：批次 Embedding 重试 3 次耗尽 → 该批全部计入 `records_failed`，跳批继续（成功批照常 upsert，不回滚已写入）；单条 question 缺向量 → 计入 `records_failed`。此处的"重试 3 次"指加载器对 `get_embeddings()` 的**外层**调用尝试（现状 `loader.py:253` 的 `range(3)`）；`EmbeddingService` 内部另有 `max_retries` 重试（现配置 3，`embedding_service.py:91`）并按内部 `batch_size` 分子批——两层相乘最坏 **9 次实际请求/子批**。本篇不改公共 EmbeddingService、不调整任一层重试数，仅注明层级归属（审核修订 18）。
4. **记录构造**：`example_id = compute_example_id(source_id, question, sql)`（即 `f"{source_id}:{sha256(question + sql)[:8]}"`，哈希口径不变、仅前缀换 source_id；经 §7.1 静态方法构造，消除原 `_process_batch` 内联拼接的双路径）；`question_sql` JSON 串 `ensure_ascii=False`、不含 domain（现状口径）；`updated_at = int(time.time())`。
5. **写入**：`upsert_batch` 每次调用前置 `replacement_started = True`；返回确认数 < 该批记录数 → 差额计 `records_unconfirmed`（该批不重试、继续其余批）；调用抛错 → 该批**整批**计 `records_unconfirmed`、不重试、跳过继续（服务端可能已部分写入，保守整批计未确认——22.2 修订 24 同款）。`records_loaded` = 服务端确认写入数（`mr.primary_keys` 口径）。
6. **成功判定与删旧**：`records_failed == 0` 且 `records_unconfirmed == 0` → `success=True` → `delete_by_expr('source_id == "{source_id}" and publish_id != "{publish_id}"')`（删除请求成功即完成，不 flush、不轮询可见性，doc 20.1 同口径）；否则 `success=False` 不删旧，已 upsert 保留，下次重跑凭相同 `example_id` 幂等补齐。`ensure_collection(..., clean=False, validate_schema=True)` 在读取输入后、首批向量化前调用；其异常中**仅结构校验 `ValueError` 归类 `error_kind="schema_mismatch"`**（发生在任何 upsert 之前，`replacement_started=False`）；连接/建库/索引/加载等普通故障（如集合加载超时）冒至第 9 条 catch-all——`error_kind=None` 带 `error_summary`，**不得**把临时服务故障误报为"请手动删除集合"（审核修订 29）。**`delete_by_expr` 调用前置 `replacement_started=True`**（22.2 修订 16 同款——全跳过零 upsert 场景下删旧超时也不得误报未开始替换、错误保留旧 current，审核修订 29）；**自身抛错在删旧点单独捕获**，归类 `error_kind="cleanup"`、`error_summary` 填异常摘要——此时写入侧全部成功（`records_failed == 0` 且 `records_unconfirmed == 0`）、`replacement_started=True`，失败行文案走 §6.3 表⑤；不得落入 catch-all 兜底归类。
7. **状态后果**：部分 upsert 后失败 → Milvus 同时存在本次（部分）与上次数据、旧 current 已撤销、平台库无 current 指向、数据不回滚——以最后一次全量成功的发布为准恢复一致（dim_value §4.2 同款）。
8. **返回结构**：`{success, replacement_started, error_kind, error_file, error_summary, total, records_loaded, records_failed, records_unconfirmed, records_skipped, execution_time}`。`error_kind` 值域：`"input"`（§7.3 第 1 条）、`"schema_mismatch"`（§4.3）、`"cleanup"`（§7.3 第 6 条删旧失败）、`None`（未分类异常，§6.3 表⑥ 兜底）——**无 `"embedding"`/`"write"`**：向量化失败按 `records_failed > 0` 判定（表④）、写入未确认按 `records_unconfirmed > 0` 判定（表③），连接类失败走 `validate()` false（§6.3 步骤 3），均不进 error_kind。**四计数互斥**：`loaded + failed + unconfirmed + skipped = total`（total = 合并后进入处理的样例总数）——该等式**仅对全部样例已完成分类的路径成立**（正常完成与 `cleanup` 删旧失败）；**提前失败路径允许计数之和 < total**：`input`（枚举/合并未完成，total 为 0 或部分值）、`schema_mismatch`（total=N、loaded/failed/unconfirmed 恒 0；**skipped 可非 0**——长度预检先于集合核验，超长样例已计入跳过，审核修订 27）、未分类异常（中途终止，剩余样例未获分类）。**不得把未处理样例虚报为 `records_failed`，也不为此新增计数字段**（未处理量 = total − 四计数之和，仅在日志与 `error_summary` 中呈现，审核修订 17）。
9. `load()` 内部全捕获、从不抛出（dim_value 修订 11 同款）；旧返回字段 `loaded`/`skipped`/`message` 废弃（CLI 移除后无消费方，发布侧只读 §7.3 第 8 条的返回结构）。**catch-all 只填 `error_summary`（异常摘要）与 `replacement_started`（当时实际值），不改写 `error_kind`**（保持 None，由 §6.3 表⑥ 兜底）——与 dim_value 的 None→`"input"` 兜底（`metaweave/core/loaders/dim_value_loader.py:466-470`）**有意不同**：sql 的删旧/未分类失败若被归入 input，会误指"重跑 sql 采集步骤"而产物完好（审核修订 11）。

### 7.4 `close()`（新增）

## 11. 错误处理与边界

| 场景 | 行为 |
|---|---|
| 预检通过后、发布前产物被删或目录被清空 | `validate()` 输入就绪失败 → 步骤失败行（§6.3 步骤 3 文案）；sql 行 marker 未变不触发重跑路径，不误报 step_not_ready |
| 预检读取 marker 后、发布取得源行锁前，sql 采集被重跑（步骤状态或 marker 已变） | `_verify_step_current_under_lock` 拒绝 → 非 current 失败行（doc 16 §1 幽灵 ID 机制）；发布先取得锁时，重跑等待锁释放，本次发布继续（A10 两种时序，审核修订 25） |
| 发布期间同作业其他步骤变 failed/running | 锁下整作业复查（`assert_job_publishable`）→ `JobNotPublishableError` → 失败行，已完成步骤不回滚 |
| Milvus 存在旧结构集合 | `validate_schema` 核验失败 → `error_kind="schema_mismatch"`，失败行用 §4.3 原文；零 upsert、`replacement_started=False`、旧 current 保留 |
| 产物坏 JSON / 非数组 / 项缺 question 或 sql / 合并零条 | `error_kind="input"` + 文件名 → 失败行表②文案（指引重跑采集）；零写入。受管链路产不出此形态（25.1 成功核验），仅手工破坏或绕过接口可达 |
| Embedding 部分失败（批次重试耗尽/单条缺向量） | 跳批/跳条继续，`success=False` 不删旧；已 upsert 保留；中间态：新旧混合、旧 current 撤销、重跑幂等补齐（§4.2 第 2 条） |
| upsert 部分确认/抛错 | 差额或整批计 `records_unconfirmed`；文案表③（"另有 X 条写入结果未确认"）；不删旧 |
| 写入全部成功但 `delete_by_expr` 删旧失败 | `error_kind="cleanup"`、失败行表⑤文案（含已写入 M 条计数）；`replacement_started=True` 撤销旧 current；Milvus 新旧混合、数据不回滚，重跑凭相同 `example_id` 幂等补齐后再次删旧（§7.3 第 6 条、审核修订 11） |
| 同源两作业先后发布（新 job 的 sql 产物） | 按源替换语义：新发布删旧 `publish_id` 记录，集合只剩新作业样例 |
| 多源并发发布 | 源行锁按源互斥（现状机制）；跨源并发写同一集合接受（table_schema/dim_value 同口径） |
| question+sql 完全相同的样例（同源内重复） | 同 `example_id`，upsert 合并为一条（天然去重） |
| 不同源产生相同 question+sql | `source_id` 前缀隔离，互不覆盖 |

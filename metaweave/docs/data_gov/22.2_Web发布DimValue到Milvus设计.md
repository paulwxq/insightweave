# 22.2 Web 发布 DimValue 到 Milvus 设计

本篇在 Web「数据画像发布」中激活 `dim_value` 步骤：发布页 d 组卡片解冻 `dim_value` 勾选（解冻条件：受管 dim_config 产物 `output/<source_id>/<job_id>/dim_config/dim_tables.yaml` 存在），行内新增"编辑"按钮弹出配置编辑窗口（人工为每张维表指定唯一的"值向量化字段"），保存写回 `dim_tables.yaml`；发布执行等价于 Web 化的 `rag_load --type dim_value`：按 yaml 配置连**源库**读取每张维表指定列的全部 DISTINCT 值，逐值向量化后写入 Milvus `dim_value_embeddings` 集合，并按 `source_id` 整份替换旧记录。

### 2.2 明确不做

- **不保留 CLI 的 dim_value 入口**：`metaweave rag_load --type dim_value` 从 `RAG_LOAD_TYPES` 移除，帮助文本同步；不为"脚本继续可用"新增任何保证或测试（§13.2）。`sql` / `table_schema`（调试）/ `cql` 类型不变。
- **不做旧集合自动迁移/自动 drop**：开发环境若存在旧结构集合（`id` auto_id、无 `source_id`），发布在集合核验处失败并提示手动删除；首次发布自动按新 schema 创建（§4.3）。
- **不做多列 embedding_col 的编辑支持**：编辑窗口一表一字段（单选）；产物中手工写入的多列值在读取时视为"未指定"，保存后收敛为单列字符串（§5.2、§13.4）。
- **不做 PUT 的列存在性校验**：保存只校验 embedding_col 非空，不对照 json 产物列清单；源库实际缺列由发布执行的 SQL 失败兜底（§9）。
- **不做异步/进度推送**：发布同步执行（同 table_schema 现状），大维表耗时由请求超时配置兜底。
- **不做检索侧（NL2SQL 查询）适配**：集合字段改名（`embedding`→`col_value_embedding` 等）后，检索代码若引用旧字段名另行处理；本篇只保证写入侧（记入 [100 备忘录](100_备忘录.md)）。
- **不改 dim_config 采集步骤**：产物生成链（doc 22.1）不变；作业重跑会重写 `dim_tables.yaml`（embedding_col 回 null），编辑窗口的版本复查负责让用户感知（§5.2、§9）。
- **不加 script 侧 dim_value 日志文件（审核修订 10）**：doc 21.1 为 domain 加过 `domain_file`（`configs/logging.yaml:98`），本篇不效仿——CLI 入口已移除，script profile 的 step=dim_value 场景只剩测试直调，未命中步骤过滤的记录不进专属文件属预期；api 侧由 `x_modules` 的 `metaweave.dim_value.loader`（`:198`）覆盖，`configs/logging.yaml` 零改动。

## 4. Milvus 集合 schema 变更（用户已拍板）

### 4.1 新字段结构（集合 `dim_value_embeddings`，`dim_loader.collection_name` 不变）

| 字段 | 类型 | 说明 |
|---|---|---|
| `col_id` | VARCHAR(2048)，**主键**（显式，关闭 auto_id） | 构成：`source_id + ":" + table_name + ":" + col_name + ":" + col_value`（四段拼接，用户拍板"拼上 col_value"，§13.1） |
| `source_id` | VARCHAR(36) | 新增；发布源 UUID（ASCII，36 字节） |
| `publish_id` | VARCHAR(36) | 新增；本次发布 UUID（用户原文 `pulish_id` 按 publish_id 笔误处理，§13.1） |
| `table_name` | VARCHAR(**256**) | 由旧 schema 的 128 **上调**（审核修订 17）：三段式 `库名.schema.表名`，PG 单标识符上限 63 字节，最坏 63×3+2=**191 字节**，128 装不下；256 留余量 |
| `col_name` | VARCHAR(128) | 不变；PG 单标识符最坏 63 字节，128 覆盖 |
| `col_value` | VARCHAR(1024) | 不变；单条 DISTINCT 值文本，**按 UTF-8 字节截断至 1024 字节**（审核修订 17，截断不撕裂多字节字符） |
| `col_value_embedding` | FLOAT_VECTOR(1024) | 原 `embedding` 改名；仍只对 `col_value` 文本计算 |
| `updated_at` | INT64 | 原 `update_ts` 改名；unix 秒不变 |

- **Milvus `VARCHAR max_length` 计 UTF-8 字节数而非字符数**（[官方说明](https://milvus.io/docs/string.md)，审核修订 17）——现实现的 `len(text)`/字符切片（`dim_value_loader.py:396-397`）按字符计，1024 个汉字达 3072 字节会插入失败，改造必须换用字节口径。
- `col_id` 最坏长度按字节重算：36+1+191+1+63+1+1024 = **1317 字节**，VARCHAR(2048) 覆盖（Milvus VARCHAR 上限 65535）。
- 索引参数不变：HNSW / COSINE / M=16 / efConstruction=200，建在 `col_value_embedding` 字段上（**审核修订 1**）：`ensure_collection` 增加 `index_field_name: str = "embedding"` 参数，缺省值保持 table_schema / sql 现行为零改动；dim_value 调用传 `index_field_name="col_value_embedding"`。
- 同一 `(source_id, table_name, col_name)` 的 N 个 DISTINCT 值产生 N 条记录，`col_id` 尾段拼 `col_value` 保证唯一；值级去重沿用 loader 现有 `seen_values`。

### 4.2 写入与替换语义（对齐 table_schema，doc 20.1 §10.3 模式）

1. 写入从 `insert_batch` 改为 **`upsert_batch`（显式主键整行 upsert）**——发布重试幂等，同 `col_id` 不产生重复。
2. **仅当全部应处理批次成功**，才按表达式删除旧记录：`source_id == "<本源>" and publish_id != "<本次>"`（`delete_by_expr`），即按源整份替换；**任一批次失败即不执行删除**，已 upsert 的记录保留（§7.3 结果规则，审核修订 15）。
3. `replacement_started` 语义：初始 False；**首个 upsert 调用之前置 True**（审核修订 16，table_schema `:518` 同款——调用报错不能假定服务端未写入），`delete_by_expr` 前确保已 True。开始替换后失败：撤销该源 `dim_value` 旧 current 并记失败行（同 table_schema，§7.2）；**Milvus 中已写入的数据不回滚、不删除**——集合可能同时含本次（部分）与上次的数据，下次重跑凭相同 `col_id` 再次 upsert 补齐，不产生重复主键。

### 4.3 旧结构集合处理

- `ensure_collection` 传 `validate_schema=True`（table_schema 同款严格核验）：已有集合字段名/类型/主键不符 → 在 Embedding、索引、加载、写入**之前**失败。
- 失败文案提示：`dim_value_embeddings 集合结构为旧版本，请手动删除该集合后重新发布`。**不自动 drop**（开发阶段旧集合仅存在于跑过 CLI 的环境，手动删一次即可）。
- 集合不存在时按新 schema 自动创建（`ensure_collection` 现有能力）。

## 5. dim_value 配置编辑 API

路由挂在 publishing router（`backend/api/routers/publishing.py`，前缀 `/api/data-sources`），实现集中在新增 `backend/profile_loading/dim_value_config_api.py`。

### 5.1 端点

| 方法与路径 | 用途 |
|---|---|
| `GET /{source_id}/collection-jobs/{job_id}/dim-config` | 读当前 `dim_tables.yaml`：`{tables: [{schema_name, object_name, embedding_col}], version}`。`version` = dim_config 步骤行 `updated_at`（ISO，保存时复查用）。产物不存在 → 404 `dim_config_output_missing`；**dim_config 步骤行缺失但文件存在（手工放置等非受管情形）→ 同样 404**（审核修订 7：解冻条件本就要求步骤行 success，无行即非受管状态，PUT 的 version 复查亦无行可比）。**空产物统一返回 `tables: []`**（含采集原生 `databases: {}` 无本库键与编辑保存的空清单两种，审核修订 3，§3 末条）。**文件空白/无法解析 → 400 `dim_value_config_invalid` + 原因摘要**（该态编辑弹窗为错误态、无修复路径，发布拦截弹窗按 §8.2 给"重新采集"指引，审核修订 14、21） |
| `GET /{source_id}/collection-jobs/{job_id}/dim-config/objects` | 扫受管 json 目录（排除 `manifest.json`，仅普通文件），**直读各产物 `object_info`**（不经文件名解析，引用标识符无损），返回对象清单 `{objects: [{schema_name, object_name, object_type}]}`（table/view/materialized_view）。**排除 schema_name 含点的对象**（审核修订 18：yaml 键 `schema.object` 经 `from_yaml` 的 `split(".", 1)` 读回时 schema 段含点无法表达，属键格式固有限制，全链不支持，非 PUT 一处）。供"新增表"弹窗候选；前端本地搜索过滤；object_name 含点/空白**不排除**（链路天然支持，见 §5.2） |
| `GET /{source_id}/collection-jobs/{job_id}/dim-config/object-columns?schema_name=&object_name=` | 返回单表列结构 `{columns: [{name, data_type, comment}]}`（来自产物 `column_profiles`，按 `ordinal_position` 排序）。产物缺失该对象 → 404 |
| `PUT /{source_id}/collection-jobs/{job_id}/dim-config` | 写回 yaml（§5.2）。请求体 `{tables: [{schema_name, object_name, embedding_col}], version}` |

**编辑 API 的错误出口（审核修订 49）**：编辑端点不走 `publish_steps` 的抛异常链，"抛异常给服务层统一处理"的模式不适用——四个错误码同样在 `backend/api/errors.py` 注册 handler（与 §6.2 发布拦截三态同款集中出口），未注册的自定义异常会让打开/保存弹窗变成 500：`dim_config_output_missing`（404，产物/步骤行缺失）、`dim_value_config_invalid`（400，GET 无效文件，与发布拦截同名同义，details.reason 对象）、`dim_value_column_missing`（400，PUT 空 embedding_col，details.tables 对象）、`dim_config_regenerated`（409，PUT 版本复查不匹配）。

### 5.2 PUT 校验与写回

按序执行，任一步失败即整次拒绝（不留部分写入）：

1. **结构校验**（审核修订 18）：`tables` 为列表；每项 `schema_name` 非空且**不含点**（键表达限制，同 GET objects 排除口径）；`object_name` 非空、**允许含点与空白**（引用标识符：`from_yaml` 的 `split(".", 1)` 使表名含点可无损读回，`_extract_table_identifiers` 直读 `object_info` 不经文件名，链路天然支持）；`schema_name + "." + object_name` 在清单内唯一。
2. **embedding_col 强校验**（需求 7 / 补充 3）：每项 `embedding_col` 必须是非空、去空白后非空的单列字符串；任一违规 → 400 `dim_value_column_missing`，`details.tables` 返回违规表名清单。**允许保存空清单**（0 张表可保存，编辑自由；但发布时将被 §6.2 拦截，提示添加表或取消勾选，修订 14）。
3. **版本复查**：请求 `version` ≠ 当前 dim_config 步骤行 `updated_at` → 409 `dim_config_regenerated`（期间作业重跑重写了产物，提示刷新后重做）。
4. **写回**：`db_name` 取登记快照；构造 config dict 后**用与 `config_generator._write_yaml` 相同的 `yaml.dump(allow_unicode=True, default_flow_style=False, sort_keys=False)` 渲染主体**（审核修订 45：**不手写"按需加引号"逻辑**——`yaml.dump` 自动处理 YAML 1.1 布尔/空值裸词（yes/null/true 等作键或列名时加引号保持字符串）与含点/空白的特殊键，含点/空白的对象名作为键正确落盘并在 `from_yaml` 无损读回，审核修订 18），表名按字典序传入（确定性输出）；**空清单也写完整结构 `databases.<db_name>.tables: {}`**，与采集原生 `databases: {}` 区分，审核修订 3；头部为固定注释模板，声明"Web 保存仅支持单列"；`mkstemp` 唯一临时文件写入、核验可解析后 `os.replace` 原子替换（`dim_config_step_service.py` 同款加固）；读取走 `O_NOFOLLOW`（`domain_loader.py` 同款）。
5. 成功返回 `{tables: [...]}`；写文件不改动 `job_info` 步骤行，`version` 不变，前端继续使用打开弹窗时取得的值。

### 5.3 读取口径（多列收敛与发布三态判定）

GET 时 `embedding_col` 为 null / 空串 / 列表 / 含逗号字符串（仅可能来自手工编辑产物）→ 一律返回 `embedding_col: null`，前端按"未指定"渲染并要求重新单选；保存后该表收敛为单列字符串（§13.4）。

发布拦截用的共享读取函数（§6.2）在上述口径上输出**三态**（审核修订 14）：

1. **无效**：文件空白、YAML 无法解析、顶层非 dict、`databases` 键缺失或非 dict，以及**文件不存在或不可读**（`FileNotFoundError` / `IsADirectoryError` / `PermissionError`、加固读取拒 symlink 的 `O_NOFOLLOW` 错误——预检与点发布是两个请求，中途被删或处于重跑清理窗口均可能，一律归入无效态，审核修订 27）—— 判"配置文件无效或不存在"（注意：`databases: {}` 与 `databases.<db>.tables` 缺失/为空属**合法结构**，不判无效）。
2. **零张表**：结构有效但表清单为空——含采集原生 `databases: {}`（无本库键，doc 22.1 零 dim 表产物）与 PUT 保存的 `databases.<db>.tables: {}` 两种形态（修订 3 的宽容口径在此适用）。
3. **有表**：返回表清单（`embedding_col` 按 §5.3 首段口径归一）。表名不含点的非法项与 `from_yaml` 一致忽略，不单独判无效。

### 6.2 发布拦截（补充需求 4 + 澄清，审核修订 14、19）

`publish_steps` 在 `normalize_publish_steps` 通过后、**生成 publish_id 与执行任何已选步骤之前**：若 `chosen` 含 `dim_value`，用共享读取函数（§5.3 三态）**读取并解析受管 yaml 一次**，按三态拦截——**任一命中即整个请求拒绝**：不生成 publish_id，同请求勾选的其他步骤也不执行。**完整顺序（审核修订 42，插在现有两道闸之后）**：run_markers 循环 → 作业准入 `_assert_job_admission`（409 `job_not_publishable`，`publish_service.py:982`）→ 步骤状态检查（400 `step_not_ready`，`:985-986`，dim_config 行须 success）→ **三态拦截读 yaml** → 生成 publish_id——作业本身不可发布（如 dim_config 行 failed 但旧产物 yaml 尚在）时必须先报 409/400 真实原因，配置态文案（零表/无效/未配置）不得挡在其前误导用户去编辑配置。**通过后这份已检查的解析结果（归一后的 `DimTablesConfig`，每表 `embedding_col` 非空单列字符串——单一解析路径，审核修订 38）随发布流程传递（`publish_steps` 的 `run_markers`/`registrations` 同款逐请求字典模式），作为本次加载的唯一输入（§7.1、§7.3，审核修订 19）——加载器不再按路径重读文件**：

| 三态 | 错误码 | message | details |
|---|---|---|---|
| 无效（空白/无法解析/结构非法/**文件不存在或不可读**，审核修订 27） | `dim_value_config_invalid` | `dim_tables.yaml 配置文件无效或不存在，请重新生成后再发布` | `{reason: <读取/解析错误摘要>}` |
| 零张表（含原生 `databases: {}` 与保存的空清单） | `dim_value_empty_tables` | `dim_value 未配置任何表：请为 dim_value 添加表并指定值向量化字段，或取消勾选 dim_value` | `{}` |
| 有表但存在 embedding_col null/空 | `dim_value_not_configured` | `dim_tables.yaml 中存在未指定 embedding_col 的表，请编辑配置或删除对应表` | `{tables: [...]}` |

三态按序判定（无效最先）。**库名与登记快照（审核修订 37）**：三态判定与注入内容**必须用登记 `db_name`**（`read_registration_snapshot`），不用主配置 `database.database`——受管 yaml 的键是源库名（生成器口径），用主配置库名键对不上；`publish_steps` 的登记快照获取从 `(json, domain)` 扩展到 dim_value（步骤成功时记录），快照含 `updated_at` 随请求传递，供 §7.2 锁下核对登记版本。

**异常与错误出口（审核修订 36）**：三态各定义异常类（`DimValueConfigInvalidError` / `DimValueEmptyTablesError` / `DimValueNotConfiguredError`，`ValueError` 子类），在 `backend/api/errors.py` `register_exception_handlers` **各注册一个 handler** → `_response(400, code, message, details=...)`（范本 `unsupported_publication_step`，`errors.py:113`）；`details` 为对象（`{reason}` / `{tables}`）。**未注册的异常会变成 500 `internal_error`**，§8.2 按 code 分流的弹窗不会出现——handler 注册是任务 3 的必要落点，不是可选项。**顺序规定（审核修订 26、42）**：拦截的 yaml 读取必须排在 **run_markers 循环（`inspect_dim_value_context` 读 dim_config 步骤行 `updated_at`）与作业准入/步骤状态两道闸之后**、publish_id 生成之前——标记锚定先于内容读取，"读取标记后发生的重跑"必被锁下复查（t1≠t2）拒绝；若顺序颠倒（先读文件后读标记），重跑后标记取到新值 t2、复查 t2==t2 全绿灯，会拿旧内容发布而 run_marker 机制失效。PUT 改写不受标记约束（**PUT 编辑保存不更新步骤行**），由注入同一份内容兜住（审核修订 19）——这正是拦截与加载必须共用同一份内容的原因。发布执行层不再有空清单路径。
- 前端按 code 弹拦截弹窗（§8.2，样式参考原型 5 错误变体）。

### 7.2 `_publish_dim_value`（`publish_steps` 循环内单独调用，审核修订 47）

结构复制 `_publish_table_schema`，但**调用方式与签名不同（审核修订 47）**：`_publish_dim_value(settings, source_id, job_id, publish_id, expected_run_marker, registration, dim_tables)` 七参——在 `publish_steps` 循环里与 json/domain 同款**单独调用**，不走 `_PUBLISHERS` 的 5 参通用分支（`publish_service.py:1015-1020` 只传 `run_markers[step]`，登记快照与拦截归一配置没有入口）；`registration` = 拦截时登记快照（§6.2，锁下版本核对用）、`dim_tables` = 拦截归一配置（§7.3 注入）。

1. 源行锁 → 源存在且启用 → 工作区归属 → **登记版本核对（审核修订 37）**：`source.updated_at != 拦截时快照的 updated_at` → `RegistrationChangedError` 按既有登记变更失败处理（`_publish_domain:835-836` 同款；**该异常原样上抛给 `publish_steps`——`_publish_domain:868-870` 同款 `except RegistrationChangedError: raise`，宽 `except Exception` 不得吞掉，否则误记为普通失败文案、A23 断言失效，审核修订 47**）——dim_value 锁下连源库做 SELECT DISTINCT，登记库名/连接在拦截后被改时，注入的旧库表清单会拿去查新库（同名表时加载错误库的数据）；table_schema 不做此查是因为 file-only 不连源库，dim_value 属 json/domain 一类 → `_verify_step_current_under_lock(session, job_id, "dim_config", expected_run_marker)`（防读取期间 dim_config 被重跑；若被重跑改写为空/无效产物，此处按步骤标识已变拒绝，§6.2 的三态拦截结果不再适用）。
2. `build_dim_value_loader(source, decrypt_password(source.password_ciphertext), job_id, publish_id, dim_tables)`（**锁内源行构造**，密码解密后传参、不落盘不进日志，审核修订 28）→ `loader.validate()`（Milvus / 源库 / Embedding 三连接，失败 → 步骤失败行，**文案用步骤 4 表①**（服务不可用句），`replacement_started=False` 保留旧 current——validate 只返回 bool，连接类失败不得套"请检查 dim_config 产物"，审核修订 50）。
3. `loader.load()`（§7.3）：load() 内部 `except Exception` 全捕获、以 `{success, replacement_started, ...}` 结果返回、**从不抛出**（`dim_value_loader.py:319-322`，审核修订 11）；`validate()` 同样只返回 bool。**success=False 时按 `result["replacement_started"]` 决定是否撤销旧 current**，不存在 table_schema 那种"load 抛异常需保守按已开始处理"的路径；外层 except 兜底仅覆盖构造 loader / prepare 阶段抛出，发生时必然未开始替换（`replacement_started=False`，不撤销）。
4. 成功（审核修订 13，明确顺序）：**先 `clear_current(session, source_id, "dim_value")` 再 `insert_publish_row(step="dim_value", STATUS_SUCCESS, is_current=True)`**（同 table_schema：success 或 replacement_started 时 clear）；失败且已开始替换：`clear_current` + 失败行；未开始替换：仅失败行。**对外文案按下列优先级顺序写死分派（审核修订 50，实现不得各写各的；`validate()` 失败在步骤 2 处理、不进此表）**：

   | 判定（按序） | 对外文案 | 状态 |
   |---|---|---|
   | ① `validate()` 为 false（步骤 2 捕获） | `维度值发布失败：Milvus、源库或 Embedding 服务不可用` | `replacement_started=False`，保留旧 current |
   | ② `error_kind="schema_mismatch"` | §4.3 原文：`dim_value_embeddings 集合结构为旧版本，请手动删除该集合后重新发布` | 无任何 upsert，`replacement_started=False`，不撤销旧 current |
   | ③ `records_unconfirmed > 0` | `维度值未全部发布到 Milvus（成功 M 条 / 失败 K 条，另有 X 条写入结果未确认），请重新发布`（M=`records_loaded`、K=`records_failed`、X=`records_unconfirmed`；可与向量化失败同时出现） | 按 `replacement_started` |
   | ④ 仅有向量化失败（`error_kind="embedding"`） | `维度值未全部发布到 Milvus（成功 M 条 / 失败 K 条），请重新发布` | 按 `replacement_started` |
   | ⑤ `error_kind="source"`（源库查询中断） | `维度值发布失败：源库查询失败（<failed_table>：<error_summary>），请检查维表配置与源库`——后续表不再处理（与向量化失败的跳批继续是有意区别） | 首表即失败 False；中途失败 True |
   | ⑥ `error_kind="input"`（注入内容防御性校验失败，A15 场景） | `维度值发布输入不可用，请检查 dim_config 产物` | False |

   > 表③先于表⑤的含义（审核修订 51）：已有未确认写入、后面某表又 SQL 失败时，对外是表③句（未确认句，不带表名）；A27 ② 的"中途失败"是前面批次**已完整写入**的情况，仍走表⑤。此优先级为有意设定，不再调整。
5. 日志：执行段 `set_current_step("dim_value")`（doc 15 分流；`configs/logging.yaml` 已有 `metaweave.dim_value.loader` 模块日志，零改动）。收尾 `finally: loader.close()`（同 `_publish_table_schema`，`publish_service.py:798-800` 同款）——断开 §7.1 唯一化的 alias 连接，避免每次发布泄漏一个（审核修订 4）。

### 7.3 `DimValueLoader.load()` 改造点（任务 1）

- 集合字段按 §4.1 渲染，`ensure_collection(clean=False, validate_schema=True, index_field_name="col_value_embedding")`（审核修订 1）。
- **配置输入：优先使用注入的 `dim_tables`（§7.1 构造参数，来自 §6.2 拦截时解析并归一的对象），不再按 `config_file` 路径重读文件**（审核修订 19：`validate()` 与 `load()` 现各自经 `_load_dim_tables` 重读一次（`:183`/`:253`/`:338`），两次读取间的 PUT 改写不受 run_marker 复查约束——PUT 不更新步骤行（§5.2 第 5 步）——最坏时拦截后配置被删光，0 表按零批次"全部成功"删光旧记录并置 current，恰好绕过零表拦截）；注入配置仅测试缺省回退读文件。**注入路径下 `validate()` 的存在性短路一并跳过（审核修订 38）**：`validate()` 现以 `dim_tables_path.exists()` 为先决（`:171-173`），注入路径下文件在拦截后被删/改坏时不得因此失败（否则误报"Milvus 或 Embedding 配置、连接不可用"）——`exists()` 与 `_load_dim_tables` 读盘**只属于未注入的测试回退路径**。**注入类型不变量（审核修订 38）**：注入对象即拦截判定所用的归一后 `DimTablesConfig`——**每表 `embedding_col` 恒为非空单列字符串**（§5.3 口径下多列已归 null 并被拦截，到达注入的配置不可能含列表/逗号串）；单一解析路径，禁止用 `from_yaml` 对原文件二次构造注入对象（防两条解析路径口径漂移）。
- **对注入的 `dim_tables` 前置校验**（审核修订 30）：任一表 `embedding_cols_list` 为空 → 受控失败——§6.2 拦截已校验过同一对象，此处为**防御性双保险**（防注入内容构造/传递缺陷），修订 19 后不存在"拦截通过后文件被改写"的窗口（不重读文件）。
- **结果规则（审核修订 15，重定义"成功"——现实现为"跳批仍成功"，见 §3 关键约束之四）**：
  1. 批次 Embedding 重试耗尽或单条值缺向量：**跳过该批/该条，继续处理其余批次**（成功批照常 upsert，不回滚已写入）。
  2. 只要有任何应处理记录最终未获得向量（批次失败或单条缺失）或**写入数量不足**（`upsert_batch` 返回数 < 该批记录数），`load()` 返回 `success=False` 并携带计数——发布步骤记 `failed`（§7.2 步骤 4），**不执行删除旧记录**；已 upsert 的记录保留，下次重跑凭相同 `col_id` 幂等补齐。**"写入数量不足视同该批失败"只作用于删旧判定（置 success=False），不作用于计数**：部分确认批按确认数拆分——`records_loaded += 确认数`、`records_unconfirmed += 该批记录数 − 确认数`（差额是"未获确认"而非"确认失败"，与写入抛错整批同类；若差额计入 failed 会让"成功 97 / 失败 3"误导为丢了 3 条数据，审核修订 29）；`replacement_started` 已随该批 upsert 调用前置 True。
  3. 全部应处理批次成功才删除旧记录（§4.2 第 2 条）并置本次发布为 current。**有表但源库零值属成功而非失败（审核修订 43）**：表已配置、`SELECT DISTINCT` 结果为 0（空表/列全空值）时零批次按"全部成功"处理——照常 `delete_by_expr` 删旧并置 current，如实反映源库现状（上次有值、本次源库无值，向量库随之清空）；**实现不得把零写入当失败**。与空清单拦截（§6.2）不是同一件事：空清单是配置缺失（用户没说要什么），有表零值是数据现状（用户说了要什么、源库没有）。
  4. **状态后果**：部分 upsert 后步骤失败时，Milvus 集合中同时存在本次（部分）与上次的数据，且旧 current 已被撤销（`replacement_started=True` 路径）——平台库无 current 指向、数据不回滚，以最后一次全量成功的发布为准恢复一致。
  5. **源库查询失败的策略与向量化失败不同（审核修订 44，有意为之，实现不得合并）**：某表 `SELECT DISTINCT` 失败（表被删、权限、连接中断）直接上抛 `load()` 总 except 结束加载，**后续表不再处理**——SQL 失败多半是配置或库级问题，继续扫无意义；向量化失败才是"跳过继续"（第 1 条）。SQL 失败的表未读取、不计入任何计数；`error_kind="source"`、`failed_table`/`error_summary` 填首个失败表名与原因摘要（§7.3 返回结构，审核修订 50），对外文案按 §7.2 步骤 4 表⑤；`replacement_started` 按是否已有表完成 upsert 取值（首表即失败 → False 保留旧 current；中途失败 → True 撤销 current，均不删旧记录）。
- 返回 `{success, replacement_started, error_kind, failed_table, error_summary, tables_total, tables_processed, tables_skipped, records_loaded, records_failed, records_unconfirmed, records_skipped, execution_time}`（**`error_kind` 值域与判定以 §7.2 步骤 4 六行表为准，审核修订 51**：`"embedding"`（向量化失败/缺向量，表④）、`"schema_mismatch"`（表②）、`"source"`（源库查询中断，表⑤——**仅此值时 `failed_table`/`error_summary` 有值**，首个失败表名与原因摘要）、`"input"`（**仅**注入内容防御性校验失败，表⑥）；**无 `"write"`**——写入未确认按表③的 `records_unconfirmed > 0` 判定，不依赖 error_kind；**连接类失败不进 error_kind**——走 `validate()` 返回 false（表①，load 可能未执行），若错标为 input 文案会误回"请检查 dim_config 产物"）（`replacement_started`/`records_failed`/`records_unconfirmed` 新增，审核修订 22、24）：**四个计数口径互斥**——`records_loaded` = **服务端确认写入数**（`mr.primary_keys`，`milvus_client.py:280-283`；**含截断后写入的值**：截断不是跳过）；`records_failed` = 有确认结果的失败（向量化失败、单条缺向量——**不含写入不足的差额**，审核修订 29）；`records_unconfirmed` = **写入侧未获确认的记录数**：写入调用抛错的批次**整批**计入（`upsert`/`flush` 抛错时确认数拿不到、服务端可能已部分写入，保守整批计未确认，审核修订 24）+ **部分确认批的差额**（返回数 < 输入数时计 `输入数 − 确认数`，审核修订 29）——该批不重试、跳过继续其余批，`replacement_started` 已在调用前置 True；`records_skipped` = 数据类正常排除（空值/列内重复——**不含截断**，审核修订 22；**不含每表上限**：`LIMIT` 在 SQL 层截断、超限行未被读取，加载器无从计数，审核修订 25），不影响 success。**四者之和 = 本次实际读取的记录数**（`max_records_per_table` 截断的源库行不在任何计数内）。
- 每条记录构造 `col_id = f"{source_id}:{table_name}:{col_name}:{col_value}"`，字段名按新 schema（`col_value_embedding` / `updated_at`）。
- **清洗截断改按 UTF-8 字节口径，且字段上限为硬边界**（审核修订 17、23）：写入前任何文本超过 `col_value` 字段上限（1024 UTF-8 字节）即**无条件安全截断**——不撕裂多字节字符（逐字符累加编码长度或字节截断后安全解码收尾），并**记录 warning（含表名/列名、原始字节数、截断后字节数）后继续向量化与写入**（用户拍板，审核修订 23）；现实现按字符截断且无此 warning，一并修改。**配置与硬边界的关系**：`LoaderOptions.max_text_length`（`models.py:85-92`）只能再收紧（生效值 = min(配置值, 1024)，配置 2048 亦按 1024 截断）；`truncate_long_text: false` **不再豁免硬边界**（该配置项对长度控制失效，Web 发布链路恒走安全截断）——`truncate_long_text: false` 或 `max_text_length > 1024` 两种配置下写入值仍保证 ≤1024 字节。空值判定仍按字符。嵌入文本与 Milvus 写入均使用截断后的值；`col_id` 中的 `col_value` 段即截断后文本（长度与 `col_value` 字段一致）。
- `insert_batch` → `upsert_batch`；**每个 upsert 调用之前置 `replacement_started = True`**（审核修订 16，照 table_schema `:518-519`：调用报错也不能假定服务端完全没有写入——若按"首批成功后"置位，upsert/flush 抛错但已部分写入时会误报未开始替换、错误保留旧 current）；`delete_by_expr` 调用前确保标记已为 True（删除报错同样无法确认服务端是否已执行）。
- 删除旧记录仅在结果规则第 3 条成立（全部应处理批次成功）时执行，表达式 `source_id == "{source_id}" and publish_id != "{publish_id}"`；删除请求成功即完成（不 flush、不轮询可见性，doc 20.1 同口径）。

## 9. 错误处理与边界

| 场景 | 行为 |
|---|---|
| yaml 中表在 json 产物中不存在（作业重跑后表集合变化） | 编辑弹窗右侧显示"该对象在产物中不存在"（object-columns 404）；保存不受阻（PUT 不校验列/表存在性）；发布执行时源库查询失败 → dim_value 步骤失败行，不影响同请求其他步骤 |
| 作业重跑覆盖了人工编辑（embedding_col 回 null） | PUT 版本复查 409（§5.2）；已绕过编辑直接发布 → 发布拦截 400（§6.2）。反向小窗口（复查通过后、写文件前重跑恰好完成）不加锁：后写者胜，重新编辑即可恢复，不设补偿机制 |
| 手工多列 embedding_col | GET 视为未指定（§5.3）；保存收敛单列 |
| 0 张表清单（空清单，审核修订 14） | 允许保存（§5.2）、允许勾选（§6.1 预检只看文件存在）；**点发布即整请求拦截**（§6.2 零表态）：400 `dim_value_empty_tables`，不生成 publish_id、其他步骤不执行，提示"添加表并指定字段，或取消勾选 dim_value" |
| 采集原生空产物 `databases: {}`（零 dim 表，无本库键，审核修订 3、14） | 与编辑保存的空清单同属"零张表"态：GET 返回 `tables: []`（可进编辑弹窗添加表）；发布拦截同上。**不判"文件无效"**（它是 doc 22.1 的合法产物形态）；loader 内部 `from_yaml` 不遇此形态（loader 仅在有表时构造） |
| 文件空白 / 无法解析 / 顶层结构非法（手工损坏）/ **预检通过后文件被删或处于重跑清理窗口** | 发布拦截"无效"态（§6.2 最先判定）：400 `dim_value_config_invalid` + 原因摘要；GET 编辑弹窗为错误态（400，无修复路径）；拦截弹窗按 §8.2 给"重新采集"指引、不放"去编辑配置"（审核修订 21）；修复 = 重跑 dim_config 步骤重新生成（审核修订 27：不存在/不可读与损坏同归无效态，不单列 404——三态同为请求级 400 拒绝语义，修复动作相同） |
| 源库连接失败 / Milvus 不可用 / Embedding 限流 | `validate()` 失败 → 步骤失败行（未开始替换，保留旧 current）；批次 Embedding 重试耗尽或单条缺向量 → 按结果规则记 `failed`（成功/失败计数入消息），不删旧记录（审核修订 15） |
| 向量化部分失败后的中间状态（审核修订 15） | 成功批已 upsert、失败批缺失：Milvus 同时含本次（部分）与上次数据，旧 current 已撤销、平台库无 current 指向；**数据不回滚**，下次重跑凭相同 `col_id` 幂等补齐，以最后一次全量成功的发布为准恢复一致 |
| 有表但源库零值（空表/列全空，审核修订 43） | **成功替换**：零批次按"全部成功"处理，删旧记录 + 置 current（`records_loaded=0`）——如实反映源库现状；与空清单拦截不同（配置缺失 vs 数据现状），不弹任何拦截 |
| 某表源库查询失败（表被删/权限/连接中断，审核修订 44、50） | **与向量化失败不同策略（有意）**：直接结束加载、后续表不再处理（SQL 失败多半是配置或库级问题）；失败表不计入任何计数；`error_kind="source"`、`failed_table`/`error_summary` 填值，文案按 §7.2 步骤 4 表⑤带表名与原因摘要。首表即失败 → `replacement_started=False` 保留旧 current；中途失败（已有表完成 upsert）→ True 撤销 current；均不删旧记录 |
| Milvus 存在旧结构集合 | `validate_schema` 核验失败 → 步骤失败 + 文案提示手动删除集合（§4.3）；**对外文案用 §4.3 原文**（`error_kind="schema_mismatch"`，不收成"输入不可用"、不套"请重新发布"），发生在任何 upsert 之前 → `replacement_started=False`、不撤销旧 current（审核修订 41） |
| 同源并发发布 | 源行锁串行化（现状机制，doc 20.1 已声明 CLI/Web 并发不在处理范围，本篇 Web 间并发由锁保证互斥） |
| 两个编辑窗口并发保存（审核修订 46） | PUT 不改步骤行、version 不变，两窗口各自 GET 拿到相同 version、各自 PUT 均通过复查——**后写覆盖先写**，版本复查只挡得住作业重跑（步骤行 updated_at 变）。受管编辑为单用户低频场景，接受为已知边界，不加编辑级乐观锁 |
| 拦截后、加载前的编辑保存（PUT 改写 yaml，审核修订 19） | **不影响本次发布**：加载输入是 §6.2 拦截时解析的同一份内容（注入 `dim_tables`，loader 不重读文件）；PUT 改写的文件留待下一次发布读取。PUT 不更新 dim_config 步骤行，run_marker 复查对其免疫属预期——内容一致性由注入保证，不依赖标记 |
| 拦截后、加载前的作业重跑（重写产物 + 更新步骤行） | run_marker 锁下复查捕获（`_verify_step_current_under_lock`），按步骤标识已变拒绝 |
| 锁下执行时长（审核修订 9） | dim_value 是第一个在源行锁下**连源库做全表 DISTINCT 扫描**的发布步骤（table_schema 锁下只读本地文件，Embedding 调用锁下已有），持锁时间 = 源库扫描 + Embedding + Milvus 写入。**接受**：同源发布串行化本就是锁的设计意图，发布为低频人工动作，doc 20.1 同步请求口径可覆盖；不做锁外分段执行 |
| 超长值截断合并（审核修订 23） | 两个**不同的原始值**若前 1024 字节相同，截断后文本相同 → `col_id` 相同 → upsert 合并为一条记录（后写覆盖先写，`col_value` 存截断文本）。**接受为已知边界**（用户拍板）：需要两个 >1KB 且前缀完全一致的维表值才触发，业务上极罕见；1024 字节上限沿用。若未来不接受，需重新确定 `col_value` 字段长度或 `col_id` 生成规则（如尾段改哈希），另立文档处理 |
| 手工 yaml 含**他库键**（`databases: {other_db: {...}}` 而无本库键，审核修订 33） | 按宽容口径归"零表"态（GET 返回空清单、发布拦截 `dim_value_empty_tables`）；**下一次 PUT 保存会静默丢弃他库内容**——写回是整份渲染且只写登记库名键。受管链路写不出此形态（生成器只写源库名键），仅手工破坏可达，接受为已知边界 |
| 引用标识符（对象名含点/空白，审核修订 18、49） | **支持**：GET objects 直读 `object_info` 如实返回、弹窗可添加、PUT 接受（写回经 `yaml.dump` 渲染，与 §5.2 第 4 步同款，`from_yaml` 的 `split(".", 1)` 无损读回）；**schema 名含点不支持**：GET objects 直接排除该对象（yaml 键格式固有限制，全链不支持），PUT 对应 400——不会出现"能添加、不能保存" |
| 标识符含冒号 / `col_value` 超长 | 四段拼接的唯一性**前提是中间段（`table_name`、`col_name`）不含冒号**：尾段 `col_value` 含冒号无害（不改变段边界），但中间段含冒号会让不同记录拼出同一 `col_id`（如 `col_name="a:b"`+`col_value="c"` 与 `col_name="a"`+`col_value="b:c"` 同拼 `db.t:a:b:c`，upsert 互相覆盖静默丢记录）。PostgreSQL 未加引号标识符不允许冒号，常规命名下前提成立；加引号标识符属已知边界，不做分隔符转义（审核修订 8）。**超长截断按 UTF-8 字节**（`max_text_length=1024` 字节，不撕裂多字节字符，审核修订 17——Milvus VARCHAR 上限是字节数，字符口径下 1024 个汉字达 3072 字节会插入失败）；`table_name` 最坏 191 字节由 VARCHAR(256) 覆盖 |
| 集合中该源无旧记录（首次发布） | `delete_by_expr` 返回 0，正常成功 |

- **A18** 结果规则（审核修订 15、16、20）——Embedding 失败 ≠ 已开始替换，分两例断言 current 状态：
  - **①a 所有批次 Embedding 全失败**（无任何 upsert 调用）：`load()` 返回 `success=False` + 计数，发布记 `failed`；`replacement_started=False` → **仅失败行、旧 current 保留**（不 `clear_current`）；**不调用 `delete_by_expr`**、Milvus 零写入。
  - **①b 部分批次成功 upsert、另有批次 Embedding 失败**：成功批数据保留写入；`replacement_started=True` → 记 `failed` 并撤销旧 current（§4.2 第 3 条）；**不调用 `delete_by_expr`**。
  - ② 单条缺向量计入 `records_failed`；**写入数量不足只置 success=False（不删旧），计数按确认数拆分**：批 N=100、确认 97 → `loaded += 97`、`unconfirmed += 3`、`failed += 0`——互斥等式成立，"视同失败"不作用于计数（审核修订 29）；upsert 调用抛错时 `replacement_started` 已在调用前置 True（①b 路径），该批**整批**计入 `records_unconfirmed`、不重试、继续其余批，失败文案含"另有 X 条写入结果未确认"而非精确 M/K 声明该批（审核修订 24）。
  - ③ 数据类跳过（空值/重复）不影响 success、计入 `records_skipped`；**截断不是跳过**——截断后的值照常写入并计入 `records_loaded`（审核修订 22）；**每表上限不计入跳过**——`LIMIT` 在 SQL 层截断、超限行未被读取，不在任何计数内（审核修订 25）；`records_failed` 独立计数**向量化失败与缺向量**（写入数量不足的差额计 `unconfirmed`、整批抛错亦计 `unconfirmed`，见 ②——审核修订 39 与 §7.3 返回结构同口径），①a/①b 用例分别断言计数互斥且总数吻合（loaded + failed + unconfirmed + skipped = **本次实际读取的记录数**，审核修订 24、25）。
  - ④ 全部批次成功 → 删旧 + current=True。
  - ⑤ 失败后重跑同数据 → 相同 `col_id` upsert 幂等（记录数不翻倍）。

## 13. 决策记录（用户拍板与澄清）

1. **col_id 构成**：`source_id:table_name:col_name:col_value` 四段拼接（用户在"拼上 col_value / 拼 hash / auto_id+普通字段"三选一中拍板第一项）；`table_name` 维持三段式 `库名.schema.表名` 现状；`pulish_id` 为笔误按 `publish_id` 处理。
2. **CLI 退化**：`rag_load --type dim_value` 入口移除（非保留共用）——loader 构造强制要求 source_id/publish_id，CLI 无自然来源，保留需造占位值，故直接移除最干净；脚本"逐渐退化"由用户明示，不为可用性背书。
3. **原型 5 用途澄清**：`18.dim-value-5` 是**保存成功确认弹窗**（绿色对勾 + 配置摘要），不是发布拦截弹窗；发布拦截弹窗为新增交互，仅参考其版式做错误变体（用户指正，§8.1）。
4. **多列收敛**：Web 编辑仅支持单列；读取时非单列值视为未指定，保存收敛单列。
5. **空清单与无效文件语义（用户澄清，审核修订 14，推翻修订 2/13 的"短路成功"路线）**：勾选自由、保存自由（空清单可保存），但**点发布时整请求拦截**——零张表提示"为 dim_value 添加表并指定值向量化字段，或取消勾选 dim_value"；文件空白/无法解析提示"配置文件无效"，不得当作零张表。不存在"空清单发布成功"路径；Milvus 旧记录与旧 current 只被下一次**有表且全配置**的成功发布替换。
6. **弹窗数据不依赖平台库**：编辑弹窗全部数据来自受管产物文件（json 产物 + dim_tables.yaml），用户未发布过 json 也可编辑（与解冻条件"只看 yaml 存在"自洽）。

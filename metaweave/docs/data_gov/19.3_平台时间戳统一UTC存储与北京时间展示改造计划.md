# 19.3 平台时间戳统一 UTC 存储与北京时间展示改造计划

## 1. 目标与口径

本计划统一平台库当前业务表中的时间戳：全部使用 PostgreSQL `timestamptz`，保存确定的时间点，精确到微秒；显式 `(6)` 与未指定精度的默认声明在精度上等价，均满足本计划要求。应用产生的时间直接取带时区的 UTC 当前时间；数据库产生的时间继续使用 `now()`。API 统一返回 UTC，Web UI 统一显示北京时间，不依赖应用服务器、数据库服务器或浏览器的本地时区。本文规划新口径的代码与表结构调整，不做已有数据迁移，不考虑向下兼容；通过重新采集并发布生成新数据。

API 时间字符串统一为六位小数、带 `Z` 的 UTC ISO 8601，例如 `2026-10-05T06:03:07.008123Z`。Web UI 统一使用微秒展示格式 `yyyy-MM-dd HH:mm:ss.SSSSSS`，将该例显示为北京时间 `2026-10-05 14:03:07.008123`。数据库类型决定时间精度，不规定显示文本；API 与页面分别使用上述格式，均保留六位小数。空值仍按各接口原有的 `null` 与页面缺省文案处理。

PostgreSQL 的时间戳列保存的是**时间类型值**，没有可设置的物理字符串格式。`timestamptz(6)` 保留六位小数，数据库会话时区只影响 SQL 客户端显示，不改变该值表示的时间点。需要固定文本格式时，由产物、API 和 Web UI 各自按上述契约格式化。

`timestamptz` 按 UTC 保存确定瞬间，不保留输入的时区名称或原始偏移。对本计划规定的带时区输入及 `now()` 写入，PostgreSQL 会话 `TimeZone` 即使设为东京或纽约，也不改变该值表示的时间点；API 仍输出 UTC，Web UI 仍显示北京时间。SQL 客户端因会话时区不同而显示不同钟面，不代表存储错误。该结论不适用于无时区输入的解释，故入库校验必须要求带时区。

范围包括 MetaWeave 管理的**平台库当前业务表**，以及 §2.3 列出的产物内嵌时间。不修改客户源库中被采集字段的类型、值或格式，也不修改文件名中的时间片段。平台库字段清单已按实际平台库的只读查询核对。当前平台库数据均为测试数据，本次不做历史数据迁移、时区追溯、修复或回填，不保留旧生成时间列的测试值；不处理业务系统数据库。

## 2. 数据库字段与写入

### 2.1 字段清单

`backend/persistence/models.py` 对应的平台库时间戳列统一为**带时区、微秒精度**。已核对实际平台库：下列 10 列中，9 列是 `timestamp with time zone`，其 `atttypmod = -1` 表示未显式指定精度，仍可保留最多六位小数；不要求为了写出 `(6)` 而变更这 9 列。`table_profile.generated_timestamp_local` 是 `timestamp without time zone`，同样未显式指定精度。ORM 对目标列使用 `timezone=True`；显式写六位精度时，其语义与上述 9 列一致。

| 表 | 时间戳列 |
| --- | --- |
| `db_source_info` | `created_at`、`updated_at` |
| `job_info` | `created_at`、`updated_at` |
| `db_profile` | `collected_at` |
| `table_definition` | `loaded_at` |
| `publish_info` | `created_at`、`updated_at` |
| `table_profile` | `generated_timestamp_local`（目标列名 `generated_timestamp`）、`loaded_at` |

目标列为 `generated_timestamp timestamptz(6)`，替代原 `generated_timestamp_local`。现有无时区列保存本地钟面，直接读取本身不会因 PostgreSQL 会话 `TimeZone` 改变而换算。本次不转换或回填旧测试值，因此不需要确定其历史时区，也不将历史时区解释作为实施前置条件。

### 2.2 写入规则

1. 应用生成需要入库的时间时使用 Python `datetime.now(timezone.utc)`，直接得到带 UTC 时区信息的当前时间，不先取无时区的服务器本地时间，也不靠 `replace(tzinfo=...)` 给本地读数补标签。保留六位微秒。
2. 数据库生成的 `created_at`、`updated_at`、`loaded_at` 等继续使用 `now()` 默认值；`backend/data_sources/repository.py`、`backend/jobs/repository.py`、`backend/publishing/repository.py` 的 `func.now()` 更新语句也保留。`now()` 是 PostgreSQL 的带时区时间值，写入 `timestamptz(6)` 时不需要应用代码换算。应用服务器与数据库服务器可使用不同的本地显示时区。
3. `metaweave/core/metadata/db_step.py` 生成 `database.json` 的 `collected_at` 时，保留现有 UTC 来源，改为固定六位微秒、`Z` 结尾；`backend/profile_loading/db_loader.py` 继续要求输入带时区，并写入 `timestamptz(6)`。
4. `metaweave/core/metadata/models.py` 生成逐表 JSON 的 `generated_timestamp` 时，由 `datetime.now()` 改为 `datetime.now(timezone.utc)`，输出六位微秒、`Z` 结尾；`backend/profile_loading/json_loader.py` 改为要求带时区输入并写入 `timestamptz(6)`。原字段名 `generated_timestamp_local` 不再符合语义，规划中将库列、ORM、API 字段统一改名为 `generated_timestamp`。

在 `metaweave/utils/time_utils.py` 提供唯一的 Python UTC 文本函数 `utc_isoformat(value: datetime) -> str`，供 `database.json`、逐表 JSON、§2.3 六处产物及后端 API、MD 运行标识直接调用。该模块只依赖 Python 标准库，不导入后端模块；后端导入此工具，不另写一份同构实现。函数检查 `tzinfo` 和 `utcoffset()` 均非空，先 `astimezone(timezone.utc)`，再 `isoformat(timespec="microseconds")`，最后将 UTC 后缀 `+00:00` 替换为 `Z`。Python 的 `isoformat()` 不会自动输出 `Z`，不得省略最后一步；例如 UTC 当前时间必须输出 `2026-10-05T06:03:07.008123Z`，而非以 `+00:00` 结尾。无时区输入直接抛出 `ValueError`；可空字段由调用方处理，不传入该函数。

改名同时覆盖 `json_loader.py` 的行映射与 `_parse_local_timestamp`：函数改名为 `_parse_aware_timestamp`，保留原有空值处理；非空值解析后检查 `tzinfo` 和 `utcoffset()` 均非空，再调用 `astimezone(timezone.utc)`，换算为同一瞬间的 UTC 时间。生成器固定输出 `Z`，加载器也接受合法的其他时区偏移；禁止用 `replace(tzinfo=timezone.utc)` 替换标签，因为这会改变非 UTC 输入表示的瞬间。同步修改 `backend/api/object_schemas.py` 的两处字段声明、`frontend/src/api/types.ts` 第 294、365 行的类型声明，以及 `ObjectDetailView.vue` 第 183、185 行的字段引用与注释；前端类型检查确认没有遗漏旧字段引用。

切换后，旧 JSON 若含无时区的 `generated_timestamp`，新加载器会拒绝发布；须使用新版生成器重新执行 `json` 步骤后再发布，不给旧字符串猜测或补贴时区。缺失或 `null` 仍按原有空值规则处理。这是新输入契约的直接结果，本计划不增加旧产物兼容逻辑。

数据库默认值、应用显式写入值、采集产物入库值最终都表示确定的时间点。保留现有字段的业务含义：`collected_at` 是库画像采集时刻，`generated_timestamp` 是逐表 JSON 生成时刻，`loaded_at` 与 `publish_info.created_at` 分别是平台库写入及发布记录的审计时间；本计划不把这些概念合并。数据库 `now()` 取当前事务开始时刻，同一事务内保持不变，不等于每条语句执行时刻或事务提交时刻；本次保留这一现有语义，不更换时间函数。参见 [PostgreSQL 当前时间函数说明](https://www.postgresql.org/docs/current/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT)。

部署时，应用服务器和数据库服务器均须启用系统时间同步（NTP 或系统自带的网络时间服务），使用可靠时间源；无需统一两台服务器的时区，也无需额外引入 Python 时区包。`datetime.now(timezone.utc)` 与数据库 `now()` 各自依赖所在机器的系统时钟，时区转换不能修正机器间的时钟偏差。若出现异常时间差，先检查两台机器的时间同步状态和事务持续时间；生成时间与入库审计时间对应不同事件，本来就不要求相等。

### 2.3 其他产物的内嵌时间

这些位置当前都直接调用 `datetime.now()`，没有转为 UTC；`isoformat()` 输出无时区的本地时间，`strftime()` 输出无时区且仅到秒的文本。统一改为应用取得的 UTC 时间，并调用 §2.2 的 `metaweave.utils.time_utils.utc_isoformat`，固定输出带 `Z` 的六位微秒 ISO 8601。只调整时间文本，不改变产物的其他结构或文件名。

| 产物 | 当前代码位置 | 当前形式 |
| --- | --- | --- |
| rel JSON 的 `generated_timestamp` | `metaweave/core/relationships/writer.py:205` | 本地无时区 ISO 字符串 |
| 表间关系发现报告的“生成时间” | `metaweave/core/relationships/writer.py:595` | 本地时间，仅到秒 |
| CQL 脚本头的“生成时间” | `metaweave/core/cql_generator/writer.py:252` | 本地无时区 ISO 字符串 |
| CQL 随附 Markdown 的“生成时间” | `metaweave/core/cql_generator/writer.py:403` | 本地时间，仅到秒 |
| DDL 头的 `Generated` 注释 | `metaweave/core/metadata/formatter.py:260` | 本地时间，仅到秒；随 DDL 正文发布到 `table_definition.define_text` |
| SQL-RAG 验证报告的“验证时间” | `metaweave/core/sql_rag/validator.py:485` | 本地无时区 ISO 字符串 |

这些产物中的时间只标识该文件或报告的生成时刻，不能替代平台库的 `collected_at`、`loaded_at` 或 `publish_info.created_at`。

## 3. 后端时间处理与 API

后端直接复用 §2.2 定义的 `metaweave.utils.time_utils.utc_isoformat`，不再建立独立实现；所有平台库时间 API 共用它。驱动返回 `+08:00` 等偏移时也必须先换算，不能直接删掉偏移后拼接 `Z`，也不能用 `replace(tzinfo=timezone.utc)` 代替换算。驱动返回无时区值（`tzinfo is None` 或 `utcoffset() is None`）时，共用函数抛出 `ValueError`，不擅自认定为 UTC。API 响应序列化遇到该错误时，使用 `backend/api/errors.py` 现有通用异常处理，返回 HTTP `500`、`code=internal_error` 和受控消息“服务暂时无法处理请求”，沿用现有日志记录，不增加错误类型或异常处理器。产物输入缺少时区仍按加载器现有输入校验失败路径处理。现有分散的秒精度、毫秒精度格式化函数统一替换，重点包括：

- `backend/assets/read_tx.py` 的 `utc_isoformat`，及其在 `object_catalog.py`、`object_detail.py` 中的调用；`backend/assets/catalog.py` 的独立 UTC 格式化。特别检查 `object_catalog.py:_list_item` 和 `object_detail.py:_profile_block`：两处 `generated_timestamp_local.isoformat()` 裸输出须随字段改名一起替换为共用格式化函数，返回带 `Z`、六位微秒的 UTC 字符串，不再直出无时区的 `T` 串。
- `backend/data_sources/registration_service.py`、`backend/jobs/listing.py`、`backend/jobs/home.py`、`backend/publishing/listing.py`、`backend/publishing/home.py` 的 UTC 格式化。首页的“近 30 天”比较保持按确定时间点计算。
- `backend/data_sources/md_step_service.py` 对平台库 `updated_at` 运行标识的 UTC 序列化：`_marker_iso` 改为调用 `metaweave.utils.time_utils.utc_isoformat`，`md/manifest.json` 的 `source_json_updated_at` 固定为 UTC、六位小数、`Z` 结尾。MD 运行期间仍按数据库 `datetime` 比较 JSON 标识，保持原有核对逻辑；未来 `table_schema` 发布读取该标识时，当前 JSON 标识也须用同一函数格式化后比较，不得与旧 `_marker_iso` 格式逐字比较。本次不兼容旧 MD 清单，重新执行 MD 生成新清单。

运行标识核对用于确认 MD 的上游 JSON 未被重跑覆盖，不代替执行成功状态检查。MD 开始时记录 JSON 的 `updated_at`，结束时检查 JSON 仍为 `success` 且该标识未变；即使两次 JSON 运行都成功，也不能让使用旧 JSON 或混合文件生成的 MD 被认定为有效输入。清单将来源标识留给后续发布核验。本计划只统一标识文本格式，不增加版本字段或新的核对机制。

检查现有 API 响应中的时间字段，包括 `created_at`、`collected_at`、`loaded_at`、`generated_timestamp`、`published_at`、`last_collected_at`、`last_published_at`、`executed_at`。`updated_at` 是平台库审计字段及内部运行标识，不作为新增 API 返回字段。除生成时间字段改名外，字段名和业务取值规则不变；非空值统一为带 `Z` 的六位微秒 UTC 文本。

`backend/jobs/collection_run.py` 与 `backend/publishing/publish_service.py` 的执行结果 `finished_at` 虽不直接来自平台库，但会显示在 Web UI，也按同一 UTC 六位微秒格式输出。

## 4. Web UI 统一展示

**Web UI 展示业务时间时，一律默认转换为北京时间（`Asia/Shanghai`，UTC+08:00）。** 该规则覆盖所有页面上的登记、采集、生成、发布、加载、作业执行与完成时间；不随用户浏览器、应用服务器或数据库服务器的本地时区变化。

在 `frontend/src/api/format.ts` 提供唯一的时间展示函数。它解析后端带 `Z` 的 UTC 时间，并固定按 `Asia/Shanghai` 显示为 `yyyy-MM-dd HH:mm:ss.SSSSSS`；不使用浏览器默认时区，也不手写加 8 小时。JavaScript `Date` 只保留毫秒精度，因此共用函数须从原始 API 字符串保留六位小数，用时区格式化得到年月日时分秒后，拼接原始六位小数，不能通过 `Date` 重建小数部分而丢失后三位。缺失值由调用方按原页面文案显示。时间排序可继续比较统一格式的 UTC 字符串，格式固定时其字典序与时间先后顺序一致。

非空时间字符串若不符合 UTC `Z` 结尾、六位小数的格式，或日期解析失败，共用展示函数返回 `—`，不抛出导致页面渲染失败的异常，也不按本地时区猜测或原样显示错误字符串。缺失值继续使用各页面原有文案。

原串通过格式校验后，供 `new Date` 解析的副本将小数截为三位，例如 `value.replace(/(\.\d{3})\d+(?=Z$)/, '$1')`；原串不变，显示仍拼接原串的六位小数。采用截断而非四舍五入，避免进位改变整秒；这样不依赖浏览器对六位小数时间字符串的扩展解析行为。

把以下页面和组件里的独立时间格式化函数改为调用该共用函数：

| 页面或组件 | 当前时间展示 |
| --- | --- |
| `DataSourcesView.vue`、`DataSourceDetailView.vue` | 登记时间、最近采集、最近发布 |
| `DataAssetsView.vue`、`DatabaseProfileView.vue` | 数据采集时间、库画像采集时间、发布失败时间 |
| `ObjectDetailView.vue` | JSON 发布时间、画像生成时间、DDL 加载时间、样例区域时间 |
| `CollectionJobsView.vue`、`SelectPublishJobView.vue`、`PublishJobsView.vue` | 采集与发布作业时间 |
| `CreateCollectionJobView.vue`、`PublishView.vue` | 步骤完成时间 |
| `SourceWorkBrowser.vue` | 作业执行时间 |

移除库画像页固定显示 `UTC`、对象详情页按浏览器时区计算偏移、资产页的 `yyyyMMdd-HH:mm:ss.SSS` 特殊格式，以及各页只显示到秒的格式。Web UI 的业务时间字段统一显示为北京时间 `yyyy-MM-dd HH:mm:ss.SSSSSS`，保留完整六位微秒。DDL 代码块属于产物原文，其中 `-- Generated: ...Z` 保留 UTC 注释，不在展示层改写 SQL 文本。

北京时间展示规则仅覆盖平台自身的业务时间字段，以下两类内容不调用共用时间展示函数：

- **DDL 原文中的时间注释**：新版产物的 `-- Generated: ...Z` 按 §2.3 生成 UTC 文本，页面保留原文；旁边独立的“DDL 加载时间”仍转换为北京时间。生成注释与加载时间是不同事件。
- **样例数据单元格中的客户业务时间**：沿用源库样例值的现有展示，不统一转换为北京时间、不补贴时区、不强制改为六位小数。样例区域的平台“采集时间”标签仍按北京时间展示规则处理。

本计划保证平台业务时间按确定瞬间统一展示，不保证客户源库时间值的时区语义或准确性。近 30 天统计继续按 UTC 时刻向前减 30 天计算，不改为按北京时间日历日切割。

## 5. 实施顺序与验收

1. 确定 UTC 六位微秒的产物/API 格式，核对平台库已有 9 个带时区列的精度口径，单独处理逐表生成时间列的类型和名称，并核对 ORM 类型及 `now()` 写入点。
2. 调整 `db`、`json` 产物生成及加载校验，确认应用产生的时间带时区、六位微秒，入库后为 `timestamptz(6)`；同步调整 §2.3 列出的产物内嵌时间。
3. 统一后端各 API 的 UTC 六位微秒输出；调整执行结果 `finished_at`。
4. 替换全部 Web UI 时间展示函数，统一使用共享格式化函数。
5. 更新并运行相关后端单元测试、产物文本断言与接口断言；运行前端 `npm run typecheck`、`npm run build`；在浏览器中人工核对时间展示，并切换浏览器时区确认显示仍为同一北京时间。当前前端没有测试脚本，不将“前端测试”列为现有验收命令。

Python 共用函数用一组用例验证：UTC 输入、非 UTC 偏移输入、微秒非零、微秒为零及无时区拒绝；产物、API 和 MD 清单的验收分别确认实际调用路径及输出符合这一契约。

异常验收包括：后端响应序列化收到无时区时间时返回受控 `500 internal_error`；产物中的无时区时间按输入校验失败处理；前端非空但无法解析或格式不合约的时间显示 `—`，页面其余内容正常渲染。

带偏移输入验收：加载器接受 `2026-10-05T14:03:07.008123+08:00`，解析并换算为 `2026-10-05T06:03:07.008123Z` 所表示的同一瞬间；入库后 API 输出后者，Web UI 显示 `2026-10-05 14:03:07.008123`，六位小数保持不变。

产物文本验收覆盖 `database.json`、逐表 JSON 和 §2.3 的六处时间：均固定输出六位小数并以 `Z` 结尾，微秒为零时仍输出 `.000000Z`；DDL 的 `-- Generated:` 注释也须符合该格式，不能残留 `+00:00` 后缀。

数据库时区独立性验收：选择同一行中已有非空值的带时区列，例如 `db_source_info.created_at`；先断言查询值非空，并确认实际调用共用格式化函数。在测试用 API 数据库连接的只读事务中，分别执行 `SET LOCAL TIME ZONE 'America/New_York'` 和 `SET LOCAL TIME ZONE 'Asia/Shanghai'`，每次均实际重新查询该列并格式化，不复用 ORM 已缓存的值。两次 API 时间字符串须完全相同，均为 UTC 六位小数、`Z` 结尾，页面仍显示同一北京时间。尚未重新发布、值为 `NULL` 的 `generated_timestamp` 不能用于此项验收；两次空值相等不算通过。时区设置必须作用于本次实际查询的连接，不能只在另一个 SQL 客户端会话中设置；不改数据库全局时区，不写入业务数据。

验收样例：平台库十个时间列均为带时区、最多六位小数的时间戳，接受未显式限定精度和显式 `(6)` 两种等价声明；应用写入与数据库 `now()` 写入均能正确表示同一时间线上的时刻；API 返回例如 `2026-10-05T06:03:07.008123Z`，页面显示 `2026-10-05 14:03:07.008123`，后三位 `123` 必须保留；六位小数为零时 API 和页面均显示 `.000000`；在浏览器时区设为 UTC 或其他地区时，页面显示文本不变；作业排序、近 30 天统计与发布来源字段的现有业务含义不变。

平台库列类型可用以下只读 SQL 验收：改造前应为现有 9 列 `PASS`、目标 `generated_timestamp` 尚不存在而 `FAIL`；改造后应返回 **10 行且全部为 `PASS`**。清单只包含当前业务表，不包含备份表。

```sql
WITH expected(table_name, column_name) AS (
    VALUES
        ('db_source_info', 'created_at'),
        ('db_source_info', 'updated_at'),
        ('job_info', 'created_at'),
        ('job_info', 'updated_at'),
        ('db_profile', 'collected_at'),
        ('table_definition', 'loaded_at'),
        ('publish_info', 'created_at'),
        ('publish_info', 'updated_at'),
        ('table_profile', 'generated_timestamp'),
        ('table_profile', 'loaded_at')
)
SELECT e.table_name,
       e.column_name,
       pg_catalog.format_type(a.atttypid, a.atttypmod) AS actual_type,
       CASE
           WHEN a.atttypid = 'timestamp with time zone'::regtype
            AND pg_catalog.format_type(a.atttypid, a.atttypmod)
                IN ('timestamp with time zone',
                    'timestamp(6) with time zone') THEN 'PASS'
           ELSE 'FAIL'
       END AS result
FROM expected AS e
LEFT JOIN pg_catalog.pg_namespace AS n
       ON n.nspname = 'public'
LEFT JOIN pg_catalog.pg_class AS c
       ON c.relnamespace = n.oid
      AND c.relname = e.table_name
      AND c.relkind IN ('r', 'p')
LEFT JOIN pg_catalog.pg_attribute AS a
       ON a.attrelid = c.oid
      AND a.attname = e.column_name
      AND a.attnum > 0
      AND NOT a.attisdropped
ORDER BY e.table_name, e.column_name;
```

另须确认旧列已经删除，以下查询改造后必须返回 `PASS`。仅新列类型通过不能代替此项核验：

```sql
SELECT CASE WHEN NOT EXISTS (
    SELECT 1
    FROM pg_catalog.pg_attribute
    WHERE attrelid = 'public.table_profile'::regclass
      AND attname = 'generated_timestamp_local'
      AND attnum > 0
      AND NOT attisdropped
) THEN 'PASS' ELSE 'FAIL' END AS old_column_removed;
```

## 6. 表结构 SQL 与设计文档同步

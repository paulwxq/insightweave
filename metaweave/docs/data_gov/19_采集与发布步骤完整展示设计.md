# 19. 采集与发布步骤完整展示设计

状态：设计稿，待实施。日期：2026-10-03。

## 1. 已定原则

数据采集与画像页面、画像发布页面都要让用户看见完整的流程范围。一个步骤尚未接入 Web，或当前作业的产物未就绪，只影响**能否选择**，不能使步骤名称从页面消失。不可选项必须保留名称、所属分组和明确原因；单靠淡色或禁用复选框不足以说明还剩哪些能力待开发。

采集步骤与发布步骤**不要求同名或一一对应**。发布是把采集产物写入平台画像库或 RAG 存储；一个发布类型可能消费多个采集产物，一个采集步骤也可能只为后续步骤准备输入。尤其 `--step md` 不是独立的 `md` 发布类型：`rag_load --type table_schema` 读取 MD，并读取同名 JSON 中的分类和时间列提示。页面要把这种来源关系写出来，不能因为发布选择项叫 `table_schema`，就让用户看不到 MD 的去向。

本文只规定步骤展示和禁用状态。启用新的 Web 采集、Web 发布、平台画像表或 RAG 加载编排，仍需各自的执行、产物校验和发布设计；不得仅改前端可选状态就让未支持的请求进入后端。

## 3. 采集产物与发布类型的对应关系

下表描述**输入关系**，不表示这些 Web 发布类型已开放。

| 采集或生成步骤 | 产物及作用 | 对应发布或加载类型 | 当前 Web 状态 |
| --- | --- | --- | --- |
| `db` | 数据库概览 JSON | `db`，写平台库画像 | 采集、发布均可选 |
| `ddl` | 数据库对象 DDL | `ddl`，写平台库当前表定义 | 采集、发布均可选 |
| `json` | 表与字段画像 JSON | 规划中的 `json` 平台画像发布；也是 `table_schema` 的补充输入 | 采集可选；发布不可选 |
| `md` | 从 JSON 渲染的表结构 Markdown | `table_schema`，与同名 JSON 一起加载到 Milvus | Web 采集已接入（doc 19.1，依赖同作业已成功的 JSON）；发布编排未接入；独立 CLI 可生成、加载 |
| `generate-domains` | 业务域配置 | `domain`，写平台库 `table_domain` 表-域映射（doc 21.2） | Web 采集可选（doc 21.1 接入 `domain` 步骤）；发布可选（doc 21.2，b 组） |
| `generate-dim-config` | 维表配置 | `dim_value` 使用配置，并从源库读取维值加载到 Milvus | Web 采集可选（doc 22.1 接入 `dim_config` 步骤，依赖同作业已成功的 JSON）；发布已接入（doc 22.2，`dim_value` 发布勾选 + 配置编辑 + 加载到 Milvus） |
| `rel` | 表关系发现结果 | `rel`，加载到 Neo4j（发布过程生成 cql 并加载，doc 23.2 接入） | Web 采集可选（doc 23.1 接入 `rel` 步骤，依赖同作业已成功的 JSON 与 Domain，连源库采样）；Web 发布可选（doc 23.2，支持发布前编辑关系） |
| `cql` | Cypher 脚本 | （发布职能并入 `rel` 发布：cql 由 rel 发布过程生成并加载，doc 23.2） | 已从 WebUI 移除（采集页删行、发布页 c 组放 `rel`，doc 23.2） |
| `generate-sql-rag` | Question–SQL 样例 | `sql`，加载到 Milvus | Web 采集已接入（doc 25.1）；Web 发布已接入（doc 25.2，加载到 Milvus `sql_example_embeddings`，按源整份替换） |

`table_schema` 的输入必须明确写作 **MD + 同名 JSON**，不能只写“JSON 产物”。`dim_value` 也不能表述为“直接发布 dim-config 文件”：加载器使用该配置，并连接源库读取维表数据。`rel` 已有独立发布项（doc 23.2，目标 Neo4j，发布过程内含 cql 生成与加载）；`generate-domains` 的发布已按 doc 21.2 接入为 `domain`。

## 4. 页面展示规则

### 4.1 数据采集与画像

固定展示 §2 的全部 9 项及其所属分组，不按 `enabled`、当前数据源状态、当前作业状态或本次选择结果过滤目录。页面为每项展示可理解的状态：`可执行`、`Web 暂未接入`；可执行项因当前上下文不能运行时，展示具体原因。禁用项的名称和说明应与可选项一样可读，不能通过低透明度、`display: none` 或仅凭灰色表达状态。

按钮禁用、单选、分组选择、全选、重跑回填和请求提交仍只接受当前后端支持的 `db/ddl/json`（doc 19.1 实施后含 `md`）。分组项数显示**全部步骤数**；全选按钮说明“选择当前可执行步骤”，避免用户误认为灰色项也被选择。`md` 在目录中的位置保持 `ddl → json → md`。

### 4.2 画像发布

固定展示现有 8 种发布类型，分组和命名保持 `db/ddl/json/domain/sql/table_schema/dim_value/rel`（domain 自 21.2 起就该补入；本清单原 7 种漏写 domain，doc 23.2 改订时补齐——cql 移出、rel 加入，行数不变仍 8）。每个非同名的 RAG 类型在选项旁显示其采集来源：`table_schema ← md + json`、`dim_value ← generate-dim-config + 源库维值`、`sql ← generate-sql-rag`、`rel ← rel（发布过程生成 cql 并加载 Neo4j，doc 23.2）`。

发布项状态至少区分 `可发布`、`采集未成功或产物未就绪`、`Web 暂未接入`。后两类保留可读的名称和原因，但不可勾选；`table_schema` 即使其 CLI 加载器已存在，也标为 `Web 暂未接入`。全选、重放回填、请求提交只允许服务端已支持且本次预检通过的 `db/ddl`。页面不凭文件存在自行把静态不可选项升级为可选。

### 4.3 状态来源与边界

“展示目录”与“允许执行”分开维护。可以继续使用静态步骤目录，但字段名应表达 `selectable` 或 `web_supported`，不能用 `enabled: false` 作为省略展示的条件；即使以后从后端获取步骤能力，服务端仅返回当前支持项时，前端仍须展示完整目录并合并能力状态。发布预检只为已实现的 `db/ddl` 返回就绪信息，其余项的 `Web 暂未接入` 文案来自静态能力声明，不伪造预检结果。

## 6. 验收口径

1. 采集页面任何时候都能看见全部 9 个步骤；未接入步骤名称清晰可读，旁边有“Web 暂未接入”，不可选择，也不会被全选或重跑回填带入请求（doc 19.1 实施后 `md` 已接入，doc 21.1 实施后 `domain` 已接入，doc 22.1 实施后 `dim_config` 已接入，doc 23.1 实施后 `rel` 已接入，doc 23.2 后 `cql` 从采集页移除，未接入步骤仅 `sql-rag`）。
2. 发布页面能看见全部发布类型及不可选原因；能直接看到 `md → table_schema`、`generate-sql-rag → sql`、`generate-dim-config → dim_value` 的关系；`rel` 有独立发布项（目标 Neo4j，doc 23.2），原 `rel → cql` 链路并入 rel 发布（`generate-domains → domain` 已接入，doc 21.2）。
3. 只有 `db/ddl/json` 可提交采集（doc 19.1 实施后含 `md`，doc 23.1 实施后含 `rel`），只有预检通过的 `db/ddl` 可提交 Web 发布；直接构造不支持的 API 请求仍被后端拒绝。
4. `--step md` 仍只依赖 JSON 产物；`rag_load --type table_schema` 仍读取 MD + 同名 JSON。展示改造不改变 CLI、pipeline、平台库、Milvus 或 Neo4j 的执行行为。

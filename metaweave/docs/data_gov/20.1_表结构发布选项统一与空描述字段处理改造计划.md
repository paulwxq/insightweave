### 1.1 通过公开接口释放 Milvus 连接

当前 `backend/publishing/publish_service.py:_publish_table_schema` 在 `finally` 中直接访问 `loader._milvus_client` 并关闭连接，后台依赖了加载器的私有状态。实施时在 `metaweave/core/loaders/table_schema_loader.py:TableSchemaLoader` 增加公开 `close()`，后台改为在 `finally` 中仅判断 loader 是否已创建，再调用 `loader.close()`，不再访问 `_milvus_client`。

### 1.2 共用受管输入准备函数

在 `metaweave/core/table_schema/managed_input.py` 增加 `prepare_managed_table_schema_input()`，作为受管 JSON/MD 输入的唯一解析与字段校验入口。它调用现有 `read_managed_pairs()` 核对目录、清单和运行标识，再用 `MDParser` 解析每份 MD，核对 JSON 字段全集，按传入的 `LoaderOptions` 判断空描述是跳过还是报错，并按 §10.2 校验待写入字符串长度，返回待加载的表级/字段级对象及空描述跳过字段名。`include_columns=false` 时仍解析和校验全部字段，只是不返回独立字段级待加载对象。该函数只读文件、处理内存数据，不初始化 Embedding 或 Milvus，也不删除、写入数据。

`backend/profile_loading/table_schema_loader.py:check_table_schema_output_ready()` 传入规范化 `source_id` 和 Web/API 固定的两个 `true` 选项调用该函数；`TableSchemaLoader.prepare_input()` 传入规范化 `source_id` 与本次加载器的实际选项调用同一函数，并保留其返回的输入快照供后续向量化。Web/API 从平台库取得当前 JSON 步骤的 `updated_at` 和数据源登记库名，分别作为 `expected_json_marker`（先用 `utc_isoformat` 格式化）和 `database_name` 传入。调试 CLI 不读平台库，这两个外部比对值省略；仍由 `read_managed_pairs()` 校验两份清单、MD 清单中运行标识的文本格式、JSON/MD 对象集合及文件身份，再按同一函数校验字段。预检和执行可以各自重新读取文件，但不能在后台与加载器分别实现字段解析、空描述过滤、长度检查或 JSON 集合校验。文件在两次读取之间变化时，执行阶段按同一规则重新校验并拒绝不一致输入。

无需删除模型配置字段，无需新增命令行选项、API 参数或 WebUI 控件。

## 4. 两个选项的执行口径

### 4.1 独立脚本

配置路径为 `loaders.table_schema_loader.options`，不是新增的 CLI 参数：

```yaml
options:
  include_columns: true
  skip_empty_desc: true
```

- `include_columns=true`：在表级对象之外加载字段级对象；`false`：只加载表级对象。
- `skip_empty_desc=true`：跳过没有有效描述的字段级对象，并记录字段名；`false`：发现任一字段没有有效描述就报错，作业退出。这里的“没有有效描述”包括空字符串、纯空白和去除首尾空白后恰好为 `无注释`；两项都只作用于字段级对象。
- 两项都默认 `true`；改变取值仅用于独立脚本调试。
- 脚本使用 `--source_id`、`--job_id` 时仍属于脚本入口，仍读取配置值；不能因为定位受管目录就强制覆盖选项。

CLI 即使把 `include_columns` 设为 `false`，也按实际加载结果判断调试任务成败；该结果不写平台库，不成为正式 current。Web/API 固定两项为 `true` 的规则不扩展到 CLI。CLI 仍核对本次 JSON/MD 产物及字段，但不执行 Web 的数据源状态、作业状态和登记库名准入，见 §10.7。

正常 MD 始终生成一条表级对象，其向量化文本是包含字段内容的整份 MD。整份 MD 为空直接报告输入错误，与上述两项取值无关。字段解析及字段身份校验照常执行；即使 `include_columns=false` 不写字段级向量，`skip_empty_desc=false` 仍核对每个字段，发现空描述立即报错。`include_columns=false` 且 `skip_empty_desc=true` 时不写字段级对象，因此没有可跳过的字段，`empty_desc_columns` 为空、CLI 输出“空描述跳过字段 0 个”，属于预期；需要查看空描述字段名单时应开启 `include_columns`。

| 入口 | `include_columns` | `skip_empty_desc` | 表级向量 | 字段级处理 |
|---|---|---|---|---|
| CLI | `true` | `true` | 始终加载 | 非空描述加载；空描述跳过并记录名字 |
| CLI | `true` | `false` | 始终加载 | 任一字段空描述则报错退出；全部非空才加载全部字段 |
| CLI | `false` | `true` | 始终加载 | 解析、核对字段，但不写独立字段向量 |
| CLI | `false` | `false` | 始终加载 | 解析、核对字段；任一字段空描述则报错，否则不写独立字段向量 |
| Web/API | 固定 `true` | 固定 `true` | 始终加载 | 非空描述加载；空描述跳过并记录名字 |

#### CLI 参数命名

本篇按本轮确认的参数名记录 `metaweave rag_load --type table_schema --source_id <UUID> --job_id <UUID>`。当前 `metaweave/cli/loader_cli.py`、doc 20 和相关测试已经使用这两个下划线参数；本次不重命名 CLI 参数。Python 内部变量仍为 `source_id`、`job_id`。这组参数与 `metadata`、`meta_load` 使用的连字符参数风格不同，文档示例和帮助文本应准确反映 `rag_load` 的实际写法。

### 4.2 WebUI/API

无论配置文件将两项写为 `true`、`false`，或者不写，Web/API 实际执行值都必须为 `true`。这里是**强制覆盖运行值**，不是仅提供默认值。

覆盖落在 `backend/profile_loading/table_schema_loader.py:build_table_schema_loader`：取得配置后，在加载器配置的深拷贝中将两项设为 Python 布尔值 `True`，再构造 `TableSchemaLoader`。不覆盖 `batch_size` 等其他配置，不修改主配置文件或原始配置快照。

不要把覆盖放在核心 `configure_managed_loader` 中：它被脚本和后台共用，放在那里会同时关闭脚本调试能力。

WebUI 不提供这两个开关，API 请求不新增这两个参数。页面经 API 发起的发布自动遵守固定口径；直接调用 API 也一样。预检采用与执行一致的固定口径。

在 `configs/metadata_config.yaml` 的对应 options 下同步注释，说明默认值、用途，以及 Web/API 忽略配置取值、固定两项为 `true`。现有 `skip_empty_desc` 注释中的“描述为空的对象”应改为“描述为空的字段”；`false` 的含义写为“字段描述为空时直接报错”。注释中的“系统运行”指 Web/API 发布，独立 CLI 仍允许调试。

## 5. 字段解析、过滤和校验规则

### 5.1 先识别字段，再决定是否加载

MD 解析器必须识别字段名并保留原始描述，例如 `{"order_id": "订单ID", "remark": ""}` 或 `{"remark": "无注释"}`。不能在解析阶段删除没有有效描述的字段。

字段列表章节接受生成器现用的 `## 字段列表：` 标题，也接受已有测试使用的 `## 字段列表`；从标题之后读到下一条 `##` 级标题或文件末尾。章节内先去除每行的首尾空白：空行和不以 `-` 开头的说明文字忽略；以 `-` 开头的列表行一律视为待解析字段行，格式为 `- 字段名 (类型) - 描述 [示例: ...]`，其中描述可以为空、行末示例标记可以缺省。不能静默忽略畸形列表行。`-` 后缺空格、缺字段名、类型或描述分隔符等均报输入错误；重复字段名报错，不允许后者覆盖前者。忽略说明文字也不能放过字段缺失，仍须与 JSON 字段集合核对。

解析类型时从字段名后的类型左括号起匹配成对的右括号，再识别后面的描述分隔符；不能用 `\([^)]+\)` 在第一个右括号处截断。这样 `numeric(10,2)`、`character varying(200)` 等嵌套括号类型仍可解析。字段名保留内部空格及 `$` 等实际字符，去掉语法边界的空白后按原名与 JSON `column_profiles` 核对；不能继续用 `[\w.-]+` 限制字段名，或按第一个空格截断。分隔符定义为**至少一个空白 + `-` + 空白或行尾**，可按 `\s+-(?:\s+|$)` 识别；去除行尾示例并 `strip()` 后，`- col (type) -` 是合法字段行，描述为空。缺少这个 `-` 才叫缺描述分隔符，`- col (type) -说明` 不符合生成格式，也报输入错误。

示例只认描述分隔符之后的**行末完整标记** ` [示例: ...]`，无标记的字段行也合法。若有多个 ` [示例: `，从最右侧那个开始剥离，以整行最后一个 `]` 作为闭合，闭合 `]` 后只能有已被 `strip()` 去掉的空白；出现 ` [示例: ` 却缺少行末闭合 `]` 时，报输入错误，不能把残缺标记当作描述送去向量化。剥离示例后再对字段描述 `strip()`；不依赖当前按 `") - "` 分割的宽松降级分支。现有生成器没有转义描述或示例中的 ` [示例: `，因此若示例值本身包含该字面标记，文本存在歧义；本次按上述最右侧规则解析，不声称能无损还原这种特殊文本。合法字段行必须由明确的结构规则解析，无法解析即报错。

MD 生成器在把每个样例值写入 ` [示例: ...]` 前，先将其字符串中的换行按现有注释渲染方式折叠为空格，使一条字段记录始终只占一行。该处理只发生在 MD 输出边界；JSON 产物及源库样例原值不变，表级仍向量化生成后的完整 MD，字段级仍只向量化字段描述。解析器不增加多行样例续行推断；不符合上述单行格式的 MD 按输入错误处理。

下文“空描述”统一指**没有有效字段描述**：取出描述并去除首尾空白后，结果为空，或结果**恰好等于** `无注释`。当前 MD 生成器对缺少字段注释会写入字面文本 `无注释`，因此该值也应跳过或报错；包含这三个字但另有实际说明的描述不算空。该判断不针对样例单元格中的 `NULL`，也不直接读取源库注释。表级描述始终取整份 MD 文本，包含字段内容；整份 MD 为空直接报输入错误。`include_columns`、`skip_empty_desc` 都不能跳过表级对象。

### 5.2 加载集合可以是 JSON 字段集合的子集

明确采用以下四条规则：

1. **MD 解析出的字段必须属于 JSON** `column_profiles`，不能多出未知字段。此检查在空描述过滤前执行，未知字段即使没有有效描述，也不能通过跳过绕过校验。
2. **`skip_empty_desc=true` 时跳过没有有效描述的字段**，不请求其字段级 Embedding，不写入其字段级 Milvus 记录；日志用完整对象 ID 记录字段名字。
3. **`skip_empty_desc=false` 时，任一字段没有有效描述即报错并退出**，列出字段名；此时不调用 Embedding，也不删除该源旧记录。不能把没有有效描述的字段交给 Embedding，也不能将其作为正常跳过。
4. **`include_columns=true` 时，全部应加载的字段必须成功写入**，不能因为解析遗漏、向量化失败或写入失败而少加载后仍报告成功；`include_columns=false` 只是不写独立字段向量，不免除字段解析、身份核对及第 3 条的空描述检查。

当 `include_columns=true` 且 `skip_empty_desc=true` 时，最终加载字段集合允许是 JSON 字段集合的子集，不再将**过滤后的集合**与 JSON 全集做相等比较。不过，仅检查子集关系不足以证明“只有空描述被忽略”：JSON 中存在、MD 中却没有识别到的字段，不能被认定为空描述字段，仍应报告产物不完整。

实现时分别核对：

- 过滤前：MD 字段身份与 JSON 对齐，确保没有未知字段或缺失字段。
- 选项处理后：`skip_empty_desc=false` 有字段没有有效描述则直接失败；`include_columns=true` 且 `skip_empty_desc=true` 时，待加载字段恰好是已识别字段中有有效描述的部分；`include_columns=false` 时不写字段级记录。
- 写入后：表级对象及所有待加载的字段级对象必须成功写入。

这样只在 `skip_empty_desc=true` 时放宽因**明确空描述**产生的集合差异，不放宽解析和写入遗漏。

### 5.3 示例

JSON 有 `order_id`、`amount`、`remark` 三个字段。以下示例采用 Web/API 的固定选项，或 CLI 的 `include_columns=true, skip_empty_desc=true`：

| MD 字段 | 解析后描述 | 处理 |
|---|---|---|
| `order_id` | `订单ID` | 向量化并加载 |
| `amount` | `金额` | 向量化并加载 |
| `remark` | 空字符串、纯空白或 `无注释` | 跳过字段级向量化，记录名字 |

例如 `- remark (text) - [示例: x]` 和 `- remark (text) -` 都解析出空描述；`- amount (numeric(10,2)) - 金额 [示例: 12.50]` 解析出 `金额`；`- remark (text) - [示例: x` 因示例标记未闭合而报输入错误。

加载 1 条表级记录、2 条字段级记录，可以发布成功。完整 MD 仍用于表级向量化，其中可以包含 `remark` 的字段名或样例；跳过的是该字段的**独立向量记录**。

同一输入在 CLI 设置 `skip_empty_desc=false` 时，须在向量化和首次 upsert 前报告 `remark` 没有有效描述并退出，不能继续加载其他对象。只有去除首尾空白后**完整等于** `无注释` 才按空描述处理，不能因为描述中出现“无注释”三个字就误跳过其他有效文本。

在 `skip_empty_desc=true` 时，若所有字段都没有有效描述，但 MD 本身有正常内容，允许仅加载表级记录并成功，日志列出所有这类字段。整个 MD 文件为空始终报输入错误，不把空文件解释成一个正常表对象。

若 `amount` 在 MD 中缺失、字段行无法解析，或向量化/写入失败，则不能成功。若 MD 多出 JSON 没有的 `extra_column`，即使其没有有效描述，也拒绝输入。

## 6. 向量化文本保持现状

当前 `_batch_embed_and_upsert` 仅把 `object_desc` 传给 Embedding，不拼接 `object_id`：

```python
texts = [obj.object_desc for obj in batch]
```

表级 `object_desc` 是完整 MD；字段级 `object_desc` 是解析出的字段描述。`object_id`、`object_desc`、`embedding` 分别存入 Milvus。不同字段描述完全相同时，当前服务会按文本去重并复用向量。

本篇保留该行为，不把字段名、表名自动补成描述，也不新增 `object_id + object_desc` 拼接规则。`skip_empty_desc=true` 时，空描述字段在调用 Embedding 前过滤；`false` 时，发现空描述就报错退出。两种分支均不向 Embedding 传空描述字段。

## 7. 日志与成功判定

`skip_empty_desc=true` 时，每个跳过的空描述字段（含字面值 `无注释`）记录 INFO 日志，至少包含 `source_id`、`job_id`（入口提供时）、完整字段对象 ID 和原因 `empty_description`。该原因统一表示“没有有效描述”，不因空字符串或 `无注释` 分两套统计。示例：

```text
跳过空描述字段 source_id=<UUID> job_id=<UUID> object_id=orders.public.orders.remark reason=empty_description
```

加载结束汇总记录实际加载对象数、空描述跳过字段数及完整字段名字列表。日志不输出样例值或完整 MD/JSON 内容。

**空描述跳过与失败跳过必须分开统计。**现有 `objects_skipped` 参与失败判定，不能把正常空描述跳过累计到这里，否则仍会导致整次加载失败。可以在加载器内部结果中增加 `empty_desc_columns` 列表，汇总数量从列表长度取得；无需为此扩展平台表、API 响应字段或 WebUI。

成功要求：表级记录和选项确定的全部待加载字段成功写入。`skip_empty_desc=true` 时因空描述跳过不判失败；`false` 时存在空描述直接失败。向量化失败、缺失向量、重试耗尽和写入数量不足仍判失败。预检只校验输入并确定可加载字段，不调用 Embedding 或 Milvus。

## 8. 验收

- **A01** 配置两项都为 `false` 时，Web/API 实际加载器两项仍为 `True`，原配置快照不被改写；独立 CLI 仍按配置执行调试分支。
- **A02** 有描述字段全部加载，空描述字段不调用字段级 Embedding、不写入字段级向量，日志记录准确字段名字。
- **A03** CLI 的 `skip_empty_desc=false` 在 `include_columns` 为 `true` 或 `false` 时均核对字段；任一字段空描述都明确报错、作业退出，且在调用 Embedding 与首次 upsert 前完成。两种取值均不把空字符串交给 Embedding。
- **A04** Web/API 与带 UUID 的调试 CLI 在各自允许的选项组合下都为正常 MD 生成表级向量；整份 MD 为空时，无论选项如何都报告输入错误，不能作为成功加载跳过该表。
- **A05** 未知字段包括“未知且空描述”均被拒绝；缺失字段、无法解析字段行、重复字段名不能作为空描述正常跳过。
- **A06** `numeric(10,2)`、`character varying(200)` 等嵌套括号类型仍能解析；字段列表中的空行和非列表说明文字可忽略，畸形 `-` 列表行直接报错；`- col (type) -` 与 `- col (type) - [示例: x]` 均识别为空描述，不把示例标记当描述；缺分隔符、`- col (type) -说明`、示例标记缺行末 `]` 均报错；示例缺省以及示例值中含普通 `]` 时按 §5.1 解析。
- **A07** 描述为空字符串、纯空白或恰好为 `无注释` 时，Web/API 与 CLI `skip_empty_desc=true` 均跳过字段并记录名字；CLI `skip_empty_desc=false` 均在向量化及首次 upsert 前报错。描述包含“无注释”但还有其他实际说明文字时，不误判为空。
- **A08** 所有字段描述都为空且 MD 正常时，表级记录成功加载，发布成功，跳过名单完整。
- **A09** 非空描述字段向量化或写入失败仍发布失败，不能混入正常空描述跳过统计。
- **A10** Web 预检与发布执行都调用 `metaweave/core/table_schema/managed_input.py:prepare_managed_table_schema_input()`，使用同一字段规则；预检不连接 Embedding/Milvus。输入在预检后变化时，执行重新读取并校验：不符合规则则拒绝，合法空描述字段按固定选项跳过，不沿用旧预检结果。
- **A11** 发布成功或失败均通过加载器公开 `close()` 释放已创建的连接；客户端未创建、重复关闭及关闭异常不改变发布结果，后台不再访问加载器私有客户端属性。
- **A12** 使用假服务完成测试，不要求启动真实 Milvus，不处理旧产物和历史数据库数据。
- **A13** MD 样例值包含换行且续行原本会以 `-` 或 `##` 开头时，生成后的字段行仍为单行，解析及 JSON 字段对账成功；JSON 原样例值不变。含空格或 `$` 的字段名按 JSON 原名识别，不因旧正则或按空格截断而失败；真正缺失或多出的字段仍按 A05 报错。

## 9. 同源发布继续使用平台库行锁等待

`backend/publishing/repository.py:lock_db_source_row` 继续使用普通 `with_for_update()`。不增加 `nowait` 参数，不把锁占用映射为 HTTP 409，不新增 `publish_source_busy`。Web/API 的 `table_schema` 与 `db`、`ddl`、`json` 相同：同源的后一个操作停在平台库 `db_source_info` 对应行上，直到持锁事务提交或回滚，再复查并执行。不同 `source_id` 不争用同一行。

这把锁在平台库，不在 Milvus。Milvus 没有等价的源级锁，也不会自己排队。对于 `table_schema`，Web/API 先取得这行锁，再在尚未提交的同一事务内做输入处理、向量化、按源替换和发布记录提交。后来的同源 Web/API 发布因此会在调用 Embedding、upsert 或清理 Milvus 之前等待。其他发布项继续按各自现有路径使用同一源行锁。Milvus 里的 upsert 和删除仍然不能随平台库事务一起回滚。调试 CLI 不访问平台库，不参与这把锁；本计划不处理 CLI 与 Web/API 同源并发。

平台库连接不设置 `lock_timeout`。等待期间发布页保持现有「发布中」，不新增繁忙提示或前端错误解析。不修改 doc 12 的单步失败后继续规则，也不改 doc 20 §5 已有的等待描述。

实施时保持 `lock_db_source_row` 的现有签名和等待方式。`_publish_table_schema` 与现有 db/ddl/json 发布路径继续使用同一函数；调试 CLI 不调用它。不新增队列或锁表。

验收：

- 同源两个 Web/API `table_schema` 发布：第二个停在平台行锁上，持锁方提交或回滚后继续执行，不返回 409，也不在等到锁之前调用 Embedding 或改写 Milvus。
- 不同 `source_id` 的 `table_schema` 发布可以并行。
- 同源 `db`、`ddl`、`json` 与 Web/API 的 `table_schema` 发布仍使用同一等待方式；调试 CLI 不属于该验收范围。

## 10. 共用 Milvus 集合与按数据源替换

### 10.1 集合与新增字段

所有数据源的 Web/API 表结构发布和调试 CLI 加载使用同一个 `table_schema_embeddings` 集合，实际名称仍由 `loaders.table_schema_loader.collection_name` 配置。停止在集合名末尾追加 source_id，不再为每个数据源创建一个集合。

表级与字段级记录都增加以下字段：

| 字段 | Milvus 类型 | 含义 |
|---|---|---|
| `source_id` | `VARCHAR(36)` | 规范化的带连字符 UUID；标识数据源，用于限定旧批次清理范围和检索过滤 |
| `publish_id` | `VARCHAR(36)` | 本次写入批次的 UUID；Web/API 对应平台库 `publish_info`，调试 CLI 仅作 Milvus 批次标记，不登记平台库 |
| `entity_id` | `VARCHAR(512)`，主键，`auto_id=false` | `source_id + ":" + object_id`，由应用生成 |

保留现有 `object_id`、`object_type`、`parent_id`、`object_desc`、`embedding`、`time_col_hint`、`table_category`、`updated_at` 字段。`object_id` 从主键改为普通字段，继续使用 `database.schema.object[.column]`；`parent_id` 保留表对象名称含义。同一批记录的 source_id、publish_id 必须一致。

Milvus 不增加 `job_id` 字段；Web/API 的正式发布需要时经平台发布记录追溯。一个 job_id 可以对应多个正式 publish_id：重复发布同一采集作业会生成新的发布 ID；每次 Web/API 发布请求对应一个 job_id，多步骤共用该次 publish_id。调试 CLI 的批次 UUID 不出现在 `publish_info`，不能用它查平台发布历史。

Web/API 与调试 CLI 都使用以上三个字段和同一共用集合。`entity_id` 是唯一主键；`source_id` **另作为独立标量字段保留**，供旧批次清理和检索过滤，不以解析 `entity_id` 代替。CLI 的参数和清理规则见 §10.7。调试 CLI 写入可能覆盖同源的正式向量记录，但不会修改平台库 current；后续 Web/API 正式发布会按源替换这些调试记录。CLI 不与 Web/API 通过平台行锁排队。

### 10.2 Milvus 不支持多字段联合主键

Milvus 的一个集合只能有一个主键字段，不支持 SQL 中将 `(source_id, object_id)` 两列声明为联合主键。采用**拼接后的单字段字符串主键**表达相同的对象身份，而不是给两列都设置 `is_primary=true`。[官方主键文档](https://milvus.io/docs/primary-field.md)

```text
source_id = b4a87275-7c37-4feb-bf1c-e5a8446c174f
object_id = orders.public.orders.order_id
entity_id = b4a87275-7c37-4feb-bf1c-e5a8446c174f:orders.public.orders.order_id
```

source_id 必须先规范化为 UUID 字符串，再拼接冒号和原 object_id。不同源即使有完全相同的数据库、表、字段名，entity_id 也不同；同源同一对象重复发布时 entity_id 不变，publish_id 更新为本次值。`publish_id` 是发布批次标识，不参与主键；成功清理后集合仅保留该源本批对象。部分写入失败时可能暂留新旧混合记录，见 §10.3。

该拼接仅用于记录主键，**不用于 Embedding 输入**。向量化仍仅使用 object_desc，遵守 §6。原 object_id 长度上限保持 256，entity_id 单独采用 512。

**在向量化和首次 upsert 之前预检长度。**Milvus 2.5 的 `VARCHAR max_length` 以 UTF-8 **字节数**计，不按字符数计；实现统一使用 `len(value.encode("utf-8"))` 与 §10.6.2 的集合字段上限比较。[Milvus 2.5 字符串字段说明](https://milvus.io/docs/v2.5.x/string.md)。保留现有 `object_desc` 8192 字节、`object_id` 256 字节的预检，并覆盖待写入记录的其余 VARCHAR 字段：`entity_id` 512、`source_id` 36、`publish_id` 36、`object_type` 64、`parent_id` 256、`time_col_hint` 512、`table_category` 64。固定 UUID 与对象类型按其规范化结果核对；无值字段先按现有写入规则转为空字符串再核对。表级 `object_desc` 是整份 MD，不截断、不摘要化，也不跳过超限对象。

共用输入准备函数接收规范化 `source_id`，在解析、过滤后校验本次待加载的全部表级/字段级记录；预检阶段尚无 `publish_id` 时，该字段由后续生成的规范化 UUID 保证 36 字节。执行阶段构造最终 VARCHAR 字段值后，再对包括实际 `publish_id` 在内的全部 VARCHAR 字段做一次长度核对，且必须发生在调用 Embedding 和首次 upsert 之前。任一字段超限就明确报出对象 ID、字段名、实际字节数和上限并使本次操作失败；旧源 Milvus 记录保持不变，Web/API 的旧 current 也保持不变。长度校验不能替代 Milvus 写入校验；其他写入错误仍按 §10.3 的失败流程处理。

### 10.3 先整行 upsert 本批对象，再清理旧批次

以 **Milvus 服务端 v2.5.2** 为目标。该版本支持显式主键的整行 upsert，以及按标量表达式删除；不使用 partial update。项目已有 `MilvusClient.upsert_batch()`，实施时复用。[Milvus 2.5 upsert 文档](https://milvus.io/docs/v2.5.x/upsert-entities.md)、[Milvus 2.5 删除文档](https://milvus.io/docs/v2.5.x/delete-entities.md)。本地已用服务端 v2.5.2 和当前 PyMilvus 2.6.5 在独立临时集合验证：同主键 upsert 会更新本次对象；旧批次中已移除的对象须另行清理；中途写入失败后会出现新旧混合；按源和批次清理不会影响另一源。测试脚本为 `scripts/probe_milvus_upsert_252.py`，没有修改正式集合。这只证明本方案用到的基础操作在该组合下可用，不推断其他 2.6 客户端特性均兼容 2.5.2 服务端。

Web/API 每次正式发布按如下顺序执行；调试 CLI 复用第 2～6 步，不执行第 1 步的平台锁与第 7 步的发布记录写入：

1. 按 §9 用 `with_for_update()` 取得平台库源行锁；锁被占用时等待，不返回 409。持锁覆盖本次输入处理、向量化、按源替换和平台结果提交。调用 Embedding 与改写 Milvus 都发生在取得该锁之后。
2. 完成清单及字段校验；Web/API 还核对平台库 JSON 运行标识及登记库名，调试 CLI 只核对清单中的运行标识格式。过滤没有有效描述的字段并记录名字；按 §10.2 对最终待写入记录完成 VARCHAR 字节长度预检，任一超限直接失败。此时不调用 Embedding、不改写 Milvus，Web/API 的旧 current 保持不变。
3. 在调用 Embedding 之前连接 Milvus，table_schema 调用 `ensure_collection(clean=False, validate_schema=True)`，确保共用集合存在并使用 §10.6.2 的新 schema。已有集合先按字段名核对字段集合、各字段类型及 VARCHAR 上限、唯一主键 `entity_id`、配置中的向量维度；字段声明顺序不参与比较。不一致则明确失败，**不调用 Embedding、不 upsert、不删除记录**，Web/API 的旧 current 保持不变。首次没有集合时按新 schema 创建并加载；不 drop 旧集合。此时不写入任何表级或字段级记录。其他加载器的 `ensure_collection()` 调用保持默认行为，见 §10.6.3。
4. 为全部待加载表级和字段级对象完成向量化，核对每个待加载对象有可写入向量，且实际返回向量的维度与集合维度一致；任一失败都在首次 upsert 前终止。预先生成的向量保留 Embedding 服务返回的 NumPy 数组形式，不在此阶段对全量向量调用 `tolist()`。已有集合的记录不变，Web/API 的旧 current 保持不变；如果第 3 步首次创建了集合，此时可能留下空集合，不视为数据发布成功。
5. 按 `batch_size` 分批调用 `upsert_batch()` 写入**完整记录**：仅在构造当前写入批次时将该批 NumPy 向量转为 Python 列表，批次完成后释放临时列表，不提前持有全量列表。`entity_id = source_id + ":" + object_id` 为主键，每条都携带本次 `publish_id`、`source_id` 和全部其余 schema 字段。相同主键覆盖旧对象，新主键插入；检查每批返回数量，任一批失败或数量不足立即停止，不执行步骤 6。`upsert_batch()` 当前在响应缺少主键列表时会回退返回 `len(data)`，实施时须修正，不能把缺失的写入结果当成成功数量。
6. **全部 upsert 成功后**，按表达式 `source_id == "<规范化 source_id>" and publish_id != "<本次 publish_id>"` 删除该源不属于本次发布的记录；删除请求成功返回后才继续，匹配不到旧记录时删除数为零也算成功。已从本次 JSON/MD 消失的旧表、字段及先前失败批次的残留都由此清掉；不可只执行 upsert，因为缺席对象没有主键可供 upsert 覆盖。不得只按 source_id 删除全部记录，也不得 drop 共用集合。本步骤不以 `flush()` 成功或立即检索可见作为完成条件；Milvus 的读取可见性取决于查询一致性级别，`flush()` 不能替代该保证。[Milvus 2.5 产品 FAQ](https://milvus.io/docs/v2.5.x/product_faq.md)、[一致性说明](https://milvus.io/docs/v2.5.x/consistency.md)。
7. upsert 和旧批次清理均成功后，按现有平台事务机制撤销旧 table_schema current，写入本次成功 current 发布记录并提交。任一写入或清理错误不能报告成功。

上述顺序意味着全部待加载向量仍需暂存在内存，内存用量随对象数增长。当前配置为 1024 维，Embedding 服务返回的 NumPy `float64` 数组约 8 KiB/条；提前转成 Python float 列表通常约 32 KiB/条，均不含对象和文本开销。逐批转换只避免同时持有全量 Python 列表，不改变“全部向量化成功后才开始 upsert”的失败边界；本计划不增加临时文件或新的内存阈值。

Web/API 与调试 CLI 禁止对共用集合执行 drop、重建或无 source_id 过滤的全量删除。首次没有集合时在向量化前创建集合；已有集合校验通过后只执行当前源的数据替换，保留索引和其他源记录。检索某个数据源时应显式过滤 source_id，不能把共享集合中的其他源数据混入结果。

这是**非原子替换**，不能承诺检索过程始终只见同一批次。输入预检、集合结构校验或向量化失败不会改写已有对象记录；若是首次创建集合后向量化失败，可能留下空集合。Web/API 的旧 current 保持不变。一旦开始调用首批 upsert，任一 upsert、清理或后续步骤失败时，都按可能已经部分改写 Milvus 处理：该源可能同时存在本次与旧批次记录，**旧批次已被同主键 upsert 覆盖的部分不能回滚**。平台库仍可写时，Web/API 将本次记为失败并撤销该源旧 table_schema current，不能继续把旧发布标为有效；调试 CLI 只报告加载失败，不修改平台库 current。即使某个 upsert 调用报错，也不假定该调用完全没有写入。重新执行使用新的批次 UUID，完整 upsert 后再清理所有非本批记录，使结果收敛。其他源不受本次清理影响。先 upsert 避免主动清空该源的阶段，但不保证 upsert 内部或并发检索完全无短暂可见性变化。平台库提交失败或进程中断时可能无法记录失败或撤销旧 current，导致平台记录与 Milvus 暂时不一致；沿用 doc 20 的重新发布处理，不引入历史回填或自动恢复。

### 10.4 与 db/ddl/json 的业务口径对照

| 发布步骤 | 当前替换范围与方式 |
|---|---|
| `db` | 替换或更新当前 source_id 的数据库画像行 |
| `ddl` | 删除当前源 `define_type='ddl'` 的旧定义，再插入本批定义 |
| `json` | 删除当前源旧 table_profile，级联删除字段画像，再插入本批对象与字段 |
| `table_schema`（本计划） | 共用集合中按 `entity_id` 整行 upsert 本批表级和字段级记录，全部成功后删除当前 source_id 下 `publish_id` 非本次的记录 |

四者都按源替换，不清空其他源。db/ddl/json 的平台库数据替换可以由 PostgreSQL 事务回滚；Milvus 替换不能随平台库事务一起回滚，不把两者描述为相同的事务能力。

验收补充：

- **M01** 一个共用集合中包含两个源；替换其中一个源后，另一个源的记录与 publish_id 保持原样。
- **M02** 两个源具有相同 object_id 时，entity_id 不同；同源表级与字段级记录均有准确的 source_id、publish_id。
- **M03** Web/API 对同一 job_id 再次正式发布时，使用新的 publish_id；同一 entity_id 经 upsert 更新为新批次，清理后该源不保留旧批次；无需 Milvus job_id 字段。
- **M04** 新范围删除了某些对象或字段后，upsert 本身不会删除这些缺席对象；清理 `source_id == 本源 and publish_id != 本次` 后它们不残留，先前失败批次也能被下一次成功发布清除。
- **M05** Web/API 输入预检、集合结构校验或向量化失败时已有对象记录和旧 current 不变；首次创建集合后向量化失败允许留下空集合，不写入记录、不登记成功发布。分批 upsert 的后续批次失败时，旧数据与新数据混合；平台库可写时旧 current 被撤销并登记本次失败。调试 CLI 在这些失败下均不修改平台库 current。重试完整 upsert 与清理可收敛；清理失败也不得报告成功。检验另一源记录未变化。
- **M06** Web/API 与调试 CLI 只在**全部 upsert 成功后**按 `source_id == 本源 and publish_id != 本次` 删除，没有 drop 共用集合或全量删除调用；查某源数据时使用 source_id 过滤。
- **M07** 拼接后的 entity_id 不改变 Embedding 输入文本；表级整份 MD 的 `object_desc`、字段级描述及其他待写入 VARCHAR 字段按 §10.2 的 UTF-8 字节上限预检。任一字段超限时，Web/API 与调试 CLI 均在 Embedding 和首次 upsert 前报错，指出对象、字段、实际字节数和上限；旧源记录不变，Web/API 的旧 current 不变。边界值等于上限时允许继续；修复超限产物后可重新执行。
- **M08** 调试 CLI 写入的 source_id 独立字段与 entity_id 的源前缀一致，publish_id 是本次调试批次 UUID；CLI 不写 `publish_info`，即使加载成功也不改变正式 current。同源下一次 Web/API 正式发布按源清理 CLI 批次；CLI 与 Web/API 同源并发不作为本次验收项。
- **M09** table_schema CLI 带或不带 `--clean` 都先 upsert 本批、再仅清理当前 source_id 的非本批记录，不能 drop 共用集合；其他 Milvus 加载类型的 `--clean` 保持原义。CLI 缺 `platform` extra 但已具备加载所需依赖时仍可执行 table_schema 调试加载。
- **M10** 用假服务核对完整记录、每批 upsert 数量（无返回数量不得按输入条数算成功）、`source_id`/`publish_id` 清理条件和调用顺序；确认全部 Embedding 完成前不 upsert，预生成阶段不把全量 NumPy 向量转为 Python 列表，写入时仅转换当前批次；另有 `scripts/probe_milvus_upsert_252.py` 对独立临时集合的实测记录，本次文档修改不操作正式 Milvus 集合。
- **M11** 用假服务核对调用顺序为“输入与长度预检 → 连接并创建/核对集合 → Embedding → 核对实际向量维度 → 首批 upsert”；table_schema 显式传 `validate_schema=True`，已有旧 schema 或配置维度不匹配时，不调用 Embedding、upsert 或删除，旧 current 保持不变；字段顺序不同但字段名及定义一致的集合可通过校验。`sql`、`dim_value` 加载器不传新参数且沿用原有集合处理行为（doc 25.2 更新：`metaweave/core/sql_rag/loader.py` 现传 `validate_schema=True`，`rag_load --type sql` 已移除、Web 发布替代。）；已有合格集合可重复初始化且不清空记录；首次建集合后 Embedding 失败可留下空集合，但没有任何对象记录或成功发布记录。
- **M12** 配置的 Milvus database 不存在时：`MilvusClient.connect()` / `test_connection()` 默认清晰失败且不创建；传 `create_database=True` 时创建并切换；table_schema 的 `validate()` 与 `load()` 均以 `create_database=True` 连接（用假客户端核对）。
- **M13** 集合定义中各 VARCHAR 字段的 `max_length` 直接取自 `VARCHAR_LIMITS`（与预检同源），测试对账两者一致，避免只改一处。

### 10.6 初始化入口核对与新建集合定义

#### 10.6.1 当前项目的初始化位置

当前项目没有独立的 Milvus `table_schema_embeddings` 建表 SQL 文件。实际初始化随加载执行，分为两处：

| 文件与函数 | 职责 | 实施时的修改要求 |
|---|---|---|
| `metaweave/core/loaders/table_schema_loader.py:TableSchemaLoader._ensure_collection` | 定义 FieldSchema、CollectionSchema、向量维度和索引参数 | 将本节的新字段和 entity_id 主键定义写入此处；输入预检后、Embedding 前调用；Web/API 调用禁止 drop 集合 |

#### 10.6.2 正确的新建集合定义（PyMilvus）

Milvus 建集合使用 SDK API；本项目沿用 PyMilvus 的 `FieldSchema`、`CollectionSchema` 和公共客户端。以下代码相当于本集合的“建表语句”，用于首次初始化新结构，没有 drop、全量删除或数据迁移操作。API 形式参照 [PyMilvus 2.5 CollectionSchema 文档](https://milvus.io/api-reference/pymilvus/v2.5.x/ORM/CollectionSchema/CollectionSchema.md)。

```python
from pymilvus import CollectionSchema, DataType, FieldSchema

from metaweave.utils.file_utils import resolve_project_path
from services.config_loader import ConfigLoader
from services.vector_db.milvus_client import MilvusClient

# 沿用主配置和环境变量解析，不在建集合代码中写连接凭据。
metadata_config = ConfigLoader(
    str(resolve_project_path("configs/metadata_config.yaml"))
).load()

embedding_config = metadata_config["embedding"]
active_provider = embedding_config["active"]
embedding_dimensions = int(
    embedding_config["providers"][active_provider]["dimensions"]
)
collection_name = metadata_config["loaders"]["table_schema_loader"][
    "collection_name"
]  # 默认 table_schema_embeddings，不追加 source_id

fields = [
    FieldSchema(
        name="entity_id",
        dtype=DataType.VARCHAR,
        max_length=512,
        is_primary=True,
        auto_id=False,
    ),
    FieldSchema(name="source_id", dtype=DataType.VARCHAR, max_length=36),
    FieldSchema(name="publish_id", dtype=DataType.VARCHAR, max_length=36),
    FieldSchema(name="object_id", dtype=DataType.VARCHAR, max_length=256),
    FieldSchema(name="object_type", dtype=DataType.VARCHAR, max_length=64),
    FieldSchema(name="parent_id", dtype=DataType.VARCHAR, max_length=256),
    FieldSchema(name="object_desc", dtype=DataType.VARCHAR, max_length=8192),
    FieldSchema(
        name="embedding",
        dtype=DataType.FLOAT_VECTOR,
        dim=embedding_dimensions,
    ),
    FieldSchema(name="time_col_hint", dtype=DataType.VARCHAR, max_length=512),
    FieldSchema(name="table_category", dtype=DataType.VARCHAR, max_length=64),
    FieldSchema(name="updated_at", dtype=DataType.INT64),
]

schema = CollectionSchema(
    fields=fields,
    description="Table and column schema embeddings for NL2SQL",
    enable_dynamic_field=False,
)
index_params = {
    "index_type": "HNSW",
    "metric_type": "COSINE",
    "params": {"M": 16, "efConstruction": 200},
}

# ensure_collection 会在需要时创建配置指定的 database（默认 nl2sql）。
client = MilvusClient(metadata_config["vector_database"]["providers"]["milvus"])
try:
    collection = client.ensure_collection(
        collection_name=collection_name,
        schema=schema,
        index_params=index_params,
        clean=False,
        validate_schema=True,
    )
finally:
    client.close()
```

定义共 11 个字段，唯一主键是 entity_id。source_id、publish_id、object_id 均为普通字段，不把两列同时设置为主键，不加入 job_id。

当前配置的向量维度为 1024；建集合始终从 `embedding.providers.<active>.dimensions` 获取维度，不能把当前值写死。向量索引保持 HNSW/COSINE、M=16、efConstruction=200。time_col_hint、table_category 对无值的对象继续写空字符串；updated_at 保留 Unix 秒整数，沿用现有向量记录口径。

已确认 `updated_at` 暂时保持原样：字段名不变，类型仍为 `INT64`，应用使用 `int(time.time())` 写入 Unix 秒整数。该字段仅用于调试时确认对象加载时间，不在 WebUI 展示，不改为微秒整数、时间字符串或 TIMESTAMPTZ，也不因该字段升级 Milvus。本次不将 doc 19.3 的六位小数展示契约扩展到此字段。

**schema 不会自动计算 entity_id，也不会自动填充 source_id、publish_id。**每条写入记录必须由应用显式赋值：`entity_id = source_id + ":" + object_id`，source_id、publish_id 使用规范化 UUID 字符串；updated_at 也由应用赋值。配置中的 embedding 维度须在向量化前与已有集合核对，向量化实际返回的维度须在首次 upsert 前核对；§10.2 的 VARCHAR 字节长度须在向量化前预检。Milvus schema 仍保留写入约束。

#### 10.6.3 已存在集合的处理与验收

当前 `ensure_collection(clean=False)` 遇到已有集合仅取得集合对象，不会把旧 object_id 主键自动改成 entity_id，也不会自动增加本篇字段。上面代码用于新结构初始化，不意味着现有初始化函数已实现 schema 核验。

实施时只为 table_schema 开启严格核验：公共 `ensure_collection()` 增加可选参数 `validate_schema: bool = False`，table_schema 的 Web/API 与调试 CLI 经加载器传入 `True`。对已有集合按字段名集合比较，不按字段声明顺序比较；核对每个字段的类型、VARCHAR 上限、主键及配置向量维度，字段缺失、多出或定义不符均拒绝。结构不符时在 Embedding、索引补建、集合加载和对象数据写入前明确失败，不对共用集合自动 drop，也不删除记录。`metaweave/core/sql_rag/loader.py` 与 `metaweave/core/loaders/dim_value_loader.py` 的现有调用不传新参数，默认不做新增的严格校验，保留原有集合处理行为。（doc 25.2 更新：`metaweave/core/sql_rag/loader.py` 现传 `validate_schema=True`，`rag_load --type sql` 已移除、Web 发布替代。）本项不要求清理或调整它们已有集合的字段、顺序或额外字段。

旧的 table_schema 测试集合需另行初始化，不迁移旧数据；Web/API 发布和调试 CLI 加载均按 §10.3 先 upsert 本批记录，再清理当前源的非本批记录。首次创建新集合可以早于 Embedding；若向量化失败，空集合可以保留，下一次加载复用并重新核验。

验收应分别确认：首次初始化得到上述 11 字段和单一 entity_id 主键；重复初始化符合结构的集合不清空数据，字段顺序不同但定义相同不误报；table_schema 遇到旧结构时在 Embedding 前停止并提示；sql、dim_value 不因本次新增的校验而拒绝原本可用的集合（doc 25.2 更新：`metaweave/core/sql_rag/loader.py` 现传 `validate_schema=True`，`rag_load --type sql` 已移除、Web 发布替代。）；运行加载器定义与本节一致；首次创建后 Embedding 失败仅可能留下空集合。本次文档修改不连接 Milvus、不执行建集合或清理操作。

### 10.7 调试 CLI、`--clean` 与 `--type all`

`metaweave rag_load --type table_schema` 必须同时传 `--source_id <UUID>`、`--job_id <UUID>`，直接读取 `output/<source_id>/<job_id>/md` 和 `json`。缺参数、UUID 无效、目录或清单不可用时，在调用 Embedding 和写 Milvus 前报错。不再从全局 `output/md`、`output/json` 加载 table_schema。加载器内部的非受管 `_load_table_objects()` 分支可暂留供直接调试/测试，不作为这条 CLI 路径；不为它增加第二套校验。

CLI 复用 §1.2 的文件输入解析、清单及 JSON/MD 字段核对，保留配置中的 `include_columns`、`skip_empty_desc` 调试取值；**不读取平台库**，因此不检查数据源启用状态、Job 步骤状态、MD 清单运行标识是否等于平台库 JSON 步骤的 `updated_at`，也不核对平台库登记库名。MD 清单自身的运行标识格式、文件身份及两目录对象集合仍需校验。`job_id` 仅定位工作区，不代表 CLI 认可该 Job 可正式发布。Web/API 的完整准入保持 §11 的规则。

CLI 每次执行生成一个 UUID，作为 Milvus `publish_id` 字段中的**调试批次标记**；`entity_id` 仍为 `source_id + ":" + object_id`。它不调用 `backend.publishing.publish_service.publish_steps()`，不写 `publish_info`，不改变旧 current，也不要求安装 `platform` extra。CLI 成功只表示这次 Milvus 调试加载完成，不能当作 Web/API 发布成功。

CLI 与 Web/API 共用 §10.3 的 Milvus 替换步骤：先准备输入、在向量化前连接并创建/核对集合，再完成全部向量，按主键整行 upsert；全部成功后仅删除 `source_id == "<当前源 UUID>" and publish_id != "<本次调试批次 UUID>"` 的旧记录。table_schema 无论是否传 `--clean` 都执行这一按源替换；绝不调用 `Collection.drop()`。对应帮助文本和 CLI 警告应写明按当前 source_id 替换，不再提示清空整张集合；`--clean` 对 sql、dim_value、cql 的既有含义保持不变。（doc 25.2 更新：sql 类型已从 CLI 移除，该句对 sql 不再适用。）CLI 可能覆盖同源 Web/API 发布的向量内容，平台库 current 不会随之变化；以后需要正式结果时，由 Web/API 对该源重新发布。CLI 与 Web/API 同源并发不在本计划处理范围。

移除独立 CLI 的 `--type all` 选项值及四类连续加载功能；`rag_load` 仍要求显式指定一个具体 `--type`，传 `all` 在参数检查阶段拒绝。原来仅服务于 `all` 的 `--continue-on-error`、多类型展开、汇总与示例一并移除。`metaweave pipeline` 按 §10.8 整体移除，不为它增加 source_id/job_id 配置。实施完成时同步 `docs/data_gov/` 的现行文档，并按 §2 的例外更正根目录仍生效的命令说明；其他目录的历史文档不处理。

验收：无 UUID 参数、无效 UUID、产物缺失或清单不一致的 table_schema CLI，以及 `--type all`，均在加载前拒绝；CLI 不要求平台库连接或 `platform` extra，不检查 Job 状态，不写 `publish_info`；合法产物即使对应 Job 状态为 `failed`，仍可用于调试加载，结果不改变正式 current。两个源共用集合时，任一源的 CLI 加载及 `--clean` 均不删除另一源记录；CLI 写入 source_id 和仅用于 Milvus 的新调试批次 UUID，Web/API 后续正式发布会清掉同源调试记录；CLI 调试配置可仅加载表级对象。实施任务全部完成时，根目录 `AGENTS.md`、`CLAUDE.md`、`README.md` 均不再推荐已移除的命令。

## 11. 采集作业进入发布流程与发布项解禁

### 11.1 当前问题与两条入口

发布有两条入口：采集完成后继承当前 `source_id`、`job_id` 点击“下一步发布”；或者在新建发布作业时，从该源的采集作业列表选择一个 `job_id`。两条入口最终进入同一发布页，调用同一发布预检。

当前采集页 `CreateCollectionJobView.vue` 只要本次 `db` 或 `ddl` 任一步成功就显示入口，即使本次其他步骤失败也可能显示；纯 JSON/MD 成功则不会显示。`SelectPublishJobView.vue` 使用的采集作业列表没有作业总体状态，失败作业也会列出并可选。`CollectionJobsView.vue` 的逐作业“发布”链接同样只判断数据源是否启用。后台目前按所选发布步骤判断状态，作业中其他步骤失败时，成功步骤仍可能被发布。

### 11.2 作业级准入

`job_info` 的主键为 `(job_id, step_name)`：同一 Job 的每个步骤只有一行，重跑该步骤会更新这一行的 `last_status`，不为每次执行新增一行。表中没有 Job 总体状态列。当前 Web 采集支持并登记 `db`、`ddl`、`json`、`md` 四个步骤；本计划只读取该 `job_id` **现有全部步骤行的最新 `last_status` 并在查询时汇总**，不新增状态列或作业状态表，也不要求 Job 必须执行某一固定步骤。

所有现有步骤行均为 `success`，作业才允许进入 Web/API 发布流程；任一行为 `failed` 或 `running` 就禁止正式发布。检查范围包含本次请求未执行、但已在该 Job 下登记的旧步骤；不只看本次采集响应的 `results`。直接打开发布地址时，后台预检和正式发布接口都要核对 Job 状态，不能仅靠页面隐藏入口：预检仍返回 `200`，把所有发布项标为不可发布（供页面展示）：失败或运行中的步骤显示自身原因，其余发布项显示作业级原因；正式发布接口返回 HTTP `409 job_not_publishable`，所选步骤自身失败或运行中时同样如此。调试 CLI 不进入正式发布流程，不适用该作业状态门槛。不存在步骤行的作业沿用现有工作区不存在的错误处理。按本次确认的范围，**不处理步骤登记 `running` 前就失败、因而没有写入 `job_info` 的情况**；不为这类请求结果补写失败步骤行。

作业汇总状态与采集首页使用同一口径，在查询时计算，不另写一套优先级。对同一 `job_id` 的全部现有步骤行：任一行为 `running`，该 Job 即为 `running`；没有 `running` 且任一行为 `failed`，该 Job 为 `failed`；全部为 `success`，该 Job 才为 `success`。采集首页 `backend/jobs/home.py` 已按此实现，本次不改变首页优先级。

同一作业可以暂时同时有 `failed` 和 `running`。例如 `db` 已经失败，`ddl` 仍在执行：这段时间总状态是 `running`。`ddl` 结束后若已没有 `running`，且 `db` 仍是 `failed`，总状态改为 `failed`。某步写入 `running` 后进程中断、该行一直没有改成 `success` 或 `failed` 时，总状态保持 `running`，直到这一步被重新执行并写回最终状态。发布准入不随展示文字放宽：`running` 和 `failed` 都不能发布。

这项限制作用于该 Job 的全部发布项：例如 `db`、`ddl`、`json` 已成功，但同一 Job 的 `md` 失败或仍为 `running`，这些已成功步骤也不能从该 Job 发布；待失败或运行中的步骤更新为 `success` 后才可进入发布流程。只执行了 `db` 且其步骤行为 `success` 的 Job 不因缺少其他步骤而受阻。

- 采集页：本次请求完成后，按整个 Job 的最新状态决定是否显示“下一步发布”，不再以本次 `db/ddl` 成功作为条件。请求本身失败且无法取得有效 `job_id` 时，不显示入口。汇总为 `running` 或 `failed` 时不显示入口。
- 新建发布作业选择页：采集作业列表提供上述汇总状态；**`failed` 和 `running` 的 Job 都不出现在候选列表中**，只有汇总状态为 `success` 的 Job 可被选择。数据源禁用时沿用现有禁止发布规则。
- 采集首页与数据采集作业列表展示同一个汇总状态。仍有 `running` 时两页都显示运行中；没有 `running` 且有 `failed` 时两页都显示失败。作业列表中的逐行“发布”入口也遵守同一作业级准入；直接访问对应地址由后台再次核对。
- 后台共用作业状态检查用于发布预检和正式发布请求，两者对不合格 Job 的响应不同：预检不返回 HTTP 错误，仍为 `200`，所有发布项 `publishable=false`，失败或运行中的步骤 `reason` 为该步骤自身原因（如“最近一次采集失败”），其余发布项为作业级原因，以便页面逐项展示；正式发布请求开始时 Job 状态不满足（包括所选步骤自身 `failed`/`running`）则返回 `409 job_not_publishable`，该检查先于所选步骤是否有成功记录的判断；作业整体成功而所选步骤没有执行记录时仍为 `400 step_not_ready`；不创建发布 ID，不读取/替换 Milvus 数据。创建发布 ID 后，按现有逐项发布流程，在每项取得源行锁后再次核对整个 Job 的状态；若此时变为 `failed` 或 `running`，该项不执行数据替换，按逐项失败规则记录结果，已完成的其他发布项不回滚。

例如，已有 Job 只重跑 JSON，不同时执行 DDL、MD：若 JSON 步骤行更新为 `success`，且该 Job 其余现有步骤行也都是 `success`，就可进入发布流程；具体发布项仍按 §11.3 核对自己的产物。若 JSON 步骤行更新为 `failed` 或仍为 `running`，整个 Job 就不能发布。单独重跑其他步骤采用相同规则。

### 11.3 发布项级解禁

通过作业级准入后，各发布项分别按自己的依赖判断是否可勾选。`ddl` 核对同一作业的 DDL 步骤及 DDL 目录产物；`table_schema` 核对同一 `source_id/job_id` 的 JSON、MD 步骤成功、两目录各自的对象文件与清单、对象集合和运行标识一致。`table_schema` **不要求该 Job 存在 `db`、`ddl` 步骤，也不要求同时发布它们**。其他发布项沿用各自的既有依赖与预检规则。进入发布页不等于所有发布项均可勾选；页面继续显示每项的预检结果与不可发布原因。

### 11.4 修改落点与验收

- `backend/jobs/listing.py`、`backend/api/schemas.py`、`frontend/src/api/types.ts`：从 `job_info` 现有步骤行计算并返回作业汇总状态，不向数据库写总体状态。优先级与 `backend/jobs/home.py` 相同：`running` 优先，其次 `failed`，否则 `success`。采集作业列表响应项新增 `job_status`，取值 `success | failed | running`，采集作业列表、采集首页与两个入口共用该口径；新建发布选择页只列 `success` 的 Job，`failed` 与 `running` 都不显示。
- `frontend/src/views/CreateCollectionJobView.vue`、`SelectPublishJobView.vue`、`CollectionJobsView.vue`：调整两个入口及逐作业入口的准入；作业列表展示与采集首页相同的汇总状态。`CollectionHomeView.vue` 保持现有 running 优先展示，不改成失败优先。发布页仍使用现有逐项预检决定勾选状态。
- `backend/publishing/publish_service.py`：生成发布 ID 前检查整个 Job 状态；逐项取得源行锁后再次检查，状态不满足时该项按失败处理，不撤销已完成项；保留 `table_schema` 的 JSON、MD 步骤、目录、清单及运行标识校验，不改成仅凭目录非空放行。
- doc 20 与 doc 18 中旧的采集页入口说明已同步。

验收覆盖：

- **J01** 采集页入口不以本次是否执行 db/ddl 作为条件。
- **J02** 仅重跑 JSON 成功且该 Job 其余现有步骤均成功时，可以继续发布。
- **J03** 该 Job 任一现有步骤行为 `failed` 或 `running` 时，两条 WebUI 入口、逐作业入口及直接调用正式发布接口均不能发布；调试 CLI 不属于正式发布入口。
- **J03a** 失败或运行中 Job 的发布预检返回 `200`，所有发布项 `publishable=false`，失败/运行中的步骤带自身原因、其余带作业级原因；同一 Job 的正式发布请求（含所选步骤自身 `failed`/`running`）返回 `409 job_not_publishable`，不生成发布 ID；作业整体成功但所选步骤无执行记录时返回 `400 step_not_ready`。
- **J04** 同一 Job 仍有 `running` 时，采集首页与数据采集作业列表都显示运行中，即使已有 `failed` 步骤；已无 `running` 且存在 `failed` 时，两页都显示失败。新建发布作业的选择列表不显示 `failed` 与 `running` 的 Job。
- **J05** 作业整体成功但 JSON/MD 产物缺失或不一致时，`table_schema` 仍不可勾选。
- **J06** 作业状态只从 `job_info` 现有步骤行推导，不新增数据库列或登记前失败的补写逻辑。

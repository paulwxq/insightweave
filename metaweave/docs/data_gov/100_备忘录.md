## 1. 把 CHECK 与排他约束写入画像 JSON，并在 Web 数据字典中显示

对照 [19.2 Web 表画像数据字典与数据画像展示设计](19.2_Web表画像数据字典与数据画像展示设计.md) §3.3，对象详情页「数据字典」现有 11 列，列名和顺序与文档一致：字段序号、字段名、数据类型、字段注释、注释来源、可空、默认值、主键约束、外键约束与目标、唯一约束、字段参与的索引。

这 11 列不能代表一张表的全部字段约束。文档把「物理约束」限定为已发布 JSON `table_profile.physical_constraints` 中的主键、外键和唯一约束。「可空」「默认值」单独成列，不计入上部基本信息的「约束数」。「字段参与的索引」只显示索引；唯一索引标为「唯一索引」，不改写成唯一约束，也不再计入约束数。

当前采集与画像 JSON 没有 CHECK（`pg_constraint.contype = 'c'`）和排他约束（`contype = 'x'`）。页面因此无法显示它们。对象定义 SQL 的生成链路同样没有写出这两类约束。

后续要补上，范围是源库中能够明确归属的 CHECK 与排他约束：

1. 采集时从 `pg_constraint` 读取这两类约束。约束名和完整表达式用 `pg_get_constraintdef`，参与字段用 `conkey`。
2. 写入画像 JSON 的 `physical_constraints`，与主键、外键、唯一约束并列，不塞进索引或候选唯一列组。
3. 平台库入库、对象详情接口按字段投影后，在 Web 数据字典增加一列显示。字段能对上时，单元格写「约束名（CHECK 或排他；表达式）」。一条约束涉及多列时，每一列都显示同一条完整定义。
4. 已发布的旧画像没有该节点。重新采集并发布之前显示「未生成」；采集后确认没有才显示「无」。

不放进这一列的内容：

- `NOT NULL` 与默认值，继续用「可空」「默认值」。
- 唯一索引，继续留在「字段参与的索引」。
- 抽样得到的候选唯一列组，继续留在「数据画像」Tab，并标明是画像候选。
- 表达式对不上任何字段的约束，不强行归到某一行。

上部「约束数」目前只计主键、外键和唯一约束。CHECK 与排他约束是否计入，实施前单独决定。对象定义 SQL 是否同时生成这两类语句，不在本条范围内。

## 2. 发布步骤页展示各步骤的采集时间、JOB ID 与文件数量

在 Web「数据画像发布」页的「发布步骤」区域，每个步骤名称后展示该步骤对应采集结果的**最近一次运行时间、`job_id` 和产物文件数量**，供执行人在发布前核对采集批次与产物情况。

- `db`、`ddl`、`json` 分别展示同名采集步骤的信息；`table_schema` 对应 MD 采集结果，展示同一作业 MD 步骤的运行时间、`job_id` 和 MD 文件数量。后续增加发布步骤时，按其实际依赖的采集结果确定展示来源。
- 时间取对应采集步骤的 `job_info.updated_at`；成功步骤显示为最近一次采集完成时间，不使用作业列表合并后的 `executed_at`。`job_id` 取该步骤所属作业。
- 文件数量按对应采集结果目录中的实际产物文件统计，排除 `manifest.json`、子目录和无关文件。没有对应采集结果或文件无法核实时显示「不可用」，不要把未知数显示为 0。
- 发布预检响应需提供逐步骤展示所需的数据；页面进入时读取，并在点击发布前的既有重新预检中刷新。验收时覆盖步骤重跑、文件缺失和仅有部分步骤产物的情况。

## 3. 采集步骤的 job_id、依赖阻断与失败落库

采集作业按步骤各写一行 `job_info`，主键是 `(job_id, step_name)`。平台库没有单独的作业表，不在点击执行时先插入一行空作业。继续沿用现在的编号分配方式。

新建且请求不带 `job_id` 时，只有 `db`、`ddl` 在检查之前调用 `uuid4()`。这个值要等该步骤执行到 `start_step` 才写入 `job_info`；检查未通过就抛错，编号不留下。`json`、`md` 不调用 `uuid4()`，没有 `job_id` 时直接失败：json 要求同一作业已有 DDL，md 要求同一作业已有 JSON。规划中的 domain 同样不生成编号，没有 `job_id` 时直接失败，因为它要读同一作业的 MD。因此新建作业的第一个步骤只能是 `db` 或 `ddl`。只勾 json、md 或 domain 时，新目录里没有它们要读的文件；给它们补上 `uuid4()` 也只得到一个空编号，步骤仍然无法完成。

重跑时请求带已有 `job_id`。`db`、`ddl`、`json`、`md` 都使用这一个，不再生成新编号；domain 接入后也这样。已有作业上可以只跑一个步骤：json 只读该作业的 DDL，md 只读该作业的 JSON，domain 只读该作业的 MD。这些文件已经在时，不必同时再勾 db 或 ddl。

一个步骤失败后，本次请求里依赖它的步骤都不再执行，并在已有 `job_id` 时直接写成 `failed`。不要先写 `running`，也不要只在本次接口结果里标失败、表里却没有这一行。当前不是这样：步骤在调用自己的 `start_step` 之前失败时只抛错，不写 `job_info`；同一次请求里上游已失败时，后继步骤被阻断，同样不写行。于是前面的步骤已经成功、后面的步骤在 `start_step` 前失败时，表里只有那些成功行，作业汇总仍是成功，发布入口仍会打开。

依赖按下表。左列失败时，右列里**本次也选中**的步骤不执行。

| 步骤 | 它依赖的上游 |
|---|---|
| db | 无 |
| ddl | 无 |
| json | 本次选了 ddl 时，依赖 ddl |
| md | 本次选了 json 时，依赖 json；本次没选 json 但选了 ddl 时，依赖 ddl |
| domain | 本次选了 md 时，依赖 md。domain 尚未接入采集作业，接入后走同一规则 |

失败后的记录规则：

1. 本次请求的第一个步骤失败，并且还没有任何 `job_info` 行、因此还没有作业：结束整个请求，不分配 `job_id`，后面的步骤不执行，也不写行。新建时 json、md、domain 作为第一个步骤即属此种。
2. 已经有 `job_id`（本次前面的步骤已创建作业，或请求带了已有作业）时，该步骤即使在调用 `start_step` 之前失败并返回，也写入本步骤的 `failed` 行。依赖它且本次选中的步骤不执行，各自直接写入 `failed` 行。
3. 步骤已经 `start_step` 之后的生成失败，维持现有做法：该行记为 `failed`。它的后继步骤仍按上一条处理，不继续执行。
4. `start_step` 登记过程中的其他异常（平台库写入失败等）不在 Domain 接入时单独处理。md 现在把这类异常收成「作业状态登记失败（类型）」并带上 `job_id`（`md_step_service.py` 会话 2 的通用异常兜底）。若提交已经成功、收尾又失败，该行会停在 `running`。domain 接入时不复制这套兜底；dim_config（doc 22.1）同样有意不复制。与上面的失败落库一起，等 Domain 接入完成后再统一处理 db、ddl、json、md、domain、dim_config（doc 23.1 后 rel 同样沿用此口径）。

## 4. 统一处理删除数据源时的关联数据

21.2 计划新增 `table_domain`，且不建外键。现有删源流程的 `purge_source_profiles`（`backend/data_sources/repository.py`）尚未包含这张表；若直接沿用该流程，删除数据源后会留下对应 `source_id` 的 Domain 映射。

删除数据源涉及多类关联数据，应在后续专门梳理删源流程时，统一盘点并确定清理范围和事务处理方式，届时把 `table_domain` 纳入处理。本阶段的 21.2 Domain 发布不修改删源流程；具体清理策略留待后续设计，不在此处预先决定。

## 5. Domain 生成要校验是否覆盖全部输入表

21.2 发布只拒绝不在同一作业 MD 产物中的表名。YAML 里没出现的真表这次没有 domain 行，发布不因此失败。

生成侧现在也没有这项校验。`domain_generator.py` 的提示词要求每个输入表至少出现在一个 domain 的 `tables` 里，但 `_normalize_domains` 只做类型和空白处理，不对照 MD 文件名，也不检查遗漏。摘要默认最多送给模型 100 个 MD 文件，模型没看到的表不可能被分进去。

后续要在 Domain 生成成功校验里补上：同一作业 MD 目录中的普通 `.md` 文件，其文件名（不含扩展名）都必须至少出现在产物的一张表映射里。漏表时生成失败，不把不完整 YAML 写成成功产物。不要把这项检查放到发布时用来阻止替换。摘要条数上限是否同时调整，实施时再定。

## 6. Milvus dim_value_embeddings 集合结构变更（doc 22.2）

[22.2 Web 发布 DimValue 到 Milvus 设计](22.2_Web发布DimValue到Milvus设计.md) §4 已拍板该集合的结构与写入语义变更，实施后生效。记录于此，供后续所有读写该集合的代码对照：

| 字段 | 旧结构（现状） | 新结构（doc 22.2，随设计修订同步） |
|---|---|---|
| 主键 | `id` INT64 auto_id | `col_id` VARCHAR(2048) 显式主键，= `source_id:table_name:col_name:col_value` 四段拼接（四段最坏合计 1317 UTF-8 字节） |
| `source_id` | 无 | VARCHAR(36) 新增 |
| `publish_id` | 无 | VARCHAR(36) 新增 |
| `table_name` | VARCHAR(128)，三段式 `库名.schema.表名` | **上限调为 VARCHAR(256)**：PG 单标识符最坏 63 字节，三段+2 点 = 191 字节，128 装不下（Milvus `max_length` 按 UTF-8 字节数计） |
| `col_name` | VARCHAR(128) | 不变（最坏 63 字节） |
| `col_value` | VARCHAR(1024) | 不变；写入前按 **UTF-8 字节硬边界 1024** 无条件安全截断（不撕裂多字节字符，超限记 warning 后继续），与 `truncate_long_text`/`max_text_length` 配置解耦 |
| 向量字段 | `embedding` FLOAT_VECTOR(1024) | 改名 `col_value_embedding`，类型与索引（HNSW/COSINE/M=16/efConstruction=200，索引字段名经 `ensure_collection(index_field_name=...)` 传入）不变 |
| 时间戳 | `update_ts` INT64 | 改名 `updated_at`，类型不变 |

写入语义同步变化：`insert` 追加（无替换）→ 显式主键 `upsert` + 全部成功后按 `source_id == 本源 and publish_id != 本次` 表达式删除旧记录（按源整份替换，同 table_schema 模式）；任一批失败（向量化失败/缺向量/写入未确认）记 `failed` 且**不删旧记录**，已写入部分凭相同 `col_id` 重跑幂等补齐。已知边界：两个不同原始值前 1024 字节相同时截断合并为一条（`col_id` 相同）。

连带影响：

- 旧结构集合与新结构不兼容，Milvus 不支持 alter；开发环境若存在旧集合（跑过 `rag_load --type dim_value` 的机器）需手动删除，首次 Web 发布按新结构自动创建。
- 现有检索代码不受改名影响（已核实 `tests/test_dim_value_search.py` 的 `output_fields` 只取 `table_name`/`col_name`/`col_value` 三个未改名字段）；后续新检索代码应使用新字段名。
- `metaweave rag_load --type dim_value` CLI 入口随 doc 22.2 移除，脚本逐渐退化，不为可用性背书。

## 8. Neo4j 多源共存与实例级互斥（doc 23.2）

Web rel 发布采用整库清空重载（`MATCH (n) DETACH DELETE n`），Table 节点已带 `source_id`/`publish_id` 溯源属性。两个边界显式接受：清库后加载中断留半图（MERGE 幂等，重跑发布即愈）；源行锁按 source_id 互斥、跨源不互斥——多源同时发布会在同一 Neo4j 上交替全删重写，当前以单源发布纪律约束。多源共存需求出现时再议：按源替换（换清理策略为按源表达式删除 + 写入侧去全清）与实例级发布互斥（单写者/发布队列）同在该时点一并处理。

## 9. 允许跳过采集失败的步骤，发布同作业中成功的步骤

现状：采集页仅在整个作业汇总状态为 `success` 时显示进入发布的按钮；独立发布页的预检和正式发布也要求同一 `job_id` 下所有已有步骤行均为 `success`。因此，只要某一步骤（包括将来接入的 SQL）写入 `failed`，该作业其他已成功的步骤目前也不能发布。独立发布页取消勾选失败步骤不能绕过服务端的作业级准入；采集页取消步骤勾选只改变下一次执行的步骤，不会改变已有 `job_info` 行的状态。

后续改造目标：

1. **作业采集页**：点击「执行作业」后，在每个已执行步骤名称后显示本次执行状态（成功或失败）；未勾选且未执行的步骤不显示状态。有勾选的步骤执行失败时，页面下方的「下一步：执行画像发布」按钮显示为灰色且不可点击。执行人取消勾选失败步骤后，只要当前勾选的步骤均已成功（且至少勾选一个可发布步骤），该按钮即可点击。失败状态仍如实显示，不因取消勾选而改写 `job_info`。
2. **画像发布页**：即使所选 `job_id` 下存在执行失败的步骤，只要本次勾选的发布步骤对应的采集结果成功、产物就绪且满足各自前置条件，就允许发布；未勾选的失败步骤不阻断本次发布。

发布预检与正式发布应按实际勾选的发布步骤校验，并在执行前复查状态和产物。仅修改前端按钮或复选框不能实现上述目标；采集页入口、独立发布页预检、服务端准入与相关测试需在后续同一改造中一起调整。

本条只记录后续需求，当前不修改发布规则；SQL 采集设计仍遵循现有作业级准入。

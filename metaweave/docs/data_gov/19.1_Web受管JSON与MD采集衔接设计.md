# 19.1. Web 受管 JSON 与 MD 采集衔接设计

状态：设计稿，待实施。日期：2026-10-03。

## 1. 目标与实际起点

在 Web「数据采集与画像」的「b.) 对表进行抽样画像」中，让 `ddl`、`json`、`md` 都可选择，并把本次作业的文件分别放在：

```text
output/<source_id>/<job_id>/ddl/
output/<source_id>/<job_id>/json/
output/<source_id>/<job_id>/md/
```

**当前代码已完成受管 JSON。** `CreateCollectionJobView.vue` 已将 `json` 设为可选；`backend/jobs/collection_run.py` 已接受并调度它；`backend/data_sources/json_step_service.py` 已把产物写到同作业 `json/`、校验 v3 与 DDL 对象集合、写 `manifest.json`，并登记 `job_info.json`。因此本篇不是重做 doc 18 的 JSON 采集，主要增量是**受管 MD、`ddl → json → md` 编排和页面说明**。实施时先对现有 JSON 链做回归核对，再补 MD。

`metaweave metadata --step md` 已能从 JSON 文件生成 Markdown，且生成过程不访问源 PostgreSQL。Web 适配应复用 `MetadataGenerator.generate(step="md")` 与 `JsonLoader`，增加的是数据源登记、同作业输入边界、作业状态、输出核验和 Web 调度；不要复制一套 Markdown 渲染器。本文仅覆盖采集，不启用 Web `json` 发布或 `table_schema` 发布。发布步骤与采集步骤不一一同名：后续 `table_schema` 加载会消费 MD 和同名 JSON，参见 [doc 19](19_采集与发布步骤完整展示设计.md)。

## 3. 作业、目录与配置

Web 继续使用 `POST /api/data-sources/{source_id}/collection-jobs`，请求 `steps` 可包含 `md`，响应仍是同一 `job_id` 加逐步 `results`。服务端先去重，再调整所选步骤的相对次序：同选 DDL 与 JSON 时 DDL 在前；同选 JSON 与 MD 时 JSON 在前；**同选 DDL 与 MD 且未选 JSON 时也先执行 DDL**，无论是否还选了 `db`；三者都选中时为 `ddl → json → md`。`db` 不建立新的依赖，不为了排序改变其已有独立语义。前端列表顺序与执行顺序一致，但服务端不能信任前端顺序。DDL 先于 MD 只是同请求排序，**不把 MD 的输入依赖改回 DDL**：未同选 JSON 时，MD 只消费该作业已成功的 JSON；本次 DDL 成功不会刷新旧 JSON，用户如需基于本次 DDL 得到 MD，应同时选择 JSON。勾选 MD 而未勾选 JSON 时页面须提示同作业 JSON 依赖；若同时选了 DDL，还须说明 MD 使用的是既有 JSON，不能暗示它基于本次 DDL。

编排层要同时记住**本次请求已执行步骤的结果**，包含生成失败、准备失败和平台库不可用：本次选了 DDL 且 DDL 失败，则本次 JSON 不启动；本次选了 JSON 且 JSON 失败，则本次 MD 不启动；同选 DDL 与 MD 且未选 JSON 时，如果本次 DDL 失败，MD 也不启动（包括 `db+ddl+md`）。已有步骤结果可返回时，后继步骤在响应中记为失败，分别提示“本次请求的 DDL 未成功，JSON 未启动；如需使用已有 DDL 产物，请单独重跑 JSON”“本次请求的 JSON 未成功，MD 未启动；如需使用已有 JSON 产物，请单独重跑 MD”；后一种同选 DDL 与 MD、未选 JSON 的情况提示“本次请求的 DDL 未成功，MD 未启动；如需使用已有 JSON 产物，请单独重跑 MD”。不登记被阻断步骤的 `running`，不清理其旧目录。若首步准备失败且没有可返回的 `job_id`，沿用现有整份请求的受控错误出口，不伪造后继步骤结果。不能只查 `job_info` 的最近状态：准备失败可能未改写旧的 `success` 行，若随后读取旧文件，就会把上一轮产物误当成本轮输入。未在本次请求选择的上游步骤，才由各步骤准备链检查同作业已有的成功产物。

受管 MD **必须复用已存在的 `job_id`**。新建请求勾选 MD 而未勾选 JSON 时，若 MD 是首个执行步骤且未传 `job_id`，则准备阶段返回“同一作业的 JSON 产物未就绪；请先执行 JSON 或指定已有 job_id”，不新建空作业；若先执行了 `db`（如 `db+md`）或 DDL，MD 仍因同作业 JSON 未就绪而失败，但保留已执行步骤的部分结果。不新建 MD 状态行或 MD 目录。这里“指定已有 job_id”仅指该作业的 JSON 已成功且通过 §4 的前置检查，不能绕过 JSON 依赖。已有作业可只补跑 MD，无须同时重跑 DDL/JSON，但必须通过 §4 的 JSON 前置。新建请求 `ddl+json+md` 则由 DDL 创建 `job_id`，后两步沿用它。同选 DDL 与 MD 而未选 JSON 时不自动补跑 JSON；MD 按依赖未就绪失败。若前面已有步骤成功，沿用现有逐步返回的部分结果语义。

在 `ddl_step_service.py` 从现有 `build_managed_ddl_config()` 抽出纯函数 `build_managed_output_snapshot(main_config, source_id, job_uuid, db_name, selected_schemas)`：只接收工作区所需的登记源标量字段，不接收带密码密文的 `source` 行或解密密码。`job_uuid` 必须保留，用于定位同一作业的目录；深拷贝主配置后以 `db_name`、`selected_schemas` 覆盖 `database.database`、`database.schemas`，并把 `output.output_dir`、`ddl_directory`、`json_directory`、`markdown_directory` 全部指向同一作业工作区。三个目录分别经受管 resolver 验证；不从全局 `output/json` 或别的 `job_id` 兜底。公共函数显式将快照中的 `database.host/port/user/password/sslmode` 置为 `None`，不保留主配置中的全局连接值；现有 `DatabaseConnector` 在缺少 `database/user/password` 时会在建连前拒绝。原 `build_managed_ddl_config()` 调用公共函数后，再用登记源的 `host/port/database/user/password/sslmode` 及 `selected_schemas` 覆盖连接和范围参数，现有 DDL 和 JSON 调用方继续使用它；其中 `password` 是原调用方传入的解密值。MD 只向公共函数传入 `source_id`、`db_name`、`selected_schemas` 和 `job_uuid`，不解密源库密码、不创建源库连接；它仍需访问**平台库**，以核对登记源、作业归属和 `job_info`。构建快照不改写主配置文件，也不影响独立 CLI/pipeline。

MD 文件名沿用格式化器的 `<db>.<schema>.<object>.md`，输出 `md/manifest.json` 与产物同目录。受管重跑只清理本作业 `md/` 顶层文件（含旧清单），不清理 DDL、JSON、其他作业或全局目录。目录和文件均拒绝符号链接、越界和非普通文件；不递归删除子目录。

实现同请求阻断时，直接扫描本次内存 `results` 列表中的上游 `step/status` 条目。现有列表已承载步骤返回的成功/失败，以及有前序结果时捕获的 `DbStepConfigError`、`PlatformUnavailableError`；首步错误直接终止整份请求，不存在后继判定。不得为判断**本次**上游是否成功而重新查询 `job_info` 的历史状态。

## 4. MD 的 JSON 前置与并发边界

**输入前置和已识别的生成器构造期配置错误，都在 `start_step(md)` 和清理旧 MD 前完成校验。** 这保证可在构造期确定的配置错误不会先清掉旧 MD；生成过程中的文件 I/O、对象映射等运行期错误仍按 §5 的失败路径处理。至少校验：

1. 数据源存在、启用且类型为 PostgreSQL；`job_id` 属于该 `source_id`；登记库名和已选 schema 合法。MD 不检查源库连接是否在线。
2. 同一作业的 `job_info(json).last_status='success'`；`json/manifest.json` 是可读的普通文件，`files` 是非空且无重复的 JSON 文件名列表。清单与 `json/` 顶层全部 `.json` 画像文件严格一致，清单本身不算画像文件；缺件、多件、符号链接、非普通文件均拒绝。
3. 用现有 `JsonLoader` 对清单中的 JSON 做 v3、库名、schema、对象名和对象类型校验。当前登记库名必须与 JSON 身份一致；每个输入对象的 schema 必须在登记源当前 `selected_schemas` 中，对象类型必须在快照当前 `database.include_object_types` 中，且对象名不能命中当前 `database.exclude_tables`。读取这些范围配置前先检查 `database` 为对象（主配置缺省或 `null` 由受管快照规范化为空对象），`database.exclude_tables` 若存在必须为列表；`null`、字符串等非列表值按 `DbStepConfigError` 拒绝，不能静默当成空列表：生成器遍历 `null` 会抛 `TypeError`，遍历字符串则会逐字符解释，均不应视为合法配置。对象类型配置在准备阶段用现有 `normalize_database_object_types()` 规范化，配置非法同样受控拒绝；`include_object_types: null` 已由该函数给出 `ValueError`，无需另建规则。后两项与生成器 `_get_tables_to_process()` 的筛选语义保持一致，尤其 `exclude_tables` 的精确匹配、末尾 `*` 前缀匹配及可选 schema 前缀规则；**包含两个及以上点的三段式/多段式模式沿用现有“记 warning 后忽略”规则，不得在 MD 前置中改成配置错误**。将纯筛选规则提取为共享函数供生成器与受管 MD 前置共用，不实例化会建目录的生成器。若登记范围或主配置收窄，导致任一既有 JSON 对象不再属于当前范围，则在 `start_step(md)` 与清理前按 `DbStepConfigError` 受控拒绝，提示“现有 JSON 画像与当前采集范围不一致；请按当前范围重跑 DDL、JSON 后再运行 MD”。范围扩大后是否有新增对象，离线 MD 无法仅凭旧 JSON 判断；本次仍以完整通过清单校验的 JSON 对象集合为准，不声称与源库实时对象集合一致。不能只凭目录存在或“至少一个 JSON 文件”放行，也不能静默忽略其他库名前缀的杂入文件。
4. 解析本次 JSON 步骤 `updated_at` 作为运行标识。取源行锁并复查 JSON 状态与标识不变后，才登记 MD 为 `running`。锁下复查与 `start_step(session, ..., 'md')` 必须使用**同一个 `platform_session` 的同一事务**；`start_step()` 内部 `commit()` 才释放源行锁，不得在复查与登记之间另开会话。生成后在提交 MD 终态前再次锁下复查；JSON 在 MD 运行期间重跑则本次 MD 判失败，清单不能作为有效产物凭据。生成期间不持续持有平台库事务。事务边界与 [doc 18 §4](18_Web受管JSON画像采集设计.md) 的 JSON 链一致。
5. 构造无凭据快照前先确认主配置的 `output` 为对象（缺省或 `null` 视为空对象）；构造后再对 `ddl_options`、`ddl_options.sample_records`、`markdown_options` 做对象类型校验（缺省或 `null` 同样视为空对象），然后调用 `MetadataGenerationConfig.from_config(snapshot)` 和 `validate_output_numeric_options(snapshot["output"])`。后者与 `OutputFormatter` 构造期共用同一规则，包含 `output.ddl_options.sample_records.count` 和 `output.markdown_options.sample_value_count`。还须在清理前覆盖 `MetadataGenerator._init_components()` 的其余构造期解析：`logical_key_detection` 必须为对象，启用时按 `LogicalKeyDetector` 的现有接受语义预检；`sampling` 必须为对象，其 `column_statistics` 以及画像解析会访问的 `identifier_detection`、`description_detection` 等子节点不得在使用 `.get()` 时为 `null` 或非对象；`column_profiling`、`table_profiling` 及其规则子节点也须覆盖 `MetadataProfiler` 的配置解析和正则编译。可在准备链复用不创建目录、不连接数据库的 `MetadataProfiler(snapshot)`、按需构造 `LogicalKeyDetector`，或抽出与生成器共用的无副作用校验函数；不能另写一套会漂移的判定规则，也不能为预检实例化会创建目录的 `MetadataGenerator` / `OutputFormatter`。例如 `sampling: null`、`sampling: "abc"`、`logical_key_detection: null` 或 `sample_value_count: "abc"`，均按 `DbStepConfigError` 受控拒绝，不新增或改写 MD 步骤行、不清理旧 MD；类型、正则及数值等配置解析异常不得漏出原始 `AttributeError`，错误摘要只给配置位置和类别，不回显可能敏感的配置原文。本篇不调用更宽的 `validate_output_options()`：它还验证 MD 不使用的 `output.json_options`，会比当前 MD 生成器入口额外收紧配置接受范围。

目录完整性、结构校验和身份核对可封装为只读的 `read_managed_json_input(source_id, job_id, database_name)`；`json_step_service.py` 已有的 v3 与对象集合校验应尽量复用，不再发明第二套 JSON schema。清单失效、作业归属错误或 JSON 状态非成功属于受控准备错误，不能报成平台库 503；准备失败不改写既有 MD 目录或 MD 步骤行。同请求中的 JSON 若已失败，由 §3 的编排层直接阻止 MD，不能依赖准备链从旧 `job_info` 推断本次结果。

§4 第 4 项的首尾锁下复查不形成生成期间的文件快照：MD 正在读取 `json/` 时，JSON 可以重跑并清理、重写该目录。MD 若读到缺件或新旧混合文件，本次按生成或核验失败处理；即使文件读取没有直接报错，提交 MD 终态前仍须验证 JSON 为 `success` 且运行标识未变，阻止混合输入成为成功清单。不为此增加跨步骤文件锁，也不承诺读取一致的中间快照。

§4 第 5 项默认直接复用真实的 `MetadataProfiler(snapshot)` 构造，并在 `logical_key_detection.enabled` 为真时按生成器同一分支构造 `LogicalKeyDetector`；两者当前均不创建文件或连接数据库。必要的节点类型检查先于构造，异常按受控配置错误收敛。只有未来构造出现副作用时，才抽取供生成器与准备链共同调用的纯校验函数，避免维护两套规则。

`job_info` 记录“该步骤最近一次运行结果”，不是跨步骤依赖版本。MD 成功清单的字段固定为 `{"files": ["<db>.<schema>.<object>.md"], "source_json_updated_at": "<UTC ISO 8601，六位小数、Z 结尾>"}`；`files` 可列多个文件，`source_json_updated_at` 保存准备阶段记录的 JSON `job_info.updated_at` 运行标识，由共用后端格式化函数输出 UTC 六位小数、`Z` 结尾文本（doc 19.3 §3）。后续读取方按这个固定键名与当前 JSON 步骤运行标识比较。JSON 此后重跑时，旧 MD 文件和历史状态可以保留，但其清单标识与当前 JSON 不符，**不得作为后续 `table_schema` 发布的有效输入**。本篇不接入该发布，只保存验证所需的来源信息。

实施时按一条通用规则处理准备链：凡准备链**自身或调用的校验器**会读取、遍历的配置节点，都要先确认其类型符合当前生成器语义；非法类型抛带配置路径的 `ValueError`，由受管服务转为 `DbStepConfigError`，不让 `AttributeError` / `TypeError` 冒充平台库故障。至少覆盖 `database`（对象；主配置缺省或 `null` 由受管快照规范化）、`database.exclude_tables`（缺省可视为空列表，显式非列表必须拒绝）、顶层 `sampling`，以及 `output.ddl_options`、`output.ddl_options.sample_records`、`output.markdown_options`；`output.json_options` 已由 `validate_json_output_options()` 做对象检查。`database.exclude_tables` 是 JSON 和 MD 生成器共用的筛选配置：把其列表类型检查抽成无副作用的共享入口，**受管 JSON 与 MD 准备链都调用**，在各自 `start_step` 与清理旧目录前受控拒绝 `null`、字符串等非列表值；MD 的对象范围预检随后复用生成器的匹配规则，不能另写类型或匹配语义。当前 JSON 若让 `exclude_tables: null` 进入生成阶段，会在遍历时抛 `TypeError` 并留下 `failed`，虽非平台库 503，仍应提前拒绝以保留旧 JSON 产物。缺省/`null` 是否容忍，沿用对应步骤原有构造与校验语义，不借此收紧 JSON 的其他空值行为。当前 JSON 准备链的 `validate_json_sampling_method(snapshot.get("sampling", {}) or {})` 遇到 `sampling: "abc"` 会抛裸 `AttributeError`；`sample_records: "abc"` 等非对象输出节点也会如此，随后均误报“平台库连接或读取失败”并可能变成 503。修复应同时覆盖 `validate_json_sampling_method()` 与 `validate_output_numeric_options()` 的入口，使 JSON 在 `start_step(json)` 和清理旧 JSON 前受控拒绝；MD 复用相同的输出节点规则，并按自身生成器构造语义拒绝非法 `sampling`。不要仅扩大 JSON 服务的 `except AttributeError` / `except TypeError` 范围，以免掩盖其他程序或平台错误。~~此项仍待 doc 19.1 审核通过后实施。~~（已于 2026-10-03 随本文实施：共享校验器入口对象/列表检查落于 `validate_json_sampling_method()` / `validate_output_numeric_options()` / `validate_exclude_tables()`，`database`/`output` 非对象由 `build_managed_output_snapshot()` 拒绝；受管 DDL 准备链同步接入 `exclude_tables` 检查，三链口径一致。）

## 5. MD 执行与成功条件

准备链通过后，以与 JSON/DDL 相同的方式登记 `job_info(job_id, 'md')=running`，清理本次 MD 目录，调用已存在的 `MetadataGenerator(config_path, config=snapshot).generate(step='md', max_workers=4)`。MD 的输入只能是同作业 JSON 快照，输出只能是同作业 MD 目录。生成器内部仍按既有规则处理普通表、视图和物化视图，不增加源库查询、LLM 调用或格式分叉。`backend/jobs/collection_run.py` 的两处不支持步骤提示须同步改为“当前仅支持 db、ddl、json、md 步骤”，对应 API 断言一并更新。

只有同时满足以下条件才标 `success` 并写入原子化 `md/manifest.json`：

- `GenerationResult.success=True`、`failed_tables=0`、成功对象数大于零；报告的 `result.output_files` 中 `.md` 路径无重复、数量与成功对象数一致，所有报告路径和磁盘实际 `.md` 文件集合完全相同且位于本次目录。逐对象核验直接使用这些**生成器声明的实际路径**，不得另按命名模板拼接一份期望路径。
- MD 文件均为非空、UTF-8、普通文件，文件名严格为当前库的三段式；MD 文件 stem 集合必须与已验证的同作业 JSON 清单 stem 集合精确一致。`result.output_files` 目前仅含路径、不含对象 ID，故从每个已校验路径的三段式文件名还原 `(schema, object_name)`，与 JSON 清单的对象键建立一对一映射；重复或未匹配均失败。**三段式 stem 解析抽为共享函数**，供 `JsonLoader._database_files()` 与 MD 核验共用，沿用现有 `stem.split(".")` 且恰好三段、每段非空的规则；库名前缀筛选和 `.json` / `.md` 扩展名检查仍由各调用方完成，不因抽取改变 `JsonLoader` 忽略其他库文件的行为。**主核验方式为重渲染后逐字节比对**：对每个映射到的 JSON 对象，通过本轮生成器所用 `JsonLoader` 的缓存限定只读接口还原元数据，缓存未命中即核验失败，**不得调用现有 `load_object()` 的读盘回退来补齐缓存**。按生成侧相同顺序设置 `metadata.database=db_name`，有 `sample_records` 时构造 `pd.DataFrame(metadata.sample_records)`，然后将 `metadata.column_profiles={}`、`candidate_logical_primary_keys=[]`、`table_profile=None`，使用本轮生成器的同一个 `OutputFormatter.generate_markdown(metadata, sample_data)` 得到期望文本。按当前 `save_text()` 的 UTF-8 写盘方式编码期望文本，与该对象在 `result.output_files` 中声明的实际 MD 路径的原始字节**完全相等**才通过；不另建格式化器，也不另写标题、字段和补充说明的解析规则。普通表、视图和物化视图采用同一流程。这样标题身份、对象类型及可选注释后缀、字段顺序与数量、补充说明、段落边界及额外文本都由同一渲染函数统一核对；不能只用 `MDParser` 的前缀匹配或字段名字典放行。配置中的对象类型或排除范围发生变化时，不得把少量 MD 当作完整本轮结果。
- 最终 JSON 步骤仍为 `success` 且运行标识未变；清单写入成功，`finish_step(md, success)` 成功。

当前格式化器会原样拼入样例值里的换行及其他 Markdown 特殊文本。只要实际文件与同一 JSON、同一配置重渲染的期望字节相同，合法样例值导致的多行文本也应通过；任何额外插入、删减或改写的文本均失败。不得为了核验通过而只在 Web 受管侧改写样例值，也不在本篇修改独立 CLI 的渲染规则。`generate_markdown()` 当前不读取时间或随机值，因此同一内存输入和配置可确定地复现写盘内容；**未来若格式化器引入时间戳、随机值等非确定输出，必须同步调整受管 MD 的核验策略与回归测试**，不能继续假设重渲染结果逐字节相同。核验必须复用本轮生成器已枚举的 JSON 内存文档；`JsonLoader.load_object()` 在缓存未命中时会回退读盘，故缓存限定接口必须在映射前检查命中，不能让核验在 JSON 并发重跑后读取另一版本并造成误判。本轮 JSON 运行标识仍按 §4 在终态锁下复查，标识变化即失败。

最终 JSON 标识的锁下复查、写入原子化 MD 清单和 `finish_step(session, ..., 'md', success)` 必须使用**同一个 `platform_session` 的同一事务**；`finish_step()` 内部 `commit()` 提交状态并释放源行锁，不得复查后先提交、再另开会话写清单或状态。清单写入失败要在该事务中改走 `finish_step(..., failed)`，不能因写文件异常直接退出而让 `job_info(md)` 停在 `running`；生成、核验或 JSON 标识复查失败也要尽力写回 `failed`，且不得留下有效清单。若状态提交失败，立即删除本次新清单，并在响应中说明需要核对作业状态。文件系统和平台库不是同一个事务，后续消费者必须同时检查 MD 清单与 `job_info(md)=success`；这里沿用 [doc 18 §4](18_Web受管JSON画像采集设计.md) 已实施的 JSON 事务约束。错误响应与日志不写 JSON 样例值、完整 Markdown 内容、源库密码或可能包含这些内容的原始异常文本。

## 6. Web 页面与发布边界

「b.) 对表进行抽样画像」保持完整展示 `ddl/json/md`：三项都可勾选、分组全选和重跑回填可包含 MD。**勾选 MD 且未勾选 JSON** 时均显示同作业 JSON 依赖提示，包括新作业的 `md`、`db+md`、`ddl+md`、`db+ddl+md`，但不在前端阻断；由服务端准备链给出最终结果。复用已有 `job_id` 时可单独选 MD；若还同选 DDL 却未选 JSON，额外提示 MD 只能读取既有 JSON，本次 DDL 不会更新它。结果区和作业列表显示 MD 的 `success/failed`，这是最近一次**执行状态**：JSON 此后重跑时，旧 MD 行仍可能显示 `success`，不能据此认定 MD 当前有效；后续 `table_schema` 发布预检须比较 MD 清单中的 `source_json_updated_at` 与当前 JSON 步骤运行标识（当前标识须用同一格式化函数生成的文本比较，不得与旧格式逐字比较，doc 19.3），并同时检查清单和步骤状态。本篇不要求采集页面新增发布就绪状态，也不把旧 `success` 自动改写为失败。**MD 成功不意味着 Web 已能发布 `table_schema`**；现有“下一步发布”入口的显示条件已由 doc 20.1 §11 改为按整个作业的汇总状态判断（原“仅依据 `db/ddl`”不再适用）；发布页白名单不因本篇放宽。

遵循 doc 19 的完整可见原则：`domains`、`dim-config`、`rel`、`cql`、`sql-rag` 仍显示为不可选；启用 MD 不删除、折叠或过滤其他步骤。UI 应说明 JSON 已接入、MD 本次接入，以及 `md` 依赖同作业 JSON。Web 采集的 `json/`、`md/` 与目前 CLI `rag_load --type table_schema` 默认读取的全局 `output/json`、`output/md` 是两套输入位置；本篇不把受管文件自动加载到 Milvus。

## 8. 验收场景

1. Web 同请求选择 `ddl+json+md`，三步复用一个 `job_id`，依次产出三个受管目录与各自清单；`job_info` 有三条成功步骤行。任一本次上游失败，后继步骤不启动；即使平台库里仍有上一次的 `success` 行，被阻断的步骤也不读取旧产物。同选 DDL 与 MD 而未选 JSON 时，包括 `db+ddl+md`，无论请求顺序如何都先执行 DDL；DDL 失败则 MD 不启动，DDL 成功而既有 JSON 有效时 MD 可运行，但页面和结果均说明它读取既有 JSON、并未基于本次 DDL 刷新画像。
2. 已有 JSON 成功作业单独重跑 MD 成功；新作业只选 MD、错源 `job_id`、JSON 非成功或清单缺失/损坏、JSON 目录缺件/多件/符号链接、v3 或库名身份不符，以及既有 JSON 对象落在当前 schema、对象类型或排除规则之外，都在清理旧 MD 与登记 `running` 前受控失败。主配置的 `database` 非对象、`database.exclude_tables: null` 或非列表，也在读取范围与清理前按配置错误拒绝，不误报平台库 503；缺省的 `exclude_tables` 仍按空列表处理。同一非法 `exclude_tables` 在受管 JSON 准备链也须于登记和清理前受控拒绝，旧 JSON 文件与清单保持不变。
   `output.markdown_options.sample_value_count="abc"`、`sampling: null`、`sampling: "abc"`、`logical_key_detection: null` 及画像配置节点/正则的构造期错误也在这一阶段拒绝，旧 MD 文件与清单逐字节保持不变；即使主配置指向另一源库，MD 快照也不保留其中的 host、port、user、password、sslmode。
3. MD 生成零对象、逐对象失败、输出缺件/多件/越界、`result.output_files` 声明路径无法与 JSON 对象一对一对应、生成器 JSON 文档缓存未命中、文件 stem 与 JSON 不同、实际 MD 字节与同一 JSON 重渲染结果不符（含标题身份、对象类型、字段增删或顺序、额外文本等篡改）、清单写入失败、JSON 运行期间重跑、最终状态提交失败，均不得留下“MD 成功且清单有效”的组合；JSON 枚举与 MD 核验使用同一三段式 stem 解析规则，`JsonLoader` 自身仍忽略其他库文件，但受管 MD 准备链按 §4 拒绝目录中的杂入文件；缓存未命中时不回退读取磁盘 JSON，清单写失败须把已登记的 MD 状态落为 `failed`，状态提交失败须删除新清单，失败后可在同作业重跑。
4. 修改源库连接可用性不影响基于有效 JSON 的 MD 生成；MD 运行中不建立源 PostgreSQL 连接。只接触本次 `output/<source_id>/<job_id>/json/` 与 `md/`，不修改全局 `output/json`、`output/md` 或其他作业文件。
5. 页面可见且可选 `ddl/json/md`，其余步骤仍清晰可见但不可选；全选、重跑和结果列表与后端步骤状态一致。JSON 后续重跑后，旧 MD 的历史 `success` 可继续显示，但不能当作当前发布就绪；清单中的 JSON 运行标识与当前 `job_info(json)` 不符时，后续发布须拒绝。Web 发布仍只支持 `db/ddl`；独立 CLI 的 JSON→MD 与 `rag_load table_schema` 行为保持原状。前端 `typecheck`、`build` 通过，并人工核对上述页面状态；当前仓库没有前端自动化测试脚本。
6. 让 JSON 在 MD 枚举或读取 JSON 文件期间重跑并清理目录：MD 可以遇到缺件或新旧混合文件，但本次必须失败、不得写出有效 MD 清单；即使文件读取未报错，也由终态 JSON 运行标识复查阻断成功。
7. JSON 样例值含换行、`[示例: ...]` 或 `##` 等 Markdown 特殊文本时，未改写的生成结果仍须通过重渲染字节比对；在此基础上额外插入、删除或改写任何字节均须失败，不写有效清单。成功清单必须含固定键 `files` 与 `source_json_updated_at`，后者为 UTC 六位小数、`Z` 结尾，微秒为零时仍输出 `.000000Z`（doc 19.3）。

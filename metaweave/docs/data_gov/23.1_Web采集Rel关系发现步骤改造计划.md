# 23.1 Web采集Rel关系发现步骤改造计划

状态：**已实施**（代码与测试完成，全量 pytest 2345 passed / 2 skipped；前端 `npm run build` 通过；F01–F04 浏览器人工验收待真实环境，见 §10）。

本篇在 Web「数据采集与画像」中激活 `--step rel` 步骤（后台步骤名 `rel`）：页面可勾选执行，依赖**同一作业已成功的 JSON 产物与 Domain 产物**（json / domain 两个步骤行 success + 受管目录产物核验），产物写入 `output/<source_id>/<job_id>/rel/`。生成逻辑复用 CLI 同款 `RelationshipDiscoveryPipeline`（直接构造调用，不经过 `execute_rel` 的 CLI 包装层）；与 md/domain/dim_config 三个 file-only 步骤不同，**rel 需要连接源库采样评分**，凭据注入走 json 步骤同款 `build_managed_ddl_config`。

本篇同时携带一项**共享层缺陷修复**：`db_domains.yaml` 表名（三段式 `db.schema.table`）与 rel 管线 `available_tables`（两段式 `schema.table`）永不匹配，导致 `relationships.domain` / `--domain` 生效时 domain 分组**恒产出 0 表对**（§3.2 实证）。修复落在共享 `DomainResolver` + 管线传参，CLI 与 WebUI 同时生效。

### 3.2 domain 表名失配（本设计的关键缺陷，实测确认）

- `db_domains.yaml`（受管 `output/<sid>/<jid>/domain/` 与未受管 `output/domains/` 两处产物一致）中表名为**三段式** `orders.public.users`（DomainGenerator 从 `<db>.<schema>.<table>.md` 文件名生成）。
- rel 管线的 `available_tables` 是 `MetadataRepository.load_all_tables` 的键 = **两段式** `schema.table`（`repository.py:78`，`object_info.schema_name + object_name`）。
- `DomainResolver.resolve_table_pairs`（`metaweave/core/domains/resolver.py`）按 casefold 全名精确匹配：三段式 domain 条目永不命中两段式 available 集合。**实测**（2026-10-09，`uv run python` 以现行 `output/domains/db_domains.yaml` + 两段式表名调用）：命中 0 个 domain、**产出 0 表对**，仅有一条 warning（"没有任何表命中 domain 配置"）。
- 后果：`relationships.domain: all`（或 CLI `--domain all`）生效时，规则与 LLM 候选的表对范围恒为空，产物只剩外键直通——**配置链路在、匹配是坏的**。需求 5 的"保证对 webui 正常"必须先修此缺陷（D2）。
- `get_domains_for_schema_table(schema_table, db_name)`（补全三段式再查）已存在但 `resolve_table_pairs` 未使用；修复采用同思路（§5.5）。

## 5. rel 步骤服务

新增 `backend/data_sources/rel_step_service.py`，对外暴露：

```python
def run_rel_step(config_path, source_id, job_id=None) -> dict:
    ...
```

- `job_id` 必填（与 md/domain/dim_config 相同："新作业单选 rel 没有任何工作区可用"）。入口处 `job_id is None` 立刻抛 `DbStepConfigError(REL_NOT_READY_TEMPLATE.format(step="JSON"))`，不写行。

### 5.1 步骤名与产物

- 步骤名常量 `REL_STEP_NAME = "rel"`（job_info.step_name、`set_operation_step`、前端步骤 id、results 行四处一致；前端 label `rel`）。
- `OPERATION_STEP_MAP` 与 `configs/logging.yaml` **零改动**（§3.1 已就绪）：script 场景写 `logs/script/rel.log`（CLI `--step rel` 同文件）；API 进程记录归 `logs/backend/metaweave.log`。
- 产物：`output/<source_id>/<job_id>/rel/{db_name}.relationships_global.json` 与同名 `.md`（文件名由 writer 按 `database.database` = 登记库名生成，与 CLI 产物同名、目录不同）。

### 5.2 准备链与依赖判定

按段执行（结构对齐 domain 步骤，差异点单独标注）：

- **入口校验段**：两级 UUID 规范化（`ValueError` → `DbStepConfigError`）；`load_main_config_snapshot(config_path)`（rel 消费主配置：relationships / llm / sampling / output / embedding，**必须加载**，与 dim_config 的不加载是有意差异）；`load_platform_settings_from_env`。

- **本地文件与配置段**（不依赖数据库连接；阶段变量依次为 `json 产物校验` / `domain 产物校验` / `快照构造` / `构造预检` / `domain 参数解析` / `LLM 预检`——R11 重排：构造预检先于后两者，`resolve_domain_params` 与 LLM 预检对 `relationships`/`llm_candidates` 的 `.get` 解引用在节点非对象时抛 `AttributeError`，先经预检收成 400，不得落 503）：

### 5.3 生成与核验

- **构造 → 清理 → 生成（R6 重排）**：`RelationshipDiscoveryPipeline(config_path, domain_filter=effective_domain, cross_domain=bool(effective_cross_domain), domain_resolver=resolver_or_None, config=snapshot)` → `clean_top_level_files(rel_dir)`（"每次完整集合"，与 ddl/md/domain 同款；自带 `mkdir(exist_ok=True)`，目录缺失不炸）→ `result = pipeline.discover()`。**构造必须先于清理**：`DatabaseConnector.__init__` 以 `ConnectionPool(..., open=True)` **急切建池**（`connector.py:90-96`，构造即连源库、失败即抛）——构造前置等价于把连接探测放到破坏性清理之前，源库连不上时旧产物保留、步骤按生成异常路径 `finish_step(FAILED)`（rel 重跑昂贵，LLM + 全量采样，值得这层保护；json 同款缺口不在本篇修）。管线内部自建 `DatabaseConnector`（读 snapshot 的 database 节点 = 登记源连接）并在 `discover()` 的 `finally` 关闭；LLM 候选按 `relationships.llm_candidates.enabled` 自动启用。构造期配置解析（top_k / name_similarity / 节点类型 / LLM）已由 §5.2 构造预检在更早的本地段覆盖；残余的未预检构造异常（未来新增解析）经本重排同样落在清理之前——旧产物保留、消息只带类型、细节在日志。
- **构造成功后的失败路径与连接池归属（R10）**：构造成功 → `clean_top_level_files` 抛错（目录不可写、unlink 失败等 `OSError`）时 `discover()` 未开始、其 `finally: connector.close()` 不会执行——与 R9（构造后半段抛、实例未返回）不同，此时**服务侧持有管线实例**，失败分支必须先显式调用 `pipeline.connector.close()` 再走 `finish_step(FAILED)`。**归属规则：`discover()` 一旦开始，关闭只交给它自己的 `finally`，服务侧不得再调**——`DatabaseConnector.close()` 只判 `if self.pool:`、不置空 `self.pool`（`connector.py:358-362`），外层再关会再次执行 `pool.close()`。实现形态：服务层以"是否已进入 `discover()`"分段界定归属（如 `discover_started` 标记或两段 try）。
- 生成异常 → `finish_step(FAILED)`，消息 `rel 采集失败（{异常类型}）`；`finish_step` 自身失败时消息追加「作业状态更新失败（{类型}），请查看日志确认作业状态」。失败时旧产物按失败时点二分（R6）：**构造期失败（清理之前，如建池失败）旧产物保留；清理之后（`discover()` 或核验阶段）失败旧产物已删、不恢复**（与其他步骤的"每次完整集合"一致）。
- **成功判定** `verify_rel_collection(result, rel_dir, database_name)`：
  1. `result.success` 为真（`add_error` 已覆盖错误路径，含 LLM 候选整体失败的降级口径 §3.1）；
  2. 声明输出恰为 2 个 `.json`/`.md` 文件，均位于 `rel_dir` 内、为普通文件（拒符号链接）；
  3. `rel_dir` 顶层实际文件集合与声明集合一致（仿 ddl/json 的目录-声明一致性；clean 语义下不应有额外文件）；
  4. json 文件可解析为对象，`database == database_name`（登记库名），`relationships` 为 list，`statistics` 为对象。
- **零关系/零推断告警（D3 + R4，R7 定互斥优先级）**：核验通过仍为 success。两条件不互斥（domain 生效且库中无外键时 `total == 0` 与 `inferred == 0` 同时为真），**判定按优先级取唯一分支、每次至多一条告警段与一条 `logger.warning`**——
  - **优先分支 ii（零推断）**：`effective_domain` 非 null 且 `result.inferred_relations == 0` → 消息 `受管 Rel 关系发现完成（{total} 条关系：外键 {fk} / 推断 0；domain 分组下推断为空，请检查 db_domains.yaml 表名与评分阈值）`。文案已含 total/外键计数，**`total == 0` 的交集场景同样由本分支覆盖**（此时计为「0 条关系：外键 0 / 推断 0」形态）——外键直通不受 domain 约束、可能撑起非零 total，domain 失配（库名不一致、yaml 表名写错）时推断静默归零正是本告警要抓的信号；
  - **分支 i（零关系，仅 domain 未生效时可达）**：`effective_domain` 为 null 且 `result.total_relations == 0` → 消息 `受管 Rel 关系发现完成（0 条关系；外键与推断均为空，请检查评分阈值）`；
  - 无告警时消息为 `受管 Rel 关系发现完成（{total} 条关系：外键 {fk} / 推断 {inf}）`。
- 状态写回：锁下 `finish_step`；`SourceRegistrationMissingError` 与写回失败的消息格式对齐 domain（`domain_step_service.py:299-332`），无 manifest 清理环节。

### 5.4 产物目录 resolver

`metaweave/core/clean_targets.py` 增加 `resolve_rel_output_dir(source_id, job_id)`：`output/<source_id>/<job_id>/rel/`，与 `resolve_domain_output_dir` 同款——两级 UUID 规范化、逐级拒绝符号链接、项目根边界与预期路径核对；受管清理、快照键与核验共用。

### 5.5 共享层修复（任务 1，先于步骤服务实施）

1. **domain 表名失配（D2）**：`DomainResolver.resolve_table_pairs` 增加 keyword-only 参数 `db_name: Optional[str] = None`。提供时为每个 `available_tables` 条目登记**两个** casefold 匹配键——原名（两段式）与 `f"{db_name}.{原名}"`（三段式）——domain 条目 casefold 后命中任一键即映射回**原始 available 名**（表对返回值仍以原始键索引 `tables` 字典，管线无感）；**归并时按原始表名去重（R4）**：同一张表在 yaml 同时写了两段式与三段式（仅手工 yaml 可能，生成器只产三段式）时两条均命中同一原始名，不去重则域内 `combinations` 产出 `(t, t)` 自配对；未提供 `db_name` 时行为逐字节不变（独立调用场景的向后兼容）。`RelationshipDiscoveryPipeline.__init__` 记录 `self.db_name = (self.config.get("database") or {}).get("database")`，`_resolve_table_pairs` 传 `db_name=self.db_name`；`LLMRelationshipDiscovery.resolve_table_pairs`（独立调用保留场景）同样从 `self.config` 取 `database.database` 传入。**两段式 domain 条目**（手工维护的 yaml）经原名键照常命中，无回归。**语义边界（R4，验收须知）**：domain 只约束推断阶段的表对范围——外键直通在 Stage 1（`pipeline.py:230`）先于表对解析（`:243`）从全部 json 表收集，`domain: all`（含 `cross_domain: false`）生效后产物仍含**跨域表对间**与**未列入任何 domain 的表**的物理外键；这是 CLI 既有语义（物理约束是事实，不因业务域分组而隐藏；domain 的定位是控制推断搜索空间，不是定义产物范围），本篇不改管线，改以零推断告警（§5.3 条件 ii）兜住"domain 失配静默成功"的观察缺口。
2. **manifest 排除**：`MetadataRepository.load_all_tables` 的 glob 过滤在既有 `_template` 前缀排除旁**按名排除 `manifest.json`**（常量从 `backend` 侧解耦：repository 定义模块级 `EXCLUDED_JSON_NAMES = ("manifest.json",)`；未受管目录无该文件，CLI 行为不变）。受管与未受管一致跳过，消除每运行一条的脏 warning；不引入参数穿透（管线/服务构造链不为此加参数）。

### 5.6 上游 marker 复查

rel 直接消费 json/domain 两个产物文件且**运行时长显著大于 md/domain**（LLM 表对 + 逐候选 DB 采样），沿用 json→ddl（doc 18）与 md→json（doc 19.1）的 marker 复查先例：会话 1 记录 json/domain 两行 `updated_at`；会话 2 复查两行仍 success 且 marker 未变；生成结束的会话 3 锁下再次复查——`ok` 但任一上游 marker 变化时按 failed 写回，消息「上游 {变化清单} 已重跑，本次 Rel 产物已失效；请重跑该步骤后再执行 Rel」，**变化清单按实际变化的行拼名（R6）：仅 JSON、仅 Domain、或「JSON 与 Domain」两者并列**（产物已落盘不删除，行 failed 保证不进入成功作业；下次重跑随 clean 清理）。与 domain/dim_config 的"不做变更复查"（其产物轻、窗口窄）是有意差异，写入本节避免误判为遗漏。

### 5.7 准备链失败与同请求阻断暂不落库

与 doc 21.1 §5.6 / doc 22.1 §5.5 口径相同：`start_step` 之前的失败（三类）与同请求上游失败的阻断都不写 `job_info`；统一改造见 [100 备忘录](100_备忘录.md) 第 3 条，本篇不实施。

## 6. 编排：白名单、顺序与失败传播

1. **白名单**：`_SUPPORTED_STEPS` 增加 `REL_STEP = "rel"`；`normalize_collection_steps` 与循环兜底两处报错文案改为"当前仅支持 db、ddl、json、md、domain、dim_config、rel 步骤"（循环兜底保留"（收到: {step}）"后缀）。
2. **顺序**：`_STEP_DEPS` 增加 `REL_STEP: (JSON_STEP, DOMAIN_STEP)`。拓扑排序规则不变（每轮选当前可执行且传入顺序最靠前者）；rel 的两条边使 `json → rel`、`domain → rel` 偏序自动成立（domain 自身经 `md → domain` 传递依赖 ddl/json）。示例：`[rel, json, ddl, md, domain] → [ddl, json, md, domain, rel]`。
3. **失败传播**：`_BLOCK_MESSAGES` 增加 `(JSON_STEP, REL_STEP)`（「本次请求的 JSON 未成功，Rel 未启动；如需使用已有 JSON 产物，请单独重跑 Rel」）与 `(DOMAIN_STEP, REL_STEP)`（「本次请求的 Domain 未成功，Rel 未启动；如需使用已有 Domain 产物，请单独重跑 Rel」）。走现有通用扫描（`_blocked_by_same_request_upstream` 按 `pair[1] == step` 自动覆盖两条）；**不复制 md 的"未选上游时改看更上游"特例**——本次没选 json/domain 时不阻断，由 §5.2 检查既有产物。
4. **作业新建与发布准入零改动**：rel 不创建作业（`job_id` 必填）；请求首步骤为 rel 且无 `job_id` → `DbStepConfigError`（400），不写行。`rollup_job_status`、采集页「下一步发布」与发布候选列表按既有口径自动包含 rel 行（failed 行阻断发布入口，§2.2）。

## 7. API 契约

- **创建采集作业：零新增字段。** `CollectionJobCreateRequest` 不变（`extra="forbid"` 不变）；`steps` 数组携带 `"rel"` 即启用。无描述/同步类成对字段，路由与 `start_collection_job` / `start_db_collection` 签名不变（rel 不消费 `domain_description` 两参数）。
- **作业列表：零改动。** `CollectionJobItem.steps` 自动含 `rel`，重跑可用性前端据此判定（§8.2）。
- **错误映射**：`backend/api/errors.py` 新增 `RelPreparationError` handler → 503 `rel_preparation_error`「Rel 准备阶段故障，请查看日志」（子类先于 `platform_unavailable` 命中，不回显异常原文；与 Domain/DimConfig 同款）。其余走既有映射：`DbStepConfigError` → 400、源禁用 → 409、平台库失败 → 503 `platform_unavailable`、「未找到指定 source_id 的数据源」→ 404。
- `CollectionJobCreateResponse` 不变；`results` 中 rel 行 `step = "rel"`。

## 8. 前端交互

### 8.1 步骤定义

- `STEP_GROUPS` c 组 rel 条目保持 `{ id: 'rel', label: 'rel' }`；可用性由 §8.2 动态计算，`isStepEnabled` 扩展 `rel` 动态分支（c 组 cql 维持静态 `enabled: false`）。

### 8.2 可勾选规则（前端信号粒度）

```ts
// rel 可勾选 = json 依赖满足 且 domain 依赖满足；
// 每个依赖独立判定：本次勾选（本次产出）或重跑作业 steps 已含（读既有产物）
const relJsonSatisfied = computed(() =>
  rerunJobId.value !== ''
    ? Boolean(selected.value.json) || rerunSteps.value.has('json')
    : Boolean(selected.value.json),
)
const relDomainSatisfied = computed(() =>
  rerunJobId.value !== ''
    ? Boolean(selected.value.domain) || rerunSteps.value.has('domain')
    : Boolean(selected.value.domain),
)
const relAvailable = computed(
  () => relJsonSatisfied.value && relDomainSatisfied.value,
)
```

- **新建作业须同时勾选 json 与 domain**（需求原话；domain 自身要求 md 可勾，md 又依赖 json——联动由既有可用性函数给出，不重复编码）。不额外强制 ddl：json 无 ddl 仅提示（`jsonWithoutDdlHint` 既有行为），rel 不叠加阻断；hint 文案建议补齐 ddl（下条）。
- 重跑模式：每个依赖"本次勾选或作业 steps 已含"即可（读既有产物粒度，与 domain/dim_config 一致）；文件级校验由后端准备链强制（§5.2）。
- 不满足时勾选框禁用，步骤区显示提示（与 `domainHint` 同容器）：
  - 新作业：「Rel 依赖同作业已成功的 JSON 与 Domain 产物；请同时勾选 JSON 与 Domain（并确保 DDL/MD 就绪），或从已有 JSON、Domain 成功的作业重跑。」
  - 重跑作业：「该作业没有 JSON / Domain 步骤，无法运行 Rel；请先补跑缺失步骤。」（不按缺失项分支，统一文案。）
- 重跑模式勾选了 rel、且至少一个依赖未在本次勾选（经作业 `steps` 满足可用性）时，显示使用流程提示（不阻断，仿 `domainReadsExistingMdHint`）。**提示按依赖逐项生成（R2 修订）：只把未在本次勾选的依赖称为"既有产物"**——本次勾选的依赖经拓扑排序先于 rel 执行，不得称"既有"。示例：本次勾 JSON 未勾 Domain →「Rel 读取既有 Domain 产物；如需基于本次采集重新生成，请同时勾选 Domain。」；两项均未勾 →「Rel 读取既有 JSON / Domain 产物；如需基于本次采集重新生成，请同时勾选对应步骤。」；两项均勾选（新建或重跑同选）→ 不显示提示。
- 失去可用性时自动清除已勾选的 rel（`watch(relAvailable, …)`，与 domain/dim_config 同款）；「全选」按点击瞬间可用性快照执行（既有 `selectAvailable` 自动覆盖）。**新建空表单的「全选」需三击才带上 rel（R5，快照规则的既定结果、非缺陷）**：第一击选中 db/ddl/json/md（domain/dim_config/rel 的依赖均未"已选"）；第二击补上 domain 与 dim_config（此时才可勾，但 rel 的 domain 依赖仍未选中）；第三击才含 rel。这与 doc 21.1 确立的"md 选中后再点一次才包含 domain"同一语义，仅依赖链再长一层（domain 两击、rel 三击）；重跑模式同理按作业既有 steps 递进。不改成"一击全选"（不动点迭代）——那会变更 21.1/22.1 已确立的全部步骤交互，超出本篇范围。

### 8.3 执行与结果区

- `createCollectionJob` **不新增参数**：`chosenSteps` 含 `'rel'` 即随 `steps` 携带；无弹窗、无描述字段。
- **成功行展示 message（D3）**：结果区 `<small>` 的条件由 `row.status === 'failed' && row.message` 放宽为 `row.message`（成功行 message 以弱化样式呈现，**零关系与零推断两类告警文案（R7 互斥分支）均经此通道可见**；失败行样式不变。**成功行与失败行同样折行（R12）**：`styles.css` 为 `li.success` 补 `flex-wrap:wrap`、`li.success small` 收窄为仅覆盖颜色——折行与字号继承基线 `li small`（`flex-basis:100%`），零推断告警这类长文案折到下一行，不横向撑出结果卡片）。这是本篇对结果区的唯一结构改动，但**视觉影响面跨全部步骤（L1，有意接受）**：db/ddl/json/md/domain/dim_config 的成功摘要（如「受管 DDL 采集完成（N 个对象）」）此后同样显示——成功摘要可见本身是改善，告警依赖该通道；如评审不接受全局放开，可退化为仅 rel 行显示（`row.step === 'rel' && row.message`），默认取全局放开。
- 重跑页面：`storedSelection` 增加 rel 分支——作业 `steps` 含 `'rel'` 且依赖满足（按 §8.2 同式判定）时预勾选；chips 与作业列表的步骤展示随 `steps` 数组自动出现 `rel`。

## 9. 错误与失败语义

准备链错误按本次请求是否已有步骤结果分流（既有编排行为，本篇不修改）：`results` 为空时整体抛出（400/409/503），已有结果时 HTTP 200 并把该步计入 failed。三类准备失败都不在服务内先写成 `failed`，不登记 rel 行。

| 场景 | 呈现 |
|---|---|
| 无 `job_id` | 抛 `DbStepConfigError`（JSON 未就绪模板）；`results` 为空时 400，已有结果时 HTTP 200 计入 failed；不登记 |
| 平台设置加载抛 `ValueError`、UUID 非法、主配置加载失败 | 转 `DbStepConfigError`；分流同上；不登记 |
| 工作区不存在或不属于该源 | 两类异常转 `DbStepConfigError`，消息保留原文；分流同上；不登记 |
| 源禁用 | 抛 `SourceDisabledError`；`results` 为空时 409，已有结果时计入 failed；不登记 |
| 会话 1 平台库连接或读取异常 | 返回「平台库连接或读取失败（{类型}）」失败字典（不带 `job_id`、不写行）；503 `platform_unavailable` 或计入 failed |
| 本地段非 `ValueError`（如 `PermissionError`） | 抛 `RelPreparationError`（消息「rel 准备阶段故障（{阶段}：{类型}）」；日志只记阶段 + 类型）；`results` 为空时 503 **`rel_preparation_error`**，已有结果时计入 failed；不转 400 |
| json / domain 行非 success、`read_managed_json_input` 失败、**对象-范围核对失败（schema / 类型 / 排除规则与登记或配置不符）**、domain 产物三查失败、**domain 生效时 `get_all_domains()` 为空**、快照目录不一致、LLM 预检失败、**构造预检失败（top_k 非法 / name_similarity 显式非法 / 节点非对象）** | 抛 `DbStepConfigError`（对应文案，范围核对文案指引重跑 DDL+JSON、构造预检消息带配置路径）；分流同上；不调用 `start_step`，**清理未发生（旧产物保留）** |
| 同请求 json 或 domain 已失败 | 编排层阻断，不调用 `run_rel_step`；`results` 中 rel `status=failed`，消息为阻断文案；不登记；HTTP 200 |
| 会话 2 `start_step` 抛 `StepAlreadyRunningError` | 返回带 `job_id` 的 failed 结果，行保持 running，HTTP 200 |
| 生成/核验失败（含 `result.success=False`，如 LLM 候选整体失败） | `results` 中 `status=failed`（HTTP 200）；行由 `finish_step(FAILED)` 落定；**构造期失败（清理之前，如建池失败）旧产物保留；清理之后的生成/核验失败旧产物已删、不恢复**（R6，"每次完整集合"语义） |
| 告警成功场景（互斥分支，R7） | **success**；domain 生效且 `inferred == 0`（含 `total == 0` 交集）→ 零推断告警段；domain 未生效且 `total == 0` → 零关系告警段；日志各恰一条 warning（D3/R4）；前端成功行展示该 message |
| 会话 3 marker 复查失败（上游 json/domain 已重跑） | failed，消息「上游 {变化清单} 已重跑，本次 Rel 产物已失效…」——清单按实际变化的行拼名：JSON / Domain / JSON 与 Domain（R6）；产物保留、行 failed |
| 状态写回失败 | 消息追加「作业状态更新失败（{类型}），请查看日志确认作业状态」 |

## 10. 验收

**后端**

- A01 作业创建接受 `steps` 含 `rel`；未知步骤报错文案含七步骤全清单。
- A02 任意传入顺序下，同请求执行序满足 `ddl→json→md→domain`、`json→dim_config` 与 **`json→rel`、`domain→rel`**（拓扑规则不变，既有六步排序用例为回归护栏）；`_BLOCK_MESSAGES` 含 `(json, rel)` 与 `(domain, rel)`，本次上游失败时 rel 不执行、不登记、消息为对应阻断文案。
- A03 rel 作为首步骤且无 `job_id` → 400，消息为 JSON 未就绪模板；`job_info` 不出现 rel 行。
- A04 json 行或 domain 行非 success（含缺行）→ `DbStepConfigError`（对应模板）；a) `results` 为空 → 400、不登记；b) 已有步骤结果 → HTTP 200、failed、不登记；c) 同请求上游失败 → 阻断文案、不调用 `run_rel_step`；d) 两行均 success → 进入本地段。
- A05 `read_managed_json_input` 任一失败（清单缺失/形状不合法/目录不一致/非三段式/v3 校验失败）与 domain 产物三查失败（缺失/非普通文件/YAML 坏/`domains` 空）→ `DbStepConfigError`，不调用 `start_step` 与管线；resolver 越界/符号链接同抛 `DbStepConfigError`。
- A06 产物落在 `output/<sid>/<jid>/rel/{db}.relationships_global.json|.md`；生成前清理目录顶层（`clean_top_level_files` 语义）；快照 `rel_directory`/`json_directory` 与受管 resolver 一致（不一致 → `DbStepConfigError`）；`build_managed_output_snapshot` 五键扩展后 ddl/json/md/domain 既有快照用例不回归。
- A07 核验：`result.success=False`（含 LLM 候选整体失败）、输出文件数 ≠ 2、输出不在 rel_dir 内、目录实际与声明不一致、json 不可解析、`database` ≠ 登记库名、`relationships` 非 list → failed；**告警分支互斥（R7 优先级）**：i) domain 未生效且 `total == 0` → success +「0 条关系」告警段；ii) domain 生效且 `inferred == 0` → success +「推断 0」告警段——**含 `total == 0` 的交集场景（此时文案为「0 条关系：外键 0 / 推断 0」的零推断形态，不用零关系文案）**；iii) 两条件均不满足 → 无告警段；每种形态日志恰一条 warning。「恰为 2 个文件」是**有意紧口径（L4）**：writer 未来新增输出文件（如 schema 粒度）须同步本核验与 A05/A06 的目录断言，防止静默多写。
- A08 平台库不可用与本地故障分离：会话 1 平台库异常 → 「平台库连接或读取失败（{类型}）」；本地段非 `ValueError` → `results` 为空时 503 **`rel_preparation_error`**（非 `platform_unavailable`、非 400），已有结果时该步 failed 且消息含阶段与类型；日志含阶段 + 类型且不含异常原文。
- A09 汇总口径回归：生成阶段 `finish_step` 写下的 rel `failed` 行使作业 failed → 发布入口不可用；准备链失败与阻断不写行，汇总只看已有行（§5.7 缺口不补）。rel 之外步骤全 success 且无 rel 失败行的作业不受影响。
- A10 rel 执行不改动 db/ddl/json/md/domain/dim_config 的产物与状态行，不触碰 `db_desc` 与数据源描述。
- A11 日志路由（分进程验收）：a) `set_operation_step("rel")` 不抛 `KeyError`；b) script profile 下执行 rel 步骤写 `logs/script/rel.log`（`logging.yaml` 零改动）——**由 §11 批次 3 的真实配置探针锁定**（复用既有 filter/file，但"Web 步骤名路由到同一文件"此前无断言），CLI `--step rel` 仍写同一文件；c) API 进程一次 Web 采集执行不产生 `logs/script/rel.log` 写入，记录归 `logs/backend/metaweave.log`（与 domain/dim_config 同款进程隔离口径，由 `logged_app` 架构隐含覆盖，不单列用例）。
- A12 **domain 失配修复（D2/R4）**：`db_name` 提供时，三段式 domain 条目命中两段式 available 表并产出非空表对（以现行受管/未受管 `db_domains.yaml` + 两段式表名实测从 0 表对转为非空）；两段式 domain 条目照常命中；**同表双写（两段式 + 三段式并存于同一 yaml）归并去重——域内表对无 `(t, t)` 自配对、无重复表对**；`db_name` 缺省时行为与现状逐字节一致（向后兼容）；表对返回值以原始两段式名索引 `tables`；管线从 `database.database` 取 `db_name` 传入（`relationships.domain: all` 的端到端用例产出域内表对，`cross_domain: true` 追加跨域表对）。**外键直通不受 domain 约束（R4 语义边界）**：`domain: all`（含 `cross_domain: false`）生效且存在**跨域表对间**或未列入任何 domain 的表间物理外键时，产物仍含该外键（既有语义，不改管线）。
- A13 **manifest 排除**：`load_all_tables` 在含 `manifest.json` 的目录不再产生「缺少 schema_name 或 object_name」warning 且不把它计入表集合；无该文件的目录行为不变。
- A14 marker 复查：生成结束后 json 或 domain 行 `updated_at` 变化 → rel failed（消息含「已重跑…已失效」）；**两行同时变化 → 消息中「JSON 与 Domain」两名并列（R6）**；两行未变 → success。**构造先于清理（R6）**：源库不可达（建池失败）等构造期异常 → 旧 rel 产物保留（目录未清理）、步骤 failed；`discover()` 运行中途的源库故障仍走"每次完整集合"既有语义（旧产物已清、不恢复，§13.11）。
- A15 构造预检（N1/R3/R8）：`llm_candidates.top_k` 非正整数、`name_similarity` 显式非法配置（`InvalidNameSimilarityConfig`）→ `DbStepConfigError`（消息含配置路径）。**节点族**：null 豁免族（`sampling`/`relationships`/`llm_candidates`/`candidate_matching`/`scoring`）配成字符串/list → 400；null 也拒绝族——顶层 `decision` 与 `relationships.weights` **无条件**、顶层 `weights` **仅当 `relationships` 无 `weights` 键时**（R8）——配成 null/字符串/list → 400；**`relationships.weights` 与非法顶层 `weights` 并存 → 放行**（顶层被 CLI 忽略，镜像其语义）。**`name_similarity`/`embedding` 配成非对象不判配置错误**（运行时降级语义，与 CLI 一致）。**LLM 开启时**：`langchain_config` 非对象 → 400；`batch_size` 为 `"abc"`（ValueError）或 list（TypeError）→ 400——**`batch_size` 为浮点/数字字符串/0/None/负数均放行**（镜像 CLI `max(1, int(x or 50))` 语义，不比 CLI 严），TypeError 用例须断言不走 503。以上全部不调用 `start_step` 与管线，**rel 目录旧产物仍在（清理未发生）**；`NameSimilarityService` 的非配置类构造异常（如无 embedding 环境）不判失败；`llm_candidates.enabled=false` 时不预检 LLM 与 `batch_size`。
- A16 对象-范围一致性（N2/N3/N4）：核对发生在**快照构造之后**（与 md 同序）；json 清单含登记 `selected_schemas` 之外的 schema 对象、`object_type` 不在 `include_object_types`、命中 `exclude_tables` → `DbStepConfigError`（文案指引重跑 DDL+JSON，**尾部为「再运行 Rel」**——`step_label` 参数化后 md 侧传 `"MD"` 文案逐字节不变），不调用 `start_step` 与管线、不清理；md 步骤既有范围核对用例（公开化 + 参数化后）不回归。**domain 生效时 `get_all_domains()` 复核（L2）**：`domains` 列表非空但全部条目无有效 `name`（如 `[{"name": ""}]`）→ `DbStepConfigError`（与 CLI `execute_rel` 同口径拒绝，不落入零表对→零关系 success）。

## 13. 边界与已知取舍

1. **CLI 影响面**：本篇对 CLI 的唯一行为变化是 §5.5 修复（D2：domain 分组从恒空变为生效；manifest 排除对未受管目录无影响）；`execute_rel`、`--domain`/`--cross-domain`/`--domains-config` 参数链路与全局 `output/rel` 产物路径均不动。受管与未受管产物互不读取、不迁移。按用户明确决定，脚本将退化，本篇不为 CLI 与 WebUI 并行使用做设计与测试。
2. **domain 依赖的语义边界（D1 的推论）**：WebUI 把 domain 步骤作为 rel 的硬依赖（行 success + 产物三查），但 `relationships.domain: null`（现行默认）时 rel 走全表两两组合、**不读** `db_domains.yaml`——此时 domain 产物被闲置而依赖仍强制。这是"沿用 CLI 合并链"决策的既定结果，不是缺陷；用户已确认 null ≠ all 的语义必须保留。
3. **长步骤与请求时长**：rel 含 LLM 表对调用与逐候选 DB 采样，耗时可能显著超过其他步骤；Web 采集请求同步等待（与 json LLM 增强同模式），不设前端轮询/超时。若后续出现体验问题，异步化属独立文档。
4. **LLM 候选整体失败即步骤失败**：管线对 LLM 整体异常的既有口径是"降级跑规则但 `add_error` 置 `success=False`"（§3.1），受管沿用——不为受管放宽为成功。
5. **产物直写最终路径（与 md/domain 同款，不做 mkstemp）**：writer 的 `open(..., "w")` 跟随符号链接，`clean_top_level_files` 删不掉悬空链接/FIFO——22.1 审核修订 2 的组合缺口在 rel 同样存在。不在本篇收口：writer 是 CLI 共享组件，单点改造收益低；若未来统一收口，应在 `file_utils` 层引入安全写盘助手（22.1 §13.8 同结论）。核验的"拒符号链接"仍保留事后发现能力。
6. **`read_managed_json_input` 的清单粒度**：复用 md 的严格校验（清单/目录/v3）+ 对象-范围核对（N2）；但不额外比对 rel 实际读入的表集合（管线自行跳过坏文件并计入日志）。`load_all_tables` 的逐文件跳过分两级（L3 措辞修正）：缺 `schema_name`/`object_name` 的文件（含修复前的 manifest 情形）为 **warning**（`repository.py:74-76`）、JSON 解析失败的文件为 **error**（`:83-84`），均不整步失败——与 md 步骤的取舍一致。
7. **embedding 降级不预检**：无 embedding 环境时 `NameSimilarityService` 降级（同名短路/禁注释闸）为设计内行为；受管环境若未配 embedding，rel 以降级评分跑完并 success，不告警到界面（日志已有 warning）。
8. **domain 产物不做独立范围核对（N2 的边界）**：json 清单的三维度范围核对（§5.2 第 3 步，快照构造后）已封住"范围外关系进产物"的全部路径——domain 表对生成以 json `available_tables` 为锚，`db_domains.yaml` 中的范围外条目不命中 available 集合即被静默过滤（§5.5 修复后按 `db_name` 规范化匹配，锚仍是 json 产物）。「json 新（范围内）+ domain 旧（含范围外表）」→ 越界条目自然失配，不产生范围外关系；「json 旧（含范围外）+ domain 新」→ json 范围核对先拒绝。残余差异只是域分组陈旧（关系的域归属划分可能与重生成后不同），由上游 marker 复查（运行期）与 json 范围核对（登记变更）间接兜底，不对 yaml 表名做独立 schema 范围核对。
9. **L2：domain 步骤自身核验口径不改**：`verify_domain_artifact`（原 `_verify_domain_output`）保持 doc 21.1 的「`domains` 列表非空」轻量口径，继续服务 domain 步骤自身的成功判定；`get_all_domains()` 过滤口径（滤除无 `name` 条目）仅在 rel 准备链 domain 生效时执行（§5.2 第 5 步），与 CLI `execute_rel` 对齐。收紧 domain 步骤自身核验超出本篇范围，如需统一另立文档。
10. **domain 的语义边界与观察兜底（R4）**：domain 只约束推断阶段的表对范围——外键直通从全部 json 表收集（`pipeline.py:230` 先于表对解析 `:243`），`domain: all`（含 `cross_domain: false`）下产物仍含**跨域表对间**与未列入 domain 的表的物理外键。这是 CLI 既有语义（物理约束是事实，不因业务域分组隐藏），本篇不改管线；「domain 失配 → 推断静默归零但外键撑起 total」的观察缺口由 §5.3 零推断告警（条件 ii）兜住——告警而非失败，因「域内确无推断关系」也是合法结果。同表双写（两段式 + 三段式）在归并时按原始名去重（§5.5），防 `(t, t)` 自配对。
11. **连接失败与产物保护（R6/R9/R10）**：`DatabaseConnector.__init__` 急切建池（`open=True`），§5.3 因此把管线构造排在破坏性清理之前——构造期连接失败（源库不可达、凭据失效）时旧 rel 产物保留。三个窗口的处置分层：**① 构造期失败**（建池失败等）→ 旧产物保留、池未建成无泄漏；**② 构造成功后、`discover()` 开始前失败**（如 `clean_top_level_files` 抛 `OSError`）→ 服务侧持有管线实例，失败分支显式 `pipeline.connector.close()`（§5.3 R10 归属规则：`discover()` 一旦开始关闭只归其 `finally`，`DatabaseConnector.close` 不置空 `self.pool`，重复关闭会再次执行 `pool.close()`）；**③ `discover()` 运行中途源库故障** → 关闭由其 `finally` 完成，旧产物已删不恢复（"每次完整集合"，与 json/ddl 同款固有语义；rel 因重跑昂贵只做构造期前移保护，运行中不做事务性产物保护，writer 直写最终路径 §13.5）。**唯一接受的残余（R9，本篇不改管线）**：构造后半段抛错（top_k / LLM 候选器 / weights / decision 等）时异常冲出 `__init__`、实例未返回——服务侧拿不到实例、`discover()` 的 `finally` 不会执行，已开的池滞留（API 进程长活）；§5.2 预检已挡住全部已知抛点（复核确认 `LLMRelationshipDiscovery.__init__` 等构造链无文件读取类 I/O 抛点）、正常路径进不了该窗口，若未来要兜"预检漏网"，关闭逻辑须写进管线 `__init__`（try/except-close），属共享层改动、波及 CLI，另立事项。json 步骤的同款缺口（构造在清理后）不在本篇修。

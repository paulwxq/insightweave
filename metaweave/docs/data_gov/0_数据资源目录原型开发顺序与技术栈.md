# 数据资源目录原型：开发顺序与技术栈

> 状态：前序概要，保留作历史背景。前端选型及开发阶段顺序已由[添加数据源与数据库概览发布模块设计](2_添加数据源与数据库概览发布模块设计.md)修订，实施以该设计为准；具体 PostgreSQL DDL、接口契约及页面设计另行编写。

## 1. 目标与当前边界

MetaWeave 已能通过 `metadata` / `pipeline` 生成数据库对象画像等文件产物，并通过 `rag_load` 将选定产物加载到 Neo4j、Milvus。下一阶段先完成一个可浏览的数据资源目录：查看已登记的数据库、表/视图/物化视图、字段、画像指标及受控样例；随后再让管理员从 Web UI 发起和查看作业。

当前元数据提取器支持 PostgreSQL；第一版数据源类型按 PostgreSQL 实现。这里的“平台 PostgreSQL”是**独立的 database**，与被分析的业务数据库在逻辑、账号和权限上分开，即使初期部署在同一 PostgreSQL 实例也不混用业务库表。

## 2. 已确定的技术选择

| 层次 | 选择与边界 |
| --- | --- |
| 元数据生成与加载 | 复用现有 Python 3.12+ MetaWeave 同步执行代码及 CLI；保留 JSON 等文件产物，不改成生成时直接写平台库。 |
| 平台主存储 | 独立 PostgreSQL database，保存数据源登记、画像目录、发布版本和作业状态；Neo4j、Milvus 继续承担现有图/向量加载职责，不作为目录页面的主读库。 |
| 后端 | FastAPI；先提供只读目录 API，后增加数据源管理及作业 API。FastAPI 的 HTTP worker 不负责执行长时间的元数据作业。 |
| 前端 | React **或** Vue，具体二选一在页面开发前确定；当前不假定已经选定其中一个。 |
| 后台作业 | 与 FastAPI 分离的作业 Worker 进程执行现有同步代码或 CLI，状态持久化到平台库。无需将 MetaWeave 的业务函数整体改写为 `async def`。 |

LangChain 继续用于现有 LLM 能力；不因建设 Web UI 而要求引入 LangGraph。第一版不引入 Airflow，也不将长作业托管给 FastAPI 进程内的 `BackgroundTasks`。

## 3. 开发顺序

### 阶段 1：平台库模型与画像导入

1. 设计 `data_source`（数据源登记）、`catalog_snapshot`（一次采集/发布版本）、数据库概览、数据库对象画像、字段画像等表；预留 `job` / `job_step` 的 ID 和关联关系。具体表名、索引及约束在 DDL 设计中确定。
2. 数据库概览由数据源登记信息与该版本对象画像汇总形成。当前每表 JSON 不包含独立的“数据库画像”文档，不能假定数据库连接信息或数据库级统计可直接从单个 JSON 取得。
3. 编写可重复运行的**导入命令**，从现有每表 JSON 读取、按当前 JSON 版本校验，并把需展示或筛选的稳定字段写入结构化列；变化较快的画像细节可使用 JSONB。字段画像至少保留为独立记录，不能只塞进一张无法按字段查询的大表。
4. 文件继续作为生成/下游处理产物。导入先写入待发布版本，校验和导入成功后再切换该数据源的当前可见版本；失败时保留上一次成功版本。现阶段通过命令**手工触发导入程序**，不是人工逐条写 SQL。
5. 如果 Web UI 所需信息已存在于 JSON，却未落库，修改导入映射；只有 MetaWeave 本身尚未采集到必要事实时，才修改生成步骤。行数采集失败与真实 `0` 行须区分，不能仅据当前 JSON 的 `total_rows: 0` 断定为空表。

验收：对已有的一份 MetaWeave JSON 产物，可重复导入；平台库能按数据源、schema 和对象查询画像；导入失败不会覆盖已发布版本。

### 阶段 2：只读 API 与 Web UI

1. FastAPI 提供数据库列表/概览、对象列表、对象与字段详情等只读 API；页面先读取平台库，不在用户打开页面时现场运行 MetaWeave。
2. 前端先完成“数据库列表 → 表/视图列表 → 对象详情与字段画像”的浏览链路。样例记录单独控制条数、脱敏和查看权限；不能把原始样本无条件返回给所有登录用户。
3. 已配置、连接可用、画像已发布、Neo4j/Milvus 已加载是不同状态，页面分别标注；数据库记录数显示其统计口径和采集时间，不将视图行数简单计入基础表合计。

验收：无需 Web 作业执行功能，即可从已导入的平台库浏览完整的第一版目录。

### 阶段 3：Web 作业提交与状态管理

1. FastAPI 只负责校验请求、创建 `queued` 作业并返回作业 ID；独立 Worker 领取并运行 `metadata`、画像发布、可选 `rag_load`，记录各步骤开始、结束、失败原因与日志关联。画像发布成功与 Neo4j/Milvus 加载成功分别记录，互不冒充。
2. Web UI 增加作业列表、详情与状态刷新。作业状态至少覆盖排队、运行、成功、失败及异常中断；Worker 重启后的未完成作业要能识别和处理。
3. 第一版可先用一个作业 Worker。要显示可靠的步骤级状态，应在 Worker 编排/步骤边界写状态，而不能仅依赖解析 CLI 的自由文本日志。

验收：管理员提交作业后，HTTP 请求立即返回；关闭页面不影响后台执行；重新打开页面仍能查看作业结果。

### 阶段 4：多数据源并行与加载目标隔离

1. 为每个数据源、每次运行确定独立配置快照与产物目录；`output_dir`、步骤目录、日志和凭据上下文一并检查。不同作业可以在不同 Worker **进程**中同步执行，不要求将 `--step ddl` 改成异步函数。
2. 对同一输出目录、Milvus Collection、Neo4j 数据库等共享目标设置互斥或排队；限制 Worker 数和源库连接数。仅“DDL 输出目录不同”不足以证明整条 pipeline 可以安全并行。
3. 目前 `rag_load cql --clean` 会清空目标 Neo4j 数据库，默认 Milvus Collection 名也由共享主配置指定。未完成目标隔离或按数据源定向清理前，不开放多数据源并发的清理加载。

验收：至少两个不同数据源的 `ddl` 作业可以在独立目录、独立进程下同时运行，状态和产物互不混淆；对相同清理目标的加载不会并发执行。

## 4. 本阶段不做

- 不以平台库直接写入取代现有 JSON/关系/CQL 文件生成链路。
- 不把 MetaWeave 同步业务函数统一改写成 `async def`；FastAPI 多 HTTP worker 也不充当作业队列。
- 不在第一版接入 Airflow、其他数据库类型、实时业务数据查询或完整的数据治理/分析功能。
- 不在尚未解决目标隔离、权限和清理范围之前开放任意多数据库并行 `rag_load --clean`。

## 5. 待确定事项

1. React 与 Vue 最终选型；可在阶段 2 开始前决定。
2. 样例数据的脱敏规则、保存期限和查看权限；须在样例入库/展示前决定。
3. 数据库概览中“记录数”的口径：仅基础表的采集时精确值、估算值，还是两者并列；须在阶段 1 的表结构设计中确定。

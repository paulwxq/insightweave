# 15. 统一日志管理模块设计

状态：已实施（阶段 1 API 日志 + 阶段 2 脚本日志，2026-09-30）。修订日期：2026-09-30。

## 1. 决策与范围

项目继续使用 Python 标准库 `logging`，统一以 `configs/logging.yaml` 定义日志名称、路径、级别、格式、轮转参数和模块注册表；不引入 Loguru、structlog 或新的日志服务。本设计中的“共享日志管理模块”负责**初始化配置、识别模块归属与补充运行上下文**，业务模块仍通过 `logging.getLogger(...)` 写日志，不直接创建文件 handler。以后新增模块满足第 3.2 节的路由、命名与线程上下文约定时，日志接入只需在 YAML 注册模块，无须修改日志管理模块或 API 请求包装器。

目标日志分为以下三类。这里的“类”表示排查用途，不表示 Python logger 的父子层级。

| 类别 | 文件 | 记录内容 | 写入进程 |
| --- | --- | --- | --- |
| API | `logs/api.log` | 所有模块共用；每个 HTTP 请求的一条摘要，含请求 ID、模块、方法、路由、状态码、耗时 | FastAPI/Uvicorn 进程 |
| 后端 | `logs/backend/platform.log`、`logs/backend/metaweave.log`；后续模块按配置增加，如 `logs/backend/nl2sql.log` | API 进程内按请求归属或 logger 名归档的业务日志、受控异常和未归属的项目/共享代码记录 | FastAPI/Uvicorn 进程 |
| 脚本 | `logs/script/` 下保留现有的 11 个文件 | 手工执行 `metaweave metadata`、`rag_load`、`meta_load`、`pipeline` 时，维持现有按步骤或 loader 分流的记录 | CLI 进程 |

**不新增 `frontend.log`。** 当前 Vue 应用在浏览器中运行；Vite 开发服务器的终端输出只是启动、构建与热更新信息，不是用户页面的运行日志。浏览器控制台继续用于前端调试，本次不做浏览器错误上报接口，也不改 `frontend/`。

脚本日志保留原有的 11 类分流与 CLI 业务步骤，只迁移日志目录并统一配置文件路径解析；为此会调整 `--log-config` 的存在性检查时机，但不改变手工命令的业务执行流程。独立辅助脚本 `scripts/run_metadata_generation.py` 现在只用 `basicConfig` 输出控制台；它不产生文件日志，本次也不为它新建日志文件。`click.echo`、`print` 与 Uvicorn 的启动控制台输出仍可存在，不把它们误称为新日志文件。

## 2. 当前代码的依据

1. `metaweave/cli/main.py` 在 CLI 根命令调用 `setup_metaweave_logging()`；`metaweave/utils/logger.py` 从 `configs/logging.yaml` 读取配置并调用 `logging.config.dictConfig()`。默认配置相对当前工作目录查找，文件名也相对工作目录；默认文件缺失时 CLI 会打印警告并退回控制台 `basicConfig`。`--log-config` 现用 `click.Path(exists=True)`，会先按工作目录检查显式路径。
2. 现有 `configs/logging.yaml` 有 `db`、`ddl`、`json`、`md`、`rel`、`cql`、`generate_domains`、`dim_config`、`sql_rag_generate`、`sql_rag_validate` 和 `loader` 共 11 个文件 handler，路径均在 `logs/` 根层。前十类依赖全局 `current_step` 和 `StepFilter`，loader 依赖显式命名 logger。
3. `backend/api/main.py:create_app()` 不初始化项目日志。文档中的 `uvicorn backend.api.main:create_app --factory` 启动方式使用 Uvicorn 自己的控制台配置；`backend/api/errors.py`、`backend/publishing/publish_service.py` 和 `backend/profile_loading/db_loader.py` 虽调用 `logging`，但 API 进程没有给它们配置项目文件输出。
4. API 的采集和发布入口分别通过 `asyncio.to_thread()` 调用共享业务代码；`backend/data_sources/db_step_service.py`、`backend/publishing/publish_service.py` 等还会设置全局 `current_step`。该全局值适用于当前 CLI 步骤分流，**不能用来给并发 API 请求决定文件归属或请求 ID**。
5. `tests/unit/test_step_logging.py` 与 `tests/unit/test_db_step.py` 验证既有步骤分流；后者会读取真实 YAML 再把测试文件路径改到临时目录。改日志配置时必须同步核对这些测试，不得只检查文件是否被创建。
6. `metaweave/utils/file_utils.py:resolve_project_path()` 是项目已有的相对路径解析入口，`tests/unit/test_project_path_unification.py` 通过替换其 `get_project_root()` 验证文件目标。`metaweave/core/metadata/generator.py` 和 `metaweave/core/sql_rag/validator.py` 各自使用 `ThreadPoolExecutor`；它不会自动传播 `ContextVar`。

## 3. 统一配置的装载方式

### 3.1 一个 YAML、两个运行配置、一个模块注册表

新增中立的共享入口 `services/logging_manager.py:configure_logging(profile, config_path=None)`，供 API 和 CLI 使用。保留现有 `metaweave/utils/logger.py:setup_metaweave_logging(config_path=None)` 签名：它作为兼容包装调用共享入口的 `script` 运行配置，现有 `StepFilter`、`set_current_step()`、`get_metaweave_logger()` 与步骤记录工厂继续在原模块工作。API 工厂直接调用共享入口的 `api` 运行配置，未来 NL2SQL 无须导入 `metaweave.utils.logger`。**YAML 顶层的 `formatters`、`filters`、`handlers`、`loggers`、`root` 就是脚本运行配置的原始形态；只有 API 专用模板放在 `x_profiles.api`，模块注册表放在 `x_modules`，不设置 `x_profiles.script`。**共享入口加载 `script` 时整段沿用顶层标准配置，只解析其中的相对日志路径，保留所有过滤器、handler 引用、logger 级别与传播设置；加载 `api` 时才依据 `x_profiles.api` 和 `x_modules` 组装独立的标准 `dictConfig` 字典，并裁剪 API 不用的内容。当前 Python 3.12 的 `dictConfig()` 会忽略未知顶层键，移除 `x_profiles`、`x_modules` 只是装载器的实现选择；装载器仍须校验自定义项，不能依赖 `dictConfig()` 校验。该校验只属于 `api` 运行配置：`script` 分支裁剪时直接丢弃 `x_profiles`/`x_modules`，**不读取也不校验**（有意为之：CLI 进程不消费 API 模块配置，`x_*` 中的错误不应阻塞脚本运行）；`api` 分支在组装前完整校验模板与注册表。

| 运行配置 | root 与专用 logger | 结果 |
| --- | --- | --- |
| `api` | root 写控制台，并挂载注册表生成的后端文件 handler；每个文件 handler 只接收归属本模块的记录；请求摘要的专用 logger `platform.http.access` 只写 `api_file`（装载期按 handler 身份严格校验：`handlers` 必须恰好为 `[api_file]`，摘要文件的路径与文件名在 `api_file.filename` 配置，换成其它文件 handler 会把摘要接到别的文件、留下空的 `api.log`，装载期拒绝）、`propagate: false`、级别放行 INFO（摘要 logger 与其文件 handler 的显式 level、及其未声明时按 logger 层级实际继承的级别——`platform.http` → `platform` → root 中最近的声明，与 `Logger.getEffectiveLevel()` 同一规则——均不得高于 INFO，WARNING 及以上会把 <500 的 INFO 摘要静默滤掉，违反 §8.1"恰好一条"，装载期拒绝；`level: null` 与 `NOTSET` 视同未声明，与 dictConfig/getEffectiveLevel 对 None/NOTSET 的语义一致）；`uvicorn.error` 只写专用 stderr handler、`propagate: false`，`--no-access-log` 关闭原生 access log | 一个请求只在共用 `api.log` 有一条请求摘要；业务调用在对应模块的后端文件，Uvicorn 原始异常 traceback 不写项目文件 |
| `script` | 原样保留顶层 root 的控制台与十个步骤文件 handler、十个 `StepFilter`、`metaweave: DEBUG` 和五个 `propagate: false` 的 loader logger | CLI 的旧分流行为不变，仅文件路径变化 |

API formatter 不能要求 `%(step)s`：Uvicorn、框架和普通业务记录未必有这个字段；脚本 formatter 继续使用现有 `%(step)s`，与步骤记录工厂和 `StepFilter` 配套。API 配置**不安装步骤过滤器，也不安装第二个全局 LogRecord 工厂**；共享函数即使调用 `set_current_step()`，也不能使 API 日志写到 `logs/script/`。业务归属字段统一命名为 `app_module`：API 与后端 formatter 使用 `%(app_module)s`、`%(request_id)s`、`%(name)s`；其中 `%(name)s` 是 logger 名，标准 `%(module)s` 保留“产生日志的源文件名”语义，**不得覆写**。API 专用 handler 过滤器在格式化前为每条记录补齐 `request_id` 和 `app_module`，缺请求 ID 时写 `-`；不能只把过滤器挂到 root logger，因为子 logger 向上传播时不会执行父 logger 的过滤器。

| API 运行配置中的 handler | 必装过滤器 | 作用 |
| --- | --- | --- |
| `api_file` | `ApiContextFilter` | 为专用请求摘要 logger 补齐两个字段 |
| 注册表生成的**每个**后端文件 handler | `ApiModuleFilter(target_module)` | 补齐两个字段，并只放行归属本模块的记录 |
| API 的 `console` | `ApiContextFilter` | 补齐两个字段，保证控制台格式化成功 |
| `uvicorn.error` 专用 stderr handler | 无（使用 Uvicorn formatter，不读取请求字段） | 保留 Uvicorn 原始终端诊断及 `exc_info`，不写项目文件 |

`uvicorn.error` 的 logger 配置**不写 `level` 键**，保留 Uvicorn 根据 `--log-level` 设置的有效级别；专用 stderr handler 复用 Uvicorn 0.53.0 的 `uvicorn.logging.DefaultFormatter`，配置 `fmt: '%(levelprefix)s %(message)s'`，保留熟悉的 `ERROR:    ` 前缀与自动追加的 traceback，不清除 `record.exc_info`。该 logger 只挂此 handler，设置 `propagate: false`，避免同一诊断再由父 logger `uvicorn` 的默认 handler 输出。两个 API 过滤器复用同一归属判定函数，重复调用只得到同一结果；业务 logger 仍使用 `logging.getLogger(__name__)` 或现有名字。现有脚本 `_install_step_log_record_factory()` 保持原样，API 初始化不调用它；若同一测试进程先装过脚本工厂，API 过滤器仍能补齐字段，API formatter 不读取 `step`，测试结束恢复原工厂。运行配置决定写入 API/后端还是脚本日志，模块注册表与请求上下文决定 API 进程内的后端文件。

默认配置文件 `configs/logging.yaml`、显式 `--log-config` 文件，以及 YAML 中每个相对日志文件路径，都统一调用 `metaweave.utils.file_utils.resolve_project_path()` 解析；绝对路径原样使用。YAML 中写 `logs/api.log`、`logs/backend/platform.log`、`logs/backend/metaweave.log` 和 `logs/script/db.log` 等，无论从哪个工作目录启动都落到同一处。不能在 `services/logging_manager.py` 自己拼项目根路径。`--log-config` 改成先接收原始路径、再由共享入口解析与检查“存在、可读、普通文件”；不能保留先按 cwd 判定存在性的 `click.Path(exists=True)`。显式配置缺失或非法应转成 Click 配置/用法错误并以 **exit 2** 退出，不能让共享入口异常直接冒泡成 exit 1。只创建当前运行配置所需的父目录；**仅 API 的后端文件 handler** 可设置 `delay: true`，首次写入时才创建文件。脚本的 11 个文件 handler 保持现有的启动时创建文件语义，不加 `delay: true`：`test_db_step.py` 会直接读取未命中步骤的空文件。API 装载时不打开或创建脚本日志文件。

文件 handler 继续使用现有 `RotatingFileHandler`，默认每文件 10 MiB、保留 5 份轮转文件、UTF-8；API 与后端文件也采用同一默认值，全部由 YAML 配置。未发生轮转的旧 `logs/*.log` 留在原处供人工归档，本次不自动移动、合并或删除旧日志。

### 3.2 模块注册与自动分流

YAML 中注册每个后端模块的 `backend_file`、负责的 API 路径前缀、独立运行时的 logger 名前缀。下面是**配置结构示例**；具体键名、默认级别与轮转参数应在实施时同现有 YAML 整合：

```yaml
x_modules:
  platform:
    backend_file: logs/backend/platform.log
  metaweave:
    backend_file: logs/backend/metaweave.log
    api_route_prefixes:
      - /api/data-sources
      - /api/data-assets
    logger_prefixes:
      - metaweave
      - backend.publishing
      - backend.profile_loading
```

`platform` 是必须注册的兜底模块，接收未归属的项目/共享代码记录；Uvicorn 的启动与运行日志只走终端，不进入该文件。当前 API 进程里这类未归属记录通常没有，`platform.log` 可因延迟创建而不存在。当前 `/api/data-sources` 下包含采集和发布入口，因此归 `metaweave`；`/api/data-assets` 同理。`backend.api` 是多个模块共用的异常处理器 logger，不能固定注册到 `metaweave`；请求发生时由上下文决定归属，启动阶段等无请求上下文时归 `platform`。以后给 NL2SQL 增加路由和业务代码时，只需为**日志接入**增加一段配置，例如：

```yaml
x_modules:
  # 在已有 platform、metaweave 同级追加
  nl2sql:
    backend_file: logs/backend/nl2sql.log
    api_route_prefixes:
      - /api/nl2sql
    logger_prefixes:
      - nl2sql
      - backend.nl2sql
```

当前 API 调用链中已核对的应用 logger 及分流结果如下；按**logger 名**匹配，而不是按源文件路径或 Python 包名匹配：

| logger 名 | MetaWeave 请求内 | 无请求上下文时 | 依据 |
| --- | --- | --- | --- |
| `backend.api` | `metaweave.log` | `platform.log` | `backend/api/errors.py`；共享异常处理器，不加 MetaWeave 专属前缀 |
| `backend.profile_loading`、`backend.publishing` | `metaweave.log` | `metaweave.log` | 现有两个业务 logger 已显式注册前缀 |
| `metaweave.db_step`、`metaweave.connector` 等 `metaweave.*` | `metaweave.log` | `metaweave.log` | 现有 MetaWeave 共享代码，命中 `metaweave` 前缀 |
| `metaweave.pg_connection` | `metaweave.log` | `metaweave.log` | 虽定义于 `services/db/pg_connection.py`，实际 logger 名仍以 `metaweave` 开头 |
| `backend.jobs.*`、`backend.persistence.*`、`backend.data_sources.*` | 当前没有对应日志调用 | 无日志可归档 | 不为这些包臆造 logger 前缀；以后新增调用再按实际名字复核 |

未来 NL2SQL 请求中调用以上 MetaWeave 共享方法时，请求上下文优先，业务记录应进 `nl2sql.log`；这正是不能仅看 logger 名前缀的原因。实施时若 API 调用链新增 logger，应在同一清单中核对它的请求内、请求外归属。

共享入口遍历 `x_modules`，生成每模块的文件 handler 与过滤器，不能在 Python 代码中写 `if module == "metaweave"` 一类专用分支。它把校验后的注册表交给请求包装器，避免包装器维护第二份路由映射。模块归属按以下优先级确定：

1. HTTP 请求进入时，用 `starlette.routing.get_route_path(scope)` 取得与 Starlette 路由匹配一致的路径；它会按 `root_path` 语义去掉已挂载前缀，再按**完整路径段边界**匹配注册的最长 `api_route_prefixes`，将模块 ID 放入 `ContextVar`。例如 `/api/nl2sql-extra` 不匹配 `/api/nl2sql`，挂在 `/prefix` 下的 `/prefix/api/nl2sql` 仍匹配 `/api/nl2sql`。请求结束在 `finally` 复位。路径只用于内部归属判定，日志摘要仍写路由模板。
2. 有请求模块上下文时，业务日志一律归该模块，包括它调用的 `services.*`、`metaweave.*` 等共享方法；这使同一个共享方法随调用者进入不同的后端文件。`asyncio.to_thread()` 会传播上下文，但业务代码自己创建的 `ThreadPoolExecutor` 不会。共享入口提供“提交任务时为每个任务单独执行 `contextvars.copy_context()`，再用 `context.run()` 执行”的辅助函数；同一个 `Context` 不能并发供多个任务运行。当前 API 尚未调用 `metaweave/core/metadata/generator.py` 的 `submit` 或 `metaweave/core/sql_rag/validator.py` 的 `map`，本次不修改它们；将来任一流程接入 API 时，须在那次集成中改用该辅助函数，并用覆盖真实提交点的测试验证。新增模块的线程池也须遵守这个入口约定，否则请求 ID 和调用方归属会丢失，退回 logger 前缀，可能写错模块文件。这是配置无法自动补救的边界。
3. 没有请求上下文时，按 logger 名匹配最长的 `logger_prefixes`，只匹配完整名称或其以 `.` 分隔的子 logger；仍无法判定时归 `platform`。定时任务或其他非 HTTP 入口若需要归业务模块，须在入口显式设置模块上下文，或使用注册表内可唯一匹配的 logger 名。单凭 YAML 无法从任意共享函数调用栈推断调用者。

配置装载时校验模块 ID（只允许小写字母、数字、下划线且以字母开头）、文件路径不重复、路径前缀格式、logger 前缀格式及冲突；同一优先级出现歧义应启动失败。模块与 API 路径无关时可省略 `api_route_prefixes`；没有专属包名时可省略 `logger_prefixes`，但其非 HTTP 日志将归 `platform`。`api.log` 中的 `app_module` 字段与后端文件的模块归属必须一致；未知路径记为 `platform`。`api_file` 只挂在请求摘要 logger 上，后端文件 handler 不处理该摘要，因此不会把一条 HTTP 摘要复制到后端文件；装载期同样会拒绝摘要文件 handler（摘要 logger 引用且带 `filename` 的 handler）被 root 或其它 logger 引用——其 formatter 需要摘要字段，业务记录进入时会逐条格式化失败（stderr 噪音且记录被丢弃）。文件目标按规范化路径全局判重：模板内部、模板与注册表 `backend_file`、注册表内部三个组合中，任何两个文件 handler 指向同一实际文件（含 `..` 等路径别名）都在装载期拒绝，同一文件不得被两个 `RotatingFileHandler` 写并轮转；script 运行配置的顶层文件 handler 同样按此规则在装载期判重（目录与可写检查两个运行配置本就共用同一套）。

这里的“新增模块只改配置”特指**新模块已按上述约定使用标准 `logging`、在线程池中传播上下文，并有可配置的独立路由前缀或 logger 前缀时，其日志接入只改 YAML**。新增模块本身的路由和业务代码仍需开发。若新模块复用一个没有独立路径前缀的旧路由，或者从非 HTTP 入口直接调用同名共享 logger 而不设置模块上下文，配置无法可靠判定归属，需先调整该模块的入口约定。

### 3.3 API 启动入口与测试隔离

新增一个部署专用应用工厂，例如 `backend/api/logged_app.py:create_logged_app()`：先调用共享入口的 `api` 运行配置，取得校验后的模块注册表，再调用现有 `backend/api/main.py:create_app()`，最后把所得 FastAPI 应用包在 `backend/api/request_logging.py` 的**外层纯 ASGI 包装器**内并返回给 Uvicorn。包装器位于整个 FastAPI/Starlette 应用之外，因此也位于 Starlette 的 `ServerErrorMiddleware` 之外；注册表直接传给包装器。包装器通过只读 `.app` 属性暴露内层 FastAPI 实例，便于调试时访问 `logged_app.app.state`、`logged_app.app.routes` 等，不通过 `__getattr__` 隐式转发 FastAPI 属性。保留 `create_app(settings=..., cors_origins=...)` 的签名与测试用法；普通单测直接构造应用时不重配 pytest 进程的全局 logging。把项目文档中的服务启动命令改为该工厂，并加 `--no-access-log`，以免 Uvicorn 原生访问日志与本设计的请求摘要重复。

示例启动命令：

```bash
uv run --extra platform uvicorn backend.api.logged_app:create_logged_app --factory --no-access-log --host 127.0.0.1 --port 8001
```

当前安装的 Uvicorn 0.53.0 在 `Config.__init__()` 中先执行自己的 `configure_logging()`，之后才加载应用并调用工厂；所以 `create_logged_app()` 内的 API 运行配置会覆盖 Uvicorn 的早期配置，并把 `uvicorn.error` 固定为只写 stderr、`propagate: false`。`--no-access-log` 已由 Uvicorn 把 `uvicorn.access` 的 handler 清空并设为不传播；共享装载器不要再给它挂 handler。**不要**给 Uvicorn 传 `--log-config configs/logging.yaml`：那会在应用工厂运行前把脚本 handler 装入 API 进程，可能提前创建脚本文件并使需要 `step` 字段的 formatter 处理启动日志；随后再覆盖也不能消除这些启动副作用。该 YAML 只由本项目的共享装载器读取。

文档须明确：继续使用旧的 `backend.api.main:create_app` 入口时不会自动得到 `api.log` / `logs/backend/*.log`。API 运行配置缺失、非法或日志目录不可写时，应在启动阶段明确失败并说明配置路径，不静默退回“只有终端输出”。由于后端文件按首次写入延迟创建，启动时还应检查配置目录的写入能力，而不能只依赖打开文件时才报错。**已存在的目标日志文件同样检查可写，且必须是普通文件**：`delay` 对已存在的文件没有“稍后创建”的语义，文件不可写（如被 chmod 只读的旧文件）应在装载时明确失败，而不是运行期每条记录写入失败丢失、API 带病运行；目录等“存在且可写”的非普通文件同样在装载期拒绝——delay handler 启动时不打开目标，否则运行期首条记录 `IsADirectoryError` 被 logging 内部吞掉，业务诊断静默丢失。不存在的文件保持延迟创建。**CLI 保留现有的不同策略**：仅当默认配置文件缺失时，在标准错误输出明确警告并降级为控制台 `basicConfig`，此时无法保证生成脚本文件日志；默认配置存在但非法，或显式 `--log-config` 指定的文件不存在/非法时，转为 Click `UsageError`/`BadParameter` 以 exit 2 退出——只有“缺失”才降级，“存在但非法”一律明确失败，不静默带病运行。两者行为不同是有意选择，不能把 CLI 的警告降级描述成静默，也不能把 API 悄悄降级。Uvicorn 在加载应用工厂之前产生的极早期启动消息仍可能只在终端；应用完成装载之后的项目业务日志按上述文件归档，Uvicorn 原始错误仍留在 stderr。

## 4. `api.log`：一次请求一条摘要

在 `backend/api/request_logging.py` 增加纯 ASGI 日志包装器，由 `create_logged_app()` 包在整个 FastAPI 应用外侧，不能作为 `create_app()` 的用户中间件注册。Starlette 1.6.0 的 `ServerErrorMiddleware` 位于用户中间件之外，`@app.exception_handler(Exception)` 由它执行；若请求上下文在用户中间件的 `finally` 中提前复位，未预期 500 的诊断就会丢失模块归属。虽然 `add_middleware()` 会把后注册的用户中间件放在已有 CORS 中间件外侧，它仍在 `ServerErrorMiddleware` 内侧，不能替代这里的外层包装器。包装器只处理 HTTP scope；在请求进入时生成 `request_id`，记录单调时钟起点，监听 `http.response.start` 的状态码，并以最终 `http.response.body` 且 `more_body=false`（省略时也视为 false）判定响应完整；若收到 `http.response.pathsend`，同样视为完整响应。状态码与完整标记只在相应消息**成功交给服务器**（`send` 正常返回）后更新：响应头或最终响应体发送失败（如连接断开）时，分别按 `no_response`（无已发状态码）与 `incomplete`（保留已成功发出的状态码）记录，不得把"已尝试发送"记成 completed。对**每个已进入包装器且执行到 `finally` 的 HTTP 请求恰好写一条**摘要，然后才复位请求上下文。Starlette 的 500 响应与异常继续按原行为传递，包装器不自行改写响应状态或响应体。

摘要级别与状态的判定顺序固定如下，避免把“异常已被处理成响应”误判为成功：

| 结束情况 | `status_code` | `outcome` | 级别 |
| --- | --- | --- | --- |
| 未发 `http.response.start` 就返回、抛错或取消 | `-` | `no_response` | `ERROR` |
| 已发响应头，但未完整发完响应体就结束或取消 | 已发送的状态码 | `incomplete` | `ERROR` |
| 响应完整结束，状态码 ≥500 | 实际状态码 | `completed` | `ERROR` |
| 响应完整结束，状态码 <500 | 实际状态码 | `completed` | `INFO` |

若应用在完整响应后仍抛异常，保留实际状态码与 `outcome=completed`，级别提升为 `ERROR`；异常仍向上抛出。客户端断连只有在应用观察到取消、异常或未完成响应时才能从 ASGI 层识别，不能承诺识别所有已断开的连接。进程被强制终止或文件写入失败不属于“恰好一条”的保证范围。摘要写入失败时包装器不改写请求结果：不顶掉在途异常、不让已完成的响应从包装器抛错，向 stderr 打印完整堆栈（不含请求内容）以便定位“api.log 长期零行但服务看似正常”的代码缺陷，请求上下文仍复位；该兜底输出自身失败（如 daemon 已关闭 stderr、管道断开）时放弃打印。

摘要字段固定为 `timestamp`、`level`、`request_id`、`app_module`、`method`、`route`、`status_code`、`outcome`、`duration_ms`；`status_code` 的 formatter 占位符使用 `%(status_code)s`，允许无响应时写 `-`；`duration_ms` 为毫秒、保留一位小数（亚毫秒请求可显示 `0.0`）。若用 `logger.info(..., extra=...)` 注入摘要字段，只能使用不与 `LogRecord` 保留属性冲突的键；以上自定义字段可用，`module`、`filename`、`lineno`、`name`、`msg`、`args`、`created`、`message`、`asctime` 等保留名不能放入 `extra`，否则日志调用会抛 `KeyError`。验证 `extra` 冲突时须启用被测 logger 的相应级别，避免记录被级别过滤而产生假通过。匹配到路由时从 `scope["route"].path` 读取路由模板，例如 `/api/data-sources/{source_id}`。该键仅由 FastAPI 的 `APIRoute` 匹配时写入；Starlette 原生 `Route` 与 `Mount` 不写该键，因此 `/docs`、`/openapi.json` 与挂载的静态资源等**已匹配**请求同样写固定标识 `-`。预检或未匹配请求可写固定标识及状态，不把任意用户输入当作路由模板。**不记录请求体、响应体、密码、数据库连接串、Cookie、Authorization 头或原始查询参数。** 当前没有前端日志需求，不为请求中间件增加前端上报端点。

请求 ID 与业务模块 ID 使用 `contextvars.ContextVar` 保存，给后端文件的 formatter 提供 `request_id`、`app_module`；没有请求上下文时请求 ID 显示 `-`，业务模块按 logger 名前缀或 `platform` 判定。采集与发布会跨异步/线程边界，必须验证上下文能到达实际写业务日志的线程，且两个并发请求不会串号。不要用现有进程级 `_CURRENT_STEP` 代替请求上下文。

例：

```text
2026-09-30 12:00:00 INFO request_id=8c1... app_module=metaweave method=POST route=/api/data-sources/{source_id}/collection-jobs status_code=200 outcome=completed duration_ms=381.4
```

`api.log` 只描述 HTTP 结果；业务失败的安全诊断写归属模块的后端文件。未处理异常即使已生成 500 响应，Starlette 仍会重新抛给 Uvicorn；Uvicorn 会另向 stderr 输出 `Exception in ASGI application` 及原始 traceback，但不写 `platform.log`。现有 `@app.exception_handler(Exception)` 正常执行时，这类失败有两条项目文件记录（API 摘要、模块安全诊断）和一条终端诊断；具名异常被内层处理器消费，不产生这条 Uvicorn traceback。若部署系统另行收集 stderr，其保留与脱敏由部署日志策略负责。

## 5. `logs/backend/`：按模块归档业务记录

API 运行配置把 `backend.*`、`metaweave.*`、`services.*` 等共享代码的现有 `logging` 调用，按第 3.2 节的模块规则归档；未归属的**项目/共享代码**记录进入 `logs/backend/platform.log`。`uvicorn.error` 单独写 stderr，不传播到任何项目文件 handler：未处理异常的原始 traceback 可能含第三方异常消息，不能在未审查前持久化到 `platform.log`。默认记录 `INFO` 及以上；日志行包含时间、级别、模块、logger 名、请求 ID、源文件/行号和消息。手工 CLI 调用同一个共享函数时，由 `script` 运行配置将其归入脚本日志，不因代码所在包名叫 `backend` 而写 API 进程的后端日志。

现有异常处理器 `backend/api/errors.py` 的安全响应继续保留。`SourceCredentialError` 等可能含凭据的异常只记录请求 ID、路由模板（§4 语义，取不到时写固定标识）和异常类型或安全错误码，不直接写 `str(exc)`，也不把请求输入的原始路径写进日志；未预期 500 需要留下可定位的受控诊断信息。`backend.api` 是共享 logger：具名异常处理器在内层 `ExceptionMiddleware` 中执行，未预期 500 的处理器在外层 `ServerErrorMiddleware` 中执行；由于日志包装器位于两者之外，**两类处理器写日志时都保有请求上下文**，按请求模块进入对应后端文件，而不是靠 `backend.api` 前缀硬归 `metaweave`。现有业务模块的日志调用按归属自动进入 `logs/backend/metaweave.log` 或以后新增模块的文件；无归属时进入 `logs/backend/platform.log`。采集、发布等**API 入口**可在成功返回时补一条业务结果，包含已有的 `source_id`、`job_id`、`publish_id`（若已生成）、步骤和结果；这类新记录只加在 API 层，不改共享业务方法，也不改变脚本原有的日志内容。失败由最有上下文的现有业务日志或异常处理器记录，不把同一堆栈沿调用链重复写入。**有业务诊断的路径，一次受控 5xx 可以同时有一条业务定位记录和一条处理器边界诊断**（如发布预检读平台库失败：业务层先记含 `source_id`/`job_id` 的定位信息再抛 `PlatformUnavailableError`，处理器再记路由模板与异常类型）；两者内容与用途不同，不属于重复。异常处理器的边界诊断对每次受控 5xx 都记录，保证无上游业务日志的路径（如 `registration_service`、`jobs` 的部分抛点）也有最低诊断。

日志不能包含源库密码、平台库密码、API Key、原始连接串或未经审查的 SQL/请求体。保留现有安全响应文案与错误码；日志规范化不改变采集、发布、数据源管理和画像页面的业务行为。

## 8. 验收标准

1. 使用新的 API 启动入口，每个已进入包装器并执行到 `finally` 的 HTTP 请求在 `logs/api.log` 恰好增加一条摘要，含正确 `app_module`。完整响应的 2xx/3xx/4xx（含 404）记 `INFO`，503、已被具名异常处理器转成的 500、未预期 500 均记 `ERROR`；未发响应头时记 `status_code=-`、`outcome=no_response`、`ERROR`，中途取消/断开的未完成响应记实际已发状态码、`outcome=incomplete`、`ERROR`。用合成 ASGI 响应验证 `http.response.pathsend` 也记 `outcome=completed`。没有第二条 Uvicorn access 记录；原有响应状态、JSON 与 CORS 行为不变。标准 `LogRecord.module` 仍表示源文件名，业务模块字段只用 `app_module`。
2. API 的发布、采集、具名异常与未预期 500 的异常处理产生日志时写 `logs/backend/metaweave.log`，与对应 `api.log` 使用同一请求 ID 和 `app_module`；未来 NL2SQL 请求的异常进入 NL2SQL 文件，`backend.api` 不被固定归 MetaWeave。另在**无请求上下文**时用未注册前缀的测试 logger 写一条，验证它归入 `logs/backend/platform.log`；未写这类记录时允许该文件因 `delay: true` 而不存在。Uvicorn 原始异常 traceback 不得出现在任何项目文件中；**启动真实 Uvicorn 子进程并发送触发未处理 500 的 HTTP 请求**后，对 stderr 中 `Exception in ASGI application` 计数为一次，并确认保留完整 traceback；分别用 `--log-level info` 与 `--log-level warning` 启动，前者有 `Started server process` 等 Uvicorn INFO 行，后者没有，但两者的 ERROR traceback 都保留。直连 ASGI 的 `TestClient` 不会产生这条协议层日志，不能单独用于此断言。并发请求不串上下文。API 进程不把这些记录写入 `logs/script/`，也不因启动而创建空的脚本日志文件。
3. `api.log` 不含请求体、原始查询参数和凭据；后端文件不含源库/平台库密码与 API Key。没有请求上下文的后台启动消息仍能按约定格式写入，`request_id=-`。
4. 手工 CLI 的 `db`、`rel` 和 loader 至少各跑一次现有日志分流测试：内容在 `logs/script/` 对应同名文件，不在根层新写 `db.log`、`rel.log`、`loader.log`；未命中步骤的空文件在配置时仍存在；`--debug`、控制台输出、步骤与 loader 语义不变。现有 step 工厂测试及九个直接构造 `create_app()` 的 API 测试通过，`caplog` 的凭据脱敏断言保持有效。
5. 测试把 `file_utils.get_project_root()` 替换为临时目录，从另一工作目录启动，默认配置文件、相对 `--log-config` 和所有日志文件都定位到临时项目根；绝对路径不改写，不往真实仓库写测试日志。旧日志文件不被自动删除或搬迁。
6. API 日志配置缺失/不可用会阻止服务按新入口启动并给出明确错误；CLI 默认配置缺失时有明确警告且仅输出控制台，默认配置存在但非法、或显式 `--log-config` 缺失/非法时 **exit 2**，不出现未捕获异常的 exit 1。直接调用 `create_app()` 的现有单测不会把 pytest 的全局 logging 改为文件配置。
7. 在测试 YAML 中只注册新模块 `nl2sql`，不改日志管理模块或请求包装器；`/api/nl2sql/...` 的请求摘要仍只写共用 `api.log`，其业务记录自动写 `logs/backend/nl2sql.log`。同一个 `services.*` logger 在 MetaWeave、NL2SQL 两个请求中各进入调用者的文件；无请求上下文的 `nl2sql.*` 记录按 logger 前缀进入 NL2SQL 文件。两个并发请求各自提交多个线程池任务时，请求 ID 和 `app_module` 均不串号、不回退到错误模块；本次只验证共享线程池辅助函数，不运行尚未接入 API 的 generator/validator。非法或冲突的注册配置启动失败。脚本 logger 级别与 API 配置裁剪测试各在干净进程中执行，须证明 `metaweave.*` 的 DEBUG 仍进入脚本文件，五个 loader logger 的记录进入 `loader.log` 和控制台、但不进入任何步骤文件，且 API 不创建脚本文件。
8. 设置 `root_path=/prefix` 并分别测试请求路径含、不含该前缀的 ASGI 入口；模块分流都按 `starlette.routing.get_route_path(scope)` 返回的实际路由路径匹配，日志写 `scope["route"].path` 模板。另验证两个边界：`path == root_path == "/prefix"` 时返回空串，按未匹配路径归 `platform`；`path="/prefixes/x"`、`root_path="/prefix"` 时仅字符串前缀相同，返回原始 `/prefixes/x`，不得误剥为 `es/x`，按当前注册规则归 `platform`。用文档中的 Uvicorn 命令启动时原生 access log 关闭，API 启动不创建脚本日志文件。

## 9. 运行边界

这一版沿用本地文件与 `RotatingFileHandler`，仅支持**一个 API 写入进程**，以及低频、避免并行写同一脚本文件的手工 CLI。文件日志部署不能使用 Uvicorn `--workers N`（`N>1`，也须检查 `WEB_CONCURRENCY`）或多个实例；多个 CLI 进程也不能直接共写并轮转同一个文件。Python 标准文件 handler 不提供跨进程安全轮转。`--reload` 是开发用重启模式，本设计的正式文件日志启动命令不使用它；当前 Uvicorn 正常重载会等待旧子进程结束再启动新的子进程，**不能把它等同于多 worker 并发写入**，但重载后的日志重新初始化不纳入正式部署验收。若需要多 worker 或多实例，应保持日志类别、字段与同一 YAML 的配置入口，将输出改为标准输出加集中采集，或使用单独的日志写入进程，而不是简单共享 `logs/api.log`、`logs/backend/*.log` 等路径。[Python Logging Cookbook：多进程写同一文件](https://docs.python.org/3/howto/logging-cookbook.html#logging-to-a-single-file-from-multiple-processes)

## 10. 实施顺序

| 阶段 | 改动与验证 | 独立回滚边界 |
| --- | --- | --- |
| 1. API 日志 | 新增共享装载器的 `api` 运行配置、模块注册、外层包装器和部署入口；YAML 中 API 专用 handler 模板放在自定义 `x_profiles.api` 下，不加入旧版 CLI 会直接交给 `dictConfig()` 的顶层 `handlers`，也不移动现有 11 个脚本文件路径。验证 API 摘要、模块分流、异常、Uvicorn stderr 隔离、`root_path`、不创建脚本文件，以及现有 CLI 分流仍可运行。 | 回退 API 入口与新增自定义配置即可，脚本文件布局未变 |
| 2. 脚本日志 | CLI 兼容包装改用共享装载器的 `script` 运行配置；装载器沿用顶层 `formatters`、`filters`、`handlers`、`loggers`、`root`，统一配置路径解析，再把 11 个脚本文件移到 `logs/script/`，**不搬到 `x_profiles.script`**。验证步骤分流、`metaweave.*` DEBUG、loader 隔离、显式错误 exit 2、`test_step_logging.py`、`test_db_step.py`、跨工作目录路径测试和九个直接调用 `create_app()` 的 API 测试。 | 回退 CLI 装载与脚本路径变更，不影响已验证的 API 入口 |

第一阶段不得直接把 API 文件 handler 加入 YAML 顶层 `handlers`：旧版 CLI 调用 `dictConfig()` 时会配置所有顶层 handler，即使 root 没有引用也可能创建文件。阶段二完成后，仍只有 **API 配置**由共享装载器按注册表组装与裁剪；脚本配置只解析路径并沿用现有顶层形态。两阶段的配置隔离断言都在干净进程执行，避免连续重配继承旧 logger 级别造成假通过。

# 发布信息表 `publish_info` 与发布动作设计

> 状态：设计稿，尚未实施。本文修订 [doc 2](2_添加数据源与数据库概览发布模块设计.md) §6 中 `publish_info` 的表设计，并在 [doc 9](9_db采集作业目录与数据库画像表设计.md) 的 `job_info` / `db_profile` 与 [doc 10](10_平台画像加载命令meta_load设计.md) 的 `publish_id` 语义之上，定义"发布"这一动作的状态记录规则；同时规划第一阶段的 Web 发布实施（仅 `db` 步骤）。与 doc 2 §6 冲突之处以本文为准。RAG 类步骤的发布编排、`ddl` / `json` 画像表与加载、发布历史页面、Worker 属于后续阶段，另行设计。

## 1. 目标与边界

发布是独立于采集与加载的动作：选定一个作业工作区（`job_id`），把其中已成功的采集产物加载到平台库与 RAG 存储，并把每个步骤的结果记录到 `public.publish_info`。发布覆盖两类步骤，共七种 `step_name`：

| 类别 | 步骤 | 目标 | 现状 |
| --- | --- | --- | --- |
| 画像类 | `db`、`ddl`、`json` | 平台库画像表（现有 `db_profile`，表/字段画像表后续） | 仅 `db` 已有加载实现（doc 10） |
| RAG 类 | `sql`、`table_schema`、`dim_value`、`cql` | Neo4j / Milvus | 加载命令已有，发布编排未实施 |

本阶段交付两件事：

1. `publish_info` 表的 DDL 与 ORM 模型——§2–§6 是它的完整契约；
2. Web 发布的第一阶段：只发布 `db` 步骤，复用 doc 10 已完成的加载链路（前置校验、文件校验、字段映射），见 §7。

本阶段不做：RAG 类步骤的发布编排、`ddl` / `json` 画像表与加载、发布历史页面、Worker、标记级版本切换、删除发布 API，也不改造 `meta_load` / `rag_load` 既有 CLI 的外部行为。

本阶段 Web 发布不提供 `clean` 参数，**不清理采集产物目录**。只读取指定 `source_id/job_id` 下的文件，不连接源库、不执行采集、不调用 Click 命令或启动 `metaweave` 子进程。已有 CLI 的 `--clean` 仍保持 doc 10 的“加载提交成功后清理顶层文件”语义。

## 2. 表设计

在已有 `public.db_source_info`、`public.job_info`、`public.db_profile` 的平台库中执行：

```sql
CREATE TABLE public.publish_info (
    publish_id uuid NOT NULL,
    step_name text NOT NULL CHECK (length(btrim(step_name)) > 0),
    source_id uuid NOT NULL,
    job_id uuid NOT NULL,
    status text NOT NULL CHECK (status IN ('success', 'failed')),
    is_current_publish boolean NOT NULL DEFAULT false,
    created_by_user_id uuid NULL,
    error_summary text NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    updated_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (publish_id, step_name)
);

CREATE UNIQUE INDEX publish_info_current_idx
    ON public.publish_info (source_id, step_name)
    WHERE is_current_publish;

CREATE INDEX publish_info_source_created_idx
    ON public.publish_info (source_id, created_at DESC);

CREATE INDEX publish_info_job_idx
    ON public.publish_info (job_id);
```

| 字段 | 含义 |
| --- | --- |
| `publish_id uuid` | 发布尝试 ID，发布动作开始时用 `uuid.uuid4()` 生成，本次所选的全部步骤共用；与 `step_name` 组成主键，不单独唯一。画像类步骤成功时，对应画像表行以同一 `publish_id` 为主键值。 |
| `step_name text` | 本次发布的步骤。约定域为 §1 的七值，但 DDL 不建白名单 CHECK——步骤集合会增长，`job_info.step_name` 同样只校验非空；非法步骤名由发布服务在入口校验。 |
| `source_id uuid` | 所属数据源 ID。不建外键，发布前由 Python 校验存在且处于激活状态（沿用 doc 11 的"拦新动作"原则）。 |
| `job_id uuid` | 本次发布读取的工作区。不建外键，发布前校验 `job_info` 中该 `job_id` 的步骤行全部归属同一 `source_id`。 |
| `status text` | 本步骤本次发布的结果，仅 `success` / `failed`；没有 `running`（发布是逐步骤的短动作）。 |
| `is_current_publish boolean` | 标记该 `(source_id, step_name)` 最后完成结果记录提交的一次发布所在行，成功、失败均可；不按请求开始时间排序，语义见 §4。 |
| `created_by_user_id uuid NULL` | 发起本次发布的平台用户，专指创建人；当前无登录体系写 `NULL`，不建外键，将来由后端从登录身份填入（沿用 doc 3 §2 的约定）。 |
| `error_summary text NULL` | 本次失败原因摘要；成功时为 `NULL`，失败时由发布服务提供受控文案。这一一致性由代码逻辑保证，不额外增加 status 与 error_summary 的数据库 CHECK。查询 current 行看到的是最后完成结果记录提交的一次发布的原因；历史失败行保留各自摘要，不覆盖旧行。 |
| `created_at timestamptz` | 本行插入时间，即该步骤本次发布尝试的落行时间。 |
| `updated_at timestamptz` | 最近一次状态写入时间；行插入时与 `created_at` 同值，此后唯一会前进的时机是被更晚的发布翻成 `is_current_publish=false`。 |

主键与三个索引各司其职，互不冗余；**不需要再建任何视图**（普通视图不存数据、无加速作用；物化视图需要 `REFRESH`、两次刷新之间是旧数据，对"当前状态指针"意味着陈旧说谎；部分唯一索引本身就是数据库免费维护、永不失效的"current 子集"）：

| 键 | 回答的问题 |
| --- | --- |
| 主键 `(publish_id, step_name)` | "某一次发布的某个步骤结果如何"——按 `publish_id` 一查，本次发布所有步骤的成败全部出来。 |
| `publish_info_current_idx` | "这个源的这个步骤当前的发布状态是谁"——`WHERE source_id = … AND step_name = … AND is_current_publish` 直查；同时以唯一性强制"每源每步骤至多一行 current"。 |
| `publish_info_source_created_idx` | 按数据源列发布历史。 |
| `publish_info_job_idx` | 按 `job_id` 追溯该工作区被哪些发布引用。 |

## 3. 发布动作的记录语义

1. 规范化并校验执行前提：数据源存在且激活；`job_info` 中该 `job_id` 的步骤行全部归属本次 `source_id`，且本次要发布的每个 `(job_id, step_name)` 行 `last_status='success'`。任一不满足即拒绝，不生成 `publish_id`、不读取文件、不触碰任何存储。
2. 生成 `publish_id = uuid.uuid4()`，一次发布只生成一个，全部所选步骤共用；发布记录或画像的主键冲突时回滚该步骤事务，按既有 `500 internal_error` 兜底处理，不重新生成 UUID、不自动重试、不补写失败记录。
3. 逐步骤执行加载，每个步骤完成后用一次平台库短事务写入记录：先把 `(source_id, step_name)` 现有 `is_current_publish=true` 的行翻成 `false`，再插入本次 `(publish_id, step_name)` 行并置 `true`。翻旧与插新必须同事务；漏翻旧行的写入会被 `publish_info_current_idx` 拒绝，数据库兜底。`status='success'` 且属于画像类时，对应画像表的插入（以同一 `publish_id` 为主键值）并入同一事务。
4. 画像类步骤失败：加载事务回滚（画像表不留半行），随后用另一个短事务完成"翻旧 + 插入 `failed` 行"，`error_summary` 写失败原因。`publish_info_current_idx` 冲突不走补写失败记录的分支，按 §7.3 回滚并返回并发冲突；主键冲突按第 2 条回滚并走既有 `500 internal_error` 兜底。
5. RAG 类步骤：目标存储无事务、先清后载；加载结束（成功或抛错）后按第 3 条规则落行。
6. 行一旦插入不再 UPDATE 业务字段；唯一允许的更新是被更晚的发布翻转 `is_current_publish`（及随之推进的 `updated_at`）。重新发布——无论全量还是只补失败步骤——都是新的 `publish_id`、新的行；不提供同 `publish_id` 补跑，重试即新尝试。
7. 发布不修改 `job_info` 的任何状态。
8. 单步骤执行失败且失败记录已提交后，继续执行其余已选步骤；不因该步骤失败终止整次发布。管理员排除故障后可以只选择失败步骤重新发布，生成新的 `publish_id`，不修改原发布记录、不重跑未选择的成功步骤。

本阶段不实现发布互斥：不增加显式 `SELECT ... FOR UPDATE`、应用锁或排队机制，也不沿用 doc 2 的发布与作业入队共用数据源行锁方案。文件读取不持有平台库事务；写入仅使用上述短事务和既有唯一索引。数据库执行 UPDATE 时的正常行锁不属于额外的发布锁定功能。前端禁用重复点击只避免同一页面重复提交，不保证多个页面或请求之间互斥。

## 4. `is_current_publish` 语义

- 该标记指向该 `(source_id, step_name)` **最后完成结果记录提交的一次发布**所在的行，**成功、失败都翻**。本文“最近一次发布尝试”均按结果记录的提交顺序理解，不按请求开始时间、UUID 或 `created_at` 排序。失败也翻的原因：RAG 类步骤先清后载，失败后目标存储可能已空或残缺，若指针停留在此前的成功行上，等于谎报状态。
- 每个源的每个步骤至多一行 `true`（部分唯一索引强制）；新行置 `true` 时，同 `(source_id, step_name)` 的旧行在同一事务翻 `false`。
- 接受并发请求按结果提交顺序生效，不保证每个并发请求都能提交。若失败记录在另一请求的成功记录之后完成提交，current 指向失败行，先前成功的画像仍作为历史保留；这符合本表语义。因 current 唯一索引冲突回滚的请求不参与提交顺序，不改变 current。
- 读取方回答"当前状态"用 `source_id + step_name + is_current_publish`；检查"某一次发布"用主键。两个查询键各答一问，不能互换。
- 当前画像的读取必须先判断 current 行的 `status`，不能假定每条 current 都有对应画像。读取规则如下；失败后的修复与重新发布由管理员负责，不自动回退历史成功版本。
- 不提供标记级版本切换与删除发布的 API；恢复或重发的手段是修复原因后重新发布。

| 当前 `db` 发布记录 | 当前画像读取与展示规则 |
| --- | --- |
| 没有 current 行 | 返回“尚未发布”的状态，不返回画像；不能从历史画像或 CLI 加载行推断当前发布。 |
| current 为 `success` | 用该行的 `publish_id` 读取对应 `db_profile` 并展示。若画像缺失，这是数据一致性错误，不能伪装为尚未发布或自动换用其他版本。 |
| current 为 `failed` | 返回当前发布 ID、失败状态及受控 `error_summary`，画像为空；页面显示“发布失败”，不展示旧画像、不查询最近成功版本作为替代。失败行没有对应画像是正常情形，不是画像丢失。 |

历史成功画像仍保留供后续排障或历史查询，但不作为失败后的当前画像。数据资产首页 `GET /api/data-assets` 按每个数据源 `db` 步骤的 current 行读取：仅 `success` 且存在对应 `db_profile` 的数据源进入可用目录；current 为失败时不回退历史成功画像，也不列入目录。成功记录缺少画像时计入 `inconsistent_count`，不换用其他版本，也不伪装成尚未发布。按数据源读取单份画像的接口仍未实现。当前发布页仍按 POST 的真实结果展示成败。

## 5. 原子性与诚实声明

- **画像类**：每步骤一个平台库短事务，失败即回滚，画像表不会出现半行。应用层合同：画像类 `success` 行的 `publish_id` 必须在同事务存在对应画像表行。
- **RAG 类**：Neo4j / Milvus 无跨语句事务，`cql` 等加载是"先清空再重载"；失败后目标存储可能为空或不完整。平台库记录与目标存储实际内容之间没有事务保障，current 仅反映最后完成结果记录提交的一次发布，不能据此保证并发加载后的目标内容一致；RAG 发布尚未在本阶段接入，其并发执行规则留待接入时设计。
- **跨步骤不整体回滚，单步失败后继续**：部分成功合法，各步骤状态独立落行、独立翻转 current。某步执行失败并完成失败记录提交后，继续按所选步骤去重后的顺序执行其余步骤，不撤销其他步骤已经提交的成功结果。这是发布的默认行为，不新增 `--continue-on-error` 参数或 Web 开关。
- **结果覆盖范围**：正常完成的发布响应中，`results` 按执行顺序包含本次全部已选步骤，每步恰有一条真实的 `success` 或 `failed` 结果；未选择的步骤不包含。普通单步失败不会使后续已选步骤变成未执行，也不需要为此增加 `skipped` 状态。
- **请求级错误的边界**：上述继续规则只针对能够完成结果记录提交的单步失败。请求前置校验不通过仍拒绝整次请求；current 索引冲突返回 `409 publish_conflict`，发布记录或画像的主键冲突回滚后走既有 `500 internal_error` 兜底，平台库故障导致结果无法记录返回 `503 platform_unavailable`，具体规则见 §7.3、§7.6。不伪造已提交的逐步结果，也不回滚此前步骤已提交的数据。本阶段仅接入 db；这些多步骤规则在后续步骤接入时沿用，不要求本阶段提前开发其他加载类型。
- **多步骤请求报错后的已提交结果**：后续步骤发生请求级错误（如 current 索引冲突返回 409）时，错误响应不包含 results，但此前步骤已提交的发布记录及数据仍保留；不能把整次请求报错理解为全部回滚。已提交结果可通过平台记录或日志排查，后续发布历史接口提供查询；不自动重试整次发布。本阶段只有 db，不会出现“前一步已提交、后一步冲突”的组合，本条只明确后续多步骤边界，不新增历史查询接口。
- **诚实声明**：翻转 `is_current_publish` 只是平台库侧的记账，不会改变 Neo4j / Milvus 的内容；要真正回退 RAG 必须从对应工作区重跑加载。本文不提供该操作，仅声明事实，防止将来的设计误以为翻标记等于回滚。

## 6. 与既有模块的关系

| 模块 | 关系 |
| --- | --- |
| `job_info` | 发布的前置校验来源（归属 + `last_status='success'`）；发布不回写作业状态。 |
| `db_profile` | 画像类步骤的锚点表，`publish_id` 即其主键。现存由 doc 10 `meta_load` 产生的画像行没有 `publish_info` 行，**不视为已发布**；不追溯补行。发布状态一律以 `publish_info` 为准，不得按 `db_profile` 行数或 `collected_at` 推断。当前画像按 §4 先判断发布状态：只有 success 才读取画像，failed 不回退历史成功画像。 |
| `meta_load` | `load_db_profile()` 目前自行生成 `publish_id` 并自开事务提交画像行；CLI 的外部行为**保持不变**（仍是"加载"不是"发布"，其画像行按上一行规则视为未发布）。为发布服务所做的内部拆分见 §7.4。 |
| 数据源删除 | 本表无外键，不触发 doc 7 §3 关于外键级联的顾虑；但删除已有发布历史的数据源会留下孤儿行，删除策略留待后续设计，届时一并考虑 `publish_info` 与 `db_profile`。 |

## 7. Web 发布第一阶段：仅 `db`

### 7.1 范围与入口

本阶段只发布 `db` 步骤。发布入口放在采集作业列表页（`CollectionJobsView`）：每个作业行提供"发布"操作，进入新页面 `/data-sources/:sourceId/collection-jobs/:jobId/publish`。现有“重新执行”占位不在本次接线范围，不将其误接成发布。发布在 API 请求内**同步完成并返回结果**；同步的文件/数据库操作在线程中执行（POST 路由使用 `async def` + `await asyncio.to_thread(...)`，与现有采集入口一致），不引入 Worker、轮询、心跳或租约。预检路由使用同步 `def`，由 FastAPI 在线程池中执行。数据源已禁用时发布入口置灰（与创建采集作业一致的禁用语义）。

页面布局参考 [原型 6：数据画像发布执行页面](ui/数据源管理到发布/6.数据画像发布执行页面(对接前页上一步).html)，不照搬原型的示例 UUID、计数或成功结果。指定数据源的发布作业列表（[原型 7](ui/数据源管理到发布/7.画像发布作业列表(指定数据源).html)）按 `publish_info` 的 `publish_id` 聚合只读展示，入口在数据源连接卡片和详情页的「相关画像发布作业」。原型 8 的独立选作业入口仍不在本次范围，「新建画像发布」不跳转。

### 7.2 发布前校验（预检）

页面上的步骤清单必须先经过预检，只有"可发布"的步骤才允许勾选。两项校验都在后端完成（前端看不到文件系统），由预检端点返回：

`GET /api/data-sources/{source_id}/collection-jobs/{job_id}/publish-check`

响应形态（本阶段 `steps` 只含发布域内步骤，即 `db`）：

```json
{
  "source_id": "…", "job_id": "…",
  "steps": [
    {"step_name": "db", "job_status": "success", "output_ready": true,
     "publishable": true, "reason": null}
  ]
}
```

校验规则：

1. **作业状态**：先用 `assert_workspace_owner()` 确认作业存在且全部步骤行归属本次数据源，再读取 `(job_id, 'db')` 行。`last_status='success'` → 状态校验通过；`'failed'`、`'running'` 或查无该步骤行 → `publishable=false`，`reason` 分别为"最近一次采集失败"、"正在执行"、"没有执行记录"，`job_status` 为实际状态或 `null`。**整个作业不存在是 404；已有作业仅缺少 db 步骤记录是 200 + 该项置灰**，两者不能混为一谈。
2. **产物就绪**：调用 §7.4 的共享函数 `resolve_db_profile_input_path(source_id, job_id)`，由它统一解析 `output/<source_id>/<job_id>/db/database.json` 并检查主产物是非符号链接的普通文件；通过即 `output_ready=true`。目录不存在、为空、仅有子目录/隐藏标记/其他文件、主产物缺失或是符号链接 → `output_ready=false`。目录路径包含符号链接、路径解析或访问失败同样不可选。预检捕获共享函数的 `ProfileInputError` 后，一律返回 false 与固定原因“产物不存在或不可用”；不区分目录/文件失败子类、不匹配异常文本、不返回底层异常原文。预检不创建目录、不删除文件、不读取链接目标，也不自行重复路径或文件类型判断。
3. 发布域外的步骤（`ddl/json/sql/table_schema/dim_value/cql`）不进预检，由前端静态置灰为"暂不支持发布"（沿用 `CreateCollectionJobView` 的 `STEP_GROUPS.enabled` 模式）。

预检捕获 `ProfileInputError` 时，必须以 WARNING 记录 `source_id`、`job_id` 和共享函数提供的受控具体原因，供开发/运维区分文件缺失、路径包含符号链接等问题；允许包含产物路径，但不记录凭据、连接串、完整 JSON 或驱动原文。不按原因细分日志级别、不增加异常分类；日志记录具体原因不用于匹配文本或决定业务分支。页面仍统一提示“产物不存在或不可用”。

两项校验分别返回真实结果，`publishable = (job_status == 'success') and output_ready`；任一不通过即不可勾选。两项都失败时优先显示作业状态的原因，只有状态成功才显示目录/文件原因；通过时 `reason=null`。目录预检是简单的存在性检查，**不解析 JSON，不验证内容、计数或版本**；即使文件为空或内容非法，也由实际加载时的现有完整校验判为失败，不在预检里复制 `_profile_fields()`。

**预检只做引导，不替代服务端校验**：页面数据可能过期（如勾选后目录被清空）。发布执行时的规则是——`job_info` 不满足属于请求级前置错误，拒绝整个发布、不生成 `publish_id`（§3 第 1 条）；目录/文件问题在执行中发现，按 §3 第 4 条落 `failed` 行。预检端点的错误映射：数据源或作业不存在、归属不符 → `404`；数据源已禁用 → `409 source_disabled`（复用 doc 11 的错误码，具体类型见 §7.6）。

### 7.3 发布端点与执行流程

`POST /api/data-sources/{source_id}/collection-jobs/{job_id}/publications`

请求体 `{"steps": ["db"]}`：请求模型 `extra="forbid"`，只接收 `steps: list[str]`，不接收 `clean`、`publish_id` 或发布人。服务层检查非空、按首次出现顺序去重、本阶段仅允许小写 `db`；空列表或非法步骤返回 `400 step_not_supported`，请求体形态/类型或路径 UUID 非法返回 `422 invalid_request`。不把表设计的七个步骤都当作本阶段可执行能力。

发布服务 `publish_steps(settings: PlatformSettings, source_id, job_id, steps) -> dict` 按以下顺序执行（使用应用工厂已加载的 `settings`，服务内部不重新读 `.env`）：

1. 请求级前置（§3 第 1 条）：数据源存在且激活（禁用 → `409 source_disabled`）、工作区存在且归属正确（否则 `404 not_found`）、每个所选步骤 `last_status='success'`（否则 `400 step_not_ready`，消息"步骤尚未采集成功"）。**重新查询，不相信预检响应或客户端传来的状态**。完成前置查询即关闭会话，不跨文件读取持有平台库事务；不满足时不生成 `publish_id`、不留任何行。
2. 生成 `publish_id`。
3. 执行 `db` 步骤：调用 §7.4 拆出的输入读取函数完成文件校验与字段提取；随后**一个平台库事务**：翻同 `(source_id, 'db')` 旧 current 行 → 插 `publish_info` 行（`success`）→ 插 `db_profile` 行（同一 `publish_id`）→ 提交。
4. 执行失败（文件缺失、解析失败、入库异常，排除下面的 current 索引冲突及既定主键冲突）：画像事务回滚（两表都不留行），再用独立短事务"翻旧 + 插 `failed` 行"（`error_summary` 为原因摘要，不包含敏感信息）。失败记录提交后将该步加入 results 并继续其余已选步骤；本阶段只有 db，因此直接进入结果返回，不增加未实现步骤的执行分支。
5. 全部已选步骤执行完成后，同步返回逐步骤结果（形态对齐采集作业创建响应）；`results` 覆盖去重后的全部已选步骤，成功、失败都保留，未选择的步骤不包含：

```json
{"publish_id": "…",
 "results": [{"step": "db", "status": "success", "message": "…", "finished_at": "…Z"}]}
```

请求级前置错误返回 `404/409/400`；执行结果（含 `failed` 步骤）以 `200` + `results` 呈现，前端按 `results` 渲染成败。**响应形态对齐采集接口，失败语义以本文 §3、§5 的结果落库规则为准**，不承诺两套接口的错误判定完全一致。发布侧的画像入库失败若能另行提交 failed 发布记录，可以返回 `200 + failed`；若结果无法记录，则返回请求级错误，不能仅凭底层操作失败就统一归为 503。采集接口目前通过中文消息前缀判断部分未登记失败；发布侧不沿用该判定，按具体异常类型和实际事务提交结果处理。本次不顺带改造采集接口。`created_by_user_id` 当前写 `NULL`。

`finished_at` 使用 UTC、带 `Z`、六位微秒精度的时间（doc 19.3 §3）。只有实际提交了成功或失败记录，才返回 200 的对应结果；**若平台库不可用，连失败记录也无法提交，返回 `503 platform_unavailable`**，不能返回“已记录失败”。日志保留 `source_id/job_id/publish_id` 与异常类型；接口消息和 `error_summary` 按失败发生的阶段使用固定受控摘要：输入读取、解析或内容校验失败统一为“画像输入不可用或校验失败”，可回滚的画像入库失败为“平台库写入失败”。不按 `ProfileInputError` 的文本区分文件或内容原因，不增加异常分类，也不在 `read_db_profile_input()` 前重复调用路径检查来选择文案。具体输入原因保留在日志中供排障，但不得记录或返回完整 JSON、凭据、连接串及驱动原文。

预检固定提示仍为“产物不存在或不可用”：预检只检查文件就绪，POST 还执行完整内容校验，两个阶段范围不同，无需使用同一提示。发布调用链仍直接调用 `read_db_profile_input()`，由其内部调用共享路径/文件检查函数。

**主键冲突的出口**：成功事务或独立失败事务发生 `publish_info` 的 `(publish_id, step_name)` 主键冲突，或 `db_profile.publish_id` 主键冲突时，回滚该步骤事务，停止本次请求并沿用既有 `500 internal_error` 兜底；不重新生成 UUID、不自动重试、不补写失败记录，也不映射为 `503 platform_unavailable`。记录受控诊断字段后，改为抛出消息固定为“服务暂时无法处理请求”的内置异常，并使用 `from None`，避免服务器堆栈带上原始 `IntegrityError`、SQL 或参数。响应仍由既有 `Exception` 兜底返回该安全文案，不新增异常类、错误码或 handler。具体冲突留在日志中排查，不返回驱动原文。此前步骤已经提交的数据保持不变。实施时按驱动的唯一冲突标识及对应表的主键约束名区分，不能把所有 `IntegrityError` 都归为主键冲突。

**current 索引冲突的例外规则**：成功事务或独立失败事务在 flush/commit 时，若发生 `publish_info_current_idx` 唯一冲突，先回滚该事务，再抛 `PublicationConflictError`，由 API 返回 `409 publish_conflict`，受控消息为“发布发生并发冲突，请重新发布”。不自动重试、不补写失败记录、不返回 200 的 failed 结果，也不映射为 503/500。本次事务对画像和 current 的修改全部回滚，其他已提交发布不受影响。服务只在驱动报告唯一冲突（SQLSTATE `23505`）且索引/约束名为 `publish_info_current_idx` 时使用此分支，不能把所有 `IntegrityError` 一概视为并发冲突；其余异常仍按各自规则处理。

上述识别统一调用 §7.4 的两个纯函数 `is_current_index_conflict(exc)` 与 `is_primary_key_conflict(exc)`，成功事务与独立失败事务共用，不在两个异常分支中复制判定逻辑。两个函数均放在现有发布服务文件中，不为此新增模块。先判定 current 索引冲突，再判定指定主键冲突；两者均不匹配时，按异常发生的事务阶段处理，不能用“不是 current 索引冲突”推断为主键冲突。

**其他约束错误的出口**：成功事务中的其他 `IntegrityError`（如 CHECK 违规）先回滚，再尝试提交独立 failed 记录；只有失败记录提交成功才返回 `200 + failed`，摘要为“平台库写入失败”。若独立失败记录事务发生其他约束错误，回滚并返回 `503 platform_unavailable`，不返回“已记录失败”、不再次补写失败记录。两个阶段的 current 索引冲突及指定主键冲突，仍优先使用上述 409/500 规则。

**约束错误日志的责任方**：`backend/publishing/publish_service.py` 在捕获 `IntegrityError` 后、重新抛出或转换为上述结果/异常前，必须以 ERROR 记录 `source_id`、`job_id`、`publish_id`、`step_name`、事务阶段（成功事务或独立失败记录事务）、异常类型，以及 `orig.sqlstate` 和 `orig.diag.constraint_name`。该要求覆盖 current 索引冲突、指定主键冲突及其他约束错误；诊断属性缺失时记“未知”，不影响既定判定和响应规则。不依赖 API 兜底 handler 补记约束信息；两个判定纯函数仍只返回布尔值，不负责日志。只记录这些上下文字段，不打印异常全文、SQL 参数、驱动原文、凭据或完整 JSON，不使用会附带这些内容的异常堆栈输出；不为此新增日志模块或异常类。

### 7.4 `db_loader.py` 的改造

现状：`load_db_profile(source_id, job_id, clean=False)`（`backend/profile_loading/db_loader.py`）内部自生成 `publish_id` 并自开事务提交 `DbProfile`，CLI（doc 10）与既有测试依赖这一行为。改造目标：**CLI 外部行为与返回值不变**，同时给发布服务提供可组合的内部函数，不复制第二套校验规则：

共享层只做最小拆分，保留 `_profile_fields()` 作为 JSON 内容与字段映射的唯一实现，不重写已经通过验收的加载器：

| 函数/类型 | 位置与合同 |
| --- | --- |
| `inspect_db_profile_context(session, source_id: UUID, job_id: UUID) -> str \| None` | 放在 `db_loader.py`。检查数据源存在且激活、调用既有 `assert_workspace_owner()`，再查询 `get_step_row(session, job_id, 'db')`；返回该步骤的 `last_status`，仅缺 db 步骤行时返回 `None`。不读文件、不生成 ID、不写库、不 commit、不读取环境变量；调用方决定非成功状态如何呈现。 |
| `MetaLoadSourceNotFoundError` / `MetaLoadSourceDisabledError` | `db_loader.py` 中新增的两个 `MetaLoadConfigError` 子类，用于上一个函数表达数据源不存在/已禁用，保留 CLI 原消息与基类捕获。工作区错误继续使用既有 `WorkspaceMissingError` / `WorkspaceSourceMismatchError`，不解析异常消息来区分。 |
| `resolve_db_profile_input_path(source_id: UUID, job_id: UUID) -> Path` | 放在 `db_loader.py`，作为跨模块共用的公开函数：调用既有 `resolve_db_output_dir()` → 定位 `database.json` → 检查普通、非符号链接文件 → 返回文件路径。文件不满足要求时抛 `ProfileInputError`；目录解析或文件检查的 `ValueError/OSError` 同样转为该异常，沿用现有受控错误文案，不增加异常分类。异常可保留具体原因供 CLI 与日志排障；Web 预检不使用这些文本区分原因，统一提示“产物不存在或不可用”。它是路径解析与主文件就绪规则的唯一入口；不读取或解析 JSON，不检查 schema_version，不创建/清理目录、不访问平台库。 |
| `read_db_profile_input(source_id: UUID, job_id: UUID) -> tuple[dict, Path]` | 放在 `db_loader.py`，抽取当前输入段：调用 `resolve_db_profile_input_path()` → UTF-8 读取与 `json.loads()` → `_profile_fields()`。返回画像字段与文件路径的 `parent`（db 目录）；不再自行实现普通/非链接判定。不查平台库、不自行生成 `publish_id`、不清理目录、不入库。现有 `ProfileInputError` 与读取/解析异常由入口转换为对应结果；执行时重新调用共享函数，不信任之前的预检结果。 |
| `insert_db_profile(session, publish_id: UUID, fields: dict) -> DbProfile` | 放在 `db_loader.py`，只构造 `DbProfile(publish_id=publish_id, **fields)` 并 `session.add()`；不 commit、不回滚、不生成 UUID。是否 flush/提交由事务调用方决定。 |
| `load_db_profile(source_id, job_id, clean=False) -> dict` | 保留既有 CLI 入口。仍自行规范化 UUID、加载 `.env` 与平台设置；调用共享前置函数，并将工作区错误包回原 `MetaLoadConfigError`。状态非成功仍返回 `success=False`（CLI exit 1），而非改为参数错误。随后复用读取与插入函数，自行生成 `publish_id`、提交；提交后才按现有规则执行可选 clean。既有返回字段、消息及退出码保持。 |

上述划分同时满足三个用途：**CLI** 非成功状态返回原任务失败；**预检** 将其呈现为不可勾选项；**发布 POST** 将其视为请求前提不满足。三者使用同一状态查询及路径/主文件就绪规则；CLI 与发布 POST 另外共用完整 JSON 校验，预检不解析 JSON。不在业务层维护第二套采集/加载逻辑，也不增加新的文件校验模块。

发布侧的最小函数清单：

| 函数/类型 | 位置与合同 |
| --- | --- |
| `check_db_output_ready(source_id, job_id) -> tuple[bool, str \| None]` | `backend/publishing/publish_service.py`，只调用 `resolve_db_profile_input_path()`：通过返回 `(True, None)`，捕获 `ProfileInputError` 时按 §7.2 以 WARNING 记录两个 ID 和受控具体原因，再一律返回 `(False, "产物不存在或不可用")`。不自行调用 `is_file/is_symlink` 重复规则，不读 JSON、不增加原因枚举、不匹配异常文本。 |
| `check_publication(settings, source_id, job_id) -> dict` | 同文件。规范化 UUID → 短会话调用 `inspect_db_profile_context()` → 关闭会话 → 检查目录 → 拼出预检响应。不生成 `publish_id`，不写入 `publish_info`。 |
| `normalize_publish_steps(steps: list[str]) -> list[str]` | 同文件。本阶段允许集合只有 `{'db'}`；检查空列表/未知名称并去重，不为尚未开发的步骤创建空加载器。 |
| `publish_steps(settings, source_id, job_id, steps) -> dict` | 同文件。按 §7.3 执行，调用共享输入函数和 `insert_db_profile()`；负责生成唯一的本次 `publish_id`、事务边界、失败记录和结果组装。 |
| `is_current_index_conflict(exc) -> bool` | 同文件中的纯函数。仅对 SQLAlchemy `IntegrityError` 检查其 `orig.sqlstate` 与 `orig.diag.constraint_name`；两者分别为 `23505`、`publish_info_current_idx` 时返回 True，否则（包括属性缺失）返回 False。不匹配异常文本、不访问数据库、不修改异常；两个事务异常分支共用此函数。 |
| `is_primary_key_conflict(exc) -> bool` | 同文件中的纯函数。仅对 SQLAlchemy `IntegrityError` 检查其 `orig.sqlstate` 与 `orig.diag.constraint_name`；SQLSTATE 为 `23505` 且约束名为 `publish_info_pkey` 或 `db_profile_pkey` 时返回 True，否则（包括属性缺失）返回 False。不匹配异常文本、不访问数据库、不修改异常；成功事务与独立失败事务共用，命中后按 §7.3 回滚并走既有 500 兜底，不补写失败记录。 |
| `UnsupportedPublicationStepError` / `PublicationStepNotReadyError` | 同文件，分别供 API 映射 `400 step_not_supported` / `400 step_not_ready`。不依赖 HTTP，也不将所有 `ValueError` 一概映射成某个业务错误。 |
| `PublicationConflictError` | 同文件，仅表达 `publish_info_current_idx` 唯一冲突；事务已回滚，供 API 映射 `409 publish_conflict`。不自动重试或补写发布行。 |
| `clear_current(session, source_id, step_name) -> None` | `backend/publishing/repository.py`，更新既有 current 行的标记和 `updated_at=func.now()`，不 commit。 |
| `insert_publish_row(session, publish_id, source_id, job_id, step_name, status, error_summary=None) -> PublishInfo` | 同文件，添加本次记录，`is_current_publish=True`、`created_by_user_id=None`；只显式传业务字段，不传 `created_at/updated_at`，由数据库默认值生成。不生成 UUID、不 commit，不修改旧行的业务字段。 |

发布服务的成功事务与失败事务都按“`clear_current()` → 添加新记录 → commit”执行；成功事务另外调用 `insert_db_profile()`，三次写操作共用同一 `Session`。失败事务开始前，成功事务须已经退出并回滚。**不得先调用完整 `load_db_profile()` 再补发布记录**：它已经自生成 ID、自提交，这样会破坏两表同 ID、同事务的合同。CLI 不写 `publish_info`，Web 服务不调用其清理分支。

Web 调用前先执行 `set_current_step('db')`，沿用当前 `db` 的日志分流，不新增一套日志系统。预检与发布只访问平台库和本地产物，不需要解密源库密码或读取 `SOURCE_CREDENTIAL_KEY`。

页面交互规则：

- 预检完成前、预检失败、没有可选步骤或正在执行时，“开始发布”不可用；只有当前 `publishable=true` 且被勾选的步骤进入请求体。“全选”只选可发布项，不启用域外步骤。
- 预检失败显示错误并提供重试；不可发布项灰色显示原因。预检成功后可用 `db` 才允许勾选，进入页面时不默认勾选，不把目录非空单独当作可发布依据。
- POST 等待期间显示“发布中”，禁用重复提交与修改选择。不做假进度条，也不照原型声明“实时进度”；请求返回后显示真实 `publish_id`、成功/失败数量、逐步骤消息与 `finished_at`。
- 200 响应仍检查 `results[].status`，不能统一显示“发布成功”。请求级错误不伪造发布 ID 或历史记录；重新预检后若步骤已不就绪，清除该项勾选。
- 发布后产物不被清理，可再次发布同一作业；每次显式点击都生成新的发布尝试，不复用此前 `publish_id`。不自动重试 POST。
- 收到 `409 publish_conflict` 时显示“发布发生并发冲突，请重新发布”，不伪造已落盘的结果或发布 ID；用户可再次显式提交。不增加锁定状态或后台重试功能。

### 7.6 API 模型与错误映射

请求路径参数由 FastAPI 解析为 UUID；JSON 响应中的 UUID 统一为小写、带连字符字符串。以下模型新增到已有 `backend/api/schemas.py`，不为本次另建一套 schema 模块：

| 模型 | 字段 |
| --- | --- |
| `PublishCheckStep` | `step_name: Literal['db']`、`job_status: Literal['running', 'success', 'failed'] \| None`、`output_ready: bool`、`publishable: bool`、`reason: str \| None`；各字段均返回。 |
| `PublishCheckResponse` | `source_id: str`、`job_id: str`、`steps: list[PublishCheckStep]`；本阶段只返回一个 db 项，缺该步骤行也必须返回该项。 |
| `PublicationCreateRequest` | `steps: list[str]`，必填，`extra='forbid'`；空列表由发布服务按 400 拒绝，格式/类型错误由请求校验按 422 拒绝。 |
| `PublicationStepResult` | `step: Literal['db']`、`status: Literal['success', 'failed']`、`message: str`、`finished_at: str`（UTC/Z，六位微秒）。 |
| `PublicationCreateResponse` | `publish_id: str`、`results: list[PublicationStepResult]`。不返回本地绝对路径或原始 JSON。 |

`PublishCheckStep.step_name` 与 `PublicationStepResult.step` 本阶段刻意限定为 `Literal['db']`，表达当前已实现的 API 能力；§2 的 DDL 不建步骤白名单，是为了未来扩展不必改表，两者不矛盾。新增发布步骤时，同步更新这两个响应模型、服务允许集合及前端对应类型，不仅放宽数据库字段便视为已支持。

`PublicationStepResult` 与既有 `CollectionJobStepResult` 分别表达发布结果与采集结果，保留独立模型：步骤结果分型的理由是 step 取值域不同，发布结果为 `Literal['db']`，采集结果为 `str`；不新增共享基类。外层响应分别使用 publish_id（`PublicationCreateResponse`）和 job_id（`CollectionJobCreateResponse`）。

在 `backend/api/errors.py` 按具体异常类型新增映射，复用现有 `ErrorResponse` 的 `{code, message}`，不靠中文消息字符串判断：

| 情形/异常 | HTTP 与 code | 记录行为 |
| --- | --- | --- |
| `MetaLoadSourceNotFoundError` | `404 not_found`，提示“数据源不存在” | 不生成发布 ID、不读产物。 |
| `WorkspaceMissingError` / `WorkspaceSourceMismatchError` | `404 not_found`，提示“作业不存在或不属于该数据源” | 同上；只影响这两种具体类型，不注册通用 `LookupError/ValueError` 处理器。 |
| `MetaLoadSourceDisabledError` | `409 source_disabled`，提示“该数据源已禁用，不能发布画像” | 同上；复用 doc 11 的错误码，不要求与采集提示逐字一致。 |
| `UnsupportedPublicationStepError` | `400 step_not_supported` | 空选择、非 db 或大小写不符；不产生发布记录。 |
| `PublicationStepNotReadyError` | `400 step_not_ready` | POST 执行前步骤未成功或缺记录；GET 预检则是 200 + 置灰，不抛此异常。 |
| `PublicationConflictError` | `409 publish_conflict` | 仅 `publish_info_current_idx` 唯一冲突；回滚本次事务，不补写失败记录、不自动重试，消息“发布发生并发冲突，请重新发布”。 |
| 发布记录或画像的主键冲突 | 既有 `500 internal_error` 兜底 | 回滚该步骤事务并停止本次请求；不重新生成 UUID、不自动重试、不补写失败记录，不影响此前已提交的数据。不新增异常类或错误码，沿用通用安全响应文案。 |
| `RequestValidationError` | 既有 `422 invalid_request` | 不进入发布业务；不记录请求原文。 |
| `PlatformUnavailableError` | 既有 `503 platform_unavailable` | 前置查询失败、或失败记录也无法提交；排除已单独识别的 current 索引冲突与主键冲突，不宣称发布结果已落盘。 |
| 文件/JSON 校验错误、可回滚的画像入库失败 | `200` + 步骤 `failed` | 排除 current 索引冲突及既定主键冲突；仅在独立失败事务成功落行后返回。输入读取/解析/校验的 message 与 error_summary 统一为“画像输入不可用或校验失败”，可回滚的画像入库失败统一为“平台库写入失败”。 |

分层保持为：路由（参数/响应）→ 发布服务（预检、事务编排）→ 共享加载函数与仓储。新路由从现有 `routers/data_sources.py` 单向导入只读的 `get_platform_settings()` 作为依赖，现有数据源路由不反向导入发布路由，避免循环；本阶段不为这一小函数新建 `dependencies.py`。

### 7.7 三条调用链

- 预检：GET 路由 → `check_publication(settings, source_id, job_id)` → `inspect_db_profile_context()` → `check_db_output_ready()` → 200 + 可选性与原因。
- 发布：POST 路由 → `asyncio.to_thread(publish_steps, settings, source_id, job_id, steps)` → 再次检查前提 → 新 `publish_id` → `read_db_profile_input()` → 成功事务（画像 + 发布记录）或独立失败事务 → 200 + 结果。
- CLI 回归：`meta_load_command()` → 既有 `load_db_profile()` → 共享前置/输入/插入函数 → CLI 自己提交画像 → 原有可选 clean；不经过 Web 发布服务、不写 `publish_info`。

### 9.3 必须覆盖的测试

| 场景 | 断言 |
| --- | --- |
| db 成功且有普通 `database.json` | GET 返回 200，`job_status='success'`、`output_ready=true`、`publishable=true`、`reason=null`；目录与文件未被修改。 |

| 空目录、目录不存在、仅子目录、仅隐藏标记/其他文件、主文件为目录/符号链接 | `output_ready=false`、不可选，产物原因固定为“产物不存在或不可用”；目录层符号链接、路径解析或访问失败同样拒绝并使用该提示。不创建目录、不读取链接目标，复用 resolver 的原有测试；若作业状态也未通过，最终展示 reason 仍按 §7.2 优先使用作业状态原因。 |
| 预检失败日志 | 用真实共享检查分别触发文件缺失、目录路径包含符号链接等失败；页面 reason 均为“产物不存在或不可用”，捕获到的 WARNING 日志含 source_id、job_id 和各自受控具体原因，可用于区分失败。日志不含凭据、连接串、完整 JSON 或驱动原文；不以文件存在代替实际日志内容断言。 |
| 预检与执行共用主文件规则 | 同一组临时文件用例分别调用 `resolve_db_profile_input_path()`、`check_db_output_ready()` 和 `read_db_profile_input()`；文件缺失、目录、符号链接在两条调用链都拒绝，普通文件均通过就绪检查。非法 JSON 的完整校验仅由实际读取执行；不替换共享检查函数来证明规则一致。 |
| 主文件存在但 JSON 非法 | GET 只做简单检查，可选；POST 完整读取/校验失败，按规则记录一次失败，不复制一套 JSON 校验。 |
| JSON 合法但其中 source_id 与请求不一致 | 以其他字段均合法的产物，仅将 JSON 的 source_id 改为另一个合法 UUID；请求的数据源与 job 归属保持正确。GET 简单预检仍可通过；POST 由真实 `_profile_fields()` 拒绝，返回 `200 + db failed`，提交带受控摘要的失败发布记录并按规则翻 current。不插入本次 `db_profile`，不修改另一数据源的画像或发布记录；不得用非法 JSON 或作业归属错误代替这一分支。 |
| 输入失败摘要一致性 | 文件缺失、路径不可用、读取 OSError、UnicodeError、JSONDecodeError 及内容 ProfileInputError，在 POST 中均记录 failed，message 与 error_summary 固定为“画像输入不可用或校验失败”；具体输入原因只用于日志排障。预检失败提示仍为“产物不存在或不可用”。不通过匹配异常文本或额外一次路径预检查来选择摘要；入库失败摘要另为“平台库写入失败”。 |
| 源或 job 不存在、归属不符、源被禁用 | GET/POST 返回约定 404/409；不生成 ID、不读文件、不添加画像或发布记录。 |
| 空选择、未知步骤、重复 db、错误请求形态 | 空/未知返回 400、形态或未知字段返回 422；重复 db 只执行一次。只有 db 被执行。 |
| 预检成功后状态变 failed/running | POST 再次查 `job_info`，返回 `400 step_not_ready`，不生成发布 ID、不写记录。 |
| 预检成功后文件被删除 | POST 前提仍成立则生成发布 ID，记录 failed；不能信任旧预检直接报成功。 |
| 发布成功 | 一次事务内翻旧、添加 success 记录与画像、提交；两表 ID 相同，旧标记与 updated_at 更新，job_info 不变，文件仍在。 |
| 画像提交失败 | 假会话模拟回滚后两表没有此次成功行，随后独立失败事务落行、翻旧，结果为 failed；不能只断言调用过 rollback 而保留假数据。 |
| 并发请求的结果提交顺序 | 不以请求开始时间或 ID 大小排序；后完成提交的失败记录可成为 current，先前成功画像保留，仍至多一行 current。可模拟不同提交顺序，不要求新增锁机制。 |
| current 索引冲突的纯函数判定 | 用真实 SQLAlchemy `IntegrityError` 包装只提供必要属性的底层异常替身，直接测试真实 `is_current_index_conflict()`；目标 SQLSTATE 与索引名匹配返回 True，其他索引（包括主键）、其他 SQLSTATE、缺失 orig/diag/属性及非 IntegrityError 返回 False。不需要构造 psycopg 内部诊断对象。 |
| 主键冲突的纯函数判定 | 用同一异常构造辅助函数直接测试真实 `is_primary_key_conflict()`；SQLSTATE 为 `23505` 且约束名为 `publish_info_pkey` 或 `db_profile_pkey` 分别返回 True。current 索引、其他约束名、其他 SQLSTATE、缺失 orig/diag/属性及非 IntegrityError 返回 False；两个判定函数不能互相误判，不构造 psycopg 内部诊断对象。 |
| 成功事务或独立失败事务发生 current 索引冲突 | 假会话只按场景抛出统一测试辅助函数构造的异常，不自行拼装驱动诊断属性、不替换 `is_current_index_conflict()` 返回 True。通过真实发布服务验证判定、事务回滚和 API `409 publish_conflict`；此次画像与发布行不落盘，不补写失败记录、不自动重试，其他已提交记录保持。其他约束冲突不能误走该分支。 |
| 成功事务或独立失败事务发生主键冲突 | 假会话抛对应主键约束名的真实 IntegrityError，通过真实 `is_primary_key_conflict()` 验证发布记录与画像两种冲突，不替换判定函数返回 True；该步骤事务回滚，API 仍返回既有 `500 internal_error`。向服务器传播的异常须为固定安全消息的内置异常，格式化堆栈不得包含测试 SQL 或参数；只检查响应正文或服务自身日志不够。不返回 409/503、不重新生成 UUID、不自动重试、不补写失败记录，其他已提交记录保持。 |
| 其他约束错误的事务阶段分流 | 用非唯一冲突（如 SQLSTATE `23514` 的 CHECK 违规）触发真实服务分支；成功事务失败后回滚，独立 failed 记录提交成功才返回 `200 + failed`、摘要“平台库写入失败”。若同类错误发生在独立失败记录事务，回滚并返回 `503 platform_unavailable`，不返回 200、不递归补写；不能误走 current 索引或主键冲突分支。 |
| 约束错误日志 | 复用上述真实服务分支的异常替身，覆盖 current 索引、两个指定主键及其他约束错误，并覆盖成功事务与独立失败记录事务。捕获实际 ERROR 日志，断言含 source_id、job_id、publish_id、step_name、正确事务阶段、异常类型、SQLSTATE 和对应约束名；缺失诊断属性记“未知”。在异常原文及 SQL 参数中放入特征明显的测试值，断言日志不含这些值或驱动原文，不以日志文件存在代替内容断言，不依赖 API 兜底日志证明服务已经记录。 |
| 前置平台查询失败或失败记录提交失败（非 current 索引冲突及主键冲突） | 503，不返回伪造的 200/已记录失败，不泄露驱动原文。 |
| 重复发布及 CLI 回归 | 每次显式发布生成不同 ID，画像不覆盖；CLI 自行加载不写发布表、不翻 current，CLI 的 `--clean` 成功后清理语义保持。 |

多步骤继续执行的规则已在 §5 确定，不留待另行选择：后续接入第二个及更多步骤时，须补“前一步失败且记录已提交，后一步仍执行”“results 覆盖全部已选步骤且顺序一致”“仅重发失败步骤不执行其他步骤”的回归用例。本阶段仍只测试已支持的 db 成功/失败结果，不为测试而提前接入其他类型或搭建通用加载框架。

测试只替换平台会话、源记录/作业记录和临时文件等外部边界；端到端 API 核心用例使用真实 `check_publication()` / `publish_steps()`。冲突测试的异常构造集中在测试辅助函数，底层异常替身只提供 `sqlstate` 和 `diag.constraint_name` 等必要属性；不修改 psycopg 内部对象，也不为测试新增生产异常体系。单独测试异常映射时可让服务抛真实的细分异常，但这种用例不能替代业务用例。假事务要分别维护待提交与已提交记录，支持回滚；不得用“返回固定成功 dict”的替身证明事务或预检有效。

## 10. 验收

表与模型：

1. 执行 §2 DDL 后，表与三个索引存在，`\d` 确认无外键；`PublishInfo` 模型与 DDL 的列、CHECK、主键一致。
2. 同一 `(source_id, step_name)` 插入第二条 `is_current_publish=true` 行被部分唯一索引拒绝；漏翻旧行的写入同样被拒绝；`status` 非法值、`step_name` 空白串被 CHECK 拒绝；同一 `publish_id` 的多个步骤行可以共存。

Web 发布（仅 `db`）：

3. 预检：`db` 步骤 `success` 且普通、非链接的 `database.json` 在 → `publishable=true`；`failed` / `running` / 已有作业缺 db 记录 / 目录为空或缺少主产物文件 → 不可勾选且 `reason` 明确；域外步骤置灰"暂不支持发布"。只有子目录或标记文件不算产物就绪。
4. 发布成功：一个事务内完成"翻旧 current + 插 `publish_info` 行 + 插 `db_profile` 行"，两表共用同一 `publish_id`；旧 current 行变 `false` 且 `updated_at` 前进；`job_info` 未被改动。
5. 发布失败（模拟文件缺失、解析或入库异常，排除 current 索引冲突及既定主键冲突）：画像与发布行都不留半行；`failed` 行带 `error_summary` 在独立短事务落盘并完成翻转；响应 `results` 含该步骤的 `failed`。
6. 请求级前置失败（数据源禁用 `409`、源或作业不存在/归属不符 `404`、所选步骤未采集成功 `400`）：不生成 `publish_id`、不留任何行。预检成功后再改变作业状态，POST 同样拒绝；预检成功后只删除文件，POST 则按执行失败规则落 failed 行。
7. CLI `metaweave meta_load --type db` 行为不变（既有测试全绿）；其画像行不写 `publish_info`、不改变任何 current。
8. 同一作业重复发布：新 `publish_id` 新行，旧行翻 `false`；`db_profile` 不覆盖旧行。可只选择需要重新发布的失败步骤，原尝试记录保持不变；本阶段只支持选择 db。
9. 前端发布页完成预检渲染、置灰原因、结果展示；无可选项时不能提交，全选不能勾选灰色步骤；HTTP 200 中的 failed 结果不显示为成功。`npm run typecheck` 与带 `VITE_API_BASE_URL` 的构建通过。
10. Web 发布不提供 clean、不清理目录、不连接源库、不修改 job_info；不需要源库密码解密密钥。先前 CLI 加载产生且没有发布记录的画像不被伪装成历史发布。
11. 平台库故障导致发布记录无法落盘时返回 `503 platform_unavailable`；平台库密码、源库凭据、驱动原文、完整 JSON 不出现在接口响应或 `error_summary` 中。
12. 不新增发布互斥锁；current 按结果记录提交顺序生效，成功、失败均可。成功事务或独立失败事务遇 `publish_info_current_idx` 冲突时回滚，返回 `409 publish_conflict`；不补写失败记录、不自动重试、不把该冲突误报成平台库不可用。本次事务未提交的画像与 current 修改不保留，其他已提交发布不受影响。指定主键冲突回滚后走既有 `500 internal_error`，不重新生成 UUID、不重试、不补写失败记录；通过 §9.3 的自动化测试验证，无需人工制造 UUID 碰撞。
13. 正常响应的 results 覆盖全部已选且去重的步骤，每步返回真实成败；本阶段仅一条 db 结果。后续多步骤接入必须遵循“单步失败记录提交后继续、不撤销其他成功步骤”的既定规则，不新增继续执行开关；请求级错误仍按 §5 与 §7.3 处理。

## 3. 安装平台字段的采集

### 3.1 候选方案对比

| 方案 | 能否给出平台 | 权限要求 | 12–19 可用性 | 结论 |
| --- | --- | --- | --- | --- |
| `SELECT version()` | 能：构建目标三元组 | 无。实测源库 `pg_proc.proacl` 为 `NULL`，即默认对 `PUBLIC` 开放执行权 | 全可用，见 §3.3 | **采纳** |
| `SHOW server_version` / `server_version_num` | 不能：只有版本号 | 无 | 8.2 起 | 已在用（提供 `server_version`），不用于平台 |
| `pg_config` 视图 | 不能稳定给出 | **默认仅超级用户可读**（官方文档 11/12 均明示；实测 `pg_class.relacl` 只有属主） | 11+ 存在 | 不采纳 |
| GUC 侧信道（`unix_socket_directories`、`dynamic_library_path` 等） | 不能：只能粗猜 | 无 | 可用 | 不采纳。实测本机 Windows 源库 `unix_socket_directories = ''`、`dynamic_library_path = '$libdir'`，与 Linux 默认值相同，区分不出平台 |
| 运行时探测（`COPY … FROM PROGRAM`、`pg_stat_file`） | 能，但仅 Linux | 超级用户 | Windows 不适用 | 不采纳 |
| 由使用方人工上报 | 不是源库事实 | — | — | 不采纳 |

`pg_config` 视图被否决还有一条实测依据：在真实 Windows 构建上它的内容也帮不上忙——本机源库（PostgreSQL 18.1 on Windows）上 `SELECT name, setting FROM pg_config WHERE name IN ('CONFIGURE','CC')` 返回 `CONFIGURE = ''`、`CC = 'cl'`，没有 host 三元组。

### 3.2 采纳方案与调用点

- 新增一次 `SELECT version()` 往返，与既有统计**共用同一条源库连接**，维持 `db_step` 模块「所有统计均基于同一次源库连接」的既有契约。它和 `SHOW server_version_num` 读的是同一时刻的同一个连接——**平台与版本号本来就是同一次读取**，这也是两者放在同一条链路上的原因。
- 不把 `version()` 合并进 `read_and_validate_server_version()`：该函数被登记与连接检查链路共用（`connection_check.py:14-15`、`scripts/register_db_source.py:29-30`），合并会让「服务端版本」这一事实出现第二处实现、并牵动本次不动的链路。多一次往返发生在同一连接上，代价可忽略。
- **解析放在采集端**（`db_step.py`）：加载端只做映射，前端只做展示。理由：解析规则与采集实现同步演进；doc 10 §3 明确加载端不做推断与补写，这个性质要保留。
- `SELECT version()` 失败时的精确语义（**前提是连接仍可用**）：两个字段写 `NULL` 并记一条 `warning`（只记异常类型与 `job_id`/`source_id`，不记连接参数），采集继续。理由：平台是附加展示字段，版本准入已由 `server_version_num` 保证；把可空展示字段的缺失升级为整步失败，等于给「补一个展示字段」引入新的失败源。
- **连接已失效时不适用上面的降级承诺**：本设计不引入重连；后续的对象统计/大小查询会按 `execute_db` 既有的阶段化失败语义让本次采集失败（错误消息标注阶段，如「schema 校验或对象统计失败」），不会因为「采集仍成功」的预期而掩盖问题。
- 因为原串入库，**解析规则日后升级可离线重算，无需重采源库**。

### 3.3 版本兼容性证据（PostgreSQL 12–19）

`version()` 的实现是单行返回编译期常量：

### 3.4 解析规则

官方文档对 `version()` 有一句必须遵守的警示（PG 12 §9.25 表 9.63、PG 19 §9.28.11 表 9.94 均如此）：

> Software developers should use `server_version_num` (available since 8.2) … instead of parsing the text version.

因此「解析」严格限定为**展示用途**：任何逻辑判断（版本准入、能力开关）继续用 `server_version_num`，任何时候都不得依赖 `os_platform`。

规则（纯函数 `normalize_os_platform(text) -> str | None`，返回**展示串**而不是结构化对象）：

1. 取首个 `on <token>` 段，正则 `\bon ([^\s,]+)`，大小写不敏感；`[^\s,]+` 在逗号处截止，可正确跳过打包后缀（实测样本：`PostgreSQL 18.6 (Debian 18.6-1.pgdg13+2) on x86_64-pc-linux-gnu, …` → `Linux x86_64`）。
2. 对 token 做 `casefold()` 后取两个维度：
   - **族名**：按下表**有序**匹配子串，首个命中即得族名；
   - **架构**：取 token 按 `-` 分段的**第 1 段**，仅当它落在架构白名单内才拼进展示串。
3. 族名匹配不到 → 整体返回 `NULL`，不猜。

| 命中子串（按判定顺序） | 族名 |
| --- | --- |
| `windows`、`mingw`、`cygwin` | `Windows` |
| `darwin` | `macOS` |
| `linux` | `Linux` |
| `freebsd` | `FreeBSD` |
| `openbsd` | `OpenBSD` |
| `netbsd` | `NetBSD` |
| `solaris`、`sunos` | `Solaris` |
| `aix` | `AIX` |
| 无 `on` 段、或 token 不含以上任何子串 | `NULL` |

架构白名单（首段命中其一才拼进展示串）：`x86_64`、`amd64`、`i386`/`i486`/`i586`/`i686`、`aarch64`、`arm64`、`armv6l`/`armv7l`/`armv8l`、`riscv64`、`s390x`、`ppc64`/`ppc64le`、`powerpc64`/`powerpc64le`、`sparc`/`sparc64`、`mips`/`mipsel`/`mips64`/`mips64el`、`loongarch64`、`rs6000`、`ia64`、`alpha`、`hppa`。

拼装：族名 + 空格 + 架构（有架构时），如 `Windows x86_64`；只解析出族名时只输出族名，如 `Linux`。白名单的作用是挡住没有架构段的三元组——`on linux-gnu` 的首段是 `linux`，不在白名单内，少了这一步会拼出 `Linux linux`。

其余约定：

- `Windows` 一类排在前面，避免 `x86_64-w64-mingw32` 之类三元组被后续规则误判。
- 已知反例（必须落 `NULL`，不许猜）：`PostgreSQL 12.3, compiled by Visual C++ build 1914, 64-bit`（部分 Windows 打包不含 `on` 段）。
- 解析函数**不改写原串**；`server_version_full` 始终原样保存，解析失败不影响它。
- 与原型示例的写法差异（D9 已定）：原型「安装平台」写的是 `windows x86`（小写、架构简写），本设计**定为** `Windows x86_64`（族名首字母大写 + 三元组首段的完整架构）。原型该处是示意值，不要求逐字一致，也不改这里的规则。
- 为什么不把族名与架构拆成两列：它是一次采集的**展示串**，与 `server_version` 同性质，页面上也是一个格子的一个值；拆列会把「有族名无架构」时的拼接歧义扩散到加载端和前端。将来若真要按族筛选，可从 `server_version_full` 离线派生或另加列。

上述规则与白名单已用 §3.3 的全部实测样本，外加边缘样本跑过一遍验证：`x86_64-pc-linux-musl` → `Linux x86_64`、`aarch64-apple-darwin23.2.0` → `macOS aarch64`、`x86_64-w64-mingw32` → `Windows x86_64`、`x86_64-pc-cygwin` → `Windows x86_64`、`powerpc64le-unknown-linux-gnu` → `Linux powerpc64le`、`sparc-sun-solaris2.11` → `Solaris sparc`、`rs6000-ibm-aix7.2.0.0` → `AIX rs6000`、`i386-unknown-openbsd7.4` → `OpenBSD i386`、`x86_64-unknown-freebsd13.2` → `FreeBSD x86_64`、`linux-gnu`（无架构段）→ `Linux`、`some-unknown-target` → `None`、`None`/空串 → `None`、`on ,`（缺 token）→ `None`。这些样本直接作为 §12 第 1 条的测试夹具。

### 3.5 与最低版本门槛的关系

现状门槛是 `MIN_POSTGRESQL_VERSION_NUM = 150000`（`db_step.py:20`），即 **PostgreSQL 15.0 及以上**才允许登记与 `db` 采集；PG 12/13/14 的源库今天在登记阶段就会被拒（doc 2 §4、doc 3 §4）。本设计**不改门槛**：新增字段在 12–19 都能采，但能不能连上源库仍由门槛决定。是否下调门槛是独立决策（§14 D1）；若下调，需另行核查全部采集 SQL 与其余元数据步骤的下限。

```python
_OS_ARCHES = frozenset({
    "x86_64", "amd64", "i386", "i486", "i586", "i686", "aarch64", "arm64",
    "armv6l", "armv7l", "armv8l", "riscv64", "s390x", "ppc64", "ppc64le",
    "powerpc64", "powerpc64le", "sparc", "sparc64", "mips", "mipsel",
    "mips64", "mips64el", "loongarch64", "rs6000", "ia64", "alpha", "hppa",
})
_OS_PLATFORM_RE = re.compile(r"\bon ([^\s,]+)", re.IGNORECASE)


def read_server_version_string(conn: psycopg.Connection) -> str | None:
    """读取 SELECT version() 原串；空结果返回 None。异常由调用方决定是否降级。"""
    with conn.cursor() as cur:
        cur.execute("SELECT version()")
        row = cur.fetchone()
    return row[0] if row and row[0] else None


def normalize_os_platform(version_string: str | None) -> str | None:
    """从 version() 原串解析安装平台展示串；族名解析不出返回 None。"""
    if not version_string:
        return None
    matched = _OS_PLATFORM_RE.search(version_string)
    if matched is None:
        return None
    token = matched.group(1).casefold()
    family = next((name for key, name in _OS_FAMILIES if key in token), None)
    if family is None:
        return None
    arch = token.split("-")[0]
    return f"{family} {arch}" if arch in _OS_ARCHES else family
```

## 6. 平台库变更（本次唯一需要执行的 SQL）

### 6.1 既有环境：直接执行

```sql
ALTER TABLE public.db_profile
    ADD COLUMN IF NOT EXISTS server_version_full text NULL,
    ADD COLUMN IF NOT EXISTS os_platform text NULL;

COMMENT ON COLUMN public.db_profile.server_version_full IS

COMMENT ON COLUMN public.db_profile.os_platform IS

-- 执行后核对：应返回 2 行
SELECT column_name, data_type, is_nullable
FROM information_schema.columns
WHERE table_schema = 'public'
  AND table_name = 'db_profile'
  AND column_name IN ('server_version_full', 'os_platform')
ORDER BY column_name;
```

- 只在 `state='ready'` 时返回 `profile`；其余状态 `profile` 为 `null`，页面用 `state` 分支，不靠 HTTP 状态码判断业务状态。
- 其他 HTTP 错误沿用 `backend/api/errors.py` 的既有映射：源不存在 404 `not_found`；平台库不可用 503 `platform_unavailable`；其余 500 `internal_error`。
- 响应里不带密码、密文、`sslmode` 等连接级选项（与画像入库口径一致）。
- `published_at` 取该行的 `publish_info.created_at`（与 `backend/publishing/listing.py:65` 对发布时间的既有口径一致：同一 `publish_id` 下多步骤行取 `max(created_at)`，这里是单行）；`collected_at` 用画像自己的采集时间，两者不混用。

### 8.4 接口与页面字段的取舍

- 「连接用户名」来自 `source.username`（`db_source_info` 的既有列，登记表当前值），不在 `profile` 内——避免让前端以为它是画像快照的一部分。
- `selected_schemas` **只出现在 `profile` 里**（该次采集的选中范围）：`source` 不再重复给出登记表的当前范围。同名字段带两种时间口径最容易混用——Schema 数量、计数标签、Schema 明细表全部取自 `profile`；要改登记范围走数据源编辑页，与画像无关。
- 统计数值与连接信息一律给原始值（`host`、`port`、`db_name`；派生值由前端算），只有 `db_type_label` 沿用资产目录的既有服务端派生。**不返回 `connection` 拼接串**：资产目录那份是 `host:port/db_name`，而画像页把 host、port、库名分在三个信息格，直接复用会显示成 `172.29.128.1:5432/orders` 与原型不符。
- 不在接口内做文案（`暂未提供`、`未知`、`整库`、`1 个 Schema`）——它们是展示层规则（§4 表）。`publish.published_at` 只用在失败态文案里（§8.3 状态表）。
- `publish.publish_id` **不展示**，用途只有两个：页面内容的渲染 key（重新发布后强制刷新）与排障时的版本标识；`profile.db_type` 是原始类型串（`postgresql`），保留给按类型上色/图标这类展示逻辑，展示文案一律用 `db_type_label`。除这两个外，响应里每个字段都能在 §4 表里找到对应卡片或说明行。

   - 发布动作：前端 `/data-sources/:sourceId/collection-jobs/:jobId/publish`，或 `POST /api/data-sources/{source_id}/collection-jobs/{job_id}/publications`，body `{"steps": ["db"]}`（先 `GET .../publish-check` 预检）。发布动作会 `clear_current` + 写 `publish_info(status='success', is_current_publish=true)` + 写 `db_profile`；
   - `GET /api/data-assets/<source_id>/profile` → `state='ready'`，`profile.os_platform = "Windows x86_64"`、`source.username = "postgres"`（登记表）；
   - 浏览器打开 `/data-assets/<source_id>/profile`：八个信息格、五张统计卡、Schema 表与合计行、底部分页与链接均按原型渲染，「安装平台」显示 `Windows x86_64`（悬停可见 `SELECT version()` 原串）、「连接用户名」显示 `postgres`。
   - ⚠️ 若库里**已有更早的成功发布**，未发布新画像前该接口会返回 `state='ready'` 但内容是**旧画像**（`os_platform` 为空）。这不是新字段失效，而是 current 仍指向旧发布；此时不能拿它当验收依据，必须先完成本步的发布。
5. 旧产物回归（§12 第 6 条）通过：删掉新键后 `meta_load` 仍成功且两列为 `NULL`；**再执行一次发布**后，画像页「安装平台」显示 `未知`（「连接用户名」来自登记表，不受旧画像影响）。
6. 未执行 §6.1 就升级代码的场景**不出现**在验收里：这条由 §11 第 0 步保证，若误操作应看到明确的列不存在失败，而不是静默 `NULL`。

### 14.1 D2 的取舍：为什么本次存画像表

你的判断是对的：**平台和版本号是同一次读取**——`SHOW server_version_num` 与 `SELECT version()` 在同一连接、同一时刻完成，采集端"顺带"拿到它没有额外代价（§3.2）。所以「能不能同步获取」不是分歧点。

分歧点在**取值时刻**，它决定了页面能不能用：

1. **画像页要的是"该次采集"的值**。页面上的库名、连接信息、大小、表数、采集时间全部来自那一次发布的 `db_profile`。若「安装平台」只存在 `db_source_info`，页面就只能显示"当前登记值"——同一张卡片里混进两个时间坐标：一个是"9 月 22 日采集时的事实"，另一个是"现在登记表里的值"。库迁移（Windows → Linux）或改连接之后，页面会自相矛盾，而且无从判断哪个对。
2. **这正是既有表结构的做法**。`host`、`port`、`db_name`、`server_version` 都是**两张表各存一份**，语义分别是"该次采集时"与"登记时"——`db_profile.host` 是采集快照，`db_source_info.host` 是当前配置。安装平台与它们完全同类，放进 `db_profile` 是沿用既有模式，不是新发明。
3. **`db_source_info` 侧将来要加也不冲突**。同一连接能读到 `version()`（你说的对），所以后续要「不采集就能在数据源管理侧看到平台」时，按同样的解析规则往 `db_source_info` 加一列即可；那时它的语义是**登记或改连接时实测到的平台**，与画像那份互不覆盖，也**依然不得用来补填画像**（doc 2 §4 的既有禁令）。触发条件与改动面见 §14.2。
4. **本次的交付目标决定了先做哪边**。本次要开发的是数据库画像页，登记侧的展示不在本次范围内；反过来，若只做登记侧、画像侧不做，页面反而没数据可显示。

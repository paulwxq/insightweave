## 执行方式说明

MetaWeave 支持两种执行方式，效果完全一致：

### 方式一：`uv run`（推荐）

无需手动激活虚拟环境，`uv` 会自动管理。

```bash
uv run metaweave <子命令> [参数]
python -m metaweave.cli.main <子命令> [参数]
```

### 方式二：激活虚拟环境后直接运行

需要先激活对应环境，之后可直接调用 `metaweave` 或 `python -m metaweave.cli.main`。

```bash
# 虚拟环境统一为项目根目录下的 .venv（uv sync 自动创建，git 忽略）

# WSL / Linux 环境
source .venv/bin/activate

# Windows 环境（PowerShell）
.venv\Scripts\Activate.ps1

# Windows 环境（CMD）
.venv\Scripts\activate.bat
```

激活后可用以下两种等价方式执行：

```bash
# 直接调用入口命令（推荐）
metaweave <子命令> [参数]

# 或通过 python -m 调用
python -m metaweave.cli.main <子命令> [参数]
```

> 后续文档中各步骤命令块同时列出三种方式：**`uv run`、`metaweave`、`python -m metaweave.cli.main`**。

## 步骤依赖与数据流向

### 执行轨道（无自动编排，手动按序执行单步命令）

```
生成轨道（单步命令按需组合；LLM 增强由配置驱动，内建于各步骤）：
  --step ddl ──► --step json ──► --step md ──► --generate-domains ──► --generate-dim-config
   ──► --step rel ──► --step cql ──► --generate-sql-rag（生成 + EXPLAIN 校验一体，
     由 sql_rag.validation.enabled 控制，默认开启）

加载轨道（统一入口 rag_load，--type 必选）：
  rag_load --type <t> [--clean]                    # 单类加载
  rag_load --type all [--clean] [--continue-on-error]
                                    # 依序四类：sql → table_schema → dim_value → cql
                                    # 默认首个失败即停止；--continue-on-error 显式继续
```

---

### 各步骤 / 命令输入 / 输出 / 依赖一览

| 步骤 | 读取（输入） | 写入（输出） | 需要 PostgreSQL | 需要 LLM |
|------|------------|------------|:--------------:|:--------:|
| `ddl` | PostgreSQL（直接查库） | `output/ddl/*.sql` | ✅ | ❌ |
| `json` | `output/ddl/*.sql`（结构）+ PostgreSQL（COUNT/采样）；LLM 注释/分类开启时（`json_generation.*.llm_enabled`）另用 LLM | `output/json/*.json` | ✅ | 开启增强时 |
| `md` | `output/json/*.json` | `output/md/*.md` | ❌（完全 file-only） | ❌ |
| `metadata --generate-domains` | `output/md/*.md` + 可选 `--description` | `output/domains/db_domains.yaml` | ❌ | ✅ |
| `rel` | `output/json/*.json` + PostgreSQL（采样验证）；LLM 候选开启时（`relationships.llm_candidates.enabled`，默认 true）另用 LLM | `output/rel/*.json` + `.md` | ✅ | 开启候选时 |
| `cql` | `output/json/*.json` + `output/rel/*.json` | `output/cql/*.cypher` + `.md` | ❌（完全 file-only） | ❌ |
| `metadata --generate-sql-rag` | `output/domains/db_domains.yaml` + `output/md/*.md`；校验启用时连 PostgreSQL；启用修复时额外读取 `output/rel/*.md` | `output/sql-rag/qs_{db}_pair.json` + 校验日志（修复时原地回写该文件） | 校验启用时 | ✅（修复时二次使用） |

> LLM 增强内建于 `json` / `rel` 步骤（配置驱动），不存在独立的 `json_llm` / `rel_llm` 命令（已随编排移除，docs/update/25）。

---

### 步骤间强依赖关系

```
ddl ──► json        （读 output/ddl/*.sql + 查库；LLM 注释/分类由
          │             json_generation.*.llm_enabled 配置驱动）
          ├──► md     （读 output/json/*.json，file-only，不查库、不读 DDL）
          │     └──► metadata --generate-domains   （读 output/md/*.md，写 output/domains/db_domains.yaml）
          │            └──► metadata --generate-sql-rag
          │                  （读 output/domains/db_domains.yaml + output/md/*.md；
          │                    校验默认随后自动执行，修复时另读 output/rel/*.md）
          │                          └──► rag_load --type sql
          └──► rel     （读 output/json/*.json + 查库；LLM 候选由
                        relationships.llm_candidates.enabled 控制，默认开）
                ↓
               cql      （读 output/json/*.json + output/rel/*.json）
```

**关键约束**：

- `json` 依赖 `output/ddl/` 非空；若 DDL 目录为空则直接报错退出。`md` 依赖 `output/json/` 下有当前库的 JSON 产物；缺失时前置检查报错并提示先执行 `--step json`（无 DDL 回退）。
- `metadata --generate-domains` 依赖 `output/md/` 非空；推荐使用 `--description` 与 `--md-context-mode full` 提高生成质量。
- `metadata --generate-sql-rag` 依赖 `output/domains/db_domains.yaml` 与 `output/md/`；任一缺失时命令以友好错误终止并提示先执行 `--generate-domains` / `--step md`（显式传入 `--domains-config` 指向不存在的文件时，由 click 在参数解析阶段快速失败）。
- 校验默认随生成自动执行（`sql_rag.validation.enabled=true`，默认值）；置 `false` 可跳过校验（此时不创建数据库连接）；`enable_sql_repair=true` 时校验段额外依赖 `output/rel/*.md` 作为修复上下文。
- `md`、`rel`、`cql` 不依赖 DDL 文件，只依赖 JSON 文件。
- `md` 与 `cql` 完全 file-only，不需要数据库连接。

---

### `load` 命令的输入依赖

| 加载类型 | 读取来源 | 前置步骤 |
|---------|---------|---------|
| `rag_load --type cql` | `output/cql/import_all.*.cypher` | `cql` |
| `rag_load --type dim_value` | PostgreSQL 维度表（直接查库） | 无文件依赖 |
| `rag_load --type table_schema` | `output/md/*.md` + `output/json/` | `md` 步骤 + `json` 步骤 |
| `rag_load --type sql` | `output/sql-rag/qs_{db}_pair.json` | `metadata --generate-sql-rag` |

> `rag_load --type table_schema` 默认读取 `output/json`，且按“MD 文件名同名 JSON（仅扩展名不同）”匹配输入。

## 一、`metadata` 命令

### 公共参数

| 参数 | 简写 | 默认值 | 说明 |
|------|------|--------|------|
| `--config PATH` | `-c` | `configs/metadata_config.yaml` | 配置文件路径 |
| `--step STEP` | 无 | 无（必填，或使用 --generate-* 模式；**仅允许传入一次**） | 执行步骤：ddl/json/cql/md/rel；不传 step 且无 --generate-* 时报错；重复传入报错 exit 2 |
| `--schemas TEXT` | `-s` | 全部 schema | 目标 schema，逗号分隔 |
| `--tables TEXT` | `-t` | 全部表 | 目标表名，逗号分隔 |
| `--max-workers N` | `-w` | `4` | 最大并发数（必须为正整数；0/负数 → 参数错误 exit 2） |
| `--clean` | 无 | false | 执行前清理目标目录顶层所有文件（不限扩展名、不递归、保留子目录）；适用于全部 step 与三个 --generate-* 模式 |

### 业务域生成：`--generate-domains`

**需要**：LLM API + Markdown 摘要文件
**依赖**：`output/md/` 目录下有 `.md` 文件（通常需先执行 `--step md`）
**输出**：`output/domains/db_domains.yaml`（默认）

该命令基于现有的 Markdown 摘要，利用 LLM 自动推断数据库的业务主题（Domains）分类及数据库描述。

```bash
# 方式 A：uv run (推荐)
uv run metaweave metadata --generate-domains

# 方式 B：python -m 调用
python -m metaweave.cli.main metadata --generate-domains

# 推荐：配合数据库描述和完整 md 上下文执行
uv run metaweave metadata --generate-domains \
  --description "这是一个DVD影片租赁连锁店的数据" \
  --md-context-mode full
metaweave metadata --generate-domains \
  --description "这是一个DVD影片租赁连锁店的数据" \
  --md-context-mode full
python -m metaweave.cli.main metadata --generate-domains \
  --description "这是一个DVD影片租赁连锁店的数据" \
  --md-context-mode full
```

**可用参数列表**：

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `--generate-domains` | (必填标志) | 启用业务域生成模式，完成后直接退出 |
| `--domains-config PATH` | `output/domains/db_domains.yaml` | 生成结果的保存路径 |
| `--description TEXT` | 无 | 可选：提供数据库背景补充说明，辅助 LLM 推断 |
| `--md-context-mode` | `name_comment` | 摘要模式：`name`(仅表名), `name_comment`(表名+首行), `full`(全文) |
| `--md-context-dir PATH` | `output/md` | Markdown 摘要文件的来源目录 |
| `--md-limit N` | `100` | 读取的 Markdown 文件数量上限 |

**需要**：仅文件（无需数据库连接）
**依赖**：`output/json/` + `output/rel/` 目录下有对应文件
**输出**：`output/cql/import_all.{db}.cypher` 和 `.md`

### Step：`md` — 生成 Markdown 文档

**需要**：仅文件（**无需数据库连接**，完全 file-only）
**依赖**：`output/json/` 目录下有当前库的 JSON 产物（`{db}.{schema}.{table}.json`；从 JSON 还原表结构、约束与类型化样本数据）
**输出**：`output/md/{db}.{schema}.{table}.md`

> **说明**：`md` 步骤在代码中明确跳过数据库连接，直接读取 JSON 产物生成 Markdown；JSON 缺失或版本不符时整步报错，不回退读 DDL（doc 17）。

```bash
# uv run
uv run metaweave metadata -c configs/metadata_config.yaml --step md

# 激活环境后
metaweave metadata -c configs/metadata_config.yaml --step md
python -m metaweave.cli.main metadata -c configs/metadata_config.yaml --step md
```

### 全流程执行（`standard` 编排已移除）

> **命令移除说明**（docs/update/25）：`--step standard` 五步串行编排已移除，
> 无等价单命令。按需逐个执行单步命令（上游产物缺失时由各单步自检报错）：
>
> | 序号 | 单步命令 | 说明 |
> |------|---------|------|
> | 1 | `metadata --step ddl` | 提取 DDL |
> | 2 | `metadata --step json` | 数据画像（LLM 注释/分类由 `json_generation.*.llm_enabled` 配置驱动） |
> | 3 | `metadata --step md` | Markdown 文档（读 JSON 产物，doc 17） |
> | 4 | `metadata --generate-domains` | 业务域配置（按需） |
> | 5 | `metadata --generate-dim-config` | 维表配置（按需；生成后需人工填写 embedding_col） |
> | 6 | `metadata --step rel` | 关系发现（LLM 候选由 `relationships.llm_candidates.enabled` 控制） |
> | 7 | `metadata --step cql` | Neo4j CQL 脚本 |
> | 8 | `metadata --generate-sql-rag` | Question-SQL 样例 + EXPLAIN 校验 |
>
> 各单步可带 `--clean`（清理该步输出目录顶层文件、保留子目录）。

## 二、Question-SQL 样例：`metadata --generate-sql-rag`

基于现有表结构文档（md）与业务主题域配置（db_domains.yaml），生成 Question-SQL 样例，并按配置自动执行 SQL EXPLAIN 校验与可选 LLM 修复。

> **命令迁移说明**（原 `sql-rag` 命令组已整组移除）：
>
> | 旧命令 | 迁移去向 |
> |---|---|
> | `sql-rag generate` | `metadata --generate-sql-rag`（生成段） |
> | `sql-rag validate` | `metadata --generate-sql-rag`（校验段，由 `sql_rag.validation.enabled` 控制是否执行） |
> | `sql-rag run-all` | 拆解为 `metadata --generate-sql-rag` + `rag_load --type sql` 两步 |
> | `sql-rag load` | `rag_load --type sql` |

### 前置依赖

| 读取来源 | 前置条件 |
|------|---------|
| `output/domains/db_domains.yaml` | 需先执行 `metadata --generate-domains` |
| `output/md/*.md` | 需先执行 `metadata --step md` |
| PostgreSQL（校验启用时） | 校验段连接数据库执行 EXPLAIN |
| `output/rel/*.md`（启用修复时） | 需先执行 `metadata --step rel` 生成关系文档 |

### 参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `--generate-sql-rag` | (必填标志) | 启用生成（+可选校验）模式，完成后直接退出 |
| `--config PATH` / `-c` | `configs/metadata_config.yaml` | 主配置文件 |
| `--domains-config PATH` | `output/domains/db_domains.yaml`（由 `output.domains_directory` 决定） | 业务域定义文件路径 |
| `--md-context-dir PATH` | `output.md` 对应目录（优先级：CLI 显式 > `output.markdown_directory` > `output.output_dir/md` > `output/md`） | md 表结构文档目录（生成与校验共用） |
| `--clean` | false | 生成前删除当前库旧样例文件 `qs_{db}_pair.json` |

### 校验行为配置（`sql_rag.validation` 段）

| 配置键 | 默认值 | 说明 |
|--------|--------|------|
| `enabled` | `true` | 校验总开关。`false` 时生成后跳过校验，且**不创建数据库连接** |
| `enable_sql_repair` | `false` | 无效 SQL 是否触发 LLM 修复（仅从配置读取，无 CLI 覆盖）；修复失败条目会从 pair 文件删除 |
| `sql_validation_max_concurrent` | `5` | 并发校验线程数 |
| `timeout` | `30` | 单条 SQL 执行超时（秒） |
| `sql_validation_readonly` | `true` | 只读校验（只读事务执行，防止 SQL 误写库） |
| `sql_validation_max_retries` | `2` | 校验失败/超时后的最大重试次数 |
| `repair_batch_size` | `1` | LLM 修复时每批送修条数 |

> ⚠️ **质量门禁**：`enable_sql_repair=false` 且校验发现无效 SQL 时，命令以**非 0 退出**（对齐 pipeline sql-rag-validate 步骤）——因为 `rag_load --type sql` 不校验 SQL 有效性，无效 SQL 会原样进入向量库。逃生口：`enabled: false`（完全跳过校验）或 `enable_sql_repair: true`（修复失败条目自动删除，落盘文件全有效）。

### 示例

```bash
# 推荐：清理旧样例后重新生成 + 自动校验（enabled 默认 true）
uv run metaweave metadata --generate-sql-rag --clean

# 只生成不校验（需在 yaml 中置 sql_rag.validation.enabled: false）
uv run metaweave metadata --generate-sql-rag

# 显式指定域配置与 md 目录
uv run metaweave metadata --generate-sql-rag \
  --domains-config output/domains/db_domains.yaml \
  --md-context-dir output/md

# 生成校验完成后加载到 Milvus
uv run metaweave rag_load --type sql
```

## 三、`rag_load` 命令 — RAG 数据统一加载

> **命令语义**（docs/update/24 重构 + docs/update/27 修订）：`--type` **必选**
> （仅允许传入一次）：单类或 `all`（依序 `sql → table_schema → dim_value → cql`，
> 前三类清/写 Milvus collection，cql 清/写 Neo4j 整库）。
> **默认首个失败即停止**（汇总含 ⏭️ 未执行）；`--continue-on-error` 显式开启
> 继续模式；任一失败最终退出码非 0。裸调用（无 `--type`）→ 中文报错 exit 2。

### 参数

| 参数 | 简写 | 默认值 | 说明 |
|------|------|--------|------|
| `--type TYPE` | `-t` | 无（**必选，仅允许传入一次**） | `sql` / `table_schema` / `dim_value` / `cql` 单类，或 `all` = 依序加载全部四类；重复传入 → 报错 exit 2 |
| `--config PATH` | `-c` | `configs/metadata_config.yaml` | 主配置文件（读取其 `loaders` 段） |
| `--clean` | 无 | false | 每类加载前先清空目标库（Milvus 删除重建 collection / cql 清空 Neo4j 整库；⚠️ 不可逆）。`--clean` 下失败与 ⏭️ 未执行类型均在汇总附补跑提示 |
| `--continue-on-error` | 无 | false | 单类失败后继续加载其余类型（默认首个失败即停止）；仅 `all` 有意义，单类型下忽略并告警 |
| `--debug` | 无 | false | 开启调试模式 |

### 加载类型

| `--type` | 目标数据库 | 数据来源 |
|----------|-----------|---------|
| `sql` | Milvus（向量数据库） | `output/sql-rag/qs_{db}_pair.json`（未配置 `sql_loader.input_file` 时自动推断） |
| `table_schema` | Milvus（向量数据库） | `output/md/` + `output/json/` |
| `dim_value` | Milvus（向量数据库） | PostgreSQL 维度表（直接查库；需 `dim_tables.yaml` 中 `embedding_col` 已人工填写） |
| `cql` | Neo4j（图数据库） | `output/cql/import_all.*.cypher` |
| `all` | 上述全部 | 按上表顺序依序加载四类 |

> ⚠️ **`rag_load --type cql` 通配符唯一性**：输入文件通过 `output/cql/import_all.*.cypher` 匹配，**必须有且只有一个匹配文件**，多个文件匹配时会直接失败。若切换过数据库或重复执行 `cql` 步骤，请先清理 `output/cql/` 中多余的 `.cypher` 文件。
>
> ⚠️ **向量 Loader 配置要求**：
> - `metadata_config_file` 建议在配置 `loaders` 段显式配置（未配置时代码默认回退 `configs/metadata_config.yaml`）。
> - `dim_loader.collection_name`、`table_schema_loader.collection_name` 与 `sql_loader.collection_name` 是必填项；缺失会直接报错并终止。

```bash
# uv run —— 加载全部四类（前三类 → Milvus，cql → Neo4j），各自先清后载
uv run metaweave rag_load --type all -c configs/metadata_config.yaml --clean

# 失败后继续加载其余类型
uv run metaweave rag_load --type all --clean --continue-on-error

# 单类加载
uv run metaweave rag_load --type sql -c configs/metadata_config.yaml --clean
uv run metaweave rag_load --type cql -c configs/metadata_config.yaml --clean

# 激活环境后（python -m 常用示例）
metaweave rag_load --type all --clean
metaweave rag_load --type sql --clean
python -m metaweave.cli.main rag_load --type cql --clean
```

## 四、`metadata --generate-dim-config` — 生成维度表配置

从 `output/json` 扫描 `table_category='dim'` 的表，生成 `dim_tables.yaml`（原顶层命令 `dim_config --generate` 已移除）。

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `--generate-dim-config` | false | 执行生成操作（与 `--generate-domains`/`--domain`/`--cross-domain` 互斥） |
| `--config PATH` | `configs/metadata_config.yaml` | 元数据配置文件 |
| `--dim-config PATH` | 由 `loaders.dim_loader.config_file` 决定（默认 `output/dim_config/dim_tables.yaml`） | 输出文件路径 |
| `--clean` | false | 写入前清理 dim_config 目录下的**顶层文件**（如旧的 `dim_tables.yaml`、`*.bak_*` 备份），**保留子目录** |

> ⚠️ **前置条件（重要）**：`--generate-dim-config` 读取 `metadata_config.yaml` 中的 `output.json_directory`，
> 并扫描该目录下的 `*.json` 文件来识别 `table_profile.table_category='dim'` 的维表。
> 生成文件结构为 `databases.<database>.tables.<schema.table>`；`load --type dim_value` 仅加载当前数据库节点。

```bash
# uv run
uv run metaweave metadata --generate-dim-config \
  -c configs/metadata_config.yaml

# 激活环境后
metaweave metadata --generate-dim-config \
  -c configs/metadata_config.yaml
python -m metaweave.cli.main metadata --generate-dim-config \
  -c configs/metadata_config.yaml
# 显式指定输出路径
python -m metaweave.cli.main metadata --generate-dim-config -c configs/metadata_config.yaml --dim-config output/dim_config/dim_tables.yaml
```

> 生成后需**手动填写** `embedding_col` 字段（指定要向量化的列名）。
> ⚠️ 重新执行本命令会**覆盖整个文件**，已人工填写的 `embedding_col` 将被重置（文件受 git 跟踪，可从版本库恢复）。

## 五、`pipeline` 命令 — 配置驱动编排

> **命令说明**（docs/update/26）：旧 `pipeline generate/load` 与
> `metadata --step standard` 已由 docs/update/25 移除；本节描述**重新引入的**
> 配置驱动编排命令——只编排既有单步命令，不恢复旧参数与隐式流程。
> pipeline 自身只有两个选项：`--config/-c` 与 `--continue-on-error`；
> **选项必须写在最终实际执行的命令之后**（`pipeline -c x.yaml metadata`
> 为参数错误 exit 2）。

### 配置文件

pipeline 读取独立的 `configs/pipeline.yaml`，其中的 `metadata_config`
指向实际使用的主配置（省略时默认 `configs/metadata_config.yaml`）。
相对路径（含 `--config` 与 `metadata_config`）均基于**项目根目录**解析。
`pipeline.yaml` 本身不执行 `${ENV}` 替换（按普通字符串处理）；被引用的
主配置仍保留既有环境变量处理。

仓库交付三份模板：

| 文件 | 用途 |
|------|------|
| `configs/pipeline.yaml` | 日常安全默认：只含 metadata 主流程，不含 generate-domains/dim-config、任何 rag_load 任务或 `clean: true` |
| `configs/pipeline_init.yaml` | 一次性 domain/dim 初始化（⚠️ 会覆盖 `db_domains.yaml`、`dim_tables.yaml` 及人工 `embedding_col`） |
| `configs/pipeline_dim.yaml` | 维度值两阶段专用（**不是**通用 rag_load 模板） |

### 步骤键

`metadata` 章节（步骤键区分大小写，必须小写）：

| 步骤键 | 实际调用 |
|------|------|
| `ddl` / `md` / `json` / `rel` / `cql` | `metadata --step <key>` |
| `generate-domains` | `metadata --generate-domains` |
| `generate-dim-config` | `metadata --generate-dim-config` |
| `generate-sql-rag` | `metadata --generate-sql-rag` |

`rag_load` 章节：`sql` / `table_schema` / `dim_value` / `cql`
（每个键对应一次明确类型的加载，不支持 `all`）。

### 选项

所有步骤支持 `clean: true/false`（必须是**未加引号的小写**字面量；
`yes`/`on`/`True`/`"true"`/`null` 等一律配置错误）。
`generate-domains` 额外支持 `description`、`md_context_mode`
（仅 `name`/`name_comment`/`full`）、`md_limit`（正整数）。
不支持任何路径覆盖键（`md_context_dir`/`domains_config`/`dim_config_path` 均报错）。

### 执行规则

- **固定顺序**：metadata 按
  `ddl → json → md → generate-domains → generate-dim-config → rel → cql → generate-sql-rag`，
  rag_load 按 `sql → table_schema → dim_value → cql`；YAML 书写顺序不参与调度；
- **完整性告警**：metadata 主流程（ddl/md/json/rel/cql）缺步骤仅告警不阻断；
  `generate-*` 与 rag_load 不参与统计；
- **失败语义**：默认失败即停（剩余任务标 `⏭️ 前序任务失败`）；
  `--continue-on-error` 记录失败后继续（唯一主动跳过：同次计划中
  `generate-sql-rag` 实际失败时阻断 `rag_load.sql`，避免未校验 SQL 进入 Milvus）；
- **dim 冲突**：裸 `pipeline` 同次计划不得同时含 `metadata.generate-dim-config`
  与 `rag_load.dim_value`（配置错误 exit 2）；用章节子命令分两次运行；
- **退出码**：0 全部成功；1 任一任务失败；2 参数/配置/计划错误（均发生在
  首个任务之前，`--continue-on-error` 不改变）；
- **clean 预警**：执行前一次性输出本次计划中全部 `clean: true` 任务的真实目标
  （绝对目录 / Milvus endpoint+collection / Neo4j 脱敏 URI+database），
  不泄露认证信息；`clean: true` 的失败或未执行任务在汇总中附单任务补跑命令。

```bash
# 裸命令：依次执行 metadata + rag_load 两章节
uv run metaweave pipeline

# 仅执行 metadata 章节（维度值两阶段的第一步）
uv run metaweave pipeline metadata -c configs/pipeline_dim.yaml

# 人工填写 embedding_col 后，仅执行 rag_load 章节
uv run metaweave pipeline rag_load -c configs/pipeline_dim.yaml

# 失败后继续
uv run metaweave pipeline --continue-on-error

# 调试（根级 --debug 写在 pipeline 之前）
uv run metaweave --debug pipeline rag_load
```

> ⚠️ `metaweave pipeline`（裸命令，使用默认 `configs/pipeline.yaml`）只运行
> metadata 主流程；`metaweave pipeline rag_load` 因默认文件不含加载步骤而以
> exit 2 报错并提示 `-c` 指定自定义配置。

## 七、关键注意事项

| 注意点 | 说明 |
|--------|------|
| LLM 注释/分类内建于 `--step json` | 由 `json_generation.*.llm_enabled` 配置驱动，原地写入 `output/json/`（`json_llm` 独立步骤已随 pipeline 移除） |
| `rel` 读取 `output/json/` | 旧版 `json_llm_directory`（`output/json_llm/`）已废弃，与 json 共用同一目录 |
| `md` 步骤完全 file-only | **不需要数据库连接**，从 JSON 产物读取（`output/json/*.json`，须在 `--step json` 之后执行，doc 17） |
| `rag_load --type cql` 通配符唯一性 | `output/cql/import_all.*.cypher` 必须恰好匹配一个文件，多个/零个均失败，需手动清理 |
| `--generate-dim-config` 输出按数据库分组 | 生成 `databases.<database>.tables` 结构；`dim_value` 仅读取当前数据库节点 |
| 加载统一走 `rag_load` | 默认四类（sql/table_schema/dim_value/cql）；`--type` 可指定单类（见第三节） |
| `metadata --generate-sql-rag` 依赖 `db_domains.yaml` + `output/md/` | 需先执行 `metadata --generate-domains` 与 `metadata --step md`；生成与校验已合并（原 sql-rag 命令组已移除） |
| `--generate-sql-rag` 修复依赖 `output/rel/` | `enable_sql_repair=true` 时，校验段读取关系 Markdown 作为修复上下文 |
| `--generate-sql-rag` 校验质量门禁 | `enable_sql_repair=false` 且存在无效 SQL 时非 0 退出，防止无效 SQL 进入向量库；可用 `sql_rag.validation.enabled=false` 跳过校验（跳过时不建 DB 连接） |
| 调试模式 | 子命令前加 `--debug`，例如：`uv run metaweave --debug metadata ...` |
| `pipeline` 选项位置 | `--config`/`--continue-on-error` 必须写在最终执行的命令之后；写在 `pipeline` 与子命令之间为参数错误 exit 2 |
| `pipeline` 默认配置限制 | 默认 `configs/pipeline.yaml` 只含 metadata 主流程：裸 `pipeline rag_load` 会 exit 2 并提示用 `-c` 指定自定义配置 |
| clean 预警的 Milvus 目标 | 与 loader 实际使用一致：取 `vector_database.providers.milvus` 的 host/port/database（host 非空、port 1..65535、database 缺省即 Milvus 默认库）；根级 `vector_database.database` 无消费者、不参与解析 |
| clean 目标安全限制 | 清理目标必须是项目根内的**严格子目录**：越界、以及 `"."`/空串/项目根路径等解析为项目根本身的取值一律拒绝（防止误删根目录顶层文件） |
| 独立 CLI 相对路径统一 | 主配置相对路径（输出/输入/clean 目标）均基于项目根目录解析，与进程 cwd 无关（docs/update/26） |
| `--md-limit` 显式值 | `--generate-domains` 的显式 `--md-limit` 必须为正整数（0/负数 exit 2，不再静默钳制为 1） |
| 虚拟环境统一为 `.venv` | 项目根目录单一 `.venv`（`uv sync` 自动创建、git 忽略）；跨系统重建时删除后重新 `uv sync --all-extras` 即可 |
